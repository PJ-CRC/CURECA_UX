## 1. 업데이트 배포 (기능 수정 · 추가를 모두에게 반영)

### 목표
Workbench 기능을 고치거나 추가하면, 다른 사람들이 압축 파일을 다시 받지 않아도 최신 버전을 쓰게 한다.

### 정한 방향
- **로컬 서버 방식은 그대로 둔다.** 요청 등록 · 캡처 · 시작 안내 · 프로젝트 전환이 로컬 서버(`/api/...`)에 의존하기 때문이다.
- 압축 배포 대신 각 PC에 **비공개 깃 저장소를 받아(clone) 두고**, **Figma AI Run을 실행할 때마다 `git pull`** 로 최신을 받은 뒤 서버를 띄운다.
- 깃허브 페이지는 보기 전용 공유가 필요할 때만 따로 검토한다. 기본이 공개 페이지라 CURECA 화면이 외부에 노출된다.

### 할 일
| 대상 | 내용 |
|---|---|
| `Figma AI Run.bat` (윈도우) | 서버 시작 전 `git pull --ff-only`. 실패(네트워크 · 충돌)해도 지금 버전으로 계속 실행하고 안내만 표시 |
| `Figma AI Run.app` · `.command` (맥) | 같은 동작. 맥은 Xcode 개발자 도구의 git 사용 |
| 시작 안내(`Setup.html`) | 「저장소 받기(clone) · 깃허브 로그인」 단계 추가, 현재 버전(커밋) 표시 |
| 상단 메뉴 | 현재 버전 · 「업데이트 있음」 표시(선택) |
| 개인 데이터 분리 | `workbench/edit_requests.json` · `jobs.json` · `projects/*/shots` 등 PC마다 달라지는 파일이 pull과 충돌하지 않게 정리(.gitignore 또는 별도 위치) |
| 문서 | README · `docs/Workbench_Setup_Other_PC.md`를 clone 방식으로 갱신 |

### 확인할 점
- 각 PC에 Git 설치 여부(윈도우는 별도 설치, 맥은 개발자 도구).
- 저장소 읽기 권한: 사용할 사람 모두 깃허브 계정이 있어야 한다.
- 작업 중 로컬에서 고친 파일이 있으면 pull이 막힌다 → 사용자 파일과 배포 파일을 분리해야 한다.

## 2. 계정 · 권한 (Workbench 안에서 그룹별 메뉴 · 권한)

### 정한 것 (2026-10-26 논의)
- **관리자가 계정을 발급**한다(아이디 · 이름 · 그룹 · 비밀번호). 본인이 그룹을 고르지 않는다.
- 그룹은 2개:
  - **작업자**: 지금 기능 전부(요청 처리 · 상태 변경 · 삭제, 프로젝트 추가 · 변경, 목록 만들기 요청, 컬러 저장, 시작 안내 7단계, Claude 감시)
  - **요청자**: **보기 + 수정 요청 등록**. 본인 「대기」 요청만 고치거나 취소. Claude · Figma 플러그인 설정 불필요
- 계정 명단은 **깃의 명단 파일**(`team.json`)에 둔다. 명단은 관리자(깃 쓰기 권한)만 고친다.

### 설계안 (한 번 구현했다가 되돌린 내용 기준)
- `team.json`: `{ version, accounts: [{ id, name, role: worker|requester, salt, hash, issuedAt }] }`, `hash = SHA-256(salt + 비밀번호)`
- 발급 도구: 윈도우 `tools/issue_account.ps1 -Id -Name -Role [-Password] / -Remove / -List`, 맥 `tools/issue_account.pl`. 비밀번호를 안 주면 임시 비밀번호 생성.
- 서버(`guide_server.ps1` · `guide_server_mac.pl` 둘 다)
  - `POST /api/login` · `/api/logout`. 로그인 상태는 PC별 `setup.json`에 `{id, hash}`로 저장(재발급하면 다시 로그인)
  - `GET /api/setup`에 `auth {required, account, role}` 추가. `/start`는 미로그인이면 `Login.html`
  - 권한 검사는 브라우저 페이지(Origin 있음)의 요청만. Claude(curl) · Figma 플러그인(Origin null)은 그대로
  - 요청자 차단: 상태 · 메모 변경, 남의 요청 삭제, 목록 만들기 요청, 작업 파일 변경, 컬러 저장
  - `team.json`이 없거나 비어 있으면 로그인 없이 모두 작업자(지금과 같음)
- 화면
  - `Login.html` 새로 추가
  - `appnav.js`: 미로그인 → 로그인 페이지로, 오른쪽에 「이름 · 그룹 · 로그아웃」, `<html data-role>`로 `.worker-only` 숨김, 프로젝트 선택은 작업자만
  - Workbench: 요청자는 상태 선택 · 삭제 대신 본인 대기 요청 [취소]만, 목록 만들기 버튼 숨김. 요청자 이름은 계정 이름으로 고정
  - 가이드 컬러 편집 [저장] · [되돌리기], 「시작 안내」 메뉴는 작업자 전용

### 아직 정할 것
1. **요청자 → 작업자 요청 전달 방법.** 지금 요청은 각자 PC의 `edit_requests.json`에만 쌓인다.
   - 깃으로 주고받으려면 요청자 PC에도 git과 저장소 **쓰기** 권한이 필요하다(깃허브의 「열람자 Read」 구성과 충돌).
   - 여러 PC가 동시에 등록하면 `R0xx` 번호가 겹치고 JSON 충돌이 난다 → 요청을 **한 건 한 파일**로 저장하고 ID를 고유하게(예: 날짜+아이디) 바꿔야 한다. 감시 스크립트(`watch_requests.*`) · CLAUDE.md 처리 흐름도 같이 바뀐다.
   - 대안: 한 PC를 사내망 공유 서버로 쓰기(서버 주소 · 방화벽 · 플러그인 허용 주소 변경 필요), 또는 외부 저장소(Supabase 등).
2. 비밀번호 변경을 본인이 할 수 있게 할지(지금 설계는 관리자 재발급만).
3. 깃허브 쪽 권한: 개인 계정 저장소는 읽기 전용 초대가 안 된다 → 무료 Organization으로 옮겨 팀(작업자 Write / 요청자 Read)을 나눌지.
4. 보안 수준: 로컬 파일 기반이라 마음먹고 고치면 우회 가능. 사내용으로 이 정도면 되는지.

### 순서 제안
1. 업데이트 배포(1번)를 먼저 한다. 계정 명단(`team.json`)도 결국 깃으로 배포되기 때문이다.
2. 요청 전달 방법(위 1번)을 정한다.
3. 계정 · 권한을 구현하고, 작업자 · 요청자 두 계정으로 화면을 확인한다.
