# 시스템 기준 (UX 문서를 새로 만들거나 작업규칙을 고칠 때)

> 새 팀(또는 새 문서)의 작업규칙 · 정책서 · 기준데이터 · 화면 정의서 · UX가이드는 그 팀 자료(Figma · 참고 파일 · 작업 방법)로 만든다. 그런데 그 문서는 **이 시스템(Workbench · 서버 · 백그라운드 Claude · Figma 플러그인)에서 쓰인다**. 그래서 만들 때 이 문서를 함께 읽고,
> 1. 문서 내용이 시스템에서 그대로 돌아가게 쓰고(2절 「꼭 정할 것」을 채운다),
> 2. 시스템이 못 하는 것 · 빠진 것을 문서 끝 **「시스템 확인」**(3절)에 남긴다.
>
> 이 문서는 팀 정책을 대신 정하지 않는다. 자료에 없는 것은 **추천안**으로 「시스템 확인」에 적고, 본문에는 자료에 있는 것만 쓴다. 언제 읽는지는 `ux-docs-new.md`(guide 1-2) · `ux-docs.md`(guide-edit 1-1). 시스템이 바뀌면(기능을 더하거나 뺄 때) 이 문서 1절도 고친다(`dev.md`).

## 1. 시스템이 하는 것 (모든 팀이 같다 — 문서로 바꿀 수 없음)

### 요청 (Workbench 수정 요청, R0xx)
- 요청에 오는 것: 대상(Figma 파일 · 페이지 · 프레임 하나 또는 페이지 전체), 글, 첨부(그림 · PDF · TXT/MD/CSV, 20개까지), 캡처 위 사각형 표시(①②…), 우선순위(높음 · 보통), 레이아웃(공통 틀 9가지 중 하나, 선택).
- **흐름(케이스 · 단계)을 고르는 칸은 없다.** 무슨 일인지 · 몇 단계째인지는 작업규칙이 **요청 글로** 정하게 써야 한다.
- 상태: 대기 → 진행 중 → 완료, 또는 보류. 보류할 때 Claude는 **질문 하나 + 선택지 2~4개(+ 직접 입력)**를 남길 수 있고, 사람이 답하면 그 답으로 이어서 처리한다. 사람은 「멈추기」(진행 중도 끊음) · 「다시 진행」을 할 수 있다.
- **한 요청에서 사람이 답하는 곳까지 이어서 진행한다**(2026-11-17~). 단계가 여럿인 일도 단계마다 새 요청을 보내지 않는다. Claude는 작업규칙이 사람에게 멈추라고 한 곳(요청자 확인)에서 「보류」 + 질문으로 멈추고, 답이 오면 다음 멈출 곳까지 다시 이어 간다. 아주 길어지면 단계 경계에서 이어 갈 곳을 기록에 쓰고 「대기」로 돌려 새 세션이 이어 간다 → 작업규칙은 **사람이 멈추는 곳**과 **이어 갈 기록의 위치 · 형식**을 정해야 한다.
- 처리 결과(note)는 Workbench 「Claude 답변」에 그대로 보인다. 첫 줄 요약, 고친 곳 한 줄씩.

### 고칠 수 있는 곳
- Figma 파일마다 **작업 페이지 하나만** 고친다. 다른 페이지는 읽기만 한다(요청이 오면 「보류」).
- 작업 페이지 안에서 더 좁히는 것(예: 파트 · 영역)은 시스템이 모른다 → 필요하면 **작업규칙이 정한다**(2절).
- 팀 프로젝트의 다음 단계 파일(① → ② → ③)로 화면을 옮기는 것은 **사람이 Workbench 「② ○○(으)로 옮기기」 · 비교 창 「복사해 옮기기」**(플러그인 · 서버가 Figma 복사 · 붙여넣기로)로 한다. Claude는 옮기지 않는다.
- 작업 기록을 멈추는 것(`status: 멈춤`)은 **사람이 일정/작업 「작업 기록」 [멈추기] · [다시 시작]**으로도 한다(2026-11-20). 멈추면 시스템이 반영 대기의 `작업 중 ({작업 기록})`을 `대기`로 되돌리고 이 PC의 그 작업 요청을 멈춘다 → 작업규칙의 작업 기록 머리말에 `status`(진행 중 · 끝남 · 멈춤)와 `이어서 작업할 곳:` 줄이 있어야 이 기능이 맞게 동작한다.

### 자동으로 되는 것 (문서에 절차로 쓸 필요 없음)
- 캡처: Figma 플러그인(작업 페이지를 고치면) · Figma 토큰(서버) · Claude가 고친 프레임.
- 변경 이력: 요청 등록 · 상태 변경 · 완료(캡처 붙임)를 서버가 남기고 모든 작업자에게 공유한다.
- 사용량 기록, 같은 프레임을 다른 작업자가 요청 중이면 「겹침 대기」, 프로토타입 「갱신 필요」 표시.

### 작업 기준 문서
- 카테고리(작업규칙 · 정책서 · UX가이드 · 기준데이터 · 화면 정의서)마다 **작업자가 [적용]한 문서 하나만** Claude가 읽는다. 모두 그 PC의 모든 프로젝트에 같이(UX가이드도 2026-11-20부터).
- 어긋나면 화면 내용은 화면 정의서 → 정책서 → 기준데이터, 공통 구성 · 컴포넌트 · 표기는 UX가이드를 따른다. 작업규칙은 일하는 방식(순서 · 확인 · 산출물)이다.
- 정책서 · 화면 정의서는 파일이 많으면 **요청 화면의 화면 ID(CID)로 찾는 것만** 읽는다 → 문서가 CID로 찾을 수 있어야 한다.

### 그 밖에 있는 기능 (작업규칙에서 이 이름으로 가리킬 수 있다)
- UX 문서: 수정 요청(Claude가 고침) · 직접 수정 · 고친 뒤 「연관 항목 찾기」(영향 받는 화면 · 문서 목록).
- 일정/작업: 논의 대상(DS) · 회의록(각자 작성 → Claude 정리본) · 화면설계서 작업대기(반영 대기 항목을 골라 수정 요청) · 일정(구글 시트, Azure DevOps는 보기만).
- 프로토타입(Figma 화면 → HTML), 변경 이력 · 사용량 통계.

### 시스템이 못 하는 것 (문서에 있으면 「시스템 확인」에 적는다)
- 외부 서비스에 쓰기: Jira · 메일 · 메신저 알림, Azure DevOps 작업 항목 고치기, 구글 시트 직접 고치기(사람이 Workbench에서 고침).
- 요청 없이 스스로 시작하기: 정해진 시각 · 매일 점검 · 「Figma가 바뀌면 바로」 같은 일은 요청이나 작업이 와야 한다.
- 작업 페이지 밖 · 다른 Figma 파일 고치기, 다음 단계 파일로 옮기기(Workbench 「복사해 옮기기」 또는 사람이 Figma에서 복사).
- 사람의 승인 · 컨펌을 대신하기, Figma 진행상태 띠 · 메뉴 상태를 사람 대신 바꾸기(문서가 그렇게 정하지 않는 한).
- Word · Excel 첨부 읽기(요청 첨부는 PDF · 그림 · 글만).
- 다른 팀 문서 고치기(가져오기만 됨).

## 2. 꼭 정할 것 (카테고리별)

자료에 있으면 본문에 그대로 쓰고, 없으면 「시스템 확인」에 **추천안과 함께** 「정해야 함」으로 적는다.

### 작업규칙
1. **요청 나누기**: 요청 글을 어떤 일로 나누는지(예: 화면 고치기 · 새 화면 · 질문 · 문서만 고치기)와 일마다 순서.
2. **단계**: 한 번에 끝나는 일인지, 여러 단계인지. 여러 단계면 단계마다 끝(요청자 확인 → 보류 + 질문)과 **이어 갈 기록의 위치 · 형식**(한 요청이 사람이 답하는 곳까지 이어 가고, 길어지면 새 세션이 이 기록에서 이어 간다).
3. **보류 기준**: 무엇이 모호하면 고치지 않고 묻는지, 질문 · 선택지 예.
4. **고칠 범위**: 작업 페이지 안에서 고쳐도 되는 곳 · 안 되는 곳(파트 · 영역 · 띠 구분이 있으면 읽는 법), 새 프레임 둘 자리, 화면 ID(프레임 이름) 규칙.
5. **완료 때 남길 것**: note에 쓸 내용, 함께 고칠 문서(화면 정의서 · 반영 대기 등)가 있으면 언제.
6. **다른 문서와의 관계**: 정책이 바뀌면 정책서를 바로 고치는지, 화면을 다 그린 뒤 고치는지.

### 정책서
- 정책마다 **적용 화면(CID)**을 적어 요청 화면으로 찾을 수 있게(파일이 여럿이면 파일 머리에 `cids`).
- 권한 · 상태 전이 · 예외 처리 · 알럿/컨펌 문구처럼 화면에 바로 쓰는 규칙은 값으로(「적절히」 같은 말 대신).

### 기준데이터
- 코드 · 상태값 · 단위 · 표기 값을 표로. 같은 값의 다른 이름(동의어)이 있으면 함께.

### 화면 정의서
- 화면(CID)마다 하나. 화면 디스크립션은 Figma 프레임 안 「Frame 1」 패널의 행(Description 인스턴스)이고, 화면 이동은 `[화면 ID] 화면명`으로 적는다.
- 정의서와 Figma가 어긋날 때 어느 쪽이 맞는지(작업규칙에 없으면 여기서).

### UX가이드
- 구성 · 크기 · 컴포넌트 · 표기. 이 PC의 모든 프로젝트에 하나를 적용하니, 대상(PC · 모바일 등)이 다르면 개요에 적는다.

## 3. 「시스템 확인」 쓰는 법

- **위치**: 한 파일 문서는 맨 끝 `## 시스템 확인`, 대분류마다 파일인 문서(CURECA 외 팀)는 마지막 파일 `시스템 확인.md`(`# 시스템 확인`), 파일형 원본 그대로(「그대로 구성」) 만든 문서는 원본을 고치지 않으므로 **완료 note에만** 적는다.
- **표**: `| 구분 | 문서 내용 (어디) | 시스템 | 할 일 |`
  - 구분: `못 함`(시스템이 못 하는 규칙) · `정해야 함`(2절 중 빠진 것) · `다름`(시스템과 다르게 쓴 것, 예: 「요청자가 케이스를 고른다」).
  - 할 일: 추천안 한두 문장(예: 「Jira 등록은 사람이 한다로 바꾸기」, 「보류 기준: 대상 화면이 10개 넘으면 묻기」).
- 없으면 「시스템과 어긋나는 것 없음」 한 줄.
- 완료 note 끝에 `시스템 확인: 못 함 n · 정해야 함 n · 다름 n`을 적는다(사람이 문서를 열기 전에 알 수 있게).
- 사람이 고쳐 해결한 줄은 지운다(수정 요청으로 「시스템 확인 ○번 반영」).
