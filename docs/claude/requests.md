# Workbench 수정 요청 처리 (`PENDING` · `RESUME`, 요청 R0xx)

> `CLAUDE.md`에서 나눈 것이다. `CLAUDE.md`의 범위 · 공통 규칙(팀 · 중복 처리 금지 · 사용량 · UTF-8 전송 · 주의)을 함께 따른다. **요청마다 늘 읽는 부분만** 둔다. 그 경우에만 필요한 것은 `requests-more.md`의 그 절만 읽는다(아래 「그때만 읽을 것」).

## 작업 흐름은 그 팀 작업규칙이 정한다 (Workbench는 고르지 않음)

Workbench는 모든 팀이 같이 쓰는 도구라 팀별 흐름(케이스 · 단계 · 작업 기록)을 고르는 칸이 없다. 요청에는 대상(파일 · 페이지 · 프레임) · 글 · 첨부 · 표시 · 우선순위 · 레이아웃만 온다. 흐름은 **요청의 `team`과 이 PC에서 적용한 작업규칙**으로 정한다.

- **작업규칙 찾기**: `GET /api/guides?team={요청 team}`의 `applied[fileKey].docs.rule`. 적용하지 않았으면 「보류」 + `ask`(UX 문서에서 작업규칙을 적용해 달라고).
- **단계 문서가 있는 작업규칙**(`work-rules.md` · `flow/`): `requests-flow.md`도 읽는다. 없는 팀(예: STAgora)은 그 작업규칙대로 아래 「요청마다」 순서로 바로 처리하고 note 첫 줄에 「작업규칙 {제목}대로 처리」.
- **작업규칙이 우선**: 작업규칙이 정한 읽을 문서 · 범위 · 절차 · 순서 · 마침 점검 · 「하지 않는 것」은 이 문서 · `requests-flow.md`의 토큰 절약 규칙보다 앞선다. 더 싸다고 작업규칙과 다른 방법(지름길)으로 바꾸지 않는다.
- **고치는 곳**: 화면 MD · 작업 기록 · 논의 대상 · 반영 대기 목록은 규칙 저장소 파일을 직접 고친다(`plan.md` 「고치는 곳」). `.history`는 서버가 자동으로 공유한다(한 PC만 멈추려면 `workbench/.history_sync_off`).
- **그때만 읽을 것**(`requests-more.md`, 해당할 때만 그 절만 — `Grep`(`^## `)으로 절 줄을 찾아 `offset` · `limit`으로, 한 세션에 한 번): 요청에 `nodeId`가 없으면(페이지 요청) · `from` · `fixRows`가 있으면 「요청 종류에 따라」, 사람이 멈춘 요청 오류를 받으면 「사람이 멈춘 요청」, Claude가 캡처해야 하면(토큰 없음) 「캡처」, `CONFLICT` · `RESUME` · 채팅으로 고침 · 대화 창 감시면 「겹침 · 대화형 감시 …」, `marks` · `images` · `layout`이 있으면 「수정할 부분 표시 · 첨부 · 레이아웃」, 요청에 `model` · `effort`가 있는데 앱 대화로 처리할 때 · 프로토타입 맞추기 · 완료 때 고를 다음 행동은 「완료 뒤 · 그 밖」.
- 감시가 보낸 메시지에 요청 내용(대상 · 글 · 첨부 · 답)이 함께 오면 다시 조회하지 않는다. JSON은 node · PowerShell로 다룬다(python이 없을 수 있음).

## 요청마다

(`TIMEOUT`이면 감시를 다시 실행, `JOBS`면 `CLAUDE.md` 「작업별 문서」의 그 문서대로. `PENDING`은 적힌 순서대로 한 요청씩 — 「진행 중」 구간마다 사용량이 쌓이니 한꺼번에 진행 중으로 두지 않는다.)

0. **대상**: 요청의 `fileKey`(없으면 시작 안내 작업 링크의 파일, 둘 다 없으면 「보류」). 요청의 `page`가 지금 수정 가능 페이지(project.json `editablePageName`)가 아니면 반영하지 않고 「보류」 + note 「○○ 페이지는 보기 전용입니다. 담당자 확인 필요」.
   - **Figma 파일 열림 확인(새 요청이면 먼저)**: 규칙 · 작업 기록 등 다른 일을 하기 전에 Figma MCP로 그 파일을 한 번 연다(`create_session` 뒤 `use_figma`로 파일 이름 · 작업 페이지 이름만 돌려받기). 이 단계에서 Figma를 쓰지 않더라도 한다 — 뒤 단계에서 막히면 그때까지 한 일이 멈춘다(2026-11-25 R001: 시작한 뒤 파일 권한이 없어 13분 대기). 열 수 없으면 바로 「보류」 + note(연결된 Figma 계정 이름과 「이 계정에 파일 편집 권한 공유 또는 권한 있는 계정으로 다시 연결」) + `ask`(「공유 · 다시 연결함, 이어서 진행」). 같은 세션에서 이미 연 파일이면 다시 하지 않는다.
1. **「진행 중」으로**: `POST /api/requests {action:'update', id, status:'진행 중', note, by:'Claude'}`. 「이미 진행 중」이면 건너뛰고, 「사람이 멈춘 요청」이면 더 고치지 않고 멈춘다.
2. **작업 기준 문서를 읽고 반영한다** — 카테고리(작업규칙 · 정책서 · UX가이드 · 기준데이터 · 화면 정의서)마다 이 PC에서 「적용」한 문서 하나만:
   - `GET /api/guides?team={team}`의 `applied[fileKey].docs`(`rule` · `policy` · `guide` · `data` · `spec` → `{id}`, 빈 id = 기준 없음. 예전 형식은 `guideId` = UX가이드). 문서마다 지금 내용(`items[].mdPath`, 파일형 문서는 `items[].fileList[].mdPath`)을 읽는다. 적용하지 않은 문서는 읽지 않는다.
   - **읽는 범위**: 작업규칙이 정한 문서 · 때 · 범위는 그대로 읽는다(줄이지 않는다). 작업규칙이 정하지 않은 것만 — 작업규칙 자체는 단계 문서가 있으면 `requests-flow.md` 「읽는 범위」, 없으면 모두 / UX가이드는 목차(`Grep` `^#{2,3} `) 뒤 요청 화면에 필요한 절만(작업규칙이 같은 원본을 정한 때에 읽게 했으면 그때 한 번만) / 정책서는 `README.md`와 머리말 `cids`에 요청 화면이 있는 파일 · 그 파일이 `data`로 가리키는 자료 / 기준데이터는 `glossary.md`와 요청에 걸린 표 / 화면 정의서는 요청 화면 CID와 짝 CID 파일. 약 20KB 넘는 파일은 목차를 먼저 보고 필요한 절만. 이 세션에서 읽은 것은 바뀌지 않았으면 다시 읽지 않는다.
   - **어긋날 때**: 화면 내용은 화면 정의서 → 정책서 → 기준데이터, 공통 구성 · 컴포넌트 · 표기는 UX가이드. 문서와 요청이 어긋나면 요청대로 하고 note에 적는다. UX가이드를 적용하지 않았으면 「보류」 + `ask`.
   - Figma는 아래 「Figma · 도구 토큰 절약」대로 그린다. 프로토타입은 여기서 고치지 않는다.
3. **캡처**: 실제로 고친 프레임 모두(요청 프레임과 다를 수 있음). `GET /api/figma`가 `token:true`이고 `deadAt`이 비어 있으면 「완료」에 보낸 `frames`를 서버가 캡처하니 Claude는 찍지 않는다. 아니면 `requests-more.md` 「캡처」. 변경 이력은 서버가 남긴다(캡처를 완료보다 먼저).
4. **「완료」**(모호하면 「보류」 + 질문):
   - **note**: Workbench 「Claude 답변」에 그대로 보이는 요약이다. 줄바꿈으로 — 첫 줄 요약 한 문장, 고친 곳 한 줄씩(`- 화면: 무엇 → 어떻게`), 참고 · 확인 필요는 마지막 줄. note와 `ask.q`는 Workbench가 마크다운 일부로 보인다(`**굵게**` · `` `코드` `` · `- ` 글머리표와 2칸 들여쓴 하위 줄 · `1.` 번호 · 빈 줄 = 문단 · 표) — 묶음 제목은 `**굵게**`, 항목은 글머리표로 써 읽기 쉽게 한다. **간략한 보고서**다: 사람이 할 일은 `ask`(보고서 위에 따로 보임)에, note는 첫 줄에 결과 한 문장, 덩어리는 `[머리표]`(사람이 볼 것은 `[확인 필요]` · `[질문 대기]`), 질문 · 확인은 줄마다 `Q1 …` · `C1 …`로, 여러 가지는 「 / 」로 잇지 말고 줄마다 쓴다. 질문은 `Q1 질문` 줄 아래에 고를 값을 `  - 값 (추천)` · `  - 값` 줄로 나눠 쓴다(근거는 그 아래 한 줄). 끝에 **작업 기준 줄** `작업 기준: basis {YYYY-MM-DD HH:mm} · 작업규칙 {제목|없음} @{수정본|원본} · 정책서 … · UX가이드 {제목} ({id}) · 기준데이터 … · 화면 정의서 …`(빈 카테고리는 「없음」).
   - **`frames:[{nodeId, name}]`**: 실제로 고친 최상위 프레임(고친 순서, 최대 12개). 요청 프레임만 고쳤으면 생략해도 된다.
   - **질문(`ask`)**: 사람이 답해야 이어 가면 `{status:'보류', note, ask:{q:'한 문장', options:[{label:'답 1'}, {label:'답 2'}], free:true}}`(선택지 2 ~ 4개, 짧게. 고를 답이 없으면 `options:[]`). 완료하며 다음 행동을 고르게 할 때(`action`)는 `requests-more.md` 「완료 뒤 · 그 밖」. 사람이 답하면 서버가 `replies[]`에 쌓고 「대기」로 돌린다 → **원래 요청과 마지막 답을 함께 읽고 그 답대로 이어서**(같은 질문을 다시 하지 않음). `replies` 없이 「대기」로 돌아온 보류 요청은 처음처럼 처리한다.
5. **프로토타입**: 「완료」 뒤 `GET /api/prototypes`에 고친 프레임이 「갱신 필요」(`stale`)인 것이 있으면 `requests-more.md` 「완료 뒤 · 그 밖」대로 맞추기 작업을 쌓는다(요청은 기다리지 않는다).

## Figma · 도구 토큰 절약 (모든 팀)

작업규칙이 정하지 않은 곳에서만 쓴다(위 「작업규칙이 우선」). 응답할 때마다 대화 전체를 다시 읽으므로 **사용량 ≈ 응답 수 × 대화 크기**다. 응답 수와 대화에 들어오는 것을 줄인다.

- **한 세션에서 한 번 읽은 문서는 다시 읽지 않는다**: 규칙 문서 · 단계 문서 · 화면 MD · 참고 문서는 이 대화에 이미 있으면 그 내용을 쓴다(2026-11-26 R003: 같은 문서를 2 ~ 6번 다시 읽어 입력 토큰의 약 9%). 처음 읽을 때 뒤에 필요한 범위까지 한 번에 읽는다. 다시 읽는 것은 다른 사람 · 다른 PC가 고쳤을 수 있는 작업 기록의 확인 줄(`requests-flow.md` 「같은 세션에서 이어 갈 때」)과, 대화 압축 뒤뿐이다. 내가 고친 파일은 고친 내용을 알고 있으니 다시 읽지 않는다.
  - **comm-index처럼 큰 색인은 찾을 것을 모아 한 번에**: 이번 단계에서 쓸 Type · 요소를 먼저 다 적어 두고, Grep 한 번(패턴을 `A|B|C`로 묶음)이나 Read 한 번으로 찾는다. 요소마다 따로 찾지 않는다.
- **바뀐 곳만 Edit으로**: 화면 MD · 작업 기록 · 문서를 고칠 때는 바뀌는 부분만 `Edit`으로 고친다. 파일 전체를 `Write`나 스크립트로 다시 쓰지 않는다(쓴 내용이 통째로 대화에 실린다). 새 파일을 만들 때만 `Write`.

- **그릴 자리 · 기존 프레임**: 먼저 `projects/{fileKey}/catalog.json`(페이지별 `frames`: nodeId · 이름 · w · h · x · y · 섹션)을 본다. Figma에서는 페이지 전체 노드를 나열하지 않고 필요한 섹션 · 프레임만 이름 · id · 위치로 받는다(자식 트리는 받지 않는다).
- **컴포넌트 메모**: 알아본 컴포넌트(이름 · 키 · 변형 속성과 값 · 글 속성 · 안쪽 글 노드 이름)는 `projects/{fileKey}/components.md`에 한두 줄로 적어 둔다. 다음에는 이 파일부터 읽고 없는 것만 알아본다. 맞지 않으면 그 줄만 고친다.
- **호출을 묶는다**: 화면 하나(짝 화면이면 한 쌍)의 화면 영역 · 패널 · 표시 · 케이스 프레임처럼 다시 해도 안전한 것은 몇 번의 호출로 묶는다. 실패하면 상태 확인과 다시 하기를 한 호출로. 파일 고치기 · 비교도 한 번의 스크립트로. 단 작업 기록 · 화면 MD처럼 이미 있는 파일을 스크립트로 통째로 다시 쓰면, 같은 스크립트에서 쓰기 전과 뒤의 줄 수를 함께 돌려받아 줄 수가 크게 줄었거나 비었으면 바로 쓰기 전 내용으로 되돌린다(2026-11-25 R001: 변수 이름 실수로 작업 기록이 두 번 비었음).
- **정해진 컴포넌트에 내용 넣기는 플러그인에**: 패널 행 · 확인 목록 · 라벨처럼 정해진 컴포넌트에 내용을 채우는 일은, 그 파일에 플러그인이 켜져 있으면 **컴포넌트 채우기 작업(`kind:'fill'`)** 하나에 제목 행 · 행 꾸밈 · 확인 목록(틀 복제) · 라벨 · 프레임 높이까지 넣고 결과(만든 수 · 넘침 · 겹침)만 확인한다. 채운 뒤 코드로 다시 꾸미지 않는다. 꺼져 있거나 3분 안에 받지 않으면 직접 그린다(`jobs.md` 「fill」).
  - **켜져 있는지는 감시가 알려 준다**: 차례 지시 끝의 「Figma 플러그인 켜짐 · 꺼짐」 줄을 따른다(감시가 없는 세션만 `GET /api/jobs?kind=fill`의 `plugins[fileKey]` 180초 안으로 확인). 2026-11-26 R003은 플러그인이 켜져 있었는데 확인하지 않고 코드로만 그렸다.
  - **작업규칙과 다른 방법이 아니다**: 작업규칙(예: CURECA 「공통 3. Figma 그리기」)은 무엇을 · 어떤 컴포넌트로 그릴지 정하고, 채우기는 그것을 넣는 도구다. 작업규칙이 정한 컴포넌트 · 값 · 순서를 그대로 채우기 작업에 담는다.
- **원본 · 참고 화면 보기**: 대상 하나에 한 번의 호출로 구조(이름 · 종류 · 위치 · 글)를 필요한 깊이까지 받고, 구조로 알 수 없는 것(색 · 아이콘 · 전체 배치)이 있으면 그 호출에서 1장만 함께 찍는다. 부분마다 나눠 찍지 않는다.
- **스크린샷**: 그린 뒤 먼저 노드 영역 비교(글이 칸 안에 있는지 · 겹치는지, 문제만 돌려받기)로 점검한다. 대상 하나를 다 그린 뒤 1장, 고칠 곳을 모아 한 번에 고친 뒤 1장. 팀 작업규칙이 정한 확인은 그대로 하되 같은 대상을 여러 호출로 나눠 찍지 않는다.
- **출력을 줄인다**: 셸 · 스크립트 · Figma 결과는 필요한 줄 · ID · 개수 · 이름만 돌려받는다. 한 번 들어온 출력은 그 뒤 모든 응답에서 다시 읽힌다.
