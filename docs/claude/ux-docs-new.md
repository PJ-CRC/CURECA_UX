# 새 UX 문서 만들기 (`guide`)

> `ux-docs.md`에서 나눈 것이다(2026-11-20). guide 작업(새 문서)일 때만 읽는다. `ux-docs.md`의 공통 절(작업 기준 · 고치는 곳 · 카테고리 · 파일형 문서 · 문서 수정본)과 `CLAUDE.md` 공통 규칙을 함께 따른다. 「위 ○○」라고 적힌 절은 `ux-docs.md`에 있다.

- **guide (새 UX 문서 만들기 — 모든 카테고리)**: 작업의 `name`(이름) · `link`(기준 Figma 링크, `fileKey` · `nodeId`, **선택**) · `files`(올린 참고 파일 `[{path, name, size}]`, **선택**, `workbench/job_files/{작업 ID}/` 이 PC에만) · `text`(작업 방법) · `by`(요청자) · `docKind`(카테고리: `''` UX가이드 · `'rule'` 작업규칙 · `'policy'` 정책서 · `'data'` 기준데이터 · `'spec'` 화면 정의서)로 만든다. 링크와 참고 파일 중 하나 이상은 늘 있다. **Figma는 읽기만 한다**(수정 가능 페이지와 상관없다).
  1. 상태를 「진행 중」으로 바꾼다. 작업 방법이 모호해 무엇을 정리할지 정할 수 없으면 「보류」로 바꾸고 note에 질문을 남긴다.
  1-1. **참고 파일**(`files`)이 있으면 모두 읽는다: md · txt · csv · json · html은 Read, pdf · 이미지는 Read(pdf는 쪽 범위), docx · xlsx · pptx는 해당 스킬(docx · xlsx · pptx)이나 압축을 풀어 글을 읽는다. 링크가 없으면 참고 파일만으로 만들고(2 · 3 건너뜀, 이미지 캡처 없음, `fileKey` ''), 둘 다 있으면 참고 파일의 내용 · 구성을 기준으로 Figma 화면을 근거 · 캡처로 함께 쓴다. 파일 내용과 Figma가 어긋나면 작업 방법을 따르고 note에 적는다.
  1-2. **시스템 기준**(2026-11-17): `docs/claude/system-basis.md`를 읽는다. 자료대로 쓰되 시스템에서 그대로 돌아가게 쓰고(그 문서 2절 「꼭 정할 것」 — 카테고리별), 시스템이 못 하는 것 · 빠진 것 · 다르게 쓴 것은 문서 끝 「시스템 확인」에 추천안과 함께 남긴다(그 문서 3절, 자료에 없는 정책을 본문에 지어 넣지 않는다). 완료 note 끝에 `시스템 확인: 못 함 n · 정해야 함 n · 다름 n`.
  2. 범위(링크가 있을 때): `nodeId`가 페이지면 그 페이지, 섹션 · 프레임이면 그 아래, 없으면 파일의 페이지 목록에서 작업 방법에 맞는 페이지를 고른다.
  3. (링크가 있을 때) `use_figma`로 구조(섹션 · 최상위 프레임 이름 · 크기), 화면 글(디스크립션 · 제목), 많이 쓴 컴포넌트(INSTANCE의 메인 컴포넌트 이름 빈도) · 색 · 글꼴을 읽는다. 한글이 많으면 `escape()`로 받거나 나눠 받는다(`CLAUDE.md` 「주의」). 필요한 프레임만 `get_screenshot`으로 본다.
  4. `.history/guides/{id}/`에 쓴다(작업 이력과 함께 서버가 깃으로 모든 작업자에게 공유한다. Claude가 직접 커밋하지 않는다). id(= 폴더 이름)는 **알아보기 쉬운 이름** `{종류}_{제목}`(2026-11-13~): 종류는 `UX가이드` · `작업규칙` · `정책서` · `기준데이터` · `화면정의서`, 제목의 빈칸 · 쓸 수 없는 글자(`/ \ : * ? " < > |` 등)는 `-`로(예: 「STAgora 작업규칙」 → `작업규칙_STAgora-작업규칙`). 제목이 이미 종류로 시작하면 한 번만(「작업규칙_TEST_V1」 → `작업규칙_TEST_V1`). 같은 이름의 폴더가 있으면 뒤에 `-2` · `-3`. 쓸 수 있는 글자: 한글 · 영문 · 숫자 · `_ . ( ) -`(`_`로 시작 · `..` 안 됨). 예전 문서의 `g20261028-brex-06-J003` 같은 ID는 이름을 바꾸며 `meta.aliases`에 남겨 두었다(서버가 예전 ID를 새 ID로 읽는다).
     - **본문 파일 이름도 제목으로**: `{제목}.md`(예: `STAgora 작업규칙.md`, 쓸 수 없는 글자만 `-`)로 쓰고 `meta.json`에 `"main": "{제목}.md"`를 적는다(없으면 서버는 예전 이름 `guide.md`를 읽는다). 이 파일이 **늘 최종 내용**이다. 아래 「guide.md」는 이 본문 파일을 말한다.
     - `guide.md`(본문 파일): `# 제목`, 소개 문단(보기 화면의 「개요」), 그다음 `## 대분류` › `### 상세 항목`으로 쓴다. 보기 화면은 왼쪽이 이 목차 트리, 오른쪽이 고른 항목의 내용이다(대분류를 고르면 그 소개와 하위 항목 카드). 기준 Figma에 목차가 있으면 그 구조를 그대로 따른다. 작업 방법을 따르고, 구성은 **Common UX 가이드(`UX가이드_Common-UX-가이드`, 예전 ID `UX가이드_Common-UX-가이드-_1105` · `g20261105-daye-J001`) 구조를 본보기**로 한다(지금 내용 `mdPath`를 열어 본다):
       - 맨 앞 「개요」: 무엇을 기준으로 정리했는지 한 문단 + 안내 인용(`>`) + `### 프레임 구성`(기준 문서 프레임 크기 · 구성 표).
       - `## 0. 문서 구성 (목차)`(+ `### CID 규칙`) 다음에 `## 1. …` ~ `## N. …` 대분류. 대분류마다 첫 문단은 한 줄 소개(대분류 화면 · 폴더 카드 위에 보인다).
       - `### {n}-{x}. 항목 이름` 상세 항목. 한 주제가 길면 `### 4-a. 이름 (1/4) · 소제목`처럼 나눈다(폴더 카드에서 「(1/4) · 앞」은 작은 글씨, 소제목이 큰 제목). 항목 첫 문장은 「…을 정의한다.」 한 문장(폴더 카드 설명).
       - 항목 안: 규칙 표 · 목록, Figma 캡처(`![…](images/…)` + `*설명*`), 컴포넌트 대분류는 맨 앞에 Figma 컴포넌트 항목.
       표는 마크다운 표로, 이미지는 `![설명](images/파일.png)`와 다음 줄 `*설명*`으로 넣는다. HTML 태그는 쓰지 않는다(글자로 보인다).
     - **CURECA가 아닌 팀(STAgora · 새로 만든 팀, 작업의 `team`이 있고 `cureca`가 아닐 때 — `team`이 없으면 CURECA)은 한 파일로 쓰지 않고 대분류마다 md 파일 하나로 쓴다**(2026-11-13 사용자 요청 — 왼쪽 목록이 md 파일 단위로 보인다). CURECA 문서는 위처럼 한 파일 그대로다.
       - 문서 폴더 바로 아래에 `0. 개요.md`(`# 0. 개요` › 소개 문단 · 안내(`>`) › `## 프레임 구성` · `## 기준 문서` 같은 소제목 — 목록 첫 항목으로 보인다)와 대분류마다 `{번호}. {대분류 이름}.md`(쓸 수 없는 글자만 `-`). 대분류 파일은 `# {번호}. {대분류 이름}` › 첫 문단 한 줄 소개 › `## {번호}-{x}. 항목` › `### 소항목`으로(보기 화면이 한 단계씩 내려 위의 `##` › `###` 구조와 같아진다). **목차는 만들지 않는다**: 「0. 문서 구성 (목차)」 파일도, 개요 안의 대분류 목록 표(「문서 구성」 · 「대분류」)도 쓰지 않는다(왼쪽 목록이 곧 목차, 2026-11-13 사용자 요청). 목차 외 내용(CID 규칙 등)은 개요의 소제목으로.
       - `meta.json`에 `"format": "files", "filesDir": "", "folderList": true, "files": ["0. 개요.md", "1. ….md", …]`(순서대로)를 적고 `main` · `overview`는 쓰지 않는다(`overview`로 두면 보기 화면이 개요를 숨긴다). `images/`는 같은 자리(문서 폴더 아래)라 그림 경로 `images/…`는 그대로 쓴다.
       - 이 문서는 폴더가 곧 목록이다(`ux-docs.md` 「폴더가 곧 목록인 문서」): 파일을 넣거나 지우면 목록이 바뀌고, 수정 요청으로 새 항목 파일을 더할 수 있다.
     - `images/`: **고화질로** 받는다 — 보기 화면이 그림을 본문 폭(표와 같은 폭)으로 늘려 보이므로, 긴 변 1600으로 줄인 `get_screenshot`은 세로로 긴 프레임이 흐려진다(2026-11-20). Figma 토큰이 있으면 REST `GET /v1/images/{fileKey}?ids=…&format=png&scale=1.5`(1920 폭 프레임 → 2880px)로 받아 `images/{cid 소문자, (n/m)은 -n}.png`로 저장한다. 토큰이 없으면 `use_figma`에서 `exportAsync({format:'PNG', constraint:{type:'WIDTH', value:2880}})`. 대화에 base64로 넣지 않는다.
     - `meta.json`(UTF-8): `{id, kind(작업의 docKind: 'rule' · 'policy' · 'data' · 'spec', UX가이드는 빼거나 'guide'), title, summary(한두 문장), link, fileKey, fileName, scope(범위 페이지 · 섹션 이름 또는 「참고 파일」), frames(참고한 프레임 수), sources(참고 파일 이름 목록), by, request(작업 방법 원문), jobId, createdAt, updatedAt}`
     - 참고 파일 원본은 `.history`로 옮기지 않는다(이 PC에만). 「개요」에 무엇(파일 이름 · Figma 링크)을 기준으로 정리했는지 적는다.
  5. `POST /api/jobs {action:'update', id, status:'완료', guide:{가이드 id}, note:'섹션 N개 · 참고 프레임 M개 · 참고 파일 K개'}`. UX가이드는 UX 문서 「UX가이드」 탭 위쪽 목록에, 다른 카테고리는 그 탭(작업규칙 · 정책서 · 기준데이터 · 화면 정의서) 카드에 나타나고(모든 작업자), `UX_Guide.html?g={id}`에서 본다. 작업 기준으로 쓸지는 작업자가 각자 탭마다 「내 작업 기준」 선택 상자 + [적용]으로 정한다(카테고리마다 하나, 그 PC에만 · 그 PC의 모든 프로젝트에 적용, Claude가 정하지 않는다. `POST /api/guides {action:'apply', kind:'rule'|'policy'|'guide'|'data'|'spec', fileKey, guideId}`).
