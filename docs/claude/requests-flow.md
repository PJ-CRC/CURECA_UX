# 단계 문서가 있는 작업규칙으로 요청 처리 (`requests-flow.md`)

> 요청의 작업규칙(`applied[fileKey].docs.rule`)에 **단계 문서**(`work-rules.md` · `flow/`)가 있을 때만 읽는다. 일하는 방식(읽는 순서 · 단계 · 케이스 · 묻는 곳 · 작업 기록 쓰고 읽는 법)은 **그 팀 작업규칙(진입 문서와 단계 문서)대로** 하고, 이 문서에는 Workbench에서 더 하는 것만 둔다. `requests.md` 「요청마다」 순서는 그대로 따른다. 문서 위치 = 그 팀의 UX 문서 폴더(CURECA `.history/guides/`, 다른 팀 `.history/teams/{team}/guides/`). `old-`로 시작하는 폴더 · 파일은 근거로 쓰지 않는다.

## 읽는 범위

- 진입 문서와 그 문서가 정한 순서대로 읽고, 진입 문서는 한 세션에 한 번만 읽는다. 단계 문서 · 케이스 문서 · 참고 문서(`reference-rules/` · `examples/` · `templates/`)는 **작업규칙이 정한 때 · 범위 그대로** 읽는다(파일을 읽으라고 했으면 「필요한 절만」으로 줄이지 않는다). 케이스별로 나뉜 문서는 이번 작업의 케이스 것만.
- 이 세션에서 이미 읽은 것은 바뀌지 않았으면 다시 읽지 않는다.
- 규칙 문서를 고치는 일(guide-edit 등)에서는 다 읽는다. 이 문서는 Workbench 요청 처리에만 쓴다.

## 같은 세션에서 이어 갈 때 작업 기록 다시 읽기

- **새 세션 · 대화 압축 뒤**: 작업 기록을 처음부터 읽지 않고 작업규칙의 「끊긴 작업 이어 가기」대로 읽는다.
- **같은 세션에서 다음 단계로 넘어가거나 질문 답이 와서 이어 갈 때**: 머리말 `status` · 「단계」 표의 마침 점검 칸 · `이어서 작업할 곳:` 줄만 다시 보고, 내가 마지막에 쓴 것과 다르면(다른 사람 · 다른 PC가 고침) 「끊긴 작업 이어 가기」대로 다시 읽는다.
- **요청자 확인 보고**는 작업 기록에서 작업규칙이 정한 절만 다시 읽고 거기 적힌 것만으로 쓴다.

## 작업 기록 (Workbench에서 더 하는 것)

- **새 요청**(`work` · `replies`가 없음): 작업규칙대로 작업 기록을 다른 일보다 먼저 만들고(테스트면 `workbench/test-work/`), 만들자마자 `update`에 `work:'{작업 기록 이름}'`(확장자 없이)을 보낸다. 겹쳐서 다른 기록으로 이어 가게 되면 `work`를 그 이름으로 바꿔 보낸다.
- **이어 가는 요청**(`work`가 있음): 새로 만들지 않고 그 기록으로 이어 간다. 새 작업인지 이어 갈 것인지 정하기 어려우면 「보류」 + `ask`(「새 작업으로 시작」 / 「{이름} 이어 하기」).
- **화면설계서 작업대기에서 만든 요청**(`fixRows`): 새 작업으로 시작하고 1단계에서 그 항목을 이번에 반영할 것으로 고른다. 케이스는 작업규칙대로 정한다(예전 요청의 `case`는 무시).
- **멈춘 작업 기록**(`status: 멈춤`, 사람이 [멈추기]): 열린 기록으로 보지 않는다. 같은 대상의 새 요청은 새 작업으로. 요청이 이어 가던 기록이 멈춘 기록이면 「보류」 + `ask`(「새 작업으로 시작」 / 「작업 기록을 [다시 시작]한 뒤 이어 하기」). 처리 중에 멈춤으로 바뀐 것을 보면(화면 · 파일 하나를 끝낼 때마다 머리말을 본다) 그 자리에서 「보류」.
- **이어 받음**: 다른 작업자의 기록을 이어 받았으면 note 첫 줄 끝에 `· {원래 요청자}의 작업 이어 받음`, 작업 기록에도 이어 받은 사람 · 날짜를 남긴다(서버가 `work`로 원래 요청에 표시하고, 기록이 「끝남」이 되면 그 요청도 닫는다 — `dev.md` 「이어 받기」).

## 사람이 답하는 곳까지 이어서 진행

- 한 요청에서 **작업규칙이 사람에게 묻는 곳**까지 진행한다. 묻는 곳은 작업규칙이 정한 곳뿐이고, 작업규칙이 「묻지 않는다」고 한 곳에서는 멈추지 않는다. 예외 질문은 작업규칙대로 모아 두었다가 다음 정해진 확인에서 묻는다.
- 묻는 곳에서는 「보류」 + `ask`. 확인할 것이 여럿이면 note에 번호로 모두 적고 `ask`는 하나로 묶는다(예: 「추천대로 진행」 / 「하나씩 정하기」, `free:true`).
- 답이 「넘어간다」면 위 「같은 세션에서 이어 갈 때」대로 확인하고 다음 단계 문서를 읽어 다음 묻는 곳까지 이어 간다.
- 범위를 임의로 나눠 사람에게 넘기지 않는다(그리는 단계는 대상 화면을 모두 그린다). 요청 글이 범위를 정했으면 그대로.
- 5분 안팎마다 `{action:'update', id, note}`로 지금 하는 일을 적는다(`status`는 넣지 않는다).
- 단계 문서가 아직 비어 있으면 앞 단계 마침 점검까지 하고 「보류」 + `ask`.

### 나눠서 이어 가기

새 세션은 시작할 때 규칙 · 작업 기록 · 단계 문서 · Figma 지침을 다시 읽느라 약 13만 ~ 21만 토큰(5시간 한도 약 5%)이 들고, 이어 가면 지금 대화 크기를 다음 응답마다 다시 싣는다.

- **끊는 곳은 큰 덩어리 사이뿐**: 단계 하나를 마쳤을 때, 또는 Figma 호출이 많은 대상 하나(화면 · 짝 화면 한 쌍)를 다 그렸을 때.
- **끊을지는 대화 크기 숫자로**(단계가 바뀐다는 이유만으로 끊지 않는다): 감시가 띄운 세션이면 `workbench/.agent_ctx.json`의 `ctx`를 한 번 읽고, 다음 덩어리가 **그리기 · 고치기면 35만 이상**, **그 밖(문서 읽기 · 분석 · 화면 MD 쓰기 · 질문)이면 45만 이상**일 때만 끊는다. 파일이 없거나 1분 넘게 지난 값이면 이 세션에서 화면 한 쌍 넘게 그렸을 때만. (계산으로는 25만 · 35만에서 같아지고, 2026-11-25 요청자 결정으로 10만씩 높였다.)
- 끊을 때는 작업 기록의 `이어서 작업할 곳:` 줄을 쓰고, note에 「n단계 · 어디까지 함 · 이어서 진행」을 적은 뒤 「대기」로 되돌린다. 감시가 새 세션으로 이어 간다.

### 끊겨도 한 일이 남게

여러 화면 · 파일을 고치는 요청은 하나를 끝낼 때마다 작업 기록의 이어 갈 곳 줄을 고친다(작업규칙이 더 자주 쓰라고 하면 그대로). 감시가 「지금 사용량이 n%」를 알리면 note도 화면마다 고친다. 사용량이 높다는 이유로 덩어리 중간에 끊지 않는다 — 한도에 걸려 끊겨도 잃는 것은 많아야 대상 하나다.

## note

- 첫 줄: `케이스 n · n ~ m단계 · 작업 기록 이름`과 이번에 한 일.
- **규칙 점검 줄**: 차례를 마치거나 멈출 때 작업 기준 줄 바로 앞에 `규칙 점검: 이번에 한 단계의 「하지 않는 것」 · 마침 점검 지킴`(다르게 했으면 `규칙 점검: 다르게 한 것 — {무엇 · 왜}`). 작업규칙과 다르게 해야만 하면 하지 말고 「보류」 + `ask`.
- 작업 기록의 작업 기준(`basis` 등)은 작업규칙대로 적고 note의 작업 기준 줄과 같은 문서를 가리키게 한다.

## 테스트로 할 때 (Workbench)

요청 글에 「테스트로」 · 「반영하지 말고」가 있으면 작업규칙의 「테스트로 할 때」대로 한다. 저장소 밖 작업 폴더 = `workbench/test-work/`, Figma 섹션 이름 뒤에 `(테스트 N)`, 저장소가 바뀌지 않았는지는 `.history`의 `git status`로 확인해 적는다. 커밋은 하지 않는다.
