# 액션별 동작 흐름

> 일정/작업 · UX 문서 · Figma Workbench · 변경 이력이 서로 이어져 동작하는 방식을 액션마다 정리한 문서입니다. (2026-11-04 기준)

## 0. 큰 그림

```
              ┌──────────── UX 문서 (기준) ─────────────────────┐
              │ 작업규칙 · 정책서 · UX가이드 · 기준데이터 · 화면 정의서 │
              │   → 작업자마다 카테고리별로 1개씩 [적용]              │
              └───────┬───────────────────────┬────────────────┘
       적용한 문서를 읽고 작업 │                       │ 문서를 고치면
                      ▼                       ▼
   일정/작업 ──요청──▶ Figma Workbench ──▶ 변경 이력      일정/작업 › 화면설계서 작업대기
   (회의록 · 임시 정책 ·   (Claude가 Figma 수정)  (공유 이력)   (고쳐야 할 화면 목록)
    논의·결정)  ◀── 보류 · 정책과 다르게 고침 ──┘                    │
        └─────────── 결정되면 정책서 · 반영 대기 목록으로 ──────────────┘
```

- **기준은 언제나 UX 문서다.** Workbench 요청을 처리할 때 Claude는 그 작업자가 **적용한 문서만** 읽는다(작업규칙 · 정책서 · UX가이드 · 기준데이터 · 화면 정의서 각 1개).
  - 어긋나면 화면 내용은 화면 정의서 → 정책서 → 기준데이터 순, 공통 구성 · 컴포넌트 · 표기는 UX가이드를 따른다.
- **처리는 Claude가 한다.** 모든 요청 · 작업은 대기열에 쌓이고, 백그라운드 감시(시작 안내 7단계)가 Claude에게 넘긴다.
- **기록은 공유된다.** `.history`에 쌓여 깃(`history` 브랜치)으로 모든 PC에 공유된다. 「적용」 선택과 프로토타입만 PC마다 따로다.

## 1. UX 문서

### 1-1. 정책서 · 작업규칙 · 기준데이터 · 화면 정의서 항목을 고칠 때

1. 보기 화면에서 항목을 고르고, 목록 · 내용 아래 「수정 요청」 입력창에 고칠 내용을 적어 보낸다(Workbench처럼. 머리의 [수정 요청]은 그 입력창으로 이동).
2. Claude가 그 파일만 고쳐 **수정본**으로 남긴다(원본은 그대로, 수정본이 「지금 내용」).
3. **UX 문서 › 변경이력**에 「수정」 기록이 남는다(누가 · 언제 · 요청 글 · 바뀐 줄).
4. 「연관 항목 찾기」가 안내된다. Claude가 다음을 찾는다.
   - **화면**: 수정 가능 페이지에서 바뀐 내용과 다른 프레임
   - **다른 문서**: 같은 용어 · 값 · 규칙을 쓰는 항목
   - **프로토타입**: 그 화면을 쓰는 프로토타입
5. 고쳐야 할 화면의 「반영 대기 목록」에 줄이 더해진다 → **일정/작업 › 화면설계서 작업대기**에 나타난다.
6. 사람이 반영할 것을 고르면:
   - 화면 → **Workbench 수정 요청**(유형 「정책서 반영」 등)
   - 문서 → 그 문서의 수정 요청
   - 프로토타입 → 프로토타입 수정 요청
7. Workbench 요청이 처리되면 Figma가 바뀌고 변경 이력에 남는다([3. Workbench](#3-figma-workbench)). 그 문서를 「적용」한 작업자는 다음 Workbench 작업부터 바뀐 내용이 기준이 된다.

### 1-2. UX가이드를 고칠 때

- 1~3은 같다.
- 4는 「고칠 화면 찾기」다. 그 가이드를 자기 작업 기준으로 적용한 사람에게만 안내되고, 화면만 찾는다.

### 1-3. 새 문서를 만들 때

1. 탭의 「＋ 새 {카테고리} 만들기」 → Figma 링크나 참고 파일을 넣는다.
2. Claude가 문서를 만들고, 변경이력에 「생성」이 남는다.
3. 쓰려면 각자 탭 위쪽 「내 작업 기준」에서 고르고 [적용]한다.

### 1-4. [적용]을 바꿀 때

- 그 PC의 Workbench 작업 기준만 바뀐다(공유되지 않는다).
- Claude는 요청 답변 마지막 줄에 「작업 기준: …」으로 어떤 문서를 따랐는지 적는다.

## 2. 일정/작업

### 2-1. 일정 (구글 시트)

- 시트 「2-2.WBS 연동」을 시트 모양 그대로 보여 준다(숨김 · 색 · 상태 칩 · 간트 · 오늘 선).
- 칸을 고치면 그 칸만 시트에 바로 저장된다. 드롭다운 칸은 시트와 같은 목록에서 고른다.
- 주간 진행 현황의 숫자에도 반영된다.

### 2-2. 주간 진행 현황 (읽기만)

- **시트**: 이번 주 마감 업무, 진행 중 · 리뷰 · 완료 수, 개발사 공유 대상, 차주 일정
- **정책서 · 임시 정책**: 정책 변동 사항, 주요 내용
- **회의록**: 그 주 회의 내역(여러 개면 넘겨 보기)

### 2-3. 회의록

1. 회의를 등록한다(일시 · 제목 · 참석자).
2. 참석자가 **각자 자기 내용**을 쓴다(사람마다 파일 하나, 내 것만 고친다).
3. [요약 정리] → Claude가 작성분을 합쳐 **정리본**을 쓴다.
4. 정리본에서 Claude가 찾아 올린다:
   - 정책을 바꾸기로 한 것 → **임시 정책(PV)**
   - 더 논의할 것 → **내부 논의(PD)**
   - 고객 답을 기다리는 것 → **고객 논의(CA)**
5. 임시 정책 · 논의·결정 탭에 나타난다 → [2-5](#2-5-임시-정책-pv) · [2-6](#2-6-논의결정-내부-pd--고객-ca)으로 이어진다.

### 2-4. 화면설계서 작업대기 (읽기만)

- 모든 화면 정의서의 「반영 대기 목록」과 `screen-fixes/`를 모아 보여 준다(메뉴별, 많은 순).
- **줄이 늘어나는 경우**
  - 문서 수정 ([1-1](#1-1-정책서--작업규칙--기준데이터--화면-정의서-항목을-고칠-때) 5)
  - 임시 정책 승인 ([2-5](#2-5-임시-정책-pv))
  - 논의 답 반영 ([2-6](#2-6-논의결정-내부-pd--고객-ca))
- **Workbench로 보내기**: 화면을 고르고 반영 대기 줄을 골라 [고른 줄로 Workbench 수정 요청] → 유형 「화면설계서 반영」 요청이 만들어진다(위치 = 화면 정의서의 `figma:` 링크). 요청한 줄에는 요청 번호 · 상태가 보인다.
- **줄이 빠지는 경우**: 그 요청이 「완료」되면 Claude가 그 줄들의 상태를 「반영 완료 (날짜)」로 바꾼다. 직접 화면을 다시 그린 경우에도 상태를 「반영 완료 (날짜)」로 바꾸면 빠진다.

### 2-5. 임시 정책 (PV)

- **생기는 곳**
  - [＋ 새 임시 정책]
  - 회의록 요약 정리
  - Workbench 요청을 정책과 다르게 고쳤을 때
  - 논의 답을 승인 담당자가 아닌 사람이 냈을 때
- **겹칠 때**: 같은 정책을 바꾸는 승인 대기 PV가 있으면, 내용이 같을 때 그 PV에 합치고 다를 때 **A/B 선택 문서**로 만든다.
- **[승인] · [A안 승인] · [B안 승인]**
  1. Claude가 PV의 상태 · 결정 표를 고친다.
  2. 「영향 화면」마다 반영 대기 줄을 더한다 → 작업대기에 나타난다.
  3. 승인 담당자가 정책서에 반영하면 [1-1](#1-1-정책서--작업규칙--기준데이터--화면-정의서-항목을-고칠-때) 흐름이 시작된다.
- **[반려]**: 사유를 적는다 → Claude가 PV를 `closed/`로 옮긴다. 적용했던 화면은 원래 정책으로 되돌릴 대상이 된다.

### 2-6. 논의·결정 (내부 PD / 고객 CA)

- **생기는 곳**
  - 회의록 요약 정리
  - Workbench에서 정하지 못해 보류된 요청
  - Claude 작업 중 논의가 필요한 것
- **[답변하기]**
  1. 답 · 날짜 · 근거를 보낸다(고객 논의는 회의록 · 메일 근거 필수).
  2. Claude가 **정리안**을 보여 준다(결정 · 바뀌는 것 · 확인 필요). 이 단계에서는 아무것도 고치지 않는다.
  3. [확인 · 반영] → Claude가 함께 고친다.
     - 항목 파일의 결과 · 상태
     - 승인 담당자의 답이면 정책서 수정([1-1](#1-1-정책서--작업규칙--기준데이터--화면-정의서-항목을-고칠-때)로), 아니면 PV 등록([2-5](#2-5-임시-정책-pv)로)
     - 관련 화면의 반영 대기 줄 추가([2-4](#2-4-화면설계서-작업대기-읽기만)로)

## 3. Figma Workbench

### 3-1. 수정 요청 등록

- 「대기」로 들어간다. 수정 가능 페이지의 프레임만 반영하고, 다른 페이지 요청은 「보류」된다.

### 3-2. Claude 처리 (요청마다 하나씩)

1. 「진행 중」으로 바뀐다(토큰 사용량 재기 시작).
2. **적용한 UX 문서 5종을 읽고** Figma에 반영한다.
3. 프레임 캡처를 새로 받는다.
4. 「완료」로 바꾸고 무엇을 고쳤는지 답변에 적는다.
5. 결과가 남는다:
   - 변경 이력(공유) · 사용량 통계
   - 그 화면을 쓰는 프로토타입은 「갱신 필요」가 되고 맞추기 작업이 쌓인다.

### 3-3. 처리 도중 갈라지는 경우

- **해석이 모호할 때**: 「보류」로 바뀌고 Claude가 질문 · 선택지를 보낸다 → Workbench나 변경 이력에서 답하면 다시 「대기」.
- **다른 작업자와 같은 프레임일 때**: 「겹침 대기」로 기다렸다가 앞 요청이 끝나면 이어서 처리한다.
- **정책과 다르게 고쳐야 할 때**: 요청대로 고치고 임시 정책을 등록한다([2-5](#2-5-임시-정책-pv)).
- **정할 수 없을 때**: 보류하고 내부 논의로 올린다([2-6](#2-6-논의결정-내부-pd--고객-ca)).

### 3-4. Figma에서 직접 고칠 때 (Common UX Sync 플러그인)

- 그 프레임 캡처만 자동으로 들어온다.
- 저장소(정책서 · 화면 정의서)에는 반영되지 않는다. 반영은 「저장소 → Figma」 한 방향뿐이다(헌법 6조).

## 4. 변경 이력

- 모든 PC의 Workbench 요청 기록을 보여 준다(등록 · 진행 중 · 보류 · 완료 · 캡처).
- [다시 진행] · [답하기] → 요청이 [3. Workbench](#3-figma-workbench) 흐름으로 돌아간다.
- UX 문서의 수정 기록은 여기가 아니라 **UX 문서 › 변경이력**에만 남는다.

---

## 5. 아직 자동으로 이어지지 않는 곳

1. **Claude 규칙에 맡긴 연결**: 회의록 → PV · PD · CA, 문서 수정 → 반영 대기 줄, Workbench → PV · PD는 CLAUDE.md의 처리 규칙이다. Claude가 그 규칙을 따를 때만 이어지고, 화면에서 따로 확인하는 장치는 없다.
2. **PV 승인 후 정책서 반영**: 정책서 본문 수정은 승인 담당자 몫이다(규칙). 승인 담당자도 아직 정해져 있지 않아, 일정/작업 쓰기 권한이 있으면 누구나 승인 버튼이 보인다.
3. **작업대기에서 만든 요청이 아닌 Workbench 수정**: 다른 경로로 화면을 고치면 반영 대기 줄은 저절로 「반영 완료」가 되지 않는다(작업대기에서 만든 요청만 줄이 연결된다).
