# 액션별 동작 흐름

> 일정/작업 · UX 문서 · Figma Workbench · 변경 이력이 서로 이어져 동작하는 방식을 액션마다 정리한 문서입니다. (2026-11-12 기준 — CURECA_AI 새 흐름: 케이스 · 단계, 논의 대상, 반영 대기 새 칸, 공통 기준 하나)
>
> 2026-11-12에 예전 흐름(임시 정책 승인 · 내부/고객 논의 · 유형별 수정 요청)을 바꿨습니다(v0.23.0). CURECA 문서는 같은 날 CURECA_AI 새 구조로 통째로 교체했습니다. 작업 기준은 카테고리마다 [적용](UX가이드는 파일마다)이라, 단계 문서가 없는 팀(STAgora 등)은 적용한 작업규칙대로 예전처럼 처리됩니다.

## 0. 큰 그림

```
     ┌─────────────── UX 문서 = 규칙 저장소 (.history/guides, CURECA_AI 구조) ───────────────┐
     │ 작업규칙(work-rules.md · 헌법 · flow/ · reference-rules/) · 정책서 · 기준데이터 ·        │
     │ 화면 정의서 → 카테고리마다 하나 [적용] (이 PC의 모든 파일)   UX가이드 → Figma 파일마다 [적용] │
     └────────┬──────────────────────────────┬──────────────────────────────┬───────────────┘
   단계 문서대로 작업 │                         결정을 반영 │                 화면 MD의 반영 대기 목록 │
              ▼                                ▼                                   ▼
  Figma Workbench ──── 작업 기록(work-logs/) ──▶ 일정/작업                일정/작업 › 화면설계서 작업대기
  케이스 1 · 2 · 3       0 → 7단계, 단계 하나 = 요청 하나   › 작업 기록 · 논의 대상       └─ 고른 항목 → 케이스 1 요청
        │  정할 것이 생기면 ──────────────▶ 논의 대상(discussions/DS-*) ──결정──▶ 정책서 · 영향 화면 반영 대기
        └──▶ 변경 이력(공유) · 캡처 · 프로토타입 「갱신 필요」
```

- **기준은 적용한 UX 문서다.** 처리하는 Claude는 적용한 작업규칙을 읽는다. 그 작업규칙에 단계 문서가 있으면(CURECA 작업규칙) `work-rules.md`(CURECA_AI의 `CLAUDE.md`) → 헌법 → `flow/` 단계 문서 순서로, 없으면(STAgora 등) 그 작업규칙대로 처리한다. 프로그램 폴더의 `CLAUDE.md` · `docs/claude/`는 프로그램 조작(API · 캡처 · 폰트 · 작업 대기열)만 다룬다.
- **작업규칙 · 정책서 · 기준데이터 · 화면 정의서는 작업자가 카테고리마다 하나를 [적용]**(이 PC의 모든 파일), **UX가이드는 Figma 파일마다** 고른다(PC 화면 · 모바일).
- **처리는 Claude가 한다.** 요청 · 작업은 대기열에 쌓이고 백그라운드 감시(시작 안내 7단계)가 Claude에게 넘긴다.
- **기록은 공유된다.** `.history`에 쌓여 깃(`history` 브랜치)으로 모든 PC에 공유된다. UX가이드 「적용」과 프로토타입만 PC마다 따로다.

## 1. Figma Workbench (화면설계)

### 1-1. 요청 등록

- 입력창 첫 선택이 **케이스**다: 케이스 1 부분 수정(고도화) · 케이스 2 신규 화면 · 케이스 3 기존 화면 다시 그리기 · 질문 · 그 밖.
- 옆의 **작업 기록**에서 「새 작업 · 0단계부터」 또는 진행 중인 작업(제목 · 지금 단계 · 요청자)을 고른다. 마우스를 올리면 그 작업의 `다음:` 줄이 보인다.
- 요청은 「대기」로 들어간다. 수정 가능 페이지의 프레임만 반영하고, 다른 페이지 요청은 「보류」된다.
- 이 Figma 파일에 적용한 UX가이드가 없으면 입력창 위에 알림이 뜬다(Claude는 화면설계 요청을 「보류」).

### 1-2. Claude 처리 (요청 하나 = 단계 하나)

1. 「진행 중」(토큰 사용량 재기 시작).
2. 규칙 저장소의 `work-rules.md` → 헌법 → `flow/README.md` → 그 단계 문서를 읽는다.
   - 새 작업이면 0단계: `work-logs/YYYYMMDD-{요청자}-{대상}.md` 작업 기록을 만들고 겹침을 본다.
   - 고른 작업이면 그 작업 기록에서 관문이 빈 첫 단계와 `다음:` 줄로 이어 간다.
3. 그 단계의 끝 관문까지 하고 멈춘다.
   - 요청자 확인 관문(1 · 2 · 4단계): 「보류」 + 질문 → Workbench · 변경 이력에서 답하면 기록하고 「완료」.
   - 겹침 없음 · 기계 검사 · 질문 대기 0개: 통과하면 「완료」.
   - 4 ~ 7단계 문서가 아직 비어 있어 3단계까지 하고 다음을 묻는다.
4. Figma를 고친 단계는 캡처를 새로 받고, 답변에 `케이스 n · n단계 · 작업 기록`과 한 일, `작업 기준: basis …`을 적는다.
5. 결과: 변경 이력(공유) · 사용량 통계, 작업 기록의 단계 표 · `다음:` 줄, 그 화면을 쓰는 프로토타입 「갱신 필요」.
6. 다음 단계는 작업자가 같은 작업 기록을 골라 새 요청으로 보낸다.

### 1-3. 처리 도중 갈라지는 경우

- **정해야 할 것이 생길 때**: 화면에는 정해진 순서(기존 원본 → 정책서 → 공통 UX → 같은 메뉴의 다른 화면)로 그리고 빨간 `※ 질문 대기`, 정책을 정해야 하면 **논의 대상**으로 올린다([2-3](#2-3-논의-대상)). 질문 대기가 남아 있으면 7단계를 통과하지 못한다.
- **다른 작업자와 같은 프레임 · 같은 CID · 같은 정책**: 0단계 겹침 확인(작업 기록 대상)과 프레임 「겹침 대기」.
- **테스트로**: 요청 글에 「테스트로」 · 「반영하지 말고」 → 순서는 같고 저장소는 고치지 않는다(작업 기록 · 화면 MD는 `workbench/test-work/`, Figma 섹션 이름 뒤 `(테스트 N)`).

### 1-4. Figma 댓글 (토큰이 있을 때)

- 캡처 위에 Figma 댓글이 핀으로 보인다(누르면 대화, 「해결됨」을 켜면 해결된 것도).
- **「＋ 댓글」**을 켜고 캡처에서 자리를 누르면 그 프레임 · 그 자리에 새 댓글을 쓴다. 댓글 창 아래 칸에서 **답글**을 쓴다(Ctrl+Enter). 토큰 주인의 Figma 계정으로 올라가고, 토큰 권한에 Comments: Read and write가 있어야 한다(서버 `POST /api/figma {action:'comment'}`).

### 1-5. Figma에서 직접 고칠 때 (Common UX Sync 플러그인)

- 그 프레임 캡처만 자동으로 들어온다.
- 저장소(정책서 · 화면 정의서)에는 반영되지 않는다. 반영은 「저장소 → Figma」 한 방향뿐이다(헌법 6조).

## 2. 일정/작업

### 2-1. 일정 (구글 시트 · Azure DevOps)

- 시트 「2-2.WBS 연동」을 시트 모양 그대로 보여 준다(숨김 · 색 · 상태 칩 · 간트 · 오늘 선). 칸을 고치면 그 칸만 시트에 저장된다.

### 2-2. 주간 진행 현황 (읽기만)

- **시트**: 이번 주 마감 업무, 진행 중 · 리뷰 · 완료 수, 개발사 공유 대상, 차주 일정
- **정책서 · 논의 대상**: 정책 변동 사항(신규 · 변경), 논의 중인 논의 대상, 주요 내용
- **회의록**: 그 주 회의 내역

### 2-3. 논의 대상

- 정책 · 화면에서 **정해야 할 것을 한 리스트로** 받는다(`discussions/DS-*.md`, 쓰는 법 `reference-rules/discussions.md`). 임시 정책 · 내부 논의 · 고객 논의를 따로 두지 않는다.
- 상태 넷: 논의 중 · 결정 · 보류 · 종료. 「진행 중」 보기는 묶음 여섯: 결정 · 반영할 것 / 논의 중 · 고객 / 논의 중 · 내부 / 결정 · 작업 중 / 보류 / 후속 확인 필요.
- **생기는 곳**: 화면설계 작업(2단계 정책 수정 범위, 3 · 4 · 5단계 질문 대기), 회의록 정리, 고객 · 개발사 이슈, 정책 정리, 주기 점검, [＋ 새 논의 대상].
- **[답변하기] · [반영 정리안]**
  1. 답 · 날짜 · 근거를 보낸다(고객이 정하는 항목은 회의록 · 메일 근거 필수). 「결정 · 반영할 것」은 답 없이 [반영 정리안].
  2. Claude가 **정리안**(결정 문장 · 영향 범위 · 바뀌는 것 · 후속 확인)을 보여 준다. 이 단계에서는 아무것도 고치지 않는다.
  3. [확인 · 반영] → Claude가 DS 파일(논의 기록 · 결정 · 반영), 정책서, 영향 화면의 반영 대기 항목(타입 「논의 결정」)을 고친다. **화면 작업이 있는 결정**(`work`에 작업 기록)은 그 작업 7단계 완료 때 한꺼번에 반영한다(헌법 4조).

### 2-4. 회의록

1. 회의를 등록한다(일시 · 제목 · 참석자). 참석자가 **각자 자기 내용**을 쓴다.
2. [요약 정리] → Claude가 작성분을 합쳐 **정리본**을 쓴다.
3. [정책 · 논의 뽑기] → Claude가 정리본에서 정해진 것 · 논의가 남은 것을 **논의 대상**으로 올린다(이미 있는 항목이면 그 항목에 기록). 회의록에 「이 회의에서 나온 논의 대상」으로 이어진다.
4. 작성 화면 「열린 논의 대상을 안건으로 넣기」로 다음 회의 안건을 넣는다.

### 2-5. 화면설계서 작업대기

- 모든 화면 정의서의 「반영 대기 목록」(`ID · 타입 · 변경 전 · 변경 후 · 근거 · 상태`, 쓰는 법 `reference-rules/pending-changes.md`)을 메뉴별로 모아 보여 준다. 상태: 대기 · 작업 중 (작업 기록) · 반영 완료 (날짜) · 제외 (날짜, 이유).
- **항목이 생기는 때**: 화면설계 작업의 7단계 완료(결정 반영 · 다른 화면 파급), 화면 작업이 없는 결정 반영, 기준 자료 · 외부 원본 변경, 주기 점검. (작업 중 0 ~ 6단계에는 만들지 않는다.)
- **[고른 항목으로 화면설계 작업(케이스 1) 요청]** → Workbench에 케이스 1 · 새 작업 요청이 만들어진다(위치 = 화면 정의서의 `figma:` 링크). 1단계에서 그 항목을 「이번에 반영」으로 고르면 `작업 중`, 7단계 완료 때 `반영 완료`.

### 2-6. 작업 기록

- 화면설계 작업 하나에 기록 하나(`work-logs/*.md`, 쓰는 법 `reference-rules/work-log.md`). 진행 중 · 끝남 · 멈춤으로 나눠, 케이스 · 요청자 · 메뉴 · 대상 CID · 지금 단계(0 ~ 7 막대) · `다음:` 줄 · 기록 본문을 보여 준다.
- [Workbench에서 이어 하기] → Workbench 입력창에서 그 작업 기록을 골라 다음 단계를 요청한다.

## 3. UX 문서

### 3-1. 작업규칙 · 정책서 · 기준데이터 · 화면 정의서

- 탭 위쪽 「내 작업 기준」에서 카테고리마다 하나를 [적용]한다(이 PC에만, 이 PC의 모든 파일에 같이). Claude는 적용한 문서만 따른다.
- **고칠 때**: 보기 화면의 「수정 요청」 → Claude가 **원본 파일을 직접** 고친다(수정본을 따로 남기지 않음). 정해지지 않은 정책 · 규칙 변경이면 고치지 않고 논의 대상으로 올린다(헌법 4조). 고친 뒤 영향 화면에는 반영 대기 항목(타입 「기준 자료 변경」 · 「논의 결정」)을 만든다 → 작업대기에 나타난다.
- 작업규칙의 첫 문서는 `work-rules.md`(CURECA_AI의 `CLAUDE.md`를 이름만 바꿔 분리)다.

### 3-2. UX가이드 (Figma 파일마다)

- UX가이드 탭 위쪽에서 Figma 파일을 고르고 가이드를 [적용] → 그 파일에만. Workbench 알림의 [「가이드」 적용]으로도 된다.
- 고칠 때는 수정본으로 남고, 그 가이드를 적용한 파일에 「고칠 화면 찾기」가 안내된다.

### 3-3. 새 문서를 만들 때

- 탭의 「＋ 새 {카테고리} 만들기」 → Figma 링크나 참고 파일. UX가이드는 만든 뒤 파일마다 [적용]한다.

## 4. 변경 이력

- 모든 PC의 Workbench 요청 기록을 보여 준다(등록 · 진행 중 · 보류 · 완료 · 캡처). 케이스 요청은 「케이스 n · n단계」로 보인다.
- [다시 진행] · [답하기] → 요청이 [1. Workbench](#1-figma-workbench-화면설계) 흐름으로 돌아간다.
- UX 문서의 수정 기록은 **UX 문서 › 변경이력**에 남는다(규칙 저장소 파일을 직접 고친 것은 깃 기록으로).

## 5. 아직 자동으로 이어지지 않는 곳

1. **Claude 규칙에 맡긴 연결**: 단계 진행 · 관문, 회의록 → 논의 대상, 결정 → 정책서 · 반영 대기 항목은 규칙 저장소 문서를 Claude가 따를 때만 이어진다. 화면에서 따로 확인하는 장치는 없다(기계 검사 스크립트는 규칙 저장소에서 만들 예정).
2. **4 ~ 7단계 문서가 비어 있음**: 규칙 저장소에서 채우는 중이라, 지금은 3단계 끝 관문까지 하고 멈춘다.
3. **옛 항목 옮기기**: 예전 PD · CA · PV를 논의 대상(DS)으로 옮기는 일은 규칙 저장소 할 일(todo 1-7)이다. 옮기기 전까지 `old-pending/` · `old-customer-agenda/` · `old-provisional/`은 무엇이 정해지지 않았는지 확인하는 용도로만 읽는다.
4. **다른 PC**: 아직 예전 흐름이다. 대표 저장소로 옮기는 날 프로그램 배포와 함께 바꾼다(규칙 저장소 `background/program-hurdles.md` H5).
