## 헌법

> 상태: v1.4 (2026-11-03). v1.2 확정 (2026-10-30)에서 4조와 개정 절차를 바꿈 (v1.3, v1.4). v0.2(`background/rules-review-draft.md` "헌법 초안")를 바탕으로 정리했습니다.

### 최상위 원칙

**사람의 검체를 다루는 장비이므로, 정확성이 속도보다 우선한다.**

이 헌법은 모든 룰 문서와 Claude 작업에 우선합니다. 룰 문서가 헌법과 다르면 헌법을 따르고, 그 룰 문서를 고칩니다.

우리가 지키려는 일관성은 "누가 작업해도 같은 결과물"이 아니라 "누가 작업해도 같은 검증 기준을 통과하는 결과물"입니다. 이를 위해 Claude가 읽는 자료와 실행 순서를 고정하고, 결과를 같은 기준으로 검증합니다.

### 조항

#### 1조. 정확성 우선

검증 관문을 통과하지 못한 변경은 일정과 관계없이 다음 단계로 넘어가지 않는다.

> 배경: 하나의 변경이 장비사, 개발사, 내부 디바이스팀까지 파급된다.

#### 2조. 단일 기준

정책과 화면의 유일한 기준은 이 저장소다. Teams, 회의록, Figma 코멘트, 고객사 자료는 근거 자료이며, 저장소에 기록되기 전까지 효력이 없다. 같은 정책이 여러 곳에서 다르면 출처 위치가 아니라 결정 기록으로 최신을 판단한다.

> 배경: 정책이 Teams, 회의록 시트, Figma 정책서, 디스크립션에 흩어져 최신본을 찾기 어려웠다.

#### 3조. 정책은 한 곳에서 정의한다

정책은 정책서에만 정의한다. 화면 디스크립션은 정책을 다시 쓰지 않고 정책 ID로 참조하며, 정책 요약과 정책서 위치 링크는 정책서에서 자동으로 가져와 붙인다.

> 배경: 디스크립션마다 정책을 녹여 쓰다 보니 변경 때 일부 화면만 고쳐졌다.

#### 4조. 공통 자료는 승인 담당자가 승인한 것만 반영하고, 화면은 작성자가 책임진다

정책서, 룰 문서 등 공통 자료(팀 프로그램의 UX 문서)는 승인 담당자 1명만 고친다. 작업 중 기존 정책을 바꿔야 하면 작성자는 공통 자료를 직접 고치지 않고 임시 정책으로 등록해 그 기준으로 작업한다. 승인 담당자는 작성자와 의견을 나눠 승인하거나 반려하고, 승인한 것만 공통 자료에 반영한다. 화면설계서는 작성자가 책임지고 고치며, 화면마다 따른 공통 규칙 버전과 적용한 임시 정책을 남긴다. 다만 영향 범위에서 찾은 다른 작성자의 화면은 작은 변경이면 함께 고치고, 이력을 남겨 작성자에게 알린다. Claude는 제안하고 실행하며, 결정은 사람이 한다.

> 배경: 같은 고객 발언도 사람마다 다르게 해석했다. 승인 단계가 많으면 초기 운영이 막힌다.

#### 5조. 변경은 영향 범위 전체를 한 단위로 처리한다

영향받는 화면을 모두 확인하기 전에는 수정을 시작하지 않는다. 담당 영역을 넘는 화면은 각 작성자에게 알려 같은 변경 안에서 함께 고친다.

> 배경: 연관 화면을 놓쳐, 이미 고친 화면까지 되돌린 사례가 있었다.

#### 6조. 반영은 한 방향으로만 흐른다

저장소 → 작업 페이지 → 고객 컨펌 페이지 → 개발사 공유 페이지 순서로만 반영한다. 모든 수정은 저장소에 먼저 반영한 뒤 Figma로 내려보내며, 하위 페이지를 고쳐 상위로 복사하지 않는다. 팀 프로그램을 쓰든 Claude에 직접 요청하든 같은 룰과 같은 순서를 따른다.

> 배경: 공유 페이지에서 고친 뒤 작업 페이지에 붙여넣어 최신본이 이전본으로 되돌아갔다. 룰이 특정 프로그램에 묶여 있으면 프로그램이 멈췄을 때 작업도 멈춘다.

#### 7조. Claude는 근거와 순서대로 작업한다

Claude는 기준 출처 목록(`sources.md`)에 있는 근거로만 작업하고, 근거가 없거나 서로 충돌하면 만들어내지 않고 질문으로 남긴다. 작업은 룰에 정한 실행 순서를 따르며, 작업 하나에 대화 하나로 시작한다. 예전 문서의 모호한 표현은 추정하더라도 단정하지 않고 묻는다.

> 배경: 개인별로 쓰던 Claude 결과가 사람마다 달랐다.

#### 8조. 설계는 실제로 작동해야 완성이다

모든 화면 흐름은 장비 상태, Service Mode, User Type별 권한, 정책에 비추어 점검한다. 사용자 실수가 가능한 지점에는 정책에 정의된 안내와 알럿이 있어야 한다. 화면은 6개 언어 중 가장 긴 표현에서도 깨지지 않아야 한다. 신규 메뉴·화면에 노출 모드와 권한 정의가 없으면 정의부터 요청한다. 정상 흐름만 그린 설계는 미완성이다.

> 배경: 장비 상태값과 사용자 작업이 많아 정책 위반 흐름을 사람이 다 검증하기 어렵다. 모드·권한 정의가 화면마다 흩어져 있었다.

#### 9조. 모든 결정은 추적 가능해야 한다

누가, 언제, 어떤 미팅에서, 무엇을 근거로 결정했는지 남긴다. 폐기된 화면과 정책도 지우지 않고 근거와 함께 보관한다.

> 배경: 약 6개월 뒤 인허가 단계에서 결정 근거가 필요해질 가능성이 높다.

#### 10조. 하나의 개념은 하나의 말로 쓴다

모든 문서는 용어집의 표준어만 쓴다. 대화에서는 편한 표현을 써도 되지만, 문서로 옮길 때는 표준어로 바꾼다. 용어집에 없는 새 용어는 문서에 쓰기 전에 용어집에 먼저 올린다.

> 배경: 같은 개념을 계정 유형, 사용자 유형, User Type, Account Type으로 섞어 써 검색과 검증이 어려웠다.

### 운영 원칙

- **룰은 최소로 시작한다.** 실제로 생긴 문제를 막기 위해서만 룰과 승인 단계를 더한다.
- **적용 범위는 UX 4명이다.** UI팀과는 상태값처럼 함께 쓰는 부분만 공유한다.
- **룰은 도구에 묶이지 않는다.** 모든 룰은 저장소 문서로만 정의하고, 팀 프로그램, Claude Code, Claude 채팅 어느 경로에서 작업해도 같은 룰을 읽는다. 프로그램이 멈춰도 Claude에 직접 요청해 같은 룰로 작업을 이어 간다.
- **git 숙련도에 기대지 않는다.** 브랜치, 커밋, PR은 프로그램이나 Claude가 처리하고, 팀원은 요청과 확인에 집중한다.

## 변경 흐름

> 상태: 초안 v0.4 (2026-11-03). v0.4에서 회의 중심 순서를 등록 → 승인·반려 → 반영 세 단계로 줄이고, 알림은 추후 연동으로 둠. 근거: 헌법 4·5조, `background/rules-review-draft.md`의 "공통 자료 변경 흐름".

공통 자료(팀 프로그램의 UX 문서)는 승인 담당자만 바꾸고, 화면설계서는 작성자가 책임지고 바꿉니다. 작성자는 기존 정책을 바꿔야 하면 임시 정책으로 등록해 그 기준으로 작업합니다.

### 1. 대상 구분

| 구분 | 대상 | 변경 방법 |
| --- | --- | --- |
| 공통 자료 | 헌법, 룰 문서, 정책서, Service Mode·권한 매트릭스, 장비 상태 정의서, 알럿 카탈로그, Common UX, 용어집 | 임시 정책 등록 → 승인 담당자 승인 → 승인 담당자가 반영 |
| 화면설계서 | CID별 화면설계서 | 작성자가 직접 수정. 다른 사람은 작성자에게 요청 |
| 언어셋 | 6개 언어 문구 | 내부 논의 대상 아님. 고객사 컨펌으로 확정 (`rules/language-set.md`) |

### 2. 공통 자료 변경 순서

1. **등록:** 작업 중 기존 정책·룰을 바꾸거나 더해야 하면 공통 자료를 직접 고치지 않고, Claude에게 임시 정책(PV)으로 등록해 달라고 한 뒤 그 기준으로 작업합니다. 이번 작업에서는 적용한 화면만 고치고, 영향받는 다른 화면은 PV 파일의 "영향 화면"에 적습니다(`rules/provisional-policy.md`). 등록할 때 Claude가 "승인 대기" 임시 정책을 확인해, 같은 규칙을 다르게 바꾸는 것이 있으면 두 안을 A/B 선택 문서로 합칩니다(`rules/provisional-policy.md` 6절).
2. **승인·반려:** 승인 담당자가 화면 작성자와 의견을 나눠 승인하거나 반려합니다. A/B 선택 문서는 한 안을 골라 승인합니다. 회의를 기다리지 않아도 됩니다. UX 문서의 임시 정책 메뉴에서 [승인]·[반려] 버튼으로 기록합니다.
3. **반영:** 승인된 것만 승인 담당자가 공통 자료에 반영하고 공통 규칙 버전을 올립니다(예: 태그 `rules-v0.3`). 영향 화면 작성자는 새 버전에 맞춰 화면을 고치고, 화면 머리말의 `rules_version`을 바꾸고 `provisional`에서 PV ID를 뺍니다.

- 공통 규칙은 대표 저장소 기준 브랜치에서만 읽으므로, 승인 전의 임시 정책은 그 PV ID를 적은 작업에서만 쓰입니다.
- 작업에 쓰지 않고 논의만 필요한 것은 협의 대기(PD)로 올립니다(3절).
- 영향받는 작성자는 UX 문서의 임시 정책 메뉴에서 확인합니다. 메신저(Slack 등) 알림은 추후 연동합니다.

### 3. 협의 대기 항목 관리

#### 항목 하나 = 파일 하나

- 협의 대기 항목은 한 파일에 모으지 않고, 항목마다 `pending/` 아래 파일 하나로 만듭니다. 여러 사람이 동시에 항목을 올려도 git 충돌이 나지 않게 하기 위해서입니다.
- 파일 이름은 항목 ID입니다: `PD-0001.md`. 번호는 네 자리 일련번호이며, `pending/`과 `pending/closed/`에 있는 가장 큰 번호에 1을 더합니다. 한 번 쓴 번호는 다시 쓰지 않습니다.
- 같은 번호가 동시에 만들어져 충돌하면, 나중에 반영되는 쪽의 번호를 바꿉니다.
- `templates/pending-item.md`를 복사해 만들고, 제안 내용, 이유와 근거, 영향 범위, 제안자, 제안일을 모두 채웁니다. 영향 범위를 모르면 비워 두지 않고 "확인 필요"라고 적습니다.

#### 항목 상태

| 상태 | 의미 | 파일 위치 |
| --- | --- | --- |
| 대기 | 올라왔고 아직 논의 전 | `pending/` |
| 보류 | 결정을 미룸 | `pending/` |
| 합의 | 합의함, 아직 반영 전 | `pending/` |
| 반영 완료 | 공통 자료에 반영됨 | `pending/closed/` |
| 기각 | 반영하지 않기로 함. 사유를 남김 | `pending/closed/` |
| 병합 | 다른 항목에 합쳐짐. 합쳐진 항목 ID를 남김 | `pending/closed/` |

- 닫힌 항목(반영 완료, 기각, 병합)은 지우지 않고 `pending/closed/`로 옮깁니다(헌법 9조).
- 논의 결과는 각 항목 파일의 "미팅 결과"에 날짜와 함께 적습니다.

#### 효력

- 협의 대기 항목은 승인 전까지 효력이 없습니다. Claude는 "대기", "보류", "합의" 항목을 근거로 화면을 그리지 않습니다.
- 작업에 먼저 써야 하는 변경은 임시 정책(PV)으로 등록하고 화면에 "임시 정책 포함" 표시를 붙입니다(`rules/provisional-policy.md`).

### 4. 긴급 변경

따로 긴급 절차는 없습니다. 바로 반영이 필요하면 승인 담당자가 바로 승인해 반영합니다. 자동 검증은 그대로 거칩니다.

### 5. 화면설계서 변경

- 작성자가 오너로서 직접 고칩니다.
- 다른 사람이 수정을 원하면 작성자에게 요청합니다. 단, 영향 범위에서 찾은 작은 변경은 함께 고치고 이력과 알림을 남길 수 있습니다(`rules/claude-work.md` 6절). Claude는 다른 팀원 계정에 직접 메시지를 보낼 수 없으므로, 요청은 git 이슈로 남깁니다.
- 변경 규모에 따른 상태 처리(작업 중으로 되돌림 / 변경 예정 표시)는 `rules/status-lifecycle.md`를 따릅니다.

### 6. 개발사 전달

정해진 주기 없이 매번 협의한 공유일에, 그때까지 확정된 범위를 묶어 전달합니다.

## Claude 작업 규칙

> 상태: 초안 v0.5 (2026-11-03). v0.5에서 공통 규칙 버전 확인·기록과 임시 정책 작업을 더함 (헌법 4조 v1.3). 9절의 남은 항목은 다른 룰이 정해진 뒤 작성합니다.

### 2. 공통 순서

모든 작업은 아래 순서를 따릅니다. 읽기만 하는 작업은 3, 5, 8단계를 건너뜁니다.

| 6. 작업 | 템플릿을 쓰고, 표준어만 쓰고, 정책은 ID로만 참조합니다. | 3·10조 |

| 8. 기록 | 상태·표시 갱신, 화면 머리말의 공통 규칙 버전(`rules_version`)과 임시 정책(`provisional`), 변경 이력, 번역 요청 목록, 협의 대기·임시 정책 연결, 커밋을 합니다. 이미 개발사에 전달된 화면을 바꿨으면 버전을 올려야 한다고 알립니다. | 9조 |
| 9. 보고 | 3절의 형식으로 보고합니다. | 7조 |

#### 계획 확인 (5단계)

- 지금은 **모든 쓰기 작업**에서 계획을 확인받습니다. 작은 수정도 같습니다.
- 운영이 안정되면 확인 범위를 줄이는 것을 검토합니다(예: 큰 변경, 공통 자료, 다른 사람 화면이 걸린 경우만). 바꿀 때는 이 문서를 개정합니다.

#### 질문이 생겼을 때 (4단계)

- 질문과 관계없는 부분은 진행하고, 질문에 걸린 부분만 멈춥니다.
- 멈춘 부분은 결과물에 "질문 대기"로 표시하고 보고의 "질문과 미결"에 적습니다. 답을 받으면 그 부분을 이어서 작업합니다.
- 질문 대기 부분이 남아 있으면 그 결과물은 완료로 보지 않습니다.

### 5. 점검 항목 (7단계)

#### 화면 점검 목록

| 점검 | 확인할 것 |
| --- | --- |
| 상태별 화면 | 정상, 로딩, 비활성, 오류, 빈 상태, 장비 이상 화면이 있는가 |
| 장비 상태 | 장비 상태마다 허용·금지 동작이 장비 상태 정의서와 맞는가 |
| Service Mode | L-IOS Service Mode(Main Mode, Console Mode, TSS Mode)에 없는 메뉴로 보내는 흐름이 없는가. 있으면 안내가 있는가 |
| 권한 | User Type별 노출이 권한 매트릭스와 맞는가. 모드와 권한이 모두 허용할 때만 노출되는가 |
| 알럿 | 사용자가 실수할 수 있는 지점에 알럿 카탈로그의 알럿이 있는가 |
| 정책 참조 | 디스크립션이 정책을 다시 쓰지 않고 ID로 참조하는가. 임시 정책을 썼으면 "임시 정책 포함" 표시가 있는가 |
| T/L 짝 | 짝 CID 화면에도 같은 변경을 했는가 (아래 "T/L 짝 화면") |
| 다국어 | 최장 언어 화면에서 레이아웃이 깨지지 않는가. 새 문구를 번역 요청 목록에 올렸는가 |
| 용어 | 쓰지 않는 표현이 남아 있지 않은가 |

#### 변경 규모에 따른 점검 범위

- **큰 변경** (흐름, 레이아웃, 상태값, 컴포넌트 구성이 바뀜): 화면 점검 목록 전부를 점검합니다.
- **작은 변경** (문구, 라벨, 디스크립션, 수치만 바뀜): 바뀐 부분에 걸린 항목과 다국어, 용어, T/L 짝만 점검합니다. 나머지는 보고의 검증 결과에 "작은 변경이라 생략"으로 적습니다.
- 신규 화면 설계(1)와 화면 검증(7), 기존 화면 재설계(21)는 항상 전부 점검합니다.

#### T/L 짝 화면

- T-IOS와 L-IOS 짝 화면은 보통 거의 똑같이 고쳐야 합니다. 한쪽 화면을 고치면 짝 CID를 항상 영향 범위(3단계)에 넣습니다.
- 작업 결과에서 짝 중 한쪽만 고쳐져 있으면, 끝내기 전에 다시 확인하고 다른 쪽도 고칠지 요청자에게 묻습니다. 답을 받기 전까지 그 부분은 "질문 대기"입니다.
- 다른 쪽을 고치지 않기로 하면 그 이유를 화면설계서 변경 이력에 남깁니다.

#### 개발사 전달 전 점검 (12번 유형)

- 전달 범위에 "임시 정책 포함", "질문 대기", "번역 대기"가 남은 화면이 있으면 목록으로 경고합니다.
- 전달할지는 담당자가 정합니다. Claude는 범위에서 빼지 않습니다.
- 담당자가 전달하기로 한 화면은 릴리즈 노트에 남은 표시를 함께 적습니다.

| | 보고 항목을 빼기 | 3절 |

#### 다른 작성자의 화면을 함께 고칠 때

- 영향 범위(3단계)에서 찾은 다른 작성자의 화면은, **작은 변경**(문구, 라벨, 디스크립션, 수치)이면 같은 작업 안에서 함께 고칠 수 있습니다. 계획 확인(5단계) 때 어느 화면이 누구 것인지 함께 보여 줍니다.
- 함께 고친 화면은 그 화면설계서의 변경 이력에 "연동 변경" 표시와 원인(CID·정책 ID), 고친 사람을 남깁니다.
- 보고의 "알릴 사람"에 그 화면의 작성자와 바꾼 내용을 적어 전달합니다.
- **큰 변경**이 필요하면 직접 고치지 않고 작성자에게 요청합니다.

### 7. 작업 하나에 대화 하나

목적은 이전 대화의 기억이 아니라 저장소를 기준으로 일하게 하는 것입니다.

- **기본:** 대화 하나에 작업 하나로 시작합니다. 같은 작업 안의 질문 답, 계획 수정은 같은 대화에서 이어 갑니다.
- **같은 대화에서 다른 작업을 요청하면:**
  1. 새 대화로 시작하기를 권합니다.
  2. 요청자가 이어서 하겠다고 하면 이어서 작업합니다. 같은 정책 때문에 두 번째 메뉴를 고치는 경우처럼 앞 작업과 이어진 일이 많기 때문입니다.
  3. 이어서 할 때, 두 번째 작업에도 공통 순서 전체(근거 다시 읽기, 점검 포함)를 적용할지 요청자에게 묻고 선택에 따릅니다. 선택한 내용은 보고의 "검증 결과"에 적습니다.
- 어느 경우든 앞선 대화 내용 자체는 근거로 쓰지 않습니다. 근거는 저장소에서 읽습니다.
- **대화가 끝날 때:** 결과물, 질문 대기, 변경 이력처럼 이어 가는 데 필요한 것은 모두 저장소에 남깁니다. 다음 사람이 저장소만 보고 이어 갈 수 있어야 합니다.
- **여러 대화에 걸치는 큰 작업**(정책서 정제 등): 진행 상황을 저장소의 작업 노트에 남기고, 다음 대화는 그 노트부터 읽고 시작합니다.

### 8. 프로그램이 멈췄을 때

룰은 모두 저장소 문서에 있으므로, 저장소를 읽을 수 있는 Claude라면 같은 순서로 작업할 수 있습니다.

| 경로 | 할 수 있는 것 |
| --- | --- |
| Claude Code (저장소를 연 상태) | 프로그램과 같이 읽기, 쓰기, 커밋 |
| Claude 채팅·프로젝트 (저장소 쓰기 불가) | 같은 순서로 결과물을 만들고, 저장소 반영은 나중에 Claude Code로 함 |

- **작업 경로 기록:** 프로그램 밖에서 작업하면 보고와 커밋 메시지에 경로를 적습니다 (예: "경로: Claude Code, 프로그램 중단 중").
- **Figma:** 프로그램이 멈춘 동안에는 저장소만 바꾸고, 바뀐 화면에 "Figma 반영 대기" 표시를 붙입니다. Figma를 직접 고치지 않습니다. 프로그램이 복구되면 표시가 붙은 화면을 한꺼번에 반영하고 표시를 뗍니다.

### 10. 외부 원본 새 버전 반영 (작업 유형 22)

이 저장소가 정리한 기준 자료가 항상 최신 기준입니다. 씨젠 문서, Common UX, IA 같은 외부 원본은 기준 자료의 출처이며, 새 버전이 와도 바로 덮어쓰지 않고 이 저장소 기준에서 무엇이 바뀌는지 확인한 뒤 반영합니다.

1. **보관:** 새 원본을 `reference/` 아래에 새 파일로 더합니다. 이전 버전은 지우지 않습니다. `reference/customer/README.md` 등 목록에 버전과 받은 날짜를 적습니다.
2. **비교:** 새 원본을 직전 원본과 비교하고, 이 저장소 기준 자료와도 비교합니다. 기준 자료의 근거 칸에 그 원본을 인용한 항목을 모두 찾습니다.
3. **변동 목록:** 바뀐 것, 새로 생긴 것, 없어진 것, 이 저장소 기준과 다른 것을 목록으로 만들어 요청자에게 보여 줍니다.
4. **애매할 때:** 무엇이 바뀐 것인지 판단하기 어려우면, 기준 자료의 근거 칸이 인용한 원본 위치(문서, 버전, 시트·프레임)를 따라가 직전 내용과 새 내용을 나란히 놓고 확인합니다. 그래도 판단이 안 되면 질문으로 남깁니다.
5. **반영:** 요청자가 합의한 것만 기준 자료에 반영하고, 근거 칸의 인용 버전을 새 버전으로 바꿉니다. 공통 자료라면 `rules/change-flow.md`를 따릅니다.
6. **기록:** 변동 목록과 처리 결과를 `reference/updates/YYYY-MM-DD_<문서 약칭>.md`에 남깁니다.

## 논의 항목 답변

> 상태: 초안 v0.1 (2026-11-04). 정하지 않은 것은 7절에 모았습니다.

논의 항목에 답을 받으면, Claude가 답을 정리해 무엇이 바뀌는지 보여 주고, 답한 사람이 확인한 뒤에 한 번에 커밋합니다. 정책과 함께 화면 정의서의 반영 대기 목록까지 고쳐서, 다음에 그 화면을 그릴 때 답이 디스크립션과 화면 예시에 들어가게 합니다.

### 1. 대상

| 구분 | 항목 | 원본 |
| --- | --- | --- |
| 내부 논의 | 협의 대기 | `pending/PD-*.md` |
| | 다시 확인할 것 | `background/worklist.md`, `background/policy-refinement.md`의 질문 |
| 고객 논의 | 고객 논의 대상 | `customer-agenda/agenda.md` (CA) |

정책 정제 중에 Claude가 질문을 모아 묻고 답을 받는 경우도 같은 순서를 따릅니다.

### 2. 어디서 답하나

- **팀 프로그램:** 일정/작업 > 논의·결정에서 항목을 열고 [답변하기]를 누르면 Claude와 대화하는 창이 열립니다.
- **프로그램이 없을 때:** Claude Code나 채팅에서 항목 ID와 답을 주면 같은 순서로 처리합니다.

### 3. 순서

1. **답 받기:** 항목 ID와 답을 받습니다. 고객 논의는 고객이 답한 날짜와 근거(회의록, 메일)도 받습니다.
2. **정리해 보여 주기:** 커밋하기 전에 Claude가 다음을 보여 줍니다.
   - 결정: 정책서 문장처럼 정해진 동작으로 씁니다. 추천처럼 쓰지 않습니다.
   - 바뀌는 것: 항목 파일의 결과 · 상태, 공통 자료(정책 · 룰)를 바꾸는 방법(4절), 화면별 반영 대기 목록 문장(5절)
   - 아직 정해지지 않은 부분은 "확인 필요"로 따로 적습니다.
3. **확인:** 답한 사람이 맞다고 하면 커밋합니다. 고칠 점을 말하면 다시 정리해 보여 줍니다. 확인 없이 커밋하지 않습니다.
4. **커밋:** 항목 파일, 공통 자료(또는 임시 정책), 반영 대기 목록을 한 커밋으로 묶습니다(헌법 5조). 커밋 메시지에 항목 ID를 적습니다.

### 4. 공통 자료가 바뀌는 답

| 답한 사람 | 처리 | 항목 상태 |
| --- | --- | --- |
| 승인 담당자 | 정책 · 룰을 바로 고치고 공통 규칙 버전을 올림 | 반영 완료 |
| 그 밖의 작성자 | 공통 자료를 직접 고치지 않고 임시 정책으로 등록 (`rules/provisional-policy.md`). 결과 칸에 PV ID | 합의 |

- **고객 논의:** 고객 논의 목록의 결정 칸에 결정 · 날짜 · 근거를 적습니다. 임시 정책이 걸려 있으면 그 PV 파일의 고객 답 표에도 적습니다. 고객이 정한 내용은 다시 정하지 않고, 정책서 문장으로 정확히 옮기는지만 확인합니다. 상태는 "결정"입니다.
- **다시 확인할 것:** 답을 `background/policy-refinement.md`에 적고, `background/worklist.md`의 항목을 체크합니다.

### 5. 화면 정의서 반영 대기 목록

- 답으로 정해진 정책을 `cids`에 둔 화면과, 걸린 임시 정책의 영향 화면 모두의 반영 대기 목록에 한 줄씩 더합니다(`rules/screen-spec.md` 1절).
- 바꿀 것 칸은 이렇게 씁니다.

| 경우 | 쓰는 법 |
| --- | --- |
| 디스크립션에 들어갈 내용 | `디스크립션에 넣음: …` |
| 숫자 형식, 단위, 상태, 칩 · 버튼 상태처럼 화면 예시에 보이는 내용 | 위 문장 뒤에 `화면 예시도 …` |
| 아직 정해지지 않은 부분 | `확인 필요: …` |

- 근거 칸에는 항목 ID와 정책(또는 PV) ID를 적습니다.
- 다른 작성자의 화면이어도 반영 대기 목록에는 줄을 더합니다. 화면 자체는 고치지 않고, 작성자가 다시 그릴 때 반영합니다(헌법 4조).
- 화면을 다시 그릴 때는 반영 대기 목록을 먼저 읽습니다(`rules/screen-spec.md` 1절).

### 1. 작업방 화면의 릴리즈 영역 (최신 화면 고르기)

작업방(`sources.md`의 작업방 메뉴 페이지)은 2.1 릴리즈를 두 번에 나눠 관리합니다. 같은 CID의 화면이 1차 영역과 2차 영역에 같은 구조로 함께 있을 수 있습니다.

| 영역 | 표시 | 뜻 |
| --- | --- | --- |
| 2.1 2차 | 민트색(#40F3EE) 세로 바 | 2차에서 고도화하거나 수정한 화면 |
| 2.1 1차 | 녹색(#84CC16) 세로 바 | 1차 화면. 바 이름이 "2.1 1차"가 아닌 녹색 바(예: "2.0 (1차)", "2.1", "2.1 고도화")도 이전 영역으로 봄 |

- **영역의 범위:** 세로 바의 세로 길이 안에서, 바 오른쪽에 놓인 화면이 그 영역의 화면입니다. 한 페이지에 바 열이 여러 개면(예: Setting 페이지) 화면 바로 왼쪽의 가장 가까운 바를 기준으로 합니다.
- **최신 화면 고르기 (CID마다):**
  1. 그 CID가 민트색 영역에 있으면 민트색 영역의 화면만 봅니다.
  2. 민트색 영역에 없고 녹색 영역에만 있으면, 2차에서 고친 내용이 없는 것이므로 녹색 영역의 화면이 최신입니다.
- 영역은 바의 색으로 구분합니다. 바 이름은 표기가 조금씩 다를 수 있습니다(예: "2.1  1차", "2.1 1치").
- **Material Setup:** 1차와 2차가 별도 페이지입니다. `Material Setup Ⓛ_2.1(2차)` 페이지(민트색 영역)를 봅니다. 1차 페이지는 기준 출처에서 뺐습니다(`sources.md`).
- 화면을 읽어 정책, 용어, 알럿, 화면 정정 대상을 정리할 때는 이 규칙으로 고른 화면만 근거로 씁니다. 이전 영역의 문구는 이미 바뀌었을 수 있습니다.

## 다국어

> 상태: 초안 v0.2 (2026-10-29). 큰 흐름만 잡은 초안입니다. 언어셋 관리 체계(엑셀 구조, ID 체계, 고유명사)는 언어셋 담당자가 담당 Claude와 협의해 이 문서를 고쳐 갑니다.

화면은 6개 언어로 서비스합니다. UX 설계는 영어로 하고, UI 작업자가 언어별 길이에 맞춰 디자인할 수 있도록 가장 긴 언어 기준의 화면을 함께 만듭니다.

### 1. 언어

| 구분 | 언어 |
| --- | --- |
| 설계 기준 | 영어 |
| 제공 언어 | 영어, 한국어, 포르투갈어, 스페인어, 이탈리아어, 프랑스어 |

### 2. 언어셋

- 6개 언어 문구는 언어셋 문서(엑셀)로 관리합니다. 문구마다 ID가 있고, 고유명사도 따로 관리합니다.
- 언어셋은 언어셋 담당자가 관리합니다. 앞으로는 언어셋 문서도 Claude가 관리하도록 바꿀 예정이며, 그 관리 체계는 담당자가 정해 이 문서에 반영합니다.
- **언어셋은 내부 논의 대상이 아닙니다.** 영어 문구는 고객사 컨펌으로 확정되고, 나머지 5개 언어 번역도 고객사를 통해 받습니다. 그래서 언어셋은 공통 자료의 주간 미팅 합의(`rules/change-flow.md`)를 거치지 않습니다.
- UX 작업에서 Claude는 언어셋을 읽기만 하고 고치지 않습니다. 번역도 만들어내지 않습니다. 새 문구는 5절의 번역 요청 목록에 올립니다.

| --- | --- | --- |
| 영어 화면 | 영어로 작성한 UX 화면 | 고객 (리뷰·컨펌) |
| 최장 언어 화면 | 같은 화면의 문구 자리마다 6개 언어 중 가장 긴 표현을 넣은 화면. 문구마다 가장 긴 언어가 다를 수 있어 여러 언어가 섞여 보임 | UI 디자이너 (언어 길이 참고) |

### 4. 작업 순서

화면을 설계하거나 문구를 바꿀 때 Claude는 다음 순서로 작업합니다.

1. **영어로 설계:** 화면의 라벨, 버튼, 메시지를 영어로 작성합니다. 용어집의 표준어를 씁니다.
2. **문구 찾기:** 화면의 문구마다 언어셋에서 같은 문구와 그 ID를 찾습니다.
3. **6개 언어 가져오기:** 찾은 문구의 6개 언어 번역을 가져옵니다. 고유명사는 언어셋의 고유명사 기준을 따릅니다.
4. **가장 긴 표현 찾기:** 문구마다 6개 언어 중 가장 긴 표현을 고릅니다.
5. **최장 언어 화면 만들기:** 영어 화면의 각 문구를 가장 긴 표현으로 바꾼 화면을 만들고, 레이아웃(버튼 폭, 줄바꿈, 말줄임)에 문제가 생기는 곳을 표시합니다.
6. **보고:** 문구별 언어셋 ID, 가장 긴 언어와 표현, 이번 작업에서 번역 요청 목록에 새로 올린 문구를 결과에 붙입니다.

### 5. 새 문구와 번역 요청

언어셋에 없는 영어 문구가 생기면, 묻지 않고 번역 요청 목록에 올리고 알립니다. 모인 목록은 고객사에 보내 5개 언어 번역을 받고, 고객사가 확인해 주면 확정됩니다.

#### 번역 요청 목록

`language-set/translation-requests.csv` 한 파일에 문구 하나를 한 줄로 둡니다.

| 칸 | 내용 |
| --- | --- |
| 영어 문구 | 화면에 쓰인 영어 문구 그대로 |
| 사용 위치 | 문구가 쓰인 CID (여러 개면 모두) |
| 추가일 | 목록에 올린 날 |
| 추가한 사람 | 작업을 요청한 팀원 |
| 상태 | 번역 필요 / 고객사 요청함 / 확정 |
| 고객사 요청일 | 고객사에 보낸 날 |
| 확정일 | 고객사가 확인해 준 날 |
| 언어셋 ID | 확정 후 언어셋에 들어간 ID |

#### 흐름

1. **추가:** 작업 중 언어셋에도, 번역 요청 목록에도 없는 영어 문구가 나오면 Claude가 "번역 필요" 상태로 목록에 올립니다. 이미 목록에 있으면 사용 위치만 더합니다.
2. **알림:** 작업 결과에 "번역 요청 목록에 새로 올린 문구"를 적어 알립니다.
3. **표시:** 최장 언어 화면에서는 그 문구를 영어로 두고 "번역 대기"로 표시합니다.
4. **정리:** 팀원이 요청하면 Claude가 "번역 필요" 문구를 뽑아 고객사에 보낼 목록을 만듭니다. 영어 문구와 5개 언어(한국어, 포르투갈어, 스페인어, 이탈리아어, 프랑스어) 빈칸, 사용 화면으로 구성합니다. 보낸 문구는 "고객사 요청함"으로 바꿉니다.
5. **확정:** 고객사가 번역을 확인해 주면 "확정"으로 바꾸고 언어셋에 반영합니다. 반영 방법은 언어셋 관리 체계를 따릅니다.

영어 문구 자체는 화면의 고객 컨펌 때 함께 확인됩니다.

## 정책서 작성 규칙

> 상태: 초안 v0.2 (2026-11-02). 규칙 문장 형식을 명사형 끝맺음으로 바꾸고, 팀원 정책 ID 기록 방법을 더함.

정책서 한 항목의 ID, 파일, 형식, 작성·수정 규칙을 정합니다. 정책은 정책서에만 정의하고, 화면설계서는 정책 ID로만 참조합니다(헌법 3조).

### 1. 정책 ID

형식은 `POL-영역-###`입니다. 예: `POL-EQP-001`

| 코드 | 영역 | 다루는 것 |
| --- | --- | --- |
| COM | 공통 | 플랫폼, 운영 언어, 모듈 구성 운영 등 모든 영역에 걸치는 것 |
| ACC | 계정·권한·로그인 | 계정 생성, 아이디·비밀번호, Session Timeout, 종료, User Type 권한 |
| EQP | 장비 | 장비 상태, Door, Enable Setting, Error Rate, Spare Storage |
| INV | Reagent·Consumable 재고와 폐기 | 유효기간, 폐기, 재사용, Lot, 재고 상태, 입출고 시점 |
| MAT | Material Setup | Carrier·Socket·Tray·Trolley 구성, 데이터 저장, 리셋 |
| LOD | 도킹·Drawer Loading | Trolley 도킹, DX Storage 투입부, STAT Storage, Cold Storage |
| SMP | Sample·검사 진행 | Sample·Plate 상태, 검사 시작·종료 시간, 재검사, Batch, 오더 취소, STAT 검사 |
| TST | 검사 정책 | 조합 검사, Cut-off Time, Cost Setting, Policy·Protocol Setting |
| EVT | Event | Event 상태·등급·종류, Event 팝업 |
| STA | 통계 | 통계 데이터 표출, 기간 설정 |
| SYS | 시스템 연동 | LIS 연동, 데이터 백업·복원 |

- 영역은 정책의 주제로 정합니다. 정책이 쓰이는 메뉴는 여러 개일 수 있으므로 메뉴는 머리말 `menus`로 연결합니다.
- 번호는 영역마다 세 자리 일련번호입니다. 그 영역의 가장 큰 번호에 1을 더하고, 한 번 쓴 번호는 다시 쓰지 않습니다.
- 새 영역이 필요하면 협의 대기 항목으로 올립니다.
- 다른 체계의 정책 ID(예: 팀원 정책 MD의 `POL-INS-06`)는 쓰지 않고, `policy/migration.csv`의 "이전 ID" 칸에 남겨 어디서 왔는지 따라갈 수 있게 합니다.

### 2. 파일

- 정책 하나에 파일 하나: `policy/<영역 코드 소문자>/POL-영역-###.md` (예: `policy/eqp/POL-EQP-001.md`)
- 템플릿: `templates/policy.md`
- 표 형태의 기준 자료(Service Mode·권한 매트릭스, 장비 상태 정의서, 알럿 카탈로그, 상태값 표)는 데이터 파일로 두고, 정책 파일이 그 파일을 참조합니다. 같은 내용을 정책 파일에 옮겨 쓰지 않습니다.

### 3. 머리말

| 키 | 내용 |
| --- | --- |
| `id` | 정책 ID |
| `title` | 정책 이름 |
| `summary` | 한 문장 요약. 화면 디스크립션에 정책 ID와 함께 자동으로 붙습니다. 표준어로 쓰고, 80자 안쪽으로 씁니다 |
| `domain` | 영역 코드 |
| `menus` | 관련 메뉴 (IA 메뉴 이름) |
| `cids` | 이 정책을 참조하는 화면 CID |
| `status` | 확정 / Deprecated |
| `version` | 이 정책이 마지막으로 바뀐 Ver. 화면 Ver와 같은 체계(X.Y.ZZ, `rules/repository-and-id.md` 6절)이며, 바뀐 정책이 처음 반영되는 화면의 Ver를 적음. 화면은 머리말 `policies`에 `정책 ID@버전`으로 참조해 어느 기준으로 그렸는지 추적함 (2026-11-02 결정) |
| `date` | 마지막으로 바뀐 날짜 |
| `sources` | 근거 (정책서_2026.08.28, Common UX 프레임, 결정 기록, 회의록 등) |
| `provisional` | 임시 정책에서 넘어왔으면 PV ID (`rules/provisional-policy.md`) |
| `alerts` | 관련 Alert·Confirm ID (`policy/alert-catalog.csv`) |
| `data` | 참조하는 기준 자료 파일 |
| `replaced_by` | Deprecated일 때 대신하는 정책 ID |

### 4. 본문

다음 순서로 씁니다. 해당 없는 절은 "없음"으로 둡니다.

1. **정의:** 이 정책이 다루는 대상과 용어
2. **규칙:** 번호를 매긴 개조식 문장. "[조건]일 때 [대상]은 [동작]함" 형식을 기본으로 씁니다. 조건을 앞에 두고, 명사형으로 끝맺습니다(~함, ~됨, ~가능, ~불가). 예: "장비 통합 상태가 Running 또는 Error일 때 프로그램 종료와 시스템 종료는 불가."
3. **예외**
4. **근거:** 출처와 결정 기록
5. **변경 이력:** 버전, 날짜, 내용, 근거(PD·PV·CR·ADR)

### 5. 작성 규칙

- 용어집의 표준어만 씁니다. 화면 항목과 업무 대상 이름은 영어로 씁니다(`glossary/glossary.md`).
- 상태값은 어느 단계의 상태인지 함께 씁니다 (예: "장비 통합 상태가 Running일 때").
- 수치는 구체값으로 씁니다. 장비가 확정되지 않아 정할 수 없는 값은 `TBD-장비`로 표시하고 지어내지 않습니다.
- 근거가 없거나 출처끼리 충돌하면 쓰지 않고 질문으로 남깁니다(헌법 7조).
- 우선순위: 공통(COM) 정책 > 영역 정책 > 화면설계서의 예외. 화면 예외는 화면설계서에 정책 ID와 함께 적습니다.
- 임시 정책에서 넘어온 정책은 `provisional`에 PV ID를 적고 근거에 남깁니다.

### 6. 바꾸기와 폐기

- 정책서는 공통 자료입니다. 바꿀 내용은 임시 정책으로 등록하고, 승인 담당자가 승인한 것만 반영합니다(`rules/change-flow.md`).
- 정책을 바꾸면 `cids`의 화면을 영향 범위에 넣습니다(헌법 5조).
- 정책이 필요 없어지면 파일을 지우지 않고 `status: Deprecated`로 바꾸고, 대신하는 정책이 있으면 `replaced_by`를 적습니다.

### 7. 정책서 정제 진행 방법 (작업 유형 20)

1. `policy/policy-backlog.md`를 먼저 읽습니다.
2. **기준 자료를 읽습니다 (빠뜨리지 않음).** 정책 문장을 쓰기 전에 아래 파일을 읽고, 쓰는 동안 계속 대조합니다.
   - 용어: `glossary/glossary.md`(표기 규칙), `glossary/terms.csv`(표준어와 쓰지 않는 표현)
   - 상태값: `glossary/status-values.csv`(분류, 레벨, 코드명, UI 표기, 정의)
   - 대상 이름: `glossary/modules.csv`, `glossary/module-units.csv`, `glossary/test-stages.csv`, `glossary/test-items.csv`, `glossary/sample-types.csv`
   - 메뉴와 CID: `ia/ia-screens.csv`
   - 그 영역의 기준 자료: 예) EQP는 `policy/equipment-states.md`, ACC는 `policy/permission-matrix.csv`, EVT는 `policy/alert-catalog.csv`
3. 영역 하나씩 진행합니다. 영역마다 8월 정책서, 작업방 화면 디스크립션, Common UX에서 그 영역의 정책 문장을 모읍니다. 작업방 화면은 `rules/figma-sync.md`의 릴리즈 영역 규칙에 따라 최신 화면을 봅니다.
4. 출처끼리 다른 곳은 충돌 목록으로 만들어 요청자에게 판정을 받습니다. 판정 전에는 정책 파일에 쓰지 않습니다.
5. 판정이 끝난 정책을 정책 파일로 씁니다. 8월 정책서의 정책명, 팀원 정책 MD의 ID(이전 ID)와 새 정책 ID의 대응을 `policy/migration.csv`에 남깁니다(헌법 9조). 팀원 정책 문장을 옮길 때는 용어를 이 저장소 용어집 표기로 바꿉니다(예: 트롤리 → Trolley, D.A.PC → D.A PC, 계정 유형 → User Type).
6. **쓴 뒤 점검합니다.** 정책 파일마다 (1) 용어가 `glossary/terms.csv`의 표준어인지, 쓰지 않는 표현이 없는지 (2) 상태값이 `glossary/status-values.csv`의 UI 표기와 같고 어느 레벨의 상태인지 적혀 있는지 (3) Module·Unit·검사 항목 이름이 기준 파일과 같은지 (4) 메뉴와 CID가 `ia/ia-screens.csv`에 있는지 확인합니다. 용어집이나 상태값 표에 없는 말이 필요하면 지어내지 않고 용어집 추가 후보로 올립니다. 점검 결과는 보고의 "확인한 것"에 적습니다.
7. 반영한 반영 대기 항목은 `policy/policy-backlog.md`에서 정책 ID와 날짜를 적어 닫습니다.

## 임시 정책

> 상태: 초안 v0.5 (2026-11-03). v0.4에서 회의 중심 절차와 상태 8단계를 걷어 내고, 등록 → 승인·반려 → 반영 세 단계로 줄임 (헌법 4조 v1.4). v0.5에서 겹치는 임시 정책 확인과 A/B 선택 문서(6절)를 더함. 같은 날 상태 이름 "검토 중"을 "승인 대기"로 바꾸고 시작 기준을 적음.

임시 정책은 공통 자료(정책서·룰 문서)에 아직 없지만 작업에 먼저 쓰는 정책입니다. 공통 자료는 승인 담당자만 고치므로(헌법 4조), 작성자는 기존 정책을 바꿔야 하거나 고객 답을 기다리지 않고 진행해야 하면 임시 정책으로 등록해 그 기준으로 작업합니다.

### 1. 흐름

1. **등록:** Claude가 먼저 "승인 대기" 임시 정책 중 같은 정책을 바꾸는 것이 있는지 확인합니다(6절). 없으면 `templates/provisional-policy.md`로 `provisional/PV-0001.md`를 만들고, 적용한 화면 머리말 `provisional`에 PV ID를 넣습니다. 번호는 `provisional/`과 `provisional/closed/`의 가장 큰 번호에 1을 더합니다.
2. **승인·반려:** 승인 담당자가 화면 작성자와 의견을 나눠 승인하거나 반려합니다. 회의를 기다리지 않아도 되고, 필요하면 회의에서 같이 봅니다. 승인하면서 내용을 고칠 수 있습니다.
3. **반영:**
   - 승인: 승인 담당자가 공통 자료에 반영하고 공통 규칙 버전을 올린 뒤, 파일에 반영 버전을 적고 `provisional/closed/`로 옮깁니다.
   - 반려: 사유를 적고 `provisional/closed/`로 옮깁니다. 적용한 화면은 작성자가 기존 정책으로 되돌립니다.

닫힌 파일은 지우지 않습니다(헌법 9조).

### 2. 상태

| 상태 | 뜻 |
| --- | --- |
| 승인 대기 | 대표 저장소에 올라와 UX 문서 목록에 보임. 작성자는 이 기준으로 작업 중이고 승인 전 |
| 승인 | 승인 담당자가 승인함. 공통 자료에 반영하면 `closed/`로 옮김 |
| 반려 | 적용하지 않기로 함 |

- 작성자 PC에서 만든 임시 정책은 대표 저장소에 올려야 승인 담당자에게 보입니다. 적용한 화면을 올릴 때 PV 파일도 함께 올립니다.
- 상태는 승인 담당자의 [승인]·[반려](또는 파일에 직접 적은 결정)로만 바뀝니다: 승인 대기 → 승인 또는 반려.

### 3. 작업할 때

- 임시 정책은 등록한 작업과, 그 PV ID를 머리말에 적은 화면에서만 씁니다. 승인 전에는 공통 규칙(UX 문서)에 넣지 않으므로 다른 팀원의 Claude는 모릅니다.
- Claude는 바뀌는 규칙만 PV 내용을 따르고, 나머지는 공통 규칙을 따릅니다.
- 이번 작업에서는 적용한 화면만 고칩니다. 같은 정책을 쓰는 다른 화면은 고치지 않고, 파일의 "영향 화면"에 적습니다.

### 4. 영향 화면

Claude가 바꾸는 정책을 쓰는 화면, 적용한 화면을 부르거나 적용한 화면이 부르는 화면, T/L 짝 CID를 찾아 영향이 있는 것만 적습니다. 승인되면 이 표가 고칠 화면 목록이 됩니다.

| 영향 | 뜻 |
| --- | --- |
| 화면 변경 | 화면 구성, 동작, 알럿이 바뀜 |
| 디스크립션 변경 | 화면은 그대로이고 디스크립션만 바뀜 |
| 확인 필요 | 영향이 있는지 그 화면 작성자가 봐야 함 |

영향받는 화면 작성자는 UX 문서의 임시 정책 메뉴에서 확인합니다. 메신저(Slack 등) 알림은 추후 연동합니다.

### 5. UX 문서의 승인·반려 버튼

팀 프로그램 UX 문서의 임시 정책 메뉴에 [승인]·[반려] 버튼을 둡니다. 승인 담당자에게만 보입니다. 버튼은 파일의 상태와 결정 칸을 채워 대표 저장소에 커밋하는 일을 대신합니다. 원본은 항상 파일이고, 프로그램이 없으면 파일에 직접 적습니다.

- [승인]: 상태 "승인", 결정 칸에 날짜·승인·결정자·메모
- [반려]: 상태 "반려", 결정 칸에 날짜·반려·결정자·사유(꼭 적음)
- A/B 선택 문서는 [A안 승인]·[B안 승인]·[반려]로 바뀝니다(6절).
- 목록에서 "바꾸는 정책"이 같은 "승인 대기" 임시 정책은 같은 표시로 묶어 보여 주고, [승인]을 누를 때 같은 정책을 바꾸는 다른 임시 정책이 있으면 먼저 알려 줍니다. 동시에 등록돼 Claude가 못 찾은 경우를 막기 위해서입니다.

### 6. 겹치는 임시 정책

Claude는 임시 정책을 새로 등록할 때마다 `provisional/`의 "승인 대기" 임시 정책을 모두 읽고, "바꾸는 정책"이 같은 것을 찾습니다. 찾은 결과에 따라 다음처럼 처리하고, 처리한 내용을 작성자에게 말합니다.

| 경우 | 처리 |
| --- | --- |
| 같은 규칙을 같은 내용으로 바꿈 | 새로 만들지 않고 그 PV를 씀. 작성자의 화면을 그 PV의 "적용한 화면"에 더함 |
| 같은 규칙을 다른 내용으로 바꿈 (충돌) | 새로 만들지 않고 기존 PV를 A/B 선택 문서로 합침(아래). 새 내용이 B안이 됨 |
| 같은 정책의 다른 규칙을 바꿈 | 새 PV를 만들고, 두 파일의 "같은 정책을 바꾸는 임시 정책"에 서로를 적음. 승인 담당자는 함께 보고 정함 |

- 같은 규칙에 서로 다른 예외나 조건을 더하는 경우처럼, 규칙 번호가 달라도 같은 상황을 다르게 정하면 충돌로 봅니다. 충돌인지 애매하면 작성자에게 묻습니다.
- "바꾸는 정책"은 `POL-EQP-008 규칙 5`, `POL-EQP-008 추가`처럼 정책 ID와 규칙 번호로 적습니다. 그래야 찾을 수 있습니다.

#### A/B 선택 문서

충돌하는 두 임시 정책을 한 파일에서 나란히 보고 하나를 고르게 하는 문서입니다. `templates/provisional-policy-ab.md`를 씁니다.

- 기존 PV 번호를 그대로 씁니다. 기존 내용이 A안, 새 내용이 B안입니다. 세 번째가 생기면 C안을 더합니다.
- 화면 머리말 `provisional`에는 `PV-0003`(A안) 또는 `PV-0003-B`(B안)처럼 적습니다. 기존 화면은 고치지 않아도 됩니다.
- Claude가 "두 안의 차이"에 무엇이 다른지와, 각 안을 고르면 고쳐야 할 화면을 정리합니다.
- 승인 담당자는 [A안 승인], [B안 승인], [반려] 중 하나를 고릅니다. 승인하면서 내용을 고칠 수 있습니다. 고르지 않은 안을 적용한 화면은 "영향 화면"(화면 변경)이 되고, 그 작성자가 고칩니다.

## 저장소 구조와 ID 체계

> 상태: 초안 v0.3 (2026-11-02). 메뉴 폴더는 `screens/<IA Lv.1 메뉴>/`로 정함 (`rules/screen-spec.md` 3절).

폴더 구조, 파일 이름, 문서 간 연결에 쓰는 ID와 버전 규칙을 정합니다.

### 1. 기본 원칙

- 문서 간 연결은 ID로만 합니다. 다른 문서의 내용을 옮겨 쓰지 않습니다(헌법 3조).
- 파일과 폴더 이름은 영어 소문자, 숫자, 하이픈(-)만 씁니다. CID, PD, PV 같은 ID는 원래 표기(대문자) 그대로 씁니다.
- 파일 안의 날짜는 항상 `YYYY-MM-DD`로 씁니다. 화면에 보이는 날짜 형식(YYYY.MM.DD)과는 별개입니다.

### 2. 화면 ID (CID)

- 지금 쓰는 CID를 그대로 씁니다. 새 ID 체계를 만들지 않고, 오타와 누락만 바로잡습니다.
- 접두어: T-IOS는 `TI`, L-IOS는 `LI`
- 접미어는 신규 CID부터 적용합니다. 기존 CID는 바꾸지 않습니다.

| 접미어 | 뜻 | 쓰는 경우 |
| --- | --- | --- |
| `-P` | Popup | 팝업 화면 |
| `-T` | Tab | 탭 화면 |
| `-V` / `-M` | 조회 / 수정 모드 | 필요한 화면에만 씀. 같은 데이터를 다루는 같은 구조의 화면인데, 수정 모드에서 UI가 추가되어 화면을 나눠야 할 때만 씀. 필수 아님 |

### 3. 화면설계서 파일

- **CID 하나에 파일 하나:** `TI-DAS.md`, `LI-DAS.md`처럼 T-IOS와 L-IOS 화면을 각각 따로 둡니다. 짝 화면이라도 구조, 버튼, 기능이 서로 다를 수 있어 하나로 합치지 않습니다.
- **짝 연결:** 짝이 있는 화면은 두 파일 모두 머리말에 `pair_cid`와 `tl_relation`(동일 / 권한 차이 / 기능 추가 / 단독)을 적습니다. 한쪽에만 적혀 있으면 검증 오류입니다.
- **공통 내용은 정책으로:** 두 화면에 함께 적용되는 규칙은 화면설계서에 따로따로 쓰지 않고 정책서에 정의한 뒤 정책 ID로 참조합니다. 그래야 한쪽만 고쳐지는 일이 줄어듭니다.
- **짝 확인:** 한쪽 화면을 고치면 짝 화면도 영향 범위에 넣고, 한쪽만 고쳐졌으면 다른 쪽도 고칠지 묻습니다(`rules/claude-work.md` 5절).
- **공통 팝업:** 여러 곳에서 열리는 팝업(예: Door Control)은 화면설계서에 호출 위치 목록을 둡니다.

### 4. 항목 ID

| 대상 | 형식 | 폴더 |
| --- | --- | --- |
| 협의 대기 | `PD-0001` | `pending/` |
| 임시 정책 | `PV-0001` | `provisional/` |
| 변경요청 | `CR-0001` | `changes/` |
| 결정 기록 | `ADR-0001` | `decisions/` |
| 정책 | `POL-영역-###` (예: POL-EQP-001) | `policy/<영역 코드 소문자>/` |
| 고객 논의 대상 | `CA-0001` | `customer-agenda/` |

- 정책 ID를 뺀 항목은 네 자리 일련번호입니다(정책은 영역마다 세 자리, `rules/policy-writing.md` 1절). 폴더(닫힌 항목 폴더 포함)에 있는 가장 큰 번호에 1을 더합니다.
- 한 번 쓴 번호는 다시 쓰지 않습니다. 같은 번호가 동시에 생기면 나중에 반영되는 쪽의 번호를 바꿉니다.

### 5. Module과 Unit

- 문서에는 UI 표기를 씁니다: `PCR Setup (1)`, `Waste Bin (Upper)`
- 데이터와 검증에는 코드명을 씁니다: `PcrSetup`, `UpperWasteBin`
- 기준: `glossary/module-units.csv`

### 6. 버전 (Ver)

화면 정보의 Ver는 `X.Y.Z` 세 자리입니다.

| 자리 | 뜻 | 예 (2.1.13) |
| --- | --- | --- |
| X | 프로젝트 차수 | 2 = 2차 프로젝트 |
| Y | 그 프로젝트 안의 릴리즈 순번. 0부터 시작 | 1 = 두 번째 릴리즈 |
| Z | 그 릴리즈 안에서 개발사에 전달한 순번 (내부 관리 번호). 항상 두 자리 (01, 02, … 13) | 13 |

- **버전은 CID마다 따로 갑니다:** 이번 작업에서 수정한 CID만 새 버전으로 올리고, 수정하지 않은 CID는 이전 버전을 그대로 유지합니다. 같은 메뉴 안에서도 CID마다 버전이 다를 수 있습니다.
- **작업 시작 때:** Claude는 쓰기 작업의 계획 확인(공통 순서 5단계)에서 이번 작업이 어느 버전에 들어가는지 묻고, 요청자가 정한 버전을 화면 정보에 적습니다.
- **개발사 전달 후:** 전달 완료가 기록되면, 이후 변경은 버전을 올려야 한다고 알립니다. 어느 자리를 올릴지는 요청자가 정합니다.

### 7. 언어셋 ID

언어셋 담당자가 정합니다(`rules/language-set.md`).

### 8. 폴더 구조

`README.md`의 폴더 구조를 따릅니다.

## 화면설계서 규칙

> 상태: 초안 작성 전. 1절(화면 반영 대기 목록과 디스크립션 기준), 3절(기존 화면 MD화), 4절(반영 대기 목록 상태와 화면설계서 작업대기, 2026-11-04)만 정함. 2026-11-04에 "정정 메모"를 "반영 대기 목록"으로 이름을 바꿈. 3절은 Instruments 메뉴 시험 후 확정.

CID 화면설계서의 템플릿과 디스크립션 작성 규칙을 정합니다.

### 1. 화면 반영 대기 목록과 디스크립션 기준 (2026-11-02)

- 화면에서 고칠 점은 화면 MD의 "반영 대기 목록" 절에 모읍니다. 화면 MD가 아직 없는 CID는 `screen-fixes/<CID>.md`에 두었다가 화면 MD를 만들 때 옮깁니다. 모든 화면 공통 항목은 `screen-fixes/README.md`에 있습니다.
- 화면을 다시 그리거나 디스크립션을 쓸 때는 그 CID와 짝 CID의 반영 대기 목록, 그 CID를 `cids`에 둔 정책 파일을 먼저 읽습니다.
- 알럿 체계를 다시 잡을 때까지(`background/worklist.md` 작업 9) 화면 MD의 알럿 정보(디스크립션 원문의 알럿 ID·문구, 호출하는 화면, 알럿 반영 대기 목록)는 지우지 않고 남깁니다. 정책에서 알럿 동작이 바뀌어도 화면 MD에는 반영 대기 목록으로 적고 원문은 그대로 둡니다 (2026-11-02).
- 화면에 Consumable·Reagent 예시 값(품목 이름, 구성품 이름, 수량 단위, 저장 위치, Barcode)을 넣을 때는 `glossary/consumables.csv`, `glossary/pcr-reagents.csv`의 실제 값을 씁니다. Reagent의 구조와 값은 Assay Pack이 정하므로, 이 표는 Reagent 검증과 화면 데이터용입니다 (2026-11-03).
- 정책에서 새로 정하거나 바꾼 내용은, 그 정책을 `cids`에 둔 화면 MD의 반영 대기 목록에 "디스크립션에 넣음: …"으로 적습니다. 논의 항목에 답을 받아 정한 경우의 순서는 `rules/discussion-answer.md` 5절을 따릅니다(2026-11-04). 숫자 형식, 단위, 상태, 칩·버튼 상태처럼 화면 예시에 보이는 내용이면 "화면 예시도 …"를 함께 적어, 다시 그릴 때 디스크립션과 화면 예시가 모두 그 정의대로 그려지게 합니다 (2026-11-03).
- 디스크립션은 기존 화면의 문장을 고쳐 쓰지 않고, 정책서와 정리된 알럿 카탈로그(`policy/alert-catalog.csv`)를 기준으로 다시 씁니다. 정책은 ID로만 참조합니다.
- 화면 머리말 `policies`에는 참고한 정책 ID와 그 정책의 버전을 함께 적습니다 (예: `POL-EQP-009@2.1.15`). 어떤 화면이 어느 기준으로 그려졌는지 추적하기 위해서입니다.
- 화면 머리말 `rules_version`에는 그 화면을 그리거나 고칠 때 따른 공통 규칙 버전(대표 저장소 기준 브랜치의 버전, 예: `rules-v0.3`)을, `provisional`에는 적용한 임시 정책 ID(A/B 선택 문서의 B안이면 `PV-0003-B`처럼 안까지)를 적습니다. 공통 규칙 버전이 올라가면 작성자는 바뀐 정책을 쓰는 자기 화면을 새 버전에 맞추고 버전을 바꿉니다. 화면을 다시 열면 Claude가 머리말 버전이 최신이 아닌지 확인해 말해 줍니다. 임시 정책이 있는 화면에는 "임시 정책 포함" 표시를 붙입니다 (헌법 4조, `rules/provisional-policy.md`, 2026-11-03).

### 2. 담을 내용 (작성 전)

- 화면 정보 칸: Ver, Date, CID, 작성자, 화면, 경로 → 파일 머리말로 정함 (`rules/status-lifecycle.md` 5절)
- 상태별 화면(정상, 로딩, 비활성, 오류, 빈 상태, 장비 이상)
- 노출 모드와 User Type 권한 정의
- 정책은 ID로만 참조
- 디스크립션 고정 문장 패턴 4~5개
- T/L 짝 화면은 CID마다 파일을 따로 두고 `pair_cid`로 연결 (`rules/repository-and-id.md` 3절). 공통 팝업은 호출 위치 목록
- 다국어: 영어 화면(고객용)과 최장 언어 화면(디자이너용), 문구별 언어셋 ID와 가장 긴 언어 (`rules/language-set.md`)

### 3. 기존 화면 MD화 (2026-11-02 확정)

정책서 작업과 함께 진행합니다. 한 메뉴의 기존 화면을 먼저 MD로 옮기고, 그 영역의 정책은 Figma 대신 화면 MD를 읽어 정리합니다. Figma는 한 번에 읽을 수 있는 양이 적어서, 한 번 읽을 때 MD로 남겨 두면 정책 작업과 화면 재설계에서 다시 읽지 않아도 됩니다.

#### 범위

- 기획 화면만 옮깁니다: 오른쪽에 화면 정보·디스크립션 패널이 있는 2252px 프레임. 같은 CID의 디자인 프레임(1920×1080), 1280 해상도, Skeleton 프레임은 지금은 옮기지 않습니다(2026-11-02 결정).
- 최신 영역의 프레임만 옮깁니다 (`rules/figma-sync.md` 1절). 파일 머리말 `figma_region`에 영역을 적습니다.
- CID가 없는 프레임(IA에 CID가 없는 Tab 등)은 옮기지 않고 메뉴 파일 `_menu.md`에 적습니다.
- 케이스 프레임은 지금은 제목만 "케이스" 절에 적고, 중요한 케이스 화면은 링크로 남깁니다.
- **취소선:** Figma에서 취소선이 그어진 글자는 제거된 항목입니다. 화면 MD에는 `~~글자~~`로 옮기거나 "(취소선, 제거됨)"으로 표시하고, 다시 그릴 때 넣지 않습니다 (2026-11-02 사용자 확인). 추출 스크립트가 취소선을 `~~ ~~`로 표시합니다.

#### 순서

1. IA(`ia/ia-screens.csv`)에서 그 메뉴의 CID 목록을 만듭니다.
2. Figma 페이지에서 CID마다 기획 화면 프레임을 찾습니다 (같은 이름 프레임 중 화면 정보 패널에 Ver가 있는 것).
3. `tools/figma/extract-screen.js`로 화면 정보, 화면 글자, 사용 컴포넌트, 디스크립션 원문, 케이스 제목, 버전 메모를 뽑습니다. Figma는 읽기만 합니다.
4. `templates/screen.md`로 `screens/<메뉴>/<CID>.md`를 만듭니다.
   - 머리말: Figma 화면 정보(Ver, Date, 작성자, 화면)와 IA(짝 CID, Type, 경로), Service Mode·User Type(`policy/service-mode-matrix.csv`, `policy/permission-matrix.csv`)
   - 디스크립션은 원문 그대로 둡니다. T/L 짝 화면에서 원문이 같은 절은 "원문은 짝 CID n과 같음"으로 적고 다른 절만 옮깁니다.
   - 화면 글자의 GNB·LNB는 한 줄로 묶고, 예시 데이터가 반복되는 줄은 줄여 적습니다.
   - 버전 메모는 변경 이력 표로 옮깁니다.
5. 옮기면서 찾은 고칠 점(정책·용어집·상태값·알럿과 다른 곳, 오타, 화면 정보 오류)을 "반영 대기 목록" 절에 적습니다. `screen-fixes/<CID>.md`가 있으면 그 내용도 옮기고 그 파일은 지웁니다.
6. 관련 정책 ID를 적습니다 (정책 파일의 `cids`에서 찾음). 정책 파일의 `cids`에 빠진 CID가 있으면 정책 파일도 고칩니다.
7. 메뉴 파일 `_menu.md`의 `cids`를 채웁니다.

### 4. 반영 대기 목록 상태와 화면설계서 작업대기 (2026-11-04)

반영 대기 목록 중 아직 화면에 반영하지 않은 줄을 모아, 팀 프로그램 일정/작업 > 화면설계서 작업대기 탭에서 얼마나 쌓여 있는지 봅니다.

#### 반영 대기 목록 상태

| 상태 | 뜻 | 작업대기에 셈 |
| --- | --- | --- |
| 대기 | 다음에 화면을 그릴 때 반영할 것. 이유가 있으면 괄호로 적음 (예: `대기 (확인 필요)`, `대기 (고객 논의)`, `대기 (팀 논의)`) | 셈 |
| 반영 완료 | 화면을 다시 그려 디스크립션 · 화면 예시에 반영함. 날짜를 함께 적음 (예: `반영 완료 (2026-11-20)`) | 세지 않음 |
| 반영 불필요 | 반영하지 않기로 함 (예: 취소선으로 제거된 항목). 이유를 괄호로 적음 | 세지 않음 |

- 반영한 줄은 지우지 않고 상태만 바꿉니다(헌법 9조).

#### 세는 법

| 숫자 | 세는 것 |
| --- | --- |
| 반영 대기 | 상태가 "대기"로 시작하는 반영 대기 목록 줄 |
| 작업 대기 화면 | 반영 대기가 1줄 이상인 화면 |
| 확인 필요 | 반영 대기 중 상태나 바꿀 것에 "확인 필요"가 있는 줄. 화면을 그리기 전에 답이 먼저 필요함 (`rules/discussion-answer.md`) |
| 메뉴 | 작업 대기 화면이 있는 메뉴 |

- 구분(디스크립션, 표기, 화면 정보, 정책 반영, 알럿, 문구 등)은 반영 대기 목록의 "구분" 칸을 그대로 씁니다.

#### 담당자

- 메뉴 담당자는 `screens/{메뉴}/_menu.md`의 `owner`입니다. 비어 있으면 "담당자 미정"으로 보여 줍니다.
- UX 담당자 칩은 여러 명을 함께 골라 볼 수 있습니다. 화면별 작성자는 화면 머리말의 `author`로 따로 보여 줍니다.

#### 보여 주는 순서

메뉴별로 반영 대기가 많은 순서로 보여 주고, 메뉴를 열면 화면별(많은 순)로, 화면을 누르면 그 화면 정의서의 반영 대기 목록으로 갑니다.

## 문서 상태

> 상태: 초안 v0.1 (2026-10-30).

화면설계서의 진행 상태, 표시(플래그), 기록 형식, 폐기 처리를 정합니다. 여기서 말하는 "상태"는 기획 문서의 진행 상태이며, 장비의 상태값(`glossary/status-values.csv`)과는 다릅니다.

### 1. 관리 단위

- 상태는 메뉴 단위로 관리합니다. 메뉴는 대시보드 LNB에서 눌리는 단위(IA 1~2 depth)입니다.
- 메뉴에 속한 CID들은 상태를 함께 씁니다. 변경 이력과 표시는 CID별로 남깁니다.

### 2. 상태값

| 축 | 값 | 바꾸는 방법 |
| --- | --- | --- |
| UX | 작업 중 / 컨펌 중 / 컨펌 완료 | 담당 기획자가 선택하면 Claude가 반영 |
| UI | 작업 중 / 컨펌 대기 중 / 컨펌 완료 | 작업 중·컨펌 대기 중은 디자이너가 Figma에서 바꾸고 Claude가 매일 점검. 컨펌 완료는 담당 기획자 요청으로 Claude가 반영 |
| 전달 | 전달 대기 / 전달 완료 | 자동 (프로그램 또는 Claude) |
| 공통 | 폐기 | 결정 기록 또는 CR이 있어야 바꿀 수 있음 (6절) |

- UI의 "컨펌 대기 중"은 전사 공통 값이라 이름과 뜻을 바꾸지 않습니다. 디자인 완료, 고객 리뷰 요청 대상입니다.
- "컨펌 완료"는 요청하면 바로 바꿉니다.
- 컨펌 완료(UX 또는 UI)와 전달 완료로 바뀔 때, 그 메뉴에서 **수정된 CID만** 화면 정보 `date`를 그날로 바꿉니다. 수정된 CID는 직전 컨펌 완료(전달 완료면 직전 전달 완료) 이후 변경 이력에 새 줄이 생긴 CID입니다. 수정하지 않은 CID는 `date`와 `version`을 그대로 둡니다(`rules/repository-and-id.md` 6절).
- 전달 완료 후 다시 바뀌는 화면은 전달 대기로 돌아가고, 버전을 올려야 한다고 알립니다(`rules/repository-and-id.md` 6절).

### 3. 큰 변경과 작은 변경

| 구분 | 무엇이 바뀌나 | 처리 |
| --- | --- | --- |
| 큰 변경 | 흐름, 레이아웃, 상태값, 컴포넌트 구성 | 메뉴의 UX 상태를 "작업 중"으로 되돌림 |
| 작은 변경 | 문구, 라벨, 디스크립션, 수치 | 상태는 유지하고 해당 CID에 "변경 예정" 표시 |

### 4. 표시 (플래그)

| 표시 | 붙이는 경우 | 함께 적는 것 |
| --- | --- | --- |
| 변경 예정 | 컨펌 완료 화면에 작은 변경이 확정됨 | CR ID |
| 임시 정책 포함 | 고객 확답 전 임시 정책을 적용함 (`rules/provisional-policy.md`) | PV ID |
| 연동 변경 | 다른 화면이나 정책의 변경으로 함께 고쳐짐 | 원인 CID 또는 정책 ID |
| Figma 반영 대기 | 프로그램이 멈춘 동안 저장소만 바뀜 (`rules/claude-work.md` 8절) | 없음 |

- 화면 옆 버전별 메모(포스트잇)는 변경 이력에서 자동으로 만듭니다. 같은 내용을 두 번 쓰지 않습니다.

### 5. 기록 형식

상태와 화면 정보는 파일 맨 위 `---` 사이의 머리말에 적습니다. 프로그램과 Claude는 이 칸만 읽고 바꿉니다. 키는 영어, 값은 이 문서와 용어집의 표기 그대로 씁니다.

#### 메뉴 파일 `screens/<메뉴>/_menu.md`

```yaml
---
menu: Dashboard
cids: [TI-DAS, LI-DAS]
owner: 서보경
ux_status: 컨펌 중          # 작업 중 | 컨펌 중 | 컨펌 완료 | 폐기
ui_status: 작업 중          # 작업 중 | 컨펌 대기 중 | 컨펌 완료 | 폐기
delivery_status: 전달 대기  # 전달 대기 | 전달 완료
delivered_version:          # 전달 완료 때 기록 (예: 2.1.13)
delivered_date:             # 전달 완료 때 기록 (YYYY-MM-DD)
---
```

본문에는 상태 이력 표를 둡니다. 상태가 바뀔 때마다 한 줄씩 더하고, 지우지 않습니다(헌법 9조).

| 날짜 | 축 | 바뀐 내용 | 바꾼 사람 | 근거 |
| --- | --- | --- | --- | --- |
| 2026-10-30 | UX | 작업 중 → 컨펌 중 | 서보경 | 고객 리뷰 요청 |

#### 화면설계서 `screens/<메뉴>/<CID>.md`

```yaml
---
cid: TI-DAS
pair_cid: LI-DAS              # 짝이 없으면 비움
tl_relation: 기능 추가         # 동일 | 권한 차이 | 기능 추가 | 단독
title: Dashboard              # 화면
path: Dashboard               # 경로
type: Page                    # Page | Popup | Tab
version: 2.1.13               # Ver (rules/repository-and-id.md 6절)
date: 2026-10-30              # 수정된 CID만 컨펌 완료·전달 완료 때 갱신
author: 서보경
service_mode: [Main Mode, Console Mode, TSS Mode]   # L-IOS 화면만
user_type: [Service, Admin, User]
policies: []                  # 정책 ID
flags:
  - type: 변경 예정
    ref: CR-0001
---
```

- 머리말 아래 본문의 구성은 `rules/screen-spec.md`를 따릅니다.
- 변경 이력은 화면설계서 본문의 "변경 이력" 표에 남깁니다.

#### 검증할 수 있는 것

- 컨펌 완료나 전달 완료인데 `date`가 비어 있음
- `flags`의 ID(CR, PV)가 해당 폴더에 없음
- `pair_cid` 파일에 이 화면이 짝으로 적혀 있지 않음
- `cids`에 있는 CID의 파일이 없거나, 파일은 있는데 `cids`에 없음
- 상태값이 2절의 값이 아님

### 6. 폐기

- 정책 변경으로 사라진 화면은 지우지 않고 "폐기"로 바꿉니다. 결정 기록 또는 CR 링크가 있어야 합니다.
- 화면설계서 파일은 `archive/`로 옮기고 Claude의 근거 자료에서 뺍니다.
- Figma: 작업방에서는 폐기 보관 영역으로 옮기고, 컨펌·개발사 페이지에서는 뺍니다. 이미 개발사에 전달된 화면이면 릴리즈 노트에 폐기를 적습니다.
- IA: 행을 지우지 않고 폐기 표시와 폐기 버전을 남깁니다.
- 정책: 그 화면에만 쓰이던 정책 ID는 Deprecated 처리하고, 다른 화면에도 연결된 정책은 유지합니다.

- [ ] 메뉴 폴더 이름 (IA 수정본을 받은 뒤)

## 주간 진행 현황

> 상태: 초안 v0.2 (2026-11-04). v0.2에서 업무(메뉴) 단위로 세는 방식으로 바꿈(3절). 같은 날 요약 카드를 총 · 진행 중 · 리뷰(예정) 중 · 완료로 줄이고 영역 이름을 "이번 주 마감 업무 내역"으로 바꿈. 다음 주 마감 예정은 업무와 담당자만 적음. 정하지 않은 것은 8절에 모았습니다.

주간 진행 현황은 한 주 동안 마감해야 할 업무, 바뀐 정책, 회의에서 나온 내용을 한 화면에 모은 것입니다. 팀 프로그램의 일정/작업 > 주간 진행 현황 탭에 보이고, 프로그램이 없을 때는 Claude가 같은 구성으로 정리해 보고합니다. 새로 정하는 내용은 없고, 원본(일정 시트, 대표 저장소, 회의록 시트)에 있는 것만 모아 보여 줍니다(헌법 7조).

### 1. 기간

- 한 주는 월요일부터 금요일까지입니다. 화면에는 `11/2(월) – 11/6(금)`처럼 적습니다.
- 지난주와 다음 주로 넘겨 볼 수 있습니다.

### 2. 구성

위에서 아래로 다음 순서로 보여 줍니다.

| # | 영역 | 원본 | 보여 줄 것 |
| --- | --- | --- | --- |
| 1 | 이번 주 마감 업무 내역 | 일정 시트 (Google 스프레드시트 › 2-2.WBS(간소)) | 업무(메뉴) 단위 숫자(총 · 진행 중 · 리뷰(예정) 중 · 완료)와 업무 목록 |
| 2 | 정책 변동 사항 | 대표 저장소 기준 브랜치 (`policy/`, `provisional/`) | 신규 · 변경 정책, 임시 정책, 주요 내용 요약 |
| 3 | 회의 내역 | 회의록 시트 (같은 스프레드시트 › 0.회의록) | 그 주 회의 요약. 없으면 "미진행" |
| 4 | 다음 주 마감 예정 | 일정 시트 | 마감할 업무와 담당자 |

### 3. 이번 주 마감 업무 내역

#### 세는 단위

- 업무(메뉴) 하나를 한 건으로 셉니다. 일정의 업무 줄(UX)과 그 아래 `ㄴUI` 줄을 묶어 한 건입니다.
- 마감일은 묶은 줄 중 가장 늦은 기간 종료일입니다. 이 날이 그 주 월요일~금요일 안에 있으면 그 주 마감 업무입니다.
- 기간이 하나도 없는 업무는 세지 않습니다.

#### 업무 상태

업무 한 건의 상태는 UX 줄과 UI 줄의 상태로 정합니다.

| 경우 | 업무 상태 |
| --- | --- |
| UX와 UI가 모두 완료 | 완료 |
| UX는 완료, UI는 완료가 아님 | 진행 중 |
| 그 밖 | UX 줄의 상태 |

- `ㄴUI` 줄이 없는 업무는 UX 줄의 상태를 그대로 씁니다.

#### 보여 주는 것

- 숫자: 총 건수와 진행 중 · 리뷰(예정) 중 · 완료 건수. 미정 · 대기 · 디스크립션 작성은 카드로 따로 보여 주지 않고 총에만 들어감
- 목록: 업무, 업무 상태, UX(담당자 · 상태), UI(담당자 · 상태), 기간

### 4. 정책 변동 사항

| 구분 | 넣는 것 | 기준 |
| --- | --- | --- |
| 신규 | 그 주에 새로 만든 정책 | `policy/{영역}/POL-*.md` 파일이 기준 브랜치에 처음 들어온 날 |
| 변경 | 그 주 전부터 있던 정책 중 정의 · 규칙 · 예외가 바뀐 것. 폐기된 것도 여기에 "폐기"로 표시 | 정책 파일의 변경 이력 표 날짜 |
| 임시 정책 | 그 주에 등록 · 승인 · 반려된 임시 정책과, 지금 승인 대기인 임시 정책 | `provisional/` 파일의 등록일과 결정 표 |

- 신규는 영역별 개수와 목록(정책 ID · 제목)으로 보여 줍니다.
- 변경은 정책 ID, 제목, 무엇이 바뀌었는지 한 문장으로 적습니다. 변경 이력 표에 남지 않는 수정(오타, 형식)은 넣지 않습니다.
- 임시 정책은 PV ID, 바꾸는 정책, 상태를 적습니다.
- **주요 내용**: Claude가 3~5줄로 요약합니다.
  - 고르는 기준: 화면 동작이 바뀌는 것, 이전 정책서(8월 정책서 등)와 달라진 것, 고객 확인이 걸린 것
  - 한 줄은 정책 ID로 시작하고, 무엇이 어떻게 바뀌었는지 한 문장으로 씁니다.
- 정책 ID와 PV ID는 모두 그 문서로 바로 가는 링크입니다.

### 5. 회의 내역

- 그 주에 열린 회의마다 일시 · 주제와 주요 내용 3~5줄을 적고, 회의록으로 가는 링크를 붙입니다.
- 주요 내용은 회의록 시트에 적힌 것을 줄여 쓴 것이며, 회의록에 없는 내용을 더하지 않습니다.
- 그 주의 회의록이 없으면 "미진행"으로 표시합니다.
- 회의 결정을 정책 근거로 잇는 구조(회의 ID)는 추후 정합니다(`background/worklist.md`).

### 6. 다음 주 마감 예정

- 기간 종료일이 다음 주 월요일~금요일 안에 있는 업무를 3절과 같은 단위로 찾습니다.
- 간단히 마감할 업무와 담당자(UX · UI 담당자)만 적습니다. 상태 · 기간 · 건수는 적지 않습니다.
- 없으면 "다음 주에 마감할 업무 없음"으로 적습니다.

### 7. 만드는 방법

- **팀 프로그램:** 원본에서 자동으로 모아 보여 줍니다(`background/ux-docs-program-proposal.md` R17). 숫자와 목록은 원본에서 계산하고, 주요 내용(4절)과 회의 요약(5절)만 Claude가 씁니다.
- **프로그램이 없을 때:** 요청을 받으면 Claude가 2절 순서대로 정리해 보고합니다(`rules/claude-work.md` 작업 유형 13).
- 일정 시트에서 바뀐 것은 새로고침하면 바로 반영됩니다.

### 8. 정할 것

1. 지난주 내용을 그 주가 끝난 시점으로 고정할지, 원본이 바뀌면 다시 계산할지
2. 주요 내용 요약을 언제 만들지 (매주 금요일에 한 번 / 볼 때마다)
