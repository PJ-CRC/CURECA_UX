# 3. 화면 설계

> 초안 · v0.64.

**목적:** 1단계 요건과 2단계 근거로 **화면 MD를 쓰고, 그것을 그대로 Figma에 그리는** 단계입니다. 화면 MD가 원본이고 Figma는 화면 MD를 옮긴 것입니다(헌법 6조). 질문이 있어도 먼저 그리고 질문 대기로 표시합니다(사용자 확인 라벨 · 사용자 확인 목록).

**목표:** 작업 기록 "요건 목록"에서 작업 대상이 `O`인 화면(CID)의 화면 MD를 쓰고 Figma에 그린 뒤, 아래 "마침 점검"(기계 검사)을 통과해 4단계로 넘깁니다.

## 절차

| 순서 | 하는 일 | 요청자 확인 |
| --- | --- | --- |
| 1 | 작업 기록과 읽을 것을 읽고 화면(CID)마다 케이스를 확인함 | 없음 |
| 2 | 화면(CID)마다 그 케이스의 흐름대로 화면 MD를 쓰고 Figma에 그림 | 없음 (질문 대기 · 변경 확인은 사용자 확인 라벨 · 사용자 확인 목록에 두고 4단계 절차 1번에서 보여 줌) |
| 3 | 용어를 점검함 | 없음 |
| 4 | 마침 점검(기계 검사)을 함 | 없음 |
| 5 | 3단계 보고를 함 | 4단계로 넘어갈지 물음. 모아 둔 질문이 있으면 함께 받음 |

- 작업 기록 "요건별 진행 경로"에서 3단계를 지나가는 요건만 그립니다. 경로 분기 기준 7 "정책만 바뀜"인 요건과 1단계에서 끝난 요건은 3단계가 "해당 없음"입니다(`flow/README.md` "단계를 지나는 규칙").
- 사용자 확인 목록(질문 대기 · 변경 확인)은 3단계에서 보여 주지 않고 4단계 절차 1번에서 보여 줍니다. 작업하다 꼭 물어야 할 것이 생기면 그 자리에서 멈추지 않고 작업 기록 "모아 둔 질문"에 적어 두고 넘어갈지 물을 때 함께 묻습니다(`flow/README.md` "단계를 지나는 규칙" 9). 화면에 걸린 질문은 먼저 그리고 질문 대기로 둡니다.

### 1) 작업 기록과 읽을 것을 읽고 화면(CID)마다 케이스를 확인함

**순서**

1. **3단계를 시작할 때 작업 기록 "요건 목록"에서 작업 대상이 `O`인 줄의 케이스를 확인하고, 화면(CID)마다 그 케이스의 흐름을 따릅니다.**

   | 케이스 | 따를 흐름 |
   | --- | --- |
   | 1 화면 부분 수정(고도화) | 아래 "케이스 1 흐름" |
   | 2 신규 | 아래 "케이스 2 흐름" |
   | 3 기존 화면 다시 그리기 | 아래 "케이스 3 흐름" |

2. **화면(CID)마다 묶어 그립니다.** 작업 기록 "요건 목록"에서 작업 대상이 `O`인 줄을 대상 화면(CID)마다 모읍니다. 한 화면의 줄은 케이스가 같으므로, 화면마다 그 케이스의 흐름을 한 번 따르며 그 화면의 요건을 모두 반영합니다. 화면 MD · 복제본 · Figma는 화면마다 한 번 고치고, 변경 확인은 요건마다 둡니다. 모은 결과는 작업 기록 "설계" 절의 화면별 표(화면 (CID) · 케이스 · 요건 번호)에 적습니다(아래 "남는 것").

**읽을 것 (모든 케이스)**

1. 작업 기록: "요건 목록"(작업 대상이 `O`인 줄, 영향 화면), "읽은 기존 화면"(기존 원본의 케이스 화면 포함), "요건별 진행 경로", "확인할 것", "이번에 반영할 반영 대기 항목", "근거"의 **읽은 자료 목록** · 관련 자료 없는 영역 · 요소 · 대조 · 정책 수정 범위 · 용어 목록, "이 작업의 결정", 질문 대기
2. **읽은 자료 목록에서 "설계에 씀"이 `O`인 자료.** 이 자료를 읽고 시작하며, 영역 · 요소를 그릴 때 그 영역에 쓰는 자료를 읽습니다. `-`인 자료는 읽지 않습니다. `관련 자료 없음`인 영역은 정책 · 가이드를 다시 찾지 않고 `공통 3-3` 요소를 찾는 순서로 그립니다.
3. `templates/screen.md` (화면 MD 틀), `reference-rules/description.md` (디스크립션 쓰는 법), `examples/`의 작성예시문서
4. UX가이드의 "Figma 컴포넌트" 표(컴포넌트 · Variant), `reference-rules/guide-element-defaults.md` (가이드 요소 기본값)
5. 그릴 Figma 페이지: 그리기 전에 먼저 열어 무엇이 있는지 확인함. 있던 그림은 옮기거나 지우지 않음

- **표시된 자료만으로 정의할 수 없는 것이 나오면 추가로 자료를 찾아 읽을 수 있습니다.** 읽은 자료는 작업 기록의 "읽은 자료 목록"에 `(3단계에서 추가)`를 붙여 더하고 설계에 씀을 표시합니다. `-`로 뺐던 자료를 쓰게 되면 `O`로 바꿉니다. 읽고도 목록에 남기지 않는 일은 없어야 합니다.
- 추가로 읽다가 정책과 기존 화면이 다른 곳을 새로 찾으면 2단계 "대조" 표에 더하고, 정책을 바꿔야 하면 요청자에게 알립니다.
- 디스크립션 번호가 정해지면 목록의 "쓰는 화면 · 영역 · 요소" 칸에 새 번호를 덧붙입니다.

### 2) 화면(CID)마다 그 케이스의 흐름대로 화면 MD를 쓰고 Figma에 그림

**순서**

1. 화면(CID)마다 아래 케이스 흐름 가운데 그 화면의 케이스 흐름을 따릅니다.

- 케이스 흐름은 **순서**입니다. 단계마다 그 케이스에만 해당하는 것은 흐름 안에 적었고, 모든 케이스가 같은 것은 "공통 규칙"에 한 번만 적고 흐름에서 `공통 1-2`처럼 가리킵니다.
- 다른 케이스의 흐름은 따르지 않습니다.
- 따른 케이스는 작업 기록 "설계" 절의 "화면별 요건" 표에 화면(CID)마다 적습니다. 마침 점검에서 확인합니다.
- **다시 고칠 때도 같은 순서입니다:** 3단계 안에서 요청자 의견으로 다시 고칠 때도 화면 MD(디스크립션)를 먼저 고치고 그다음 Figma를 고칩니다(헌법 6조). 버튼 위치 · 영역 크기처럼 배치만 바뀌는 수정도 같습니다.
- 케이스 3 기존 화면 다시 그리기는 기존 메뉴를 작업방으로 다 옮기면 없어집니다. 그때 이 문서에서 "케이스 3 흐름"과 공통 규칙 안의 케이스 3 표를 지웁니다.

#### 케이스 1 흐름 — 화면 부분 수정(고도화)

이미 있는 화면(T · L 모두)을 요청에 따라 일부 고칩니다. 고칠 범위는 1 · 2단계에서 정해져 옵니다.

| 순서 | 할 일 | 자세히 |
| --- | --- | --- |
| 1 | 작업 기록 "설계" 절 "화면별 요건" 표에 이 화면과 케이스 1을 적고 "읽을 것"을 읽음 | |
| 2 | **T 화면 MD를 먼저 고침** | 아래 1-2 |
| 3 | 바뀐 곳마다 변경 확인을 둠 | 아래 1-3 |
| 4 | **Figma를 열어 복제본을 만들고 T 원본을 고침** | 아래 1-4 |
| 5 | 같은 CID의 케이스 화면을 함께 고침 | 아래 1-5 |
| 6 | **요건 목록에서 작업 대상이 `O`인 짝 화면(L)에** 같은 순서로 고침 (2 ~ 5) | 아래 1-6 |
| 7 | 마무리 확인 (T · L 한 쌍), 작업 기록 `이어서 작업할 곳:` 고침 | `공통 3-10` |
| 8 | 모든 화면(CID)을 그렸으면 절차 3번으로, 남은 화면이 있으면 그 화면의 케이스 흐름으로 감 | |

**1-2. 화면 MD 고치기**

- `templates/screen.md` 구조를 그대로 씁니다(절을 빼거나 더하지 않음).
- **직전 버전의 빨간 표시:** 화면 MD를 고치기 전에 직전 버전의 바뀐 글 표시를 되돌립니다. 빨간 글씨 태그(`<span style="color:red">`)는 떼어 검정 글자로, 빨간 취소선은 `~~글자~~`로 둡니다. 그 뒤 이 작업에서 고치거나 더한 글자는 빨간 태그로 씁니다(`reference-rules/description.md` 7절 "바뀐 글 표시").
- 1 · 2단계에서 넘어온 것(작업 기록 "요건 목록"에서 작업 대상이 `O`인 줄의 요건, "확인할 것", 2단계 대조 결과)만 고칩니다. 고칠 범위는 1 · 2단계에서 정해져 오므로 3단계에서 따로 넓히지 않습니다. 화면 MD 변경 이력에 변경한 번호를 남깁니다.
- 기존 화면에 바로 고치며(시안을 따로 만들지 않음, 복제본은 1-4), 확정을 기다리지 않고 수정안이 바뀔 때마다 디스크립션을 화면과 함께 고칩니다.
- 디스크립션 · 화면 예시 · 케이스 표 · 반영 대기 · 작업 중 결정 · 가이드 요소 · 화면 표기 글자 표 · Alert · Confirm · Toast 표는 `공통 1`대로 씁니다.
- **번호:** 있던 번호는 바꾸지 않습니다. 요소를 **더하면 끝 번호**를 붙입니다. 단독 기능이면 화면의 맨 끝 번호 다음, 이미 번호가 있는 영역에 속하는 기능이면 그 영역의 맨 끝 번호 다음이며, 화면에서 놓이는 위치와 상관없습니다. 요소를 **제거하면** 번호를 그대로 두고(디스크립션은 그 번호의 블록을 지우지 않고 취소선, "제거된 요소"), 그 번호는 새 요소에 다시 쓰지 않습니다. 번호를 화면 순서대로 다시 매기는 때는 아직 정하지 않았습니다(`background/todo.md` 6 "보류"의 "기존 화면을 고친 뒤 취소선 정리와 번호 다시 매기기"). 예(TI-SPT-01 Samples, 지금 1 검색 영역 1-1 ~ 1-6 · 2 리스트 · 3 [Export] · 4 페이지네이션): 검색 영역에 Sample Type 조건을 더하면 1-7 / 리스트 위에 [Print] 버튼을 더하면 5 / STAT Only를 빼면 1-6은 번호와 글을 그대로 둠
- 변경 종류마다 디스크립션은 아래 1-3 표의 "디스크립션" 칸대로 처리합니다.

**1-3. 변경 확인**

바뀐 곳마다 변경 확인을 둡니다(번호 · 사용자 확인 라벨 · 사용자 확인 목록 · 화면 MD 표 · 작업 기록 표는 `공통 2`). 업데이트 메모 제목은 `v{Ver} update`(Ver은 4단계 UX 확정 때 요청자가 정함, `reference-rules/description.md` 7절 "화면 정보에 적는 값", 색은 `reference-rules/description.md` 5절 "업데이트 메모"의 색 규칙).

| 변경 | 디스크립션 | 사용자 확인 목록 문구 | 사용자 확인 라벨 |
| --- | --- | --- | --- |
| 더함 | 새 번호로 씀 | `{요소} 추가 (이유)` | 그 번호 표시 옆 |
| 바꿈 | 그 번호의 글을 고침 | `{기존} → {바꾼 것} (이유)` | 그 번호 표시 옆 |
| 제거 | 글을 지우지 않고 **3단계에서 바로 빨간 취소선**을 그음(개발자가 지운 것을 알 수 있게) | `화면에서 제거, 확정 시 취소선 처리 예정 (이유)` | **두지 않음.** 화면에서 요소와 번호 표시를 떼므로 사용자 확인 목록에만 둠 |
| 케이스를 지움 | 제거된 요소 때문에 필요 없어진 케이스는 바로 지움 | 본 화면 사용자 확인 목록 문구 끝에 `… Case n 삭제` | 케이스 조각에는 두지 않음 |

- 4단계에서 확인되면 다른 변경 확인과 같이 **Figma의 사용자 확인 목록 항목과 사용자 확인 라벨의 ID만 지웁니다.** 업데이트 메모는 4단계에서 UX 확정을 기입할 때 만듭니다(`reference-rules/description.md` 5절 "업데이트 메모"). 제거된 요소의 취소선 디스크립션은 지우지 않고 남깁니다.
- 고객 논의로 제거된 요소가 되살아나면 취소선과 Figma의 사용자 확인 목록 항목을 지우고 화면에 요소를 다시 넣습니다.
- 정해지지 않은 곳은 질문 대기(`공통 2`)입니다.

**1-4. Figma: 복제본을 만들고 원본을 고침**

- **복제본:** 원본을 고치기 직전에 원본의 복제본을 하나 만들어 두고, 고치는 것은 원본에 바로 합니다(고객 요청으로 원복하는 경우가 있음). T · L 각각 만듭니다.
  - 이름은 `CID-복제본`(예: `TI-SPT-01-복제본`), 위치는 원본 아래 200px입니다. 원본 높이가 바뀌면 복제본을 다시 원본 아래 200px로 옮깁니다(위치는 Figma 구조를 확인한 뒤 다시 정함, `background/todo.md` 3-8).
  - 4단계(수정 · 확인)가 끝나면 지웁니다.
  - 복제본은 바탕 · 후보 · 화면 MD 추출의 근거로 쓰지 않습니다.
- **직전 버전의 빨간 표시:** 복제본을 만든 직후, 원본을 고치기 전에 원본 패널의 빨간 글씨를 검정으로(코드는 파란색, `reference-rules/description.md` 7절 "참고 코드 표시"), 빨간 취소선을 검은 취소선으로 되돌립니다. 그 뒤 이 작업에서 고치거나 더한 글자는 빨간색, 제거된 요소와 제거된 문구는 빨간 취소선으로 씁니다(`reference-rules/description.md` 7절 "바뀐 글 표시").
- 화면 MD를 그대로 옮기며, 바뀌는 요소만 건드립니다. 컴포넌트 · 예시 데이터 · 번호 표시 · 질문 표시는 `공통 3`대로 합니다.
- 더하는 요소는 `공통 3-3`의 **"케이스 1 · 2" 표** 순서로 찾아 그립니다(가이드 컴포넌트 → 후보 → 신규로 만듦).
- 더한 요소에는 1-2의 끝 번호로 번호 표시를 붙이고, 바꾼 요소는 번호 표시를 그대로 두며, 제거된 요소는 요소와 번호 표시를 뗍니다.
- **패널:** `공통 3-6`대로 옮기고, 화면 정보의 Date는 작성일, 작성자는 요청자. Ver은 4단계 UX 확정 때 요청자가 정해 기입함(그 전까지 기존 화면의 Ver 그대로, `reference-rules/description.md` 7절 "화면 정보에 적는 값").

**1-5. 케이스 화면 함께 고치기**

본 화면을 고치면 같은 CID의 케이스 화면도 함께 고칩니다(케이스 화면 공통 규칙은 `공통 5`).

1. 고칠 케이스는 화면 MD 케이스 표의 "디스크립션 번호" 칸으로 찾고, 그 CID의 케이스 조각을 모두 훑어 고친 요소가 그려져 있는지도 봅니다.
2. 더한 요소의 그 조건에서의 값을 모르면 요청 · 정책에 있는 값, 없으면 본 화면과 같은 예시 값을 넣고 질문 대기를 둡니다.
3. 제거된 요소 때문에 필요 없어진 케이스는 확정을 기다리지 않고 바로 지우고, 케이스 표에 지웠다는 것을 남깁니다(그 Case 번호는 다시 쓰지 않음).
4. 케이스 조각에서 생긴 질문 · 변경은 그 조각의 번호 표시 옆에 사용자 확인 라벨을 두고, 사용자 확인 목록 항목은 본 화면의 사용자 확인 목록에 둡니다. 본 화면 변경이 케이스에도 걸리면 사용자 확인 목록 문구에 걸린 케이스를 적습니다(예: `… Case 1 · 3에도 반영`, `… Case 2 삭제`).

**1-6. L 화면**

요건 목록에서 짝 화면(L)의 작업 대상이 `O`이면, L 화면이 이미 있으므로 T를 복제하지 않고, L 원본의 복제본을 만든 뒤 T와 같은 순서(화면 MD → 변경 확인 → Figma → 패널 → 케이스 화면)로 L 화면을 고칩니다. L 디스크립션이 T를 가리키는 말 없이 완결인지 확인합니다. T · L 번호는 따로 관리합니다(`공통 3-7`).

**2-2. 구상**

화면 MD를 쓰기 전에 화면을 어떻게 짤지 정하고 **구상안 표**로 남깁니다. 구상안은 요청자에게 먼저 보여 주고 확인받지 않습니다. 묻지 않고 바로 그리고, 구상안 표는 기록으로 남깁니다(확인이 늘면 작업이 막히므로).

1. **하는 일 정하기:** 요청 글 · 요건 목록 · 2단계 근거(부르는 화면 · 형제 화면 · 같은 데이터)에서 새 화면의 목적 · 하는 일을 정합니다. 근거가 없는 것은 질문 대기로 두고 4단계에서 받습니다.
2. **틀 정하기:**
   - **Page = 레이아웃 구조 가이드의 9종**(공용 저장소 `PJ-CRC/CURECA_UX`의 `docs/layout_structures/Layout_Structure.html`): 1 대시보드 · 2 목록(테이블) · 3 목록 + 상세 패널 · 4 상태 모니터링 · 5 탭 + 장비 매트릭스 · 6 탭 + 목록 · 상세 분할 · 7 카드 선택 · 8 단계 진행 · 9 차트 + 필터 패널
     - 요청에 레이아웃이 정해져 있으면(팀 프로그램에서는 요청 입력의 레이아웃 선택) 그것을 따릅니다. 하는 일과 안 맞아 보여도 묻지 않고 고른 대로 그리고, 구상안 표에 "요청자가 고른 레이아웃"이라고 남깁니다.
     - 정해져 있지 않으면 Claude가 고릅니다. 가이드 "레이아웃 고르기" 표의 "화면이 하는 일"을 1번에서 정한 "하는 일"과 맞춰 봅니다(요약 → 1 / 목록이고 상세를 다른 화면으로 이동 → 2, 같은 화면 패널 → 3, 늘 함께 → 6 / 진행률 반복 → 4 / 장비 비교 → 5 / 작업 고르는 첫 화면 → 7 / 단계별 안내 → 8 / 추이 분석 → 9). 맞는 것이 둘 이상이면 1번에서 정한 "목적"에 해당하는 것, 그래도 갈리면 같은 메뉴의 다른 화면이 쓰는 구조를 고릅니다. 맞는 것이 없으면 억지로 고르지 않고 공통 틀 · 배치 원칙만 따라 그린 뒤 질문 대기 `맞는 레이아웃 구조 없음`을 둡니다.
   - **Popup = Common UX의 Popup(COMM-5-m).** 안의 내용은 화면 요소를 구성하는 방법과 똑같이 합니다(`공통 3-3`). Basic Popup의 Case는 Common UX의 "쓰임"으로 고릅니다: Case 1 단순 정보 전달 / Case 2 입력 · 선택 후 저장 / Case 3 저장 불필요.
3. **영역 나누기 → 영역마다 들어갈 요소 → 요소마다 쓸 것**(`공통 3-3` 요소를 찾는 순서)을 정합니다.
4. **구상안 표**를 작업 기록 "설계" 절에 남깁니다(아래 "남는 것"). 고른 레이아웃 · 고른 이유 · 고르지 않은 구조 · 맞는 구조가 없었는지 같은 판단도 적습니다.

**2-3. 화면 MD 새로 쓰기**

- `templates/screen.md` 구조를 그대로, 틀부터 새로 씁니다(절을 빼거나 더하지 않음).
- 1단계에서 정한 CID를 화면 MD · 섹션 · 화면 정보에 채웁니다. 구상하다 화면이 더 생기면 그 메뉴의 번호를 이어 붙이고 작업 기록에 더합니다. CID는 5단계(완료)에서 IA에 넣어 확정합니다(`flow/1-requirements.md` 절차 4번 순서 4, `flow/5-done.md` 절차 2번 순서 1).
- 0번의 User Type · L-IOS Client Mode는 근거가 있어도 늘 질문 대기로 두고 4단계(수정 · 확인)의 고객 검토에서 답을 받습니다.
- **번호:** 화면 · 디스크립션 번호를 처음부터 매깁니다(구상안 표의 번호 순서).
- 디스크립션 · 화면 예시 · 케이스 표 · 반영 대기 · 작업 중 결정 · 가이드 요소 · 화면 표기 글자 표 · Alert · Confirm · Toast 표는 `공통 1`대로 씁니다.

**2-4. 질문 대기 · 변경 확인**

- 변경 확인은 두지 않습니다(비교할 기존 화면이 없음).
- 정해지지 않은 곳은 질문 대기(`공통 2`)입니다. Claude가 판단한 곳(레이아웃 고르기, 후보 · 신규, Popup의 Case, 케이스 점검)은 질문 대기 없이 기록으로 남깁니다(`공통 2`).

**2-5. Figma 그리기**

- 화면 MD를 그대로 그립니다(`공통 4` 작업방 구성).
- 요소는 `공통 3-3`의 **"케이스 1 · 2" 표** 순서로 찾아 그립니다(가이드 컴포넌트 → 후보 → 신규로 만듦).
- 컴포넌트 · 예시 데이터 · 번호 표시 · 질문 표시 · Popup은 `공통 3`대로 합니다.
- **패널:** `공통 3-6`대로 옮기고, 화면 정보의 Date는 작성일, 작성자는 요청자. Ver은 4단계 UX 확정 때 요청자가 정해 기입함(그 전까지 비워 둠, `reference-rules/description.md` 7절 "화면 정보에 적는 값").
- 바뀐 글 표시(빨간 글씨)는 하지 않습니다. 모두 새로 쓴 글입니다(`reference-rules/description.md` 7절 "바뀐 글 표시").

**2-6. 케이스 화면**

`공통 5`대로 그립니다. 근거는 디스크립션 조건 · 요청자입니다. 빠뜨린 조건이 없는지 **구상에서 참고한 기준 화면의 케이스를 한 번 훑어** 점검합니다. 같은 종류의 조건이 신규 화면에도 있고 근거(요청 · 정책 · 2-2 구상 1번에서 정한 목적 · 하는 일)가 있으면 디스크립션에 적고 그립니다. 근거 없이 기준 화면만 보고 그린 케이스는 질문 대기 `이 케이스가 필요한지 (참고한 화면 · Case)`로 둡니다(요청자는 필요한지만 답하면 됨). 점검한 내용은 작업 기록 "찾은 것"에 남깁니다.

| 2 | **요건 목록에서 작업 대상이 `O`인 화면의 화면 MD(T · L 모두)를 한 번에 asis에서 tobe로 새로 씀** (번호는 그대로, 제거된 요소는 지우고 제거된 문구는 검은 취소선으로 옮김) | 아래 3-2 |
| 3 | 기존 화면과 다르게 그린 곳마다 변경 확인을 둠 | 아래 3-3 |

| 7 | 마무리 확인 (T · L 한 쌍), 작업 기록 `이어서 작업할 곳:` 고침 | `공통 3-10` |
| 8 | 모든 화면(CID)을 그렸으면 절차 3번으로, 남은 화면이 있으면 그 화면의 케이스 흐름으로 감 | |

**3-2. 화면 MD 새로 쓰기**

- 1단계에서 만든 `screens/tobe/{메뉴}/{CID}.md`를 `templates/screen.md` 틀대로 채우고(반영 대기 목록은 그대로 둠, `source: tobe`, 절을 빼거나 더하지 않음. `screens/asis/`의 화면 MD는 그대로 둠), 변경 이력에 "작업방에 새로 그림 (기존 작업방 링크 · Ver)"을 남깁니다.
- 기존 원본에 있던 케이스 화면은 빠짐없이 옮깁니다(Case 번호 그대로).
- 디스크립션 · 화면 예시 · 케이스 표 · 반영 대기 · 작업 중 결정 · 가이드 요소 · 화면 표기 글자 표 · Alert · Confirm · Toast 표는 `공통 1`대로 씁니다.
- **번호:** 기존 디스크립션 번호를 그대로 씁니다(다시 매기지 않음). 기존 디스크립션의 제거된 요소(번호 블록 전체에 취소선)는 디스크립션에서 지우고, 화면 위 그 번호 표시도 지웁니다. 기존 디스크립션의 제거된 문구(남은 요소 안의 일부 문구에만 취소선)는 지우지 않고 검은 취소선으로 옮깁니다(화면 MD에는 `~~글자~~`). 빈 번호(예: TI-SPT-01의 1-3)는 그대로 두고 새 번호로 쓰지 않습니다. 기존 원본에 같은 번호가 두 번 나오면 앞의 것은 그대로 두고 뒤의 것에 그 화면(또는 그 영역)의 끝 번호 다음 번호를 붙이며, 기존 원본에 없는 요소를 더할 때도 끝 번호 다음 번호를 붙입니다(케이스 1과 같은 법). 번호를 바꾼 곳은 변경 확인으로 둡니다. 지운 것은 사용자 확인 목록의 0번(화면 정의) 블록에 변경 확인 한 줄로 둡니다(사용자 확인 라벨은 두지 않음): `제거된 요소 n개 지움 (기존 디스크립션에서 이미 지운 기능)`.
- **기존 디스크립션에 없는 설명을 더할 때:** `reference-rules/description.md` 3절 "공통 UX가 화면에 맡긴 것" 때문에 기존 디스크립션에 없던 설명을 더하면(예: 표의 칸 구성), 화면 글자 · 정책에서 채우고 변경 확인을 둡니다(사용자 확인 목록 문구 예: `표출 항목 추가 (기존 디스크립션에 칸 구성 없음)`).
- 기존 디스크립션의 참고 줄은 `○○ 참고 : 코드` 모양(`reference-rules/description.md` 2절 "참고")으로 옮겨 씁니다. 문장 끝 괄호 안의 케이스 코드(`(참고 : TI-STA-01/Case > Case 2)`)는 블록 끝 `케이스 참고` 줄로 옮깁니다. 동작 줄 안의 Alert · Confirm · Toast · 화면 코드는 그대로 둡니다. 모양만 바꾼 것이라 바뀐 글 표시를 하지 않습니다.
- 기존 디스크립션에 Alert · Confirm · Toast 문구가 적혀 있으면 지우고 코드만 남깁니다(`reference-rules/description.md` 3절). 모양만 바꾼 것이라 바뀐 글 표시 · 변경 확인을 하지 않습니다.
- **토스트에 코드가 없으면** 토스트 카탈로그(일반 메뉴 `alert/toast-catalog.csv`, Material Setup `alert/toast-catalog-ms.csv`)에서 찾습니다. 문구는 코드를 찾는 데만 쓰고, 디스크립션에는 코드만 남깁니다.
  - **토스트 줄:** 줄에 `토스트` 또는 `toast`가 있음(대소문자 · 띄어쓰기 · "팝업" · "Popup" · "메시지"가 붙은 것도 같음).
  - **문구:** 그 줄의 `:` 뒤, 거기 없으면 바로 아래 줄(`Main text:` · `text :` 등)의 영어 글. 취소선 글자는 빼고 봅니다.
  - **사용 화면 맞춰 보기:** 카탈로그 "사용 화면"이 줄인 이름이면 CID 끝부분으로 맞춰 봅니다(`DXI-02` = `LI-TSS-DXI-02`). 범위(`DXI-01~07`)는 그 안의 번호를 모두, 묶음 이름(`DXI`)은 그 이름으로 끝나는 CID만 포함으로 봅니다(`LI-TSS-DXI`는 듦, `LI-TSS-DXI-01`은 들지 않음).
  - **같음**(문구가 글자 그대로 같음. 카탈로그 문구의 `{…}` 자리는 어떤 값과도 같은 것으로 봄): 그 코드를 그 줄에 적고, 카탈로그 그 줄의 "사용 화면"에 이 CID가 없으면 더합니다(Alert · Confirm처럼 여러 화면이 한 줄을 씀).
  - **비슷함**(① 대소문자 · 마침표 · 띄어쓰기를 빼면 같음, 또는 ② 카탈로그 줄의 "사용 화면"에 이 화면이 있는데 문구가 다름): 같은 것으로 보지 않고 아래 "없음"처럼 새 줄을 만듭니다.
  - **없음**: 그 카탈로그에 새 줄을 더해(다음 번호, 종류 `Toast`, 발생 조건 · 제목 · 부제는 디스크립션에서, "등급"(Property: Success / Info)은 `alert/alert-catalog.md` "토스트"의 기준으로, 사용 화면 = 이 CID) 그 코드를 적습니다. 질문 대기 · 변경 확인은 두지 않습니다.
  - **문구 없음**(토스트라는 말만 있음): 카탈로그에 줄을 더하지 않고 질문 대기를 둡니다(예: `토스트 문구 (기존 디스크립션에 문구 없음)`). 답으로 문구를 받으면 같음 · 비슷함 · 없음대로 합니다.
  - `toast-catalog.csv`가 아직 없으면 `toast-catalog-ms.csv`와 같은 칸으로 만들고, 번호는 `Toast_001`부터, 사용 화면은 CID 전체로 씁니다.
  - 카탈로그에 줄을 더하거나 사용 화면을 더하면 작업 기록 "이 작업이 남긴 것"의 "고친 카탈로그 줄"에 적습니다.

**3-3. 변경 확인**

기존 화면과 다르게 그린 곳마다 변경 확인을 둡니다(언제 두는지 · 번호 · 표는 `공통 2`). 단, 디스크립션 `공통 UX 참고`의 번호를 새 Common UX 번호로 바꾼 것(예: COMM-5-s → COMM-5-p)은 변경 확인을 두지 않습니다. 케이스 3은 새 Common UX로 다시 그리므로 모든 화면에서 생기는 일이기 때문입니다. 업데이트 메모는 기존 작업방의 그 화면 메모를 그대로 옮겨 옵니다. 다시 그리며 바뀐 것을 남기는 `재설계 후 변경 내역` 메모는 4단계 UX 확정 때 만듭니다(`reference-rules/description.md` 5절 "업데이트 메모"의 "케이스 3"). 정해지지 않은 곳은 질문 대기(`공통 2`)입니다.

#### 공통 2. 질문 대기 · 변경 확인 (질문이 생기거나 기존 화면과 다르게 그릴 때)

질문 대기 · 변경 확인은 디스크립션 본문에 넣지 않고, 사용자 확인 라벨과 사용자 확인 목록에만 둡니다(`reference-rules/description.md` 5절). 케이스마다 변경 확인을 어디에 두는지와 업데이트 메모 제목은 케이스 흐름(1-3 / 2-4 / 3-3)에 있습니다.

- **번호:** 작업 하나에 통번호를 씁니다(Q1 · Q2 … / C1 · C2 …). T · L에 같은 것은 같은 번호. 사용자 확인 라벨 · 사용자 확인 목록 · 화면 MD 표 · 작업 기록에 같은 번호를 씁니다.
- **질문 대기 — 정해지지 않은 곳:** 먼저 그립니다. 따를 것을 이 순서로 찾습니다: 그 화면의 기존 원본(UX 화면설계서) → 정책서 → 공통 UX → 같은 메뉴의 다른 화면. 찾은 내용으로 그리고 쓴 뒤 질문을 작업 기록 질문 대기 표 · 사용자 확인 목록에 올리고 그 번호 옆에 사용자 확인 라벨을 둡니다. 넷 다 없으면 디스크립션에 지어 쓰지 않고 질문만 둡니다.
- **변경 확인 — 근거가 있어 기존 화면과 다르게 그린 곳:** 2단계 대조에서 "기존 화면이 정책과 다름"으로 나온 곳은 정책을 따라 그리고, 기존과 무엇이 달라졌는지 사용자 확인 목록에 적고 그 번호 옆에 사용자 확인 라벨을 둡니다. 반영 대기 항목을 반영해 달라진 곳, 행을 줄여 그린 곳도 같습니다. 작업 기록 변경 확인 표에 올립니다. 4단계 요청자 확인에서 맞는지 확인받고, 확인된 것은 사용자 확인 목록 항목과 라벨 ID를 지우고, **업데이트 메모**는 4단계에서 UX 확정을 기입할 때 만듭니다. 변경 확인 줄을 만들 때 작업 기록 변경 확인 표의 "업데이트 메모 (O / -)" 칸을 채웁니다(`reference-rules/description.md` 5절 "업데이트 메모").
- 정책을 정해야 하는 질문이면 논의 대상을 `논의 중`으로 만들고(`work`에 작업 기록 이름) 질문 대기 표에 DS ID를 잇습니다(`reference-rules/discussions.md` "자주 있는 네 가지 경우" 라).
- 내 화면만 바뀌는 질문(표현 · 배치 · 문구)은 논의 대상을 만들지 않고 요청자가 답하면 고친 뒤 Figma의 사용자 확인 목록 항목과 라벨 ID를 지웁니다.
- **Claude가 판단해 정한 곳은 질문 대기 · 변경 확인을 붙이지 않고 기록으로만 남깁니다.** 질문 대기 · 변경 확인은 요청자가 실제로 정해 줘야 하는 것에만 씁니다. 새 표시(`※ 판단 확인` 같은 것)는 만들지 않습니다. 규칙이 Claude에게 판단을 맡긴 곳(레이아웃 고르기, 후보에서 찾아 쓰기 · 신규로 만들기, Popup의 Case 고르기, 케이스 화면 점검)은 판단한 내용을 구상안 표 · 작업 기록 "찾은 것"("규칙에 없어 판단한 곳") · "컴포넌트 없이 그린 요소" 표에 남깁니다. 요청자가 화면을 보다 이상한 곳이 있으면 이 기록에서 근거를 찾습니다. 근거가 없어 정할 수 없는 곳은 기록이 아니라 질문 대기입니다.
- 고객이 앞서 정한 결정을 다시 고치면 같은 논의 대상에 결정 줄을 더하고 화면을 새 결정으로 고칩니다(경우 다).

#### 공통 3. Figma 그리기

화면 MD를 그대로 그립니다. 페이지 · 배치 · 프레임 이름은 `공통 4` 작업방 구성을 따릅니다. 그리기 시작할 때 그 메뉴의 기획 진행 표시를 `공통 4` "메뉴 단위 표시"대로 둡니다(케이스 1 · 2는 `작업 중`, 케이스 3은 기존 표시를 옮김).

1. **그리는 차례:**
   - **자리를 먼저 잡음 (케이스 2 · 3):** 화면을 그리기 전에 페이지 · 메뉴 단위 표시 · 이번에 그릴 CID의 섹션(T · L 모두, 빈 섹션)을 먼저 만들어 자리를 잡습니다(`공통 4`).
   - **T · L 한 쌍씩:** 목록 화면 → 상세 → Popup처럼 메뉴 흐름 순서로, 같은 CID의 T · L 한 쌍마다 T를 먼저 끝내고 바로 L을 그립니다.
   - **다 그린 뒤:** 메뉴 단위 표시 너비와 L-IOS 줄 위치를 다시 맞춥니다(`공통 4`).
2. **컴포넌트:** 가이드 "Figma 컴포넌트" 표의 컴포넌트를 인스턴스로 씁니다. 떼어 내지(detach) 않고 속성(Variant) · 글자 · 크기 · 보이기만 바꿉니다. 맞는 Variant가 있으면 그것을 쓰고, 없으면 그 컴포넌트의 기본 Variant를 쓴 뒤 질문 대기를 둡니다. 다른 컴포넌트로 바꿔 쓰지 않습니다. 그리는 재료 · 컴포넌트 대응표는 Common UX 담당자와 정하는 중이며, 정해질 때까지 가이드 "Figma 컴포넌트" 표를 그대로 씁니다(`background/todo.md` 3-2).
   - **기획 공통 컴포넌트:** 화면 요소가 아닌 기획 표시는 UX-AI-TEST 파일 Common UX 페이지의 **SB-Components (기획 공통)** 프레임([`2673:21866`](https://www.figma.com/design/etCQFF3CTf1EA6C79d4BBf/UX-AI-TEST?node-id=2673-21866))의 컴포넌트를 인스턴스로 씁니다: 시스템 구분 표시(`시스템 구분`) · 기획 진행 표시(`진행상태-기획`)는 `공통 4`, 패널(`Description`) · 번호 표시(`Description Number`) · 업데이트 메모(`ver`)는 `reference-rules/description.md` 7절 · 5절, 사용자 확인 라벨 · 사용자 확인 목록(`Label/Status/With Icon` · `Review List/…` · `사용자 확인 목록 (Template)`)은 같은 문서 5절.
   - **LNB 선택 상태:** 그 화면이 속한 메뉴의 `LNB/Menu`를 Selected = On으로 둡니다. 하위 메뉴가 있는 메뉴면 그 `LNB/Menu`의 2 Depth = On(펼침)으로 두고, 그 화면의 하위 메뉴 `LNB/2 Depth`를 Selected = On으로 둡니다. 어느 메뉴 · 하위 메뉴인지는 IA(`ia/ia-screens.csv`)의 Lv.1 · Lv.2로 봅니다.
3. **요소를 찾는 순서:** 요소를 그릴 때 쓸 것을 아래 순서로 찾습니다. **순서가 케이스마다 다르므로 자기 케이스의 표를 따릅니다.**

   **케이스 1 화면 부분 수정(고도화) · 케이스 2 신규**

   | 순서 | 상황 | 그리는 법 |
   | --- | --- | --- |
   | ① | 가이드에 컴포넌트가 있음 | 가이드 컴포넌트를 씀 (위 2번) |
   | ② | 가이드에 없고, 후보 목록(`common-ux/candidates.md`)에 맞는 것이 있음 | 후보를 가져다 씀. 목록의 "Figma 링크"에서 값을 읽어 **같은 값으로** 그리고, 작업 기록 "컴포넌트 없이 그린 요소" 표에 후보 ID를 남김 |
   | ③ | 후보에도 적절한 것이 없음 | **신규로 만들어 씀.** 묻지 않고 만들어 그리고, 작업 기록 "컴포넌트 없이 그린 요소" 표에 "신규로 만듦"으로 남김 |

   - **후보 목록에 "맞는 것":** 화면 MD 디스크립션에 적힌 그 요소의 종류 · 하는 일이 후보 목록의 "요소 이름 (종류)" · "하는 일"과 같으면 맞는 것으로 봅니다. 같은지 애매하면 가장 비슷한 후보로 그리고 질문 대기 `{후보 ID}를 써도 되는지`를 둡니다.

   **케이스 3 기존 화면 다시 그리기**

   | 순서 | 상황 | 그리는 법 |
   | --- | --- | --- |
   | ① | 가이드에 컴포넌트가 있음 | 가이드 컴포넌트를 씀 (위 2번). 컴포넌트로 바꿔 원본 요소와 크기가 달라지면, 원본에서 따온 나머지 요소(영역 틀 · 간격 · 그 뒤의 요소)와 번호 표시를 그 컴포넌트에 맞춰 다시 그림 |
   | ② | 가이드에 없고, 그 화면의 기존 UX 화면설계서에 있음 | 그 요소를 똑같이 따옴. 바탕 도형 · 영역 틀(예: 콘텐츠 영역 바탕, 검색 영역 바탕, 요약 줄 틀)도 이 요소에 들어감. 기존 프레임에서 크기 · 색 · 글자 크기 · 간격 값을 읽어 **같은 값으로** 그리고, 읽은 원본 위치를 화면 예시 표의 "기준" 칸에 적음. 따온 요소는 작업 기록 "컴포넌트 없이 그린 요소" 표에 "기존 화면에서 따옴"으로 남김 |
   | ③ | 가이드에도 기존 화면에도 없음 | **직접 그리고 변경 확인을 둠.** 기존 화면에 없던 것이 생긴 것이므로 요청자가 확인할 수 있게 표시하고, 작업 기록 "컴포넌트 없이 그린 요소" 표에 "신규로 만듦"으로 남김 |

   어느 케이스든 아래는 같습니다.
   - **가이드에 컴포넌트가 "있음":** 화면 MD 디스크립션에 적힌 그 요소의 종류 · 하는 일이 가이드 컴포넌트와 같으면 가이드에 있는 것으로 봅니다. 모양(안에 든 칸 · 배치)이 달라도 종류 · 하는 일이 같으면 ①입니다. 맞는 Variant가 없으면 위 2번대로 기본 Variant를 쓰고 질문 대기를 둡니다. 같은지 애매하면 ①로 보고 가장 비슷한 가이드 컴포넌트로 그린 뒤 질문 대기 `{컴포넌트 이름}을 써도 되는지`를 둡니다.
   - **가져다 쓰는 것은 근거가 확인된 것이어야 합니다.** 테스트로 그린 그림과 완료되지 않은 그림은 바탕으로도 후보로도 쓰지 않습니다.
   - **후보** = 후보 목록(`common-ux/candidates.md`)에 있는 요소. 가이드에는 없지만 완료된 다른 화면에서 이미 쓰고 있는 것입니다. 목록에는 5단계 완료 때만 올리므로(`common-ux/candidate-rules.md`, 지금은 올리지 않음: `flow/5-done.md` 절차 2번 순서 6) 3단계에서는 목록에 쓰지 않고 작업 기록에만 남깁니다.
   - 기존 화면은 **UX 화면설계서**(기존 작업방에서 오른쪽에 화면 정보 · 디스크립션 패널이 붙은 너비 2252의 기획 프레임과 그 디스크립션)만 근거로 씁니다. 디자인 화면(1920×1080 디자인 프레임 · 디자인 파일)에서는 가져오지 않습니다.
   - 가이드에 그림만 있고 컴포넌트가 없는 경우도 "가이드에 컴포넌트가 없는 요소"로 봅니다.
   - 컴포넌트 없이 그린 요소는 어디서 가져왔는지(후보 · 신규로 만듦 · 기존 화면에서 따옴)를 작업 기록 "컴포넌트 없이 그린 요소" 표에 남깁니다.
4. **예시 데이터:** 화면 MD "화면 예시" 표의 값만 씁니다. **목록 · 표는 한 페이지 최대 노출 개수(예: 10 items)만큼 행을 채웁니다.** 최대 개수의 행이 화면 높이(1080) 안에 들어가지 않으면 들어가는 만큼만 그리고, 그린 행 수와 이유를 화면 예시 표에 적은 뒤 변경 확인을 둡니다.
5. **L은 T를 복제한 뒤 다른 점만 바꿈 (케이스 2 · 3):** LNB · GNB를 L-IOS로, CID · 호출 화면 CID를 L로, 0번에 L-IOS Client Mode 소제목, 원본에서 찾은 L만의 차이. 바꾼 뒤 L 디스크립션이 T를 가리키는 말 없이 완결인지 확인합니다. 케이스 1은 복제하지 않고 있는 L을 고칩니다(1-6).
6. **패널:** 오른쪽 패널에 화면 정보 표와 디스크립션을 화면 MD 그대로 옮깁니다. 그리는 중에 문장을 고치면 화면 MD와 Figma를 함께 고칩니다. 패널은 모든 화면에서 같은 틀 · 크기 · 위치로 그립니다(`reference-rules/description.md` 7절): 화면 오른쪽에 너비 332, 맨 위 화면 정보(Ver · Date · CID · 작성자 · 화면 · 경로), 번호 칸은 영역은 회색 · 요소는 흰색, 맨 아래 Dev · SG 줄은 두지 않음. 화면 정보의 Ver · Date · 작성자는 케이스 흐름(1-4 / 2-5 / 3-4)에 있습니다.
7. **번호 표시:** SB-Components (기획 공통) 프레임의 `Description Number` 컴포넌트(키 `8a4b8376fadaebeee5604169fd2b206cfb323b84`) 인스턴스로 둡니다. 화면 위 번호를 디스크립션 번호(영역 1 · 요소 1-1)와 같게 매깁니다. 번호를 매기는 법과 빼는 요소 · 취소선 항목의 번호 표시는 케이스 흐름(1-2 · 1-4 / 2-3 / 3-2)에 있습니다.
   - **T · L 번호는 따로 관리합니다 (모든 케이스):** T와 L은 화면마다 번호를 매기며, 같은 영역이라도 번호가 달라도 됩니다. 예: T는 4번까지, L은 L만의 요소가 있어 5번까지일 때 버튼을 더하면 T 5 · L 6.
   - **자리:** 번호 표시는 그 요소의 왼쪽 위 모서리에 걸쳐 둡니다. 글자 요소(제목 · 라벨)는 글자 바로 왼쪽에 둡니다. **케이스 3**은 기존 원본(기존 작업방 기획 프레임)의 같은 번호와 같은 자리에 두고, 기존 원본에 없는 요소만 왼쪽 위 모서리에 둡니다. 사용자 확인 라벨 때문에 빈 곳으로 옮길 때도 가리키는 요소 바로 옆을 벗어나지 않습니다.
8. **질문 표시:** 질문 대기 · 변경 확인마다 화면의 그 번호 표시 옆에 사용자 확인 라벨(`Label/Status/With Icon`)을 두고, 패널 오른쪽에 사용자 확인 목록을 둡니다(라벨 · 목록 규칙은 `reference-rules/description.md` 5절).
9. **Popup을 그리는 법 (작성예시문서 LI-RUN-P Run Preparation Popup):** ① 크기는 정해 둔 너비 · 높이 없이 내용에 맞춰 잡고, 높이를 제한하지 않고 내용을 모두 보여 주도록 길게 그립니다(스크롤 · 높이 · 일반 팝업이냐 풀 팝업이냐는 UI 디자이너가 판단). 내용이 화면 높이를 넘으면 기획 프레임을 길게 늘립니다 ② 모든 Popup은 부르는 화면을 뒤에 깔지 않고 **Dim만 깔고** 그 위에 그립니다. 여러 화면에서 부르는 공통 Popup도 같습니다.
10. **마무리 확인:** T · L 한 쌍마다 스크린샷을 찍어 아래를 보고, 고친 뒤에 다음으로 넘어갑니다. 한 쌍을 끝낼 때마다 작업 기록 `이어서 작업할 곳:` 줄을 고칩니다.
    - **글자가 칸을 넘지 않음:** 버튼 · 사용자 확인 라벨 · 표의 셀 · 입력란 · 카드 · 패널의 글자가 자기 칸 밖으로 나가거나, 잘리거나, 옆 요소와 겹치지 않음
    - 넘치면 이 순서로 고침: ① 컴포넌트의 너비 · 높이를 내용에 맞게 늘림(떼어 내지 않고 크기만) ② 가이드가 말줄임을 정한 곳(예: 표의 셀)은 말줄임으로 ③ 그래도 안 되면 배치를 넓히고, 배치를 바꿀 수 없으면 질문 대기로 남김. 글자 크기를 줄이거나 예시 값을 임의로 짧게 바꾸지 않음
    - 요소끼리 겹치지 않고, 번호 표시가 가리키는 요소 옆에 있으며, 패널이 화면 오른쪽에 붙어 있음

#### 공통 5. 케이스 화면

조건에 따라 화면의 모습이 달라지는 곳을 보여 주는 그림입니다(작업 유형인 케이스 1 · 2 · 3과 다른 말입니다). 작성예시문서는 `examples/case-samples.md`이고, 이 결로 그립니다. 케이스마다 더 하는 일은 케이스 흐름(1-5 함께 고침 / 2-6 점검 / 케이스 3은 기존 원본을 빠짐없이 옮김)에 있습니다.

**케이스의 원본은 화면 MD "케이스" 표 하나입니다.** 따로 파일이나 버전을 두지 않습니다.

```markdown
| Case | 제목 | 조건 | 디스크립션 번호 | 종류 | 근거 |
| --- | --- | --- | --- | --- | --- |
```

**표에 올릴 수 있는 근거는 셋뿐입니다.** 어느 것도 아니면 올리지 않고 질문으로 둡니다.

| 근거 | 뜻 |
| --- | --- |
| 기존 원본 | 기존 작업방에 있던 케이스. 빠짐없이 옮기고 Case 번호도 그대로 가져옴 |
| 디스크립션 조건 | 디스크립션에 적힌 조건 가운데 아래 여섯 종류에 드는 것 |
| 요청자 | 요청자가 그리라고 한 것 |

**"디스크립션 조건"으로 그리는 것은 여섯 종류입니다.** 여기에 들지 않는 조건(버튼 활성화 조건, 기본값 등)은 디스크립션에만 적고 그리지 않습니다.

#### 공통 6. 영향 화면

- 같은 메뉴(같은 CID 체계)에서 함께 고칠 화면은 1 · 2단계에서 작업 기록 "요건 목록"에 작업 대상 `O`인 줄로 들어옵니다. 그 화면도 요건 목록의 줄로 보고 그 케이스의 흐름대로 그립니다.
- 다른 메뉴의 화면(작업 기록 "영향 화면" 표)은 3단계에서 고치지 않습니다. 5단계 완료 때 그 화면의 반영 대기 목록에 항목으로 남깁니다(`flow/5-done.md`).

- 질문이 있다고 그 부분을 그리지 않거나 디스크립션에서 빼기
- 출처 없는 내용을 질문 대기 없이 확정된 것처럼 쓰기
- 고르지 않은 반영 대기 항목을 반영하기, "반영 대기"로 고른 다른 화면을 고치기
- 같은 페이지의 기존 그림을 옮기거나 지우기
- 테스트로 그린 그림 · 완료되지 않은 그림을 복제해 바탕으로 쓰거나 후보로 쓰기. 케이스 1의 `CID-복제본`을 바탕 · 후보 · 화면 MD 추출의 근거로 쓰기
- 자기 케이스가 아닌 흐름을 따르기
- 기존 화면을 참고할 때 디자인 화면(디자인 프레임 · 디자인 파일)에서 모양이나 내용을 가져오기. 기존 화면은 UX 화면설계서(기획 프레임과 디스크립션)만 근거로 씀
- 기존 화면과 다르게 그리고도 변경 확인을 두지 않기
- 글자가 칸을 넘거나 잘린 채로 끝내기, 넘친다고 글자 크기를 줄이기

### 남는 것

- 화면 MD: `screens/tobe/{메뉴}/{CID}.md` (테스트면 저장소 밖 작업 폴더)
- Figma: CID 섹션마다 기획 프레임, 케이스가 있으면 `CID/Case` 프레임
- 작업 기록 "질문 대기" · "변경 확인" 절: 작업 기록에는 이 두 표를 "설계" 절 아래에 두지 않고 최상위 절 하나씩만 둡니다(`reference-rules/work-log.md` "틀"). 3단계는 줄을 만들며 질문 대기는 번호 · 질문 · 관련된 곳 · 논의 대상 · T · L 같음을, 변경 확인은 번호 · 기존 화면 · 바꿔 그린 것 · 관련된 곳 · 근거 · T · L 같음 · 업데이트 메모 (O / -)를 채웁니다. "풀린 날 · 어떻게"와 "확인한 날 · 답" 칸은 4단계가 채웁니다.

## 마침 점검

기계 검사입니다. 하나라도 통과하지 못하면 이 단계 안에서 고칩니다. 질문 대기가 남아도 그리기는 끝까지 하고, 남은 질문은 4단계 요청자 확인으로 넘깁니다. 결과는 "통과" / "통과하지 못함" 둘로만 적습니다. 통과하면 작업 기록 "단계" 표 "3. 화면 설계" 줄의 "끝낸 날"과 "마침 점검" 칸에 `기계 검사 통과 (날짜)`를 적습니다(4단계가 이 칸을 보고 시작함).

| # | 검사 | 보는 것 |
| --- | --- | --- |
| 1 | 짝 CID | 요건 목록에서 작업 대상이 `O`인 화면(CID)이 모두 화면 MD와 Figma 섹션으로 있음. 작업 대상이 `X`인 짝 화면은 그리지 않음 |
| 2 | 화면 MD 틀 | `templates/screen.md`의 절이 모두 있음. 디스크립션 동작 줄의 Alert · Confirm · Toast 코드가 모두 "Alert · Confirm · Toast" 표에 있음 |
| 3 | 화면 MD = Figma | 디스크립션 · 번호 · 예시 값이 같음 (제거된 요소는 화면에 번호 표시가 없음. 제거된 문구만 있는 요소는 번호 표시가 있음). 화면 MD "화면 표기 글자" 표의 영어 글자가 화면의 글자와 같고, 화면에 표기된 글자가 표에 빠짐없이 있음 |
| 4 | 행 수 | 목록 행 수가 디스크립션의 노출 개수와 같음 (줄였으면 이유가 있음) |
| 5 | 케이스 화면 | 화면 MD 케이스 표, Figma의 Case, 디스크립션의 `케이스 참고 : CID/Case > Case n` 줄이 서로 1:1로 맞음. 표의 줄마다 근거(기존 원본 · 디스크립션 조건 · 요청자)가 있음. 기존 원본의 케이스가 빠지지 않음 |
| 6 | 질문 대기 · 변경 확인 | 항목마다 번호(Q · C)가 있고, 같은 번호가 사용자 확인 라벨 · 사용자 확인 목록 · 작업 기록 표에 모두 있음(화면에 번호 표시가 없는 곳 — 0번, 케이스 1의 제거된 요소, 케이스 3에서 지운 제거된 요소 — 은 사용자 확인 라벨 제외). 작업 기록 질문 대기 표 · 사용자 확인 목록의 질문 대기 그룹이 1:1. 작업 기록 변경 확인 표 · 사용자 확인 목록의 변경 확인 그룹이 1:1. 디스크립션 본문에 질문 · 변경 표시가 없음. 1단계 "확인할 것"의 줄마다 이어진 번호가 적혀 있음. 2단계 대조에서 "기존 화면이 정책과 다름"으로 나온 곳마다 변경 확인이 있음 |
| 7 | 컴포넌트 | 가이드 컴포넌트를 떼어 내지 않고 인스턴스로 씀 |
| 8 | 예시 데이터 | 화면의 상태값 · Module · Unit(이름과 구성) · 품목 · 수량이 화면 예시 표 · 기준데이터 값임 |
| 9 | 용어 | 쓰지 않는 표현이 남지 않음 (단어 단위) |
| 10 | 반영 대기 | 1단계에서 고른 항목(`작업 중`)만 반영했고, 고르지 않은 항목은 `대기` 그대로임. 이 단계에서 `반영 완료`로 바꾼 줄이 없음. 케이스 3이면 asis 반영 대기 목록의 항목 ID가 모두 To-Be 화면 MD 반영 대기 목록에 있음(`reference-rules/pending-changes.md` 6절) |
| 11 | 글자 넘침 | 기획 프레임 · 케이스 프레임 · 패널의 모든 글자가 자기 칸 안에 있음(넘침 · 잘림 · 겹침 없음). 글자 노드의 영역이 부모 칸 안에 있는지 확인하고, 스크린샷으로 한 번 더 봄 |
| 12 | 작업방 구성 | 섹션 이름 · 프레임 이름 · 섹션 안 순서 · 섹션 너비(100 + 기획 프레임 너비 + 5 + 330 + 100) · 위 · 왼쪽 · 아래 여백 100px · 섹션끼리의 가로 간격 200px · 사용자 확인 목록 폭 330 · 기획 프레임 너비 2252(케이스 3은 기존 원본의 너비) · 케이스 프레임 너비(기획 프레임과 같음) · 패널 너비 332가 `공통 4` 작업방 구성과 같음. 1280 프레임은 검사에서 뺌(`공통 4`) |
| 13 | 케이스 | 작업 기록 "설계" 절 "화면별 요건" 표의 케이스가 "요건 목록"에서 그 화면 줄의 케이스와 맞음. 화면마다 요소를 찾는 순서 · 변경 확인 · 화면 정보를 그 케이스의 흐름대로 했음. 컴포넌트 없이 그린 요소가 모두 "컴포넌트 없이 그린 요소" 표에 있고, 테스트로 그린 그림 · 완료되지 않은 그림에서 가져온 것이 없음 |
| 14 | 기존 원본의 바탕 · 틀 (케이스 3) | 기존 원본(AS-IS) 기획 프레임의 바탕 도형 · 영역 틀(예: 콘텐츠 영역 바탕, 검색 영역 바탕, 요약 줄 틀)이 그린 화면에 모두 같은 값(크기 · 색)으로 있음(`공통 3-3` "케이스 3" 표 ②) |
| 15 | 화면 MD 머리말 `figma` | 작업한 화면(CID)마다 화면 MD 머리말 `figma`에 작업방의 그 CID 섹션 링크가 있음(`공통 4` "화면 MD 머리말 `figma`") |
| 16 | 업데이트 메모 (케이스 3) | 옮긴 메모마다 기존 작업방 메모와 같이 글머리 기호(•)와 들여쓰기 단계가 있고, 메모 수 · 쌓인 순서가 같음 |
