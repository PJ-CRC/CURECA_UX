# 4. 수정 · 확인

> 초안 · v0.3

**목적:** 3단계 초안이 나온 뒤부터 완료 전까지 머무는 단계입니다. 사용자 확인 목록(질문 대기 · 변경 확인)의 답, 고객 UX 검토 의견, 고객 UI 검토에서 바뀐 것으로 화면을 고치고, UX 확정 뒤 언어셋을 정리해 UI팀에 넘길 것을 준비합니다. 더 들어온 요건 · 바뀐 요건 · 빠진 요건도 이 단계 안에서 처리하고, 앞 단계로 돌아가지 않습니다(`flow/README.md` "단계를 지나는 규칙" 3).

**목표:** 작업 기록 "단계" 표 4단계 줄에 UX 확정과 UI 확정(또는 해당 없음)을 기입하고, 아래 "마침 점검"을 통과해 5단계로 넘깁니다.

## 절차

| 순서 | 하는 일 | 요청자 확인 |
| --- | --- | --- |
| 1 | 사용자 확인 목록을 보여 주고 답을 받아 고침 | 받음 (사용자 확인 목록에 항목이 있을 때) |
| 2 | 고객 UX 검토 의견을 받아 고침 (검토마다 되풀이) | 의견을 받을 때마다. 고친 결과를 보여 줄 때 모아 둔 질문이 있으면 받음 |
| 3 | UX 확정을 기입함 | 사용자 확인 목록과 "의견" 절의 미해결 항목이 모두 풀리면 "최종으로 UX 확정을 하시겠습니까?"를 물음. 확정한다고 하면 "기계 검사를 한 번 더 검토할까요?"를 묻고, UI 작업 칸과 이번 작업의 Ver(한 번)을 함께 물음 |
| 4 | 언어셋을 정리하고 UI팀에 넘길 것을 보여 줌 | 모아 둔 질문이 있을 때만 받음 (보여 줄 때 함께) |
| 5 | 고객 UI 검토에서 바뀐 것을 UX에 맞추고 UI 확정을 기입함 | 요청자가 "UI 확정됐어" · "최종 확정됐어"라고 알림. 이 말이 5단계로 넘어가는 트리거 |
| 6 | 4단계를 정리하고 닫음 | 없음 (절차 4 · 5 끝에 이어 바로 함) |

- 절차 1번은 한 번 합니다. 절차 2번은 검토 의견이 올 때마다 되풀이합니다. 절차 3 ~ 5번은 UX 확정 → 언어셋 · UI팀에 넘김 → UI 확정 순서로 합니다.
- 기다리는 구간이 둘 있습니다. 고객 UX 검토를 기다릴 때(절차 1 · 2번 뒤)와, UI팀 작업 · 고객 UI 검토를 기다릴 때(절차 4번 뒤)입니다. UI팀의 작업과 UI 화면의 수정은 이 흐름에서 하지 않습니다. 기다리는 동안에는 작업을 쉬고, 작업 기록의 `이어서 작업할 곳:` 줄에서 이어 갑니다(`reference-rules/work-log.md` "끊긴 작업 이어 가기").
- 화면을 고치는 절차(1 · 2 · 5번)에서는 아래 "절차 공통: 화면 수정 규칙"을 따릅니다.
- 확인받는 것은 절차마다 다릅니다. 무엇을 보여 주고 묻는지는 그 절차의 순서 안에 적습니다.
- **기획 진행 표시는 정해진 때 Claude가 바꿉니다**(날짜 = 바꾼 날, `flow/3-design.md` 공통 4): 절차 1번 순서 5에서 `검토 중`, 절차 3번 순서 7에서 `검토 완료`. 케이스 3은 바꾸지 않습니다(3단계에서 기존 작업방 표시를 옮긴 값 그대로, `flow/3-design.md` 공통 4). 그 밖에 요청자가 "기획 진행 표시를 검토 중으로 변경해 줘"처럼 말하면 말한 상태로 바꿉니다.
- 진행 경로가 3단계를 지나가지 않는 요건(정책만 바뀜)은 화면이 없으므로 기계 검사 · 언어셋 · UI 확정이 "해당 없음"입니다. 그 요건의 정책 결정에 대한 의견만 절차 2번으로 받습니다. **[초안 2026-11-17, 다시 검토]** UX 확정은 이 요건에도 절차 3번의 물음("최종으로 UX 확정을 하시겠습니까?")으로 기입합니다. 절차 3번 가운데 화면에 딸린 순서(UI 작업 칸 · Ver · 업데이트 메모 · 화면 MD의 `basis`)는 이 요건에 "해당 없음"입니다.

### 절차 공통: 화면 수정 규칙 (절차 1 · 2 · 5번)

> 초안 (확정 전).

**수정 순서**

- 화면 MD를 먼저 고치고 Figma를 고칩니다(헌법 6조). 그리는 법은 그 줄의 케이스 흐름과 공통 규칙을 따릅니다(`flow/3-design.md`).
- 한쪽 화면을 고치면 짝 화면도 봅니다. 짝 화면을 고치지 않으면 요건 목록 비고에 근거를 기입합니다.
- 디스크립션에서 고치거나 더한 글자는 빨간색, 제거된 요소와 제거된 문구는 빨간 취소선으로 씁니다(케이스 1 · 3, `reference-rules/description.md` 7절 "바뀐 글 표시").
- **화면이 바뀐 곳은 모두 "변경 확인" 표에 있어야 합니다.** 작업 기록의 "변경 확인" 표(원본, 화면 MD에는 두지 않음)는 이 작업으로 화면에서 무엇이 바뀌었는지(요소)를 적는 목록이고, UX 확정 때 이 표로 업데이트 메모를 만듭니다(절차 3번).

  | 화면이 바뀐 까닭 | "변경 확인" 표에 적는 법 |
  | --- | --- |
  | 요건대로 고침 (3단계, 더해지거나 바뀐 요건) | 3단계에서 이미 줄이 있음. 4단계에서 더 고쳤으면 줄을 더함 |
  | 질문 대기의 답으로 화면이 바뀜 | 줄을 더함. 근거에 `Qn의 답`을 적음 |
  | 검토 의견으로 화면이 바뀜 | 줄을 더함. 근거에 "의견" 절의 번호를 적음 |

  - 요청자 · 고객의 답이나 의견대로 고친 곳은 이미 확인된 것이므로 변경 확인 표시(사용자 확인 라벨 · Figma의 사용자 확인 목록 항목)를 두지 않고, 표의 "확인한 날 · 답" 칸에 `맞음 (날짜)`을 바로 기입합니다.
  - **줄마다 "업데이트 메모" 칸에 `O` 또는 `-`를 적습니다.** 업데이트 메모는 개발사에 이 화면에서 무엇이 추가 · 수정 · 제거됐는지 알리는 요약이므로, 화면과 동작이 바뀐 것만 넣습니다.

    | 칸 | 어떤 변경인가 |
    | --- | --- |
    | `O` | 화면에 보이는 것이 바뀜(표기 · 화면 표기 글자 · 값 · 상태값), 동작 · 조건이 바뀜(정책 반영 · 알럿), 요소가 추가 · 제거됨 |
    | `-` | 디스크립션의 말투 · 용어 · 오타 정리, 번호 정리, 패널의 화면 정보(CID · 경로 · 화면 이름) 정리. 화면 MD "변경 이력"에만 남김 |

  - Claude가 근거를 찾아 기존 화면과 다르게 고친 곳에만 변경 확인 표시(사용자 확인 라벨 · Figma의 사용자 확인 목록 항목)를 두어 확인받습니다. 근거 없이 정해야 하는 곳에는 질문 대기를 둡니다(`reference-rules/description.md` 5절). 번호는 이 작업의 통번호를 이어 씁니다.
- 화면 표기 글자가 생기거나 · 바뀌거나 · 없어졌으면 화면 MD를 고칠 때 "화면 표기 글자" 표의 상태 칸도 함께 고칩니다(`templates/screen.md` "화면 표기 글자"). 번역은 여기서 하지 않고 절차 4번에서 합니다.

**기계 검사 시점**

고칠 때마다 하지 않습니다. 아래 때에만 합니다.

| 때 | 하는가 |
| --- | --- |
| 절차 1번에서 요청자가 답할 수 있는 질문 대기 · 변경 확인을 모두 반영함 | 묻지 않고 함 |
| 요청자가 UX 확정을 하기로 답함 (절차 3번 순서 2) | "기계 검사를 한 번 더 검토할까요?"라고 묻고, 검토한다고 하면 함 |
| 그 밖 (검토 사이, 고객 UI 검토에서 바뀐 것을 맞춘 뒤 등) | 요청자가 "기계 검사해 줘"라고 할 때만 함 |

**기계 검사 방법**

- 마지막 기계 검사 뒤로 고친 화면(화면 MD · Figma)과 그 짝 화면에 3단계 마침 점검의 기계 검사를 합니다(`flow/3-design.md` "마침 점검"). 고치지 않은 화면은 다시 검사하지 않습니다.
- 통과하지 못한 것 가운데 근거가 분명한 것은 바로 고치고 다시 검사합니다. 근거 없이 정해야 하는 것은 고치지 않고 질문 대기로 더합니다.
- 통과했는지와 바로 고친 것을 알립니다. 더한 질문 대기와 모아 둔 질문이 있을 때만 그 질문을 함께 묻습니다(`flow/README.md` "단계를 지나는 규칙" 9).
- 판단이 필요한 점검(정책 대조 · 장비 상태 · 권한 · 알럿 등)은 이 흐름에 넣지 않습니다.

### 1) 사용자 확인 목록을 보여 주고 답을 받아 고침

> 초안 (확정 전).

> **사용자 확인 목록:** 질문 대기(Q)와 변경 확인(C)을 합쳐 부르는 이름입니다(`reference-rules/description.md` 5절). 원본은 작업 기록의 "질문 대기" · "변경 확인" 표입니다(화면 MD에는 두지 않음). 3단계에서 만들어져 넘어오고, 4단계에서 항목이 더해집니다. 그 가운데 아직 해결되지 않은 항목을 **미해결 항목**이라고 부릅니다. 채팅에서는 "답해 주실 것"에 미해결 항목을 보여 주고, Figma에는 사용자 확인 라벨과 패널 오른쪽의 사용자 확인 목록으로 있습니다. Figma에서 하는 일을 적을 때는 "Figma의 사용자 확인 목록"이라고 씁니다.

**순서**

1. **작업 기록을 보고 3단계가 끝났는지 확인합니다.** 새 대화로 이어 가면 작업 기록을 처음부터 읽고, 같은 대화에서 3단계를 막 끝냈으면 다시 읽지 않습니다(`flow/README.md` "단계 전환", `reference-rules/work-log.md` "쓰는 법"). 작업 기록 "단계" 표에서 "3. 화면 설계" 줄의 "마침 점검" 칸을 봅니다.

   | "마침 점검" 칸 | 하는 일 |
   | --- | --- |
   | 기계 검사를 통과한 날이 적혀 있음 | 순서 2로 감 |
   | 비어 있음 | 4단계를 시작하지 않음. 요청자에게 "3단계가 아직 끝나지 않았습니다. 3단계를 마무리한 뒤 4단계를 진행하겠습니다."라고 알리고, 3단계를 어디서부터 이어 갈지 찾아(`reference-rules/work-log.md` "끊긴 작업 이어 가기") 남은 일을 마저 하고 3단계 마침 점검을 통과한 뒤 4단계를 시작함 |

2. **사용자 확인 목록을 한 번에 보여 줍니다.** 작업 기록 "질문 대기" · "변경 확인" 표를 `reference-rules/work-log.md` "요청자에게 보여 주는 법"의 "사용자 확인 목록을 보여 주는 모양"으로 보여 줍니다(3단계 보고에서는 보여 주지 않았으므로 여기서 처음 보여 줌). 하나도 없으면 묻지 않고 순서 5로 갑니다.

   | # | 언제 | 보여 주는 것 | 고르는 것 |
   | --- | --- | --- | --- |
   | 1 | 질문 대기가 있음 | 질문 대기 표를 번호(Q)마다 | 번호마다 답 / 고객에게 물음 |
   | 2 | 변경 확인이 있음 | 변경 확인 표를 번호(C)마다 | 번호마다 맞음 / 되돌림 |

3. **답을 받는 대로 고칩니다.**
   - 답은 한 번에 다 받아도 되고 일부만 받아도 됩니다. 요청자가 번호로 답하면("Q5 ID, C4 맞음") 그대로 반영합니다.
   - 받은 답부터 고치고("절차 공통: 화면 수정 규칙"의 "수정 순서"), 답이 없는 번호는 남은 목록으로 다시 보여 줍니다.
   - 답을 작업 기록 "요청자 확인" 표에 날짜 · `4단계` · 확인한 것 · 요청자 답으로 기입합니다.

   | 답 | 하는 일 |
   | --- | --- |
   | 질문 대기의 답 | 답대로 화면 MD → Figma를 고치고 사용자 확인 라벨의 그 ID와 Figma의 사용자 확인 목록에서 그 항목을 지움(`reference-rules/description.md` 5절 "해결 시 처리"). 화면 MD와 작업 기록 "질문 대기" 표의 "풀린 날 · 어떻게"를 기입. **답으로 화면이 바뀌었으면 "변경 확인" 표에 줄을 더함**("절차 공통: 화면 수정 규칙") |
   | 변경 확인 "맞음" | 사용자 확인 라벨의 그 ID와 Figma의 사용자 확인 목록에서 그 항목을 지우고 작업 기록 "변경 확인" 표의 "확인한 날 · 답"에 `맞음 (날짜)`을 기입. 줄은 표에 그대로 남음 |
   | 변경 확인 "되돌림" | 기존 화면대로 되돌리고 사용자 확인 라벨의 그 ID와 Figma의 사용자 확인 목록에서 그 항목을 지움. 작업 기록 표의 "확인한 날 · 답"에 `되돌림 (날짜)`를 기입. 화면이 바뀌지 않았으므로 업데이트 메모에 넣지 않음 |
   | 고객에게 물음 | 사용자 확인 라벨과 Figma의 사용자 확인 목록 항목을 남김. 논의 대상을 `논의 중`으로 두고(`reference-rules/discussions.md` 2절) "질문 대기" 표의 "논의 대상" 칸에 논의 대상 ID를 기입 |
   | 정책을 바꾸는 답 | 논의 대상에 결정 줄을 더하고 작업 기록 "이 작업의 결정" 표에 기입. 정책서에는 5단계에서 반영. 새 화면의 User Type · L-IOS Client Mode 답은 정책을 바꾸는 답으로 보지 않고 위 "질문 대기의 답"대로 화면만 고침 |

   "고객에게 물음"으로 넘긴 질문(요청자가 답할 수 없고 고객 · 개발사가 정할 것)의 답은 두 길 가운데 하나로 옵니다.

   | 길 | 하는 일 |
   | --- | --- |
   | 요청자가 고객에게 채팅으로 먼저 물어 답을 전함 | 답을 받는 대로 위 표대로 고침. 고객 UX 검토를 기다리지 않음 |
   | 고객 UX 검토에서 받음 | 사용자 확인 라벨과 Figma의 사용자 확인 목록 항목을 남긴 채 검토에 가고, 절차 2번에서 답을 받아 고침 |

4. **모두 반영하면 기계 검사를 합니다.** 사용자 확인 목록에 요청자가 답할 수 있는 미해결 항목이 하나도 남지 않았을 때 묻지 않고 합니다("고객에게 물음"으로 넘긴 항목은 남아 있어도 됨). 방법은 "절차 공통: 화면 수정 규칙"의 "기계 검사 방법"을 따릅니다. 고친 것이 없으면 하지 않고 3단계 마침 점검의 결과를 그대로 씁니다. 알릴 때 사용자 확인 목록과 "의견" 절에 미해결 항목이 하나도 없으면 절차 3번 "언제"의 물음을 함께 합니다.
5. **기획 진행 표시를 `검토 중`으로 바꿉니다.** 사용자 확인 목록에서 요청자가 답하는 항목을 모두 고쳤을 때 그 화면이 있는 페이지의 기획 진행 표시를 바꿉니다("고객에게 물음"으로 넘긴 항목은 남아 있어도 됨, 날짜 = 바꾼 날).
6. **`이어서 작업할 곳:` 줄을 고칩니다.** 기계 검사를 통과한 뒤 고칩니다(예: `4단계 · 사용자 확인 목록 반영함 · 기계 검사 통과, 질문 대기 Q3 (논의 중 DS-0012) · Q7 (논의 중 DS-0013) 남음`). 요청자가 검토 일정을 알려 줬으면 덧붙입니다(예: `… , 고객 UX 검토 11-20`).

### 2) 고객 UX 검토 의견을 받아 고침

> 초안 (확정 전).

요청자가 고객 UX 검토의 의견을 전할 때마다 합니다. 검토 → 고침 → 다시 검토를 UX 검토가 끝날 때까지 되풀이합니다. 검토 사이에 요청자가 주는 의견도 같은 순서로 받습니다.

**순서**

1. **의견을 기입합니다.** 받은 의견을 하나씩 작업 기록 "의견" 절에 적습니다(아래 "작업 기록에 쓰는 것"의 "의견 틀"). 출처가 회의면 회의록 ID를 함께 적습니다.
2. **의견마다 어떤 의견인지 보고 할 일을 정합니다.**

   | 어떤 의견인가 | 예 | 하는 일 |
   | --- | --- | --- |
   | 남아 있던 질문 대기 · 변경 확인에 대한 답 | "Q3은 ID로 해 주세요" | 답대로 화면을 고치고 그 번호의 사용자 확인 라벨 ID와 Figma의 사용자 확인 목록 항목을 지움. 답마다 하는 일은 절차 1번 순서 3 "답을 받는 대로 고칩니다"의 표와 같음 |
   | 요건은 그대로 두고, 그린 것을 고쳐 달라는 의견 | "Effect 항목을 Event Code 아래로 옮겨 주세요" | 의견대로 화면 MD를 먼저 고치고 Figma를 고침. 짝 화면도 함께 보고, 바뀐 곳은 "변경 확인" 표에 줄을 더함 (자세한 순서는 위 "절차 공통: 화면 수정 규칙"의 "수정 순서") |
   | 요건 목록에 없던 것을 더하거나, 있던 요건을 바꾸는 의견 | "내보낼 범위에 '선택한 항목만'을 더해 주세요" | 작업 기록 "요건 목록"에 `추가 · 변경 (날짜, 누가, 왜)`로 달고, 아래 "더해지거나 바뀐 요건"대로 한 뒤 고침 |
   | 있던 요건을 빼 달라는 의견 | "[Print] 버튼은 이번에 넣지 않습니다" | 그 줄의 요청 상태를 `제거 (날짜, 누가, 왜)`, 작업 대상을 `X`로 바꾸고, 이미 그린 것을 되돌림. 케이스 1 화면은 `CID-복제본`을 보고 되돌림 |
   | 화면이 아니라 정책을 정하거나 바꿔야 하는 의견 | "이 값의 기준은 정책으로 정해야 합니다" | 논의 대상에 올리거나 결정 줄을 더하고(`reference-rules/discussions.md`), 작업 기록 "이 작업의 결정" 표에 기입 |

   - 요청자가 반영하지 않기로 한 의견은 고치지 않고, "의견" 절의 처리에 `반영 안 함 (이유, 누가 정함)`을 기입합니다.
   - 어떤 의견인지 분명하지 않으면 그 의견의 처리를 비워 두고 작업 기록 "모아 둔 질문"에 적은 뒤, 순서 5에서 묻습니다(`flow/README.md` "단계를 지나는 규칙" 9).

3. **고칩니다.** 순서 2에서 정한 대로 화면 MD → Figma 순서로 고칩니다. 기계 검사는 여기서 하지 않습니다("절차 공통: 화면 수정 규칙"의 "기계 검사 시점").
4. **기록을 고칩니다.** "의견" 절의 처리 · 처리한 날을 기입하고, `이어서 작업할 곳:` 줄을 "의견" 절의 상태대로 고칩니다. 한 일과 남은 것만 사실대로 적고, 다음에 일어날 일(검토를 한 번 더 하는지 등)은 짐작해 적지 않습니다(`reference-rules/work-log.md` "쓰는 법").

   | "의견" 절의 상태 | `이어서 작업할 곳:` 줄 (예) |
   | --- | --- |
   | 미해결 항목이 남음 ("처리"가 비어 있음) | `4단계 · 검토 의견 반영 중, 의견 3 남음 (질문 대기 Q6 답 기다림)` |
   | 미해결 항목이 없음 (모든 항목에 "처리"가 기입됨) | `4단계 · 검토 의견 1 ~ 5 반영함` |
   | 요청자가 다음 검토 일정을 알려 줌 | 그 말을 덧붙임: `… , 고객 UX 검토 2차 (11-27)` |

5. **고친 결과를 보여 줍니다.** 의견마다 처리와 바뀐 곳(변경 확인 번호)을 보여 줍니다. 작업 기록 "모아 둔 질문"에 답이 비어 있는 줄이 있으면 "답해 주실 것"에 함께 묻고, 답을 받으면 그대로 고치고 "모아 둔 질문"의 답과 "의견" 절의 처리를 기입합니다(`flow/README.md` "단계를 지나는 규칙" 9). 사용자 확인 목록과 "의견" 절에 미해결 항목이 하나도 없으면 절차 3번 "언제"의 물음을 함께 합니다.

**더해지거나 바뀐 요건**

앞 단계로 돌아가지 않고, 그 요건 하나에 대해서만 1 · 2 · 3단계에서 하던 일을 아래 차례대로 합니다.

| # | 하는 일 | 따르는 곳 |
| --- | --- | --- |
| 1 | 대상 화면을 짚고 케이스를 붙임. 같은 것을 쓰는 다른 화면을 찾음 | `flow/1-requirements.md` 절차 2번 "요건을 뽑고 대상 화면을 짚음" |
| 2 | 새로 대상이 된 화면을 읽음 | `flow/1-requirements.md` 절차 3번 "대상 화면을 읽음" |
| 3 | 경로 분기 기준 · 문구 · UI 작업을 정해 "요건별 진행 경로"에 한 줄 더함 | `flow/1-requirements.md` 절차 4번 순서 6 |
| 4 | 강도대로 근거를 읽고 대조함. 읽은 자료 목록에 더함 | `flow/2-evidence.md` 절차 1 ~ 5번 |
| 5 | 화면을 그림 | `flow/3-design.md`의 그 케이스 흐름 |

- **위 표 1에서 찾은 화면은 요청자가 고치라고 한 것만 그립니다.** 고칠지 정해지지 않은 화면(짝 화면, 같은 메뉴에서 찾은 화면)은 작업 기록 "요건 목록"에 작업 대상 `미정`으로 올리고 "모아 둔 질문"에 적어 순서 5 "고친 결과를 보여 줍니다"에서 묻고, 다른 메뉴의 화면은 "영향 화면" 표에만 적습니다(`flow/1-requirements.md` 절차 2번 "요건을 뽑고 대상 화면을 짚음").
  - 예: 의견이 "TI-EVT-P의 [Export]를 [Download]로"이면 TI-EVT-P만 고칩니다. 짝 화면 LI-EVT-P에 같은 버튼이 있으면 순서 5에서 "함께 바꿀까요?"라고 묻고, 다른 메뉴의 화면에 같은 버튼이 있으면 "영향 화면" 표에 적어 둡니다.
- 1 · 2단계의 요청자 확인은 다시 받지 않습니다. 정한 것과 찾은 것은 순서 5에서 고친 결과와 함께 보여 주고, 모아 둔 질문만 묻습니다.

### 3) UX 확정을 기입함

> 초안 (확정 전).

**언제:** 사용자 확인 목록(질문 대기 · 변경 확인)과 "의견" 절의 미해결 항목이 모두 풀리면 Claude가 "사용자 확인 목록과 의견이 모두 풀렸습니다. 최종으로 UX 확정을 하시겠습니까?"라고 묻고, 요청자가 확정한다고 답했을 때만 이 절차를 합니다. 고친 것이 다 끝났다고 UX 확정이 된 것은 아니고, 고객 검토가 언제 끝날지도 미리 알 수 없으므로 묻지 않고 넘어가지 않습니다. 고객이 검토 전에 미리 확정했거나 고객 검토가 없는 요건도 같습니다(아래 "고객 검토가 없는 요건"). UX 확정은 사용자 확인 목록과 "의견" 절만 봅니다. 반영 대기 목록과는 상관없습니다.

- 묻는 때: 절차 1번 순서 4(기계 검사 결과를 알릴 때)와 절차 2번 순서 5(고친 결과를 보여 줄 때)에서 사용자 확인 목록과 "의견" 절에 미해결 항목이 하나도 없으면 함께 묻습니다.
- 답이 "아직"이면(검토가 더 남음 등) 기다립니다. 다음에 미해결 항목이 다시 모두 풀리면 다시 묻습니다.
- 요청자가 먼저 "UX 확정해 줘"라고 하면 순서 1부터 합니다.

**순서**

1. **미해결 항목이 없는지 확인합니다.** UX 확정은 사용자 확인 목록(질문 대기 · 변경 확인)과 "의견" 절에 미해결 항목이 하나도 없어야 기입합니다.

   | 묶음 | 보는 곳 | 미해결 항목 |
   | --- | --- | --- |
   | 사용자 확인 목록 | "질문 대기" 표 | "풀린 날 · 어떻게"가 비어 있는 항목. 논의 대상이 `논의 중`인 항목(고객에게 물음)도 미해결 항목 |
   | 사용자 확인 목록 | "변경 확인" 표 | "확인한 날 · 답"이 비어 있는 항목 |
   | 4단계에서 받은 의견 | "의견" 절 | "처리"가 비어 있는 항목. 처리가 논의 대상 ID인데 그 논의 대상이 `논의 중`인 항목도 미해결 항목 |

   | 결과 | 하는 일 |
   | --- | --- |
   | 미해결 항목이 없음 | 순서 2로 감 |
   | 미해결 항목이 있음 | UX 확정을 기입하지 않습니다. 미해결 항목을 번호(Q · C, 의견 번호)로 보여 주고 "아래 미해결 항목이 해결되어야 UX 확정을 기입할 수 있습니다"라고 알립니다. 요청자의 답을 받아 고친 뒤(절차 1번 순서 3, 절차 2번) 다시 확인합니다 |

2. **기계 검사를 한 번 더 검토할지 묻습니다.** 요청자가 확정한다고 답하면 "기계 검사를 한 번 더 검토할까요?"라고 묻고 고르게 합니다. 검토에서 고친 것이 얼마나 되는지는 요청자가 판단합니다. 절차 1번의 기계 검사 뒤로 고친 화면이 없으면 묻지 않고 순서 3으로 갑니다.

   | 답 | 하는 일 |
   | --- | --- |
   | 검토함 | 절차 1번의 기계 검사 뒤로 고친 화면에 기계 검사를 합니다("절차 공통: 화면 수정 규칙"의 "기계 검사 방법"). 질문 대기가 더해지면 UX 확정을 기입하지 않고 그 질문을 보여 줍니다(다 풀리면 위 "언제"의 물음부터 다시). 더해진 것이 없으면 순서 3으로 갑니다 |
   | 하지 않음 | 하지 않고 순서 3으로 갑니다 |

3. **UI 작업 칸과 이번 작업의 Ver을 한 번에 묻습니다.** 아래 둘을 "답해 주실 것" 하나로 묻습니다.
   - **UI 작업 칸:** 요건마다 실제로 고친 것을 보고 아래 표대로 UI 작업 칸의 값을 정해, 요건마다 값과 근거(바뀐 요소 · 바뀐 화면 표기 글자의 디스크립션 번호)를 보여 주고 확인받습니다. 1단계에서 이 칸에 적은 값은 화면을 그리기 전에 적어 둔 임시 값입니다.

     | 실제로 고친 것 | UI 작업 칸 |
     | --- | --- |
     | 화면의 배치 · 요소가 바뀜, 새 화면 | `대상` |
     | 화면 표기 글자가 생기거나 바뀌거나 없어짐(화면 MD "화면 표기 글자" 표의 상태 칸이 `신규` · `변경` · `제거`인 줄이 있음) | `대상` |
     | 디스크립션만 바뀜 | `대상 아님` |

     - 디자인 화면은 읽지 않으므로, 디자인 화면에서 그 글자를 쓰는 곳(우리 화면과 다르게 그린 케이스 등)은 보지 못했다는 것을 함께 알립니다.
   - **Ver:** 이 작업의 Ver을 한 번만 묻습니다("이번 작업의 Ver을 알려 주세요"). 이번 작업에서 고친 케이스 1 · 2 화면은 모두 같은 Ver으로 갑니다. 화면마다 묻지 않습니다. 케이스 3 화면은 묻지 않습니다(기존 화면의 Ver 그대로).
4. **답을 기입합니다.**
   - UI 작업 칸: 요청자가 확인한 값을 작업 기록 "요건별 진행 경로"의 UI 작업 칸에 확정 값으로 적습니다. 1단계의 임시 값과 달라졌으면 그 칸에 `바뀜 (날짜, 이유)`를 함께 적습니다. 요청자가 값을 바꾸면 바꾼 값과 이유를 기입합니다.
   - Ver: 이 작업의 케이스 1 · 2 화면마다 화면 MD 머리말 `version`에 적고 패널 화면 정보의 Ver에 옮깁니다(`reference-rules/description.md` 7절 "화면 정보에 적는 값").
5. **업데이트 메모를 만듭니다.** 작업 기록 "변경 확인" 표에서 "확인한 날 · 답"이 `맞음`이고 "업데이트 메모" 칸이 `O`인 줄을 "관련된 곳"의 화면(CID)마다 모아 패널 옆에 업데이트 메모를 만듭니다(`reference-rules/description.md` 5절 "업데이트 메모"). 이 줄들이 이 작업으로 화면과 동작이 바뀐 것 전부입니다(요건대로 고친 것, 질문 대기의 답으로 바뀐 것, 검토 의견으로 바뀐 것). `되돌림`인 줄과 `-`인 줄은 넣지 않습니다. 넣을 줄이 없으면 만들지 않습니다. 제목의 Ver은 순서 3에서 받은 이번 작업의 Ver입니다.
   - **케이스 3 화면:** 3단계에서 옮겨 둔 기존 작업방의 메모는 그대로 두고, 같은 줄(변경 확인 `맞음` · `O`)로 `재설계 후 변경 내역` 메모를 만듭니다. Ver을 묻지 않으므로 제목에 Ver을 쓰지 않습니다(`reference-rules/description.md` 5절 "업데이트 메모"의 "케이스 3").
6. **기입합니다.** 작업 기록 "단계" 표 4단계 줄의 "남긴 것"에 `UX 확정 (날짜)`를 적습니다. 작업 기록 머리말과 이 작업에서 고친 화면 MD 머리말에 화면 기준 `basis` · `basis_versions`를 적습니다(`reference-rules/work-log.md` "작업 기준").
7. **기획 진행 표시를 `검토 완료`로 바꿉니다.** 이 작업에서 그린 화면이 있는 페이지의 기획 진행 표시를 바꿉니다(날짜 = UX 확정 날짜).
8. **`이어서 작업할 곳:` 줄을 고칩니다.** `4단계 · UX 확정 기입함, 언어셋 정리할 차례`로 고치고 절차 4번으로 갑니다.

**고객 검토가 없는 요건**

- 요청 글 · 요청 자료에 고객 검토 없이 반영해 달라는 말이 있거나 고객이 미리 확정한 요건도 따로 넘기지 않고, 위 "언제"의 물음으로 똑같이 UX 확정을 받습니다.
- 고객 검토 없이 UX 확정을 기입할 때는 근거를 함께 적습니다: `UX 확정 (날짜) · 내부 검토 반영 (근거)`.

**UX 확정 뒤에 고칠 때**

- UX 확정 뒤에 들어온 의견은 절차 2번의 순서대로 고칩니다. 고객 UI 검토에서 바뀐 것은 절차 5번에서 맞춥니다.
- 들어온 의견은 미해결 항목이 됩니다. 고쳐서 사용자 확인 목록과 "의견" 절이 다시 모두 풀리면 위 "언제"의 물음("최종으로 UX 확정을 하시겠습니까?")을 다시 하고, 확정한다고 답하면 작업 기록 "단계" 표 4단계 줄의 UX 확정 날짜를 고쳐 적습니다. 고객 검토를 다시 받을지는 따로 묻지 않습니다(요청자가 "아직"이라고 답하면 기다림). Ver은 다시 묻지 않습니다(같은 작업이라 같은 Ver).
- 절차 4번에서 UI팀에 넘길 것을 이미 보여 줬으면, 다시 확정한 뒤 바뀐 화면만 `templates/ui-handover.md` 양식으로 채워 보여 줍니다. 케이스 3 화면은 바뀐 화면 표기 글자만 넣습니다.
- UX 확정 뒤에 확인된 변경은 그때 업데이트 메모에 더합니다.
- 정책 · 기준데이터를 다시 읽고 고친 화면은 그 화면 MD와 작업 기록 머리말의 `basis` · `basis_versions`를 고친 때로 다시 적습니다. 고객 UI 검토에서 바뀐 것을 UX에 맞춘 것(절차 5번)은 다시 적지 않습니다.
- UX 확정 뒤에는 디스크립션 번호를 바꾸지 않습니다. 더한 요소는 새 번호를 이어 붙입니다. 제거된 요소는 디스크립션의 블록을 지우지 않고 취소선을 긋고, 그 번호는 새 요소에 다시 쓰지 않습니다.
- 화면 표기 글자가 바뀌었으면 화면 MD "화면 표기 글자" 표의 상태 칸을 고치고("절차 공통: 화면 수정 규칙"), 절차 4번을 그 화면 표기 글자만 다시 해 작업 기록 "언어셋" 절의 줄을 고칩니다.

### 4) 언어셋을 정리하고 UI팀에 넘길 것을 보여 줌

> 초안 (확정 전, 2026-11-18 다시 씀. 테스트하며 다시 봄).

UX 확정을 기입한 뒤에 합니다. 화면 표기 글자가 확정된 뒤에 해야 같은 화면 표기 글자를 두 번 작업하지 않고, UI팀이 번역 길이를 보고 디자인할 수 있습니다.

이 절차에서는 언어셋 원본(`language-set/db/`)을 **읽기만** 합니다. 원본을 고치는 일(줄을 더하거나 지우거나 고침, 다른 화면이 그 글자를 쓰는지 보는 일)은 5단계 절차 2번 순서 5에서 합니다.

**대상**

이 작업에서 고친 화면의 화면 MD "화면 표기 글자" 표(`templates/screen.md` "화면 표기 글자")에서 아래 가운데 하나인 줄입니다. 케이스로 나누지 않습니다.

| 대상인 줄 | 어떤 글자인가 |
| --- | --- |
| 상태가 `신규` · `변경` · `제거` | 3단계와 이 단계에서 화면 MD를 고치며 표시해 둔 글자 |
| 상태가 `-`인데 Language ID가 빔 | 아직 언어셋과 맞춰 보지 않은 글자. 주로 케이스 3으로 작업방에 처음 옮긴 화면. 케이스 3 화면에서 언어셋 원본에 같은 글자가 없으면 작업 기록 "언어셋" 절 상태를 `추가 (언어셋에 없음)`으로 적음(화면 MD 상태는 `-` 그대로, UI팀에 넘길 것에 넣지 않음) |
| 상태가 `-`이고 Language ID가 있는데, 원본의 그 줄과 영어가 다르거나 그 줄의 CID 칸에 이 화면이 없음 | 화면을 고치며 상태를 표시하지 못한 글자. 원본과 대어 보아 잡음 |

- 3단계에서 작업 기록 "언어셋" 절에 적은 `언어셋에만 있음` 줄(케이스 3, `flow/3-design.md` 공통 1의 8)도 그대로 두고 함께 다룹니다. 번역 대상은 `- (언어셋에만 있음)`입니다.
- 대상인 줄이 없으면 작업 기록 "언어셋" 절에 `해당 없음 (화면 표기 글자가 바뀌지 않음)`을 기입하고 순서 6으로 갑니다.
- 디스크립션만 바뀐 것은 대상이 아닙니다(화면 표기 글자가 아님).

**순서**

1. **대상을 작업 기록 "언어셋" 절에 옮깁니다**(아래 "작업 기록에 쓰는 것"의 "언어셋 틀"). 상태는 화면 MD 그대로 적고(세 번째 대상은 `변경`으로), `변경`은 변경 전 → 변경 후를 적습니다. T-IOS · L-IOS에 같은 글자는 한 줄로 합칩니다.
2. **번역 대상을 가립니다.** `O` / `-`(이유). `제거` 줄과, 어느 언어에서도 영어 그대로 쓰는 말(고유명사 · 상태값 · 단위 등)은 `-`입니다.
3. **번역 대상이 `O`인 줄을 채웁니다.** 아래 "채우는 법"을 따릅니다. `변경` 줄은 변경 후 글자로 채웁니다.
4. **가장 긴 언어를 적습니다.** 채운 번역 가운데 글자 수(띄어쓰기 포함)가 가장 많은 언어를 "가장 긴 언어" 칸에 적습니다. UI팀이 이 길이를 보고 디자인합니다(헌법 8조).
5. **화면 MD의 Language ID · 가장 긴 언어 · 번역 글자 칸을 채웁니다.** Language ID는 순서 3에서 가져온 줄만 적습니다. 화면 MD에는 늘 메뉴 파일의 ID를 적고, 공통 파일의 ID(`LID-COM-…`)는 적지 않습니다(`language-set/README.md` "칸"). "가장 긴 언어 · 번역 글자" 칸에는 순서 4의 언어와 그 언어로 번역한 글자를 적습니다(예: `DE · (독일어로 번역한 글자)`, 번역 대상이 `-`인 줄은 비워 둠).
6. **UI팀에 넘길 것을 보여 줍니다.** `templates/ui-handover.md` 양식을 그 파일의 주석대로 채워 요청자에게 보여 줍니다(작업 범위 · 변경 정보 · 언어셋 · 새로 그린 요소 · 상태별 화면 · 알럿 · 토스트). 요청자가 복사해 UI팀에 넘깁니다. 작업 기록 "모아 둔 질문"에 답이 비어 있는 줄(비슷한 글자 등)이 있으면 함께 묻고, 답대로 "언어셋" 절을 고친 뒤 채웁니다(`flow/README.md` "단계를 지나는 규칙" 9).
   - **케이스 3 화면은 화면 표기 글자가 바뀐 것만 넣습니다.** 작업 기록 "언어셋" 절에 그 화면의 `신규` · `변경` · `제거` 줄이 있으면 그 줄만 "언어셋" 묶음에 넣고, 작업 범위에는 그 화면을 `다시 그리기 (글자만)`로 적습니다. 화면 · 변경 정보 · 새로 그린 요소 · 상태별 화면 · 알럿 · 토스트 묶음에는 넣지 않습니다.
   - 작업의 요건이 모두 케이스 3이고 바뀐 화면 표기 글자가 없으면 UI팀에 넘길 것을 만들지 않고, "단계" 표 4단계 줄의 "남긴 것"에 `UI 확정 해당 없음 (케이스 3, 바뀐 글자 없음)`을 적고 절차 6번으로 갑니다. 바뀐 글자가 있으면 넘길 것을 보여 주고, 다른 케이스와 같이 절차 5번에서 요청자가 UI 확정을 알릴 때 UI 확정을 기입합니다.
   - 모든 요건의 UI 작업 칸이 `대상 아님`이면 "단계" 표 4단계 줄의 "남긴 것"에 `UI 확정 해당 없음 (이유)`를 적고 절차 6번으로 갑니다. 바뀐 화면 표기 글자가 있으면 "언어셋" 절은 그래도 보여 줍니다.
7. **`이어서 작업할 곳:` 줄을 고칩니다.** `4단계 · UI팀에 넘길 것을 보여 줌 (날짜)`로 고칩니다.

**채우는 법**

| 법 | 언제 | 하는 일 |
| --- | --- | --- |
| 가져옴 | 언어셋 원본의 메뉴 파일에 같은 영어 글자가 있음 | 그 줄의 Language ID · 번역 · 검증 상태를 가져옴 |
| 가져옴 (공통) | 메뉴 파일에는 없고 공통 파일에만 있음 | 번역 · 검증 상태를 가져오고 "참조 시트"에 공통 ID를 적음. Language ID는 비움 |
| 번역함 | 원본에 없음 | Claude가 AI 번역을 붙이고 검증 상태 `AI 번역`. Language ID는 비움. 법인 검토를 받으면 `법인 검토 완료`가 됨(`language-set/README.md` "법인 검토 받기") |

- **같은 글자:** 영어가 완전히 같을 때만 가져옵니다. 대소문자 · 마침표 · 띄어쓰기만 다른 글자가 있으면 가져오지 않고 Language ID를 비워 둔 채 "모아 둔 질문"에 적어, 순서 6에서 "비슷한 글자가 있습니다(원본의 글자, Language ID). 같은 글자로 볼까요?"라고 묻습니다.
- **찾는 범위:** 상태가 `사용`인 줄만 봅니다(`삭제`인 줄은 보지 않음).
- **같은 글자가 여럿:** 이 화면(CID)의 줄 → 같은 메뉴의 줄 → 다른 메뉴의 줄 순서로, 그 안에서는 검증 상태가 `법인 검토 완료`인 줄을 먼저 고릅니다. 같은 글자인데 번역이 서로 다른 줄이 있으면 가져오지 않고 "모아 둔 질문"에 적어 순서 6에서 묻습니다.
- Language ID가 빈 줄은 5단계에서 원본에 반영할 때 만듭니다.

### 5) 고객 UI 검토에서 바뀐 것을 UX에 맞추고 UI 확정을 기입함

> 초안 (확정 전).

요청자가 "UI 확정됐어" · "최종 확정됐어"라고 알리면 합니다. 이 말이 4단계를 마치고 5단계로 넘어가는 트리거입니다(절차 6번). UI팀의 작업, 고객 UI 검토, UI 화면의 수정은 이 흐름 밖에서 진행됩니다. 여기서는 고객 UI 검토에서 바뀐 것을 UX 화면설계에 맞춰 둡니다.

**순서**

1. **바뀐 것을 받습니다.** 고객 UI 검토에서 화면 표기 글자 · 요소 · 화면이 바뀌었거나 더해졌는지를 요청자가 글로 알려 줍니다. 디자인 화면을 읽어 바뀐 곳을 찾지 않습니다. 바뀐 것이 없으면 순서 3으로 갑니다.
2. **UX에 맞춥니다.**
   - 받은 것을 하나씩 작업 기록 "의견" 절에 출처 `고객 UI 검토`로 기입합니다.
   - 화면 MD를 먼저 고치고 Figma를 고칩니다. 짝 화면도 함께 보고, 바뀐 곳은 "변경 확인" 표에 줄을 더합니다("절차 공통: 화면 수정 규칙"의 "수정 순서").
   - 화면 표기 글자가 바뀌었으면 절차 4번을 그 화면 표기 글자만 다시 해 작업 기록 "언어셋" 절의 줄을 고칩니다.
   - 화면이 하는 일이 바뀌는 수정이면 절차 3번 "UX 확정 뒤에 고칠 때"를 따릅니다.
3. **UI 확정을 기입합니다.** 작업 기록 "단계" 표 4단계 줄의 "남긴 것"에 `UI 확정 (날짜)`를 적고 절차 6번으로 갑니다.

### 6) 4단계를 정리하고 닫음

> 초안 (확정 전).

확인받는 절차가 아니라 4단계를 닫는 정리입니다. 4단계가 끝나는 길 셋이 모두 여기로 옵니다: UI 확정(절차 5번), UI 작업이 없음(절차 4번을 마침), 요청 전체를 반영하지 않기로 함. 같은 정리를 길마다 두 번 쓰지 않으려고 한 곳에 모았습니다.

**순서**

1. **마침 점검을 합니다**(아래 "마침 점검"). 질문 대기 · 변경 확인 · 의견 · 모아 둔 질문에 풀리지 않은 항목이 하나도 없어야 합니다. 보통은 UX 확정 때 모두 풀려 있으므로 묻지 않고 지나갑니다. 풀리지 않은 항목이 남아 있으면(UX 확정 뒤 들어온 의견 등) 5단계로 가지 않고, 그 항목을 번호로 보여 주고 답을 받아 고친 뒤 다시 점검합니다. 그 밖에 통과하지 못한 것도 이 단계 안에서 풉니다.
2. **케이스 1의 `CID-복제본`을 지웁니다**(T · L, `flow/3-design.md` 케이스 1 흐름 1-4). 요청을 반영하지 않기로 했으면 원본을 복제본대로 되돌린 뒤 지웁니다.
3. **기입하고 5단계로 넘어갑니다.** 작업 기록 "단계" 표 4단계 줄의 "끝낸 날"과 "마침 점검" 칸에 `통과 (날짜)`를 적고, `이어서 작업할 곳:` 줄을 `5단계 · 완료`로 고칩니다. 넘어갈지 묻지 않고 5단계 절차 1번을 시작합니다. UI 확정을 알린 말이 트리거이고, UI 작업이 없으면(`UI 확정 해당 없음`) 절차 4번을 마친 것이 트리거입니다(`flow/README.md` "단계 전환").

## 마침 점검

5단계로 넘어가기 전에 모두 통과해야 합니다(절차 6번 순서 1).

- "단계" 표 4단계 줄 "남긴 것"에 UX 확정 날짜가 있음(내부 검토 반영이면 근거가 함께 있음). 작업 기록 머리말과 고친 화면 MD 머리말에 화면 기준 `basis` · `basis_versions`가 있음
- "남긴 것"에 UI 확정 날짜 또는 `UI 확정 해당 없음 (이유)`가 있음
- "의견" 절의 항목마다 처리와 처리한 날이 있음
- 사용자 확인 목록(질문 대기 · 변경 확인), "의견", "모아 둔 질문"에 미해결 항목이 없음
- "요건 목록"에서 요청 상태가 `추가` · `변경`인 줄마다 "요건별 진행 경로"에 줄이 있음
- "언어셋" 절에 바뀐 화면 표기 글자가 기입돼 있거나 `해당 없음 (화면 표기 글자가 바뀌지 않음)`이 있음. 신규 · 변경 줄에 번역과 "가장 긴 언어"가 채워져 있음(번역 대상이 아닌 줄은 `-`)
- 절차 1번의 기계 검사를 통과함. UX 확정 때나 요청을 받아 기계 검사를 했으면 그것도 통과함("절차 공통: 화면 수정 규칙"의 "기계 검사 시점")
- 요청을 반영하지 않기로 했으면 위 대신: 원본을 되돌렸음, 반영하지 않은 이유가 "의견" 절 또는 "요청자 확인" 표에 있음
