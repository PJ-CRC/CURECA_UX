# 4. 수정 · 확인

> 초안 · v0.1 (커밋 전)

3단계 초안이 나온 뒤부터 완료 전까지 머무는 단계입니다. 3단계에서 넘어온 사용자 확인 목록(질문 대기 · 변경 확인)의 답을 받아 고치고, 고객 UX 리뷰 의견을 받아 고치고, UX 확정 뒤 언어셋을 정리해 UI팀에 넘길 것을 준비하고, UI 리뷰에서 바뀐 것을 UX에 맞춥니다. 더 들어온 요건 · 바뀐 요건 · 빠진 요건도 이 단계 안에서 처리하고, 앞 단계로 돌아가지 않습니다(`flow/README.md` "단계를 지나는 규칙" 3). UX 확정 · UI 확정은 이 단계 안의 날짜로 기입합니다.

## 절차

| 순서 | 하는 일 | 요청자 확인 |
| --- | --- | --- |
| 1 | 사용자 확인 목록을 보여 주고 답을 받아 고침 | 받음 (사용자 확인 목록에 항목이 있을 때) |
| 2 | 고객 UX 리뷰 의견을 받아 고침 (리뷰마다 되풀이) | 의견을 받을 때마다 |
| 3 | UX 확정을 기입함 | 요청자가 알림. UI 작업 칸을 확인받고, 화면마다 Ver을 물음 |
| 4 | 언어셋을 정리하고 UI팀에 넘길 것을 보여 줌 | 없음 |
| 5 | UI 리뷰에서 바뀐 것을 UX에 맞추고 UI 확정을 기입함 | 요청자가 알림 |
| 6 | 단계를 끝냄 | 없음 |

- 절차 1번은 한 번 합니다. 절차 2번은 리뷰 의견이 올 때마다 되풀이합니다. 절차 3 ~ 5번은 UX 확정 → 언어셋 · UI팀에 넘김 → UI 확정 순서로 합니다.
- 기다리는 구간이 둘 있습니다. 고객 UX 리뷰를 기다릴 때(절차 1 · 2번 뒤)와, UI팀 작업 · 고객 UI 리뷰를 기다릴 때(절차 4번 뒤)입니다. UI팀의 작업과 UI 화면의 수정은 이 흐름에서 하지 않습니다. 기다리는 동안에는 작업을 쉬고, 작업 기록의 `이어서 작업할 곳:` 줄에서 이어 갑니다(`reference-rules/work-log.md` "끊긴 작업 이어 가기").
- 화면을 고치는 절차(1 · 2 · 5번)에서는 아래 "화면 수정 규칙"을 따릅니다.
- **기획 진행 표시는 요청받았을 때만 바꿉니다.** 답을 반영했거나 UX 확정을 기입했다고 해서 스스로 바꾸지 않습니다. 요청자가 "기획 진행 표시를 컨펌 중으로 변경해 줘"처럼 말하면 기획 진행 표시를 말한 상태로 바꿉니다(날짜 = 바꾼 날, `flow/3-design.md` 공통 4).
- 진행 경로가 3단계를 지나가지 않는 요건(정책만 바뀜)은 화면이 없으므로 기계 검사 · 언어셋 · UI 확정이 "해당 없음"입니다. 그 요건의 정책 결정에 대한 의견만 절차 2번으로 받습니다. **[초안 2026-11-17, 다시 검토]** UX 확정은 이 요건에도 기입합니다: 고객 UX 리뷰에서 그 요건의 결정을 확인받은 날, 고객 컨펌이 필요 없으면 `고객 컨펌 없음 (근거)`("고객 컨펌이 필요 없는 요건"). 절차 3번 "UX 확정을 기입함" 가운데 화면에 딸린 순서(UI 작업 칸 · Ver · 업데이트 메모 · 화면 MD의 `basis`)는 이 요건에 "해당 없음"입니다.

### 화면 수정 규칙 (절차 1 · 2 · 5번 공통)

> 초안 (확정 전).

**수정 순서**

- 화면 MD를 먼저 고치고 Figma를 고칩니다(헌법 6조). 그리는 법은 그 줄의 케이스 흐름과 공통 규칙을 따릅니다(`flow/3-design.md`).
- 한쪽 화면을 고치면 짝 화면도 봅니다. 짝 화면을 고치지 않으면 요건 목록 비고에 근거를 기입합니다.
- **화면이 바뀐 곳은 모두 "변경 확인" 표에 있어야 합니다.** 화면 MD(원본)와 작업 기록(작업 단위로 모은 것)의 "변경 확인" 표는 이 작업으로 화면에서 무엇이 바뀌었는지(요소)를 적는 목록이고, UX 확정 때 이 표로 업데이트 메모를 만듭니다(절차 3번).

  | 화면이 바뀐 까닭 | "변경 확인" 표에 적는 법 |
  | --- | --- |
  | 요건대로 고침 (3단계, 더해지거나 바뀐 요건) | 3단계에서 이미 줄이 있음. 4단계에서 더 고쳤으면 줄을 더함 |
  | 질문 대기의 답으로 화면이 바뀜 | 줄을 더함. 근거에 `Qn의 답`을 적음 |
  | 리뷰 의견으로 화면이 바뀜 | 줄을 더함. 근거에 "의견" 절의 번호를 적음 |

  - 요청자 · 고객의 답이나 의견대로 고친 곳은 이미 확인된 것이므로 변경 확인 표시(화면 라벨 · Figma의 사용자 확인 목록 항목)를 두지 않고, 표의 "확인한 날 · 답" 칸에 `맞음 (날짜)`을 바로 기입합니다.
  - **줄마다 "업데이트 메모" 칸에 `O` 또는 `-`를 적습니다.** 업데이트 메모는 개발사에 이 화면에서 무엇이 추가 · 수정 · 제거됐는지 알리는 요약이므로, 화면과 동작이 바뀐 것만 넣습니다.

    | 칸 | 어떤 변경인가 |
    | --- | --- |
    | `O` | 화면에 보이는 것이 바뀜(표기 · 화면 표기 글자 · 값 · 상태값), 동작 · 조건이 바뀜(정책 반영 · 알럿), 요소가 추가 · 제거됨 |
    | `-` | 디스크립션의 말투 · 용어 · 오타 정리, 번호 정리, 패널의 화면 정보(CID · 경로 · 화면 이름) 정리. 화면 MD "변경 이력"에만 남김 |

  - Claude가 근거를 찾아 기존 화면과 다르게 고친 곳에만 변경 확인 표시(화면 라벨 · Figma의 사용자 확인 목록 항목)를 두어 확인받습니다. 근거 없이 정해야 하는 곳에는 질문 대기를 둡니다(`reference-rules/description.md` 5절). 번호는 이 작업의 통번호를 이어 씁니다.
- 화면 표기 글자가 생기거나 · 바뀌거나 · 없어졌으면 화면 MD를 고칠 때 "화면 표기 글자" 표의 상태 칸도 함께 고칩니다(`templates/screen.md` "화면 표기 글자"). 번역은 여기서 하지 않고 절차 4번에서 합니다.

**기계 검사 시점**

고칠 때마다 하지 않습니다. 아래 때에만 합니다.

| 때 | 하는가 |
| --- | --- |
| 절차 1번에서 요청자가 답할 수 있는 질문 대기 · 변경 확인을 모두 반영함 | 묻지 않고 함 |
| 요청자가 "UX 확정됐어"라고 알림 (절차 3번) | "기계 검사를 한 번 더 진행할까요?"라고 묻고, 한다고 하면 함 |
| 그 밖 (리뷰 사이, UI 리뷰에서 바뀐 것을 맞춘 뒤 등) | 요청자가 "기계 검사해 줘"라고 할 때만 함 |

**기계 검사 방법**

- 마지막 기계 검사 뒤로 고친 화면(화면 MD · Figma)과 그 짝 화면에 3단계 끝 관문의 기계 검사를 합니다(`flow/3-design.md` "끝 관문"). 고치지 않은 화면은 다시 검사하지 않습니다.
- 통과하지 못한 것 가운데 근거가 분명한 것은 바로 고치고 다시 검사합니다. 근거 없이 정해야 하는 것은 고치지 않고 질문 대기로 더합니다.
- 통과했는지와 바로 고친 것을 알립니다. 더한 질문 대기가 있을 때만 그 질문을 함께 묻습니다.
- 판단이 필요한 점검(정책 대조 · 장비 상태 · 권한 · 알럿 등)은 이 흐름에 넣지 않습니다.

### 1) 사용자 확인 목록을 보여 주고 답을 받아 고침

> 초안 (확정 전).

> **사용자 확인 목록:** 질문 대기(Q)와 변경 확인(C)을 합쳐 부르는 이름입니다(`reference-rules/description.md` 5절). 원본은 화면 MD · 작업 기록의 "질문 대기" · "변경 확인" 표입니다. 3단계에서 만들어져 넘어오고, 4단계에서 항목이 더해집니다. 그 가운데 아직 해결되지 않은 항목을 **미해결 항목**이라고 부릅니다. 채팅에서는 "답해 주실 것"에 미해결 항목을 보여 주고, Figma에는 화면 라벨과 패널 오른쪽의 사용자 확인 목록으로 있습니다. Figma에서 하는 일을 적을 때는 "Figma의 사용자 확인 목록"이라고 씁니다.

**순서**

| # | 하는 일 |
| --- | --- |
| 1 | 작업 기록을 처음부터 다시 읽고, 3단계가 끝났는지 확인함 |
| 2 | 사용자 확인 목록(질문 대기 · 변경 확인)을 한 번에 보여 줌 |
| 3 | 답을 받는 대로 고침 |
| 4 | 요청자가 답할 수 있는 것을 모두 반영하면 기계 검사를 함 |
| 5 | `이어서 작업할 곳:` 줄을 고침 |

**1. 작업 기록을 처음부터 다시 읽고, 3단계가 끝났는지 확인합니다** (`reference-rules/work-log.md` "쓰는 법")

- **보는 곳:** 작업 기록 "단계" 표에서 "3. 화면 설계" 줄의 "관문" 칸.

| 관문 칸 | 하는 일 |
| --- | --- |
| 기계 검사를 통과한 날이 적혀 있음 | 2로 감 |
| 비어 있음 | 4단계를 시작하지 않고, 아래 "3단계가 끝나지 않았을 때"대로 함 |

3단계가 끝나지 않았을 때:

1. 요청자에게 알립니다: "3단계가 아직 끝나지 않았습니다. 3단계를 마무리한 뒤 4단계를 진행하겠습니다."
2. 3단계를 어디서부터 이어 갈지 찾습니다(`reference-rules/work-log.md` "끊긴 작업 이어 가기").
3. 3단계의 남은 일을 마저 하고 끝 관문을 통과한 뒤 4단계를 시작합니다.

**2. 사용자 확인 목록을 한 번에 보여 줍니다**

작업 기록 "질문 대기" · "변경 확인" 표를 `reference-rules/work-log.md` "요청자에게 보여 주는 법"의 모양으로 보여 줍니다(3단계 보고의 "답해 주실 것" 목록 그대로). 하나도 없으면 묻지 않고 5로 갑니다.

| # | 언제 | 보여 주는 것 | 고르는 것 |
| --- | --- | --- | --- |
| 1 | 질문 대기가 있음 | 질문 대기 표를 번호(Q)마다 | 번호마다 답 / 고객에게 물음 |
| 2 | 변경 확인이 있음 | 변경 확인 표를 번호(C)마다 | 번호마다 맞음 / 되돌림 |
| 3 | 새 화면(케이스 2)의 User Type · L-IOS Client Mode가 질문 대기로 남아 있음 | "새 화면 ○○의 User Type · L-IOS Client Mode는 고객 리뷰에서 받을까요?" | 고객 리뷰에서 받음 / 지금 답함 |

**3. 답을 받는 대로 고칩니다**

- 답은 한 번에 다 받아도 되고 일부만 받아도 됩니다. 요청자가 번호로 답하면("Q5 ID, C4 맞음") 그대로 반영합니다.
- 받은 답부터 고치고("화면 수정 규칙"의 "수정 순서"), 답이 없는 번호는 남은 목록으로 다시 보여 줍니다.
- 답을 작업 기록 "요청자 확인" 표에 날짜 · `4단계` · 확인한 것 · 요청자 답으로 기입합니다.

| 답 | 하는 일 |
| --- | --- |
| 질문 대기의 답 | 답대로 화면 MD → Figma를 고치고 화면 라벨의 그 ID와 Figma의 사용자 확인 목록에서 그 항목을 지움(`reference-rules/description.md` 5절 "해결 시 처리"). 화면 MD와 작업 기록 "질문 대기" 표의 "풀린 날 · 어떻게"를 기입. **답으로 화면이 바뀌었으면 "변경 확인" 표에 줄을 더함**("화면 수정 규칙") |
| 변경 확인 "맞음" | 화면 라벨의 그 ID와 Figma의 사용자 확인 목록에서 그 항목을 지우고 화면 MD와 작업 기록 "변경 확인" 표의 "확인한 날 · 답"에 `맞음 (날짜)`을 기입. 줄은 표에 그대로 남음 |
| 변경 확인 "되돌림" | 기존 화면대로 되돌리고 화면 라벨의 그 ID와 Figma의 사용자 확인 목록에서 그 항목을 지움. 화면 MD와 작업 기록 표의 "확인한 날 · 답"에 `되돌림 (날짜)`를 기입. 화면이 바뀌지 않았으므로 업데이트 메모에 넣지 않음 |
| 고객에게 물음 | 화면 라벨과 Figma의 사용자 확인 목록 항목을 남김. 논의 대상을 `논의 중`으로 두고(`reference-rules/discussions.md` 2절) "질문 대기" 표의 "논의 대상" 칸에 논의 대상 ID를 기입 |
| 정책을 바꾸는 답 | 논의 대상에 결정 줄을 더하고 작업 기록 "이 작업의 결정" 표에 기입. 정책서에는 5단계에서 반영. **[초안 2026-11-17, 다시 검토]** 새 화면의 User Type · L-IOS Client Mode 답은 질문 대기의 답이면서 정책을 바꾸는 답입니다. 질문 대기의 답대로 화면을 고치고, 함께 논의 대상에 결정 줄을 더하고 "이 작업의 결정" 표에 기입합니다. 바뀌는 곳(`policy/client-mode-matrix.csv`, `policy/permission-matrix.csv`, 새 메뉴면 Common UX COMM-3-a "모드별 LNB")은 5단계에서 반영합니다 |

"고객에게 물음"으로 넘긴 질문(요청자가 답할 수 없고 고객 · 개발사가 정할 것)의 답은 두 길 가운데 하나로 옵니다.

| 길 | 하는 일 |
| --- | --- |
| 요청자가 고객에게 채팅으로 먼저 물어 답을 전함 | 답을 받는 대로 위 표대로 고침. 고객 UX 리뷰를 기다리지 않음 |
| 고객 UX 리뷰에서 받음 | 화면 라벨과 Figma의 사용자 확인 목록 항목을 남긴 채 리뷰에 가고, 절차 2번에서 답을 받아 고침 |

**4. 모두 반영하면 기계 검사를 합니다**

- **시점:** 사용자 확인 목록에 요청자가 답할 수 있는 미해결 항목이 하나도 남지 않았을 때입니다("고객에게 물음"으로 넘긴 항목은 남아 있어도 됨). 묻지 않고 합니다.
- 방법은 "화면 수정 규칙"의 "기계 검사 방법"을 따릅니다. 고친 것이 없으면 하지 않고 3단계 끝 관문의 결과를 그대로 씁니다.

**5. `이어서 작업할 곳:` 줄을 고칩니다**

- 기계 검사를 통과한 뒤 `이어서 작업할 곳:` 줄을 고칩니다(예: `4단계 · 사용자 확인 목록 반영함 · 기계 검사 통과, 질문 대기 Q3 (논의 중 DS-0012) · Q7 (논의 중 DS-0013) 남음`). 요청자가 리뷰 일정을 알려 줬으면 덧붙입니다(예: `… , 고객 UX 리뷰 11-20`).

### 2) 고객 UX 리뷰 의견을 받아 고침

> 초안 (확정 전).

요청자가 고객 UX 리뷰의 의견을 전할 때마다 합니다. 리뷰 → 고침 → 다시 리뷰를 UX 리뷰가 끝날 때까지 되풀이합니다. 리뷰 사이에 요청자가 주는 의견도 같은 순서로 받습니다.

**순서**

1. **의견을 기입합니다.** 받은 의견을 하나씩 작업 기록 "의견" 절에 적습니다(아래 틀). 출처가 회의면 회의록 ID를 함께 적습니다.
2. **의견마다 어떤 의견인지 보고 할 일을 정합니다.**

   | 어떤 의견인가 | 예 | 하는 일 |
   | --- | --- | --- |
   | 남아 있던 질문 대기 · 변경 확인에 대한 답 | "Q3은 ID로 해 주세요" | 답대로 화면을 고치고 그 번호의 화면 라벨 ID와 Figma의 사용자 확인 목록 항목을 지움. 답마다 하는 일은 절차 1번 순서 3 "답을 받는 대로 고칩니다"의 표와 같음 |
   | 요건은 그대로 두고, 그린 것을 고쳐 달라는 의견 | "Effect 항목을 Event Code 아래로 옮겨 주세요" | 의견대로 화면 MD를 먼저 고치고 Figma를 고침. 짝 화면도 함께 보고, 바뀐 곳은 "변경 확인" 표에 줄을 더함 (자세한 순서는 위 "화면 수정 규칙"의 "수정 순서") |
   | 요건 목록에 없던 것을 더하거나, 있던 요건을 바꾸는 의견 | "내보낼 범위에 '선택한 항목만'을 더해 주세요" | 작업 기록 "요건 목록"에 `추가 · 변경 (날짜, 누가, 왜)`로 달고, 아래 "더해지거나 바뀐 요건"대로 한 뒤 고침 |
   | 있던 요건을 빼 달라는 의견 | "[Print] 버튼은 이번에 넣지 않습니다" | 그 줄의 요청 상태를 `제거 (날짜, 누가, 왜)`, 작업 대상을 `X`로 바꾸고, 이미 그린 것을 되돌림. 케이스 1 화면은 `CID-복제본`을 보고 되돌림 |
   | 화면이 아니라 정책을 정하거나 바꿔야 하는 의견 | "이 값의 기준은 정책으로 정해야 합니다" | 논의 대상에 올리거나 결정 줄을 더하고(`reference-rules/discussions.md`), 작업 기록 "이 작업의 결정" 표에 기입 |

   - 요청자가 반영하지 않기로 한 의견은 고치지 않고, "의견" 절의 처리에 `반영 안 함 (이유, 누가 정함)`을 기입합니다.
   - 어떤 의견인지 분명하지 않으면 요청자에게 묻습니다.

3. **고칩니다.** 순서 2에서 정한 대로 화면 MD → Figma 순서로 고칩니다. 기계 검사는 여기서 하지 않습니다(위 "화면 수정 규칙"의 "기계 검사 시점").
4. **기록을 고칩니다.** "의견" 절의 처리 · 처리한 날을 기입하고, `이어서 작업할 곳:` 줄을 "의견" 절의 상태대로 고칩니다. 한 일과 남은 것만 사실대로 적고, 다음에 일어날 일(리뷰를 한 번 더 하는지 등)은 짐작해 적지 않습니다(`reference-rules/work-log.md` "쓰는 법").

   | "의견" 절의 상태 | `이어서 작업할 곳:` 줄 (예) |
   | --- | --- |
   | 미해결 항목이 남음 ("처리"가 비어 있음) | `4단계 · 리뷰 의견 반영 중, 의견 3 남음 (질문 대기 Q6 답 기다림)` |
   | 미해결 항목이 없음 (모든 항목에 "처리"가 기입됨) | `4단계 · 리뷰 의견 1 ~ 5 반영함` |
   | 요청자가 다음 리뷰 일정을 알려 줌 | 그 말을 덧붙임: `… , 고객 UX 리뷰 2차 (11-27)` |

**더해지거나 바뀐 요건**

앞 단계로 돌아가지 않고, 그 요건 하나에 대해서만 1 · 2 · 3단계에서 하던 일을 아래 순서대로 합니다.

| 순서 | 하는 일 | 따르는 곳 |
| --- | --- | --- |
| 1 | 대상 화면을 짚고 케이스를 붙임. 같은 것을 쓰는 다른 화면을 찾음 | `flow/1-requirements.md` 절차 2번 "요건을 뽑고 대상 화면을 짚음" |
| 2 | 새로 대상이 된 화면을 읽음 | `flow/1-requirements.md` 절차 3번 "대상 화면을 읽음" |
| 3 | 경로 분기 기준 · 문구 · UI 작업을 정해 "요건별 진행 경로"에 한 줄 더함 | `flow/1-requirements.md` 절차 4번 순서 6 |
| 4 | 강도대로 근거를 읽고 대조함. 읽은 자료 목록에 더함 | `flow/2-evidence.md` 절차 1 ~ 5번 |
| 5 | 화면을 그림 | `flow/3-design.md`의 그 케이스 흐름 |

- **순서 1에서 찾은 화면은 요청자가 고치라고 한 것만 그립니다.** 고칠지 정해지지 않은 화면(짝 화면, 같은 메뉴에서 찾은 화면)은 작업 기록 "요건 목록"에 작업 대상 `미정`으로 올려 요청자에게 묻고, 다른 메뉴의 화면은 "영향 화면" 표에만 적습니다(`flow/1-requirements.md` 절차 2번 "요건을 뽑고 대상 화면을 짚음").
  - 예: 의견이 "TI-EVT-P의 [Export]를 [Download]로"이면 TI-EVT-P만 고칩니다. 짝 화면 LI-EVT-P에 같은 버튼이 있으면 "함께 바꿀까요?"라고 묻고, 다른 메뉴의 화면에 같은 버튼이 있으면 "영향 화면" 표에 적어 둡니다.
- 1 · 2단계의 요청자 확인은 다시 받지 않습니다. 정한 것과 찾은 것을 고친 결과와 함께 보여 주고, 물을 것만 묻습니다.

**의견 틀** (작업 기록 "의견" 절)

```markdown
## 의견

| 번호 | 받은 날 | 출처 (요청자 · 고객 UX 리뷰 · 고객 UI 리뷰) | 의견 | 관련된 곳 (CID · 디스크립션 번호) | 처리 | 처리한 날 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 2026-11-18 | 요청자 | Effect 항목을 Event Code 아래로 | TI-EVT-01-P #2-3 | 고침 (C7) | 2026-11-18 |
| 2 | 2026-11-18 | 요청자 | [Download] 범위 선택을 취소할 때 묻는 컨펌이 없음 | TI-EVT-P #1-4 | 질문 대기 Q6 | 2026-11-18 |
| 3 | 2026-11-20 | 고객 UX 리뷰 (MT-20261120-01) | 내보낼 범위에 "선택한 항목만"을 더함 | TI-EVT-02-P | 요건 5 추가 (C8) | 2026-11-21 |
```

- 처리에는 `고침` · `요건 N 추가 · 변경 · 제거` · `질문 대기 Qn` · `논의 대상 ID` · `반영 안 함 (이유, 누가 정함)` 가운데 하나를 기입합니다.
- 화면을 고쳤으면 "변경 확인" 표에 더한 줄의 번호를 괄호로 함께 적습니다(예: `고침 (C7)`). 의견대로 고친 것은 이미 확인된 것이라 변경 확인 표시를 다시 두지 않으므로, `변경 확인 Cn`을 처리 값으로 따로 쓰지 않습니다("화면 수정 규칙"의 "수정 순서").

### 3) UX 확정을 기입함

> 초안 (확정 전). ※가 붙은 곳은 "※ 정할 것"의 안을 넣어 둔 것입니다.

요청자가 "UX 확정됐어"(고객 UX 리뷰가 끝남)라고 알리면 합니다.

1. **미해결 항목이 없는지 확인합니다.** UX 확정은 미해결 항목이 하나도 없어야 기입합니다. 미해결 항목은 사용자 확인 목록과 "의견" 절에서 아직 해결되지 않은 항목입니다.

   | 묶음 | 보는 곳 | 미해결 항목 |
   | --- | --- | --- |
   | 사용자 확인 목록 | "질문 대기" 표 | "풀린 날 · 어떻게"가 비어 있는 항목. 논의 대상이 `논의 중`인 항목(고객에게 물음)도 미해결 항목 |
   | 사용자 확인 목록 | "변경 확인" 표 | "확인한 날 · 답"이 비어 있는 항목 |
   | 4단계에서 받은 의견 | "의견" 절 | "처리"가 비어 있는 항목 |

   | 결과 | 하는 일 |
   | --- | --- |
   | 미해결 항목이 없음 | 2로 감 |
   | 미해결 항목이 있음 | UX 확정을 기입하지 않습니다. 미해결 항목을 번호(사용자 확인 목록의 Q · C, 의견 번호)로 보여 주고 "아래 미해결 항목이 해결되어야 UX 확정을 기입할 수 있습니다"라고 알립니다. 요청자의 답을 받아 고친 뒤(절차 1번 순서 3, 절차 2번) 다시 확인합니다 |

2. **UI 작업 대상인지 확인받습니다.** 요건마다 실제로 고친 것을 보고 아래 표대로 UI 작업 칸의 값을 정해, 요건마다 값과 근거(바뀐 요소 · 바뀐 화면 표기 글자의 디스크립션 번호)를 보여 주고 확인받습니다. 1단계에서 이 칸에 적은 값은 화면을 그리기 전에 적어 둔 임시 값입니다.

   | 실제로 고친 것 | UI 작업 칸 |
   | --- | --- |
   | 화면의 배치 · 요소가 바뀜, 새 화면 | `대상` |
   | 화면 표기 글자가 생기거나 바뀌거나 없어짐(화면 MD "화면 표기 글자" 표의 상태 칸이 `신규` · `변경` · `제거`인 줄이 있음) | `대상` |
   | 디스크립션만 바뀜 | `대상 아님` |

   - 디자인 화면은 읽지 않으므로, 디자인 화면에서 그 글자를 쓰는 곳(우리 화면과 다르게 그린 케이스 등)은 보지 못했다는 것을 함께 알립니다. 요청자가 값을 바꾸면 바꾼 값과 이유를 기입합니다.
   - 요청자가 확인한 값을 작업 기록 "요건별 진행 경로"의 UI 작업 칸에 확정 값으로 적습니다. 1단계의 임시 값과 달라졌으면 그 칸에 `바뀜 (날짜, 이유)`를 함께 적습니다.
3. **기계 검사를 할지 묻습니다.** "기계 검사를 한 번 더 진행할까요?"라고 묻습니다. 리뷰에서 고친 것이 얼마나 되는지는 요청자가 판단합니다.

   | 답 | 하는 일 |
   | --- | --- |
   | 진행함 | 절차 1번의 기계 검사 뒤로 고친 화면에 기계 검사를 하고("화면 수정 규칙"의 "기계 검사 방법") 4로 감 |
   | 하지 않음 | 하지 않고 4로 감 |

   - 절차 1번의 기계 검사 뒤로 고친 화면이 없으면 묻지 않습니다.
4. **Ver을 묻고 기입합니다.** 이 작업의 케이스 1 · 2 화면을 CID마다 보여 주고(CID · 화면 이름 · 기존 Ver · 업데이트 메모에 넣을 줄이 있는지) "이번 작업의 Ver을 알려 주세요"라고 묻습니다. 요청자가 정한 Ver을 화면 MD 머리말 `version`에 적고 패널 화면 정보의 Ver에 옮깁니다(`reference-rules/description.md` 7절 "화면 정보에 적는 값"). 케이스 3 화면은 묻지 않습니다(기존 화면의 Ver 그대로).
5. **업데이트 메모를 만듭니다.** 화면마다 그 화면 MD "변경 확인" 표에서 "확인한 날 · 답"이 `맞음`이고 "업데이트 메모" 칸이 `O`인 줄을 모아 패널 옆에 업데이트 메모를 만듭니다(`reference-rules/description.md` 5절 "업데이트 메모"). 이 줄들이 이 작업으로 화면과 동작이 바뀐 것 전부입니다(요건대로 고친 것, 질문 대기의 답으로 바뀐 것, 리뷰 의견으로 바뀐 것). `되돌림`인 줄과 `-`인 줄은 넣지 않습니다. 넣을 줄이 없으면 만들지 않습니다. 제목의 Ver은 순서 4에서 정한 그 화면의 Ver입니다.
6. **기입합니다.** 작업 기록 "단계" 표 4단계 줄의 "남긴 것"에 `UX 확정 (날짜)`를 적습니다. 작업 기록 머리말과 이 작업에서 고친 화면 MD 머리말에 화면 기준 `basis` · `basis_versions`를 적습니다(`reference-rules/work-log.md` "작업 기준").
7. `이어서 작업할 곳:` 줄을 `4단계 · UX 확정 기입함, 언어셋 정리할 차례`로 고치고 절차 4번으로 갑니다.

**※ 고객 컨펌이 필요 없는 요건** (※ 정할 것 나-1)

- 요청 글 · 요청 자료에 고객 컨펌 없이 바로 반영해 달라는 말이 있었거나, 고객 컨펌을 미리 받은 요건은 고객 UX 리뷰를 받지 않습니다. 절차 1번까지 마친 것이 최종 수정입니다.
- 작업의 모든 요건이 그러면, 절차 1번을 마친 날을 UX 확정 날짜로 기입하고 `UX 확정 (날짜) · 고객 컨펌 없음 (근거)`로 적습니다. 요청자에게 그렇게 적는다고 알립니다.
- 고객 컨펌이 필요한 요건이 섞여 있으면, 필요 없는 요건은 최종 수정까지 해 두고 작업의 UX 확정은 고객 컨펌을 받은 날로 기입합니다.

**※ UX 확정 뒤에 고칠 때** (※ 정할 것 나-4)

- UX 확정 뒤에 들어온 의견은 절차 2번의 순서대로 고칩니다. UI 리뷰에서 바뀐 것은 절차 5번에서 맞춥니다.
- 화면이 하는 일이 바뀌는 수정(경로 분기 기준 3 · 4 · 6)이면 고객 컨펌을 다시 받을지 요청자에게 묻고, 답을 "의견" 절의 처리에 기입합니다.
- UX 확정 뒤에 확인된 변경은 그때 업데이트 메모에 더합니다.
- 정책 · 기준데이터를 다시 읽고 고친 화면은 그 화면 MD와 작업 기록 머리말의 `basis` · `basis_versions`를 고친 때로 다시 적습니다. UI 리뷰에서 바뀐 것을 UX에 맞춘 것(절차 5번)은 다시 적지 않습니다.
- UX 확정 뒤에는 디스크립션 번호를 바꾸지 않습니다. 더한 요소는 새 번호를 이어 붙이고, 뺀 요소의 번호는 비워 둡니다.
- 화면 표기 글자가 바뀌었으면 화면 MD "화면 표기 글자" 표의 상태 칸을 고치고("화면 수정 규칙"), 절차 4번을 그 화면 표기 글자만 다시 해 작업 기록 "언어셋" 절의 줄을 고칩니다.

### 4) 언어셋을 정리하고 UI팀에 넘길 것을 보여 줌

> 초안 (확정 전). ※가 붙은 곳은 "※ 정할 것" 가-3의 안을 넣어 둔 것입니다. 언어셋의 저장 형식 · Language ID · 번역 상태는 언어셋 담당자가 정하는 중입니다.

UX 확정을 기입한 뒤에 합니다. 화면 표기 글자가 확정된 뒤에 해야 같은 화면 표기 글자를 두 번 작업하지 않고, UI팀이 번역 길이를 보고 디자인할 수 있습니다.

**대상**

- 이 작업에서 고친 화면의 화면 MD "화면 표기 글자" 표에서 아래 둘 가운데 하나인 줄입니다(`templates/screen.md` "화면 표기 글자"). 케이스로 나누지 않습니다.

  | 대상인 줄 | 어떤 화면 표기 글자인가 |
  | --- | --- |
  | 상태 칸에 `신규` · `변경` · `제거`가 있음 | 3단계와 이 단계에서 화면 MD를 고치며 표시해 둔, 생김 · 바뀜 · 이 화면에서 제거된 화면 표기 글자 |
  | Language ID 칸이 비어 있음 | 아직 언어셋과 맞춰 보지 않은 화면 표기 글자(기존 화면을 작업방으로 처음 옮긴 화면의 화면 표기 글자 등) |

- 대상인 줄이 없으면 작업 기록 "언어셋" 절에 `해당 없음 (화면 표기 글자가 바뀌지 않음)`을 기입하고 아래 "UI팀에 넘길 것을 보여 줌"으로 갑니다.
- 디스크립션만 바뀐 것은 대상이 아닙니다(화면 표기 글자가 아님).

**순서**

1. **대상 목록을 모읍니다.** 고친 화면의 화면 MD "화면 표기 글자" 표에서 대상인 줄을 모읍니다. T-IOS · L-IOS에 같은 화면 표기 글자는 한 줄로 합칩니다. 번역은 이 목록에 대해서만 합니다.
2. **언어셋과 대조해 구분을 붙입니다.** `이미 있음`인 줄은 화면 MD "화면 표기 글자" 표의 Language ID 칸에 언어셋의 Language ID를 채우고, 번역하지 않습니다. 화면 MD "화면 표기 글자" 표의 상태 칸은 화면에서 생기고 바뀐 것이고, 아래 구분은 언어셋에 있는지로 붙입니다. 화면에는 `신규`인 화면 표기 글자가 언어셋에는 `이미 있음`일 수 있습니다. 다른 화면이 쓰는지는 다른 화면 MD의 "화면 표기 글자" 표에서 찾고, 아직 작업방으로 옮기지 않은 화면은 화면 MD "화면 글자"에서 찾습니다.

   | 구분 | 뜻 |
   | --- | --- |
   | 신규 | 언어셋에 없는 화면 표기 글자. Language ID는 이 단계에서 만들지 않고 비워 둠(5단계에서 언어셋 문서에 반영할 때 만듦) |
   | 변경 | 언어셋에 있는 화면 표기 글자가 바뀌고, 변경 전 글자를 쓰는 화면이 남지 않음 (변경 전 → 변경 후). 다른 화면이 변경 전 글자를 쓰면 언어셋은 그대로 두고 변경 후 글자를 `신규`로 붙임 |
   | 삭제 | 화면에서 `제거`된 화면 표기 글자를 쓰는 화면이 하나도 남지 않음. 이때만 언어셋에서 삭제할 대상으로 올림 |
   | 그대로 (다른 화면이 씀) | 화면에서 `제거`됐지만 다른 화면이 쓰고 있음. 언어셋은 그대로 둠 |
   | 이미 있음 | 같은 화면 표기 글자가 언어셋에 있음. 새로 만들지 않고 그 Language ID를 다시 씀 |

3. **번역 대상인지 가립니다.** 어느 언어에서도 영어 그대로 쓰는 말(고유명사, 상태값, 단위 등)은 번역하지 않고 `-`와 이유를 적습니다.
4. **※ 번역을 붙입니다.** 번역 대상인 신규 · 변경 화면 표기 글자에 제공 언어의 번역을 붙이고, 번역 상태를 `AI 번역`으로 적어 확정된 번역과 구분합니다.
5. **※ 가장 긴 번역 글자를 적습니다.** 화면 표기 글자마다 제공 언어 가운데 가장 긴 언어와 그 언어로 번역한 글자를 적습니다. UI팀이 이 길이를 보고 디자인합니다(헌법 8조). 같은 값을 화면 MD "화면 표기 글자" 표의 "가장 긴 언어 · 번역 글자" 칸에도 채웁니다. 다음에 이 화면을 고칠 때 그 길이를 보고 그리기 위해서입니다.
6. **작업 기록 "언어셋" 절에 기입합니다**(아래 틀).

**언어셋 틀** (작업 기록 "언어셋" 절)

```markdown
## 언어셋

| 구분 | 화면 (CID · 번호) | 화면 표기 글자 (영어, 변경은 변경 전 → 변경 후) | Language ID | 번역 대상 (O / - 이유) | 번역 상태 | 가장 긴 언어 · 번역 글자 |
| --- | --- | --- | --- | --- | --- | --- |
| 신규 | TI-EVT-01-P · LI-EVT-01-P #2-3 | Effect | | O | AI 번역 | DE · (독일어로 번역한 글자) |
| 변경 | TI-EVT-P #1-4 | Export → Download | (언어셋의 ID) | O | AI 번역 | PT · (포르투갈어로 번역한 글자) |
| 이미 있음 | TI-EVT-02-P #3 | Cancel | (언어셋의 ID) | O | (언어셋의 상태) | (언어셋의 값) |
```

**UI팀에 넘길 것을 보여 줌**

1. 아래를 요청자에게 한 번에 보여 줍니다. UI팀에 넘기는 것은 요청자가 합니다.

   | 넘길 것 | 작업 기록의 절 |
   | --- | --- |
   | UI 작업 칸이 `대상`인 요건의 화면 목록과 바뀐 곳 | "요건 목록", 화면의 업데이트 메모 |
   | 바뀐 화면 표기 글자와 번역, 가장 긴 번역 글자 | "언어셋" |

2. 모든 요건의 UI 작업 칸이 `대상 아님`이면 "단계" 표 4단계 줄의 "남긴 것"에 `UI 확정 해당 없음 (이유)`를 적고 절차 6번으로 갑니다. 바뀐 화면 표기 글자가 있으면 "언어셋" 절은 그래도 보여 줍니다.
3. `이어서 작업할 곳:` 줄을 `4단계 · UI팀에 넘길 것을 보여 줌 (날짜)`로 고칩니다.

### 5) UI 리뷰에서 바뀐 것을 UX에 맞추고 UI 확정을 기입함

> 초안 (확정 전).

요청자가 고객 UI 리뷰가 끝났다고 알리면 합니다. UI팀의 작업, 고객 UI 리뷰, UI 화면의 수정은 이 흐름 밖에서 진행됩니다. 여기서는 UI 리뷰에서 바뀐 것을 UX 화면설계에 맞춰 둡니다.

1. **바뀐 것을 받습니다.** UI 리뷰에서 화면 표기 글자 · 요소 · 화면이 바뀌었거나 더해졌는지를 요청자가 글로 알려 줍니다. 디자인 화면을 읽어 바뀐 곳을 찾지 않습니다. 바뀐 것이 없으면 3으로 갑니다.
2. **UX에 맞춥니다.**
   - 받은 것을 하나씩 작업 기록 "의견" 절에 출처 `고객 UI 리뷰`로 기입합니다.
   - 화면 MD를 먼저 고치고 Figma를 고칩니다. 짝 화면도 함께 보고, 바뀐 곳은 "변경 확인" 표에 줄을 더합니다(위 "화면 수정 규칙"의 "수정 순서").
   - 화면 표기 글자가 바뀌었으면 절차 4번을 그 화면 표기 글자만 다시 해 작업 기록 "언어셋" 절의 줄을 고칩니다.
   - 화면이 하는 일이 바뀌는 수정이면 절차 3번 "UX 확정 뒤에 고칠 때"를 따릅니다.
3. **UI 확정을 기입합니다.** 작업 기록 "단계" 표 4단계 줄의 "남긴 것"에 `UI 확정 (날짜)`를 적고 절차 6번으로 갑니다.

### 6) 단계를 끝냄

> 초안 (확정 전).

UI 확정(UI 작업이 없으면 UX 확정과 언어셋 정리)을 마친 뒤 합니다. 요청 전체를 반영하지 않기로 했을 때도 여기로 옵니다.

1. **끝 관문을 검사합니다** (아래). 통과하지 못한 것이 있으면 이 단계 안에서 풉니다.
2. **케이스 1의 `CID-복제본`을 지웁니다**(T · L, `flow/3-design.md` 케이스 1 흐름 1-4). 요청을 반영하지 않기로 했으면 원본을 복제본대로 되돌린 뒤 지웁니다.
3. 작업 기록 "단계" 표 4단계 줄의 "끝낸 날"과 관문 칸에 `끝 관문 통과 (날짜)`를 적고, `이어서 작업할 곳:` 줄을 `5단계 · 완료`로 고칩니다.

**끝 관문**

- "남긴 것"에 UX 확정 날짜가 있음(고객 컨펌이 없으면 근거가 함께 있음). 작업 기록 머리말과 고친 화면 MD 머리말에 화면 기준 `basis` · `basis_versions`가 있음
- "남긴 것"에 UI 확정 날짜 또는 `UI 확정 해당 없음 (이유)`가 있음
- "의견" 절의 항목마다 처리와 처리한 날이 있음
- 사용자 확인 목록(질문 대기 · 변경 확인)과 "의견"에 미해결 항목이 없음
- "요건 목록"에서 요청 상태가 `추가` · `변경`인 줄마다 "요건별 진행 경로"에 줄이 있음
- "언어셋" 절에 바뀐 화면 표기 글자가 기입돼 있거나 `해당 없음 (화면 표기 글자가 바뀌지 않음)`이 있음. 화면 MD "화면 표기 글자" 표의 대상 줄에 "가장 긴 언어 · 번역 글자"가 채워져 있음(번역 대상이 아닌 줄은 `-`)
- 절차 1번의 기계 검사를 통과함. UX 확정 때나 요청을 받아 기계 검사를 했으면 그것도 통과함("화면 수정 규칙"의 "기계 검사 시점")
- 요청을 반영하지 않기로 했으면 위 대신: 원본을 되돌렸음, 반영하지 않은 이유가 "의견" 절 또는 "요청자 확인" 표에 있음
