# 화면설계 흐름 가이드 (팀 공유)

> 상태: 1차 (2026-11-10). 화면설계 흐름(0 ~ 7단계)을 함께 쓰는 UX 팀원이 꼭 알아야 할 것을 모은 문서입니다. 자세한 순서는 단계 문서(`flow/0-start.md` …)에 있고, 이 문서는 "왜 이렇게 하는지"와 "놓치기 쉬운 것"만 짧게 둡니다. 단계 문서를 하나 쓸 때마다 그 단계의 포인트를 3절에 더합니다.

## 1. 한눈에

- **케이스 세 개:** ① 화면 부분 수정(고도화): 신규 작업방에 그려진 화면을 고객 요청 등에 따라 부분만 고침 ② 신규 화면 ③ 기존 화면 다시 그리기 (기존 메뉴를 신규 작업방으로 다 옮기면 없어지는 케이스)
- **단계:** 0 시작 → 1 요건 정의 → 2 근거 · 분석 → 3 화면 설계 → 4 검토 → 5 고객 UX 리뷰 → 6 다국어 → 7 완료
- **요청자 확인은 세 번:** 1단계 끝(요건), 2단계 끝(정책 수정 범위), 4단계 끝(남은 질문 대기 · 변경 확인). 나머지 단계의 끝은 기계 검사로 확인합니다.
- **단계를 건너뛰지 않습니다.** 앞 단계의 끝 관문을 통과해야 다음 단계로 갑니다(헌법 1조).

## 2. 꼭 알고 있어야 할 것

### 2-1. 질문이 있어도 먼저 그립니다

- 정해지지 않은 곳도 따를 것을 정해진 순서(기존 원본 → 정책서 → 공통 UX → 같은 메뉴의 다른 화면)로 찾아 그리고 쓴 뒤, **빨간 글씨 `※ 질문 대기`**로 표시합니다. 근거가 있어 기존 화면과 다르게 그린 곳은 **`※ 변경 확인`**으로 표시합니다. 질문 때문에 화면이나 디스크립션을 비워 두지 않습니다.
- 담당자가 판단하거나 Claude와 이야기해 정하면 고치고 빨간 표시를 지웁니다.
- 빨간 표시가 남아 있으면 완료가 아닙니다. 고객사 · 개발사에 전달하기 전에 모두 지웁니다.

### 2-2. 정해야 할 것은 "논의 대상" 한 리스트로

- 내부 논의 · 고객 논의를 따로 두지 않고 **논의 대상 하나**로 받습니다. 누가 정하는지(내부 / 고객)는 칸 하나로 거릅니다.
- 결정은 **정한 사람의 이름과 날짜**로 남습니다. 따로 정한 승인 담당자는 없습니다(헌법 4조).
- 상태는 넷입니다: **논의 중**(답이 아직 없음) → **결정**(정해졌고 정책서 · 화면에 넣는 일이 남음) → **종료**(논의가 끝났고 처리할 것도 모두 처리해, 이 항목을 닫아도 됨), 그리고 **보류**(미뤄 둠, 언제 다시 볼지 적음)
- 결정을 적으면 Claude가 **영향 범위**(정책서 + 화면 / 화면 / 없음)와 올릴 반영 대기 항목을 정리해 보여 주고, 확인받은 뒤 반영합니다. 영향 범위를 사람이 고르지 않습니다.
- 화면 영향은 없지만 **작업할 때 알아야 하는 이슈**(개발 중 이슈, 고객사 내부 정책 이슈)와 **하지 않기로 한 요청**도 논의 대상에 남깁니다(영향 범위 없음). 걸린 정책 · 화면을 적어 두면 그 화면을 작업할 때 2단계에서 Claude가 읽습니다.
- 같은 질문이 둘 생기면 먼저 생긴 쪽으로 모으고 다른 쪽은 지웁니다. Claude가 제안하고 확인받은 뒤 합칩니다.
- "논의 리스트 보여 줘"로 한 번에 봅니다.

### 2-3. 화면 작업이 있는 결정은 완료 때 한꺼번에

- 화면을 설계하다 보면 처음 정한 정책이 바뀌는 일이 많습니다. 그래서 **그 결정으로 화면을 그리는 작업이 있으면, 그 작업이 완료(화면 컨펌)될 때 한꺼번에** 정책서와 다른 화면 반영 대기에 들어갑니다. 그 전까지는 논의 대상에 `결정`(작업 기록 이름과 함께)으로 보이고, 바뀌면 결정 줄을 더합니다.
- 고객이 알려 준 정책이라도 그것으로 곧바로 화면을 그리면 마찬가지로 화면 컨펌 때 반영합니다. **화면 작업이 없는 결정**(정책 문장만 바뀜, 참고 이슈)만 바로 반영합니다.
- 설계하다 발견한 이슈는 `논의 중`으로 올리고 화면에 빨간 "※ 질문 대기"를 둡니다. 답이 올 때까지 그 화면은 완료하지 못합니다.
- 개발사 검토에 따라 화면이 달라질 수 있으면 **논의 중**으로 둡니다. 다 정해졌고 한 번 확인만 해 보기로 한 것은 종료로 두고 논의 대상에 **"후속 확인 필요: 누구에게 · 무엇을"** 한 줄을 적습니다. 논의 리스트 "후속 확인 필요" 묶음이 회의 때 물을 목록입니다.
- 후속 확인의 답이 오면: 그대로면 그 줄만 "후속 확인 끝"으로 고치고, 바뀌면 결정 줄을 더해 정책서와 영향 화면 반영 대기에 넣습니다(전달한 화면은 다음 Ver).
- 임시 정책은 따로 두지 않습니다(2026-11-10).

### 2-4. 반영 대기 목록 = 내 작업 밖 다른 화면에 반영할 것

- 내가 고치는 화면은 바로 고칩니다. 내 작업 때문에 **다른 화면도 바뀌어야 하면**, 작업이 완료될 때 그 화면의 반영 대기 목록에 항목이 생깁니다. 다른 작성자에게 알리는 대신 이 항목이 알림입니다(헌법 5조).
- 간단한 것은 그 화면 작성자에게 구두로 묻고 **함께 고칠 수 있습니다.** 그때는 항목을 만들지 않고 그 화면 변경 이력에 "연동 변경"을 남깁니다(2단계 "영향 화면" 표의 처리: 함께 고침 / 반영 대기).
- 항목은 왜 올라왔는지(타입)를 적습니다: 논의 결정 · 다른 화면 파급 · 기준 자료 변경 · 외부 원본 변경 · 점검 발견
- 칸: `ID | 타입 | 변경 전 | 변경 후 | 근거 | 상태`. 상태는 `대기` · `작업 중 (작업 기록 이름)` · `반영 완료 (날짜)` · `제외 (날짜, 이유)` 넷. 작업 중인 화면설계가 이번에 반영하기로 고른 항목은 `작업 중`, 화면 컨펌(7단계) 때 `반영 완료`. 항목은 지우지 않습니다.
- 주기 점검은 "주기 점검 해 줘"라고 요청할 때 돕니다. 화면 · 정책 · 기준 자료를 대조해 어긋난 곳을 항목으로 만듭니다.

### 2-5. 기준은 모두 같게, Common UX만 대상에 맞게

- 흐름 · 규칙 · 정책서 · 기준데이터 · 화면 정의서는 **팀 모두가 같은 것 하나**를 씁니다.
- Common UX(UX가이드)만 그릴 대상에 맞게 고릅니다. PC 화면이면 Common UX - PC, 모바일이면 모바일 가이드.
- 화면 MD에는 **언제의 최신본과 맞춰 봤는지(기준점)**를 남깁니다. 옛 버전으로 그리려는 것이 아니라, 나중에 "그 뒤로 무엇이 바뀌었나"를 찾고 근거를 다시 보려는 것입니다.

### 2-6. 디스크립션은 고객사 · 개발사가 읽습니다

- **본보기를 따라 씁니다.** 기존 작업방에서 고른 세 화면(Samples 목록 · Samples Details · Test Analytics)이 기준입니다(`examples/description-samples.md`).
- **개조식으로, 명사로 끝냅니다**(노출 · 조회 · 이동 · 불가). "~됩니다 · ~합니다"를 쓰지 않고, 한 줄에 사실 하나만 씁니다.
- **화면에서 보이고 일어나는 일은 풀어 씁니다.** 정책 ID만 적지 않습니다. 정책 ID는 블록 끝 `● 정책 참고`에만 둡니다(헌법 3조).
- 모양: 번호(0 화면 · 1 영역 · 1-1 요소), 제목에 종류(`Status(Dropdown)`, `[Save] 버튼`), `● 라벨` 아래 `- 내용`(정의 · 기능 · Default · 표출 항목 · 정렬 · 노출 조건 · 동작)
- 늘 보이는 항목은 값이 없어도 지우지 않고 값이 없을 때의 표기를 적습니다(예: 부재 시 '-' 노출).
- **패널 틀은 하나로 통일합니다.** 화면 오른쪽에 너비 332, 맨 위 화면 정보(Ver · Date · CID · 작성자 · 화면 · 경로), 번호 칸은 영역(1, 2, 3)은 회색 · 요소(1-1, 2-1)는 흰색. 맨 아래 Dev · SG 확인 일자 줄은 두지 않습니다.
- **기존 화면을 다시 그릴 때(케이스 3)는 Ver · Date · 작성자를 기존 화면 그대로** 가져옵니다. 화면 부분 수정 · 신규일 때만 Date는 작성일, 작성자는 요청자로 씁니다.
- 내부 표기(작업 메모, 저장소 경로 등)는 넣지 않습니다. T-IOS · L-IOS 디스크립션은 **각자 완결**합니다. User Type · Service Mode는 0번에 값만 씁니다.

### 2-6b. 케이스 화면은 근거가 있는 것만, 달라지는 부분만

- 케이스 화면의 원본은 화면 MD의 **케이스 표 하나**입니다. 근거가 **기존 원본 · 디스크립션 조건 · 요청자** 셋 중 하나여야 표에 올립니다. 근거 없이 더 필요해 보이면 그리지 않고 질문으로 올립니다.
- 디스크립션 조건으로 그리는 것은 여섯 종류입니다: 상태별 데이터 노출 / 올리거나 눌렀을 때 뜨는 것 / 유형 · 대상에 따라 표출 항목 구성이 다른 것 / 개수가 기준을 넘어 요소가 생기거나 배치가 바뀌는 것 / 처음 들어왔거나 데이터가 없을 때 / 한 번의 조작으로 여러 단계를 거쳐 바뀌는 것
- **달라지는 부분만 잘라 그립니다.** 화면 전체가 달라질 때만 전체를 그립니다. 초록 띠 `Case n. 제목`, 노란 띠 `n-1. 조건`, 띠 아래 설명 한두 줄.
- **늘 보이는 항목은 지우지 않습니다.** 값이 없으면 '-', 누를 수 없는 버튼은 Disabled로 둡니다.
- 케이스에는 패널과 버전을 두지 않습니다. 설명은 본 화면 디스크립션에 번호를 두고 적고, 케이스 조각에 그 번호 표시를 붙입니다.
- 본보기: `examples/case-samples.md` (Samples, Samples Details, Test Management, Door Control, Waste Bin/Bottle, LIS Setting)

### 2-7. Claude는 제안하고 실행합니다

- 결정은 사람이 합니다. Claude는 근거가 없으면 만들어 쓰지 않고 질문으로 남깁니다(헌법 7조).
- 대화 하나에 작업 하나. 앞선 대화가 아니라 저장소를 근거로 일합니다.

## 3. 단계별 포인트

### 0. 시작 (`flow/0-start.md`)

**이 단계에서 하는 일 (요약)**

1. **요청 기본 정보:** 케이스 · 대상 CID(짝 포함) · 요청자 · 테스트인지를 밝힘
2. **작업 기준 확인:** 공통 기준은 팀 최신본, Common UX는 그 Figma 파일의 가이드. 기준점(`basis`)을 적음
3. **작업 기록 만들기:** `work-logs/`에 만들고 고칠 것으로 보이는 CID · 정책을 적음
4. **겹침 확인 (끝 관문):** 열린 작업 기록과 같은 CID · 정책이 있으면 먼저 어떻게 할지 정함

| 포인트 | 왜 |
| --- | --- |
| 시작할 때 **케이스 · 대상 CID · 요청자 · 테스트인지**를 밝힘. 애매하면 시작 전에 물음 | 단계마다 할 일이 케이스에 따라 달라짐 |
| 요청이 한쪽 CID만 말해도 **짝 CID(T-IOS · L-IOS)를 모두** 대상에 넣음 | 한쪽만 고쳐지는 일을 막음 |
| **기준점**을 작업 기록에 적음 (시각 · Common UX와 분류별 수정본 번호) | 2-5 |
| **작업 기록**을 만들어 대표 저장소 `work-logs/`에 두고 7단계까지 이어 씀. 단계를 시작할 때마다 다시 읽음 | 다음 사람 · 다음 대화가 이어 가고, 건너뛴 단계가 드러남. 팀원 모두 누가 어떤 메뉴를 몇 단계까지 했는지 봄 |
| 작업 기록의 `다음:` 한 줄을 늘 최신으로 둠. 끊기면 "작업 기록 `<이름>` 이어서 해 줘" | 토큰이 모자라거나 대화가 끊겨도 새 대화에서 바로 이어 감 |
| 다른 사람의 열린 작업과 **같은 CID · 같은 정책**을 고치는지 확인. 겹치면 어떻게 할지 먼저 정함 | 같은 화면 · 정책을 두 사람이 다르게 고치는 일을 막음 |
| "테스트로"라고 하면 순서는 그대로, 저장소는 고치지 않음 | 규칙을 시험할 때 실제 자료가 바뀌지 않게 |
| 화면설계가 아닌 요청(질문, 자료 찾기, 정책만 고치기)은 이 흐름을 타지 않음 | 흐름을 가볍게 |

### 1. 요건 정의 (`flow/1-requirements.md`, 초안)

**이 단계에서 하는 일 (요약)**

1. **기존 화면을 정확히 읽기:** 기존 화면 MD 전부, 기존 UX 화면설계서의 원본 프레임 · 케이스 프레임, 호출하는 · 호출되는 화면, 디스크립션이 가리키는 화면을 T · L 각각 끝까지 읽음. 화면 부분 수정은 요청 원문과 신규 작업방에 그려진 그 화면의 화면 MD, 신규는 요청 · 회의록을 읽음. **UX가이드 · 정책서 · 기준데이터는 읽지 않음**(2단계)
2. **요건서 쓰기 (작업 기록 "요건" 절):** 무엇을 · 왜, 요건 대상 화면 목록(짝 CID · 영역 · 기존 원본의 케이스 화면), 이번에 반영할 반영 대기 항목, 확인할 것. 화면 부분 수정은 변경할 것 표, 신규는 새 화면 정의와 새 CID 제안을 더함
3. **확인할 것 찾기:** 기능 정의가 안 된 요소, 알럿 / 컨펌 보완 필요 지점, IA와 화면이 다른 곳, 새로 필요한 CID, 예전 반영 대기의 `대기 (확인 필요)` 항목 — 다섯 가지. **적어 두기만 하고 묻지 않음**
4. **요청자 확인 (끝 관문):** 요건을 정하는 데 필요한 것만, 정해진 문장으로 물음

| 포인트 | 왜 |
| --- | --- |
| 1단계는 **작업자가 무엇을 하기 원하는지**를 분명히 하는 단계. 기존 화면을 정확히 분석해야 요건이 분명해짐 | 요건이 틀리면 2 · 3단계가 모두 헛일이 됨 |
| 묻는 것은 여섯 가지뿐: 요건 대상 화면 목록, 이번에 반영할 반영 대기 항목, (화면 부분 수정) 변경할 내용 · 짝 화면, (신규) 새 화면 정의 · 새 CID. 문장도 정해져 있음 | 사람마다 · 작업마다 확인받는 내용이 달라지지 않게 |
| 화면을 그리는 데 필요한 질문(케이스 화면, 가이드 요소, 기능 정의가 안 된 요소)은 1단계에서 묻지 않음 | 요건 정의에 필요 없는 질문을 줄임. 정책에 관한 것은 2단계에서, 화면에 관한 것은 3단계 빨간 글씨로 물음 |
| 기존 화면은 **UX 화면설계서(패널이 붙은 기획 프레임과 디스크립션)**만 읽음. 디자인 화면은 읽지 않음 | 디자인 화면에서 가져오면 UX 설계 기준과 달라짐 |
| 기존 케이스 프레임을 T · L 각각 열어 Case 번호 · 제목 · 조건을 빠짐없이 적음 | 3단계 케이스 표의 근거 "기존 원본"이 됨 |
| 반영 대기 `대기` 항목은 근거가 같은 것끼리 묶어 보여 주고, 묶음마다 반영할지 고름. 고른 항목은 `작업 중`으로 | 답을 받기 전에는 반영하지 않음. 다른 사람이 남긴 변경을 마음대로 넣지 않음 |
| 신규 화면의 Service Mode는 묻지 않음 | 화면이 나온 뒤 고객이 정하는 값이라 3단계에서 질문 대기로 두고 5단계 고객 UX 리뷰에서 받음 |
| 새 화면은 1단계에서 **CID를 제안하고 요청자가 확정** → 3단계 화면에 채움 → 7단계에 IA에 넣음 | CID는 담당자가 책임지고, IA가 화면과 어긋나지 않게 |
| 이행 기간에는 기존 작업방의 최신 영역(민트색 바 = 2.1 2차)만 보고, 화면 MD가 없는 CID는 먼저 옮김 | 예전 영역의 문구는 이미 바뀌었을 수 있음 |

### 2. 근거 · 분석 (`flow/2-evidence.md`, 초안)

**이 단계에서 하는 일 (요약)**

1. **넓게 찾아 읽기:** 정책 여섯 길(CID · 화면 머리말 · 화면 본문 · 정책이 가리키는 것 · 장비 · 늘 읽음)로 정책을 찾고, 변경하는 값 · 동작이 있으면 "정의된 곳 → 쓰는 정책 → 쓰는 화면"으로 따라감. UX가이드 · 기준데이터 · 관련된 논의 대상도 읽음
2. **대조:** 요건과 근거를 영역 · 요소마다 대조해 "정책에 있음 / 기존 화면이 정책과 다름 / 정책에 없음 / 정책을 바꿔야 함 / 논의 대상에 이미 있음"으로 나눔
3. **좁히기:** 읽은 자료를 모두 "읽은 자료 목록"에 적고, 이 작업에 실제로 쓰이는 것에 **설계에 씀 O**를 표시. 3단계는 O인 자료를 읽고 그림
4. **정책 수정 범위 · 영향 화면 내기:** 바꿀 · 더할 정책과 그것을 쓰는 다른 화면(짝 CID 포함)을 표로
5. **용어 정리:** 단어 단위로 용어집과 대조해 용어 목록을 만듦. 새 용어는 용어집에 먼저
6. **요청자 확인 (끝 관문):** 정책 수정 범위 · 영향 화면(함께 고침 / 반영 대기) · 새 용어 · 확인할 것 중 정책에 관한 것

| 포인트 | 왜 |
| --- | --- |
| **넓게 읽고 좁힘.** 처음에는 쓰일지 확실하지 않은 것도 읽고, 대조한 뒤 실제로 쓰이는 것에 "설계에 씀"을 표시함. 읽었지만 쓰이지 않는 자료도 지우지 않고 남김 | 3단계가 필요한 문서만 읽고 그릴 수 있게 |
| 요건의 영역 · 요소마다 설계에 쓸 자료가 표시되어 있어야 함. 관련된 자료가 없으면 **`관련 자료 없음`**이라고 따로 적음 | 찾아봤는데 없는 것과 찾아보지 않은 것을 구분. 근거 없이 그리게 되는 영역을 미리 드러냄 |
| 영역 · 요소는 번호가 아니라 이름으로 적음(기존 번호는 괄호로). 신규 화면은 "하는 일"을 적음 | 다시 그리면 번호가 바뀔 수 있고, 신규 화면은 아직 번호가 없음 |
| **정책을 다 읽기 전에는 그리지 않음.** 규칙 절만이 아니라 정의 · 규칙 · 예외 · 근거를 모두 읽음 | 예외에 관련된 동작을 빠뜨리지 않게 |
| 자료끼리 다르면 **우리 기준 자료 > Common UX > 기존 화면**. 기존 화면과 다르게 그리는 곳은 3단계에서 `※ 변경 확인`으로 표시 | 기존 화면은 옛 정책으로 그려졌을 수 있음. 작업자가 달라진 곳을 알아보고 확인하게 |
| UX가이드는 이 단계에서 읽음: 기존 화면에 없는데 가이드가 정한 요소, 가이드에 컴포넌트가 없는 요소, 가이드와 기존 화면이 다른 곳을 찾음 | 1단계에서는 읽지 않음 |
| 다른 작업이 바꾸는 중인 결정을 만나면 Claude가 고르지 않고 물음: 새 결정대로 그림 / 기다림 | 컨펌 전 결정은 바뀔 수 있어, 어느 쪽 위험을 질지는 사람이 정함 |
| 값 · 동작을 변경하면 **처음 정의된 곳에서 출발**해 그것을 쓰는 정책 · 화면을 모두 찾음 | 한 화면만 고쳐지고 같은 값을 쓰는 다른 화면이 어긋나는 일을 막음 |
| 영향 화면은 항상 **짝 CID**까지. 화면마다 **함께 고침 / 반영 대기**를 고름 | 작은 변경(문구 · 표기 · 값만 바뀜)은 같이 고치고, 나머지는 완료 때 반영 대기 항목으로 |
| 정책을 바꿀 것은 **논의 대상에 `결정`**(작업 기록 이름과 함께)으로 남김. 정책서 · 다른 화면은 7단계 완료 때 | 설계하며 결정이 바뀌어도 다른 사람에게 번지지 않음 |
| 관련된 논의 대상은 **정책서 · 화면에 아직 들어가지 않은 것**을 읽음: 논의 중 · 보류, 다른 작업이 바꾸는 중인 결정, 영향 범위가 없는 참고 이슈 · 하지 않기로 한 요청, 후속 확인 필요 | 정책서만 읽어서는 보이지 않는 것을 놓치지 않게 |
| 용어는 **단어 단위로** 대조 (예: "질문" 속 "문"을 Door로 바꾸지 않음) | 2026-11-06 테스트에서 글자 단위로 잘못 잡힌 적이 있음 |
| 문서 지도는 "근거 찾는 법" 표가 규칙이고, 색인은 스크립트가 만들어 문서가 바뀔 때마다 자동으로 다시 만듦 | 정책이 자주 바뀌어 손으로 맞추면 어긋남 |

### 3. 화면 설계 (`flow/3-design.md`, 초안)

**이 단계에서 하는 일 (요약)**

1. **설계에 쓸 자료 읽기:** 2단계의 읽은 자료 목록에서 "설계에 씀 O"인 자료를 읽고 시작. 그것만으로 정의할 수 없으면 추가로 찾아 읽고, 읽은 자료는 목록에 `(3단계에서 추가)`로 더함
2. **화면 MD 쓰기:** 틀 그대로, 디스크립션은 본보기의 결로 빠짐없이, 화면 예시 값은 기준데이터에서, 케이스 표는 근거가 있는 것만
3. **Figma 그리기:** 화면 MD를 그대로 옮김. T를 끝내고 L은 복제해 다른 점만 변경. 패널은 정해진 틀로, 케이스 화면은 `CID/Case` 프레임에
4. **빨간 글씨 두 가지:** 정해지지 않은 곳은 `※ 질문 대기`, 근거가 있어 기존 화면과 다르게 그린 곳은 `※ 변경 확인`
5. **함께 고침으로 고른 영향 화면 고치기, 용어 점검**
6. **끝 관문 (기계 검사 12개):** 짝 CID, 틀, 화면 MD = Figma, 행 수, 케이스 화면, 빨간 글씨, 컴포넌트, 예시 데이터, 용어, 반영 대기, 글자 넘침, 작업방 구성

| 포인트 | 왜 |
| --- | --- |
| 화면 MD가 원본, Figma는 그것을 옮긴 것. 고칠 때는 둘을 함께 | 글과 그림이 어긋나지 않게 (헌법 6조) |
| 가이드에 컴포넌트가 있으면 가이드 컴포넌트, **없으면 기존 UX 화면설계서에서 같은 값으로 따옴.** 디자인 화면에서는 가져오지 않음 | 갈래를 나누지 않고 한 줄로. 디자인 화면은 UX 설계 기준이 아님 |
| 기존 화면에 그 요소가 없으면 그리지 않고 `※ 질문 대기` | 지어 그리지 않음 |
| 질문이 있어도 먼저 그림. 따를 것은 기존 원본 → 정책서 → 공통 UX → 같은 메뉴의 다른 화면 순서로 찾음 | 질문 때문에 화면을 비워 두지 않음 |
| 기존 화면과 다르게 그린 곳(정책을 따름, 반영 대기 항목 반영, 가이드 요소 추가, 행을 줄임)은 `※ 변경 확인` | 작업자가 달라진 곳을 알아보고 맞는지 확인 |
| 케이스 화면은 근거(기존 원본 · 디스크립션 조건 · 요청자)가 있는 것만, 달라지는 부분만 그림. 늘 보이는 항목은 지우지 않음 | 2-6b |
| 목록 · 표는 최대 노출 개수만큼 행을 채움 | 실제 화면에 가깝게 |
| 묶음마다 스크린샷으로 **글자가 칸을 넘지 않는지** 확인. 넘치면 크기를 늘리거나 말줄임. 글자 크기를 줄이지 않음 | 마무리되지 않은 화면을 넘기지 않음 |
| 반영 대기 항목은 화면에 반영해도 `작업 중` 그대로. `반영 완료`는 7단계 | 화면 컨펌 전에는 확정이 아님 |
| 다른 사람 화면을 함께 고쳐도 그 화면의 Ver · Date · 작성자는 그대로 | 화면설계를 변경하는 수준이 아님 |
