# 0. 시작

> 상태: 초안 (2026-11-09). 2026-11-10부터 이 문서로 작업합니다. "※ 정할 것" 표시는 아직 정하지 않은 곳이며, 안을 적어 두었습니다(이 문서 끝 "정할 것").

요청을 받아 무엇을 할지 가르고, 작업 기록을 만들어 다른 사람 작업과 겹치지 않는지 본 뒤 1단계로 넘깁니다.

## 읽을 것

1. `CLAUDE.md` → `constitution.md` → `flow/README.md` → 이 문서
2. 열려 있는 작업 기록 전부 (겹침 확인용, `reference-rules/work-log.md`)
3. 대상 메뉴의 `screens/<메뉴>/_menu.md`와 IA(`ia/ia-screens.csv`)의 대상 CID · 짝 CID 줄

## 할 일

### 1) 요청 기본 정보

요청을 받으면 아래를 정해 요청자에게 한 번에 밝힙니다. 하나라도 애매하면 시작 전에 묻습니다.

| 정할 것 | 어떻게 |
| --- | --- |
| 케이스 | 1 화면 부분 수정(고도화) / 2 신규 화면 / 3 기존 화면 다시 그리기 (`flow/README.md`) |
| 대상 | 메뉴와 CID. 요청이 한쪽 CID만 말해도 **짝 CID(T-IOS · L-IOS)를 모두** 넣음. 짝이 없는 CID만 한쪽 |
| 요청자 | 요청한 사람. 1 · 2 · 4단계 끝에서 확인받을 사람 |
| 테스트인지 | "테스트로", "반영하지 말고"라고 하면 테스트 (아래 "테스트로 할 때") |

- **화면설계가 아닌 요청**(질문, 자료 찾기, 정책만 고치기, 회의록 정리 등)은 이 흐름을 타지 않습니다. 묻는 것에 답하거나, 그 일의 쓰는 법 문서를 따릅니다(정책은 `reference-rules/policy-writing.md`, 논의는 `reference-rules/discussions.md`).
- 케이스 2(신규)인데 IA에 없는 화면이면 새 CID는 1단계에서 제안합니다(`flow/1-requirements.md` "새 화면의 CID").

### 2) 작업 기준 확인

무엇을 기준으로 그렸는지 남기기 위해(헌법 4조) 기준을 확인하고 작업 기록에 적습니다. **기준은 옛 버전으로 그리려고 고정하는 것이 아니라 "언제의 최신본과 맞춰 봤나"를 남기는 기준점입니다.** 화면은 늘 최신 공통 기준으로 그립니다.

- **공통 기준 (흐름 · 규칙 · 정책서 · 기준데이터 · 화면 정의서):** 팀 모두가 같은 것 하나를 읽습니다(2026-11-09 결정).
- **UX가이드 (Common UX):** 그릴 대상에 맞는 가이드를 그 Figma 파일에 골라 씁니다(PC 화면이면 Common UX - PC, 모바일이면 모바일 가이드). 다른 기준과 달리 파일마다 다를 수 있습니다.
- **남기는 모양 (2026-11-10 정함):** 작업 기록과 화면 MD 머리말에 `basis`(맞춰 본 시각 · UX가이드)와, 그 밑에 담당자가 바로 확인할 수 있게 분류마다 그때 수정본 번호(`basis_versions`)를 적습니다. 수정본이 없는 문서는 `@원본`.

```yaml
basis: 2026-11-10 14:00 · Common UX - PC (g20261028-brex-06-J003)
basis_versions:
  rules: CURECA 작업규칙 @20261109-093829_brex-01
  policy: CURECA 정책서 @수정본
  glossary: 기준데이터 @수정본
  screens: 화면 정의서 @수정본
  ux_guide: Common UX - PC @수정본
```

- **언제 쓰나:** 0단계에 시작 기준을 적고, 7단계 완료 때와 화면을 고칠 때마다 마지막으로 맞춰 본 시점으로 새로 씁니다. 작업 기록에는 시작 기준과 마지막 기준을 둘 다 남깁니다.
- **어디에 쓰나:** ① 화면을 다시 열 때 기준 시점 뒤로 바뀐 정책 · 기준데이터만 골라 보여 줌 ② 주기 점검에서 기준 뒤로 바뀐 정책인데 반영 대기 항목이 없는 화면을 찾음(반영 대기가 빠뜨린 것을 잡는 안전망) ③ 추적(헌법 9조): 그때의 정책을 다시 열어 근거를 보여 줌
- **작업 중에 정책이 바뀌면:** 그 결정으로 내 화면에 반영 대기 항목이 생기고, 단계를 시작할 때 다시 읽으므로 이번 작업에 넣을지 요청자에게 묻습니다. 전달한 화면은 그 Ver 그대로 두고 다음 Ver에서 반영합니다.
- **그릴 Figma 페이지:** 먼저 열어 무엇이 있는지 확인합니다. 기존 내용은 옮기거나 지우지 않습니다.

### 3) 작업 기록 만들기

`reference-rules/work-log.md`의 틀로 작업 기록을 만들고 1)의 결과와 2)의 기준, **고칠 것으로 보이는 대상**(CID · 정책 ID)을 적습니다. 이 기록은 대표 저장소 `work-logs/`에 두고(2026-11-10 정함) 7단계까지 이어 쓰며, Claude는 단계를 시작할 때마다 작업 기록을 다시 읽고 시작합니다. 대화가 끊겨도 작업 기록의 `다음:` 줄에서 이어 갑니다(`reference-rules/work-log.md` "끊긴 작업 이어 가기").

### 4) 겹침 확인

열려 있는 다른 작업 기록의 대상(CID · 정책 ID)과 이번 대상을 대조합니다.

- 같은 CID나 같은 정책 ID가 있으면 **겹침**입니다. 누구의 어느 작업과 무엇이 겹치는지 요청자에게 보여 주고, 기다릴지 · 범위를 나눌지 · 함께 할지를 묻습니다. 답을 받기 전에는 1단계로 넘어가지 않습니다.
- 대상이 짝 CID나 호출하는 · 호출되는 화면으로만 이어지면 겹침이 아니라 참고로 알려만 줍니다.
- 다른 작업에서 이번 대상 화면에 만든 반영 대기 항목은 1단계에서 읽습니다(겹침 아님).

## 작업 하나에 대화 하나

- 대화 하나에 작업 하나로 시작합니다. 같은 작업 안의 질문 답 · 계획 수정은 같은 대화에서 이어 갑니다.
- 같은 대화에서 다른 작업을 요청하면 새 대화를 권합니다. 요청자가 이어서 하겠다고 하면 새 작업 기록을 만들고 0단계부터 다시 합니다.
- 앞선 대화 내용은 근거로 쓰지 않습니다. 근거는 저장소에서 읽습니다(헌법 7조).
- 대화가 끝날 때 이어 가는 데 필요한 것(결과물, 질문 대기, 지금 단계)은 모두 작업 기록과 저장소에 남깁니다. 다음 사람이 작업 기록만 보고 이어 갈 수 있어야 합니다.

## 테스트로 할 때

순서(0 ~ 7단계)는 그대로 하고 남기는 곳만 바꿉니다.

- 작업 기록과 화면 MD는 저장소 밖 작업 폴더에 씁니다. 저장소의 화면 MD · 반영 대기 상태 · 논의 대상 · `_menu.md` · `common-ux/feedback.md`는 고치지 않습니다.
- Figma 섹션 이름 뒤에 `(테스트 N)`을 붙입니다.
- 같은 페이지의 기존 그림은 옮기거나 지우지 않습니다.
- 보고 끝에 저장소가 바뀌지 않았는지(git 상태) 확인한 결과를 적습니다.
- 테스트는 겹침 확인을 하되, 겹쳐도 멈추지 않고 알려만 줍니다.
- 반영 대기 항목의 상태(`작업 중`)도 바꾸지 않습니다. 어느 항목을 반영하기로 했는지는 작업 기록에만 적습니다.

## 팀 프로그램 밖에서 할 때 (Claude Code · 채팅)

- **UX가이드:** 요청자가 알려 준 가이드 문서를 읽습니다. 요청에 가이드가 적혀 있지 않으면 시작 전에 묻습니다.
- **기준 버전:** 팀 프로그램의 수정본 번호가 없으므로 `basis_versions`에는 이 저장소의 커밋 번호와 가이드 폴더 이름을 적습니다(예: `repo: 084ce08`, `ux_guide: g20261105-daye-J001`).
- **기존 화면:** 요청자가 Figma 링크를 주면 그 프레임을 기존 UX 화면설계서로 읽습니다. 링크가 기획 프레임(패널이 붙은 너비 2252)이 아니면 읽기 전에 알립니다.

## 남는 것

- 작업 기록 (케이스 · 대상 · 요청자 · 기준 · 고칠 것으로 보이는 대상 · 겹침 확인 결과)
- 대상 CID 목록 (짝 CID 포함)

## 끝 관문

- **겹치는 작업 없음:** 겹침이 있으면 요청자의 답을 받은 뒤에만 1단계로 넘어감
- 작업 기록에 케이스 · 대상 · 요청자 · 기준이 모두 있음 (기계 검사)

## 도구

- 스킬: 진입 스킬 (요청 기본 정보 → 작업 기록 → 겹침 확인을 순서대로) — 단계 문서를 다 쓴 뒤 함께 만듦
- 에이전트: 없음
- 스크립트: 겹침 확인 (열린 작업 기록의 대상 목록을 모아 이번 대상과 비교) — 나중에 만듦
