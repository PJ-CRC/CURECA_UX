# 5. 완료

> 초안 · v0.1 (커밋 전). 2026-11-17에 절차 초안을 씀. ※가 붙은 곳은 "※ 정할 것"의 안을 넣어 둔 것입니다.

작업에서 확정된 것을 정책서 · 다른 화면 · IA · 언어셋 · Common UX 후보에 넣고, 무엇을 했고 무엇을 하지 않았는지 남기고, 작업 기록을 닫는 단계입니다. 흐름은 여기서 끝납니다.

## 절차

| 순서 | 하는 일 | 요청자 확인 |
| --- | --- | --- |
| 1 | 완료 때 넣을 것을 모아 보여 주고 확인받음 (결정 반영 정리안, 영향 화면의 처리, 새 CID, 끝난 방식) | 받음 |
| 2 | 결정을 반영하고 영향 화면을 처리함 | 없음 (절차 1번에서 받은 대로) |
| 3 | 반영 대기 항목 · 새 CID · IA를 확정함 | 없음 |
| 4 | 언어셋 문서에 반영하고 Common UX 후보를 올림 | 없음 |
| 5 | 작업 기록을 닫음 | 커밋할지 물음 |

- 4단계 끝 관문을 통과한 뒤에 시작합니다(작업 기록 "단계" 표 4단계 줄의 관문 칸 `끝 관문 통과 (날짜)`). 1단계에서 끝나는 작업은 절차 5번만 합니다(아래 "끝나는 방식").
- 할 일이 없는 순서는 "해당 없음 (이유)"로 지나갑니다. 예: 정책만 바뀐 작업은 새 CID · 언어셋 · Common UX 후보가 해당 없음, 케이스 3만 있는 작업은 결정이 없으면 결정 반영이 해당 없음.
- 요청 전체를 반영하지 않기로 한 작업(4단계 절차 6번에서 원본을 되돌림)은 결정 반영 · 새 CID · 언어셋 · Common UX 후보를 하지 않고, 반영 대기 항목을 되돌리고(절차 3번) 절차 5번으로 갑니다.
- 테스트로 하는 작업(`test: true`)은 순서는 그대로 하고 저장소 밖에만 남깁니다(`flow/README.md` "테스트로 할 때"). 반영 대기 상태 · 논의 대상 · IA · 언어셋 문서 · Common UX 후보 목록은 고치지 않습니다.

### 1) 완료 때 넣을 것을 모아 보여 주고 확인받음

1. **결정 반영 정리안을 만듭니다.** 작업 기록 "이 작업의 결정" 표와, `work`에 이 작업 기록 이름이 적힌 `결정` 논의 대상이 같은지 먼저 봅니다. 다르면 논의 대상이 원본이므로 표를 논의 대상에 맞추고 다른 곳을 보고에 적습니다. **[초안 2026-11-17, 다시 검토]** 그다음 결정마다 `reference-rules/discussions.md` 6절 "결정 반영 순서"의 1 ~ 3(확인 · 영향 화면 찾기 · 정리안)을 합니다.
   - 새 화면의 User Type · L-IOS Client Mode 결정은 `policy/client-mode-matrix.csv` · `policy/permission-matrix.csv`와, 새 메뉴면 Common UX COMM-3-a "모드별 LNB"도 고칠 곳에 넣습니다. **[초안 2026-11-17, 다시 검토]** (4단계 정할 것 다-3)
2. **영향 화면마다 처리 안을 붙입니다.** 작업 기록 "영향 화면" 표의 화면마다 `함께 고침` 또는 `반영 대기`를 붙입니다. 작은 변경이면 `함께 고침`을, 큰 변경이면 `반영 대기`를 안으로 둡니다(`reference-rules/pending-changes.md` 1절 "작은 변경 · 큰 변경"). (※ 정할 것 가-1)
3. **새 CID를 모읍니다.** 이 작업에서 붙인 새 CID 전체(1단계 절차 4번 순서 4에서 붙인 것, 3단계에서 더 붙인 것)와 짝 CID를 모읍니다.
4. **끝난 방식을 고릅니다.** 아래 "끝나는 방식"에서 하나를 안으로 둡니다.
5. **한 번에 보여 주고 확인받습니다.**

   | 보여 주는 것 | 고르는 것 |
   | --- | --- |
   | 결정마다 정리안(영향 범위 · 바뀌는 정책 문장 · 영향 화면마다 올릴 반영 대기 항목) | 확인 / 고칠 점 |
   | 영향 화면마다 처리 안과 바뀌는 곳 | 함께 고침 / 반영 대기 |
   | 새 CID 전체 (화면 이름 · 짝 CID · 근거) | 그대로 씀 / 고침 |
   | 끝난 방식 안 | 맞음 / 고침 |

   - 고칠 점을 말하면 다시 정리해 보여 줍니다. 결정 문장이나 정한 사람이 없는 결정은 반영하지 않고 묻습니다(`reference-rules/discussions.md` 6절 1).
   - 답을 작업 기록 "요청자 확인" 표에 날짜 · `5단계` · 확인한 것 · 요청자 답으로 기입합니다.

### 2) 결정을 반영하고 영향 화면을 처리함

1. **결정을 반영합니다.** 절차 1번에서 확인받은 정리안대로 `reference-rules/discussions.md` 6절 "결정 반영 순서"의 4 ~ 7(정책서 · 반영 대기 항목 · 닫기 · 보고)을 결정마다 합니다.
2. **`함께 고침`인 영향 화면을 고칩니다.** 화면 MD → Figma 순서로 고치고, 그 화면 변경 이력에 `연동 변경`과 원인(CID · DS ID), 고친 사람을 남깁니다. 그 화면의 Ver · Date · 작성자는 바꾸지 않습니다(`reference-rules/pending-changes.md` 1절). 이 화면에는 반영 대기 항목을 만들지 않고, 논의 대상 6절 "함께 고친 화면"에 적습니다.
3. **`반영 대기`인 영향 화면에 항목을 만듭니다.** 결정에서 온 것은 1에서 만들어집니다. 결정 없이 내 화면을 고쳐 맞춰야 하는 화면(다른 화면 파급)은 그 화면 MD 반영 대기 목록에 타입 `다른 화면 파급`, 근거 칸에 원인 CID로 한 줄을 만듭니다(`reference-rules/pending-changes.md` 2절).
   - ※ 그 화면이 이미 컨펌 완료 · 전달 완료된 화면이면 그 화면의 상태를 어떻게 둘지는 "※ 정할 것" 가-2입니다. 정하기 전에는 항목만 만들고 보고에 적습니다.
4. 작업 기록 "영향 화면" 표의 처리 칸에 `함께 고침 (날짜)` 또는 `반영 대기 (항목 ID)`를 기입합니다.

### 3) 반영 대기 항목 · 새 CID · IA를 확정함

1. **이 작업의 반영 대기 항목을 확정합니다.** 대상 화면의 반영 대기 목록에서 상태가 `작업 중 (이 작업 기록 이름)`인 항목을 `반영 완료 (날짜)`로 바꾸고, 그 화면 변경 이력에 반영한 항목 ID를 적습니다(`reference-rules/pending-changes.md` 4절). 요청을 반영하지 않고 끝나면 `대기`로 되돌립니다.
2. **새 CID를 확정합니다.** 절차 1번에서 고친 CID가 있으면 화면 MD · Figma 섹션 · 프레임 이름 · 화면 정보 · 작업 기록을 고친 CID로 맞춥니다.
3. **IA에 넣습니다.** `ia/change-requests.md`의 그 줄(1단계에서 `요청 전`으로 올린 "새 CID" 줄)을 `확정 (확정 CID, 요청자, 날짜)`로 바꾸고, 확정한 CID를 저장소 IA(`ia/ia-screens.csv`)에 넣은 뒤 `반영 (IA 버전)`으로 바꿉니다. IA 스프레드시트(IA-T-IOS · IA-L-IOS 탭)와 IA-문서이력 탭에도 넣고 넣은 줄을 보고합니다. ※ IA 스프레드시트에 넣는 길은 "※ 정할 것" 가-6입니다.
   - IA 문서이력의 작성자는 요청자, 버전은 하루 단위로 묶습니다: 그날 처음 넣을 때 직전 버전의 끝자리를 1 올리고, 같은 날 다시 넣으면 그 버전을 그대로 씁니다.

### 4) 언어셋 문서에 반영하고 Common UX 후보를 올림

1. **언어셋 문서에 반영합니다.** 작업 기록 "언어셋" 절의 줄을 언어셋 문서에 반영한 뒤, 반영된 줄만 화면 MD "화면 표기 글자" 표의 상태를 비웁니다. 순서는 언어셋 문서 → 화면 MD입니다. ※ 언어셋 문서의 형식과 Language ID의 번호 체계는 "※ 정할 것" 가-4입니다.

   | 구분 | 하는 일 |
   | --- | --- |
   | 신규 | 언어셋 문서에 반영하기 직전에 같은 글자가 그 사이 언어셋에 생겼는지 한 번 더 봄. 있으면 그 Language ID를 쓰고, 없으면 이때 Language ID를 만들어 언어셋 문서와 화면 MD에 채운 뒤 상태를 비움(미리 만들어 두지 않음) |
   | 변경 | 화면 MD의 "변경 전 → 변경 후"를 변경 후만 남기고 상태를 비움 |
   | 제거 | 화면 MD에서 그 줄을 지움 |
   | 이미 있음 | 4단계에서 채운 Language ID 그대로. 언어셋 문서는 고치지 않음 |

   - 언어셋 문서에 반영하지 못한 줄은 상태를 그대로 둡니다(다음 작업에서 다시 대상이 됨). 반영하지 못한 줄과 이유를 보고에 적습니다.
   - 요청을 반영하지 않고 끝나면 비우지 않고 "화면 표기 글자" 표를 작업 전으로 되돌립니다.
2. **Common UX 후보를 올립니다.** 작업 기록 "컴포넌트 없이 그린 요소" 표를 보고 `common-ux/candidates.md`에 올립니다(`common-ux/candidate-rules.md` "5단계에서 올리는 법"). 쓴 화면 수가 3화면 이상이 된 후보는 상태를 `추가 제안`으로 바꾸고 보고에 적습니다.

### 5) 작업 기록을 닫음

1. **끝 관문을 검사합니다** (아래). 통과하지 못한 것이 있으면 이 단계 안에서 풉니다.
2. **기입합니다.** 작업 기록 "단계" 표 5단계 줄의 "끝낸 날"과 관문 칸에 `끝 관문 통과 (날짜)`, "남긴 것"에 끝난 방식을 적습니다. "이 작업이 남긴 것" 절(논의 대상 · 다른 화면의 반영 대기 항목)을 채우고, 머리말 `status`를 `끝남`으로 바꿉니다. `이어서 작업할 곳:` 줄을 `5단계 · 끝남 (날짜)`로 고칩니다.
3. **보고하고 커밋할지 묻습니다.** 이 단계에서 고친 것(정책 문장, 만든 반영 대기 항목, 함께 고친 화면, 확정한 CID, 언어셋에 반영한 줄과 반영하지 못한 줄, 올린 Common UX 후보)을 표로 보여 주고 "커밋할까요?"라고 묻습니다. 커밋하면 "이 작업이 남긴 것"의 커밋 줄에 커밋 번호를 적습니다.

**끝 관문**

- 작업 기록 "단계" 표 1 ~ 4단계 줄마다 관문이 채워져 있음(1단계에서 끝난 작업은 2 ~ 4단계 줄이 `해당 없음 (이유)`)
- "이 작업의 결정" 표의 결정마다 논의 대상이 `종료`이고 6절 "반영"이 채워져 있음. `work`에 이 작업 기록 이름이 적힌 `논의 중` 논의 대상이 없음("후속 확인 필요" 줄은 남아도 됨)
- 대상 화면의 반영 대기 목록에 `작업 중 (이 작업 기록 이름)`인 항목이 없음
- "영향 화면" 표의 화면마다 처리 칸이 채워져 있음
- 새 CID마다 `ia/change-requests.md`의 줄이 `반영 (IA 버전)`임
- "언어셋" 절의 줄마다 언어셋 문서에 반영됐거나, 반영하지 못한 이유가 보고에 있음
- "컴포넌트 없이 그린 요소" 표의 줄마다 Common UX 후보 목록에 올라 있음(테스트 작업 제외)
- "남긴 것"에 끝난 방식이 있고 `status`가 `끝남`임

## 끝나는 방식

완료 때 작업 기록 "단계" 표 5단계 줄의 "남긴 것"에 하나를 적습니다.

| 끝난 방식 | 적는 말 |
| --- | --- |
| 요청대로 끝남 | 반영 |
| 요청이 바뀐 채로 끝남 | 바뀌어 반영 |
| 기존 화면을 그대로 둠 | 반영 안 함 (이유). 이미 반영돼 1단계에서 종료하면 `반영 안 함 (이미 반영됨)` |
| 정책만 바뀌고 화면은 그대로 | 정책만 반영 |
| 진행 중인 다른 작업과 같은 요청이라 그 작업으로 이어 감 | 기존 작업으로 이어 감 (작업 기록 이름) |

- 1단계에서 끝나는 두 경우(`반영 안 함 (이미 반영됨)`, `기존 작업으로 이어 감`)는 `flow/1-requirements.md` 절차 2번 순서 6과 절차 4번 순서 2에서 정해집니다. 이때는 절차 5번만 합니다.
- 요건마다 끝난 방식이 다르면 요건이 하나라도 반영됐으면 `반영` 또는 `바뀌어 반영`으로 적고, 반영하지 않은 요건과 이유를 "요건 목록" 비고에 적습니다. ※ (정할 것 가-7)
