# 1. 시작 · 요건 정의

> 초안 · v0.4

**목적:** 요청을 받아 작업 기록을 열고, 요청을 요건 목록으로 정리해 대상 화면 · 케이스 · 경로 분기 기준을 정하는 단계입니다. 예전 0단계(시작)와 1단계(요건 정의)를 합쳤습니다.

**목표:** 요건 목록을 요청자에게 확인받아 작업 대상에 `미정`이 남지 않게 하고, 아래 "마침 점검"을 통과해 다음 단계로 넘깁니다.

## 절차

| 순서 | 하는 일 | 요청자 확인 |
| --- | --- | --- |
| 1 | 작업 기록 생성 및 시작 (메뉴 · 요청자 · 그릴 곳 · 작업 기준) | 없음 |
| 2 | 요청 글 · 요청 자료에서 요건을 뽑고 대상 화면을 짚음 | 없음 |
| 3 | 대상 화면을 읽음 | 없음 |
| 4 | 요건 목록을 정리하고 확인할 것을 적음 | 없음 |
| 5 | 요건 목록을 확인받음 (신규 메뉴면 메뉴 이름 · CID 체계도 함께 물음) | 받음. 2단계로 넘어갈지 함께 물음 |

### 1) 작업 기록 생성 및 시작

**순서**

1. **작업 기록을 만듭니다.** 요청을 받으면 먼저 `reference-rules/work-log.md`의 틀로 `work-logs/`에 작업 기록을 만듭니다.
2. **생성 시 항목을 기입합니다.** 누가 · 언제 · 무엇을 요청했는지 적습니다: 제목 · `status` · `requester` · `menu` · `figma` · `test` · `basis_start` · `started` · 본문 "요청" 절 · `이어서 작업할 곳:` 줄
   - 항목마다 적는 것은 `reference-rules/work-log.md` "항목마다 적는 법"을 따릅니다. 나머지 항목은 비워 두고, 그 표의 "기입되는 때"에 기입합니다.
   - 비워 둔 것(신규 메뉴의 `menu`, `figma`의 페이지)과 그릴 곳에 다른 UX가이드가 적용돼 있는 것은 절차 5번 "요건 목록을 확인받음"에서 답을 받습니다.

### 2) 요건을 뽑고 대상 화면을 짚음

> 초안 (확정 전).

요청 글과 요청 자료에서 요건을 뽑고, 요건마다 대상 화면을 짚어 작업 기록 "요건 목록" 절에 기입합니다.

**읽을 것**

| 읽을 것 | 무엇을 보나 |
| --- | --- |
| 요청 글과 요청 자료 (작업 기록 "요청" 절의 출처 · 링크로 찾음) | 무엇을 바꿔 달라는지 |
| IA `ia/ia-screens.csv` | 대상 화면의 CID와 짝 CID (`CID` · `짝 CID` 칸) |
| 정책 파일 머리말 (`policy/`) | 정책을 바꾸는 요건일 때만, 그 정책의 `cids`만 (순서 2). 정책 내용은 2단계에서 읽음 |
| 화면 MD (`screens/tobe/` · `screens/asis/`) | 모든 화면 MD에서 요청에 적힌 글자 · 대상 화면의 Common UX 번호 · 대상 화면의 CID가 나오는 곳과 그 요소의 디스크립션만 (순서 3). 대상 화면의 `screens/tobe/` 화면 MD 머리말 `figma` (순서 4 케이스) |
| `work-logs/`의 `status: 진행 중`인 작업 기록 | `menu` · `cids` (겹침 확인) |

**순서**

1. **요건을 뽑습니다.** 요청 글과 요청 자료에서 바뀌는 것을 하나씩 한 문장으로 적습니다. 요청 글과 요청 자료에 없는 요건은 만들지 않습니다. 요청 글과 요청 자료에 적혀 있지 않아 요건을 다 정할 수 없는 것(예: 무엇으로 바꿀지 값이 없음, 어느 화면인지 적혀 있지 않음)은 지어 채우지 않고 작업 기록 "확인할 것" 절에 "요청에서 생긴 물음"으로 기입합니다(절차 4번 순서 3의 6).
   - **1280 화면은 이 흐름의 작업 대상이 아닙니다.** 1280 화면은 1920 화면과 UX가 같고 UI만 1280이라, UX 버전은 없고 UI 버전만 있습니다. 1280 프레임은 손대지 않고 화면 MD에 옮기지 않습니다(`flow/3-design.md` 공통 4 "작업방 구성"). 요청에 1280 화면에 대한 것이 있으면 요건으로 뽑지 않고, 뽑지 않았다는 것을 보고에 한 줄로 알립니다.
2. **요건마다 대상 화면을 짚습니다.** 요건이 여러 화면에 걸치면 같은 번호로 화면마다 한 줄씩 씁니다.
   1. **대상 화면을 찾습니다.**

      | 요청 글 · 요청 자료 | 대상 화면 | 작업 대상 | 비고에 기입 |
      | --- | --- | --- | --- |
      | 화면이 적혀 있음 | IA에서 그 CID를 찾아 `화면 이름 (CID)`로 적음 | O | |
      | 화면이 없고, 정책을 바꾸는 요건임 (예: "Module 상태값에 Paused가 추가됨") | 그 정책 파일 머리말의 `cids`에 적힌 화면 | O | `정책 cids (정책 ID)` |
      | 화면이 없고, 어느 정책인지도 알 수 없음 | "(2단계에서 정책으로 찾음)" | 미정 | |

   2. **짝 화면을 넣습니다.** IA에 짝 CID가 있으면 짝 화면도 한 줄로 넣고, 요청 글 · 요청 자료로 가릴 수 있는 것만 적습니다. 화면을 읽어야 가릴 수 있는 것은 절차 4번 "요건 목록을 정리하고 확인할 것을 적음"에서 최종 판단합니다.

      | 요청 글 · 요청 자료 | 작업 대상 | 비고에 기입 |
      | --- | --- | --- |
      | 한쪽만 적혀 있음 (예: "T-IOS만") | X | `짝 화면 · 고치지 않음 (요청 글: T-IOS만)` |
      | T-IOS · L-IOS 둘 다 고치라고 적혀 있음 | O | `짝 화면 · 함께 고침 (요청 글)` |
      | 적혀 있지 않음 | 미정 | `짝 화면 · 읽고 가림` |

3. **이 변경이 함께 걸리는 다른 화면을 찾습니다.** 화면 MD(`screens/tobe/`, 그 화면의 To-Be 화면 MD가 없으면 `screens/asis/`)에서만 찾고, Figma · 정책서 · 다른 자료에서는 찾지 않습니다. 정책 · 기준데이터를 읽어야 나오는 화면(화면 MD의 정책 ID, 알럿 · 토스트 카탈로그의 사용 화면, 상태값 · 기준데이터 값으로 찾는 화면)은 여기서 찾지 않고 2단계에서 찾습니다. 순서 2에서 정책 `cids`로 대상 화면을 짚은 요건은 "해당 없음 (정책 cids로 짚음)"을 기입하고 4로 갑니다.
   1. **후보를 찾습니다.** 요건마다 해당하는 찾는 법으로 화면 MD를 모두 찾습니다. 하나도 없으면 "다른 화면 없음"을 기입하고 4로 갑니다.

      | 찾는 법 | 무엇으로 찾나 | 언제 |
      | --- | --- | --- |
      | 같은 글자 | 요청에 적힌 버튼명 · 문구 · 값이 나오는 화면 MD | 화면 글자가 바뀔 때 |
      | 같은 Common UX 규칙 | 대상 화면 MD에 적힌 Common UX 번호(예: `COMM-4-b`)가 나오는 다른 화면 MD | Common UX 요소 · 표기 기준이 바뀔 때 |
      | 호출 관계 | 대상 화면의 CID가 본문에 나오는 화면 MD(그 화면을 부르는 화면), 대상 화면 MD 본문에 나오는 CID(그 화면이 부르는 화면) | 팝업 · 이동 · 버튼 동작이 바뀔 때 |

   2. **후보마다 그 요소의 디스크립션을 읽고 가립니다.** 이름 · 번호 · CID가 같은 것만으로는 대상으로 넣지 않습니다. 그 요소가 화면에서 하는 일(디스크립션)이 이번 변경에 걸리는지 봅니다.

      | 디스크립션을 읽은 결과 | 기입 |
      | --- | --- |
      | 같은 요소이고 하는 일도 같음 | 요건 목록에 넣고 작업 대상 `O`, 비고에 `찾음 · 대상 (디스크립션 근거)` |
      | 이름만 같고 하는 일이 다름 | 요건 목록에 넣지 않음. 아래 "찾았지만 대상 아님"에 이유와 함께 |
      | 디스크립션만으로 가릴 수 없음 | 요건 목록에 넣고 작업 대상 `미정`, 비고에 `찾음 · 요청자 확인`. 절차 5번 "요건 목록을 확인받음"에서 물음 |

   3. **대상으로 가린 화면을 작업의 단위에 따라 나눕니다** (`reference-rules/work-log.md` "작업의 단위").

      | 대상으로 가린 화면 | 하는 일 |
      | --- | --- |
      | 이 작업과 같은 CID 체계 | 요건 목록에 그대로 둠 |
      | 다른 CID 체계 (메뉴 작업일 때) | 요건 목록에서 빼고 작업 기록 "영향 화면" 표에 기입. 반영 대기 항목은 지금 만들지 않고 완료 때 만듦(`reference-rules/pending-changes.md` 1절) |
      | 다른 CID 체계 (일괄 변경(메뉴 전반)일 때) | 요건 목록에 그대로 둠 |
4. **줄마다 케이스를 붙입니다.** `flow/README.md` "케이스"대로 붙입니다.

   | 대상 화면 | 케이스 |
   | --- | --- |
   | IA에 있고 `screens/tobe/` 화면 MD 머리말 `figma`에 작업방 섹션 링크가 있음 | 1 |
   | IA에 없는 새 화면. 대상 화면 칸에 "새 화면 (하는 일 한마디)"을 적고, CID 번호는 절차 4번 "요건 목록을 정리하고 확인할 것을 적음"에서 붙임 | 2 |
   | IA에 있고 `screens/tobe/` 화면 MD 머리말 `figma`가 비어 있거나, `screens/tobe/`에 화면 MD가 없음 | 3 |
5. **머리말 `cids`를 채웁니다.** 요건 목록에서 작업 대상이 `O`인 대상 화면의 CID를 적습니다. `미정`인 화면은 절차 4 · 5번에서 `O`가 되면 더하고, 새 화면은 번호를 붙인 뒤 더합니다.
6. **다른 작업과 겹치는지 봅니다.** 진행 중인 작업 기록 가운데 `menu` 또는 `cids`가 겹치는 것을 찾습니다. 없으면 "겹치는 작업 없음"을 기입합니다.

   | 찾은 결과 | 하는 일 |
   | --- | --- |
   | 진행 중인 작업의 요건 목록에 이번 요건 · 대상 화면이 **모두** 있음 (같은 요청) | 절차 3번으로 가지 않습니다. 그 작업 기록의 이름 · 요청자 · 지금 단계 · `이어서 작업할 곳:` 줄 · 남은 질문 대기를 요약해 보여 주고, 그 작업으로 이어 가게 합니다. 이번에 만든 작업 기록은 `status: 끝남`, 끝난 방식 `기존 작업으로 이어 감 (작업 기록 이름)`으로 닫습니다 |
   | 일부만 겹침 | 그 작업 기록 이름 · 요청자 · 지금 단계 · `이어서 작업할 곳:` 줄을 보고에 보여 주고 넘어갑니다. |

### 3) 대상 화면을 읽음

> 초안 (확정 전).

절차 2번에서 짚은 대상 화면이 지금 어떤지 끝까지 읽고, 읽은 화면을 작업 기록 "읽은 기존 화면" 절에 기입합니다. 읽으며 찾은 것은 절차 4번 "요건 목록을 정리하고 확인할 것을 적음"에서 적습니다.

**순서**

1. **읽을 화면을 정합니다.** 아래 "읽는 것" · "읽지 않는 것"대로 정합니다.
2. **케이스마다 읽습니다.** 아래 "케이스마다 읽는 것"대로 읽고, 케이스 3은 "케이스 3에서 더 하는 것"을 먼저 합니다.
3. **읽은 화면을 기입합니다.** 작업 기록 "읽은 기존 화면" 절에 적습니다(아래 "작업 기록에 쓰는 것"의 "읽은 기존 화면 틀").

**읽는 것**

- 요건 목록에서 작업 대상이 `O`인 화면과, `미정`이고 비고가 `짝 화면 · 읽고 가림`인 짝 화면
- 대상 화면을 호출하는 화면 · 대상 화면이 호출하는 화면, 디스크립션이 가리키는 화면. 무엇을 열고 어디로 가는지, 값의 범위가 거기 정의돼 있는지만 읽습니다.
- 대상 화면의 반영 대기 목록 (짝 CID 포함)

**읽지 않는 것**

- "찾았지만 대상 아님" · "영향 화면"의 화면. 절차 2번에서 가린 것으로 끝납니다.
- UX가이드 · 정책서 · 기준데이터. 2단계에서 읽습니다. 정책 파일은 절차 2번에서 머리말 `cids`만 봅니다.

**케이스마다 읽는 것**

| 케이스 | 읽는 것 |
| --- | --- |
| 1 | 대상 화면의 `screens/tobe/` 화면 MD 전부(T-IOS · L-IOS 각각)와 작업방 Figma의 그 화면 기획 프레임 |
| 2 | 새 화면이라 읽을 기존 화면이 없음. 요청 글 · 요청 자료와 같은 메뉴의 비슷한 기존 화면 MD(`screens/tobe/`)를 읽음 |
| 3 | 아래 "케이스 3에서 더 하는 것"대로 기존 작업방에서 **다시 옮긴** 화면 MD 전부(T-IOS · L-IOS 각각)와 **기획 프레임 안의 케이스 프레임**(기존 작업방에서는 `case`). 다시 옮겼으므로 Figma 기획 프레임의 디스크립션은 따로 읽지 않음 |

- 화면 MD의 반영 대기 목록이 예전 칸으로 적혀 있어도 `대기` 항목을 빠짐없이 읽습니다(`reference-rules/pending-changes.md` 6절).
- 요청자는 Figma 링크를 페이지 단위로 줍니다(기획 프레임 하나의 링크가 아님. 작업방 페이지는 `flow/3-design.md` 공통 4 "페이지", 기존 작업방은 메뉴 페이지). 그 페이지에서 대상 CID의 기획 프레임을 찾아 읽습니다. 케이스 3은 아래 "최신 화면 고르기"의 세로 바(2.1 2차 민트색)로 영역을 찾습니다. 찾은 기획 프레임 링크는 "읽은 기존 화면"의 Figma 링크 칸에 적습니다.
- 기존 작업방에서는 기획 프레임(오른쪽 패널이 붙은 너비 2252)과 그 안의 것만 읽습니다. 기획 프레임 밖의 섹션 · 프레임은 UI 화면일 수 있어 열지 않습니다(`CLAUDE.md` "늘 지키는 것").

**케이스 3에서 더 하는 것 (이행 기간)**

- **최신 화면 고르기:** 기존 작업방은 2.1 릴리즈를 두 영역에 나눠 둡니다. 세로 바는 페이지 왼쪽의 `진행상태-기획` 인스턴스입니다. 민트색(#40F3EE) 세로 바 = 2.1 2차, 녹색(#84CC16) 세로 바 = 2.1 1차. CID가 민트색 영역에 있으면 그것만, 녹색에만 있으면 녹색 화면을 읽습니다. 바 오른쪽, 바 길이 안의 화면이 그 영역이고, 바가 여러 열이면 화면 바로 왼쪽 바를 기준으로 합니다. Material Setup은 2차 페이지(`Material Setup Ⓛ_2.1(2차)`)만 봅니다.
- **읽기 전에 늘 다시 옮기기:** 화면 MD를 옮긴 뒤 기존 작업방 화면이 바뀌었을 수 있으므로, 케이스 3 대상 화면은 화면 MD가 있어도 읽기 전에 기존 작업방 기획 프레임에서 다시 옮깁니다(추출 도구 `tools/figma/extract-screen.js`, 틀 `templates/screen-asis.md`, 옮기는 곳 `screens/asis/{메뉴}/{CID}.md`).
  - 기획 프레임의 최신 영역만 옮깁니다. 글자 색은 옮기지 않습니다: 빨간 글씨는 검정 글씨로, 빨간 취소선은 검은 취소선(`~~글자~~`)으로, 검은 취소선은 그대로 `~~글자~~`로 둡니다.
  - **기준은 기존 작업방 원본입니다.** `screens/asis/` 화면 MD는 옮긴 뒤 고객 대응을 작업방 밖에서 하며 원본과 많이 달라졌을 수 있으므로, 예전 값을 지키지 않고 원본대로 다시 씁니다.
    - 기획 프레임은 최신 영역에서 CID 이름으로 다시 찾습니다(머리말 `figma`의 예전 링크가 없어진 프레임일 수 있음).
    - 머리말: 원본에서 읽을 수 있는 칸을 모두 원본대로 고칩니다. `figma`(찾은 기획 프레임 링크) · `figma_region` · `title` · `path` · `type` · `pair_cid` · `tl_relation`, 패널 화면 정보의 `version` · `date` · `author`. 원본에 없는 `client_mode` · `user_type` · `policies`는 그대로 둡니다(2단계에서 다시 확인).
    - 본문: 기존 화면(화면 글자 · 사용 컴포넌트 · 디스크립션 · 케이스)과 변경 이력(기존 작업방의 버전 메모)을 원본대로 다시 쓰고, 머리 문장의 옮긴 날 · 영역 · Ver을 고칩니다.
    - 반영 대기 목록만 원본에 없는 우리 기록이라 그대로 둡니다(아래 To-Be 화면 MD로 옮김).
  - `screens/asis/`에 화면 MD가 없는 CID는 새로 만듭니다.
  - 다시 옮겨 바뀐 곳이 있으면 "읽은 기존 화면"의 "읽은 것" 칸에 `다시 옮김 · 바뀐 곳 있음 (무엇)`을, 없으면 `다시 옮김 · 바뀐 곳 없음`을 기입합니다.
  - 다시 옮길 때 그 화면의 To-Be 화면 MD(`screens/tobe/{메뉴}/{CID}.md`)를 `templates/screen.md` 빈 틀로 만들고(이미 있으면 그 파일), asis 반영 대기 목록의 항목을 ID 그대로 모두 옮깁니다. asis 반영 대기 목록 위에는 "`screens/tobe/`로 옮김 (날짜)"를 남깁니다(`reference-rules/pending-changes.md` 6절).
  - 옮기며 찾은 고칠 점은 그 화면의 To-Be 화면 MD(`screens/tobe/`) 반영 대기 목록에 "점검 발견"으로 적습니다(ID는 그 목록의 가장 큰 번호에 이어 매김).
  - 옮긴 화면의 Module · Unit 이름과 Unit 구성(예: 폐기함 · Door 목록)을 `glossary/modules.csv` · `module-units.csv`에 대어 봅니다. 없는 이름(예전 이름)이거나 구성이 다르면(제조사에 따라 다른 Unit 포함) 위 "점검 발견"으로 적고, 3단계 절차 3번(용어 점검)에서 고칩니다.
  - 테스트로 할 때는 저장소의 화면 MD를 고치지 않고 작업 폴더에 옮깁니다.

### 4) 요건 목록을 정리하고 확인할 것을 적음

> 초안 (확정 전).

절차 2번 · 3번의 결과로 요건 목록을 다듬고, 요청자에게 보여 줄 것을 모두 준비합니다. 새로 읽지 않습니다. 물을 것은 절차 5번 "요건 목록을 확인받음"으로 넘깁니다.

**순서**

1. **짝 화면을 최종 판단합니다.** 비고가 `짝 화면 · 읽고 가림`인 줄을 절차 3번 "대상 화면을 읽음"에서 읽은 결과로 가려 작업 대상과 비고를 고칩니다. `O`가 된 화면은 머리말 `cids`에 더합니다.

   | 읽은 결과 | 작업 대상 | 비고에 기입 |
   | --- | --- | --- |
   | 두 화면에 같은 기능이 있음 | O | `짝 화면 · 함께 고침 (두 화면에 같은 기능)` |
   | 그 기능이 한쪽에만 있음 | X | `짝 화면 · 고치지 않음 (L-IOS에만 있는 기능)` |
   | 읽어도 가릴 수 없음 | 미정 (절차 5번에서) | `짝 화면 · 요청자 확인` |

2. **요건을 기존 화면에 비춰 다듬습니다.** 읽어 보니 요건이 가리키는 요소가 기존 화면에 없거나, 요청 글과 기존 화면이 다르게 말하면 요건 문장을 고치지 않고 "확인할 것"에 기입합니다. 요건마다 기존 화면에 이미 반영됐는지도 봅니다.

   - **이미 반영됨의 기준:** 요청한 내용이 화면 MD(`screens/tobe/`)에 있고, 그 화면을 고치는 진행 중인 작업 기록(`work-logs/`의 `status: 진행 중`, `cids`에 그 화면)이 없을 때만 이미 반영된 것으로 봅니다. 화면 MD에는 있지만 그 화면을 고치는 진행 중인 작업 기록이 있으면 다른 작업이 하다 만 것이므로, 절차 2번 순서 6 "다른 작업과 겹치는지"의 같은 요청으로 보고 그 작업으로 이어 가게 합니다.

   | 결과 | 하는 일 |
   | --- | --- |
   | **모든 요건이 이미 반영됨** | 절차 5번에서 "요청하신 내용은 이미 화면에 반영되어 있습니다(근거). 1단계에서 종료할까요, 아니면 더 바꿀 것을 알려 주시겠어요?"라고 묻습니다. 종료하면 2 ~ 4단계는 "해당 없음 (이미 반영됨)"으로 지나가고, 5단계 완료에서 끝난 방식 `반영 안 함 (이미 반영됨)`을 기입하고 닫습니다. 더 바꿀 것을 주면 요건 목록에 `추가`로 달고 이어 갑니다 |
   | **일부 요건만 이미 반영됨** | 그 요건 줄의 요청 상태를 `제거 (이미 반영됨, 근거)`, 작업 대상을 `X`로 바꾸고 나머지로 이어 갑니다. 절차 5번에서 보여 줍니다 |
3. **확인할 것을 적습니다.** 아래 여섯 가지를 작업 기록 "확인할 것" 절에 기입합니다. 정책에 관한 것은 2단계에서, 화면에 관한 것은 3단계 질문 대기로 넘깁니다.
   1. **기능 정의가 안 된 요소:** 화면에 그려져 있는데 디스크립션에 동작이 없는 것 (예: [Refresh]에 번호 · 설명이 없음, 정렬 아이콘이 있는데 기본 정렬 기준이 없음, 값이 없을 때 무엇을 보여 주는지 없음)
   2. **Alert · Confirm 보완 필요 지점 (안전 장치):** 잘못 누르면 되돌리기 어려운데 디스크립션에 다시 묻는 Alert · Confirm이 적혀 있지 않은 것 (예: [Delete]를 누르면 바로 지워지는지 없음, 편집 중 닫을 때 묻는지 없음). 디스크립션에 없다는 것만 적고, 보완이 필요한지 · 어떤 알럿인지는 판단하지 않습니다. 요건의 진행 경로가 2단계를 지나가면 2단계에서 알럿 카탈로그 · 정책과 대조하고, 지나가지 않으면 3단계 질문 대기로 넘깁니다. 대상 화면을 끝까지 읽는 것은 1단계뿐이라, 읽으며 본 빈 곳을 2단계 대조로 넘기려고 둔 것입니다
   3. **IA와 화면이 다른 곳:** CID, 경로, 짝 화면
   4. **IA에 없는데 새로 필요한 화면:** 요건 목록에 새 화면 줄로 넣고 순서 4에서 번호를 붙임
   5. **반영 대기 목록에 `대기 (확인 필요)`로 남은 항목:** 무엇으로 바꿀지 정해지지 않은 것. 반영할지 묻는 대상이 아니라 질문으로 넘김
   6. **요청에서 생긴 물음:** 절차 2번 순서 1에서 요청 글 · 요청 자료로 알 수 없어 넘긴 것, 이 표의 순서 2에서 기존 화면과 맞지 않아 넘긴 것
4. **새 화면에 CID 번호를 붙입니다.** 요건 목록의 "새 화면" 줄마다 Claude가 번호를 붙여 대상 화면 칸을 고칩니다. 절차 5번에서 보여 주고, 완료(5단계) 때 한번에 확정합니다.
   - 접두어(T-IOS `TI` · L-IOS `LI`), 접미어(`-P` Popup · `-T` Tab), 같은 메뉴의 번호 순서를 따릅니다. 짝 화면이 있으면 짝 CID도 함께 붙입니다.
   - 근거(어느 화면에서 열리는지, 왜 따로 화면이 필요한지)를 비고에 적습니다.
   - 신규 메뉴면 메뉴 이름(영어)과 CID 체계(메뉴 코드 세 글자, IA의 기존 메뉴 코드와 겹치지 않게)를 Claude가 제안해 두고 그 체계로 붙입니다. 제안은 절차 5번에서 함께 묻습니다.
   - 새 CID는 작업 기록에만 적습니다. IA(`ia/ia-screens.csv`)에는 5단계에서 넣습니다(`flow/5-done.md` 절차 2번 순서 1).
   - 머리말 `cids`에 새 CID를 더합니다.
5. **이번에 반영할 반영 대기 항목 후보를 적습니다.** 대상 화면(짝 CID 포함)의 반영 대기 목록에서 `대기` 항목을 근거가 같은 것끼리 묶어 작업 기록 "이번에 반영할 반영 대기 항목" 절에 적습니다(아래 "이번에 반영할 반영 대기 항목 틀"). 반영할지는 절차 5번에서 묻습니다. `대기 (확인 필요)`는 여기에 넣지 않고 순서 3의 확인할 것으로 넘깁니다. 그 화면 케이스의 규칙과 부딪혀 반영할 수 없는 항목(예: 빈 번호를 채우는 "번호 정리", 케이스 1 · 3은 빈 번호를 그대로 둠)은 후보에 넣지 않고, 묻지 않고 그 화면 MD에서 `제외 (날짜, 케이스 N 규칙과 부딪힘: 무엇)`으로 바꿉니다. 요청자에게 보여 주지 않습니다(테스트로 할 때는 바꾸지 않음).
6. **요건마다 경로 분기 기준을 가르고 지나가는 단계를 적습니다.** 요건 번호마다 아래 경로 분기 기준 여덟 가운데 하나를 붙이고, 작업 기록 "요건별 진행 경로" 절에 기입합니다.

   | # | 경로 분기 기준 | 판단 신호 | 예 (기존 작업방 Revision History 등) | 2단계에서 읽는 강도 | 지나가는 단계 |
   | --- | --- | --- | --- | --- | --- |
   | 1 | 글자 · 표기만 | 워딩 · 대소문자 · 오타 · 라벨이 바뀜. 정책과 상관없음 | 워딩 수정 "Total → Total Samples", 라벨 "Standard / Custom" | 가볍게 | 1 → 2 → 3 → 4 → 5 |
   | 2 | 화면 구성이 바뀜 | 요소가 생기거나 없어지거나, 배치 · 표현이 바뀜. 하는 일은 그대로 | PD-0004 [Next] 제거, Capacity 항목 제거, 테이블 → 카드 형태, 간격 재조정 | 그 요소만 | 1 → 2 → 3 → 4 → 5 |
   | 3 | 동작 · 조건 · 값 · 순서가 바뀜 | 활성 조건, 저장 범위, 계산, 데이터 처리, 프로세스 순서가 바뀜. 디스크립션에 정책을 반영하는 것, 기능을 다른 화면으로 옮기는 것도 여기 | PD-0002 SMTP [Save] 범위, Batch ID 생성 정책 수정, Run 폐기물 확인 단계 추가, 재고 산출 정책 디스크립션 반영, Language 설정을 Profile로 이관 | 정책 전부 | 1 → 2 → 3 → 4 → 5 |
   | 4 | 장비 · 알럿 · 권한 · 상태값에 닿음 | 장비 동작, 상태값이 생기거나 없어지거나 뜻이 바뀜, Alert · Confirm, User Type · L-IOS Client Mode | Module 상태값에 Paused 추가, Door Closed 제거, 트롤리 감지 실패 알림, 모드별 메뉴 접근 | 정책 전부 + 장비 · 알럿 · 권한 | 1 → 2 → 3 → 4 → 5 |
   | 5 | 공통 기준을 화면에 맞춤 | 표기 · 정렬 규칙, Common UX 컴포넌트, 용어 · 상태값의 이름이 바뀌어 화면을 맞춤 | 소모품/시약 표기 및 정렬 기준 변경 반영, 대소문자 "spare caps → Spare Caps", 명칭 변경 "Requirements for Run Completion → Inventory status" | 기준 문서 | 1 → 2 → 3 → 4 → 5 |
   | 6 | 화면이 생기거나 없어짐 | IA에 없는 화면이 필요함(케이스 2), 또는 화면(CID) 자체가 없어짐 | View Trolley Info 신규, Run Report 신규, Run-time Info Popup 제거 | 정책 전부 | 1 → 2 → 3 (새 화면은 구상부터, 없어지는 화면은 폐기 표시) → 4 → 5 (IA 반영) |
   | 7 | 정책만 바뀜 | 규칙은 바뀌지만 화면에 보이는 것이 그대로 | 조합 검사 가능 여부 | 정책 전부 | 1 → 2 → 4 (UX 확정) → 5 (3 해당 없음) [초안 2026-11-17, 다시 검토] |
   | 8 | 옮겨 다시 그림 (케이스 3) | **요건 목록에서 케이스가 3인 줄.** 바꾸는 요건 없이 기존 작업방의 화면을 작업방에 새 규칙 · Common UX · 정리한 정책으로 다시 그림 | Event History를 작업방 새 페이지로 옮김, 기존 메뉴 이행 | 케이스 3 (다시 그리기) | 1 → 2 → 3 → 4 → 5 |

   거의 모든 요건이 1 ~ 5단계를 다 지나갑니다. 경로 분기 기준은 단계를 건너뛰게 하기보다 **2단계에서 얼마나 깊이 읽는지**를 정합니다. 강도마다 읽는 것은 `flow/2-evidence.md` "경로 분기 기준마다 읽는 것"에 있습니다.

   **가르는 규칙**
   - **한 요건에는 기준 하나입니다.** 여러 기준이 섞이면 요건을 나눕니다. 예: "Module 상태값에 Paused 추가 + Door Control 버튼 UI 변경" → 요건 둘(4번 / 2번)
   - **겉모습보다 이어진 것을 봅니다.** 1 · 2번이어도 그 요소가 장비 동작 · 상태값 · 알럿 · 권한과 이어져 있으면(절차 3번에서 읽은 디스크립션으로 봄) 4번으로 가릅니다.
   - **근거가 정책이면 3번입니다.** 글자 · 디스크립션만 바뀌어도 정책을 디스크립션에 반영하는 것이면 1번이 아니라 3번으로 가릅니다.
   - **새 요소의 값이 어디서 오는지 봅니다.** 2번이어도 새 요소에 보여 줄 값이 정책 · 기준데이터에서 오면(연결 · 계산 · 여러 건 처리 등) 3번으로 가릅니다. 예: Event 상세의 Effect 항목은 Event Code에 연결된 Scenario Code의 설명을 여러 건이면 줄을 바꿔 보여 주므로 3번
   - **기능을 옮기면 3번입니다.** 옮겨 가는 화면과 옮겨 오는 화면을 모두 대상 화면으로 적습니다.
   - **상태값은 이름 · 표기만 바뀌면 5번, 값이 생기거나 없어지거나 뜻이 바뀌면 4번입니다.**
   - **7번은 1단계에서 확정하지 않습니다.** 화면에 드러나는지는 정책을 읽어야 알 수 있으므로 3번으로 가르고 근거에 `정책만일 수 있음`을 적습니다. 2단계에서 정책을 읽은 뒤 7번으로 바꿉니다.
   - **케이스가 3이면 8번입니다.** 요건 목록에서 케이스가 3인 줄의 요건(기존 화면을 옮겨 다시 그림)은 다른 판단 신호를 보지 않고 8로 가릅니다.
     - 케이스 3 화면에 바꾸는 것(요소 추가 · 값 변경 등)도 함께 요청됐으면 요건을 둘로 나눕니다. 옮기는 요건은 8, 바꾸는 요건은 그 화면 줄도 케이스 3이지만 1 ~ 7 가운데서 가릅니다. 예: "Event History를 옮기면서 Effect 항목 추가" → 요건 1 옮김(8) / 요건 2 Effect 추가(3)
     - 8은 2단계에서 그 화면에 걸린 정책 · 기준 자료와 알럿을 읽고, 기존 화면이 지금 정책과 다른 곳을 찾습니다. UX가이드 · 용어는 3단계에서 그리며 읽습니다.
     - 문구는 `안 바뀜`, UI 작업은 `대상 아님`을 기본으로 적고, 다시 그리며 바뀐 곳이 생기면 4단계 UX 확정 때 다시 정합니다.
   - **애매하면 더 무거운 쪽으로 가르고** 그렇게 가른 이유를 근거에 적습니다(헌법 최상위 원칙). 가벼운 쪽으로 바꾸는 것은 절차 5번에서 요청자가 정합니다.
   - 작업의 단위(메뉴 하나 / 일괄 변경(메뉴 전반))는 경로 분기 기준과 따로 가릅니다(`reference-rules/work-log.md` "작업의 단위").
   - 경로 분기 기준 말고 아래 둘도 요건마다 기입합니다. 단계를 건너뛰게 하지 않고 그 단계 안의 일만 더하거나 뺍니다.

     | 칸 | 답 | 달라지는 일 |
     | --- | --- | --- |
     | 문구 | 바뀜 / 안 바뀜 | 바뀌면 언어셋을 맞춤 |
     | UI 작업 | 대상 / 대상 아님 | UI팀이 작업해야 하는 요건인지. 배치 · 요소 · 화면 표기 글자가 바뀌면 `대상`, 디스크립션만이면 `대상 아님`. 1단계에서 적는 값은 화면을 그리기 전의 임시 값이고 4단계에서 요청자에게 확인받아 확정함(`flow/4-revise-verify.md` 절차 3번 "UX 확정을 기입함" 순서 3) |

   - **작업이 지나가는 단계:** 요건 하나라도 그 단계를 지나가면 작업은 그 단계를 지나갑니다. 모든 요건이 "해당 없음"인 단계는 "해당 없음 (이유)"로 지나갑니다. 그 단계 안에서는 그 단계를 지나가는 요건만 다룹니다.
   - **요청자가 바꿀 수 있습니다.** 흐름에 대한 판단(경로 분기 기준 · 지나가는 단계 · 문구 · UI 작업)은 Claude가 가른 안이고, 요청자가 바꿀 수 있습니다. 절차 5번 "요건 목록을 확인받음"에서도, 그 뒤 어느 단계에서도 됩니다.
     - **더해 달라고 하면 더합니다.** 요청자가 필요하다고 해서 단계나 일을 더해 달라고 하면(예: "이 요건도 2단계에서 정책을 봐 줘") 묻지 않고 더합니다.
     - **빼 달라고 하면** 가벼운 쪽으로 바꾸고, 빼서 놓칠 수 있는 것(예: 장비 상태값에 닿는 요건의 정책 대조)이 있으면 그것만 한 줄로 알린 뒤 요청자의 답대로 합니다.
     - 바꾼 것은 "요건별 진행 경로"의 그 칸에 `바뀜 (날짜, 요청자, 이유)`로 기입하고, Claude가 처음 가른 안은 지우지 않고 취소선으로 남깁니다. 작업이 지나가는 단계도 다시 적습니다.

7. **절차 5번에서 물을 것을 모읍니다.** 작업 대상이 `미정`인 줄(짝 화면 · 찾은 화면), 신규 메뉴 이름 · CID 체계, 비어 있는 그릴 곳 페이지 · 그릴 곳에 적용된 다른 UX가이드, 반영 대기 항목 후보, 요건별 진행 경로(경로 분기 기준 · 지나가는 단계는 보여 주고, `요청자 확인`인 칸은 확인받음), 이미 반영된 요건(모두면 1단계에서 종료할지 묻고, 일부면 `제거 (이미 반영됨)`으로 바꾼 것을 보여 줌).

### 5) 요건 목록을 확인받음

> 초안 (확정 전).

절차 4번 순서 7에서 모은 것을 **한 번에** 보여 주고 답을 받습니다. 1단계의 정해진 확인은 여기 한 번입니다(예외 질문은 `flow/README.md` "단계를 지나는 규칙" 9). 작업 기록을 다시 읽고, 아래 "보여 줄 것" · "물을 것"을 `reference-rules/work-log.md` "요청자에게 보여 주는 법"의 모양으로 씁니다.

**보여 줄 것** (바꿀 곳이 있으면 말해 달라고 함)

| 보여 줄 것 | 작업 기록의 절 |
| --- | --- |
| 요건 목록 (대상 화면 · 케이스 · 짝 화면 판단 · 새 화면 CID 번호) | "요건 목록" |
| 요건별 진행 경로 (경로 분기 기준 · 지나가는 단계 · 문구 · UI 작업)와 작업이 지나가는 단계 | "요건별 진행 경로" |
| 찾았지만 대상 아님 | "찾았지만 대상 아님" (요건 목록 아래) |
| 영향 화면 (비어 있어도 따로 보여 줌) | "영향 화면" (요건 목록 아래) |
| 확인할 것과 넘기는 곳 (2단계 / 3단계 질문 대기) | "확인할 것" |
| 일부 요건이 이미 반영돼 `제거 (이미 반영됨)`으로 바꾼 것 | "요건 목록" |
| 이번에 반영할 반영 대기 항목 (묶음마다 질문 6으로 물음) | "이번에 반영할 반영 대기 항목" |

**물을 것** (해당할 때만, 이 순서대로)

| # | 언제 | 묻는 문장 | 고르는 것 |
| --- | --- | --- | --- |
| 1 | 모든 요건이 이미 반영됨 | "요청하신 내용은 이미 화면에 반영되어 있습니다(근거). 1단계에서 종료할까요, 아니면 더 바꿀 것을 알려 주시겠어요?" | 종료 / 더 바꿀 것 있음 |
| 2 | 신규 메뉴 | "새 메뉴의 이름과 CID 체계를 아래와 같이 제안합니다." 메뉴 이름(영어)과 CID 체계를 보여 줌 | 항목마다 이대로 / 직접 적음 |
| 3 | 그릴 곳 페이지가 비어 있거나, 그릴 곳에 다른 UX가이드가 적용돼 있음 | "작업방의 어느 페이지에 그릴까요?" / "그릴 곳에 ○○ 가이드가 적용돼 있습니다. 어느 가이드로 그릴까요?" | 페이지 이름 / 가이드 |
| 4 | 작업 대상이 `미정`이고 비고가 `짝 화면 · 요청자 확인`인 줄 | "짝 화면 ○○도 같게 고칠까요?" 짝 CID와 넣을 변경을 보여 줌 | 함께 고침 / 이 화면만 |
| 5 | 작업 대상이 `미정`이고 비고가 `찾음 · 요청자 확인`인 줄 | "○○ 화면의 ○○도 같은 요소로 보입니다(디스크립션 근거). 이번 작업에 넣을까요?" | 넣음 / 넣지 않음 |
| 6 | 이번에 반영할 반영 대기 항목 후보가 있음 | "이번 작업 화면의 반영 대기 항목입니다. 어디까지 반영할지 골라 주세요." 근거가 같은 것끼리 묶어 보여 줌 | 묶음마다 반영 / 이번엔 안 함 |
| 7 | 늘 (마지막) | "위 요건 목록과 흐름대로 진행할까요?" | 이대로 진행 / 고칠 곳 있음 |

- 1번에서 종료를 고르면 2 ~ 7번은 묻지 않습니다.
- 위 표에 없는 질문을 늘 묻는 질문으로 더하지 않습니다. 케이스 · 경로 분기 기준 · 짝 화면처럼 이 단계에서 Claude가 가르는 것은 묻지 않고 가르고, 근거로 가를 수 없을 때만 작업 기록 "모아 둔 질문"에 적어 위 질문 다음에 함께 묻습니다(`flow/README.md` "단계를 지나는 규칙" 9). 뒤 단계에서 풀 물음은 "확인할 것"에 적어 넘깁니다.
- 묻는 문장에는 "줄", "맞는지"처럼 무엇을 가리키는지 흐린 말을 쓰지 않고, 확인하는 대상의 이름(CID · 화면 이름 · 항목 ID)을 그대로 씁니다.

**답을 받은 뒤**

1. 작업 기록 "요청자 확인" 표에 날짜 · `1단계` · 확인한 것 · 요청자 답을 기입합니다.
2. 답대로 고칩니다.

   | 답 | 고치는 것 |
   | --- | --- |
   | 종료 | 2 ~ 4단계 "해당 없음 (이미 반영됨)", 5단계 완료에서 `반영 안 함 (이미 반영됨)`으로 닫음 |
   | 더 바꿀 것 · 고칠 곳 있음 | 요건 목록에 `추가 · 변경 · 제거 (날짜, 요청자, 이유)`로 달고, 그 요건만 절차 2 ~ 4번을 다시 한 뒤 이 순서로 돌아옴 |
   | 신규 메뉴 이름 · CID 체계 | `menu` · `cid_system`에 적음. 제안과 다르면 붙인 새 화면 번호를 고침 |
   | 짝 화면 · 찾은 화면 | 요건 목록의 작업 대상을 `O` / `X`로, 비고를 답대로 고침(`바뀜 (날짜, 요청자)`). `O`가 된 화면은 머리말 `cids`에 더함. 그 화면의 반영 대기 `대기` 항목은 절차 4번 순서 5대로 "이번에 반영할 반영 대기 항목"에 더하고(케이스 규칙과 부딪히는 항목은 제외), 1단계를 마치기 전에 그 항목만 질문 6으로 한 번 더 물음 |
   | 반영 대기 "반영" | 그 항목의 화면 MD 상태를 `작업 중 (작업 기록 이름)`으로 바꿈(`reference-rules/pending-changes.md` 4절). "이번엔 안 함"은 `대기` 그대로. 요청자가 제외한다고 말한 항목만 `제외 (날짜, 이유)`로 바꿈 |

3. 작업 기록 "단계" 표의 1단계 "마침 점검" 칸에 `요청자 확인 (날짜)`를 적고, `이어서 작업할 곳:` 줄을 작업이 지나가는 다음 단계로 고칩니다. 다음 단계로 넘어갈지는 이 절차의 질문과 함께 묻습니다(`flow/README.md` "단계 전환").

**영향 화면** (작업 기록 "요건 목록" 절 아래 `### 영향 화면`)

| 화면 (CID) | 작성자 | 영향 (화면 변경 / 디스크립션 변경 / 확인 필요) | 무엇 때문 (요건 번호 · 정책) | 찾은 곳 (1단계 글자 · Common UX 번호 · 호출 관계 / 2단계 정책) | 처리 (반영 대기 항목 ID) |
| --- | --- | --- | --- | --- | --- |
| (예) 다른 메뉴의 화면 이름 (CID) | (그 화면 작성자) | 디스크립션 변경 | 요건 3 ([Export] 이름) | 1단계 글자 · 디스크립션 | 완료 때 만듦 |

- **요청 상태**는 그 요건이 처음부터 있었는지, 도중에 바뀌었는지입니다. 줄은 지우지 않고 값만 바꿉니다.

  | 값 | 뜻 |
  | --- | --- |
  | `최초` | 요청을 받을 때 요청 글 · 요청 자료에 있던 요건 |
  | `추가 (날짜, 누가, 왜)` | 작업 도중 더 들어온 요건 |
  | `변경 (날짜, 누가, 왜)` | 내용이 바뀐 요건 |
  | `제거 (날짜, 누가, 왜)` | 빠진 요건. 이미 반영돼 빠지면 `제거 (이미 반영됨, 근거)` |

- **작업 대상**은 그 화면 줄을 이번 작업에서 고치거나 그리는지입니다.

  | 값 | 뜻 |
  | --- | --- |
  | `O` | 이번 작업에서 고치거나 그림 |
  | `X` | 이번 작업에서 고치지 않음 (짝 화면 · 고치지 않음, 요청 상태가 `제거`인 줄 등) |
  | `미정` | 아직 정하지 않음. 절차 4번(읽고 가림) 또는 절차 5번(요청자 확인)에서 `O` / `X`로 바꿈 |

- 화면은 어느 표에서든 `화면 이름 (CID)` 순서로 적습니다(예: `Event History Detail (TI-EVT-01-P)`).
- 비고에는 작업 대상을 그렇게 가린 근거를 적습니다.
- "찾았지만 대상 아님"은 이름만 같고 하는 일이 다른 후보를 왜 넣지 않았는지 남기는 표입니다. 찾은 후보가 없으면 "다른 화면 없음"만 기입합니다.
- "영향 화면"은 이 작업에 넣지 않지만 맞춰 고쳐야 할 다른 메뉴의 화면을 모으는 표입니다. 1단계에서 글자 · 디스크립션으로 찾은 것을 적고, 2단계에서 정책으로 찾은 것을 같은 표에 더합니다. 반영 대기 항목은 완료 때 이 표를 보고 만듭니다(`reference-rules/pending-changes.md` 1절). 한 화면은 "찾았지만 대상 아님"과 "영향 화면" 가운데 한 곳에만 적습니다.

**이번에 반영할 반영 대기 항목 틀** (작업 기록 "이번에 반영할 반영 대기 항목" 절에 이 표를 씀)

| --- | --- | --- | --- | --- | --- |
| 1 표기 기준 (`archive/glossary/review-v0.md`) | Event History (TI-EVT-P) | TI-EVT-P R05 | Expiration date Status, Under 30 Day | 대소문자 통일, Under 30 days | |

- 항목은 대상 화면(작업 대상이 `O`인 화면과 그 짝 CID)의 반영 대기 목록에서 상태가 `대기`인 것만 옮깁니다. 칸의 값은 그 화면 MD의 반영 대기 목록에 적힌 그대로 씁니다.
- 상태 괄호 안에 이유가 적힌 `대기` 항목(예: `대기 (이 화면에 없는 글자, 2026-11-06 이번엔 안 함)`)도 다른 `대기` 항목과 같이 옮겨 묻습니다. 이번에 반영하지 않으면 `대기` 그대로 두고, 요청자가 제외한다고 말할 때만 `제외 (날짜, 이유)`로 바꿉니다(케이스 규칙과 부딪히는 항목은 위 절차 4번 순서 5에서 이미 제외함).
- 근거가 같은 항목은 같은 묶음 번호로 묶습니다. 절차 5번 질문 6은 묶음마다 묻습니다.
- "반영 / 이번엔 안 함"은 비워 두고, 절차 5번에서 답을 받은 뒤 채웁니다. "반영"으로 고른 항목은 그 화면 MD에서 상태를 `작업 중 (작업 기록 이름)`으로 바꿉니다(`reference-rules/pending-changes.md` 4절). 테스트로 할 때는 바꾸지 않습니다.
- 옮길 `대기` 항목이 없으면 "대상 화면에 `대기` 항목 없음"을 기입합니다.

## 마침 점검

다음 단계로 넘어가기 전에 모두 통과해야 합니다(절차 5번 "답을 받은 뒤" 3).

- 요청자 확인의 답을 받았고, 답대로 요건 목록 · 요건별 진행 경로 · 머리말을 고쳤음
- 요건 목록의 작업 대상에 `미정`이 남아 있지 않음
- 이번에 반영할 반영 대기 항목마다 반영 / 이번엔 안 함이 적혀 있음
