# 1. 시작 · 요건 정의

> 초안 · v0.10 (커밋 전)

**목적:** 요청을 받아 작업 기록을 열고, 요청을 요건 목록으로 정리해 대상 화면 · 케이스 · 경로 분기 기준을 정하는 단계입니다. 예전 0단계(시작)와 1단계(요건 정의)를 합쳤습니다.

**목표:** 요건 목록을 요청자에게 확인받아 작업 대상에 `미정`이 남지 않게 하고, 아래 "마침 점검"을 통과해 다음 단계로 넘깁니다.

## 절차

| 순서 | 하는 일 | 요청자 확인 |
| --- | --- | --- |
| 1 | 작업 기록 생성 및 시작 (메뉴 · 요청자 · 그릴 곳 · 작업 기준) | 없음 |
| 2 | 요청 글 · 공유 파일에서 요건을 뽑고 대상 화면을 짚음 | 없음 |
| 3 | 대상 화면을 읽음 | 없음 |
| 4 | 요건 목록을 정리하고 뒤 단계용 확인 항목을 적음 | 없음 |
| 5 | 요건 목록을 확인받음 (신규 메뉴면 메뉴 이름 · CID 체계도 함께 물음) | 받음. 2단계로 넘어갈지 함께 물음 |

- **절차 하나를 끝낼 때마다 작업 기록 `이어서 작업할 곳:` 줄을 고칩니다.** 한 일, 다음 절차, 다시 읽을 곳(단계 문서의 절차 · 작업 기록의 절)을 적습니다(예: `이어서 작업할 곳: 1단계 · 절차 3 대상 화면 읽기 끝냄, 절차 4 할 차례 (다시 읽을 곳: 1단계 절차 4 / 작업 기록 "요건 목록" · "읽은 화면")`). 절차 5에서 질문을 보낸 뒤에도 고칩니다(예: `1단계 · 요건 목록 확인 질문 보냄, 답 기다림 (다시 읽을 곳: 1단계 절차 5 "답을 받은 뒤" / 작업 기록 "요청자 확인")`). 끊기면 다음 Claude가 이 줄부터 이어 갑니다(`reference-rules/work-log.md` "끊긴 작업 이어 가기").

### 1) 작업 기록 생성 및 시작

**순서**

1. **작업 기록을 만듭니다.** 요청을 받으면 먼저 `reference-rules/work-log.md` "틀"로 `work-logs/`에 작업 기록을 만듭니다.
2. **만들 때 적는 항목을 기입합니다.** 누가 · 언제 · 무엇을 요청했는지 적습니다: 제목 · `status` · `requester` · `menu` · `figma` · `test` · `basis_start` · `started` · 본문 "요청" 절 · `이어서 작업할 곳:` 줄
   - 항목마다 적는 것은 `reference-rules/work-log.md` "항목마다 적는 법"을 따릅니다. 나머지 항목은 비워 두고, 그 표의 "기입되는 때"에 기입합니다.
   - 비워 둔 것(신규 메뉴의 `menu`, `figma`의 페이지)은 절차 5번 "요건 목록을 확인받음"에서 답을 받습니다.

### 2) 요건을 뽑고 대상 화면을 짚음


요청 글과 공유 파일에서 요건을 뽑고, 요건마다 대상 화면을 짚어 작업 기록 "요건 목록" 절에 기입합니다.

**읽을 것**

| 읽을 것 | 무엇을 보나 |
| --- | --- |
| 요청 글과 공유 파일 (작업 기록 "요청" 절의 출처 · 링크로 찾음) | 무엇을 바꿔 달라는지 |
| IA `ia/ia-screens.csv` | 대상 화면의 CID와 짝 CID (`CID` · `짝 CID` 칸) |
| 정책 파일 머리말 (`policy/`) | 정책을 바꾸는 요건일 때만, 그 정책의 `cids`만 (순서 2). 정책 내용은 2단계에서 읽음 |
| 화면 MD (`screens/tobe/` · `screens/asis/`) | 모든 화면 MD에서 요청에 적힌 글자 · 대상 화면의 Common UX 번호 · 대상 화면의 CID가 나오는 곳과 그 요소의 디스크립션만 (순서 3). 대상 화면의 `screens/tobe/` 화면 MD 머리말 `figma` (순서 4 케이스) |
| `work-logs/`의 `status: 진행 중`인 작업 기록 | `menu` · `cids` (겹침 확인) |

**순서**

1. **요건을 뽑습니다.** 요청 글과 공유 파일에서 바뀌는 것을 하나씩 한 문장으로 적습니다. 요청 글과 공유 파일에 없는 요건은 만들지 않습니다. 요청 글과 공유 파일에 적혀 있지 않아 요건을 다 정할 수 없는 것(예: 무엇으로 바꿀지 값이 없음, 어느 화면인지 적혀 있지 않음)은 지어 채우지 않고 작업 기록 "요청자 확인"에 적어 절차 5번에서 묻습니다(절차 4번 순서 3 "1단계에서 풂").
   - **1280 화면은 이 흐름의 작업 대상이 아닙니다.** 1280 화면은 1920 화면과 UX가 같고 UI만 1280이라, UX 버전은 없고 UI 버전만 있습니다. 1280 프레임은 손대지 않고 화면 MD에 옮기지 않습니다(`flow/3-design.md` 공통 4 "작업방 구성"). 요청에 1280 화면에 대한 것이 있으면 요건으로 뽑지 않고, 뽑지 않았다는 것을 보고에 한 줄로 알립니다.
2. **요건마다 대상 화면을 짚습니다.** 요건마다 "요건 목록"에 요건 묶음을 하나 만들고(아래 "요건 목록 틀"), 그 요건의 대상 화면 표에 화면마다 한 줄씩 씁니다.
   1. **대상 화면을 찾습니다.**

      | 요청 글 · 공유 파일 | 대상 화면 | 작업 대상 | 근거에 기입 |
      | --- | --- | --- | --- |
      | 화면이 적혀 있음 | IA에서 그 CID를 찾아 `화면 이름 (CID)`로 적음 | O | |
      | 화면이 없고, 정책을 바꾸는 요건임 (예: "Module 상태값에 Paused가 추가됨") | 그 정책 파일 머리말의 `cids`에 적힌 화면 | O | `정책 cids (정책 ID)` |
      | 화면이 없고, 어느 정책인지도 알 수 없음 | "(2단계에서 정책으로 찾음)" | 미정 | |

   2. **짝 화면을 넣습니다.** IA에 짝 CID가 있으면 짝 화면도 한 줄로 넣고, 요청 글 · 공유 파일로 가릴 수 있는 것만 적습니다. 화면을 읽어야 가릴 수 있는 것은 절차 4번 "요건 목록을 정리하고 뒤 단계용 확인 항목을 적음"에서 최종 판단합니다.

      | 요청 글 · 공유 파일 | 작업 대상 | 근거에 기입 |
      | --- | --- | --- |
      | 한쪽만 적혀 있음 (예: "T-IOS만") | X | `짝 화면 · 고치지 않음 (요청 글: T-IOS만)` |
      | T-IOS · L-IOS 둘 다 고치라고 적혀 있음 | O | `짝 화면 · 함께 고침 (요청 글)` |
      | 적혀 있지 않음 | 미정 (절차 3번에서 읽고 절차 4번에서 가림) | |

3. **이 변경이 함께 걸리는 다른 화면을 찾습니다.** 화면 MD(`screens/tobe/`, 그 화면의 To-Be 화면 MD가 없으면 `screens/asis/`)에서만 찾고, Figma · 정책서 · 다른 자료에서는 찾지 않습니다. 정책 · 기준데이터를 읽어야 나오는 화면(화면 MD의 정책 ID, Alert · Toast 카탈로그의 사용 화면, 상태값 · 기준데이터 값으로 찾는 화면)은 여기서 찾지 않고 2단계에서 찾습니다. 순서 2에서 정책 `cids`로 대상 화면을 짚은 요건은 "해당 없음 (정책 cids로 짚음)"을 기입하고 4로 갑니다.
   1. **후보를 찾습니다.** 요건마다 해당하는 찾는 법으로 화면 MD를 모두 찾습니다. 하나도 없으면 "다른 화면 없음"을 기입하고 4로 갑니다.

      | 찾는 법 | 무엇으로 찾나 | 언제 |
      | --- | --- | --- |
      | 같은 글자 | 요청에 적힌 버튼명 · 문구 · 값이 나오는 화면 MD | 화면 글자가 바뀔 때 |
      | 같은 Common UX 규칙 | 대상 화면 MD에 적힌 Common UX 번호(예: `COMM-4-b`)가 나오는 다른 화면 MD | Common UX 요소 · 표기 기준이 바뀔 때 |
      | 호출 관계 | 대상 화면의 CID가 본문에 나오는 화면 MD(그 화면을 부르는 화면), 대상 화면 MD 본문에 나오는 CID(그 화면이 부르는 화면) | Popup · 이동 · 버튼 동작이 바뀔 때 |

   2. **후보마다 그 요소의 디스크립션을 읽고 가립니다.** 이름 · 번호 · CID가 같은 것만으로는 대상으로 넣지 않습니다. 그 요소가 화면에서 하는 일(디스크립션)이 이번 변경에 걸리는지 봅니다.

      | 디스크립션을 읽은 결과 | 기입 |
      | --- | --- |
      | 같은 요소이고 하는 일도 같음 | 요건 목록에 넣고 작업 대상 `O`, 근거에 `찾음 · 대상 (디스크립션 근거)` |
      | 이름만 같고 하는 일이 다름 | 요건 목록에 넣지 않음. 아래 "찾았지만 대상 아님"에 이유와 함께 |
      | 디스크립션만으로 가릴 수 없음 | 요건 목록에 넣고 작업 대상 `미정`(근거는 비움). 절차 5번 "요건 목록을 확인받음" 질문 5로 물음 |

   3. **대상으로 가린 화면을 작업의 단위에 따라 나눕니다** (`reference-rules/work-log.md` "작업의 단위").

      | 대상으로 가린 화면 | 하는 일 |
      | --- | --- |
      | 이 작업과 같은 CID 체계 | 요건 목록에 그대로 둠 |
      | 다른 CID 체계 (메뉴 작업일 때) | 요건 목록에서 빼고 작업 기록 "영향 화면" 표에 기입. 반영 대기 항목은 지금 만들지 않고 완료 때 만듦(`reference-rules/pending-changes.md` 1절) |
      | 다른 CID 체계 (일괄 변경(메뉴 전반)일 때) | 요건 목록에 그대로 둠 |
4. **줄마다 케이스를 붙입니다.** `flow/README.md` "케이스"대로 붙입니다.

   | 대상 화면 | 케이스 |
   | --- | --- |
   | IA에 있고 `screens/tobe/` 화면 MD 머리말 `figma`에 작업방 섹션 링크가 있음 | 1 |
   | IA에 없는 새 화면. 대상 화면 칸에 "새 화면 (하는 일 한마디)"을 적고, CID 번호는 절차 4번 "요건 목록을 정리하고 뒤 단계용 확인 항목을 적음"에서 붙임 | 2 |
   | IA에 있고 `screens/tobe/` 화면 MD 머리말 `figma`가 비어 있거나, `screens/tobe/`에 화면 MD가 없음 | 3 |
5. **머리말 `cids`를 채웁니다.** 요건 목록에서 작업 대상이 `O`인 대상 화면의 CID를 적습니다. `미정`인 화면은 절차 4 · 5번에서 `O`가 되면 더하고, 새 화면은 번호를 붙인 뒤 더합니다.
6. **다른 작업과 겹치는지 봅니다.** 진행 중인 작업 기록 가운데 `menu` 또는 `cids`가 겹치는 것을 찾습니다. 결과는 작업 기록 "단계" 표 1단계 줄의 "남긴 것"에 `겹치는 다른 작업: 없음` 또는 `있음 (작업 기록 이름)`으로 기입합니다.

   | 찾은 결과 | 하는 일 |
   | --- | --- |
   | 진행 중인 작업의 요건 목록에 이번 요건 · 대상 화면이 **모두** 있음 (같은 요청) | 절차 3번으로 가지 않습니다. 그 작업 기록의 이름 · 요청자 · 지금 단계 · `이어서 작업할 곳:` 줄 · 남은 질문 대기를 요약해 보여 주고, 그 작업으로 이어 가게 합니다. 이번에 만든 작업 기록은 `status: 끝남`, 끝난 방식 `기존 작업으로 이어 감 (작업 기록 이름)`으로 닫습니다 |
   | 일부만 겹침 | 그 작업 기록 이름 · 요청자 · 지금 단계 · `이어서 작업할 곳:` 줄을 보고에 보여 주고 넘어갑니다. |

### 3) 대상 화면을 읽음


절차 2번에서 짚은 대상 화면이 지금 어떤지 끝까지 읽고, 읽은 화면을 작업 기록 "읽은 화면" 절에 기입합니다. 읽으며 찾은 것은 절차 4번 "요건 목록을 정리하고 뒤 단계용 확인 항목을 적음"에서 적습니다.

**순서**

1. **읽을 화면을 정합니다.** 아래 "읽는 것" · "읽지 않는 것"대로 정합니다.
2. **케이스마다 읽습니다.** 아래 "케이스마다 읽는 것"대로 읽고, 케이스 3은 "케이스 3에서 더 하는 것"을 먼저 합니다.
3. **읽은 화면을 기입합니다.** 작업 기록 "읽은 화면" 절에 적습니다(아래 "작업 기록에 쓰는 것"의 "읽은 화면 틀").

**읽는 것**

- 요건 목록에서 작업 대상이 `O`인 화면과, 작업 대상이 `미정`인 짝 화면(IA의 짝 CID)
- 대상 화면을 호출하는 화면 · 대상 화면이 호출하는 화면, 디스크립션이 가리키는 화면. 무엇을 열고 어디로 가는지, 값의 범위가 거기 정의돼 있는지만 읽습니다.
- 반영 대기 목록(`pending/open.md`)에서 대상 화면의 CID(짝 CID 포함)인 줄

**읽지 않는 것**

- "찾았지만 대상 아님" · "영향 화면"의 화면. 절차 2번에서 가린 것으로 끝납니다.
- 정책서 · 기준데이터. 2단계에서 읽습니다. Common UX(`common-ux/comm-index.md`)는 3단계에서 그리며 읽습니다(경로 분기 기준 5만 2단계). 정책 파일은 절차 2번에서 머리말 `cids`만 봅니다.

**케이스마다 읽는 것**

| 케이스 | 읽는 것 |
| --- | --- |
| 1 | 대상 화면의 `screens/tobe/` 화면 MD 전부(T-IOS · L-IOS 각각)와 작업방 Figma의 그 화면 기획 프레임 |
| 2 | 새 화면이라 읽을 기존 화면이 없음. 요청 글 · 공유 파일과 같은 메뉴의 비슷한 기존 화면 MD(`screens/tobe/`)를 읽음 |
| 3 | 아래 "케이스 3에서 더 하는 것"대로 작업 전에 추출해 둔 `screens/asis/` 화면 MD 전부(T-IOS · L-IOS 각각)와 `{메뉴}_asis` 페이지 **기획 프레임 안의 케이스 프레임**(`case`). 디스크립션은 화면 MD로 읽고 Figma 기획 프레임의 디스크립션은 따로 읽지 않음 |

- 반영 대기 항목은 반영 대기 목록(`pending/open.md`) 한 곳에만 있습니다. CID로 걸러 그 화면의 `대기` 항목을 빠짐없이 읽습니다(`reference-rules/pending-changes.md` 3절).
- 요청자는 Figma 링크를 페이지 단위로 줍니다(기획 프레임 하나의 링크가 아님. 작업방 페이지는 `flow/3-design.md` 공통 4 "페이지", 케이스 3 원본은 같은 파일의 `{메뉴}_asis` 페이지). 그 페이지에서 대상 CID의 기획 프레임을 찾아 읽습니다. 찾은 기획 프레임 링크는 "읽은 화면"의 Figma 링크 칸에 적습니다.
- `{메뉴}_asis` 페이지에서는 기획 프레임(오른쪽 패널이 붙은 너비 2252)과 그 안의 것만 읽습니다. 기획 프레임 밖의 섹션 · 프레임은 UI 화면일 수 있어 열지 않습니다(`CLAUDE.md` "늘 지키는 것"). 기획 프레임 옆 업데이트 메모 · 위 기획 진행 표시는 3단계에서 옮길 때 읽습니다(`flow/3-design-case3.md`).

**케이스 3에서 더 하는 것 (이행 기간)**

- **원본은 같은 파일의 `{메뉴}_asis` 페이지입니다 (2026-11-25 결정).** 요청자가 기존 화면 가운데 최신 화면만 골라 기획 프레임 · 업데이트 메모 · 기획 진행 표시를 옮겨 둔 페이지이고, 옮겨 둔 뒤 바뀌지 않습니다. 읽기만 하고, 그 메뉴의 To-Be 작업이 끝날 때까지 남겨 둡니다. 페이지 이름은 늘 `{메뉴}_asis` / `{메뉴}_tobe`입니다(`flow/3-design.md` 공통 4 "페이지").
- **asis 화면 MD는 작업 전에 추출해 둔 것을 그대로 읽습니다.** To-Be 작업을 시작하기 전에 `{메뉴}_asis` 페이지의 기획 프레임을 `screens/asis/{메뉴}/{CID}.md`로 단순 추출해 둡니다(추출 도구 `tools/figma/extract-screen.js`, 틀 `templates/screen-asis.md`). 원본이 바뀌지 않으므로 1단계에서 다시 옮기지 않습니다.
  - 추출할 때 글자 색은 옮기지 않습니다: 빨간 글씨는 검정 글씨로, 빨간 취소선은 검은 취소선(`~~글자~~`)으로, 검은 취소선은 그대로 `~~글자~~`로 둡니다.
  - 머리말: 원본에서 읽을 수 있는 칸을 모두 원본대로 채웁니다. `figma`(기획 프레임 링크) · `title` · `path` · `type` · `pair_cid` · `tl_relation`, 패널 화면 정보의 `version` · `date` · `author`. 원본에 없는 `client_mode` · `user_type` · `policies`는 비워 둡니다(2단계에서 확인: `flow/2-evidence.md` "경로 분기 기준마다 읽는 것"의 "케이스 3 (다시 그리기)" 줄).
  - 본문: 기존 화면(화면 글자 · 사용 컴포넌트 · 디스크립션 · 케이스)을 원본대로 쓰고, 머리 문장에 옮긴 날 · 페이지 · Ver을 적습니다.
- 1단계에서 그 화면의 To-Be 화면 MD(`screens/tobe/{메뉴}/{CID}.md`)를 `templates/screen.md` 빈 틀로 만듭니다. 이미 있으면 빈 틀로 다시 씁니다(예전에 그린 메뉴도 처음부터 다시 그림, 2026-11-25 결정). 반영 대기 항목은 이미 `pending/open.md`에 있으므로 옮기지 않습니다(`reference-rules/pending-changes.md` 6절).
- 읽으며 찾은 고칠 점은 반영 대기 목록(`pending/open.md`)에 그 화면의 줄로 "점검 발견"을 더합니다(ID는 `pending/open.md` · `closed.md`에서 그 CID의 가장 큰 번호에 이어 매김, `reference-rules/pending-changes.md` 3절).
- 읽은 화면의 Module · Unit 이름과 Unit 구성(예: 폐기함 · Door 목록)을 `glossary/modules.csv` · `module-units.csv`에 대어 봅니다. 없는 이름(예전 이름)이거나 구성이 다르면(제조사에 따라 다른 Unit 포함) 바로 위처럼 반영 대기 목록에 "점검 발견" 줄로 적고, 3단계 절차 3번(용어 점검)에서 고칩니다.
- 테스트로 할 때는 저장소의 화면 MD를 고치지 않고 작업 폴더에 둡니다.

### 4) 요건 목록을 정리하고 뒤 단계용 확인 항목을 적음


절차 2번 · 3번의 결과로 요건 목록을 다듬고, 요청자에게 보여 줄 것을 모두 준비합니다. 새로 읽지 않습니다. 물을 것은 절차 5번 "요건 목록을 확인받음"으로 넘깁니다.

**순서**

1. **짝 화면을 최종 판단합니다.** 작업 대상이 `미정`인 짝 화면 줄을 절차 3번 "대상 화면을 읽음"에서 읽은 결과로 가려 작업 대상과 근거를 적습니다. `O`가 된 화면은 머리말 `cids`에 더합니다.

   | 읽은 결과 | 작업 대상 | 근거에 기입 |
   | --- | --- | --- |
   | 두 화면에 같은 기능이 있음 | O | `짝 화면 · 함께 고침 (두 화면에 같은 기능)` |
   | 그 기능이 한쪽에만 있음 | X | `짝 화면 · 고치지 않음 (L-IOS에만 있는 기능)` |
   | 읽어도 가릴 수 없음 | 미정 (절차 5번 질문 4로 물음) | |

2. **요건을 기존 화면에 비춰 다듬습니다.** 읽어 보니 요건이 가리키는 요소가 기존 화면에 없거나, 요청 글과 기존 화면이 다르게 말하면 요건 문장을 고치지 않고 순서 3의 기준대로 나눠 적습니다(요청자만 알 수 있으면 1단계에서 묻고, 정책으로 풀릴 수 있으면 2단계로 넘김). 요건마다 기존 화면에 이미 반영됐는지도 봅니다.

   - **이미 반영됨의 기준:** 요청한 내용이 화면 MD(`screens/tobe/`)에 있고, 그 화면을 고치는 진행 중인 작업 기록(`work-logs/`의 `status: 진행 중`, `cids`에 그 화면)이 없을 때만 이미 반영된 것으로 봅니다. 화면 MD에는 있지만 그 화면을 고치는 진행 중인 작업 기록이 있으면 다른 작업이 하다 만 것이므로, 절차 2번 순서 6 "다른 작업과 겹치는지"의 같은 요청으로 보고 그 작업으로 이어 가게 합니다.

   | 결과 | 하는 일 |
   | --- | --- |
   | **모든 요건이 이미 반영됨** | 절차 5번에서 "요청하신 내용은 이미 화면에 반영되어 있습니다(근거). 1단계에서 종료할까요, 아니면 더 바꿀 것을 알려 주시겠어요?"라고 묻습니다. 종료하면 2 ~ 4단계는 "해당 없음 (이미 반영됨)"으로 지나가고, 5단계 완료에서 끝난 방식 `반영 안 함 (이미 반영됨)`을 기입하고 닫습니다. 더 바꿀 것을 주면 요건 목록에 `추가`로 달고 이어 갑니다 |
   | **일부 요건만 이미 반영됨** | 그 요건의 요청 상태를 `제거 (이미 반영됨, 근거)`, 그 요건의 대상 화면 표의 작업 대상을 모두 `X`로 바꾸고 나머지로 이어 갑니다. 절차 5번에서 보여 줍니다 |
3. **읽으며 본 빈 곳 · 어긋난 곳을 나눠 적습니다.** 요건 목록을 정하는 데 필요한 것은 1단계에서 풀고, 요건 목록과 상관없이 읽다가 본 것만 작업 기록 "뒤 단계용 확인 항목(claude)" 절에 적어 뒤 단계로 넘깁니다. 대상 화면을 끝까지 읽는 것은 1단계뿐이라(2단계는 정책이 걸린 디스크립션 번호만 다시 봄), 읽으며 본 것은 1단계가 적어야 뒤 단계가 압니다.
   - **1단계에서 풂:** 아래는 "뒤 단계용 확인 항목(claude)"에 두지 않습니다.

     | 무엇 | 어떻게 |
     | --- | --- |
     | IA와 화면이 다른 곳: CID, 경로, 짝 화면 | 작업 기록 "요청자 확인"에 적어 절차 5번에서 묻습니다 |
     | 요청자만 알 수 있는 물음: 무엇으로 바꿀지 값이 없음, 어느 화면인지 적혀 있지 않음(절차 2번 순서 1), 요건이 가리키는 요소가 기존 화면에 없음(순서 2) | 작업 기록 "요청자 확인"에 적어 절차 5번에서 묻습니다 |
     | IA에 없는데 새로 필요한 화면 | 묻지 않고 요건 목록에 새 화면 줄로 넣고 순서 4에서 번호를 붙입니다 |

   - **뒤 단계로 넘김 ("뒤 단계용 확인 항목(claude)"):** 아래 넷을 "뒤 단계용 확인 항목(claude)" 절에 적습니다(아래 "뒤 단계용 확인 항목 틀").
     1. **기능 정의가 안 된 요소:** 화면에 그려져 있는데 디스크립션에 동작이 없는 것 (예: [Refresh]에 번호 · 설명이 없음, 정렬 아이콘이 있는데 기본 정렬 기준이 없음, 값이 없을 때 무엇을 보여 주는지 없음). 3단계로 넘깁니다(3단계가 `reference-rules/description.md` 5절 "기존 디스크립션에 없던 설명을 더한 곳" 표대로 쓰거나 질문 대기로 둠). 3단계는 넘어온 범위만 고치므로 1단계가 적지 않으면 찾는 곳이 없습니다
     2. **Alert · Confirm 보완 필요 지점 (안전 장치):** 잘못 누르면 되돌리기 어려운데 디스크립션에 다시 묻는 Alert · Confirm이 적혀 있지 않은 것 (예: [Delete]를 누르면 바로 지워지는지 없음, 편집 중 닫을 때 묻는지 없음). 디스크립션에 없다는 것만 적고, 보완이 필요한지 · 어떤 Alert인지는 판단하지 않습니다. 요건의 지나가는 단계에 2가 있으면 2단계에서 Alert 카탈로그 · 정책과 대조하고, 없으면 3단계 질문 대기로 넘깁니다
     3. **이번에 넣기로 한 `대기 (확인 필요)` 항목:** 무엇으로 바꿀지 정해지지 않은 옛 항목 가운데 절차 5번 질문 6에서 "반영"으로 고른 것. 답을 받은 뒤 적습니다. 2단계로 넘겨 근거로 풀어 보고, 못 풀면 3단계 질문 대기로 갑니다. 다만 **답이 화면을 보지 않아도 정해지는 것**(이름 · 값 · 목록 항목을 고르는 것, 어느 쪽으로 맞출지)은 넘기지 않고 절차 5번 질문 6에서 값을 함께 묻습니다(위 "가르는 기준"). 화면을 봐야 정할 수 있는 것(배치 · 묶음 · 모양)과 근거 자료로 풀릴 수 있는 것만 넘깁니다. "이번엔 안 함"을 고른 것은 적지 않습니다
     4. **요청과 기존 화면이 맞지 않는 곳:** 순서 2에서 요청 글과 기존 화면이 다르게 말한 것 가운데 정책 · 기준데이터로 풀릴 수 있는 것. 2단계로 넘깁니다
   - **가르는 기준:** 답이 정책 · 기준데이터에 있을 수 있으면 2단계로 넘기고, 요청자만 알 수 있으면(무엇으로 바꿀지, 어느 화면인지) 1단계에서 묻습니다. 애매하면 2단계로 넘깁니다.
4. **새 화면에 CID 번호를 붙입니다.** 요건 목록의 "새 화면" 줄마다 Claude가 번호를 붙여 대상 화면 칸을 고칩니다. 절차 5번에서 보여 주고, 완료(5단계) 때 한번에 확정합니다.
   - 접두어(T-IOS `TI` · L-IOS `LI`), 접미어(`-P` Popup · `-T` Tab), 같은 메뉴의 번호 순서를 따릅니다. 짝 화면이 있으면 짝 CID도 함께 붙입니다.
   - 근거(어느 화면에서 열리는지, 왜 따로 화면이 필요한지)를 근거 칸에 적습니다.
   - 신규 메뉴면 메뉴 이름(영어)과 CID 체계(메뉴 코드 세 글자, IA의 기존 메뉴 코드와 겹치지 않게)를 Claude가 제안해 두고 그 체계로 붙입니다. 제안은 절차 5번에서 함께 묻습니다.
   - 새 CID는 작업 기록에만 적습니다. IA(`ia/ia-screens.csv`)에는 5단계에서 넣습니다(`flow/5-done.md` 절차 2번 순서 1).
   - 머리말 `cids`에 새 CID를 더합니다.
5. **대상 화면의 반영 대기 항목 후보를 적습니다.** 요건 목록의 대상 화면 표에서 작업 대상이 `O`이거나 `미정`인 화면(짝 화면 · 찾은 화면 포함)의 CID로 반영 대기 목록(`pending/open.md`)을 걸러 `대기` 항목을 근거가 같은 것끼리 묶어 작업 기록 "대상 화면의 반영 대기 항목" 절에 적습니다(아래 "대상 화면의 반영 대기 항목 틀"). 반영할지는 절차 5번에서 묻습니다. 작업 대상이 `미정`인 화면의 항목에는 `(○○ 화면을 함께 고치면)`을 붙여, 절차 5번에서 그 화면을 넣을지와 한 번에 묻습니다. `대기 (확인 필요)` 항목은 다른 묶음과 섞지 않고 맨 끝에 묶음 하나("무엇으로 바꿀지 아직 정해지지 않은 항목")로 적습니다. 많으면 근거가 같은 것끼리 다시 나눕니다. 그 화면 케이스의 규칙과 부딪혀 반영할 수 없는 항목(예: 빈 번호를 채우는 "번호 정리", 케이스 1 · 3은 빈 번호를 그대로 둠)은 후보에 넣지 않고, 묻지 않고 반영 대기 목록에서 `제외 (날짜, 케이스 N 규칙과 부딪힘: 무엇)`으로 바꿔 `pending/closed.md`로 옮깁니다. 요청자에게 보여 주지 않습니다(테스트로 할 때는 바꾸지 않음).
6. **요건마다 경로 분기 기준을 가르고 지나가는 단계를 적습니다.** 요건 번호마다 아래 경로 분기 기준 여덟 가운데 하나를 붙이고, 그 기준의 "2단계에서 읽는 강도"를 기준 뒤에 함께 적어, 작업 기록 "요건 목록"의 그 요건 머리 아래 줄(경로 분기 기준 (근거) · 읽는 강도 / 지나가는 단계 / UI 작업)에 기입하고, 맨 끝에 "작업이 지나가는 단계"를 적습니다(아래 "요건 목록 틀"). 2단계는 이 강도대로 읽고, 강도가 바뀔 때만 이 줄을 고칩니다.

   | --- | --- | --- | --- | --- | --- |
   | 1 | 글자 · 표기만 | 워딩 · 대소문자 · 오타 · 라벨이 바뀜. 정책과 상관없음 | 워딩 수정 "Total → Total Samples", 라벨 "Standard / Custom" | 가볍게 | 1 → 2 → 3 → 4 → 5 |
   | 2 | 화면 구성이 바뀜 | 요소가 생기거나 없어지거나, 배치 · 표현이 바뀜. 하는 일은 그대로 | PD-0004 [Next] 제거, Capacity 항목 제거, 테이블 → 카드 형태, 간격 재조정 | 그 요소만 | 1 → 2 → 3 → 4 → 5 |
   | 3 | 동작 · 조건 · 값 · 순서가 바뀜 | 활성 조건, 저장 범위, 계산, 데이터 처리, 프로세스 순서가 바뀜. 디스크립션에 정책을 반영하는 것, 기능을 다른 화면으로 옮기는 것도 여기 | PD-0002 SMTP [Save] 범위, Batch ID 생성 정책 수정, Run 폐기물 확인 단계 추가, 재고 산출 정책 디스크립션 반영, Language 설정을 Profile로 이관 | 정책 전부 | 1 → 2 → 3 → 4 → 5 |
   | 4 | 장비 · Alert · 권한 · 상태값에 닿음 | 장비 동작, 상태값이 생기거나 없어지거나 뜻이 바뀜, Alert · Confirm, User Type · L-IOS Client Mode | Module 상태값에 Paused 추가, Door Closed 제거, 트롤리 감지 실패 알림, 모드별 메뉴 접근 | 정책 전부 + 장비 · Alert · 권한 | 1 → 2 → 3 → 4 → 5 |
   | 5 | 공통 기준을 화면에 맞춤 | 표기 · 정렬 규칙, Common UX 컴포넌트, 용어 · 상태값의 이름이 바뀌어 화면을 맞춤 | 소모품/시약 표기 및 정렬 기준 변경 반영, 대소문자 "spare caps → Spare Caps", 명칭 변경 "Requirements for Run Completion → Inventory status" | 기준 문서 | 1 → 2 → 3 → 4 → 5 |
   | 6 | 화면이 생기거나 없어짐 | IA에 없는 화면이 필요함(케이스 2), 또는 화면(CID) 자체가 없어짐 | View Trolley Info 신규, Run Report 신규, Run-time Info Popup 제거 | 정책 전부 | 1 → 2 → 3 (새 화면은 구상부터, 없어지는 화면은 폐기 표시) → 4 → 5 (IA 반영) |
   | 7 | 정책만 바뀜 | 규칙은 바뀌지만 화면에 보이는 것이 그대로 | 조합 검사 가능 여부 | 정책 전부 | 1 → 2 → 4 (UX 확정) → 5 (3 해당 없음) |
   | 8 | 옮겨 다시 그림 (케이스 3) | **요건 목록에서 케이스가 3인 줄.** 바꾸는 요건 없이 `{메뉴}_asis` 페이지의 기존 화면을 `{메뉴}_tobe` 페이지에 새 규칙 · Common UX · 정리한 정책으로 다시 그림 | Event History를 작업방 새 페이지로 옮김, 기존 메뉴 이행 | 케이스 3 (다시 그리기) | 1 → 2 → 3 → 4 → 5 |

   거의 모든 요건이 1 ~ 5단계를 다 지나갑니다. 경로 분기 기준은 단계를 건너뛰게 하기보다 **2단계에서 얼마나 깊이 읽는지**를 정합니다. 강도마다 읽는 것은 `flow/2-evidence.md` "경로 분기 기준마다 읽는 것"에 있습니다.

   **가르는 규칙**
   - **한 요건에는 기준 하나입니다.** 여러 기준이 섞이면 요건을 나눕니다. 예: "Module 상태값에 Paused 추가 + Door Control 버튼 UI 변경" → 요건 둘(4번 / 2번)
   - **겉모습보다 이어진 것을 봅니다.** 1 · 2번이어도 그 요소가 장비 동작 · 상태값 · Alert · 권한과 이어져 있으면(절차 3번에서 읽은 디스크립션으로 봄) 4번으로 가릅니다.
   - **근거가 정책이면 3번입니다.** 글자 · 디스크립션만 바뀌어도 정책을 디스크립션에 반영하는 것이면 1번이 아니라 3번으로 가릅니다.
   - **새 요소의 값이 어디서 오는지 봅니다.** 2번이어도 새 요소에 보여 줄 값이 정책 · 기준데이터에서 오면(연결 · 계산 · 여러 건 처리 등) 3번으로 가릅니다. 예: Event 상세의 Effect 항목은 Event Code에 연결된 Scenario Code의 설명을 여러 건이면 줄을 바꿔 보여 주므로 3번
   - **기능을 옮기면 3번입니다.** 옮겨 가는 화면과 옮겨 오는 화면을 모두 대상 화면으로 적습니다.
   - **상태값은 이름 · 표기만 바뀌면 5번, 값이 생기거나 없어지거나 뜻이 바뀌면 4번입니다.**
   - **7번은 1단계에서 확정하지 않습니다.** 화면에 드러나는지는 정책을 읽어야 알 수 있으므로 3번으로 가르고 근거에 `정책만일 수 있음`을 적습니다. 2단계에서 정책을 읽은 뒤 7번으로 바꿉니다.
   - **케이스가 3이면 8번입니다.** 요건 목록에서 케이스가 3인 줄의 요건(기존 화면을 옮겨 다시 그림)은 다른 판단 신호를 보지 않고 8로 가릅니다.
     - 케이스 3 화면에 바꾸는 것(요소 추가 · 값 변경 등)도 함께 요청됐으면 요건을 둘로 나눕니다. 옮기는 요건은 8, 바꾸는 요건은 그 화면 줄도 케이스 3이지만 1 ~ 7 가운데서 가릅니다. 예: "Event History를 옮기면서 Effect 항목 추가" → 요건 1 옮김(8) / 요건 2 Effect 추가(3)
     - 8은 2단계에서 그 화면에 걸린 정책 · 기준 자료와 Alert을 읽고, 기존 화면이 지금 정책과 다른 곳을 찾고, 용어는 2단계 용어 목록에서 기존 화면 전체를 대조합니다. Common UX는 3단계에서 그리며 읽습니다.
     - UI 작업은 `대상 아님`을 기본으로 적고, 다시 그리며 바뀐 곳이 생기면 4단계 UX 확정 때 다시 정합니다.
   - **애매하면 더 무거운 쪽으로 가르고** 그렇게 가른 이유를 근거에 적습니다(헌법 최상위 원칙). 가벼운 쪽으로 바꾸는 것은 절차 5번에서 요청자가 정합니다.
   - 작업의 단위(메뉴 하나 / 일괄 변경(메뉴 전반))는 경로 분기 기준과 따로 가릅니다(`reference-rules/work-log.md` "작업의 단위").
   - 경로 분기 기준 말고 아래 줄도 요건마다 기입합니다. 단계를 건너뛰게 하지 않고 그 단계 안의 일만 더하거나 뺍니다.

     | 줄 | 답 | 달라지는 일 |
     | --- | --- | --- |
     | UI 작업 | 대상 / 대상 아님 | UI팀이 작업해야 하는 요건인지. 배치 · 요소 · 화면 표기 글자가 바뀌면 `대상`, 디스크립션만이면 `대상 아님`. 1단계에서 적는 값은 화면을 그리기 전의 임시 값이고 4단계에서 요청자에게 확인받아 확정함(`flow/4-revise-verify.md` 절차 3번 "UX 확정을 기입함" 순서 3) |

   - **작업이 지나가는 단계:** 요건 하나라도 그 단계를 지나가면 작업은 그 단계를 지나갑니다. 모든 요건이 "해당 없음"인 단계는 "해당 없음 (이유)"로 지나갑니다. 그 단계 안에서는 그 단계를 지나가는 요건만 다룹니다.
   - **요청자가 바꿀 수 있습니다.** 흐름에 대한 판단(경로 분기 기준 · 읽는 강도 · 지나가는 단계 · UI 작업)은 Claude가 가른 안이고, 요청자가 바꿀 수 있습니다. 절차 5번 "요건 목록을 확인받음"에서도, 그 뒤 어느 단계에서도 됩니다.
     - **더해 달라고 하면 더합니다.** 요청자가 필요하다고 해서 단계나 일을 더해 달라고 하면(예: "이 요건도 2단계에서 정책을 봐 줘") 묻지 않고 더합니다.
     - **빼 달라고 하면** 가벼운 쪽으로 바꾸고, 빼서 놓칠 수 있는 것(예: 장비 상태값에 닿는 요건의 정책 대조)이 있으면 그것만 한 줄로 알린 뒤 요청자의 답대로 합니다.
     - 바꾼 것은 "요건 목록"의 그 요건 줄에 `바뀜 (날짜, 누가, 이유)`로 기입하고, Claude가 처음 가른 안은 지우지 않고 취소선으로 남깁니다(아래 "요건 목록 틀"). 작업이 지나가는 단계도 다시 적습니다.

7. **절차 5번에서 물을 것을 모읍니다.** 작업 대상이 `미정`인 줄(짝 화면 · 찾은 화면), 신규 메뉴 이름 · CID 체계, 비어 있는 그릴 곳 페이지, 반영 대기 항목 후보, 요건마다 가른 경로(경로 분기 기준 · 지나가는 단계는 보여 주고, `요청자 확인`인 칸은 확인받음), 이미 반영된 요건(모두면 1단계에서 종료할지 묻고, 일부면 `제거 (이미 반영됨)`으로 바꾼 것을 보여 줌), 순서 3에서 1단계에서 풀기로 해 "요청자 확인"에 적은 것(IA와 다른 곳, 요청자만 알 수 있는 물음).

### 5) 요건 목록을 확인받음


절차 4번 순서 7에서 모은 것을 **한 번에** 보여 주고 답을 받습니다. 1단계의 정해진 확인은 여기 한 번입니다(예외 질문은 `flow/README.md` "단계를 지나는 규칙" 9). 작업 기록에서 아래 "보여 줄 것"에 나오는 절과 "요청자 확인" 표를 다시 읽고, "보여 줄 것" · "물을 것"을 `reference-rules/work-log.md` "요청자에게 보여 주는 법"의 모양으로 씁니다.

**보여 줄 것** (바꿀 곳이 있으면 말해 달라고 함)

| 보여 줄 것 | 작업 기록의 절 |
| --- | --- |
| 요건 목록: 요건마다 경로(경로 분기 기준 · 읽는 강도 · 지나가는 단계 · UI 작업)와 대상 화면(케이스 · 짝 화면 판단 · 새 화면 CID 번호), 작업이 지나가는 단계. 작업 기록의 요건 묶음 모양 그대로 보여 줌 | "요건 목록" |
| 찾았지만 대상 아님 | "찾았지만 대상 아님" (요건 목록 아래) |
| 영향 화면 (비어 있어도 따로 보여 줌) | "영향 화면" (요건 목록 아래) |
| 일부 요건이 이미 반영돼 `제거 (이미 반영됨)`으로 바꾼 것 | "요건 목록" |
| 대상 화면의 반영 대기 항목 (묶음마다 질문 6으로 물음) | "대상 화면의 반영 대기 항목" |

- "뒤 단계용 확인 항목(claude)"은 보여 주지 않습니다. 2 · 3단계에서 Claude가 처리하는 것이라 작업 기록에만 남깁니다.

**물을 것** (해당할 때만, 이 순서대로)

| # | 언제 | 묻는 문장 | 고르는 것 |
| --- | --- | --- | --- |
| 1 | 모든 요건이 이미 반영됨 | "요청하신 내용은 이미 화면에 반영되어 있습니다(근거). 1단계에서 종료할까요, 아니면 더 바꿀 것을 알려 주시겠어요?" | 종료 / 더 바꿀 것 있음 |
| 2 | 신규 메뉴 | "새 메뉴의 이름과 CID 체계를 아래와 같이 제안합니다." 메뉴 이름(영어)과 CID 체계를 보여 줌 | 항목마다 이대로 / 직접 적음 |
| 3 | 그릴 곳 페이지가 비어 있음 | "작업방의 어느 페이지에 그릴까요?" | 페이지 이름 |
| 4 | 작업 대상이 `미정`인 짝 화면 줄 (절차 4번 순서 1에서 읽어도 가릴 수 없었음) | "짝 화면 ○○도 같게 고칠까요?" 짝 CID와 넣을 변경을 보여 줌 | 함께 고침 / 이 화면만 |
| 5 | 작업 대상이 `미정`인 찾은 화면 줄 (절차 2번 순서 3에서 찾음) | "○○ 화면의 ○○도 같은 요소로 보입니다(디스크립션 근거). 이번 작업에 넣을까요?" | 넣음 / 넣지 않음 |
| 6 | 대상 화면의 반영 대기 항목 후보가 있음 | "이번 작업 화면의 반영 대기 항목입니다. 어디까지 반영할지 골라 주세요." 근거가 같은 것끼리 묶어 보여 줌. 작업 대상이 `미정`인 화면(질문 4 · 5)의 항목은 `(○○ 화면을 함께 고치면)`을 붙여 함께 보여 줌. `대기 (확인 필요)` 묶음은 "무엇으로 바꿀지 아직 정해지지 않은 항목입니다. 이번에 넣으면 2 · 3단계에서 정해 반영합니다."를 붙여 보여 줌. 그 가운데 답이 화면을 보지 않아도 정해지는 항목(절차 4번 순서 3 "뒤 단계로 넘김"의 3)은 항목마다 정할 것과 후보 값을 함께 보여 줌 | 묶음마다 반영 / 이번엔 안 함. 값을 함께 묻는 항목은 항목마다 후보 값 / 바꾸지 않음 / 이번엔 안 함 ("모름 · 고객에게 물어야 함"이면 "반영"으로 넘겨 3단계 질문 대기로 그림) |
| 7 | 늘 (마지막) | "위 요건 목록과 흐름대로 진행할까요?" | 이대로 진행 / 고칠 곳 있음 |

- 1번에서 종료를 고르면 2 ~ 7번은 묻지 않습니다.
- 위 표에 없는 질문을 늘 묻는 질문으로 더하지 않습니다. 케이스 · 경로 분기 기준 · 짝 화면처럼 이 단계에서 Claude가 가르는 것은 묻지 않고 가르고, 근거로 가를 수 없을 때만 작업 기록 "요청자 확인"에 적어 위 질문 다음에 함께 묻습니다(`flow/README.md` "단계를 지나는 규칙" 9). 뒤 단계에서 풀 물음은 "뒤 단계용 확인 항목(claude)"에 적어 넘깁니다.
- 묻는 문장에는 "줄", "맞는지"처럼 무엇을 가리키는지 흐린 말을 쓰지 않고, 확인하는 대상의 이름(CID · 화면 이름 · 항목 ID)을 그대로 씁니다.

**답을 받은 뒤**

1. 작업 기록 "요청자 확인" 표에 물은 질문마다 줄을 적고 답(날짜)을 채웁니다. 예외 질문 줄은 답만 채웁니다.
2. 답대로 고칩니다.

   | 답 | 고치는 것 |
   | --- | --- |
   | 종료 | 2 ~ 4단계 "해당 없음 (이미 반영됨)", 5단계 완료에서 `반영 안 함 (이미 반영됨)`으로 닫음 |
   | 더 바꿀 것 · 고칠 곳 있음 | 요건 목록에 `추가 · 변경 · 제거 (날짜, 누가, 이유)`로 달고, 그 요건만 절차 2 ~ 4번을 다시 한 뒤 이 순서로 돌아옴 |
   | 신규 메뉴 이름 · CID 체계 | `menu` · `cid_system`에 적음. 제안과 다르면 붙인 새 화면 번호를 고침 |
   | 짝 화면 · 찾은 화면 | 요건 목록의 작업 대상을 `O` / `X`로 바꾸고, 근거에 요청자 답을 적음(예: `짝 화면 · 함께 고침 (요청자 답, 날짜)`). `O`가 된 화면은 머리말 `cids`에 더함. 그 화면의 반영 대기 항목은 질문 6에서 이미 함께 물었으므로(`(○○ 화면을 함께 고치면)`) 다시 묻지 않음. `X`가 된 화면의 항목은 질문 6의 답과 상관없이 "반영 / 이번엔 안 함"에 `이번엔 안 함 (화면을 고치지 않음)`을 적고 `대기` 그대로 둠 |
   | 반영 대기 "반영" | 반영 대기 목록(`pending/open.md`)에서 그 항목의 상태를 `작업 중 (작업 기록 이름)`으로 바꿈(`reference-rules/pending-changes.md` 4절). `대기 (확인 필요)` 묶음에서 "반영"을 고른 항목은 같이 `작업 중`으로 바꾸고 "뒤 단계용 확인 항목(claude)"에 적음(절차 4번 순서 3 "뒤 단계로 넘김"의 3). 1단계에서 값을 고른 항목은 그 값을 변경 후에 채우고 `작업 중`으로 바꾸며 뒤 단계용 확인 항목에는 적지 않음. "바꾸지 않음"을 고른 항목은 `제외 (날짜, 바꾸지 않음)`로 바꾸고 `pending/closed.md`로 옮김. "이번엔 안 함"은 `대기` · `대기 (확인 필요)` 그대로. 요청자가 제외한다고 말한 항목만 `제외 (날짜, 이유)`로 바꾸고 `pending/closed.md`로 옮김 |

3. 작업 기록 "단계" 표 1단계 줄의 "끝낸 날"과 "마침 점검" 칸에 `요청자 확인 (날짜)`를 적고, `이어서 작업할 곳:` 줄을 작업이 지나가는 다음 단계로 고칩니다. 다음 단계로 넘어갈지는 이 절차의 질문과 함께 묻습니다(`flow/README.md` "단계 전환").

## 작업 기록에 쓰는 것

1단계가 작업 기록(`reference-rules/work-log.md` "틀")에 쓰는 곳입니다. 틀이 따로 있는 절은 아래에 둡니다.

| 작업 기록의 절 · 칸 | 쓰는 것 | 절차 |
| --- | --- | --- |
| 머리말 · 제목 · "요청" 절 | 만들 때 적는 항목(`reference-rules/work-log.md` "항목마다 적는 법") | 1 |
| `이어서 작업할 곳:` 줄 | 만들 때 첫 줄(`reference-rules/work-log.md` "항목마다 적는 법"), 절차마다 한 일 · 다음 절차 · 다시 읽을 곳, 절차 5에서 질문을 보낸 뒤 `답 기다림`, 단계를 마칠 때 다음 단계 (위 절차 표 아래) | 1 ~ 5 |
| 머리말 `cids` · `menu` · `cid_system` | 작업 대상이 `O`인 화면의 CID, 신규 메뉴 이름 · CID 체계 | 2 · 4 · 5 |
| "단계" 표 1단계 줄 | "남긴 것"에 겹치는 다른 작업, "끝낸 날" · "마침 점검"에 `요청자 확인 (날짜)` | 2 · 5 |
| "요건 목록" (요건마다 경로 · 대상 화면, "찾았지만 대상 아님" · "영향 화면" 포함) | 아래 "요건 목록 틀". 경로는 절차 4번 순서 6 | 2 · 4 · 5 |
| "읽은 화면" | 아래 "읽은 화면 틀" | 3 |
| "뒤 단계용 확인 항목(claude)" | 아래 "뒤 단계용 확인 항목 틀" | 4 |
| "대상 화면의 반영 대기 항목" | 아래 "대상 화면의 반영 대기 항목 틀" | 4 · 5 |
| "요청자 확인" | 물은 것과 답 (정해진 질문 · 예외 질문) | 1 ~ 5 |

**요건 목록 틀** (작업 기록 "요건 목록" 절에 요건마다 이 묶음을 씀)

요건마다 머리(`### 요건 번호. 요건`)와 요건에 대한 네 줄을 쓰고, 그 아래 대상 화면 표를 둡니다. 요건에 대한 것(요청 상태 · 경로)은 요건마다 한 번, 화면에 대한 것(케이스 · 작업 대상)은 화면 줄마다 적습니다. 요건 목록 맨 끝에 "작업이 지나가는 단계" 한 줄을 둡니다.

```markdown

- 경로 분기 기준 (근거) · 읽는 강도: 3 동작 · 조건 · 값 · 순서가 바뀜 (Effect 값이 Scenario Code 설명에서 옴) · 정책 전부

### 요건 2. Event Popup에 Effect 항목 추가

- 경로 분기 기준 (근거) · 읽는 강도: 3 동작 · 조건 · 값 · 순서가 바뀜 (요건 1과 같음) · 정책 전부

- UI 작업: 대상 (요소가 생김)

### 요건 3. [Export] 버튼 이름을 [Download]로

- 경로 분기 기준 (근거) · 읽는 강도: 6 화면이 생김 (IA에 없는 새 화면) · 정책 전부
```

- 경로 분기 기준 · 읽는 강도 · 지나가는 단계 · UI 작업은 절차 4번 순서 6에서 적습니다. 그 전(절차 2번)에는 요청 상태와 대상 화면 표만 적습니다.
- 읽는 강도는 순서 6 표의 "2단계에서 읽는 강도" 값을 그대로 씁니다(`flow/2-evidence.md` "경로 분기 기준마다 읽는 것").
- 요건에 대한 줄의 값이 바뀌면(2단계에서 기준 · 강도가 바뀜, 요청자가 바꿈, 4단계에서 UI 작업을 확정함) `reference-rules/work-log.md` "쓰는 법"의 바뀐 기록 모양(처음 값은 취소선, 뒤에 `바뀜 (날짜, 누가, 이유)`)대로 적습니다(예시의 요건 3). 바뀌지 않은 값은 고치지 않습니다.

**찾았지만 대상 아님** (작업 기록 "요건 목록" 절 아래 `### 찾았지만 대상 아님`)

| 찾은 화면 (CID) | 찾은 법 (말 · 번호 · CID) | 대상이 아닌 이유 |
| --- | --- | --- |
| (예) 같은 메뉴의 다른 화면 이름 (CID) | 같은 글자 [Export] | 이름만 같고 하는 일이 다름 (디스크립션 번호) |

**영향 화면** (작업 기록 "요건 목록" 절 아래 `### 영향 화면`)

| 화면 (CID) | 작성자 | 영향 (화면 변경 / 디스크립션 변경 / 확인 필요) | 무엇 때문 (요건 번호 · 정책) | 찾은 곳 (1단계 글자 · Common UX 번호 · 호출 관계 / 2단계 정책) | 처리 (반영 대기 항목 ID) |
| --- | --- | --- | --- | --- | --- |
| (예) 다른 메뉴의 화면 이름 (CID) | (그 화면 작성자) | 디스크립션 변경 | 요건 3 ([Export] 이름) | 1단계 글자 · 디스크립션 | 완료 때 만듦 |

- **요청 상태**는 그 요건이 처음부터 있었는지, 도중에 바뀌었는지입니다. 요건 묶음은 지우지 않고 값만 바꿉니다. 대상 화면 표의 줄도 지우지 않습니다.

  | 값 | 뜻 |
  | --- | --- |
  | `최초` | 요청을 받을 때 요청 글 · 공유 파일에 있던 요건 |
  | `추가 (날짜, 누가, 이유)` | 작업 도중 더 들어온 요건 |
  | `변경 (날짜, 누가, 이유)` | 내용이 바뀐 요건 |
  | `제거 (날짜, 누가, 이유)` | 빠진 요건. 이미 반영돼 빠지면 `제거 (이미 반영됨, 근거)` |

- **작업 대상**은 그 화면 줄을 이번 작업에서 고치거나 그리는지입니다.

  | 값 | 뜻 |
  | --- | --- |
  | `O` | 이번 작업에서 고치거나 그림 |
  | `X` | 이번 작업에서 고치지 않음 (짝 화면 · 고치지 않음, 요청 상태가 `제거`인 요건의 화면 등) |
  | `미정` | 아직 정하지 않음. 절차 4번(읽고 가림) 또는 절차 5번(요청자 확인)에서 `O` / `X`로 바꿈 |

- 화면은 어느 표에서든 `화면 이름 (CID)` 순서로 적습니다(예: `Event History Detail (TI-EVT-01-P)`).
- **근거:** 요청 글 밖에서 Claude가 넣거나 뺀 화면에 그 까닭을 짧게 적습니다. 절차 5번에서 요청자가 이 칸을 보고 판단합니다. 요청 글에 적힌 화면과 작업 대상이 `미정`인 줄(절차 5번에서 물음)은 비웁니다.
- "찾았지만 대상 아님"은 이름만 같고 하는 일이 다른 후보를 왜 넣지 않았는지 남기는 표입니다. 찾은 후보가 없으면 "다른 화면 없음"만 기입합니다.
- "영향 화면"은 이 작업에 넣지 않지만 맞춰 고쳐야 할 다른 메뉴의 화면을 모으는 표입니다. 1단계에서 글자 · 디스크립션으로 찾은 것을 적고, 2단계에서 정책으로 찾은 것을 같은 표에 더합니다. 반영 대기 항목은 완료 때 이 표를 보고 만듭니다(`reference-rules/pending-changes.md` 1절). 한 화면은 "찾았지만 대상 아님"과 "영향 화면" 가운데 한 곳에만 적습니다.

**읽은 화면 틀** (작업 기록 "읽은 화면" 절에 이 표를 씀)

| 화면 (CID) | 읽은 것 (화면 MD / 기획 프레임 / 케이스 프레임 / 호출 화면) | Figma 링크 |

- Figma 고유 번호만 나열하지 않고 화면 이름과 링크로 적습니다.

**뒤 단계용 확인 항목 틀** (작업 기록 "뒤 단계용 확인 항목(claude)" 절에 이 표를 씀. 1단계가 읽다가 본 것 가운데 뒤 단계로 넘기는 것만)

| # | 무엇 (절차 4번 순서 3 "뒤 단계로 넘김"의 1 ~ 4) | 관련된 곳 (CID · 디스크립션 번호) | 넘기는 곳 (2단계 / 3단계) | 이어진 번호 (Q · C · 논의 대상 ID / 근거로 풀림) |
| --- | --- | --- | --- | --- |
| 1 | 1. 기능 정의가 안 된 요소: 2-1 "Scan" 설명이 비어 있음 | LI-TSS-PSI-SAM-01-01 #2-1 | 3단계 질문 대기 | |
| 2 | 3. 반영 대기 R03가 `대기 (확인 필요)` | LI-TSS-PSI-SAM-01-01 R03 | 2단계 | |

- 1단계에서 푸는 것(IA와 다른 곳, 요청자만 알 수 있는 물음)은 이 표에 적지 않고 "요청자 확인"에 적습니다.
- "이어진 번호"는 비워 둡니다. 뒤 단계에서 그 물음을 처리할 때 채웁니다(3단계 마침 점검 6에서 확인).

**대상 화면의 반영 대기 항목 틀** (작업 기록 "대상 화면의 반영 대기 항목" 절에 이 표를 씀)

| 묶음 (근거) | 화면 (CID) | 항목 ID | 변경 전 | 변경 후 | 반영 / 이번엔 안 함 / 제외 (바꾸지 않음) |
| --- | --- | --- | --- | --- | --- |
| 1 표기 기준 (`archive/glossary/review-v0.md`) | Event History (TI-EVT-P) | TI-EVT-P-R05 | Expiration date Status, Under 30 Day | 대소문자 통일, Under 30 days | |

- 항목은 대상 화면(작업 대상이 `O` · `미정`인 화면)의 CID로 반영 대기 목록(`pending/open.md`)을 걸러 상태가 `대기` · `대기 (확인 필요)`인 것만 옮깁니다. 칸의 값은 반영 대기 목록(`pending/open.md`)에 적힌 그대로 씁니다.
- 상태 괄호 안에 이유가 적힌 `대기` 항목(예: `대기 (이 화면에 없는 글자, 2026-11-06 이번엔 안 함)`)도 다른 `대기` 항목과 같이 옮겨 묻습니다. 이번에 반영하지 않으면 `대기` 그대로 두고, 요청자가 제외한다고 말할 때만 `제외 (날짜, 이유)`로 바꿉니다(케이스 규칙과 부딪히는 항목은 위 절차 4번 순서 5에서 이미 제외함).
- 근거가 같은 항목은 같은 묶음 번호로 묶습니다. 절차 5번 질문 6은 묶음마다 묻습니다. 값을 함께 묻는 `대기 (확인 필요)` 항목(절차 4번 순서 3 "뒤 단계로 넘김"의 3)은 항목마다 묻고, 고른 값은 "변경 후" 칸에 채웁니다.
- "반영 / 이번엔 안 함"은 비워 두고, 절차 5번에서 답을 받은 뒤 채웁니다. "반영"으로 고른 항목은 반영 대기 목록(`pending/open.md`)에서 상태를 `작업 중 (작업 기록 이름)`으로 바꿉니다(`reference-rules/pending-changes.md` 4절). 테스트로 할 때는 바꾸지 않습니다.
- 옮길 `대기` 항목이 없으면 "대상 화면에 `대기` 항목 없음"을 기입합니다.

## 마침 점검

다음 단계로 넘어가기 전에 모두 통과해야 합니다(절차 5번 "답을 받은 뒤" 3).

- 요청자 확인의 답을 받았고, 답대로 요건 목록(요건마다 경로 포함) · 머리말을 고쳤음
- 요건 목록의 작업 대상에 `미정`이 남아 있지 않음
- 대상 화면의 반영 대기 항목마다 반영 / 이번엔 안 함이 적혀 있음
