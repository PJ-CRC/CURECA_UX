# 3. 화면 설계

> 초안 · v0.45. "※ 정할 것" 표시는 이 문서 끝 "정할 것"에 안이 있습니다.

1단계 요건과 2단계 근거로 **화면 MD를 쓰고, 그것을 그대로 Figma에 그리는** 단계입니다. 화면 MD가 원본이고 Figma는 화면 MD를 옮긴 것입니다(헌법 6조). 질문이 있어도 먼저 그리고 질문 대기로 표시합니다(화면 라벨 · 사용자 확인 목록).

작업 기록 "요건별 진행 경로"에서 3단계를 지나가는 요건만 그립니다. 경로 분기 기준 7 "정책만 바뀜"인 요건과 1단계에서 끝난 요건은 3단계가 "해당 없음"입니다(`flow/README.md` "단계를 지나는 규칙").

## 이 문서를 읽는 법

**3단계를 시작할 때 작업 기록 "요건 목록"에서 작업 대상이 `O`인 줄의 케이스를 확인하고, 화면(CID)마다 그 케이스의 흐름을 따릅니다.**

| 케이스 | 따를 흐름 |
| --- | --- |
| 1 화면 부분 수정(고도화) | 아래 "케이스 1 흐름" |
| 2 신규 | 아래 "케이스 2 흐름" |
| 3 기존 화면 다시 그리기 | 아래 "케이스 3 흐름" |

**화면(CID)마다 묶어 그립니다.** 작업 기록 "요건 목록"에서 작업 대상이 `O`인 줄을 대상 화면(CID)마다 모읍니다. 한 화면의 줄은 케이스가 같으므로, 화면마다 그 케이스의 흐름을 한 번 따르며 그 화면의 요건을 모두 반영합니다. 화면 MD · 복제본 · Figma는 화면마다 한 번 고치고, 변경 확인은 요건마다 둡니다. 모은 결과는 작업 기록 "설계" 절의 화면별 표(화면 (CID) · 케이스 · 요건 번호)에 적습니다(아래 "남는 것").

- 케이스 흐름은 **순서**입니다. 단계마다 그 케이스에만 해당하는 것은 흐름 안에 적었고, 모든 케이스가 같은 것은 "공통 규칙"에 한 번만 적고 흐름에서 `공통 1-2`처럼 가리킵니다.
- 다른 케이스의 흐름은 따르지 않습니다.
- 따른 케이스는 작업 기록 "설계" 절의 "화면별 요건" 표에 화면(CID)마다 적습니다. 끝 관문에서 확인합니다.
- **다시 고칠 때도 같은 순서입니다:** 3단계 안에서 요청자 의견으로 다시 고칠 때도 화면 MD(디스크립션)를 먼저 고치고 그다음 Figma를 고칩니다(헌법 6조). 버튼 위치 · 영역 크기처럼 배치만 바뀌는 수정도 같습니다.
- 케이스 3 기존 화면 다시 그리기는 기존 메뉴를 작업방으로 다 옮기면 없어집니다. 그때 이 문서에서 "케이스 3 흐름"과 공통 규칙 안의 케이스 3 표를 지웁니다.

## 읽을 것 (모든 케이스)

1. 작업 기록: "요건 목록"(작업 대상이 `O`인 줄, 영향 화면), "읽은 기존 화면"(기존 원본의 케이스 화면 포함), "요건별 진행 경로", "확인할 것", "이번에 반영할 반영 대기 항목", "근거"의 **읽은 자료 목록** · 관련 자료 없는 영역 · 요소 · 대조 · 정책 수정 범위 · 용어 목록, "이 작업의 결정", 질문 대기
2. **읽은 자료 목록에서 "설계에 씀"이 `O`인 자료.** 이 자료를 읽고 시작하며, 영역 · 요소를 그릴 때 그 영역에 쓰는 자료를 읽습니다. `-`인 자료는 읽지 않습니다. `관련 자료 없음`인 영역은 정책 · 가이드를 다시 찾지 않고 `공통 3-3` 요소를 찾는 순서로 그립니다.
3. `templates/screen.md` (화면 MD 틀), `reference-rules/description.md` (디스크립션 쓰는 법), `examples/`의 작성예시문서
4. UX가이드의 "Figma 컴포넌트" 표(컴포넌트 · Variant), `reference-rules/guide-element-defaults.md` (가이드 요소 기본값)
5. 그릴 Figma 페이지: 그리기 전에 먼저 열어 무엇이 있는지 확인함. 있던 그림은 옮기거나 지우지 않음

- **표시된 자료만으로 정의할 수 없는 것이 나오면 추가로 자료를 찾아 읽을 수 있습니다.** 읽은 자료는 작업 기록의 "읽은 자료 목록"에 `(3단계에서 추가)`를 붙여 더하고 설계에 씀을 표시합니다. `-`로 뺐던 자료를 쓰게 되면 `O`로 바꿉니다. 읽고도 목록에 남기지 않는 일은 없어야 합니다.
- 추가로 읽다가 정책과 기존 화면이 다른 곳을 새로 찾으면 2단계 "대조" 표에 더하고, 정책을 바꿔야 하면 요청자에게 알립니다.
- 디스크립션 번호가 정해지면 목록의 "쓰는 화면 · 영역 · 요소" 칸에 새 번호를 덧붙입니다.

## 케이스 1 흐름 — 화면 부분 수정(고도화)

이미 있는 화면(T · L 모두)을 요청에 따라 일부 고칩니다. 고칠 범위는 1 · 2단계에서 정해져 옵니다.

| 순서 | 할 일 | 자세히 |
| --- | --- | --- |
| 1 | 작업 기록 "설계" 절 "화면별 요건" 표에 이 화면과 케이스 1을 적고 "읽을 것"을 읽음 | |
| 2 | **T 화면 MD를 먼저 고침** | 아래 1-2 |
| 3 | 바뀐 곳마다 변경 확인을 둠 | 아래 1-3 |
| 4 | **Figma를 열어 복제본을 만들고 T 원본을 고침** | 아래 1-4 |
| 5 | 같은 CID의 케이스 화면을 함께 고침 | 아래 1-5 |
| 6 | **요건 목록에서 작업 대상이 `O`인 짝 화면(L)에** 같은 순서로 고침 (2 ~ 5) | 아래 1-6 |
| 7 | 마무리 확인 (T · L 한 쌍), 작업 기록 `이어서 작업할 곳:` 고침 | `공통 3-10` |
| 8 | 용어 점검 → 작업 기록 "설계" 절 → 끝 관문 → 답해 주실 것 | `공통 7`, 아래 "남는 것" · "끝 관문" |

**1-2. 화면 MD 고치기**

- `templates/screen.md` 구조를 그대로 씁니다(절을 빼거나 더하지 않음).
- 1 · 2단계에서 넘어온 것(작업 기록 "요건 목록"에서 작업 대상이 `O`인 줄의 요건, "확인할 것", 2단계 대조 결과)만 고칩니다. 고칠 범위는 1 · 2단계에서 정해져 오므로 3단계에서 따로 넓히지 않습니다. 화면 MD 변경 이력에 변경한 번호를 남깁니다.
- 기존 화면에 바로 고치며(시안을 따로 만들지 않음, 복제본은 1-4), 확정을 기다리지 않고 수정안이 바뀔 때마다 디스크립션을 화면과 함께 고칩니다.
- 디스크립션 · 화면 예시 · 케이스 표 · 반영 대기 · 작업 중 결정 · 가이드 요소 · 화면 표기 글자 표는 `공통 1`대로 씁니다.
- **번호:** 있던 번호는 바꾸지 않습니다. 요소를 **더하면 끝 번호**를 붙입니다. 단독 기능이면 화면의 맨 끝 번호 다음, 이미 번호가 있는 영역에 속하는 기능이면 그 영역의 맨 끝 번호 다음이며, 화면에서 놓이는 위치와 상관없습니다. 요소를 **빼면** 번호를 그대로 두고(디스크립션은 취소선), 비어 있는 번호는 다시 쓰지 않습니다. 번호를 화면 순서대로 다시 매기는 것은 큰 업데이트 때입니다(`flow/5-done.md`). 예(TI-SPT-01 Samples, 지금 1 검색 영역 1-1 ~ 1-6 · 2 리스트 · 3 [Export] · 4 페이지네이션): 검색 영역에 Sample Type 조건을 더하면 1-7 / 리스트 위에 [Print] 버튼을 더하면 5 / STAT Only를 빼면 1-6은 번호와 글을 그대로 둠
- 변경 종류마다 디스크립션은 아래 1-3 표의 "디스크립션" 칸대로 처리합니다.

**1-3. 변경 확인**

바뀐 곳마다 변경 확인을 둡니다(번호 · 화면 라벨 · 사용자 확인 목록 · 화면 MD 표 · 작업 기록 표는 `공통 2`). 업데이트 메모 제목은 `v{Ver} update`(Ver은 4단계 UX 확정 때 요청자가 정함, `reference-rules/description.md` 7절 "화면 정보에 적는 값", 색은 `reference-rules/description.md` 5절 "업데이트 메모"의 색 규칙).

| 변경 | 디스크립션 | 사용자 확인 목록 문구 | 화면 라벨 |
| --- | --- | --- | --- |
| 더함 | 새 번호로 씀 | `{요소} 추가 (이유)` | 그 번호 표시 옆 |
| 바꿈 | 그 번호의 글을 고침 | `{기존} → {바꾼 것} (이유)` | 그 번호 표시 옆 |
| 뺌 | 글을 지우지 않고 **3단계에서 바로 취소선**을 그음(개발자가 지운 것을 알 수 있게) | `화면에서 제거, 확정 시 취소선 처리 예정 (이유)` | **두지 않음.** 화면에서 요소와 번호 표시를 떼므로 사용자 확인 목록에만 둠 |
| 케이스를 지움 | 뺀 요소 때문에 필요 없어진 케이스는 바로 지움 | 본 화면 사용자 확인 목록 문구 끝에 `… Case n 삭제` | 케이스 조각에는 두지 않음 |

- 4단계에서 확인되면 다른 변경 확인과 같이 **Figma의 사용자 확인 목록 항목과 화면 라벨의 ID만 지웁니다.** 업데이트 메모는 4단계에서 UX 확정을 기입할 때 만듭니다(`reference-rules/description.md` 5절 "업데이트 메모"). 뺀 요소의 취소선 디스크립션은 지우지 않고 남깁니다.
- 고객 논의로 뺀 기능이 되살아나면 취소선과 Figma의 사용자 확인 목록 항목을 지우고 화면에 요소를 다시 넣습니다.
- 정해지지 않은 곳은 질문 대기(`공통 2`)입니다.

**1-4. Figma: 복제본을 만들고 원본을 고침**

- **복제본:** 원본을 고치기 직전에 원본의 복제본을 하나 만들어 두고, 고치는 것은 원본에 바로 합니다(고객 요청으로 원복하는 경우가 있음). T · L 각각 만듭니다.
  - 이름은 `CID-복제본`(예: `TI-SPT-01-복제본`), 위치는 원본 아래 200px입니다. 원본 높이가 바뀌면 복제본을 다시 원본 아래 200px로 옮깁니다(위치는 Figma 구조를 확인한 뒤 다시 정함, `background/todo.md` 3-8).
  - 4단계(수정 · 확인)가 끝나면 지웁니다.
  - 복제본은 바탕 · 후보 · 화면 MD 추출의 근거로 쓰지 않습니다.
- 화면 MD를 그대로 옮기며, 바뀌는 요소만 건드립니다. 컴포넌트 · 예시 데이터 · 번호 표시 · 질문 표시는 `공통 3`대로 합니다.
- 더하는 요소는 `공통 3-3`의 **"케이스 1 · 2" 표** 순서로 찾아 그립니다(가이드 컴포넌트 → 후보 → 신규로 만듦).
- 더한 요소에는 1-2의 끝 번호로 번호 표시를 붙이고, 바꾼 요소는 번호 표시를 그대로 두며, 뺀 요소는 요소와 번호 표시를 뗍니다.
- **패널:** `공통 3-6`대로 옮기고, 화면 정보의 Date는 작성일, 작성자는 요청자. Ver은 4단계 UX 확정 때 요청자가 정해 기입함(그 전까지 기존 화면의 Ver 그대로, `reference-rules/description.md` 7절 "화면 정보에 적는 값").

**1-5. 케이스 화면 함께 고치기**

본 화면을 고치면 같은 CID의 케이스 화면도 함께 고칩니다(케이스 화면 공통 규칙은 `공통 5`).

1. 고칠 케이스는 화면 MD 케이스 표의 "디스크립션 번호" 칸으로 찾고, 그 CID의 케이스 조각을 모두 훑어 고친 요소가 그려져 있는지도 봅니다.
2. 더한 요소의 그 조건에서의 값을 모르면 요청 · 정책에 있는 값, 없으면 본 화면과 같은 예시 값을 넣고 질문 대기를 둡니다.
3. 뺀 요소 때문에 필요 없어진 케이스는 확정을 기다리지 않고 바로 지우고, 케이스 표에 지웠다는 것을 남깁니다(그 Case 번호는 다시 쓰지 않음).
4. 케이스 조각에서 생긴 질문 · 변경은 그 조각의 번호 표시 옆에 화면 라벨을 두고, 사용자 확인 목록 항목은 본 화면의 사용자 확인 목록에 둡니다. 본 화면 변경이 케이스에도 걸리면 사용자 확인 목록 문구에 걸린 케이스를 적습니다(예: `… Case 1 · 3에도 반영`, `… Case 2 삭제`).

**1-6. L 화면**

요건 목록에서 짝 화면(L)의 작업 대상이 `O`이면, L 화면이 이미 있으므로 T를 복제하지 않고, L 원본의 복제본을 만든 뒤 T와 같은 순서(화면 MD → 변경 확인 → Figma → 패널 → 케이스 화면)로 L 화면을 고칩니다. L 디스크립션이 T를 가리키는 말 없이 완결인지 확인합니다. T · L 번호는 따로 관리합니다(`공통 3-7`).

## 케이스 2 흐름 — 신규

없던 화면을 새로 그립니다. 비교할 기존 화면이 없습니다.

| 순서 | 할 일 | 자세히 |
| --- | --- | --- |
| 1 | 작업 기록 "설계" 절 "화면별 요건" 표에 이 화면과 케이스 2를 적고 "읽을 것"을 읽음 | |
| 2 | **구상:** 틀 · 영역 · 요소를 정하고 구상안 표로 남김 | 아래 2-2 |
| 3 | **T 화면 MD를 틀부터 새로 씀** | 아래 2-3 |
| 4 | 질문 대기만 둠 (변경 확인은 두지 않음) | 아래 2-4 |
| 5 | **Figma에 T를 그림** | 아래 2-5 |
| 6 | 케이스 화면을 그림 (점검 포함) | 아래 2-6 |
| 7 | **L: 다 그린 T를 복제한 뒤 다른 점만 바꿈** (짝이 없는 화면이면 건너뜀) | `공통 3-5` |
| 8 | 마무리 확인 (T · L 한 쌍), 작업 기록 `이어서 작업할 곳:` 고침 | `공통 3-10` |
| 9 | 용어 점검 → 작업 기록 "설계" 절 → 끝 관문 → 답해 주실 것 | `공통 7`, 아래 "남는 것" · "끝 관문" |

**2-2. 구상**

화면 MD를 쓰기 전에 화면을 어떻게 짤지 정하고 **구상안 표**로 남깁니다. 구상안은 요청자에게 먼저 보여 주고 확인받지 않습니다. 묻지 않고 바로 그리고, 구상안 표는 기록으로 남깁니다(확인이 늘면 작업이 막히므로).

1. **하는 일 정하기:** 요청 글 · 요건 목록 · 2단계 근거(부르는 화면 · 형제 화면 · 같은 데이터)에서 새 화면의 목적 · 하는 일을 정합니다. 근거가 없는 것은 질문 대기로 두고 4단계에서 받습니다.
2. **틀 정하기:**
   - **Page = 레이아웃 구조 가이드의 9종**(공용 저장소 `PJ-CRC/CURECA_UX`의 `docs/layout_structures/Layout_Structure.html`): 1 대시보드 · 2 목록(테이블) · 3 목록 + 상세 패널 · 4 상태 모니터링 · 5 탭 + 장비 매트릭스 · 6 탭 + 목록 · 상세 분할 · 7 카드 선택 · 8 단계 진행 · 9 차트 + 필터 패널
     - 요청에 레이아웃이 정해져 있으면 그것을 따릅니다. Workbench에서는 요청 칸의 「레이아웃 선택」이 바로 이 9종이고, 고른 것이 요청에 `3. 목록 + 상세 패널`처럼 번호 · 이름으로 들어옵니다. 하는 일과 안 맞아 보여도 묻지 않고 고른 대로 그리고, 구상안 표에 "요청자가 고른 레이아웃"이라고 남깁니다.
     - 정해져 있지 않으면 Claude가 고릅니다. 가이드 "레이아웃 고르기" 표의 "화면이 하는 일"을 1번에서 정한 "하는 일"과 맞춰 봅니다(요약 → 1 / 목록이고 상세를 다른 화면으로 이동 → 2, 같은 화면 패널 → 3, 늘 함께 → 6 / 진행률 반복 → 4 / 장비 비교 → 5 / 작업 고르는 첫 화면 → 7 / 단계별 안내 → 8 / 추이 분석 → 9). 맞는 것이 둘 이상이면 1번에서 정한 "목적"에 해당하는 것, 그래도 갈리면 같은 메뉴의 다른 화면이 쓰는 구조를 고릅니다. 맞는 것이 없으면 억지로 고르지 않고 공통 틀 · 배치 원칙만 따라 그린 뒤 질문 대기 `맞는 레이아웃 구조 없음`을 둡니다.
   - **Popup = Common UX의 Popup(COMM-5-m).** 안의 내용은 화면 요소를 구성하는 방법과 똑같이 합니다(`공통 3-3`). Basic Popup의 Case는 Common UX의 "쓰임"으로 고릅니다: Case 1 단순 정보 전달 / Case 2 입력 · 선택 후 저장 / Case 3 저장 불필요.
3. **영역 나누기 → 영역마다 들어갈 요소 → 요소마다 쓸 것**(`공통 3-3` 요소를 찾는 순서)을 정합니다.
4. **구상안 표**를 작업 기록 "설계" 절에 남깁니다(아래 "남는 것"). 고른 레이아웃 · 고른 이유 · 고르지 않은 구조 · 맞는 구조가 없었는지 같은 판단도 적습니다.

**2-3. 화면 MD 새로 쓰기**

- `templates/screen.md` 구조를 그대로, 틀부터 새로 씁니다(절을 빼거나 더하지 않음).
- 1단계에서 정한 CID를 화면 MD · 섹션 · 화면 정보에 채웁니다. 구상하다 화면이 더 생기면 그 메뉴의 번호를 이어 붙이고 작업 기록에 더합니다. CID는 5단계(완료)에서 요청자가 한 번 확정합니다(`flow/1-requirements.md` "새 화면의 CID").
- 0번의 L-IOS Client Mode는 근거가 있어도 늘 질문 대기로 두고 4단계(수정 · 확인)의 고객 리뷰에서 답을 받습니다.
- **번호:** 화면 · 디스크립션 번호를 처음부터 매깁니다(구상안 표의 번호 순서).
- 디스크립션 · 화면 예시 · 케이스 표 · 반영 대기 · 작업 중 결정 · 가이드 요소 · 화면 표기 글자 표는 `공통 1`대로 씁니다.

**2-4. 질문 대기 · 변경 확인**

- 변경 확인은 두지 않습니다(비교할 기존 화면이 없음).
- 정해지지 않은 곳은 질문 대기(`공통 2`)입니다. Claude가 판단한 곳(레이아웃 고르기, 후보 · 신규, Popup의 Case, 케이스 점검)은 질문 대기 없이 기록으로 남깁니다(`공통 2`).

**2-5. Figma 그리기**

- 화면 MD를 그대로 그립니다(`공통 4` 작업방 구성).
- 요소는 `공통 3-3`의 **"케이스 1 · 2" 표** 순서로 찾아 그립니다(가이드 컴포넌트 → 후보 → 신규로 만듦).
- 컴포넌트 · 예시 데이터 · 번호 표시 · 질문 표시 · Popup은 `공통 3`대로 합니다.
- **패널:** `공통 3-6`대로 옮기고, 화면 정보의 Date는 작성일, 작성자는 요청자. Ver은 4단계 UX 확정 때 요청자가 정해 기입함(그 전까지 비워 둠, `reference-rules/description.md` 7절 "화면 정보에 적는 값").

**2-6. 케이스 화면**

`공통 5`대로 그립니다. 근거는 디스크립션 조건 · 요청자입니다. 빠뜨린 조건이 없는지 **구상에서 참고한 기준 화면의 케이스를 한 번 훑어** 점검합니다. 같은 종류의 조건이 신규 화면에도 있고 근거(요청 · 정책 · 2-2 구상 1번에서 정한 목적 · 하는 일)가 있으면 디스크립션에 적고 그립니다. 근거 없이 기준 화면만 보고 그린 케이스는 질문 대기 `이 케이스가 필요한지 (참고한 화면 · Case)`로 둡니다(요청자는 필요한지만 답하면 됨). 점검한 내용은 작업 기록 "찾은 것"에 남깁니다.

**3-2. 화면 MD 새로 쓰기**

- `source: asis` → `tobe`로 바꿔 `templates/screen.md` 틀대로 새로 쓰고(절을 빼거나 더하지 않음), 변경 이력에 "작업방에 새로 그림 (기존 작업방 링크 · Ver)"을 남깁니다.
- 기존 원본에 있던 케이스 화면은 빠짐없이 옮깁니다(Case 번호 그대로).
- 디스크립션 · 화면 예시 · 케이스 표 · 반영 대기 · 작업 중 결정 · 가이드 요소 · 화면 표기 글자 표는 `공통 1`대로 씁니다.
- **번호:** 기존 디스크립션 번호를 그대로 씁니다(다시 매기지 않음). 기존 디스크립션에서 취소선으로 처리된 항목은 디스크립션에서 지우고, 화면 위 그 번호 표시도 지웁니다. 빈 번호(예: TI-SPT-01의 1-3)는 그대로 둡니다. 지운 것은 사용자 확인 목록의 0번(화면 정의) 블록에 변경 확인 한 줄로 둡니다(화면 라벨은 두지 않음): `취소선 항목 n개 지움 (기존 디스크립션에서 이미 지운 기능)`.
- **기존 디스크립션에 없는 설명을 더할 때:** `reference-rules/description.md` 3절 "공통 UX가 화면에 맡긴 것" 때문에 기존 디스크립션에 없던 설명을 더하면(예: 표의 칸 구성), 화면 글자 · 정책에서 채우고 변경 확인을 둡니다(사용자 확인 목록 문구 예: `표출 항목 추가 (기존 디스크립션에 칸 구성 없음)`).

**3-3. 변경 확인**

기존 화면과 다르게 그린 곳마다 변경 확인을 둡니다(언제 두는지 · 번호 · 표는 `공통 2`). 업데이트 메모는 기존 작업방의 그 화면 메모를 그대로 옮겨 옵니다(`reference-rules/description.md` 5절 "업데이트 메모"). 정해지지 않은 곳은 질문 대기(`공통 2`)입니다.

**3-4. Figma 그리기**

- 화면 MD를 그대로 그립니다(`공통 4` 작업방 구성). 컴포넌트 · 예시 데이터 · 번호 표시 · 질문 표시 · Popup은 `공통 3`대로 합니다.
- 요소는 `공통 3-3`의 **"케이스 3" 표** 순서로 찾아 그립니다(가이드 컴포넌트 → 기존 UX 화면설계서에서 따옴 → 직접 그리고 변경 확인).
- **패널:** `공통 3-6`대로 옮기고, 화면 정보의 Ver · Date · 작성자를 기존 화면 그대로 적음. 도중에 고객 요청으로 내용이 바뀌면 그 화면은 케이스 1로 보고 Date · 작성자를 바꿈.

## 공통 규칙 (모든 케이스)

케이스 흐름에서 `공통 …`으로 가리키는 곳입니다. 케이스마다 다른 것은 위 흐름에 있습니다.

### 공통 1. 화면 MD 쓰기 (CID마다)

1. `templates/screen.md` 구조를 그대로 씁니다(절을 빼거나 더하지 않음). 어떻게 시작하는지는 케이스 흐름(1-2 / 2-3 / 3-2)을 따릅니다.
2. **디스크립션:** 먼저 작성예시문서(`examples/description-samples.md`)를 읽고 그 결로 씁니다. 목록 화면은 작성예시문서 1, 그 밖의 화면은 작성예시문서 2를 따르고, 차트가 있는 화면만 작성예시문서 3을 함께 봅니다. `reference-rules/description.md`대로 화면의 모든 영역 · 요소에 빠짐없이 씁니다. 개조식(명사로 끝냄)으로, 그 화면에서 보이고 일어나는 일을 풀어 쓰고 정책 ID는 블록 끝 `● 정책 참고`에만 둡니다(헌법 3조). T-IOS · L-IOS는 각자 완결합니다.
3. **화면 예시 표:** 그릴 때 넣을 값을 기준데이터에서 가져와 적고 "기준" 칸에 출처를 적습니다. 상태값은 `status-values.csv`, Module · Unit은 `module-units.csv`, 품목 · 수량은 `consumables.csv` · `pcr-reagents.csv`의 UI 표기입니다. 기준데이터에 없는 목록 제목 · 설명 글만 상황에 맞게 지어 씁니다.
4. **케이스 화면:** 화면 MD "케이스" 표에 근거가 있는 것만 적습니다(`공통 5`). 근거 없이 Claude가 판단해 더하지 않고, 더 필요해 보이면 질문으로 올립니다.
5. **반영 대기 항목:** 1단계에서 "이번에 반영"으로 고른 항목(상태 `작업 중`)만 반영합니다. 고르지 않은 `대기` 항목은 건드리지 않습니다. 화면에 반영해도 상태는 `작업 중` 그대로 두고, 5단계 완료 때 `반영 완료`로 바꿉니다(`reference-rules/pending-changes.md` 4절)
6. **작업 중 결정:** 2단계에서 정한 결정(`결정` + 이 작업 기록)을 기준으로 씁니다. 정책서는 아직 고치지 않았으므로 디스크립션에는 결정 내용을 풀어 쓰고, 어느 논의 대상에서 온 것인지는 화면 MD 머리말(정책 참고)에 `POL-EQP-004 · DS-0012`처럼 적어 둡니다(디스크립션 · 패널에는 논의 대상 ID를 쓰지 않음). 5단계 반영 뒤 머리말의 논의 대상 ID를 뗍니다.
7. **기존 화면에 없는 가이드 요소:** 2단계에서 찾은 것을 `reference-rules/guide-element-defaults.md` 기본값 표대로 처리합니다. "넣음"은 넣고 변경 확인을 둡니다(기존 화면에 없던 요소가 생긴 것이므로). "물음"과 표에 없는 요소는 질문 대기로 둡니다.
8. **화면 표기 글자 표:** 화면 MD "화면 표기 글자" 표에 화면에 표기되는 영어 글자를 디스크립션 번호와 함께 적습니다(칸과 상태 값은 `templates/screen.md` "화면 표기 글자"). **[초안 2026-11-17, 다시 검토]** 디스크립션에만 있고 우리 화면(케이스 화면 포함)에는 그리지 않은 글자도 적습니다. 디자인 화면에서는 그 글자를 쓸 수 있어, 바뀌면 UI 작업 대상이고 언어셋 대상이기 때문입니다. 3단계에서는 번역과 언어셋 대조를 하지 않고, "가장 긴 언어 · 번역 글자" 칸은 비워 둡니다(`flow/4-revise-verify.md` 절차 4번 "언어셋을 정리하고 UI팀에 넘길 것을 보여 줌"에서 채움).
   - **케이스 1 · 2:** 이 작업에서 생긴 글자는 상태 `신규`, 영어 글자가 바뀐 줄은 `변경`(변경 전 → 변경 후), 이 화면에서 없어진 글자는 줄을 지우지 않고 `제거`로 적습니다. 그대로인 글자는 상태를 비워 둡니다.
   - **케이스 3:** 기존 화면을 옮겨 화면 MD를 새로 쓸 때 화면에 보이는 영어 글자를 적고, Language ID · 상태 칸은 비워 둡니다(4단계 절차 4번이 언어셋 문서를 보고 채움).

### 공통 2. 질문 대기 · 변경 확인 (질문이 생기거나 기존 화면과 다르게 그릴 때)

질문 대기 · 변경 확인은 디스크립션 본문에 넣지 않고, 화면 라벨과 사용자 확인 목록에만 둡니다(`reference-rules/description.md` 5절). 케이스마다 변경 확인을 어디에 두는지와 업데이트 메모 제목은 케이스 흐름(1-3 / 2-4 / 3-3)에 있습니다.

- **번호:** 작업 하나에 통번호를 씁니다(Q1 · Q2 … / C1 · C2 …). T · L에 같은 것은 같은 번호. 화면 라벨 · 사용자 확인 목록 · 화면 MD 표 · 작업 기록에 같은 번호를 씁니다.
- **질문 대기 — 정해지지 않은 곳:** 먼저 그립니다. 따를 것을 이 순서로 찾습니다: 그 화면의 기존 원본(UX 화면설계서) → 정책서 → 공통 UX → 같은 메뉴의 다른 화면. 찾은 내용으로 그리고 쓴 뒤 질문을 화면 MD 질문 대기 표 · 작업 기록 질문 대기 · 사용자 확인 목록에 올리고 그 번호 옆에 화면 라벨을 둡니다. 넷 다 없으면 디스크립션에 지어 쓰지 않고 질문만 둡니다.
- **변경 확인 — 근거가 있어 기존 화면과 다르게 그린 곳:** 2단계 대조에서 "기존 화면이 정책과 다름"으로 나온 곳은 정책을 따라 그리고, 기존과 무엇이 달라졌는지 사용자 확인 목록에 적고 그 번호 옆에 화면 라벨을 둡니다. 반영 대기 항목을 반영해 달라진 곳, 행을 줄여 그린 곳도 같습니다. 화면 MD 변경 확인 표에 올립니다. 4단계 요청자 확인에서 맞는지 확인받고, 확인된 것은 사용자 확인 목록 항목과 라벨 ID를 지우고, **업데이트 메모**는 4단계에서 UX 확정을 기입할 때 만듭니다. 변경 확인 줄을 만들 때 화면 MD · 작업 기록 변경 확인 표의 "업데이트 메모 (O / -)" 칸을 채웁니다(`reference-rules/description.md` 5절 "업데이트 메모").
- 정책을 정해야 하는 질문이면 논의 대상을 `논의 중`으로 만들고(`work`에 작업 기록 이름) 질문 대기 표에 DS ID를 잇습니다(`reference-rules/discussions.md` "자주 있는 네 가지 경우" 라).
- 내 화면만 바뀌는 질문(표현 · 배치 · 문구)은 논의 대상을 만들지 않고 요청자가 답하면 고친 뒤 Figma의 사용자 확인 목록 항목과 라벨 ID를 지웁니다.
- **Claude가 판단해 정한 곳은 질문 대기 · 변경 확인을 붙이지 않고 기록으로만 남깁니다.** 질문 대기 · 변경 확인은 요청자가 실제로 정해 줘야 하는 것에만 씁니다. 새 표시(`※ 판단 확인` 같은 것)는 만들지 않습니다. 규칙이 Claude에게 판단을 맡긴 곳(레이아웃 고르기, 후보에서 찾아 쓰기 · 신규로 만들기, Popup의 Case 고르기, 케이스 화면 점검)은 판단한 내용을 구상안 표 · 작업 기록 "찾은 것"("규칙에 없어 판단한 곳") · "컴포넌트 없이 그린 요소" 표에 남깁니다. 요청자가 화면을 보다 이상한 곳이 있으면 이 기록에서 근거를 찾습니다. 근거가 없어 정할 수 없는 곳은 기록이 아니라 질문 대기입니다.
- 고객이 앞서 정한 결정을 다시 고치면 같은 논의 대상에 결정 줄을 더하고 화면을 새 결정으로 고칩니다(경우 다).

### 공통 3. Figma 그리기

화면 MD를 그대로 그립니다. 페이지 · 배치 · 프레임 이름은 `공통 4` 작업방 구성을 따릅니다.

1. **T · L 한 쌍씩 순서대로:** 목록 화면 → 상세 → Popup처럼 메뉴 흐름 순서로, 같은 CID의 T · L 한 쌍마다 T를 먼저 끝내고 바로 L을 그립니다.
2. **컴포넌트:** 가이드 "Figma 컴포넌트" 표의 컴포넌트를 인스턴스로 씁니다. 떼어 내지(detach) 않고 속성(Variant) · 글자 · 크기 · 보이기만 바꿉니다. 맞는 Variant가 있으면 그것을 쓰고, 없으면 그 컴포넌트의 기본 Variant를 쓴 뒤 질문 대기를 둡니다. 다른 컴포넌트로 바꿔 쓰지 않습니다. ※ 정할 것 1
   - **기획 공통 컴포넌트:** 화면 요소가 아닌 기획 표시는 UX-AI-TEST 파일 Common UX 페이지의 **SB-Components (기획 공통)** 프레임([`2673:21866`](https://www.figma.com/design/etCQFF3CTf1EA6C79d4BBf/UX-AI-TEST?node-id=2673-21866))의 컴포넌트를 인스턴스로 씁니다: 시스템 구분 표시(`시스템 구분`) · 기획 진행 표시(`진행상태-기획`)는 `공통 4`, 패널(`Description`) · 번호 표시(`Description Number`) · 업데이트 메모(`ver`)는 `reference-rules/description.md` 7절 · 5절, 화면 라벨 · 사용자 확인 목록(`Label/Status/With Icon` · `Review List/…` · `사용자 확인 목록 (Template)`)은 같은 문서 5절.
3. **요소를 찾는 순서:** 요소를 그릴 때 쓸 것을 아래 순서로 찾습니다. **순서가 케이스마다 다르므로 자기 케이스의 표를 따릅니다.**

   **케이스 1 화면 부분 수정(고도화) · 케이스 2 신규**

   | 순서 | 상황 | 그리는 법 |
   | --- | --- | --- |
   | ① | 가이드에 컴포넌트가 있음 | 가이드 컴포넌트를 씀 (위 2번) |
   | ② | 가이드에 없고, 후보 목록(`common-ux/candidates.md`)에 맞는 것이 있음 | 후보를 가져다 씀. 목록의 "Figma 링크"에서 값을 읽어 **같은 값으로** 그리고, 작업 기록 "컴포넌트 없이 그린 요소" 표에 후보 ID를 남김 |
   | ③ | 후보에도 적절한 것이 없음 | **신규로 만들어 씀.** 묻지 않고 만들어 그리고, 작업 기록 "컴포넌트 없이 그린 요소" 표에 "신규로 만듦"으로 남김 |

   - **후보 목록에 "맞는 것":** 화면 MD 디스크립션에 적힌 그 요소의 종류 · 하는 일이 후보 목록의 "요소 이름 (종류)" · "하는 일"과 같으면 맞는 것으로 봅니다. 같은지 애매하면 가장 비슷한 후보로 그리고 질문 대기 `{후보 ID}를 써도 되는지`를 둡니다.

   **케이스 3 기존 화면 다시 그리기**

   | 순서 | 상황 | 그리는 법 |
   | --- | --- | --- |
   | ① | 가이드에 컴포넌트가 있음 | 가이드 컴포넌트를 씀 (위 2번) |
   | ② | 가이드에 없고, 그 화면의 기존 UX 화면설계서에 있음 | 그 요소를 똑같이 따옴. 기존 프레임에서 크기 · 색 · 글자 크기 · 간격 값을 읽어 **같은 값으로** 그리고, 읽은 원본 위치를 화면 예시 표의 "기준" 칸에 적음. 따온 요소는 작업 기록 "컴포넌트 없이 그린 요소" 표에 "기존 화면에서 따옴"으로 남김 |
   | ③ | 가이드에도 기존 화면에도 없음 | **직접 그리고 변경 확인을 둠.** 기존 화면에 없던 것이 생긴 것이므로 요청자가 확인할 수 있게 표시하고, 작업 기록 "컴포넌트 없이 그린 요소" 표에 "신규로 만듦"으로 남김 |

   어느 케이스든 아래는 같습니다.
   - **가져다 쓰는 것은 근거가 확인된 것이어야 합니다.** 테스트로 그린 그림과 완료되지 않은 그림은 바탕으로도 후보로도 쓰지 않습니다.
   - **후보** = 후보 목록(`common-ux/candidates.md`)에 있는 요소. 가이드에는 없지만 완료된 다른 화면에서 이미 쓰고 있는 것입니다. 목록에는 5단계 완료 때만 올리므로(`common-ux/candidate-rules.md`) 3단계에서는 목록에 쓰지 않고 작업 기록에만 남깁니다.
   - 기존 화면은 **UX 화면설계서**(기존 작업방에서 오른쪽에 화면 정보 · 디스크립션 패널이 붙은 너비 2252의 기획 프레임과 그 디스크립션)만 근거로 씁니다. 디자인 화면(1920×1080 디자인 프레임 · 디자인 파일)에서는 가져오지 않습니다.
   - 가이드에 그림만 있고 컴포넌트가 없는 경우도 "가이드에 컴포넌트가 없는 요소"로 봅니다.
   - 컴포넌트 없이 그린 요소는 어디서 가져왔는지(후보 · 신규로 만듦 · 기존 화면에서 따옴)를 작업 기록 "컴포넌트 없이 그린 요소" 표에 남깁니다.
4. **예시 데이터:** 화면 MD "화면 예시" 표의 값만 씁니다. **목록 · 표는 한 페이지 최대 노출 개수(예: 10 items)만큼 행을 채웁니다.** 최대 개수의 행이 화면 높이(1080) 안에 들어가지 않으면 들어가는 만큼만 그리고, 그린 행 수와 이유를 화면 예시 표에 적은 뒤 변경 확인을 둡니다.
5. **L은 T를 복제한 뒤 다른 점만 바꿈 (케이스 2 · 3):** LNB · GNB를 L-IOS로, CID · 호출 화면 CID를 L로, 0번에 L-IOS Client Mode 소제목, 원본에서 찾은 L만의 차이. 바꾼 뒤 L 디스크립션이 T를 가리키는 말 없이 완결인지 확인합니다. 케이스 1은 복제하지 않고 있는 L을 고칩니다(1-6).
6. **패널:** 오른쪽 패널에 화면 정보 표와 디스크립션을 화면 MD 그대로 옮깁니다. 그리는 중에 문장을 고치면 화면 MD와 Figma를 함께 고칩니다. 패널은 모든 화면에서 같은 틀 · 크기 · 위치로 그립니다(`reference-rules/description.md` 7절): 화면 오른쪽에 너비 332, 맨 위 화면 정보(Ver · Date · CID · 작성자 · 화면 · 경로), 번호 칸은 영역은 회색 · 요소는 흰색, 맨 아래 Dev · SG 줄은 두지 않음. 화면 정보의 Ver · Date · 작성자는 케이스 흐름(1-4 / 2-5 / 3-4)에 있습니다.
7. **번호 표시:** SB-Components (기획 공통) 프레임의 `Description Number` 컴포넌트(키 `8a4b8376fadaebeee5604169fd2b206cfb323b84`) 인스턴스로 둡니다. 화면 위 번호를 디스크립션 번호(영역 1 · 요소 1-1)와 같게 매깁니다. 번호를 매기는 법과 빼는 요소 · 취소선 항목의 번호 표시는 케이스 흐름(1-2 · 1-4 / 2-3 / 3-2)에 있습니다.
   - **T · L 번호는 따로 관리합니다 (모든 케이스):** T와 L은 화면마다 번호를 매기며, 같은 영역이라도 번호가 달라도 됩니다. 예: T는 4번까지, L은 L만의 요소가 있어 5번까지일 때 버튼을 더하면 T 5 · L 6.
   - **자리:** 번호 표시는 그 요소의 왼쪽 위 모서리에 걸쳐 둡니다. 글자 요소(제목 · 라벨)는 글자 바로 왼쪽에 둡니다. **케이스 3**은 기존 원본(기존 작업방 기획 프레임)의 같은 번호와 같은 자리에 두고, 기존 원본에 없는 요소만 왼쪽 위 모서리에 둡니다. 화면 라벨 때문에 빈 곳으로 옮길 때도 가리키는 요소 바로 옆을 벗어나지 않습니다.
8. **질문 표시:** 질문 대기 · 변경 확인마다 화면의 그 번호 표시 옆에 화면 라벨(`Label/Status/With Icon`)을 두고, 패널 오른쪽에 사용자 확인 목록을 둡니다(라벨 · 목록 규칙은 `reference-rules/description.md` 5절).
9. **Popup을 그리는 법 (작성예시문서 LI-RUN-P Run Preparation Popup):** ① 크기는 정해 둔 너비 · 높이 없이 내용에 맞춰 잡고, 높이를 제한하지 않고 내용을 모두 보여 주도록 길게 그립니다(스크롤 · 높이 · 일반 팝업이냐 풀 팝업이냐는 UI 디자이너가 판단). 내용이 화면 높이를 넘으면 기획 프레임을 길게 늘립니다 ② 모든 Popup은 부르는 화면을 뒤에 깔지 않고 **Dim만 깔고** 그 위에 그립니다. 여러 화면에서 부르는 공통 Popup도 같습니다.
10. **마무리 확인:** T · L 한 쌍마다 스크린샷을 찍어 아래를 보고, 고친 뒤에 다음으로 넘어갑니다. 한 쌍을 끝낼 때마다 작업 기록 `이어서 작업할 곳:` 줄을 고칩니다.
    - **글자가 칸을 넘지 않음:** 버튼 · 화면 라벨 · 표의 셀 · 입력란 · 카드 · 패널의 글자가 자기 칸 밖으로 나가거나, 잘리거나, 옆 요소와 겹치지 않음
    - 넘치면 이 순서로 고침: ① 컴포넌트의 너비 · 높이를 내용에 맞게 늘림(떼어 내지 않고 크기만) ② 가이드가 말줄임을 정한 곳(예: 표의 셀)은 말줄임으로 ③ 그래도 안 되면 배치를 넓히고, 배치를 바꿀 수 없으면 질문 대기로 남김. 글자 크기를 줄이거나 예시 값을 임의로 짧게 바꾸지 않음
    - 요소끼리 겹치지 않고, 번호 표시가 가리키는 요소 옆에 있으며, 패널이 화면 오른쪽에 붙어 있음

### 공통 5. 케이스 화면

조건에 따라 화면의 모습이 달라지는 곳을 보여 주는 그림입니다(작업 유형인 케이스 1 · 2 · 3과 다른 말입니다). 작성예시문서는 `examples/case-samples.md`이고, 이 결로 그립니다. 케이스마다 더 하는 일은 케이스 흐름(1-5 함께 고침 / 2-6 점검 / 케이스 3은 기존 원본을 빠짐없이 옮김)에 있습니다.

**케이스의 원본은 화면 MD "케이스" 표 하나입니다.** 따로 파일이나 버전을 두지 않습니다.

```markdown
| Case | 제목 | 조건 | 디스크립션 번호 | 종류 | 근거 |
| --- | --- | --- | --- | --- | --- |
| 1 | Order Reception Mode 선택에 따른 Port 입력 상태 | Push Mode / Query Mode | 3-1, 3-2 | 3 | 기존 원본 |
```

**표에 올릴 수 있는 근거는 셋뿐입니다.** 어느 것도 아니면 올리지 않고 질문으로 둡니다.

| 근거 | 뜻 |
| --- | --- |
| 기존 원본 | 기존 작업방에 있던 케이스. 빠짐없이 옮기고 Case 번호도 그대로 가져옴 |
| 디스크립션 조건 | 디스크립션에 적힌 조건 가운데 아래 여섯 종류에 드는 것 |
| 요청자 | 요청자가 그리라고 한 것 |

**"디스크립션 조건"으로 그리는 것은 여섯 종류입니다.** 여기에 들지 않는 조건(버튼 활성화 조건, 기본값 등)은 디스크립션에만 적고 그리지 않습니다.

| # | 종류 | 그리는 때 | 작성예시문서 |
| --- | --- | --- | --- |
| 1 | 상태별 데이터 노출 | 상태에 따라 어떤 값이 '-'가 되거나 버튼이 비활성화되는지 보여 줄 때 | Samples Case 1 |
| 2 | 올리거나 눌렀을 때 뜨는 것 | 툴팁, 팝업, 알럿 | Samples Case 2 |
| 3 | 유형 · 대상 · 데이터에 따라 표출 항목 구성이 다른 것 | 고른 유형이나 대상마다 보이는 항목이 다를 때. 유형마다 한 장. **데이터에 따라 요소(카드 · 영역 · 표의 열)가 생기거나 없어져 모양이 달라질 때도 여기에 듦**(예: LI-RUN-03 Capacity 카드가 있고 없음, Inventory에서 고른 품목마다 하위 정보 구성이 다름). 요소는 그대로이고 값만 비는 경우는 그리지 않고 디스크립션에 `부재 시 '-' 노출`만 적음 | Samples Details Case 2, Waste Bin/Bottle Module별 |

**그리는 법**

| 무엇 | 어떻게 |
| --- | --- |
| 두는 곳 | 케이스가 1개여도 `CID/Case` 프레임 하나에 모음. 기획 프레임 아래 100px에 둠 **(우선 이 안, 테스트해 보고 확정)** |
| 제목 | 초록 띠에 `Case 1. 제목` |
| 케이스 안 구분 | 노란 띠에 `1-1. 조건` |
| 설명 | 띠 아래 한두 줄. 왜 그렇게 보이는지 개조식으로 |
| 그림 | **달라지는 부분만** 잘라서 그림(표의 행 몇 줄, 카드 하나, 팝업 하나). 화면 전체가 달라질 때만 전체를 그림 |
| 번호 표시 | 조각에 본 화면 디스크립션의 번호를 붙임. 설명은 본 화면 디스크립션 한 곳에만 있음 |
| 패널 · 버전 | 케이스에는 패널과 화면 정보 줄(Ver · Date 등)을 두지 않음. 버전은 본 화면을 따르고, 케이스를 고치면 본 화면 변경 이력에 남김 |

- 화면 MD "케이스" 표에 있는 것을 모두 그립니다. 표에 없는 것은 그리지 않습니다.
- **늘 보이는 항목은 지우지 않습니다.** 값이 없으면 '-'로, 누를 수 없는 버튼은 Disabled로 둡니다. 항목이나 영역이 사라지는 것은 디스크립션에 `노출 조건`으로 적힌 경우뿐입니다.
- 케이스의 조건과 동작은 본 화면 디스크립션에 번호를 두고 적고, 그 블록 끝에 `● 참고 : CID/Case > Case n`을 둡니다. 케이스에서만 나타나는 요소도 본 화면 디스크립션에 번호를 줍니다.
- Case 번호는 바꾸지 않습니다. 케이스를 지워도 그 번호를 다시 쓰지 않습니다.
- T-IOS · L-IOS는 CID마다 케이스 표와 Case 프레임을 따로 둡니다.
- 여섯 종류로 특정하기 어려운 케이스(Material Setup의 [Skip] Case · Tub Guide 등)는 종류를 더하지 않고, 요청자가 직접 요청할 때 그립니다(근거 "요청자"). (저장소 화면 MD 45개의 케이스 제목으로 점검)
- **User Type에 따라 달라지는 모습, 장비사가 달라 화면이 갈리는 곳**을 케이스 화면으로 나눠 그릴지는 2단계 요청자 확인에서 물어 정합니다(`flow/2-evidence.md`). 답이 "그리지 않음"이면 디스크립션에만 씁니다. 2단계에서 놓쳤다가 3단계에서 그리며 찾으면 질문 대기로 둡니다.

### 공통 6. 영향 화면

- 같은 메뉴(같은 CID 체계)에서 함께 고칠 화면은 1 · 2단계에서 작업 기록 "요건 목록"에 작업 대상 `O`인 줄로 들어옵니다. 그 화면도 요건 목록의 줄로 보고 그 케이스의 흐름대로 그립니다.
- 다른 메뉴의 화면(작업 기록 "영향 화면" 표)은 3단계에서 고치지 않습니다. 함께 고칠지 · 반영 대기로 남길지는 5단계 완료 때 고릅니다(`flow/5-done.md`).

### 공통 7. 용어 점검

다 그린 뒤 `terms.csv`의 쓰지 않는 표현 · `glossary.md` 표기 규칙 · `status-values.csv` · `module-units.csv` UI 표기로 Figma 화면 글자 · 디스크립션 · 화면 MD를 **단어 단위로** 찾아 용어집 표기로 바꾸고, "용어 치환" 목록(원래 표현 → 표준어, 위치)을 남깁니다. 용어집에 없는 새 말은 지어 바꾸지 않고 질문으로 남깁니다.

### 답해 주실 것 (3단계 보고의 맨 끝)

## 하지 않는 것

- 2단계 관문을 통과하기 전에 그리기
- 가이드에 있는 요소를 직접 그리거나 컴포넌트를 떼어 내기
- 기준데이터에 있는 값(상태값 · Module · 품목 · 수량)을 지어 쓰기
- 한쪽 CID만 그리고 끝내기, 기획 프레임만 그리고 케이스 표에 있는 케이스 화면을 미루기
- 근거 없는 케이스를 판단으로 더하기, 케이스에서 늘 보이는 항목을 지우기, 기획 화면 전체를 복제해 값만 바꾸기(달라지는 부분만 그림)
- 질문이 있다고 그 부분을 그리지 않거나 디스크립션에서 빼기
- 출처 없는 내용을 검은 글씨로 확정처럼 쓰기
- 고르지 않은 반영 대기 항목을 반영하기, "반영 대기"로 고른 다른 화면을 고치기
- 같은 페이지의 기존 그림을 옮기거나 지우기
- 테스트로 그린 그림 · 완료되지 않은 그림을 복제해 바탕으로 쓰거나 후보로 쓰기. 케이스 1의 `CID-복제본`을 바탕 · 후보 · 화면 MD 추출의 근거로 쓰기
- 자기 케이스가 아닌 흐름을 따르기
- 기존 화면을 참고할 때 디자인 화면(디자인 프레임 · 디자인 파일)에서 모양이나 내용을 가져오기. 기존 화면은 UX 화면설계서(기획 프레임과 디스크립션)만 근거로 씀
- 기존 화면과 다르게 그리고도 변경 확인을 두지 않기
- 글자가 칸을 넘거나 잘린 채로 끝내기, 넘친다고 글자 크기를 줄이기
