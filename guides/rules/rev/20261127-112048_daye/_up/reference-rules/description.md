# 디스크립션 쓰는 법

> 상태: 초안 (2026-11-10). 작성예시문서 중심으로 다시 썼습니다. 2026-11-10부터 이 문서로 작업합니다.

디스크립션은 **고객사와 개발사가 그 화면만 보고 확인 · 개발하는 글**입니다. 화면에서 일어나는 일을 풀어 쓰고, 정책 ID는 끝에 참고로만 붙입니다(헌법 3조).

## 1. 작성예시문서를 따릅니다

**`examples/description-samples.md`의 작성예시문서 세 화면과 같은 결로 씁니다.** 이 문서의 문장과 작성예시문서가 다르게 읽히면 작성예시문서를 따릅니다. 쓰기 전에 작성예시문서를 먼저 읽습니다. 목록 화면은 작성예시문서 1, 그 밖의 화면은 작성예시문서 2를 따르고, 차트가 있는 화면만 작성예시문서 3을 함께 봅니다.

## 2. 모양

**3-2  [Save] 버튼**
- 정의
  - 입력한 내용을 저장하는 버튼
- 활성화 조건
  - 필수 항목 모두 입력 시 활성화
  - 필수 항목 미입력 시 비활성화
- 동작
  - 클릭 시 입력 내용 저장 후 목록 화면으로 이동
- 정책 참고 : POL-SMP-004

| 무엇 | 쓰는 법 |
| --- | --- |
| **말투** | 개조식. 명사로 끝냄: 노출 · 조회 · 이동 · 닫힘 · 가능 · 불가 · 미노출 처리. "~됩니다 · ~합니다"를 쓰지 않음 |
| **한 줄에 한 가지** | 한 줄에 사실 하나. 조건이 둘이면 두 줄로 나눔 |
| **화면 MD에 적는 모양** | 코드 블록 없이 씀: 번호 줄은 굵게(`**1-1  항목 이름**`), 라벨 · 내용은 아래 "라벨" 줄대로 목록 2단. 위 예시 모양 (2026-11-17 정함) |
| **번호** | 0은 화면 정의, 1 · 2 · 3은 영역, 1-1 · 1-2는 그 안의 요소. 화면 위 번호 표시와 같음. T · L 번호는 따로 관리함(같은 영역이라도 번호가 달라도 됨, `flow/3-design.md` 공통 3-7) |
| **번호 가리키기** | 디스크립션 · 업데이트 메모에서 화면 번호 표시(디스크립션 번호)를 가리킬 때는 늘 괄호 안에 번호만 씀: `(3)`, `(4-1)`. 예: `(1-1) Calendar에서 일자 선택 시 (2) · (3) 정보 업데이트`. 다른 화면의 번호는 그 화면 CID 뒤에 씀: `TI-IVT-05-T (3-3) 참고`. 원문자(①) · 대괄호(`[3]`) · `3번`으로 쓰지 않음(대괄호는 버튼 이름에만 씀). 괄호 안에 숫자만 있는 이 모양은 화면 번호에만 쓰고, 값 · 개수 · 날짜 · 코드의 숫자는 이 모양으로 쓰지 않음 (2026-11-27 정함) |
| **제목** | 영역은 `○○ 영역` · `○○ 리스트`, 요소는 이름 뒤에 종류를 괄호로: `Sample ID(Text Input)`, `Status(Dropdown)`. 버튼은 `[Save] 버튼` |
| **라벨** | 라벨 줄 아래에 내용 줄. 내용이 한 줄이면 `라벨 : 내용`. 화면 MD에서는 `●` 글자 없이 Markdown 목록 2단으로 씀: 라벨 줄은 1단(`- 라벨`), 내용 줄은 2단(`  - 내용`). **Figma 패널에서도 `●` · `-` 문자를 쓰지 않고 글 상자의 글머리 기호 목록(•)으로 옮깁니다: 라벨 줄은 1단, 내용 줄은 2단 (기존 작업방 패널과 같음)** |
| **하위 내용** | 한 줄을 더 풀 때는 그 줄보다 한 단계 더 들여쓴 글머리로 씀. 단계 수는 정하지 않고 풀수록 계속 들여씀(1단 › 2단 › 3단 …, 화면 MD는 `  ` 두 칸씩, Figma 패널은 글머리 기호 목록의 들여쓰기 단계). `ㄴ` · `-` 문자를 줄 앞에 직접 쳐서 하위 내용을 쓰지 않음(글머리 기호 목록의 기호와 다름). 글머리 기호의 모양(● · ○ · ■ 등)은 보는 도구가 단계마다 그리는 것이라 정하지 않음 (2026-11-27 정함) |
| **참고** | 블록 끝 참고 줄은 `○○ 참고 : 코드` 모양으로 한 줄씩: `공통 UX 참고 : COMM-5-f`, `정책 참고 : POL-SMP-004`, `케이스 참고 : TI-SPT-01/Case > Case 2`, `화면 참고 : TI-STN-03-01-02-01`. Alert · Confirm · Toast와 동작으로 여는 화면의 코드는 참고 줄로 빼지 않고 그 동작 줄 안에 적음(예: `[Delete] 버튼 클릭 시 Confirm 노출 : Confirm_015`, `선택 시 Popup 노출 : TI-STN-05-01-P`) |
| **뜨는 것의 이름** | Popup · Alert · Confirm · Toast는 컴포넌트 이름(용어집 표준어)으로 씀: `Confirm 노출 : Confirm_015`, `Alert 노출 : Alert_031`, `Popup 노출 : TI-TMG-01-P`. "팝업" · "알럿" · "컨펌"은 쓰지 않음(용어집 쓰지 않는 표현). 무엇이 뜨는지는 뒤에 오는 코드의 종류(Alert_ · Confirm_ · Toast_ · 화면 CID · COMM 번호)로 고름 |

### 자주 쓰는 라벨

필요한 것만 씁니다. 순서는 아래 순서를 따릅니다.

| 라벨 | 쓰는 것 | 주로 쓰는 곳 |
| --- | --- | --- |
| 정의 | 이것이 무엇인지 한두 줄 | 화면(0번), 영역, 버튼 |
| 기능 | 무엇을 하는 입력 요소인지 | 입력 · 드롭다운 · 체크박스 |
| Default | 처음 들어왔을 때의 값 | 드롭다운 · 탭 · 체크박스 · 기간 |
| 드롭다운 리스트 항목 | 실제 값을 그대로 나열 | 드롭다운 |
| 컬럼 항목 | 컬럼 이름과 그 뜻 · 표기 · 값이 없을 때 | 리스트(표) |
| 노출 항목 | 항목 이름과 그 뜻 · 표기 · 값이 없을 때 | 정보 영역 |
| 정렬 | 기본 정렬과 같을 때의 다음 기준 | 리스트 |
| 노출 조건 | 영역 · 요소가 보이거나 사라지는 조건 | 조건에 따라 달라지는 영역 |
| 활성화 조건 | 눌리는 때와 눌리지 않는 때 | 버튼 |
| 동작 | 누르거나 고르면 일어나는 일 | 모든 요소 |
| 산출 방식 · 예시 | 계산하는 법과 숫자 예 | 계산이 들어가는 값 |
| 공통 UX 참고 · 정책 참고 · 케이스 참고 · 화면 참고 | 코드 | 블록 맨 끝 |

- 리스트(표)의 컬럼은 「컬럼 항목」으로 씁니다. 작성예시문서(`examples/description-samples.md`)의 「리스트 노출 항목」 · 「테이블 노출 항목」은 기존 작업방 원문이라 그대로 두었고, 새로 쓸 때는 「컬럼 항목」으로 씁니다.

## 3. 풀어 쓰기와 정책 ID

- 화면에서 일어나는 일(조건 · 동작 · 표기 · 값이 없을 때)은 **정책서에 있어도 디스크립션에 풀어 씁니다.** 읽는 사람이 정책서를 열지 않고도 화면을 이해할 수 있어야 합니다.
- 정책 ID는 그 블록 끝 `정책 참고`에 ID만 적습니다. 규칙 번호는 적지 않습니다.
- 풀어 쓰는 범위는 **그 화면에서 보이고 일어나는 것까지**입니다. 다른 화면의 동작, 장비 안쪽 처리, 정책이 그렇게 정해진 이유는 쓰지 않습니다.
- 정책이 바뀌면 그 정책을 쓰는 화면의 반영 대기 목록에 항목이 생기고, 그때 디스크립션을 고칩니다(`reference-rules/pending-changes.md`).
- Common UX에 정의된 동작(페이지네이션, 드롭다운 열림 등)은 풀어 쓰지 않고 `공통 UX 참고`만 적습니다. 그 화면에서만 다른 점이 있으면 그것만 씁니다.

### Common UX가 화면에 맡긴 것 (디스크립션에 꼭 적음)

Common UX는 동작만 정하고 아래 값은 화면마다 정하게 했습니다. 해당 요소가 있으면 디스크립션에 빠뜨리지 않습니다. COMM 번호는 `common-ux/comm-index.md`에서 찾아 적습니다.

| 요소 | 디스크립션에 꼭 적을 것 |
| --- | --- |
| 표 (Data Table) | 컬럼 항목, 데이터가 없을 때 문구, 줄 수가 기본과 다르면 그 줄 수 |
| 정렬 (Sorting) | Default 정렬 기준(예: Date 내림차순), 정렬 가능한 컬럼 항목 |
| 페이지 (Pagination) | Pagination 유형 (Type 1 Number · Type 2 Indicator) |
| 검색 영역 (Search Bar) | 조건 칸, 입력 규칙, Default |
| 입력 · 검증 (Text Input) | 글자 수 제한, 최댓값, 오류 문구, 검증 뒤 다시 누르면 초기화하는지 |
| 드롭다운 · 선택 (Dropdown · Checkbox · Chips) | 옵션 값, Default |
| 날짜 고르기 (Calendar) | 기본 기간, 최대 기간이 기본과 다르면 그 값 |
| 날짜 · 시간 표기 | 좁은 영역에서 줄인 형식을 쓰면 그 형식 |
| 목록 노출 순서 | 공통 순서와 다르면 그 순서 |
| Popup | 어느 유형인지, 저장하지 않고 닫을 때 |
| Alert · Confirm · Toast | 코드만 그 Alert이 뜨는 동작 줄 안에 적음. 문구는 쓰지 않음(문구의 원본은 카탈로그 `alert/`) |
| Tooltip | 문구 |
| 로딩 | 어느 유형을 쓰는지 |
| 스크롤 · 화면 위로 | 어느 경우인지 |
| Badge 숫자 | 상한이 기본과 다르면 그 값 |
| 입력 방법 | 당겨서 새로고침 · 드래그 앤 드롭 · 단축키를 쓰면 그 동작 |

## 4. 꼭 지킬 것

| 지킬 것 | 내용 |
| --- | --- |
| 빠짐없이 | 화면의 모든 영역 · 요소에 번호와 디스크립션이 있음 |
| 화면마다 완결 | T-IOS와 L-IOS는 개발사가 다름. 짝 화면과 내용이 같아도 그 화면에 다 씀. "T 참고", "원문은 TI-…와 같음", "(T-IOS는 조회만 가능)"처럼 상대 플랫폼을 가리키거나 설명하지 않음 |
| 0번 | 정의 · 동작. User Type은 값만(Service, Admin, User), L-IOS Client Mode는 L-IOS에만 노출 Mode 값만. 두 값은 화면 MD 머리말 `user_type` · `client_mode`의 값을 옮겨 적음. 권한 설명 · 모드별 기능 설명은 넣지 않음 |
| 값은 그대로 | 드롭다운 항목 · 상태값 · 표기는 기준데이터 값을 그대로 나열. 출처 파일 이름은 쓰지 않음 |
| 값이 없을 때 | 늘 보이는 항목은 지우지 않고 값이 없을 때의 표기를 적음(예: `데이터 존재 시 노출/부재 시 '-' 노출`). 영역이 사라지는 경우만 `노출 조건`으로 적음 |
| 내부 표기 금지 | 저장소 경로, 질문 번호, "확인 필요", 정책 규칙 번호, 회의 ID, 논의 대상 ID, 화면 MD 절 이름을 쓰지 않음 |
| 지어 쓰지 않음 | 문장마다 출처가 있어야 함: 기존 원문(T · L 각각), 정책서, Common UX, 기준데이터, 확인받은 결정. 출처가 없으면 아래 질문 대기로 |
| 기존 원문 살리기 | 기존 디스크립션의 표현이 정책 · 용어집과 맞으면 그대로 씀. 틀린 값 · 오타 · 지운 기능(취소선)만 고침 |

## 5. 질문 대기 · 변경 확인 표시 (사용자 확인 라벨 · 사용자 확인 목록)

**사용자 확인 목록**은 질문 대기와 변경 확인을 합쳐 부르는 이름입니다. 모든 문서에서 이 뜻으로 씁니다. 원본은 작업 기록의 "질문 대기" · "변경 확인" 표이고(화면 MD에는 두지 않음), 아래 두 곳에 보여 줍니다.

| 보여 주는 곳 | 무엇 | 규칙 |
| --- | --- | --- |
| Figma | 사용자 확인 라벨과, 패널 오른쪽에 옮겨 둔 사용자 확인 목록(Figma에서 하는 일을 적을 때는 "Figma의 사용자 확인 목록") | 이 절 |
| 채팅 보고 | "답해 주실 것"에 사용자 확인 목록의 미해결 항목을 보여 주고 답을 받음 | `reference-rules/work-log.md` "요청자에게 보여 주는 법" 5번 |

화면을 그리며 생긴 질문 대기와 변경 확인은 **디스크립션 본문에 넣지 않습니다.** Figma에는 아래 두 곳에, 정해진 컴포넌트로만 표시합니다. 둘 다 확인이 끝나면 지우고, 하나라도 남은 화면은 완료가 아닙니다.

1. **사용자 확인 라벨:** 화면의 그 번호 표시 옆에 ID 라벨
2. **Figma의 사용자 확인 목록:** 패널 오른쪽에 질문 · 변경 원문을 옮겨 둔 목록. 아래에서 "사용자 확인 목록"에 컴포넌트 · 위치 · 지우는 법을 적은 곳은 모두 이 목록을 가리킵니다

| 표시 | 뜻 | 요청자가 할 일 | 사용자 확인 목록 문구 예 |
| --- | --- | --- | --- |
| 질문 대기 `Q번호` | 정해지지 않아 임시로 그린 것 | 답을 정함 | 데이터가 없을 때 버튼을 비활성화할지 |
| 변경 확인 `C번호` | 근거가 있어 **기존 화면과 다르게** 그린 것 | 맞는지 확인함 | 기본값 Query Mode → Push Mode (정책에 따름) |

- 화면 MD 디스크립션에도 넣지 않습니다(Figma 패널은 화면 MD를 그대로 옮긴 것, 6절). 질문 대기 · 변경 확인의 원본은 작업 기록 "질문 대기" · "변경 확인" 표이고, Figma의 사용자 확인 목록은 이 표에서 그 화면(CID)의 줄 가운데 "풀린 날 · 어떻게" · "확인한 날 · 답"이 빈 줄을 옮긴 것입니다(3단계에서 `맞음 (…)`으로 확인한 변경 확인 줄은 옮기지 않음, 아래 "변경 확인").
- 요청자는 채팅 보고의 "답해 주실 것"을 보고 채팅으로 답합니다. Figma의 사용자 확인 목록에 답변 칸, 상태, 해결 처리는 그리지 않습니다.

**질문 대기**

- 정해지지 않은 곳은 아래 순서로 따를 것을 찾아 그 내용으로 디스크립션을 쓰고 화면을 그린 뒤, 질문을 작업 기록 "질문 대기" 표와 사용자 확인 목록에 둡니다.
  1. 그 화면의 기존 원본(UX 화면설계서의 기획 프레임 · 디스크립션)
  2. 정책서
  3. Common UX
  4. 같은 메뉴의 다른 화면
- 넷 다 없으면 디스크립션에 내용을 지어 쓰지 않고, 질문만 둡니다.

**변경 확인**

- 기존 화면을 다시 그릴 때, 2단계에서 정책 · 용어집 · 기준데이터와 기존 화면이 다른 것으로 드러난 곳은 **기준 자료를 따라 그리고** 이 표시를 둡니다. 작업자가 기존 화면과 달라진 곳을 알아보고 맞는지 확인하게 하려는 것입니다.
- 표의 행을 최대 개수보다 줄여 그린 것처럼, 규칙과 다르게 그릴 수밖에 없던 곳도 이 표시를 둡니다(예: 최대 10행 중 8행만 그림 (화면 높이 초과)).
- **반영 대기 항목을 반영해 기존과 달라진 곳**(1단계에서 대상 화면을 읽다 찾은 고칠 점도 같음, `flow/1-requirements.md` 절차 4번 순서 3 "뒤 단계로 넘김"의 5)은 그 항목의 "변경 후"가 어떤지에 따라 아래 표대로 나눕니다. 3단계에서 반영할 때 가르고, 항목이 가리킨 자료(정책 · 기준데이터 · 다른 화면 MD)는 반드시 열어 봅니다.

  | 항목의 "변경 후" | 3단계 | 확인 |
  | --- | --- | --- |
  | 오타 · 표기만 고침 (맞춤법 · 철자 · 띄어쓰기 · 대소문자, 뜻은 그대로. 반영 대기 항목이 아니어도 3단계에서 찾아 고친 오타는 같음. 예: `Run Start로 통해 → Run Start를 통해`) | 고치고 변경 확인 줄을 만듦. 사용자 확인 라벨 · 사용자 확인 목록 항목은 두지 않음 | 확인된 것으로 보고 "확인한 날 · 답"에 `맞음 (오타, 날짜)`를 바로 적음 |
  | 바꿀 값이 그대로 적혀 있음 (예: `Allplex_HPV28 → Allplex HPV28`) | 그 값으로 반영하고 변경 확인 줄을 만듦. 사용자 확인 라벨 · 사용자 확인 목록 항목은 두지 않음 | 3단계 마침 점검에서 기계 검사(적힌 값이 화면 MD · Figma에 있는지)로 확인하고 "확인한 날 · 답"에 `맞음 (기계 검사, 날짜)` |
  | 방향만 적혀 있고, 항목이 가리킨 자료로 값이 하나로 정해짐 (예: 「검사 단계 기준으로」 → `glossary/test-stages.csv`) | 그 값으로 반영하고 이 표시를 둠. 근거 칸에 그 자료를 적음 | 4단계에서 맞음 / 되돌림 |
  | 방향만 적혀 있고 자료로 하나로 정해지지 않음, 또는 항목 내용이 사실과 다름 (예: 「하나로 맞춤」, 없는 장치 구분을 전제로 함) | 기존대로 그리고 질문 대기를 둠(변경 확인 아님) | 4단계에서 답을 받음 |

- **기존 디스크립션에 없던 설명을 더한 곳**(1단계 "뒤 단계용 확인 항목"의 기능 정의가 안 된 요소, 3절 "Common UX가 화면에 맡긴 것")은 아래 표대로 확인합니다.

  | 더한 설명 | 3단계 | 확인 |
  | --- | --- | --- |
  | Common UX가 정한 요소에 번호 · 정의와 `공통 UX 참고`를 적음(동작은 풀어 쓰지 않음, 3절), 또는 기존 화면에 이미 보이는 것을 글로 적음 (예: [Reset] · [Search], 정렬되는 칸 = 화면의 정렬 아이콘, 페이지네이션 형) | 쓰고 변경 확인 줄을 만듦. 사용자 확인 라벨 · 사용자 확인 목록 항목은 두지 않음 | "확인한 날 · 답"에 `맞음 (Common UX, 날짜)` 또는 `맞음 (기존 화면, 날짜)`를 바로 적음 |
  | Common UX가 화면에 맡겼는데 기존 원본 · 정책서 · 같은 메뉴에도 없음 (예: 데이터가 없을 때 문구) | 디스크립션에 지어 쓰지 않음 | 질문 대기 |

- 3단계에서 Common UX Type의 조건 · 컴포넌트 줄대로 써 기존 화면에 없던 요소가 생긴 곳에도 둡니다(예: 리스트에 노출 개수 Dropdown 추가 (Common UX), `flow/3-design.md` 공통 1의 8).
- 작업 기록의 "변경 확인" 표는 **이 작업으로 화면에서 바뀐 요소의 목록**입니다. 3단계에서 요건대로 고친 곳은 빠짐없이 이 표에 있어야 합니다. 4단계에서 질문 대기의 답이나 검토 질의로 화면이 바뀌면 줄을 더하고, 이미 확인된 것이므로 사용자 확인 라벨 · 사용자 확인 목록 항목 없이 "확인한 날 · 답" 칸에 `맞음 (날짜)`을 바로 적습니다(`flow/4-revise-verify.md` "화면 수정 규칙").
- 줄을 만들 때 "업데이트 메모 (O / -)" 칸을 채웁니다(아래 "업데이트 메모").

**번호 (2026-11-11 정함)**

- 번호는 **작업 하나에 통번호**입니다. 그 작업의 모든 화면을 통틀어 질문 대기는 Q1, Q2 …, 변경 확인은 C1, C2 …로 매깁니다. T-IOS와 L-IOS에 같은 질문 · 같은 변경이면 같은 번호를 씁니다.
- 같은 번호를 세 곳에 씁니다: 작업 기록의 표(원본), 사용자 확인 라벨, 사용자 확인 목록. 3단계에서 `맞음 (…)`으로 확인한 변경 확인 줄은 작업 기록 표에만 둡니다. 화면 MD에는 이 표를 두지 않습니다. 번호 하나는 한 가지만 가리킵니다.
- 한 번 쓴 번호는 다시 쓰지 않습니다. 풀려서 지운 번호도 비워 둡니다.

**사용자 확인 라벨**

- 위치: 그 번호 표시 바로 오른쪽에 둡니다.
  - 오른쪽에 두면 화면의 글자를 가릴 때는 번호 표시의 왼쪽 · 위 · 아래 순서로 보고, 글자를 가리지 않는 곳에 둡니다. 이때도 번호 표시에서 5px 안에 둡니다.
  - 네 방향 모두 5px 안에서는 글자를 가리면, 글자를 가려도 번호 표시 바로 오른쪽에 둡니다.
  - 사용자 확인 라벨 때문에 번호 표시와 화면 요소를 옮기지 않습니다(배치를 바꾸지 않음).
- 한 번호에 라벨은 Type별로 하나씩만 둡니다(질문 라벨 1개, 변경 라벨 1개). 같은 Type이 둘 이상이면 한 라벨의 Label에 쉼표로 이어 씁니다(예: `Q1, Q2`). 라벨이 둘이면 가로로 잇습니다(간격 5px).
- 순서: 질문 라벨 먼저, 그다음 변경 라벨. 라벨 안의 ID는 숫자 오름차순입니다. 예: 3번 옆 → `? Q1, Q2` `! C6, C8, C13, C15`
- 화면에 번호 표시가 없는 곳(0번 화면 정의, 케이스 1의 제거된 요소, 케이스 3에서 지운 제거된 요소)은 라벨을 두지 않고 사용자 확인 목록에만 둡니다.
- 케이스 화면(`CID/Case`)에서 생긴 것은 케이스 조각의 번호 표시 옆에 라벨을 두고, 사용자 확인 목록 항목은 본 화면의 사용자 확인 목록에 둡니다.

**사용자 확인 목록**

Template 프레임을 복제한 뒤, 제목 "사용자 확인 목록" 아래를 이 구조로 채웁니다.

```
사용자 확인 목록
├─ 그룹: 질문 대기
│   ├─ Group Header (Type=Question, Title="질문 대기 (n)")
│   ├─ Block
│   │   ├─ Desc Title ("3  목록")
│   │   └─ Item (Type=Question, ID=Q1, Text=…)
│   ├─ Divider
│   └─ Block …
└─ 그룹: 변경 확인
    └─ (같은 구조, Type=Change)
```

- 그룹 순서: 질문 대기 → 변경 확인. 항목이 없는 그룹은 통째로 뺍니다.
- Title의 (n)은 그 그룹의 항목 수입니다.
- Block은 디스크립션 번호 하나에 하나, 번호 오름차순(0, 1, 2 …)입니다. Block 사이에만 Divider를 넣습니다.
- Desc Title은 그 디스크립션의 번호와 제목을 그대로 씁니다(공백 2칸). 예: `6  [Export] 버튼`
- Item은 Block 안에서 사용자 확인 라벨과 같은 순서로 놓습니다. 가로는 FILL입니다.
- 위치: 업데이트 메모가 있으면 마지막(맨 아래) 메모 아래에 30px 띄우고 메모와 왼쪽을 맞춰 둡니다. 업데이트 메모가 없으면 패널 위쪽에 맞추고, 패널 오른쪽에서 5px 띄워 둡니다. 폭 330px 고정입니다.

**문구**

- 한 줄 요약으로 쓰고, 근거나 상세는 괄호 안에 넣습니다.
- 질문(Q): 요청자가 정해야 하는 것을 명사형으로 씁니다. 예: `정렬 아이콘을 둘 칸 (기존 화면에 정렬되는 칸 정의 없음)`
- 변경(C): 무엇을 어떻게 바꿨는지 →로 씁니다. 예: `표기 수정 (Statue → Status, Cureca → CURECA)`
- 변경의 근거가 Common UX면 괄호에 항목명을 적습니다. 예: `(Common UX 로딩)`
- "※", "변경 확인", "질문 대기" 같은 접두어는 문구에 넣지 않습니다(그룹과 라벨이 이미 구분합니다).

**케이스 1(화면 부분 수정)의 변경 (2026-11-12 정함)**

| 변경 | 디스크립션 | 사용자 확인 목록 문구 |
| --- | --- | --- |
| 더함 | 새 번호로 씀 | `{요소} 추가 (이유)` |
| 바꿈 | 그 번호의 글을 고침 | `{기존} → {바꾼 것} (이유)` |
| 제거 | 글을 지우지 않고 3단계에서 바로 빨간 취소선 (7절 "바뀐 글 표시") | `화면에서 제거, 확정 시 취소선 처리 예정 (이유)` |
| 케이스를 지움 | 제거된 요소 때문에 필요 없어진 케이스는 바로 지움 | 본 화면 사용자 확인 목록 문구 끝에 `… Case n 삭제` |

- 전달 때까지 정해지지 않았는데 개발에 꼭 알려야 하면 디스크립션에 읽는 사람 말로 한 줄: `※ 협의 중: {무엇}`

**해결 시 처리**

요청자 답으로 질문이 풀리거나 변경이 확인되면 그 항목의 표시를 모두 지웁니다.

1. 답 내용을 화면과 디스크립션 본문에 반영합니다(질문 대기). 디스크립션에서 고치거나 더한 글자는 빨간색으로 씁니다(케이스 1 · 3, 7절 "바뀐 글 표시"). 확인된 변경 확인은 작업 기록 "변경 확인" 표의 "확인한 날 · 답" 칸에 `맞음 (날짜)`을 적습니다. 업데이트 메모는 이때 만들지 않고 4단계에서 UX 확정을 기입할 때 만듭니다(아래 "업데이트 메모").
2. 사용자 확인 라벨에서 풀린 ID만 지웁니다(예: `Q1, Q2` → `Q2`). 남은 ID가 없으면 라벨을 지웁니다.
3. 사용자 확인 목록에서 그 Item을 지웁니다.
4. 그룹 Title의 (n)을 남은 항목 수로 고칩니다.
5. Item이 남지 않은 Block은 Desc Title과 붙어 있는 Divider까지 지웁니다.
6. 항목이 남지 않은 그룹은 통째로 지우고, 두 그룹이 모두 비면 사용자 확인 목록 프레임도 지웁니다.

- 케이스 1의 제거된 요소는 사용자 확인 목록 항목만 지우고 취소선을 그은 디스크립션은 남깁니다.
- 작업 기록 표의 줄은 지우지 않습니다. 질문 대기는 "풀린 날 · 어떻게" 칸에, 변경 확인은 "확인한 날 · 답" 칸에 `맞음 (날짜)` 또는 `되돌림 (날짜)`를 적습니다.

**하지 말 것 · 제출 전 체크**

- 컴포넌트를 떼어 내거나(detach) 색 · 아이콘 · 글자 크기를 바꾸지 않습니다.
- 디스크립션 본문에 질문 · 변경 문구나 참조를 넣지 않습니다.
- 답변 칸, 상태 태그, 선택지, 표는 만들지 않습니다.
- 사용자 확인 목록 제목 아래에 CID나 버전을 쓰지 않습니다.
- 체크: 사용자 확인 라벨의 ID와 사용자 확인 목록의 ID가 빠짐없이 같음 / 그룹 Title의 (n)이 항목 수와 같음 / Block이 디스크립션 번호 순서대로임 / 라벨이 위 "위치" 규칙대로 있음(가릴 수밖에 없을 때만 오른쪽에 겹침)

**만드는 때**

- 변경 확인을 하나 확인받을 때마다 만들지 않습니다. **4단계에서 UX 확정을 기입할 때** 한꺼번에 만듭니다(`flow/4-revise-verify.md` 절차 3번 "UX 확정을 기입함").
- 작업 기록 "변경 확인" 표에서 "확인한 날 · 답"이 `맞음`이고 "업데이트 메모 (O / -)" 칸이 `O`인 줄을, "관련된 곳"의 화면(CID)마다 모아 만듭니다. `되돌림`인 줄, `-`인 줄, 확인받지 않은 줄은 넣지 않습니다. 넣을 줄이 없으면 만들지 않습니다.
- UX 확정 뒤에 확인된 변경은 그때 업데이트 메모에 더합니다.

**"업데이트 메모 (O / -)" 칸**

변경 확인 줄을 만들 때 채웁니다. 화면과 동작이 바뀐 것만 `O`입니다.

| 칸 | 어떤 변경인가 |
| --- | --- |
| `O` | 화면에 보이는 것이 바뀜(표기 · 화면 표기 글자 · 값 · 상태값), 동작 · 조건이 바뀜(정책 반영 · Alert), 요소가 추가 · 제거됨 |
| `-` | 디스크립션의 말투 · 용어 · 오타 정리, 번호 정리, 패널의 화면 정보(CID · 경로 · 화면 이름) 정리. 화면 변경 이력(`screen-history.md`)에만 남김 |

**컴포넌트**

- SB-Components (기획 공통) 프레임 **Group/Description · Number · History**의 **`ver` 컴포넌트**(History, 세트 키 `018ccd5d1658f6f1e87fd87a9343ff004e7da730`, 너비 230) 인스턴스로 넣습니다. 직접 그리지 않고, 떼어 내지(detach) 않습니다.
- `ver`의 Variant(`v0.1` ~ `v1.0`)에 들어 있는 색과 글자는 예시 데이터입니다. 정해진 색은 없고, 아래 "색" 규칙만 지킵니다.

**케이스 2 (신규)**

- 변경 확인을 두지 않으므로 넣을 줄 대신 `• 신규 화면` 한 줄로 만듭니다. 만드는 때 · 제목 · 색은 위와 같습니다(4단계 UX 확정 때, `v{Ver} update`).

**케이스 3 (기존 화면 다시 그리기)**

- `{메뉴}_asis` 페이지의 그 화면 기획 프레임 옆에 있는 메모를 **그대로 옮겨 옵니다**(버전 · 글 · 색 · 쌓인 순서 그대로, 글머리 기호(•)와 들여쓰기 단계까지). 줄이거나 고쳐 쓰지 않습니다.
- 다시 그리며 바뀐 것은 **`재설계 후 변경 내역` 메모**를 하나 더 만들어 남깁니다. 케이스 3은 Ver을 바꾸지 않아, `v{Ver} update` 제목을 쓰면 옮겨 온 메모와 제목이 같아지기 때문입니다.

  | 무엇 | 값 |
  | --- | --- |
  | 만드는 때 · 넣는 줄 | 위 "만드는 때"와 같음(4단계 UX 확정 때, 변경 확인 `맞음` · `O` 줄). 넣을 줄이 없으면 만들지 않음 |
  | 제목 (첫 줄) | `재설계 후 변경 내역` |
  | 색 | 회색 `#E5E5E5` 고정. 아래 "색" 규칙 두 가지는 이 메모에 쓰지 않음 |
  | 위치 | 옮겨 온 메모 아래(위에서 아래로 쌓는 순서의 마지막). 사용자 확인 목록은 이 메모 아래 30px |
  | 내용 · 크기 · 컴포넌트 | 아래 "새로 생기는 메모"와 같음 |

**새로 생기는 메모**

| 무엇 | 값 |
| --- | --- |
| 위치 | 기획 프레임 오른쪽 바깥, 패널 오른쪽 5px. 패널 위쪽에 맞춤. 메모가 여럿이면 위에서 아래로 쌓음. 사용자 확인 목록은 마지막 메모 아래 30px에 둠(위 "사용자 확인 목록"의 위치) |
| 크기 | 너비 230 고정, 높이는 내용만큼 |
| 제목 (첫 줄) | `v{Ver} update`. Ver은 UX 확정 때 요청자가 한 번 정한 이번 작업의 Ver(이 작업의 화면 모두 같음, 7절 "화면 정보에 적는 값") |
| 내용 | 제목 아래에 확인된 변경을 개조식으로 한 줄씩 (번호 · 무엇이 어떻게 달라졌나. 번호는 2절 "번호 가리키기"대로 괄호로), 줄마다 글 상자의 글머리 기호 목록(•)으로. 더 풀 때는 한 단계 들여 쓴 글머리 기호로. `●` · `-` 문자로 대신하지 않음(7절 패널과 같음) |
| 색 | ① 직전 버전의 메모와 같은 색은 쓰지 않음 ② 버전이 같은 메모는 같은 색으로만 씀 |

```
v2.1.15 update
 • (3) Order Reception Mode 기본값 변경
   • 기존 Query Mode → Push Mode (정책에 따름)
 • (2) 리스트에 노출 개수 Dropdown 추가 (Common UX)
 • (2-1) 날짜 표기 YYYY-MM-DD로 변경
```

- 업데이트 메모의 원본은 작업 기록 "변경 확인" 표입니다. 메모로 옮기는 줄은 위 "만드는 때"를 따릅니다. 확인받지 않은 변경은 메모에 넣지 않습니다(사용자 확인 목록에 남음).
- 메모에는 내부 표기(정책 규칙 번호, 논의 대상 ID, 반영 대기 항목 ID)를 쓰지 않습니다.

## 6. 화면 MD와 Figma

- 화면 MD의 디스크립션이 원본이고, Figma 패널은 그대로 옮긴 것입니다. 고칠 때는 둘을 함께 고칩니다(헌법 6조).

## 7. 패널 틀 (2026-11-10 정함)

모든 화면의 패널을 같은 틀 · 같은 크기 · 같은 위치로 그립니다. 값은 기존 작업방 패널(Part.2 TI-SPT-01)을 잰 것입니다.

### 위치와 크기

| 무엇 | 값 |
| --- | --- |
| 기획 프레임 | 너비 2252 = 화면 1920 + 패널 332. 케이스 3(기존 화면 다시 그리기)은 기존 원본 기획 프레임의 너비와 같게 그림(`flow/3-design.md` 공통 4) |

| 줄 | 한 줄(행)이 번호 칸 22 + 내용 칸 310. 줄 높이는 내용만큼, 가장 낮은 줄 26 |

### 바뀐 글 표시 (2026-11-17 정함)

개발사는 업데이트 메모만 보고는 디스크립션의 어디가 바뀌었는지 헷갈릴 수 있습니다. 그래서 패널에서 이번 버전에 바뀐 글을 빨간색으로 보여 줍니다.

| 케이스 | 기준 | 빨간색으로 쓰는 것 |
| --- | --- | --- |
| 케이스 1 화면 부분 수정(고도화) | 직전 버전의 디스크립션 | 이 작업에서 고치거나 더한 글자(3단계에서 요건대로 고친 것, 4단계에서 답 · 검토 질의로 고친 것 모두). 제거된 요소와 제거된 문구는 지우지 않고 빨간 취소선 |
| 케이스 2 신규 | 없음 | 바뀐 글 표시를 하지 않음 (모두 새로 쓴 글) |
| 케이스 3 기존 화면 다시 그리기 | 기존 원본(`{메뉴}_asis` 페이지 · asis 화면 MD)의 디스크립션 | 변경 확인과 질문 대기의 답으로 기존과 달라진 글자. 기존을 그대로 옮긴 글은 검정이고, 기존 원본에서 빨간색이던 글도 검정으로 옮김. 기존 원본의 제거된 문구는 검은 취소선으로 옮김(빨간 취소선이던 것도). 이번 작업에서 제거된 요소와 제거된 문구는 지우지 않고 빨간 취소선 |

- 빨간색은 글자 색만 바꿉니다. 번호 칸 · 글머리 기호 · 굵기는 그대로입니다.
- 화면 MD에도 같은 표시를 둡니다. 화면 MD에서는 HTML 태그로 적습니다: 빨간 글씨 `<span style="color:red">글자</span>`, 빨간 취소선 `<span style="color:red">~~글자~~</span>`, 검은 취소선 `~~글자~~`.
- 케이스 1 · 3 공통: 직전 버전의 빨간 표시는 그 화면의 다음 작업(케이스 1)에서, 복제본을 만든 직후 검정으로 되돌립니다(빨간 취소선은 검은 취소선으로, 코드는 파란색으로(아래 "참고 코드 표시"), `flow/3-design-case1.md` 1-4). 복제본에는 직전 버전의 표시가 그대로 남습니다. 화면 MD의 빨간 태그는 그보다 앞서, 같은 문서 1-2에서 화면 MD를 고치기 직전에 되돌립니다.

### 참고 코드 표시

패널 디스크립션에 적힌 코드(참고 대상을 가리키는 코드)만 파란색(`#3242FF`)으로 씁니다. 참고 줄의 `:` 뒤에 있든 동작 줄 안에 있든 같습니다. 라벨 · 문구는 검정입니다.

| 코드 | 모양 |
| --- | --- |
| 화면 · 케이스 | `TI-…` · `LI-…` (`/Case > Case n` 포함) |
| Alert · Confirm · Toast | `Alert_###` · `Confirm_###` · `MS_Alert_###` · `MS_Confirm_###` · `MS_Toast_###` |
| Common UX · 정책 | `COMM-…` · `POL-…` |

- 글자 색만 바꿉니다. 화면 MD에는 색을 적지 않고, 패널에 옮길 때 위 모양의 코드를 칠합니다.
- 이번 작업에서 바뀐 코드는 바뀐 글 표시(빨간색)가 앞섭니다. 빨간 표시를 검정으로 되돌릴 때 코드는 파란색으로 되돌립니다.
- 취소선 안의 코드는 취소선 색을 따릅니다(검은 취소선은 검정, 빨간 취소선은 빨강).

### 화면 정보에 적는 값

| 케이스 | Ver | Date | 작성자 |
| --- | --- | --- | --- |
| 케이스 3 기존 화면 다시 그리기 | 기존 화면의 Ver 그대로 | 기존 화면의 Date 그대로 | 기존 화면 담당자 그대로 |
| 케이스 1 화면 부분 수정(고도화) | UX 확정 때 요청자가 정한 Ver. 그 전까지는 기존 화면의 Ver 그대로 | 작성일 | 요청자 |
| 케이스 2 신규 | UX 확정 때 요청자가 정한 Ver. 그 전까지는 비워 둠 | 작성일 | 요청자 |

- Date 모양은 `YYYY.MM.DD`입니다.
- **Ver 모양은 `X.Y.ZZ`입니다.**

  | 자리 | 뜻 | 예 (2.1.13) |
  | --- | --- | --- |
  | X | 프로젝트 차수 | 2 = 2차 프로젝트 |
  | Y | 그 프로젝트 안의 릴리즈 순번. 0부터 시작 | 1 = 두 번째 릴리즈 |
  | ZZ | 그 릴리즈 안에서 개발사에 전달한 순번. 항상 두 자리 (01, 02, … 13) | 13 |

- **Ver은 CID마다 따로 갑니다.** 같은 메뉴 안에서도 CID마다 Ver이 다를 수 있습니다.
- **Ver은 요청자가 정하고, UX 확정 때 기입합니다**(`flow/4-revise-verify.md` 절차 3번 "UX 확정을 기입함" 순서 3 · 4). 이번 작업의 Ver을 한 번만 받아, 이 작업에서 고친 케이스 1 · 2 화면 모두에 같은 Ver을 씁니다. 화면 MD 머리말 `version`에 적고 패널 화면 정보에 옮기며, 업데이트 메모 제목 `v{Ver} update`에도 이 Ver을 씁니다(5절 "업데이트 메모").
- 케이스 3은 내용을 바꾸는 작업이 아니라 옮겨 그리는 작업이라 Ver · Date · 작성자를 바꾸지 않습니다.
- 화면 정보 값은 화면 MD 머리말에서 옮기고, Figma에서 따로 고치지 않습니다.
- 예전 "공통 규칙 버전 · 표시" 칸은 두지 않습니다. 기준 시각(`basis`)은 화면 MD 머리말에만 적습니다. 테스트 그림은 섹션 이름 뒤 `(테스트 N)`으로 구분합니다.

## 하지 않는 것
