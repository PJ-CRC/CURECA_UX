# 변경 흐름

> 상태: 초안 v0.5 (2026-11-04). v0.5에서 승인 담당자 1명을 없애고, 모두가 임시 정책을 등록하고 함께 확인해 [승인]으로 반영하게 함(헌법 4조 v1.6). v0.4 (2026-11-03)에서 v0.4에서 회의 중심 순서를 등록 → 승인·반려 → 반영 세 단계로 줄이고, 알림은 추후 연동으로 둠. 근거: 헌법 4·5조, `background/rules-review-draft.md`의 "공통 자료 변경 흐름".

공통 자료(팀 프로그램의 UX 문서)는 누구도 직접 바꾸지 않습니다. 누구든 바꿀 내용을 임시 정책으로 등록하고, 모두에게 보이는 목록에서 함께 확인한 뒤 [승인]을 눌러 반영합니다. 화면설계서는 작성자가 책임지고 바꿉니다.

## 1. 대상 구분

| 구분 | 대상 | 변경 방법 |
| --- | --- | --- |
| 공통 자료 | 헌법, 룰 문서, 정책서, Service Mode·권한 매트릭스, 장비 상태 정의서, 알럿 카탈로그, Common UX, 용어집 | 임시 정책 등록 → 함께 확인 → [승인]으로 반영. Common UX는 수정 요청 목록(`common-ux/feedback.md`)에 올리고 함께 확인해 [반영] (반영 기능은 추후) |
| 화면설계서 | CID별 화면설계서 | 작성자가 직접 수정. 다른 사람은 작성자에게 요청 |
| 언어셋 | 7개 언어 문구 | 내부 논의 대상 아님. 고객사 컨펌으로 확정 (`rules/language-set.md`) |

## 2. 공통 자료 변경 순서

1. **등록:** 작업 중 기존 정책·룰을 바꾸거나 더해야 하면 공통 자료를 직접 고치지 않고, Claude에게 임시 정책(PV)으로 등록해 달라고 한 뒤 그 기준으로 작업합니다. 이번 작업에서는 적용한 화면만 고치고, 영향받는 다른 화면은 PV 파일의 "영향 화면"에 적습니다. 그 화면들의 반영 대기 목록 줄은 승인될 때 만듭니다(`rules/provisional-policy.md`, `rules/screen-spec.md` 4절). 등록할 때 Claude가 "승인 대기" 임시 정책을 확인해, 같은 규칙을 다르게 바꾸는 것이 있으면 두 안을 A/B 선택 문서로 합칩니다(`rules/provisional-policy.md` 6절).
2. **함께 확인하고 승인·반려:** 등록된 임시 정책은 UX 문서의 임시 정책 메뉴에 모두에게 보입니다. 함께 확인한 뒤 확인한 사람이 [승인] 또는 [반려]를 누릅니다. 따로 정한 승인 담당자는 없습니다. A/B 선택 문서는 한 안을 골라 승인합니다. 회의를 기다리지 않아도 됩니다.
3. **반영:** [승인]을 누르면 Claude가 그 내용을 공통 자료에 반영하고 공통 규칙 버전을 올립니다(예: 태그 `rules-v0.3`). 이때 Claude가 영향 화면의 반영 대기 목록에 줄을 만들고(`rules/screen-spec.md` 4절), 영향 화면 작성자는 그 줄을 반영하며 새 버전에 맞춰 화면을 고치고, 화면 머리말의 `rules_version`을 바꾸고 `provisional`에서 PV ID를 뺍니다.

- 공통 규칙은 대표 저장소 기준 브랜치에서만 읽으므로, 승인 전의 임시 정책은 그 PV ID를 적은 작업에서만 쓰입니다.
- 작업에 쓰지 않고 논의만 필요한 것은 협의 대기(PD)로 올립니다(3절).
- 영향받는 작성자는 UX 문서의 임시 정책 메뉴에서 확인합니다. 메신저(Slack 등) 알림은 추후 연동합니다.

## 3. 협의 대기 항목 관리

### 항목 하나 = 파일 하나

- 협의 대기 항목은 한 파일에 모으지 않고, 항목마다 `pending/` 아래 파일 하나로 만듭니다. 여러 사람이 동시에 항목을 올려도 git 충돌이 나지 않게 하기 위해서입니다.
- 파일 이름은 항목 ID입니다: `PD-0001.md`. 번호는 네 자리 일련번호이며, `pending/`과 `pending/closed/`에 있는 가장 큰 번호에 1을 더합니다. 한 번 쓴 번호는 다시 쓰지 않습니다.
- 같은 번호가 동시에 만들어져 충돌하면, 나중에 반영되는 쪽의 번호를 바꿉니다.
- `templates/pending-item.md`를 복사해 만들고, 제안 내용, 이유와 근거, 영향 범위, 제안자, 제안일을 모두 채웁니다. 영향 범위를 모르면 비워 두지 않고 "확인 필요"라고 적습니다.

### 항목 상태

| 상태 | 의미 | 파일 위치 |
| --- | --- | --- |
| 대기 | 올라왔고 아직 논의 전 | `pending/` |
| 보류 | 결정을 미룸 | `pending/` |
| 합의 | 합의함, 아직 반영 전 | `pending/` |
| 반영 완료 | 공통 자료에 반영됨 | `pending/closed/` |
| 기각 | 반영하지 않기로 함. 사유를 남김 | `pending/closed/` |
| 병합 | 다른 항목에 합쳐짐. 합쳐진 항목 ID를 남김 | `pending/closed/` |

- 닫힌 항목(반영 완료, 기각, 병합)은 지우지 않고 `pending/closed/`로 옮깁니다(헌법 9조).
- 논의 결과는 각 항목 파일의 "미팅 결과"에 날짜와 함께 적습니다.

### 효력

- 협의 대기 항목은 승인 전까지 효력이 없습니다. Claude는 "대기", "보류", "합의" 항목을 근거로 화면을 그리지 않습니다.
- 작업에 먼저 써야 하는 변경은 임시 정책(PV)으로 등록하고 화면에 "임시 정책 포함" 표시를 붙입니다(`rules/provisional-policy.md`).

## 4. 긴급 변경

따로 긴급 절차는 없습니다. 바로 반영이 필요하면 임시 정책으로 등록하고 함께 확인해 바로 [승인]합니다. 자동 검증은 그대로 거칩니다.

## 5. 화면설계서 변경

- 작성자가 오너로서 직접 고칩니다.
- 다른 사람이 수정을 원하면 작성자에게 요청합니다. 단, 영향 범위에서 찾은 작은 변경은 함께 고치고 이력과 알림을 남길 수 있습니다(`rules/claude-work.md` 6절). Claude는 다른 팀원 계정에 직접 메시지를 보낼 수 없으므로, 요청은 git 이슈로 남깁니다.
- 변경 규모에 따른 상태 처리(작업 중으로 되돌림 / 변경 예정 표시)는 `rules/status-lifecycle.md`를 따릅니다.

## 6. 개발사 전달

> **보류 (2026-11-05):** 작업방 → 공유방 → 개발사로 내보내는 흐름은 이행 기간이 끝날 때까지 보류합니다(`rules/figma-sync.md` 2절).

정해진 주기 없이 매번 협의한 공유일에, 그때까지 확정된 범위를 묶어 전달합니다.
