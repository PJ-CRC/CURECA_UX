# 화면설계서 규칙

> 상태: 초안 v1.0 (2026-11-04). v1.0에서 디스크립션의 화면 정의 · 요소별 필수 항목 · 번호 매기기를 정함(8절). v0.9에서 디스크립션 문장 패턴과 표준어를 정함(8절). v0.8에서 임시 정책의 영향 화면 줄은 승인 때 만들기로 함(4절). v0.7에서 제외 줄을 10일 뒤 변경 이력으로 옮기는 정리를 더함(4절). v0.6에서 반영 대기 목록을 다시 정의함(4절: 정의, 줄이 생기는 경우, 영향 화면 찾기, 줄 만들기, 원인이 바뀌면). v0.5에서 반영 대기 목록 ID · 상태 5개 · 반영과 롤백(4절), 새 CID 요청(2절 빈칸 찾기)을 더함. v0.4에서 설계안 화면 MD(6절)와 템플릿을 정함. v0.3에서 이행 기간(0절)과 신규 작업방 구성(5절)을 정함. v0.2에서 그리는 순서(2절)를 정함. 7절에 정할 것을 모았습니다.

화면설계서를 어디에, 어떤 순서로, 무엇을 담아 그리는지 정합니다. 기존 메뉴를 새로 그릴 때, 신규 메뉴를 그릴 때, 이미 그린 화면을 고칠 때 모두 2절의 순서를 따릅니다.

### 이행 기간

기존 메뉴를 모두 신규 작업방에 새로 그릴 때까지를 이행 기간으로 봅니다.

1. 메뉴를 새로 그리면(그 메뉴의 CID를 모두 2절 순서로 그려 `source: tobe` 화면 MD가 되면) `_menu.md` 머리말 `redrawn`에 그 날짜를 적습니다. 그 메뉴는 이때부터 기존 작업방을 읽지 않고, 화면 MD와 신규 작업방만 기준으로 씁니다.
2. 모든 메뉴의 `redrawn`이 채워지면 이행 기간이 끝납니다. `sources.md`의 화면 출처를 신규 작업방으로 바꾸고 기존 작업방을 뺍니다.
3. 이행 기간이 끝나면 이 0절의 기존 작업방 줄, 3절(기존 화면 MD화), `rules/figma-sync.md` 1절(1 · 2차 영역)은 이행 기록으로만 남깁니다. 지우지 않습니다(헌법 9조).

- 고객 컨펌 페이지 · 개발사 공유 페이지로 내보내는 방법은 `rules/figma-sync.md` 2절에서 정합니다.

## 1. 화면 반영 대기 목록과 디스크립션 기준 (2026-11-02)

- 화면에 반영할 변경은 화면 MD의 "반영 대기 목록" 절에 모읍니다. 정의, 줄이 생기는 경우, 영향 화면 찾기, 상태와 롤백은 4절입니다. 화면 MD가 아직 없는 CID는 `screen-fixes/<CID>.md`에 두었다가 화면 MD를 만들 때 옮깁니다. 모든 화면 공통 항목은 `screen-fixes/README.md`에 있습니다.
- 화면을 다시 그리거나 디스크립션을 쓸 때는 그 CID와 짝 CID의 반영 대기 목록, 그 CID를 `cids`에 둔 정책 파일을 먼저 읽습니다.
- 알럿 체계를 다시 잡을 때까지(`background/worklist.md` 작업 9) 화면 MD의 알럿 정보(디스크립션 원문의 알럿 ID·문구, 호출하는 화면, 알럿 반영 대기 목록)는 지우지 않고 남깁니다. 정책에서 알럿 동작이 바뀌어도 화면 MD에는 반영 대기 목록으로 적고 원문은 그대로 둡니다 (2026-11-02).
- 화면에 Consumable·Reagent 예시 값(품목 이름, 구성품 이름, 수량 단위, 저장 위치, Barcode)을 넣을 때는 `glossary/consumables.csv`, `glossary/pcr-reagents.csv`의 실제 값을 씁니다. Reagent의 구조와 값은 Assay Pack이 정하므로, 이 표는 Reagent 검증과 화면 데이터용입니다 (2026-11-03).
- 정책에서 새로 정하거나 바꾼 내용은 영향 화면의 반영 대기 목록에 "디스크립션에 넣음: …"으로 적고, 화면 예시에 보이는 내용이면 "화면 예시도 …"를 함께 적습니다(4절 "줄 만들기", 2026-11-03).
- 디스크립션은 기존 화면의 문장을 고쳐 쓰지 않고, 정책서와 정리된 알럿 카탈로그(`policy/alert-catalog.csv`)를 기준으로 다시 씁니다. 정책은 ID로만 참조합니다.
- 화면 머리말 `policies`에는 참고한 정책 ID와 그 정책의 버전을 함께 적습니다 (예: `POL-EQP-009@2.1.15`). 어떤 화면이 어느 기준으로 그려졌는지 추적하기 위해서입니다.
- 화면 머리말 `rules_version`에는 그 화면을 그리거나 고칠 때 따른 공통 규칙 버전(대표 저장소 기준 브랜치의 버전, 예: `rules-v0.3`)을, `provisional`에는 적용한 임시 정책 ID(A/B 선택 문서의 B안이면 `PV-0003-B`처럼 안까지)를 적습니다. 공통 규칙 버전이 올라가면 작성자는 바뀐 정책을 쓰는 자기 화면을 새 버전에 맞추고 버전을 바꿉니다. 화면을 다시 열면 Claude가 머리말 버전이 최신이 아닌지 확인해 말해 줍니다. 임시 정책이 있는 화면에는 "임시 정책 포함" 표시를 붙입니다 (헌법 4조, `rules/provisional-policy.md`, 2026-11-03).

## 2. 그리는 순서 (2026-11-04)

메뉴 하나를 그리는 순서입니다. 화면 MD가 설계의 원본이고, Figma는 화면 MD를 그린 결과입니다(헌법 6조). 그래서 화면 MD를 먼저 쓰고(2단계) 그다음 그립니다(4단계). Claude의 공통 순서(`rules/claude-work.md` 2절)를 화면 작업에 맞춘 것입니다.

| 단계 | 할 일 | 남는 것 |
| --- | --- | --- |
| 0. 준비 | 메뉴, 담당자(`_menu.md` owner), 들어갈 버전(`rules/repository-and-id.md` 6절)을 정함. 따를 공통 규칙 버전과 그 메뉴에 걸린 임시 정책을 확인 | 메뉴 UX 상태 "작업 중" |
| 1. 근거 읽기와 빈칸 찾기 | 아래 "읽는 자료"를 읽고, 놓친 부분 · 넣을 부분을 목록으로 만듦 | 빈칸 목록 → 질문, 논의 항목(PD · CA), 임시 정책 |
| 2. 화면 MD 작성 (설계안) | 화면마다 구성, 디스크립션, 상태별 화면, 케이스, 문구(언어셋 ID), 호출하는 알럿을 저장소에 먼저 씀(6절) | `screens/{메뉴}/{CID}.md` (`source: tobe`) |
| 3. 확인 | 계획과 질문을 작성자에게 보여 주고 답을 받음. 답이 없는 곳은 "질문 대기"로 두고 나머지는 진행(`rules/claude-work.md` 2절 4 · 5단계) | 확인 기록 |
| 4. Figma 그리기 | 신규 작업방의 그 메뉴 페이지에 화면 MD를 그대로 그림: 기획 프레임(영어), 최장 언어 화면, 상태별 화면, 케이스(5절) | 프레임, 화면 MD 머리말 `figma` 링크 |
| 5. 점검 | 화면 점검 목록(`rules/claude-work.md` 5절)과, Figma가 화면 MD와 같은지 | 점검 결과 |
| 6. 기록 · 커밋 | 변경 이력, 반영 대기 목록 "반영 완료"(4절), `rules_version` · `provisional`, 번역 요청 목록 | 커밋, 보고 8항목 |
| 7. 리뷰 이후 | 컨펌 중 → 컨펌 완료 → UI 작업 → 개발사 전달 (`rules/status-lifecycle.md`) | 상태 이력 |

### 읽는 자료 (1단계)

IA(`ia/ia-screens.csv`), 그 메뉴 CID를 `cids`에 둔 정책, 기존 화면 MD와 반영 대기 목록(짝 CID 포함), 알럿 카탈로그, 용어집 · 상태값, Service Mode · 권한 매트릭스, 장비 상태 정의서, 언어셋, Common UX, 임시 정책 · 논의 항목. 읽는 순서는 `rules/claude-work.md` 4절을 따릅니다.

### 빈칸 찾기 (1단계)

다음을 찾아 목록으로 남깁니다. 정의가 없는 것은 만들어 넣지 않고 질문이나 논의 항목으로 올립니다(헌법 7 · 8조).

- 화면에 있지만 정책에 정의가 없는 동작 · 상태 · 수치
- 정책에 있지만 화면에 없는 것
- 사용자가 실수할 수 있는데 알럿이 없는 지점
- IA와 기존 화면이 다른 곳 (CID, 경로, 짝 화면)
- IA에 없는데 새로 필요한 화면 → 새 CID 요청 (`rules/repository-and-id.md` 2절 "새 CID 만들기")
- 반영 대기 목록 중 "확인 필요"로 남은 줄

### 고칠 때

이미 그린 화면을 고칠 때도 같은 순서를 밟습니다. 시작점은 반영 대기 목록이나 요청이고, 범위는 바뀐 화면과 영향받는 화면(T/L 짝, 다른 작성자의 화면 포함)으로 좁힙니다. 큰 변경 · 작은 변경의 처리는 `rules/status-lifecycle.md` 3절, 점검 범위는 `rules/claude-work.md` 5절을 따릅니다.

## 3. 기존 화면 MD화 (2026-11-02 확정)

정책서 작업과 함께 진행합니다. 한 메뉴의 기존 화면을 먼저 MD로 옮기고, 그 영역의 정책은 Figma 대신 화면 MD를 읽어 정리합니다. Figma는 한 번에 읽을 수 있는 양이 적어서, 한 번 읽을 때 MD로 남겨 두면 정책 작업과 화면 재설계에서 다시 읽지 않아도 됩니다.

### 범위

- 기획 화면만 옮깁니다: 오른쪽에 화면 정보·디스크립션 패널이 있는 2252px 프레임. 같은 CID의 디자인 프레임(1920×1080), 1280 해상도, Skeleton 프레임은 지금은 옮기지 않습니다(2026-11-02 결정).
- 최신 영역의 프레임만 옮깁니다 (`rules/figma-sync.md` 1절). 파일 머리말 `figma_region`에 영역을 적습니다.
- CID가 없는 프레임(IA에 CID가 없는 Tab 등)은 옮기지 않고 메뉴 파일 `_menu.md`에 적습니다.
- 케이스 프레임은 지금은 제목만 "케이스" 절에 적고, 중요한 케이스 화면은 링크로 남깁니다.
- **취소선:** Figma에서 취소선이 그어진 글자는 제거된 항목입니다. 화면 MD에는 `~~글자~~`로 옮기거나 "(취소선, 제거됨)"으로 표시하고, 다시 그릴 때 넣지 않습니다 (2026-11-02 사용자 확인). 추출 스크립트가 취소선을 `~~ ~~`로 표시합니다.

### 순서

1. IA(`ia/ia-screens.csv`)에서 그 메뉴의 CID 목록을 만듭니다.
2. Figma 페이지에서 CID마다 기획 화면 프레임을 찾습니다 (같은 이름 프레임 중 화면 정보 패널에 Ver가 있는 것).
3. `tools/figma/extract-screen.js`로 화면 정보, 화면 글자, 사용 컴포넌트, 디스크립션 원문, 케이스 제목, 버전 메모를 뽑습니다. Figma는 읽기만 합니다.
4. `templates/screen-asis.md`로 `screens/<메뉴>/<CID>.md`를 만듭니다.
   - 머리말: Figma 화면 정보(Ver, Date, 작성자, 화면)와 IA(짝 CID, Type, 경로), Service Mode·User Type(`policy/service-mode-matrix.csv`, `policy/permission-matrix.csv`)
   - 디스크립션은 원문 그대로 둡니다. T/L 짝 화면에서 원문이 같은 절은 "원문은 짝 CID n과 같음"으로 적고 다른 절만 옮깁니다.
   - 화면 글자의 GNB·LNB는 한 줄로 묶고, 예시 데이터가 반복되는 줄은 줄여 적습니다.
   - 버전 메모는 변경 이력 표로 옮깁니다.
5. 옮기면서 찾은 고칠 점(정책·용어집·상태값·알럿과 다른 곳, 오타, 화면 정보 오류)을 "반영 대기 목록" 절에 적습니다. `screen-fixes/<CID>.md`가 있으면 그 내용도 옮기고 그 파일은 지웁니다.
6. 관련 정책 ID를 적습니다 (정책 파일의 `cids`에서 찾음). 정책 파일의 `cids`에 빠진 CID가 있으면 정책 파일도 고칩니다.
7. 메뉴 파일 `_menu.md`의 `cids`를 채웁니다.

## 4. 반영 대기 목록 (2026-11-04 다시 정의)

### 정의

반영 대기 목록은 **그 화면에 아직 반영하지 않은, 확정되었거나 확정을 기다리는 변경**을 화면(CID)마다 모아 둔 표입니다. 화면 MD의 "반영 대기 목록" 절에 둡니다(화면 MD가 아직 없는 CID는 이행 기간 동안 `screen-fixes/<CID>.md`).

처음에는 "정책서를 정리한 뒤 화면을 다시 그릴 때 반영할 목록"으로 시작했지만, 지금은 어디서 생긴 변경이든 영향받는 화면에 빠짐없이 전달되는 통로입니다. 한 화면이나 한 회의 · 논의에서 생긴 변경이 다른 화면에도 영향을 주면, Claude가 영향 화면을 찾아 그 화면들의 반영 대기 목록에 줄을 만듭니다. 화면을 그리거나 고칠 때는 이 목록을 먼저 읽고 반영합니다(2절).

### 줄이 생기는 경우

| 원인 | 언제 | 근거 칸에 적는 원인 ID | 줄의 처음 상태 |
| --- | --- | --- | --- |
| 화면을 고치다 정책이 새로 생기거나 바뀜 | 임시 정책이 **승인될 때** (`rules/provisional-policy.md`). 등록 때는 PV 파일의 "영향 화면" 표에만 적음 | PV ID, 원인 화면 CID | `대기` |
| 임시 정책 승인 · 반려, A/B 선택 | 함께 확인하고 [승인] · [반려]를 누를 때 | PV ID | 아래 "원인이 바뀌면" |
| 고객 회의에서 정책이 정해짐 | 안건에 답할 때, 또는 회의록 정책 후보로 등록한 임시 정책이 승인될 때 (`rules/meeting-notes.md` 5 · 6절) | 회의 ID와 PV · CA ID | `대기` |
| 내부 논의(PD) · 고객 논의(CA)가 끝남 | 답변을 커밋할 때 (`rules/discussion-answer.md`) | PD · CA ID, 바뀐 정책 ID | `대기` (확인 필요가 남으면 `대기 (확인 필요)`) |
| 정책서를 바꿈 | [승인]으로 공통 자료에 반영할 때 (`rules/change-flow.md`) | 정책 ID@버전 | `대기` |
| 기준 자료를 바꿈 (용어집 · 상태값 · 알럿 카탈로그 · Common UX · 언어셋) | 그 자료를 고치는 커밋에서 | 자료 이름과 바뀐 항목 | `대기` |
| 외부 원본 새 버전 (씨젠 문서 · IA 등) | 반영할 때 (`rules/claude-work.md` 10절) | 원본 이름 · 버전 | `대기` |
| 화면 검증 · 용어 검토 · 기존 화면 옮기기 중 찾은 고칠 점 | 찾았을 때 | 찾은 작업과 기준 자료 | `대기` |

### 영향 화면 찾기

원인이 생기면 Claude가 아래 순서로 영향 화면을 찾습니다. 찾기 전에는 원인 작업을 끝내지 않습니다(헌법 5조).

| 바뀐 것 | 찾는 곳 |
| --- | --- |
| 정책 | 그 정책의 `cids`, 화면 MD 머리말 `policies`, 그 정책을 참조하는 다른 정책의 `cids` |
| 용어 · 표기 | 모든 화면 MD의 디스크립션 · 문구 · 화면 예시에서 그 표현 |
| 상태값 | 화면 예시 · 문구 · 디스크립션에서 그 값 |
| 알럿 | 알럿 표 · 디스크립션의 그 알럿 ID, 알럿 카탈로그의 사용 화면 |
| 화면 동작 · 이동 | 그 화면을 부르는 화면과 그 화면이 부르는 화면, 공통 팝업의 호출 위치 |
| 모든 경우 | T/L 짝 CID |

- 찾은 화면마다 영향을 "화면 변경 / 디스크립션 변경 / 확인 필요"로 나눕니다(`rules/provisional-policy.md` 4절과 같은 말).
- 영향 화면 목록(화면, 작성자, 영향, 만들 줄의 문장)을 원인 작업의 계획 확인(`rules/claude-work.md` 2절 5단계)이나 정리 화면에서 보여 주고, 확인을 받은 뒤 줄을 만듭니다.

### 줄 만들기

- **같은 커밋:** 영향 화면의 줄은 원인 작업의 커밋에 함께 넣습니다. 원인만 바뀌고 영향 화면 줄이 빠진 커밋을 만들지 않습니다.
- **다른 작성자의 화면:** 화면 자체는 고치지 않고 줄만 만듭니다(헌법 4조). 요청자가 원하고 작은 변경이면 같은 작업에서 바로 고칠 수 있는데(`rules/claude-work.md` 6절), 그때도 줄을 만들고 바로 `반영 완료`로 둡니다.
- **바꿀 것 칸:**

| 경우 | 쓰는 법 |
| --- | --- |
| 디스크립션에 들어갈 내용 | `디스크립션에 넣음: …` |
| 숫자 형식, 단위, 상태, 칩 · 버튼 상태처럼 화면 예시에 보이는 내용 | 위 문장 뒤에 `화면 예시도 …` |
| 아직 정해지지 않은 부분 | `확인 필요: …` |

- **근거 칸:** 원인 ID를 맨 앞에 적습니다(예: `PV-0004 (원인 TI-STN-05), POL-ACC-006`). 같은 원인으로 만든 줄은 근거 칸의 원인 ID로 한꺼번에 찾습니다.
- **원인 문서에 줄 ID 남기기:** 만든 줄의 전체 ID를 원인 문서에 적습니다. 임시 정책은 "영향 화면" 표, 논의 항목은 결과 칸, 회의록은 정책 후보 · 점검 결과의 처리 칸, 정책서는 변경 이력의 내용 칸입니다. 원인이 바뀌면 이 목록으로 줄을 찾습니다.
- **겹칠 때:** 같은 곳을 같은 내용으로 바꾸는 `대기` 줄이 이미 있으면 새로 만들지 않고 그 줄 근거 칸에 원인 ID를 더합니다. 같은 곳을 다르게 바꾸면 새 줄을 만들고 앞 줄은 `제외 (날짜, R07로 대체)`로 바꿉니다.
- **컨펌 완료 · 전달 완료된 화면:** 줄이 생기면 그 화면의 표시와 상태는 `rules/status-lifecycle.md` 3 · 4절을 따릅니다(작은 변경은 "변경 예정", 큰 변경은 작업 중으로 되돌림).
- **알림:** Claude는 메신저로 알리지 않습니다. 보고의 "알릴 사람"에 줄이 생긴 화면의 작성자와 내용을 적고, 작성자는 화면설계서 작업대기 탭에서 봅니다.

### 원인이 바뀌면

| 원인의 변화 | 줄 처리 |
| --- | --- |
| 임시 정책 승인 | 영향 화면을 다시 찾아(등록 뒤 바뀐 화면이 있을 수 있음) PV의 "영향 화면" 표와 맞춘 뒤, 그 화면들에 줄을 만듦. 승인하면서 내용을 고쳤으면 고친 내용으로 씀. 만든 줄 ID는 PV의 영향 화면 표에 적음 |
| 임시 정책 반려 | 영향 화면에는 줄이 없으므로 할 일 없음. 적용한 화면의 줄(`대기 (임시 정책 적용 예정)`)은 `제외 (날짜, PV-0004 반려)`, 이미 반영했으면 아래 "반영과 롤백"으로 되돌리고 `반영 롤백` |
| A/B 선택 | 고른 안의 영향 화면에만 줄을 만듦. 고르지 않은 안을 적용한 화면은 반려와 같이 처리 |
| 논의 결과 · 정책이 다시 바뀜 | 새 원인으로 새 줄을 만들고, 앞 줄은 "겹칠 때"와 같이 처리 |

### 반영 대기 목록 ID (2026-11-04)

여러 줄을 한꺼번에 반영한 뒤 그중 한 줄만 되돌려야 할 때, 그 줄이 바꾼 곳만 찾아 되돌릴 수 있게 줄마다 ID를 붙입니다.

- **표 안의 ID:** `R01`, `R02` … 그 화면 MD(또는 `screen-fixes/<CID>.md`) 안에서 순서대로 붙입니다. 새 줄은 표와 변경 이력(정리한 제외 줄)에 나온 번호 중 가장 큰 번호 다음 번호를 씁니다. 한 번 쓴 번호는 다시 쓰지 않고, 번호를 바꾸지 않습니다. 줄을 표에서 빼는 것은 아래 "제외 줄 정리"뿐입니다.
- **전체 ID:** 표 밖(커밋 메시지, 변경 이력, 다른 문서, 논의 항목)에서는 CID를 붙여 `TI-INS-01-T-R03`처럼 씁니다. CID가 하나뿐이라 전체 ID도 하나뿐입니다.
- 짝 CID에 같은 내용을 반영할 때도 줄은 화면마다 따로 두고, 근거 칸에 짝 줄의 전체 ID를 적어 서로 잇습니다.

### 반영 대기 목록 상태 (2026-11-04)

| 상태 | 뜻 | 작업대기에 셈 |
| --- | --- | --- |
| 대기 | 다음에 화면을 그릴 때 반영할 것. 이유가 있으면 괄호로 적음 (예: `대기 (확인 필요)`, `대기 (고객 논의)`, `대기 (팀 논의)`, `대기 (임시 정책 적용 예정)`). "임시 정책 적용 예정"은 임시 정책을 등록한 작업의 적용한 화면에만 씀. 반영하면 화면에 "임시 정책 포함"을 붙임 | 셈 |
| 반영 중 | 이번 작업에 넣어 화면 MD · Figma를 고치는 중 (계획 확인 뒤, 커밋 전) | 셈 ("반영 중"으로 따로 보여 줌) |
| 반영 완료 | 화면 MD · Figma에 반영하고 커밋함. 날짜를 적음 (예: `반영 완료 (2026-11-20)`) | 세지 않음 |
| 제외 | 반영하지 않기로 함 (예: 취소선으로 제거된 항목). 날짜와 이유를 괄호로 적음 (예: `제외 (2026-11-04, 취소선)`, 예전 이름 "반영 불필요"). 10일이 지나면 표에서 빼고 변경 이력으로 옮김 | 세지 않음 |
| 반영 롤백 | 반영했다가 이 줄만 되돌림. 날짜와 이유를 적음 (예: `반영 롤백 (2026-11-25, 고객 재요청)`) | 세지 않음. 다시 반영하려면 "대기"로 바꿈 |

- 상태가 바뀌어도 줄은 지우지 않습니다. 제외 줄만 아래와 같이 10일 뒤 변경 이력으로 옮깁니다.

### 제외 줄 정리 (10일)

제외 줄이 쌓이면 표를 보기 어려우므로, 제외로 바꾼 날부터 10일이 지난 줄은 반영 대기 목록 표에서 빼고 그 화면 MD의 변경 이력에만 남깁니다(2026-11-04 사용자 결정).

- **언제:** Claude는 날짜가 지났다고 혼자 움직이지 않습니다. 그 화면 MD를 고치는 작업이나 화면설계서 작업대기 정리(`rules/claude-work.md` 작업 유형 25)를 할 때, 10일이 지난 제외 줄을 함께 정리합니다.
- **변경 이력에 남기는 줄:** 버전 칸은 비우고, 날짜는 정리한 날, 바뀐 내용은 `반영 대기 R08 제외 정리: {바꿀 것 요약} (제외 {날짜}, {이유})`, 바꾼 사람은 정리를 요청한 사람, 근거는 그 줄의 근거 칸을 그대로 적습니다.
- **번호:** 뺀 줄의 번호는 다시 쓰지 않습니다(위 "표 안의 ID"). 원인 문서(PV · 논의 항목 · 회의록 · 정책 변경 이력)에 적힌 그 줄의 전체 ID는 그대로 두고, 변경 이력에서 찾습니다.
- **추적:** 무엇을 왜 제외했는지는 변경 이력과 git 기록에 남으므로 결정을 추적할 수 있습니다(헌법 9조).
- 대기 · 반영 중 · 반영 완료 · 반영 롤백 줄은 표에서 빼지 않습니다.

### 반영과 롤백

**반영할 때**

1. 반영할 줄을 정해 상태를 "반영 중"으로 바꿉니다(그리는 순서 3단계 확인 뒤).
2. 화면 MD와 Figma를 고칩니다. 줄마다 "지금 → 바꿀 것"이 반영 내용이므로, 한 곳을 두 줄이 함께 고치면 계획 확인 때 미리 알립니다.
3. 상태를 "반영 완료 (날짜)"로 바꾸고, 변경 이력의 "바뀐 내용"에 반영한 ID를 적습니다(예: `R03 · R05 · R07 반영`).
4. 커밋 메시지에 반영한 전체 ID를 모두 적습니다(예: `반영: TI-INS-01-T-R03, TI-INS-01-T-R05`). 줄마다 고친 곳(절 · 번호, Figma 프레임)을 커밋 본문에 한 줄씩 적어, 나중에 한 줄만 되돌릴 수 있게 합니다.

**한 줄만 되돌릴 때 (롤백)**

1. 되돌릴 전체 ID와 이유를 받습니다.
2. 그 ID를 반영한 커밋과 본문에서 그 줄이 고친 곳을 찾습니다. 같은 커밋의 다른 ID가 고친 곳은 건드리지 않습니다.
3. 그 뒤에 다른 줄이 같은 곳을 다시 고쳤으면 멈추고 어떻게 할지 묻습니다.
4. 화면 MD와 Figma의 그곳을 그 줄의 "지금" 내용으로 되돌립니다. 짝 CID의 이어진 줄도 되돌릴지 묻습니다(`rules/claude-work.md` 5절 T/L 짝).
5. 상태를 "반영 롤백 (날짜, 이유)"로 바꾸고, 변경 이력에 `R03 반영 롤백: 이유` 한 줄을 남깁니다.
6. 커밋 메시지는 `반영 롤백: TI-INS-01-T-R03`. 이미 컨펌 완료나 전달 완료된 화면이면 버전 처리는 `rules/status-lifecycle.md` 2 · 3절을 따릅니다.

### 화면설계서 작업대기

반영 대기 목록 중 아직 화면에 반영하지 않은 줄을 모아, 팀 프로그램 일정/작업 > 화면설계서 작업대기 탭에서 얼마나 쌓여 있는지 봅니다. 근거 칸의 원인 ID(PV · PD · CA · 회의 ID · 정책 ID)로 걸러 "이 원인 때문에 어느 화면에 몇 줄이 남았는지"도 봅니다.

#### 세는 법

| 숫자 | 세는 것 |
| --- | --- |
| 반영 대기 | 상태가 "대기"로 시작하거나 "반영 중"인 반영 대기 목록 줄 (반영 중은 따로 표시) |
| 작업 대기 화면 | 반영 대기가 1줄 이상인 화면 |
| 확인 필요 | 반영 대기 중 상태나 바꿀 것에 "확인 필요"가 있는 줄. 화면을 그리기 전에 답이 먼저 필요함 (`rules/discussion-answer.md`) |
| 메뉴 | 작업 대기 화면이 있는 메뉴 |

- 구분(디스크립션, 표기, 화면 정보, 정책 반영, 알럿, 문구 등)은 반영 대기 목록의 "구분" 칸을 그대로 씁니다.

#### 담당자

- 메뉴 담당자는 `screens/{메뉴}/_menu.md`의 `owner`입니다. 비어 있으면 "담당자 미정"으로 보여 줍니다.
- UX 담당자 칩은 여러 명을 함께 골라 볼 수 있습니다. 화면별 작성자는 화면 머리말의 `author`로 따로 보여 줍니다.

#### 보여 주는 순서

메뉴별로 반영 대기가 많은 순서로 보여 주고, 메뉴를 열면 화면별(많은 순)로, 화면을 누르면 그 화면 정의서의 반영 대기 목록으로 갑니다.

## 8. 디스크립션 쓰는 법 (2026-11-04)

디스크립션은 개발자와 고객사가 함께 읽습니다. 4명의 Claude가 같은 문장을 쓰도록 문장 형식과 말을 고정합니다.

### 원칙

1. 정책서 규칙 문장과 같은 형식을 씁니다(`rules/policy-writing.md`). 조건을 앞에 두고 "~함 / ~됨 / ~임"으로 끝맺습니다.
2. 한 문장에는 한 가지만 씁니다.
3. 정책 내용은 다시 쓰지 않고 정책 ID로만 잇습니다(헌법 3조).
4. 화면 항목 이름은 영어 표준어로 씁니다(용어집).

### 고정 문장 패턴

| # | 쓰는 곳 | 패턴 | 예 |
| --- | --- | --- | --- |
| 1 | 보여 주기 | `[조건]이면 [요소]를 표시함` | Not in Use Module이 있으면 Disabled 수를 표시함 |
| 2 | 누르기 · 고르기 | `[버튼]을 누르면 [결과]함` / `[항목]을 고르면 [결과]함` | [Save]를 누르면 입력한 값을 저장하고 팝업을 닫음 |
| 3 | 사용 가능 여부 · 기본값 | `[조건]이면 [버튼]을 비활성화함` / `기본값은 [값]임` | 입력한 값이 없으면 [Save]를 비활성화함 |
| 4 | 화면 이동 · 알럿 | `[CID] 화면 이름으로 이동함` / `[조건]이면 [알럿 ID]를 띄움` | 등록되지 않은 Module Tab에 들어가면 Alert_004를 띄움 |
| 5 | 정책 · 값 표기 | `[주제]는 [정책 ID]를 따름` / `[항목]은 [형식]으로 표기함 (기준)` | Module 수는 `Enabled n · Total n (Disabled n)`으로 표기함 (POL-EQP-009) |

### 표준어로 맞출 말

| 쓰지 않는 말 | 쓰는 말 |
| --- | --- |
| 노출 · 표출, 보여 준다는 뜻의 "제공" | 표시 (기능 · 메뉴를 갖춘다는 뜻의 "제공"은 그대로 씀) |
| 미노출 | 표시하지 않음 |
| 클릭 시 · 선택 시 | 버튼 · 아이콘 · 링크 · 탭은 "누르면", 목록 · 옵션 · 라디오 · 체크박스 · 드롭다운 값은 "고르면" |
| Default | 기본값 |
| 상세 UI는 하단 이미지 참조 | 쓰지 않음. 화면 MD의 "화면 예시" 표 · 케이스로 옮김 |

- 이 표의 쓰지 않는 말은 용어집(`glossary/terms.csv`)에도 올려, 화면 점검의 용어 항목(`rules/claude-work.md` 5절)에서 함께 거릅니다.
- 정책 `summary`를 디스크립션에 정책 ID와 함께 붙이는 방식(`rules/policy-writing.md`)은 그대로 씁니다.

### 0. 화면 정의 (고객이 먼저 읽는 곳)

"0. 화면 정의"는 아래 순서로 씁니다. 화면 위에는 번호를 표시하지 않습니다.

1. 목적: 이 화면에서 무엇을 하는지 한 문장
2. 쓰는 사람: User Type
3. 들어오는 길: LNB 경로, 또는 이 화면을 여는 화면 · 버튼
4. Service Mode (L-IOS 화면)
5. 관련 정책: 정책 ID

### 요소별 필수 항목

기존 디스크립션(180화면)을 세어 보니 입력 필수 여부(9화면), User Type별 차이(7), 긴 글 처리(2), 팝업 닫기(거의 없음)가 특히 빠져 있었습니다(2026-11-04 분석). 요소 종류마다 아래를 반드시 적고, 빠지면 점검(2절 5단계)에서 걸러냅니다. 정해지지 않은 것은 만들지 않고 "질문 대기"에 올립니다.

| 요소 | 반드시 적을 것 |
| --- | --- |
| 목록 · 표 | 칸(이름 · 값 · 형식 · 단위), 기본 정렬과 정렬되는 칸, 한 번에 보이는 줄 수 · 스크롤, 빈 상태, 값이 바뀌는 때 |
| 입력 칸 | 필수 여부, 형식 · 길이 제한, 기본값, 안내 글(placeholder), 틀렸을 때(알럿 ID 또는 안내 문구), 저장되는 때 |
| 버튼 | 누르면 결과, 쓸 수 있는 조건(입력 · 장비 상태 · User Type · Service Mode), 확인 알럿 |
| 필터 · 검색 | 대상 칸, 기본값, 찾는 방식(일부 일치 / 정확히 일치), 초기화 |
| 상태 표시 | 상태값 기준(`glossary/status-values.csv`), 값이 바뀌는 때(실시간 / 새로고침 / 주기) |
| 팝업 | 여는 곳, 닫는 방법(버튼 · ESC · 바깥 누르기), 저장하지 않은 채 닫을 때 |
| 모든 글 | 긴 글 처리(말줄임과 툴팁 / 줄바꿈). 7개 언어 중 가장 긴 표현 기준(`rules/language-set.md`) |

- 날짜 · 시간 · 숫자 · 단위 표기, 정렬 · 페이지처럼 여러 화면에 같은 규칙은 디스크립션마다 쓰지 않고 공통 정책 ID로 잇습니다. 공통 정책은 Common UX 정의를 먼저 옮겨 1차로 쓰고, 부족한 부분은 질문으로 채워 갑니다(`rules/policy-writing.md`).
- T/L 짝 화면에서 한쪽에만 있는 내용은 문장 앞에 `(L-IOS만)` · `(T-IOS만)`을 붙입니다.

### 번호 매기기

디스크립션 번호는 Claude가 붙입니다. 기존 화면의 `0 → 1, 2, 3 → 3-1, 3-2` 두 단계 모양을 따릅니다.

1. `0`은 화면 정의입니다. 화면 위에는 표시하지 않습니다.
2. 영역 번호 `1, 2, 3…`은 화면을 위에서 아래로, 같은 줄이면 왼쪽에서 오른쪽으로 읽는 순서로 붙입니다. GNB · LNB는 번호를 붙이지 않고 Common UX를 따릅니다.
3. 영역 안 세부는 `1-1, 1-2`까지만 씁니다. 그보다 깊은 내용은 번호 없이 문장으로 씁니다.
4. 화면 위 번호 표시(Description Number 컴포넌트)는 그 요소의 왼쪽 위에 둡니다. 같은 요소가 반복되면(표의 줄 등) 첫 번째에만 둡니다.
5. 팝업 · Tab은 CID마다 `1`부터 따로 매깁니다.
6. T/L 짝 화면은 같은 영역에 같은 번호를 씁니다. 한쪽에만 있는 영역은 공통 번호 뒤 번호를 쓰고, 다른 쪽에서는 그 번호를 비워 둡니다(예: L-IOS에만 있는 영역이 `7`이면 T-IOS 디스크립션에는 7이 없음). 개발자가 T/L을 번호로 바로 맞대어 봅니다.
7. 상태별 화면 · 케이스 · 최장 언어 화면은 기획 프레임과 같은 번호를 쓰고, 달라진 영역에만 번호 표시를 둡니다.
8. 컨펌 전까지는 다시 매길 수 있습니다. 컨펌 완료 뒤에는 번호를 바꾸지 않습니다. 새 영역은 끝 번호를 받고, 지운 영역의 번호는 `(삭제)`로 남겨 비워 둡니다. 반영 대기 목록과 개발사 QA가 번호로 그 자리를 가리키기 때문입니다.
9. 다른 문서에서 가리킬 때는 `TI-INS-01-T #3-2`처럼 CID와 번호를 함께 씁니다. 화면 MD의 화면 예시 · 문구 · 알럿 표의 "번호" 칸도 같은 번호입니다.
