# CURECA UX 협업 룰 작업 인계 요약

Oct 29, 2026 · @서보경

## 이 문서 사용법

이 문서는 2026년 10월 29일까지 진행한 "UX 기획 협업 룰" 작업을 새 Claude 세션에서 이어가기 위한 인계 요약입니다. 상세 내용과 표는 본 문서인 [UX 기획 협업 룰 검토 및 초안](https://claude.ai/artifact/76X9TsXUpwEBpjMX5DGyvo)에 있고, 이 문서는 그 결정의 맥락과 남은 일을 한곳에 모았습니다.

**새 세션 시작 방법:** 새 대화에서 이 문서 링크와 본 문서 링크를 함께 주고 "두 문서를 읽고 이어서 진행해줘"라고 요청합니다. 다음 작업은 아래 "남은 할 일"의 1번(저장소 구조 확정과 진행 방식 선택)입니다.

**대화 방식 메모:** 프로젝트 리더(사용자)와 한국어로 진행했고, 결정은 본 문서에 바로 반영하면서 "(결정)", "(확인)", "(보류)" 표시로 상태를 구분했습니다.

## 프로젝트 배경과 목표

UX 4명이 Claude와 공통 git으로 기획하면서, 누가 작업하든 같은 기준의 화면과 정책이 나오도록 공통 룰을 만드는 것이 목표입니다. 지금은 2단계(룰 초안 확정)에 있습니다.

### 프로젝트

| 구분 | 내용 |
| --- | --- |
| 장비 | CURECA. 검체 투입부터 전처리, 핵산추출, 시약반응까지 자동화. 장비 제작과 개발은 타 업체 |
| T-IOS (CID 접두어 TI) | 웹 브라우저 관제 플랫폼. 관리자가 구동 상태를 확인하고 장비 정책·프로토콜·외부 통신·계정을 설정. 여기서 만든 계정을 T/L 공통으로 사용 |

### 해결하려는 문제

- 장비가 시운전 전이라 화면과 정책 변경이 잦고, 화면들이 같은 정책으로 엮여 있어 한 변경이 다른 담당자 화면까지 번짐
- 정책이 Teams, 회의록 시트, Figma 정책서, 각 화면 디스크립션에 흩어져 최신본을 찾기 어렵고, 연관 화면을 놓쳐 이미 고친 화면까지 되돌린 사례가 있음
- Figma 3개 페이지를 손으로 맞추다가 누락이나 미컨펌 내용 유출, 이전본 덮어쓰기가 생김
- 4명이 각자 다른 방식으로 기획해 용어와 구조가 다름

### 이미 있는 프로그램

Figma 화면을 프레임 단위로 불러와 요청을 입력하면 Claude가 작업하고, 담당자가 승인하면 Figma에 자동 반영하며 리비전 이력도 남기는 자체 프로그램이 있습니다. 이 프로그램은 git의 룰을 읽고 Claude 결과값으로만 동작합니다. 준비가 끝나면 Figma 직접 수정은 금지할 예정입니다.

## 주요 결정 사항

최상위 원칙은 "사람의 검체를 다루는 장비이므로 정확성이 속도보다 우선한다"이며, 아래 결정은 모두 본 문서에 반영되어 있습니다.

### 헌법 v0.2 (10개 조항)

| 조 | 원칙 |
| --- | --- |
| 1 | 정확성 우선. 검증 관문을 통과하지 못한 변경은 일정과 관계없이 넘어가지 않음 |
| 2 | 단일 기준은 git 저장소. 저장소에 없으면 효력 없음. 여러 곳에서 다르면 결정 기록으로 최신 판단 |
| 3 | 정책은 정책서에만 정의. 디스크립션은 정책 ID + 자동 요약 + 정책서 위치 링크로 참조 |
| 4 | 공통 자료는 주간 미팅에서 함께 합의, 화면설계서는 작성자가 책임. Claude는 제안만 |
| 5 | 변경은 영향 범위 전체를 한 단위로. 다른 담당 화면은 각 작성자에게 알려 함께 수정 |
| 6 | 반영은 저장소 → 작업 → 컨펌 → 개발사 한 방향. 모든 수정은 프로그램 경유 |
| 7 | Claude는 근거로만 작업. 근거 없거나 충돌하면 질문. 작업 하나에 대화 하나. 기준 출처 목록 밖은 근거 아님. 예전 모호한 표현은 단정하지 않고 질문 |
| 8 | 모든 흐름을 장비 상태·서비스 모드·User Type별 권한·정책으로 점검. 모드와 권한은 늘 최신 문서로 관리. 신규 메뉴에 정의 없으면 정의부터 요청. 정상 흐름만 그린 설계는 미완성 |
| 9 | 모든 결정은 추적 가능해야 함. 폐기 화면·정책도 근거와 함께 보관 |
| 10 | 하나의 개념은 용어집의 표준어 하나로만. 새 용어는 협의 대기 목록에 먼저 |

운영 원칙: 룰과 승인 단계는 최소로 시작해 필요할 때 추가, 헌법 개정은 주간 미팅 합의, 적용 범위는 UX 4명(UI팀은 상태값 등 공유 부분만), git 작업은 프로그램이 처리.

### 변경 흐름

- **승인자 없음.** 단계별 승인자를 두면 초기 운영이 막혀서 뺐습니다. 오너 지정도 운영하며 필요해지면 미팅에서 추가합니다.
- **공통 자료**(정책서, Common UX, 용어집, 장비 상태 정의서, 알럿 카탈로그, 권한 매트릭스, 룰 문서): 협의 대기 목록에 올림 → 미팅 전 Claude가 중복·충돌·영향 화면 정리 → 주 1회 UX 4명 미팅에서 합의·보류·기각 → 합의 항목만 반영하고 결정 기록 → 영향 화면 작성자에게 알림.
- **협의 대기 항목은 효력 없음.** 고객이 먼저 작업을 요청한 경우에만 "미결 정책 포함" 표시를 붙여 진행합니다.
- **긴급 변경:** 팀원이 요청하면 미팅 없이 바로 반영. 자동 검증은 거치고, 긴급 표시와 요청자·사유를 남겨 다음 미팅에서 공유합니다.
- **화면설계서:** 작성자가 오너로 직접 수정. 다른 사람은 작성자에게 요청합니다.
- **팀원 간 요청:** Claude는 다른 팀원 계정에 직접 메시지를 보내거나 답을 받을 수 없어서, git 이슈나 협의 대기 목록을 요청 창구로 씁니다.
- **개발사 전달:** 정해진 주기 없이 매번 협의한 공유일에, 그때까지 확정된 범위를 묶어 전달합니다.

### 상태값

| 축 | 상태 | 바꾸는 방법 |
| --- | --- | --- |
| UX | 작업 중 / 컨펌 중 / 컨펌 완료 | 담당 기획자가 프로그램에서 선택하면 Claude가 반영 |
| UI | 작업 중 / 컨펌 대기 중 / 컨펌 완료 | 작업 중·컨펌 대기 중은 디자이너 수동(Claude 일일 점검), 컨펌 완료는 기획자 요청으로 Claude 반영 |
| 전달 | 전달 대기 / 전달 완료 | 프로그램 자동 |

- **관리 단위는 메뉴**(대시보드 LNB에서 눌리는 단위, IA 1\~2 depth). 메뉴 안 CID들은 상태를 공유하고, 변경 이력과 표시는 CID별로 남깁니다.
- UI "컨펌 대기 중"은 전사 공통 값이라 이름과 뜻을 바꾸지 않습니다(고객 리뷰 요청 가능 상태이자 리뷰 중일 수도 있음).
- "컨펌 완료"는 요청하면 바로 변경. 컨펌 완료와 전달 완료로 바뀔 때마다 화면 정보의 Date를 그날로 갱신합니다.
- **표시(플래그) 3개:** 변경 예정(CR ID), 미결 정책 포함(정책 ID), 연동 변경(원인 CID·정책 ID).
- **큰 변경과 작은 변경:** 흐름·레이아웃·상태값·컴포넌트 구성이 바뀌면 메뉴를 "작업 중"으로 되돌림, 문구·라벨·디스크립션·수치만 바뀌면 "변경 예정" 표시. 화면설계서 룰에 포함.
- 화면 옆 버전별 포스트잇 메모는 유지하되 리비전 히스토리에서 자동 생성합니다.
- 매일 정해진 시간에 메뉴별 상태로 진행 현황을 정리하는 안은 팀 논의 중입니다.
- **폐기:** 정책 변경으로 사라진 화면은 지우지 않고 "폐기" 상태로 보관 폴더에 옮기고, Figma 컨펌·개발사 페이지와 Claude 근거에서 제외합니다. Runtime Info 팝업(TI/LI-INS-02-02-P)은 폐기 확정.

### ID와 화면설계서

- 기존 CID는 그대로 하나만 씁니다. 새 ID는 만들지 않고, IA에 "짝 CID" 칸을 두어 T/L 공통 화면을 연결합니다.
- T/L 짝 화면은 화면설계서 파일 하나(파일명은 T-IOS CID, L-IOS 단독은 LI CID)에 두 CID와 제품별 차이를 함께 적습니다.
- T/L 관계는 "화면동일"과 "중복" 두 칸을 합쳐 동일 / 권한 차이 / 기능 추가 / 단독 4가지로 표시합니다.
- 접미어 규칙(팝업 -P, 탭 -T, 권한 변형 -V/-M)은 신규 CID부터 적용합니다.
- 화면 정보 칸은 Ver, Date, CID, 작성자, 화면, 경로만 둡니다. Dev·SG 확인 일자는 다른 템플릿의 잔재라 제거합니다.
- 화면설계서 체크포인트: 상태별 화면(정상·로딩·비활성·오류·빈 상태·장비 이상), 노출 모드와 User Type 권한 정의, 정책은 ID 참조, 디스크립션은 고정 문장 패턴("\[조건\]일 때 \[대상\]은 \[동작\]한다" 등 4\~5개).

### User Type과 권한

| User Type | 누가 갖나 | 권한 |
| --- | --- | --- |
| Service | 장비를 설치·셋팅하는 고객사 직원 | 슈퍼관리자. 숨겨진 기능까지 전부. 설치 후 Admin·User 계정 생성 |
| Admin | 장비를 구매한 기관의 관리자 | 프로토콜·계정 셋팅 등 운영 관리 메뉴. Admin·User 계정 생성 |
| User | 구매 기관에서 실제 검사를 하는 사용자 | 기본 메뉴와 기능만 |

- Setting은 하위 메뉴별로 권한이 다르고 일부만 Service 전용입니다(정책서의 "Admin은 Setting 접근 불가" 문장은 정정 필요).
- 종료 옵션은 Common UX(COMM-3-a)가 최신: Service는 \[Exit\]로 프로그램·시스템 종료, Admin과 User는 \[Shut Down\]으로 시스템 종료만.
- 예전 디스크립션의 "관리자"는 Admin입니다(Session Timeout, 계정 잠금 시간 설정). 고객이 정책을 자주 바꿔 예전 표현이 남아 있으니, 모호하면 작업 때마다 확인합니다.
- 메뉴·버튼은 서비스 모드가 허용하고 User Type 권한도 허용할 때만 노출됩니다. 모드는 개발사 기준(외부 자료, 변경은 CR로 받음), 권한은 우리 정책서 기준입니다.

### 용어

- 표준어는 화면 라벨과 같은 **User Type**. 계정 유형, 사용자 유형, Account Type, 등급, 유형을 뜻하는 "권한"은 쓰지 않습니다. 허용 범위를 뜻하는 "권한"은 다른 개념이라 그대로 씁니다.
- Claude 검토 6단계: 읽기 → 찾기 → 바꾸기(뜻이 확실한 것만) → 묻기(문맥 따라 다른 것) → 검사 → 보고(치환 목록과 질문 목록 첨부).
- 정책서 현행화를 시작하기 전에 용어집을 확정하고, 정책서부터 표준어로 씁니다.
- 서비스 모드 표의 기능 이름(View, Status Control, Note Writing, Initialize, Stop, Door Control, Change Settings)을 기능 이름 기준으로 씁니다.

### Claude 작업 방식

- 공통 지침은 하나만 두고 개인 커스텀은 쓰지 않습니다. 팀 공유 Claude 프로젝트에 헌법·용어집·공통 지침을 두는 것을 권했습니다.
- 기준 출처 목록: Common UX = DY common UX 페이지, 화면 = 작업방 메뉴별 페이지, 정책서 = 작업방 정책서\_2026.08.28. 작업방이 정리되면 갱신합니다.
- 일관성 목표는 "같은 결과물"이 아니라 "같은 검증 기준 통과"입니다. 입력(지침·로딩 순서)을 고정하고 결과를 자동 검증합니다.
- 정책서 현행화 때는 기존 문서 간 충돌 목록부터 뽑아 미팅에서 판정한 뒤 반영합니다.

## 저장소 구조안 (사용자 확인 대기)

마지막으로 제안한 로컬 git 저장소 구조입니다. 화면 폴더를 상태 관리 단위인 메뉴로 나누고, 효력 없는 `pending/`과 효력 있는 `policy/`를 분리했으며, 검증용 데이터는 CSV로 두었습니다.

## 남은 할 일과 다음 단계

다음 세션은 저장소 구조 확정과 진행 방식 선택에서 시작해, 헌법과 P1 룰을 실제 파일로 옮기는 순서로 진행합니다.

### 다음 단계 순서

1. **저장소 구조 확정:** 사용자가 구조안에서 바꾸거나 뺄 폴더를 정하고, 진행 방식(채팅 압축 파일 / Claude Code)을 고릅니다.
2. **기본 파일 생성:** README, CLAUDE.md, constitution.md(헌법 v0.2를 v1.0으로 정리), sources.md, templates/를 만듭니다.
3. **P1 룰 문서화:** 공통 룰 목록의 P1 8개(헌법, 저장소·ID, 문서 상태, Claude 작업, 장비 상태 정의서, 알럿 카탈로그, 권한 매트릭스, 용어·표기)를 rules/와 reference/에 옮깁니다.
4. **데이터 파일:** 서비스 모드 매트릭스와 권한 매트릭스 초안을 CSV로, 용어집 v0을 만듭니다.
5. **IA 반영:** 사용자가 고친 IA를 받아 ia/와 menu-map.csv를 만듭니다.
6. 이후 3단계(정책서 현행화)로 넘어갑니다. 시작 전에 용어 후보를 모아 용어집을 확정합니다.
