# UX 기획 협업 룰 검토 및 초안

Oct 28, 2026 · @서보경

## 개요

UX 4명이 Claude와 공통 git으로 기획하면서도 누가 작업하든 같은 기준의 결과물이 나오도록, 공통 룰의 범위와 우선순위를 정하는 문서입니다.

| 구분 | 내용 |
| --- | --- |
| 프로젝트 | 검체 투입부터 전처리, 핵산추출, 시약반응까지 자동화하는 장비의 온프레미스 제어 앱 + 브라우저 기반 관제 플랫폼 기획·디자인 |
| T-IOS (CID 접두어 TI) | 웹 브라우저 기반 관제 플랫폼. 관리자가 자리에서 장비 구동 상태를 확인하고, 장비 정책·프로토콜·외부 통신·계정을 설정. 여기서 만든 계정은 T-IOS와 L-IOS에서 같은 아이디로 사용 |
| L-IOS (CID 접두어 LI) | 장비에 온프레미스로 설치된 제어 앱. 장비 본체 모니터와, 큰 장비를 돌아다니며 쓰는 콘솔(둘 다 24인치)에서 사용하고, PCR 시약 오염 방지를 위해 별도 공간의 데스크탑에도 설치. 장비 상태 확인과 제어(장비 열기, 중단, 소모품·시약 투입 등) 중심 |
| 역할 분담 | 장비 제작·개발은 타 업체, 우리는 기획(UX 4명)과 UI(2명) |
| 협업 도구 | Figma(팀 작업 / 고객 컨펌 / 개발사 공유 3개 페이지), 공통 git, Claude 계정 4개 |
| 핵심 문제 | 장비 미완성으로 화면·정책 변경 빈발, 화면 간 정책 연동 누락, 3개 Figma 페이지 간 누락 및 미컨펌 내용 유출 |
| 현재 진행 | Common UX 재설계, Figma 프레임 연동 Claude 작업 프로그램(승인 후 자동 반영, 리비전 관리) 구축 |
| 예정 작업 | 정책서 현행화, 현행화 정책 + Common UX 기반 기존 화면 재설계, CID 기반 MD 저장소 구축 |

## 검토 결론

현재 방향은 맞습니다. git 저장소를 기준으로 두고 Claude가 그 기준에 맞춰 작업하는 구조는 업계의 스펙 주도 개발(SDD)과 같고, CID·정책 ID 연결은 의료기기 사용적합성 표준의 추적성 요구와도 맞닿아 있습니다.

| 관점 | 현재 방식과 일치하는 점 | 근거 |
| --- | --- | --- |
| 스펙 주도 개발(SDD) | 채팅이 아닌 저장소 문서를 기준(SSOT)으로 삼고, Claude는 그 문서에 맞춰 생성·수정 | 2026년 기준 GitHub Spec Kit, Kiro 등 전용 도구와 방법론이 자리 잡음 ([참고](https://codemyspec.com/blog/spec-driven-development)) |
| IEC 62366 추적성 | CID ↔ 정책 ID 연결로 화면 결정의 근거를 추적 | 체외진단(IVD) 장비는 사용적합성 엔지니어링 파일(UEF)로 추적성을 증명해야 함 ([참고](https://userfocus.co.uk/articles/ISO62366.html)) |
| 사람 승인 게이트 | Claude 제안 → 담당자 승인 → Figma 반영 | SDD 도구들도 단계별 검증 후 다음 단계로 넘어가는 관문 구조 사용 ([참고](https://addyosmani.com/blog/good-spec/)) |
| 리비전 관리 | 변경 이력을 저장소에서 관리 | git을 AI 작업의 기억 계층으로 쓰는 방식과 동일 ([참고](https://pasqualepillitteri.it/en/news/158/framework-ai-spec-driven-development-guide-bmad-gsd-ralph-loop)) |

## 보완 필요 지점

가장 중요한 보완은 일관성 목표를 "같은 결과물"에서 "같은 검증 기준 통과"로 바꾸는 것입니다. 나머지 다섯 가지는 구조적으로 누락과 불일치를 막기 위한 장치입니다.

| # | 이슈 | 리스크 | 대응 방안 | 반영할 룰 |
| --- | --- | --- | --- | --- |
| 1 | "같은 질문 = 같은 결과" 목표 | Claude는 같은 입력에도 표현이 매번 달라 목표 달성 불가 | 입력(지침·로딩 순서) 고정 + 결과물 자동 검증 | Claude 작업 룰, 검증 룰 |
| 2 | 정책서 현행화 순서 | 4명이 다르게 쓴 기존 문서의 불일치까지 흡수 | 충돌 목록 먼저 추출 → 사람이 판정 → 결정 기록(ADR) 후 현행화 | 정책서 룰, 결정 기록 룰 |
| 3 | 쓰기 경로 이원화 | 프로그램과 개인 Claude 대화가 각각 저장소를 수정하면 일관성 붕괴 | 저장소·Figma 쓰기는 프로그램 경유만, 개인 대화는 질의·초안까지 | Claude 작업 룰, Git 룰 |
| 4 | Figma 3개 페이지 수동 관리 | 누락, 미컨펌 내용의 개발사 유출 | MD 상태값 기반으로 페이지 이동 자동화 | 상태 룰, Figma 동기화 룰 |
| 5 | 시운전 기간 변경 빈도 | 잦은 전달로 개발사 혼선 | `TBD-장비` 태그로 변동 영역 분리, 개발사 전달은 협의한 공유일에 묶어서 | 정책서 룰, 변경관리 룰 |
| 6 | 컨텍스트 증가 | 정책·화면이 늘면 전체를 Claude에 넣을 수 없음 | CID별 참조 정책·컴포넌트 인덱스 파일로 필요분만 로드 (영향도 분석 기반 겸용) | 저장소 구조 룰 |

## 다른 팀 협업 사례

개발 조직의 AI 협업 방식과 규제 산업의 문서 관리 방식에서 바로 가져올 수 있는 것이 다섯 가지 있습니다.

| 사례 | 핵심 방식 | 우리 적용 방법 |
| --- | --- | --- |
| [GitHub Spec Kit](https://codemyspec.com/blog/spec-driven-development) | 헌법(constitution) → 명세 → 계획 → 작업 → 구현, 모두 저장소의 마크다운으로 관리하고 단계별 검증 후 진행 | 모든 룰 위에 짧고 거의 바뀌지 않는 "헌법" 문서 1개 배치 |
| [Kiro (EARS 문법)](https://www.augmentcode.com/tools/best-spec-driven-development-tools) | 요구사항을 몇 가지 고정 문장 패턴으로만 작성 | 디스크립션 문장 패턴 4\~5개로 제한 (예: "\[조건\]일 때 \[대상\]은 \[동작\]한다") |
| [git을 기억으로 쓰는 방식](https://pasqualepillitteri.it/en/news/158/framework-ai-spec-driven-development-guide-bmad-gsd-ralph-loop) | 긴 대화를 이어가지 않고 작업마다 새 컨텍스트로 시작, 기억은 git에 | "작업 하나 = 대화 하나", 이전 대화 의존 금지 |
| 결정 기록(ADR) | 중요한 결정의 배경·대안·결론을 문서로 남김 | 정책 충돌 판정, 고객 결정사항을 ADR로 기록해 Claude 근거 자료로 활용 |
| [IEC 62366 추적성](https://www.benkana-interfaces.com/landing) | 사용자 요구·위험 → 설계 결정 → 위험 통제 → 테스트 결과까지 추적 | CID·정책 ID에 "근거 / 위험 관련 여부" 칸 추가, 고객사 인허가 양식 확인 |

주의할 점: SDD는 문서 작성 부담 때문에 "워터폴 2.0"이라는 비판도 받습니다 ([참고](https://alexcloudstar.com/blog/spec-driven-development-2026/)). 룰은 최소로 시작해 운영하며 늘립니다.

| 변경관리(CR) | 모든 변경은 CR로 시작, 영향 CID 일괄 수정, 리비전 기록 형식, 개발사 전달은 릴리즈 단위 | P2 | 미착수 |
| Git 협업 | 브랜치 전략, 커밋 메시지 규칙, 공통 영역은 주간 미팅 합의 후 반영, 화면 담당 배정 | P2 | 미착수 |
| 검증·리뷰·승인 | 자동 검증(ID 참조 유효성, 용어집, 필수 섹션), 리뷰 체크리스트, 재현성 골든 세트 | P2 | 미착수 |
| Figma 동기화 | 3개 페이지 역할, 상태 기반 자동 이동, Figma 직접 수정 시 역반영 규칙 | P3 | 미착수 |
| 역할·룰 운영 | 공통 자료는 주간 미팅 합의로 변경, 화면설계서는 작성자가 오너, 오너·승인자 지정은 필요해질 때 미팅에서 추가, 룰 개정도 미팅 합의 | P3 | 미착수 |

## 표준 작업 흐름

모든 변경은 9단계를 거치며, 각 단계의 통과 조건을 충족하지 못하면 이전 단계로 돌아갑니다.

| 단계 | 작업 | 담당 | 산출물 | 통과 조건 |
| --- | --- | --- | --- | --- |
| 1 | 변경 요청 등록 | 요청 접수자 | CR 문서 (출처: 고객사 / 장비사 / 개발사 / 내부) | 근거 자료 첨부 |
| 2 | 영향도 분석 | Claude + 담당 기획자 | 영향 정책 ID·CID 목록 | 인덱스 기준 누락 없음 확인 |
| 3 | 정책 수정 | 제안자 + Claude | 정책서 diff, 필요 시 ADR | 주간 미팅 합의 (협의 대기 목록 경유) |
| 4 | 영향 화면 일괄 수정 | 화면 담당 + Claude | CID MD diff | 영향 CID 전체가 같은 PR에 포함 |
| 5 | 자동 검증 | 프로그램 | 검증 리포트 | ID 참조·용어집·필수 섹션 통과 |
| 6 | 자체 점검 | 화면 작성자 | 점검 결과 첨부 | 체크리스트와 자동 검증 통과 |
| 7 | 고객 컨펌 | 담당 기획자 | 고객 컨펌 페이지 반영 (상태: Client Review) | 고객 컨펌 확인 |
| 8 | 확정 | 상태 변경 권한자 | main 머지 (상태: Confirmed) | Date 갱신 |
| 9 | 개발사 전달 | 프로그램 | 개발사 공유 페이지 자동 반영 + 릴리즈 노트 (상태: Delivered) | 협의된 공유일 도래 |

## 헌법 초안 (v0.2)

우리 팀의 최상위 원칙은 "사람의 검체를 다루는 장비이므로 정확성이 속도보다 우선한다"이며, 아래 10개 조항은 모든 룰과 Claude 작업에 우선합니다. 각 조항은 실제로 겪은 문제에서 출발했습니다.

| 조 | 원칙 | 배경 (우리가 겪은 문제) |
| --- | --- | --- |
| 1 | **정확성 우선.** 검증 관문을 통과하지 못한 변경은 일정과 관계없이 다음 단계로 넘어가지 않는다. | 하나의 변경이 장비사, 개발사, 내부 디바이스팀까지 파급됨 |
| 2 | **단일 기준.** 정책과 화면의 유일한 기준은 git 저장소다. Teams, 회의록, Figma 코멘트는 근거 자료이며, 저장소에 기록되기 전까지 효력이 없다. 같은 정책이 여러 곳에서 다르면 출처 위치가 아니라 결정 기록으로 최신을 판단한다. | 정책이 Teams, 회의록 시트, Figma 정책서, 디스크립션에 흩어져 최신본을 찾느라 시간 낭비 |
| 3 | **정책은 한 곳에서 정의한다.** 정책은 정책서에만 정의하고, 화면 디스크립션은 정책을 다시 쓰지 않고 정책 ID와 자동 생성된 요약으로 참조하며, ID를 누르면 정책서의 해당 위치로 이동한다. | 디스크립션마다 정책을 녹여 쓰다 보니 변경 시 일부 화면만 수정됨 |
| 4 | **공통 자료는 함께 합의하고, 화면은 작성자가 책임진다.** 정책은 고객 미팅에서 결정되고, 정책서·Common UX 등 공통 자료의 변경은 협의 대기 목록에 올려 주간 팀 미팅에서 합의한 것만 반영한다. 화면설계서는 작성자가 직접 고친다. Claude는 제안만 한다. | 같은 고객 발언도 사람마다 다르게 해석함. 승인 단계가 많으면 초기 운영이 막힘 |
| 5 | **변경은 영향 범위 전체를 한 단위로 처리한다.** 영향받는 화면을 모두 확인하기 전에는 수정을 시작하지 않으며, 담당 영역을 넘는 화면은 각 작성자에게 알려 같은 변경 안에서 함께 고친다. | 연관 화면을 놓쳐, 이미 고친 화면까지 되돌린 사례 |
| 6 | **반영은 한 방향으로만 흐른다.** 저장소 → 작업 페이지 → 고객 컨펌 페이지 → 개발사 공유 페이지. 모든 수정은 프로그램을 거치며, 하위 페이지를 고쳐 상위로 복사하지 않는다. | 공유 페이지에서 고친 뒤 작업 페이지에 붙여넣어 최신본이 이전본으로 되돌아감 |
| 7 | **Claude는 근거로만 작업한다.** Claude는 저장소에 있는 근거로만 작업하고, 근거가 없거나 정책이 충돌하면 만들어내지 않고 질문으로 남긴다. 작업 하나에 대화 하나로 시작한다. 기준 출처 목록 밖의 자료는 근거로 쓰지 않고, 예전 디스크립션의 모호한 표현은 추정하더라도 단정하지 않고 묻는다. | 개인별 질의로 쓰던 Claude 결과가 사람마다 달랐음 |
| 8 | **설계는 실제로 작동해야 완성이다.** 모든 화면 흐름은 장비 상태, 서비스 모드, User Type별 권한, 정책에 비추어 점검하고, 사용자 실수가 가능한 지점에는 정책에 정의된 안내와 알럿이 있어야 한다. 서비스 모드와 권한은 늘 문서로 최신 상태를 유지하고, 신규 메뉴·화면에 노출 모드와 권한 정의가 없으면 정의부터 요청한다. 정상 흐름만 그린 설계는 미완성이다. | 장비 상태값과 사용자 작업이 많아 정책 위반 흐름을 사람이 다 검증하기 어려움. 모드·권한 정의가 화면마다 흩어져 있음 |
| 9 | **모든 결정은 추적 가능해야 한다.** 누가, 언제, 어떤 미팅에서, 무엇을 근거로 결정했는지 남긴다. 폐기된 화면과 정책도 지우지 않고 근거와 함께 보관한다. | 약 6개월 후 인허가 단계에서 결정 근거가 필요해질 가능성 |
| 10 | **하나의 개념은 하나의 말로 쓴다.** 정책서, Common UX, 화면설계서 모두 용어집의 표준어만 쓴다. 용어집에 없는 새 용어는 쓰기 전에 협의 대기 목록에 올린다. | 같은 개념을 계정 유형, 사용자 유형, User Type, Account Type으로 섞어 써 검색과 검증이 어려움 |

### 운영 원칙

- **룰은 최소로 시작한다.** 실제로 발생한 문제를 막기 위해서만 룰과 승인 단계를 추가하고, 헌법 개정은 주간 미팅에서 합의한다.
- **적용 범위는 UX 4명.** UI팀에는 상태값처럼 함께 쓰는 부분만 공유한다.
- **git 숙련도에 기대지 않는다.** 브랜치, 커밋, PR은 프로그램이 처리하고, 팀원은 요청과 확인에 집중한다. git에 익숙한 1명이 저장소 관리를 돕는다.

### 이 초안에서 결정이 필요한 것

- (결정) 3조: 디스크립션에는 정책 ID와 정책 요약을 프로그램이 자동으로 표시하고, ID에 정책서 해당 위치 링크를 건다. 고객은 화면에서 요약을 읽고, 자세한 내용은 링크로 원문을 본다.
- (결정) 승인자 1인을 두지 않는다. 공통 자료 변경은 주간 팀 미팅에서 합의해 반영하고, 화면설계서는 작성자가 직접 고친다. 아래 "공통 자료 변경 흐름" 참고.
- (진행 중) 상태값: 아래 "상태값 설계안"에서 검토 중입니다.

### 공통 자료 변경 흐름 (주간 미팅 합의)

화면설계서를 뺀 공통 자료는 누가 바꾸자고 하든 바로 고치지 않고 "협의 대기 목록"에 올린 뒤, 주 1회 UX 4명이 모이는 미팅에서 합의한 것만 반영합니다. 화면설계서는 작성자가 오너이므로 작성자가 직접 고칩니다.

| 구분 | 대상 | 변경 방법 |
| --- | --- | --- |
| 공통 자료 | 정책서, Common UX, 용어집, 장비 상태 정의서, 알럿 카탈로그, 권한 매트릭스, 룰 문서(헌법 포함) | 협의 대기 목록 → 주간 미팅 합의 → 반영 |
| 화면설계서 | CID별 화면설계서 | 작성자가 직접 수정. 다른 사람이 수정을 원하면 작성자에게 요청 |

1. **발견:** 작업 중 공통 자료의 변경·추가가 필요하면, 직접 고치지 않고 Claude에게 협의 대기 목록에 올려 달라고 합니다.
2. **기록:** Claude는 저장소의 협의 대기 목록에 항목을 추가합니다. 제안 내용, 이유와 근거(고객 요청, 장비 변경 등), 영향받는 정책 ID·CID, 제안자, 날짜를 적습니다.
3. **미팅 준비:** 미팅 전에 Claude가 목록을 정리합니다. 중복 항목을 합치고, 서로 충돌하는 항목을 표시하고, 항목별 영향 화면을 붙입니다.
4. **합의:** 주간 미팅에서 항목마다 합의, 보류, 기각을 정합니다.
5. **반영:** 합의된 항목만 Claude가 공통 자료에 반영하고 결정 기록을 남깁니다. 보류는 목록에 남기고, 기각은 사유와 함께 닫습니다.
6. **화면 후속:** 반영으로 영향받는 화면은 Claude가 각 작성자에게 알리고, 작성자가 자기 화면을 고칩니다.

- **협의 대기 항목은 효력이 없다:** Claude는 합의 전 항목을 근거로 화면을 그리지 않습니다. 고객이 먼저 작업을 요청한 경우에만 해당 화면에 "미결 정책 포함" 표시를 붙여 진행합니다.
- **긴급 변경:** 팀원이 긴급 반영을 요청하면 미팅을 기다리지 않고 바로 반영합니다. 자동 검증은 그대로 거치고, 긴급 표시와 요청자·사유를 이력에 남겨 다음 주간 미팅에서 공유합니다.
- **오너 지정은 나중에:** 지금은 공통 자료에 별도 오너나 승인자를 두지 않습니다. 운영하면서 꼭 필요해지면 주간 미팅에서 논의해 추가합니다.

## 상태값 설계안 (v0.1)

지금 쓰는 UX·UI 두 축은 그대로 두고, UI의 "컨펌 대기 중"은 전사 공통 값이라 그대로 둡니다. 상태를 늘리는 대신 표시(플래그) 3개와 프로그램이 자동 계산하는 "전달" 축을 더합니다. 상태는 CID 한 장씩이 아니라 대시보드 LNB에서 눌리는 메뉴 단위(IA의 1\~2 depth)로 묶어 관리합니다. 화면 흐름을 메뉴 단위로 검토하기 때문입니다. 메뉴에 속한 CID들은 같은 상태를 공유하고, 변경 이력과 표시(플래그)는 CID별로 남깁니다.

### 상태값

| 축 | 상태 | 의미 | 바꾸는 사람 |
| --- | --- | --- | --- |
| UX | 작업 중 | 고객사에 넘기기 전 | Claude (담당 기획자가 프로그램에서 선택) |
| UX | 컨펌 중 | 고객사에 리뷰·컨펌 요청함 | Claude (담당 기획자가 프로그램에서 선택) |
| UX | 컨펌 완료 | UI 작업 시작 가능 (Date 갱신) | Claude (담당 기획자가 프로그램에서 선택) |

| 전달 | 전달 완료 | 공유일에 전달됨 (전달 버전·일자 기록) | 프로그램 자동 |

| 표시 | 붙이는 경우 | 효과 |
| --- | --- | --- |
| 변경 예정 (CR ID) | 컨펌 완료 화면에 작은 변경이 확정됨 | 상태는 유지하고 디자이너·개발사 화면에 변경 예정을 표시. 지금의 구두 전달을 대체 |

| 연동 변경 (원인 CID·정책 ID) | 다른 화면의 정책 변경으로 함께 수정됨 | 리비전 히스토리와 포스트잇에 원인을 함께 표시 |

### 운영 규칙

- **상태 변경 경로:** 담당 기획자가 프로그램에서 상태를 선택하면 Claude가 저장소와 Figma에 반영합니다. 사람이 결정하고 Claude가 실행하는 구조로 헌법 4조와 맞습니다. "컨펌 완료"는 요청하면 바로 바꿉니다. 컨펌 완료와 전달 완료로 바뀔 때마다 화면 정보의 Date를 그날 날짜로 갱신합니다.
- **UI 수동 변경 점검:** 디자이너가 Figma에서 직접 바꾸는 UI 상태(작업 중, 컨펌 대기 중)는 Claude가 매일 확인해, "컨펌 대기 중"이 된 화면과 저장소와 어긋난 값을 담당 기획자에게 알립니다.
- **일일 진행 현황 (팀 논의 중):** 매일 정해진 시간에 메뉴별 상태를 읽어 작업 중, 리뷰 중, 전달 대기 화면을 분류하고 일정을 정리합니다.
- **큰 변경과 작은 변경의 기준 (확정, 화면설계서 룰에 포함):** 흐름, 레이아웃, 상태값, 컴포넌트 구성이 바뀌면 "작업 중"으로 되돌립니다. 문구, 라벨, 디스크립션, 수치만 바뀌면 "변경 예정" 표시를 붙입니다.
- **포스트잇 유지:** 화면 옆 버전별 변경 메모는 유지하되, 프로그램이 리비전 히스토리에서 자동 생성합니다. 같은 내용을 두 번 쓰지 않습니다.
- **개발사 페이지 이동:** UI 컨펌 완료이면서 전달 대기인 메뉴만 공유일에 자동으로 옮겨지고, 이때 릴리즈 노트가 함께 만들어집니다.

### 확인 필요

- [ ] (결정) 큰 변경과 작은 변경의 기준은 제안대로 확정하고 화면설계서 룰에 포함
- [ ] (결정) UI "컨펌 대기 중"은 전사 공통 값이라 분리하지 않음
- [ ] (결정) 상태는 CID가 아니라 메뉴 단위(1\~2 depth)로 관리

### 폐기 처리

정책 변경으로 사라진 화면은 지우지 않고 "폐기" 상태로 바꿔 근거와 함께 남기되, 작업·컨펌·개발사 페이지와 Claude의 근거 자료에서는 빠지게 합니다. 지우면 왜 없어졌는지 추적이 끊기고, 그대로 두면 Claude나 팀원이 옛 정책을 근거로 쓸 수 있기 때문입니다.

- **상태값 "폐기" 추가:** UX·UI 공통 상태로, 결정 기록 또는 CR 링크가 있어야 바뀝니다. 담당 기획자가 프로그램에서 선택하면 Claude가 반영합니다.
- **저장소:** 화면설계서 파일을 보관 폴더로 옮기고, Claude가 읽는 근거 자료에서 제외합니다.
- **Figma:** 작업방에서는 폐기 보관 영역으로 옮기고, 컨펌·개발사 페이지에서는 뺍니다. 이미 개발사에 전달된 화면이면 릴리즈 노트에 폐기를 적습니다.
- **IA:** 행을 지우지 않고 폐기 표시와 폐기 버전을 남깁니다.
- **정책:** 그 화면에만 쓰이던 정책 ID는 Deprecated 처리하고, 다른 화면에도 연결된 정책은 유지합니다.

## IA 분석과 ID 체계 제안 (v0.1)

IA v1.13 기준으로 T-IOS 90개, L-IOS 120개 항목 중 54개 경로가 두 제품에 공통으로 있습니다. 하지만 같은 화면의 CID 번호가 서로 다르거나 "화면 동일" 표시가 한쪽에만 있어서, 지금 상태로는 T/L 짝을 프로그램이 자동으로 찾을 수 없습니다. 새 ID는 만들지 않고, 지금 CID를 그대로 쓰면서 T/L 짝을 IA에 명시하는 방식을 제안합니다.

### T/L 관계 분류

"화면 동일"과 "중복" 두 칸을 하나의 관계 값으로 합칩니다.

| 관계 | 의미 | 예 |
| --- | --- | --- |
| 동일 | 레이아웃과 기능이 같음 | Sample Tracking 화면 |
| 권한 차이 | 레이아웃은 같고 버튼·권한만 다름 (T는 등록·수정·삭제, L은 조회만 등) | Instruments 탭, Inventory Item details |
| 기능 추가 | 같은 메뉴에 한쪽에만 있는 버튼·화면이 붙음 | L-IOS Dashboard의 Door Control |
| 단독 | 한쪽 제품에만 있음 | T-IOS Statistical Analysis, L-IOS Material Setup |

### 제안 규칙

- **CID는 하나만 쓴다:** 문서, Figma, 고객사·개발사 소통, Claude 작업 모두 지금 CID를 그대로 씁니다. 새 ID는 만들지 않고 오타와 누락만 바로잡습니다.
- **짝 CID 연결:** IA에 "짝 CID" 칸을 두어 T/L 공통 화면의 상대 CID를 적습니다 (예: TI-STN-01-04 ↔ LI-STN-01-03).
- **공통 화면은 설계서 하나:** 짝이 있는 화면은 저장소에서 화면설계서 파일 하나에 두 CID를 함께 적고, 제품별 차이만 따로 적습니다. 파일 이름은 T-IOS CID(L-IOS 단독 화면은 L-IOS CID)로 하고, 어느 CID로 검색해도 찾을 수 있게 색인을 둡니다.
- **번호가 다른 5건:** 짝 CID로 연결해 두고, 번호 통일은 개발사 영향을 보고 따로 결정합니다.
- **공통 팝업:** Door Control처럼 여러 곳에서 열리는 팝업은 화면설계서에 "호출 위치" 목록을 둡니다.
- **신규 CID부터 접미어 규칙 적용:** 팝업 -P, 탭 -T, 권한 변형 -V/-M. 기존 CID는 유지합니다.

## L-IOS 서비스 모드 (정책 검토 참고 자료)

### 검증에 쓰는 방법

이 표를 저장소에 데이터 파일로 두면, Claude가 화면 흐름을 검토할 때 "이 모드에서 이 화면으로 갈 수 있는가"를 확인할 수 있습니다. 예를 들면 다음과 같은 점검입니다.

- Run 진행 중 소모품·시약이 부족할 때 Load Materials로 이동시키는 흐름이 있다면, Main과 TSS에는 그 메뉴가 없으므로 Console로 안내하는 알럿이 필요한지 확인
- Run의 Check waste bin/bottle 단계에서 Empty Waste Bin으로 이동한다면 같은 문제가 생김 (Console에만 있음)
- TSS 모드의 Dashboard나 Instrument 화면에 Door Control 버튼이 보이면 위반
- 공통 팝업 Door Control(LI-INS-01-P)을 여는 위치가 Console·Main 전용 화면인지 확인

### 운영 규칙 (제안)

- **외부 기준 자료로 관리:** 모드 매트릭스는 개발사가 정한 것이므로 우리가 임의로 바꾸지 않고, 바뀌면 개발사발 변경요청(CR)으로 받아 반영합니다.
- **모드와 권한은 함께 본다:** 메뉴와 버튼은 서비스 모드가 허용하고 계정 권한도 허용할 때만 노출됩니다. 모드는 개발사 기준, 권한은 우리 정책서(권한 매트릭스) 기준으로 따로 관리하고, 검증할 때는 둘을 합쳐서 봅니다.
- **화면설계서에 노출 조건 표시:** 화면설계서에는 "노출 권한" 칸(L-IOS는 "노출 모드" 칸도)을 두고, 모드나 권한에 따라 달라지는 버튼은 디스크립션에 조건을 정책 ID로 적습니다.
- **기능 이름 통일:** All, View, Status Control, Note Writing, Initialize, Stop, Door Control, Change Settings를 기능 이름의 기준 목록으로 삼아 용어집에 넣고, 권한 매트릭스도 같은 이름을 씁니다.

### Claude 작업에 반영할 점

- **예전 표현은 단정하지 않는다:** 디스크립션의 "관리자"처럼 정책 변경 전에 쓰인 표현은 Admin으로 추정하더라도 단정하지 않고, 작업할 때마다 담당자에게 확인 질문을 남깁니다 (헌법 7조).
- **최신 판단은 위치가 아니라 결정 기록으로:** 종료 옵션은 Common UX가 최신이었지만, 다른 정책은 정책서가 최신일 수도 있습니다. 출처 위치로 우선순위를 정하지 않고, 판정 결과를 결정 기록(ADR)으로 남겨 Claude가 그 기록을 근거로 삼게 합니다.

### 함께 발견한 것

- **Common UX에 다른 프로젝트 내용 혼입 (정리 예정):** 작업방의 APP,Web\_Common UX 페이지에 다른 프로젝트 정책이 섞여 있으나, 준비 작업이 끝나면 작업방을 정리하고 앞으로는 이 프로젝트 정보만 넣기로 했습니다. 지금 Common UX의 기준은 [UX-AI-TEST > DY common UX](https://www.figma.com/design/etCQFF3CTf1EA6C79d4BBf/UX-AI-TEST?node-id=355-53300) 페이지(COMM-0 \~ COMM-5)이며, 확인 결과 다른 프로젝트 내용은 없습니다.
- **기준 출처 목록:** Claude가 근거로 읽는 Figma 페이지를 목록으로 정해두고, 목록 밖 페이지는 근거로 쓰지 않습니다. 현재는 Common UX = DY common UX, 화면 = 작업방 메뉴별 페이지, 정책서 = 작업방 정책서\_2026.08.28입니다. 작업방이 정리되면 목록을 갱신합니다.
- **제거된 화면 잔존 (폐기 확정):** IA v1.03에서 제거된 Runtime Info 팝업(TI-INS-02-02-P, LI-INS-02-02-P)이 작업방에 남아 있고 권한 설명도 붙어 있습니다. 폐기로 확정했고, 처리 방법과 다른 제거 화면 점검 결과는 "상태값 설계안 > 폐기 처리"에 정리했습니다.
- **검색 범위:** 정책서, Common UX, Login, Dashboard, Event History, Run, Test Management, Instrument, Inventory, Profile·Information, Setting, Material Setup(2차) 페이지를 "권한, Admin, Service, 관리자" 등 단어로 검색했습니다. Sample Tracking, Statistical Analysis와 단어 없이 암시된 권한 조건은 포함되지 않았습니다.

## 용어 통일 검토 흐름

화면을 다시 그릴 때 같은 개념은 하나의 표준어로만 쓰도록, Claude는 쓰기 전에 용어집을 읽고, 쓰는 중에 표준어만 쓰고, 쓴 뒤에 위반을 검사합니다. 뜻이 달라질 수 있는 치환은 Claude가 혼자 바꾸지 않고 질문으로 남기며, 바꾼 내역은 결과물마다 목록으로 붙여 리뷰어가 확인합니다.

### 진행 단계별 적용

| 단계 | 용어 작업 | 산출물 |
| --- | --- | --- |
| 1. Common UX 정리 (진행 중) | Common UX에 쓰인 용어와 변형 표기를 수집 | 용어 후보 목록 (출처 CID 포함) |
| 2. 룰 초안 확정 | 용어집 형식과 이 검토 흐름 확정 | 용어집 템플릿 |
| 3. 정책서 현행화 | 시작 전에 정책서·화면 전체에서 용어 후보를 모아 표준어를 확정하고, 정책서를 표준어로만 작성 | 용어집 v1, 결정 기록 |
| 4. 화면 재설계 | 모든 디스크립션을 표준어로 작성하고, 작성 후 검사와 치환 목록 첨부 | 화면설계서 + 치환 목록 |
| 5. 운영 | 주 1회 저장소 전체 점검, 표준어 변경은 CR로 처리 | 용어 점검 리포트 |

### 용어집 한 항목의 구성

| 칸 | 예시 (User Type) |
| --- | --- |
| 표준어 (기획 문서) | User Type (화면 라벨과 일치) |
| 정의 | 계정에 부여된 Service, Admin, User 구분 |
| 값 | Service, Admin, User (첫 글자 대문자) |
| 화면 UI 라벨 | User Type |
| 쓰지 않는 표현 | 계정 유형, 사용자 유형, Account Type, 등급, 관리자(→ Admin), 유형을 뜻하는 "권한" |
| 구분해야 하는 말 | 권한: User Type이 할 수 있는 일(메뉴 접근, 버튼 사용). User Type과 다른 개념이라 그대로 씀 |
| 근거 | 결정 기록 링크 |

### Claude 검토 순서 (화면 하나를 작업할 때마다)

1. **읽기:** 작업 전에 용어집 전체와 대상 화면의 기존 디스크립션을 읽습니다.
2. **찾기:** 기존 디스크립션에서 "쓰지 않는 표현"과 용어집에 없는 도메인 용어를 찾아 표시합니다.
3. **바꾸기:** 뜻이 확실한 것만 표준어로 바꿉니다 (예: 계정 유형, Account Type → User Type).
4. **묻기:** 뜻이 문맥에 따라 달라질 수 있는 것은 바꾸지 않고 담당자에게 질문합니다 (예: "관리자"가 User Type(Admin)인지 일반적인 의미인지, "권한"이 User Type인지 허용 범위인지). 용어집에 없는 새 용어는 신규 용어 후보로 올립니다.
5. **검사:** 작성을 마친 뒤 쓰지 않는 표현이 남았는지 다시 검사합니다.
6. **보고:** 결과물에 치환 목록(원래 표현 → 표준어, 위치)과 질문 목록을 붙입니다.

### 운영 규칙

- **화면 UI 라벨 변경은 디자인 영향:** 화면에 보이는 라벨을 바꾸면 UI 작업이 생기므로 해당 CID에 "변경 예정" 표시를 붙입니다.
- **용어집 수정 권한:** 용어집 오너만 표준어를 추가·변경하고, 표준어가 바뀌면 CR로 처리해 영향 CID를 한 번에 바꿉니다.
- **다른 프로젝트 용어 제외:** Common UX 등에 섞인 다른 프로젝트 용어는 후보 수집에서 제외하고 출처를 보고합니다.
