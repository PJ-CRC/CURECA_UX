## 0. 한 줄 요약

UX 4명이 각자 Figma AI Run과 Claude로 일해도 **같은 규칙으로 같은 결과물**이 나오도록, ① UX 문서를 대표 저장소(규칙 저장소)를 그대로 보여 주는 화면으로 바꾸고, ② 위쪽 메뉴에 **일정/작업**을 새로 만들어 일정 · 진행 현황 · 작업대기 · 승인 · 논의를 한곳에서 처리하게 해 주세요.

## 1. 바뀌는 구조

### 위쪽 메뉴

```
지금:  시작 안내 · UX 문서 · Figma Workbench · 변경 이력 · 사용량 통계 · 프로토타입
변경:  시작 안내 · [일정/작업] · UX 문서 · Figma Workbench · 변경 이력 · 사용량 통계 · 프로토타입
```

### 탭

| 메뉴 | 탭 (왼쪽부터) | 화면 모양 |
| --- | --- | --- |
| 일정/작업 (새) | 일정 · 주간 진행 현황 · 화면설계서 작업대기 · 회의록 · 임시 정책 · 논의·결정 | 일정 · 주간 진행 현황 · 작업대기는 한 화면, 나머지는 왼쪽 목록 + 오른쪽 문서 |
| UX 문서 | 작업 규칙 · 정책서 · UX 가이드 · 기준 데이터 · 화면 정의서 · 변경 이력 | 왼쪽 목록 + 오른쪽 문서 |

지금 UX 문서의 "공통 규칙 · 정의서" 두 탭은 없어지고, "공통 규칙" 탭의 가이드는 **UX 가이드** 탭으로 갑니다.

### 꼭 지켜 주세요 (원칙)

1. **원본은 파일입니다.** UX 문서는 대표 저장소의 md · csv 파일을 읽어 보여 주기만 합니다. 화면용 사본을 따로 만들지 않습니다.
2. **버튼은 파일을 고치고 커밋합니다.** 승인 · 반려 · 답변 같은 버튼은 정해진 파일의 정해진 칸만 고치고 대표 저장소에 커밋합니다(4절 데이터 형식).
3. **일정의 원본은 Google 스프레드시트입니다.** 프로그램은 시트를 읽어 보여 주기만 하고, 수정은 시트에서 한 뒤 [새로고침]으로 다시 읽습니다. **회의록의 원본은 저장소(`meetings/`)**입니다(2026-11-04).
4. **모든 PC가 같은 규칙을 읽습니다.** 지금처럼 PC마다 가이드를 골라 "내 작업 기준"으로 쓰는 방식 대신, 대표 저장소 기준 브랜치 하나를 모두가 읽습니다. **Workbench Claude(백그라운드 에이전트 포함)도 작업 전에 대표 저장소의 `CLAUDE.md` → 헌법 → 규칙 문서 순서로 읽고, 그 체계 안에서만 일합니다(2026-11-04).** 프로그램 폴더의 `CLAUDE.md`는 프로그램 조작(API · 캡처 · 폰트 · 작업 대기열)만 다루고, 화면을 어떻게 설계할지는 대표 저장소 규칙을 따릅니다. 작업규칙 · 정책서 · 기준데이터 · 화면 정의서 사본은 대표 저장소와 늘 같아야 하므로 손으로 일괄 교체하지 않고 자동으로 맞춥니다(R1). Common UX는 UX가이드에서 "적용"한 가이드 문서가 원본이고, Common UX 가이드는 한 벌만 둡니다. 가이드 적용 기능은 모바일처럼 다른 가이드로 바꿔 쓸 때를 위한 범용 기능으로 두고, PC 화면은 4명 모두 같은 가이드를 적용합니다(2026-11-05).
5. **공통 규칙은 누구도 직접 바꾸지 않습니다.** 누구든 임시 정책으로 등록하고, 모두에게 보이는 [승인] · [반려] 버튼으로 함께 확인한 사람이 결정합니다. [승인]하면 반영됩니다(헌법 4조 v1.6). 따로 정한 승인 담당자는 없습니다.
6. **알림(Slack 등)은 이번 범위가 아닙니다.** 나중에 연동합니다.

## 2. 화면별 요청

각 화면은 예시 화면에서 같은 이름의 탭을 열어 보면 됩니다. 탭 위의 파란 점선 상자에 원본 · 보여 줄 것 · 요청 번호가 있습니다.

### 2-1. 일정/작업 › 일정 (R15)

- **원본:** 스프레드시트 "1.CURECA-2026_Part2" › **2-2.WBS 연동** 탭 (메뉴 값 목록은 3.메뉴 탭)
- **모양:** 시트와 같게. 왼쪽에 플랫폼 · 메뉴 · 업무 내역 · 작업 완료일 · 개발사 공유일 · UX 담당자 · UI 담당자 · UX 상태 · UI 상태를 고정하고, 오른쪽에 평일 날짜 칸. 그룹 줄(Part · 구분)로 묶음. 오늘은 빨간 선. **한 줄 = 업무 한 건 (UX · UI가 같은 줄)**
- **보기만 함 (수정 기능 없음, 2026-11-04):** 담당자 · 메뉴 · 날짜 · 상태는 스프레드시트에서 고치고 [새로고침]으로 반영
  - 상태는 시트 값 그대로 배지로 보여 줌: UX `진행 중 · 리뷰 중(예정) · 디크 검토 · 완료 · 업무 범위 제외`, UI `대기 · 진행 중 · 리뷰 중(예정) · 완료 · 작업필요X · 업무 범위 제외`
  - 날짜 칸: 작업하는 날을 초록으로 칠함 (진행 중이면 진한 초록).
- **[새로고침]:** 시트를 다시 읽어 반영. 옆에 "시트에서 읽은 시각" 표시.
- **Figma 상태 연동 (R23):** 신규 작업방의 메뉴 페이지 맨 위 **메뉴 상태 카드**(3.메뉴 탭 값마다 하나, UX · UI · 전달 상태 · 담당자 · 전달 버전)를 읽음 (2026-11-04 정함, `rules/screen-spec.md` 5절). 만들기 전까지 상태는 시트에서 직접 바꿈.
  - 작업자가 카드의 상태를 바꾸면, 시트에서 같은 메뉴 줄 중 그 칸이 완료 · 작업필요X · 업무 범위 제외가 아닌 줄의 상태가 자동으로 바뀜. 바뀐 줄에는 "Figma" 표시.

  | 메뉴 상태 카드 | UX 상태 (K) | UI 상태 (L) |
  | --- | --- | --- |
  | UX 작업 중 | 진행 중 | - |
  | UX 컨펌 중 | 리뷰 중(예정) | - |
  | UX 컨펌 완료 | 디크 검토 | 대기 |
  | UI 작업 중 | - | 진행 중 |
  | UI 컨펌 대기 중 | - | 리뷰 중(예정) |
  | UI 컨펌 완료 | - | 완료 |

  UX의 "완료"는 담당자가 디스크립션을 확인한 뒤 직접 바꿈. Figma 쪽 상태 표시 방법은 정할 것(5절).
- **거르기:** 담당자 선택, 상태 칩.
- 규칙: `rules/schedule.md`

### 2-2. 일정/작업 › 주간 진행 현황 (R17)

- **기간:** 월~금. 지난주 · 다음 주로 넘겨 보기.
- **구성 (위에서 아래)**
  1. 요약 카드 4개: 이번 주 마감 업무 · 총 / 진행 중 / 리뷰 중(예정) / 완료
  2. 이번 주 마감 업무 내역: 메뉴 · 업무 내역 · 업무 상태 · UX(담당자 · 상태) · UI(담당자 · 상태) · 작업 완료일
  3. **개발사 공유 대상:** 개발사 공유일이 이번 주인 건수와 메뉴별 건수(많은 순), 그중 아직 완료가 아닌 건수
  4. 정책 변동 사항: 신규 · 변경 건수, 임시 정책(승인 대기 등), 주요 내용 3~5줄, 영역별 신규 목록. **정책 ID · PV ID를 누르면 그 문서로 이동**
  5. 회의 내역 (2-4) + 다음 주 마감 예정 (마감할 업무 · 담당자만)
- **세는 법 (중요)**
  - 한 줄이 한 건. **이번 주 마감 = 작업 완료일(G열)이 이번 주**, 개발사 공유 대상 = 개발사 공유일(H열)이 이번 주
  - UX 상태가 "업무 범위 제외"인 줄은 세지 않음
  - 업무 상태: UX 완료이고 UI가 완료 · 작업필요X · 업무 범위 제외 · 빈 칸 → 완료 / UX 완료인데 UI가 그 밖 → **진행 중** / 그 밖 → UX 상태
  - 디크 검토와 시작 전(빈 칸)은 카드로 따로 보이지 않고 총에만 들어감
  - 회의록이 없는 주는 "미진행"
- **정책 변동 계산:** 신규 = 그 주에 기준 브랜치에 처음 들어온 `policy/*/POL-*.md`, 변경 = 그 주 전부터 있던 정책 중 변경 이력 표 날짜가 그 주인 것. 주요 내용 요약과 회의 요약은 Claude 작업으로 만듦.
- 규칙: `rules/weekly-status.md`

### 2-3. 일정/작업 › 화면설계서 작업대기 (R22)

- **원본:** 모든 `screens/{메뉴}/{CID}.md`의 `## 반영 대기 목록` 표, 메뉴 담당자는 `screens/{메뉴}/_menu.md`의 `owner`
- **구성**
  1. UX 담당자 칩: 여러 명 체크(기본 모두 선택), 칩마다 건수. owner가 비면 "담당자 미정"
  2. 요약 카드: 반영 대기 · 작업 대기 화면 · 확인 필요 · 메뉴
  3. 구분 칩: 디스크립션 · 표기 · 화면 정보 · 정책 반영 · 공통 · 화면 · 문구 · 알럿 · 그 밖
  4. 메뉴별 표(반영 대기 많은 순, 막대) → 누르면 화면 목록(많은 순) → 화면 ID를 누르면 UX 문서 화면 정의서로
- **세는 법:** 상태 칸이 "대기"로 시작하거나 "반영 중"인 줄을 셈("반영 중"은 따로 표시). 상태는 대기 · 반영 중 · 반영 완료 · 제외 · 반영 롤백, 줄 ID는 `R01`(밖에서는 `CID-R01`) (`rules/screen-spec.md` 4절). "확인 필요"는 상태나 바꿀 것에 "확인 필요"가 있는 줄. 반영 완료 · 제외 · 반영 롤백은 세지 않음.
- 참고 (2026-11-04 저장소 기준): 반영 대기 1,049 · 작업 대기 화면 182 · 확인 필요 222 · 메뉴 15
- 규칙: `rules/screen-spec.md` 4절

### 2-4. 일정/작업 › 회의록 (R16)

- **원본:** 저장소 `meetings/MT-YYYYMMDD-NN.md` (고객 회의만, 회의 하나 = 파일 하나). 2026-11-03까지의 43건은 시트에서 원문 그대로 옮김(`status: 원문`)
- 왼쪽 회의 목록(최근 순, 월별), 오른쪽 회의록 (머리말 · 안건 · 내용 · 결정 · 할 일 · 정책 후보 · 기타)
- **작성:** 참석한 사람이 프로그램 아이디별로 작성본을 써서 `meetings/drafts/{회의 ID}/{아이디}.md`에 임시 저장 → [요약/분석하기]를 누르면 Claude 작업으로 정리본(`meetings/{회의 ID}.md`)을 만들고 점검까지 함: 정책서 · 임시 정책 · 논의 항목과 맞대어 이미 있는 것은 거르고 신규 · 변경만 정책 후보로, 빠뜨린 것은 "점검 결과"에 확인 필요로
- **안건:** 논의·결정 항목의 [회의 안건으로 올리기] → `meetings/next-agenda.md` → 새 회의록의 안건으로. 회의록에서 안건에 답하는 방법은 목업으로 정한 뒤 요청
- **정책 후보:** Claude가 뽑은 후보마다 [임시 정책으로 등록] / [제외]. 누구나 누를 수 있음
- **점검 결과 처리:** "확인 필요" · "임시 정책에 있음" 줄마다 [처리하기] → 논의·결정 [답변하기]와 같은 Claude 대화 창(묻기 → 답 → 바뀌는 것 정리 → 확인하고 커밋). 누구나, 완료 전후 언제든. 처리한 줄은 "처리함 (아이디 · 날짜)"
- **상태:** 작성 중 · 완료 · 원문. [+ 새 회의록]으로 만든 `작성 중` 회의록은 [회의록 취소]로 지울 수 있음(안건은 다음 회의 안건으로 되돌림). 완료하면 답을 못 받은 안건은 안건 목록에서 빼고, 작성본은 맨 아래에 접어 두고 [내용 보기]로 펼침
- **완료:** 요약/분석한 뒤 누구나 [완료하기]
- **일시 · 참석자:** 새 회의록 참석자 기본값 씨젠 - 김의식, 노경민 / 브렉스 - 서보경, 정다예, 하승현, 이상헌. 날짜 · 시간 · 참석자는 상태와 관계없이 언제든 고침(마우스를 올리면 입력칸으로 보임, 원문 회의록은 제외). 날짜를 바꾸면 회의 ID를 새 날짜로 다시 붙이고 파일 · 작성본 폴더 이름과 이 ID를 근거로 적은 곳도 함께 고침
- 안건 답하기는 목업으로 함께 정한 뒤 요청합니다
- 규칙: `rules/meeting-notes.md`, 템플릿: `templates/meeting.md`

### 2-5. 일정/작업 › 임시 정책 (R6 · R7 · R8 · R9)

## 4. 프로그램이 읽고 쓰는 데이터 형식

칸 이름은 바꾸지 않습니다. 형식이 바뀌면 이 문서와 룰을 먼저 고칩니다.

### 정책서 머리말 (`policy/{영역}/POL-*.md`)

`id, title, summary, domain, menus, cids, status, version, date, sources, provisional, alerts, data, replaced_by` (YAML). 본문 절: 정의 · 규칙 · 예외 · 근거 · 변경 이력(표: 버전 | 날짜 | 내용 | 근거).

### 화면 정의서 (`screens/{메뉴}/{CID}.md`)

- 머리말: `cid, pair_cid, tl_relation, title, path, type, version, date, author, service_mode, user_type, policies, rules_version, provisional, flags, source, figma, figma_region`
- `provisional`에 값이 있으면 "임시 정책 포함". B안은 `PV-0003-B`처럼 적힘.
- `## 반영 대기 목록` 표: `ID | 구분 | 지금 | 바꿀 것 | 근거 | 상태`. 상태는 `대기`(괄호로 이유 가능, 예: `대기 (확인 필요)`), `반영 중`, `반영 완료 (날짜)`, `제외 (날짜, 이유)`(10일 지나면 표에서 빠지고 화면 MD 변경 이력으로 옮겨짐), `반영 롤백 (날짜, 이유)`.
- 메뉴 파일 `_menu.md` 머리말의 `owner` = 메뉴 담당자

### 임시 정책 (`provisional/PV-*.md`)

| 읽는 칸 | 쓰임 | 버튼이 쓰는 것 |
| --- | --- | --- |
| 머리말 표 "상태" 줄 | 목록 필터, 버튼 활성("승인 대기"일 때만) | "승인" / "반려" |
| "바꾸는 정책" 줄의 `POL-` ID | 같은 정책 묶음, 승인 경고, 링크 | |
| "작성자", "등록일" 줄 | 목록 | |
| 제목 끝 "(A/B 선택)" 또는 `## A안` | A/B 표시, 버튼 바꿈 | |
| "영향 화면" 표의 "영향" 열 | 영향 화면 수 | |
| "결정" 표 (`날짜 | 결정 | 결정자 | 메모`) | 결정 기록 | 끝에 한 줄 더함 |
| 위치 `provisional/` · `closed/` | 열림 · 닫힘 | 반려면 `closed/`로 이동 |

## 6. 확인 방법 (1차 테스트)

- [ ] 두 PC에서 같은 시점에 UX 문서를 열면 같은 공통 규칙 버전과 같은 내용이 보인다
- [ ] 정책서의 화면 ID, 화면 정의서의 정책 ID, 주간 진행 현황의 정책 ID를 누르면 해당 문서로 간다
- [ ] 시트에서 담당자 · 상태 · 날짜를 고친 뒤 일정 탭에서 [새로고침]을 누르면 바로 보인다 (일정 탭에는 수정 기능이 없다)
- [ ] 주간 진행 현황의 숫자가 2-2절의 세는 법과 맞는다 (UX 완료 · UI 미완료 업무가 진행 중으로 셈)
- [ ] 화면설계서 작업대기의 숫자가 저장소의 반영 대기 목록과 맞고, 담당자 칩을 끄면 그 사람 몫이 빠진다
- [ ] 모든 계정에 승인 · 반려 버튼이 보이고, 누르면 PV 파일(결정자 = 누른 사람)과 커밋이 4절 형식대로 남는다 (테스트 브랜치)
- [ ] [답변하기] → 정리 확인 → 커밋 후, 영향 화면의 반영 대기 목록에 새 줄이 "새로 추가"로 보인다
