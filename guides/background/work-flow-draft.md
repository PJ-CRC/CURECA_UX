# 화면설계 작업 흐름 (초안)

> 상태: 논의용 초안 (2026-11-09). 화면설계 7단계를 정리하고, 이 흐름을 새 토대로 규칙 문서를 다시 쓸지 함께 보려고 만든 문서입니다. 정해진 것은 아직 없습니다.

## 1. 한눈에 보기

| 단계 | 하는 일 | 남는 것 | 끝 관문 |
| --- | --- | --- | --- |
| 0. 시작 | 대표 저장소에서 가져오기, 케이스(1 · 2 · 3) 가르기, 작업 기록 만들기 | 작업 기록 | 겹치는 작업 없음 |
| 1. 요건 정의 | 케이스에 맞게 요건을 뽑음 | 요건서 | **요청자 확인** |
| 2. 근거 · 분석 | 요건에 걸린 정의 · 정책 · 사용 화면을 찾고, 정책 수정 범위를 냄. 용어 정리 | 근거표, 영향 화면 목록, 정책 수정안, 용어 목록 | **요청자 확인** (정책 수정 범위) |
| 3. 화면 설계 | 화면 MD(디스크립션 포함) → 예시 데이터 → Figma → 패널 | 화면 MD, Figma 프레임(기획 · 상태 · 케이스) | 기계 검사 |
| 4. 검토 | 다른 눈(검토 에이전트)으로 정책 · 용어 · 기준데이터 · 형식 대조 | 점검 결과, 고친 목록, 남은 질문 | **요청자 확인** (남은 질문) |
| 5. 고객 UX 리뷰 | 피드백을 나눠 간단 수정은 3단계부터, 정책 영향은 1단계부터 | 피드백 분류표 | 분류 기준 통과 |
| 6. 다국어 | 신규 단어 추출 → 7개 언어셋 → 언어별 Figma | 신규 단어 목록, 언어셋, 언어별 프레임 | 기계 검사 |
| 7. 완료 | 상태 · 버전 기록, 대표 저장소에 올림 | 상태 카드 · `_menu.md` · 일정 시트 | 질문 대기 0개 |

- 요청자 확인은 1 · 2 · 4단계 끝, 세 번만 둡니다. 나머지 관문은 스크립트로 검사합니다.
- 질문이 있어도 멈추지 않고, 근거가 가장 가까운 안으로 진행한 뒤 빨간 글씨 질문 대기로 표시합니다(지금 규칙과 같음).

## 2. 케이스별로 달라지는 곳

| 단계 | 케이스 1 화면 부분 수정(고도화) | 케이스 2 신규 | 케이스 3 기존 화면 다시 그리기 |
| --- | --- | --- | --- |
| 1 요건 | 고객 요청에서 바꿀 것을 뽑고, 신규 작업방에 그려진 화면의 화면 MD를 기준으로 삼음 | 요청 · 회의록에서 새 요건을 정의함 (요건서 틀로 인터뷰) | 기존 원본 프레임 · 케이스 프레임 · 디스크립션에서 화면 요건을 뽑음 (T · L 각각) |
| 2 근거 | 바꾸는 값 · 동작이 정의된 곳과 그것을 쓰는 다른 화면 | 비슷한 기존 화면 · 정책, 새로 필요한 정책 | 그 화면의 정책 · 기준데이터 전부 |
| 3 설계 | 바뀐 곳만 고치고 변경 표시 | 전체를 새로 그림 (새 CID) | 전체를 새로 그림 |
| 5 리뷰 | 같음 | 같음 | 같음 |

## 3. 단계별 세부

각 단계는 **읽을 것 · 할 일 · 남는 것 · 끝 관문 · 도구**로 씁니다. 도구는 스킬(단계 지시), 에이전트(다른 눈), 스크립트(기계 검사)입니다.

### 0. 시작

- 할 일: 대표 저장소에서 가져옴 → 요청을 케이스로 가름 → 작업 기록 파일을 만들고 "고칠 정책 · 화면"을 적어 다른 사람 작업과 겹치는지 봄
- 남는 것: 작업 기록 (지금 단계, 끝낸 관문, 질문 대기, 요청자 확인을 계속 적음)
- 도구: 진입 스킬, 겹침 확인 스크립트
- 지금 있는 것: 없음 (케이스 표만 `old-rules/screen-spec.md`에 있음)

### 1. 요건 정의

- 할 일: 케이스별 요건서 틀을 채움 (화면 목록 · 영역 · 요소 · 동작 · 데이터 · 바꾸는 이유)
- 남는 것: 요건서
- 끝 관문: 요청자 확인
- 도구: 요건 스킬 (케이스별 틀 3개)
- 지금 있는 것: 케이스 3 "1-1 화면 정의서" 읽는 법 (`old-rules/screen-spec.md`)
- 정할 것: 요건서 형식, 케이스 1 · 2 틀

### 2. 근거 · 분석

- 할 일: ① 문서 지도로 요건에 걸린 값 · 동작의 정의 위치, 정책, 쓰는 화면을 찾음 ② 정책 수정 · 추가안과 영향 화면 목록을 냄 ③ 영향 화면의 반영 대기 목록에 한 줄씩 남김 ④ 용어집 기준으로 단어 정리
- 남는 것: 근거표, 영향 화면 목록, 정책 수정안, 용어 목록
- 끝 관문: 요청자 확인 (정책 수정 범위)
- 도구: 근거 스킬, **문서 지도 스크립트**(정책 머리말 `cids` · `data`, 화면 MD, 기준데이터를 훑어 색인을 만듦), 용어 점검 스크립트(단어 단위)
- 지금 있는 것: 정책 찾는 여섯 길 · 기준데이터 표 (`old-rules/screen-spec.md` 케이스 3), 정책 쓰는 법 (`old-rules/policy-writing.md`), 임시 정책 (`old-rules/provisional-policy.md`)
- 정할 것: 문서 지도 모양

### 3. 화면 설계

- 할 일: ① 화면 MD(디스크립션 포함)를 템플릿대로 씀 ② 기준데이터에서 예시 데이터를 뽑음 ③ Common UX 컴포넌트로 Figma를 그림(기획 · 상태 · 케이스) ④ 패널에 화면 MD 디스크립션을 옮김
- 남는 것: 화면 MD, Figma 프레임
- 끝 관문(기계 검사): 템플릿 절이 다 있음, 목록 행 수 = 노출 개수, 상태 · 케이스 프레임 수 = 화면 MD 표, 빨간 질문 = 질문 대기 표, 번호 표시 = 디스크립션 번호
- 도구: 설계 스킬, **컴포넌트 대응표**(요소 → 컴포넌트 · Variant), 잘 된 예시(Samples 테스트)
- 지금 있는 것: 케이스 3의 3 · 4단계, 그리는 차례, 디스크립션 쓰는 법 (`old-rules/screen-spec.md` 8절)
- 정할 것: 컴포넌트 대응표, 케이스 1의 변경 표시 방법

### 4. 검토

- 할 일: 그린 Claude가 아닌 검토 에이전트 3개가 따로 봄 — ① 정책 대조 ② 용어 · 기준데이터 ③ 디스크립션 형식 · 말투 · T/L 완결. 나온 것을 고치고 남은 질문을 모음
- 남는 것: 점검 결과, 고친 목록, 남은 질문
- 끝 관문: 요청자 확인 (남은 질문)
- 도구: 검토 에이전트 3개 (점검표 고정)
- 지금 있는 것: 5단계 점검 5-1 ~ 5-5 (`old-rules/screen-spec.md`)

### 5. 고객 UX 리뷰

- 할 일: 피드백을 한 줄씩 나눔 → 정책 · 기준데이터 · 다른 화면에 영향이 없으면 "간단 수정"(3단계부터), 하나라도 있으면 "재정의"(1단계부터)
- 남는 것: 피드백 분류표
- 도구: 리뷰 스킬, 문서 지도(영향 판단)
- 지금 있는 것: 고객 논의(CA), 변경 흐름 (`old-rules/change-flow.md`)
- 정할 것: 분류 기준 확정, 고객 확답 전 임시 정책과의 관계

### 6. 다국어

- 할 일: 화면 문구 추출 → 기존 언어셋에 없는 신규 단어 → AI로 7개 언어 → 언어별 Figma
- 남는 것: 신규 단어 목록, 언어셋, 언어별 프레임
- 도구: 다국어 스킬, 문구 추출 · 비교 스크립트
- 지금 있는 것: 큰 흐름 (`old-rules/language-set.md`), 그리는 방식 안 (`language-set/multilingual-screen-options.md`, 보류)
- 정할 것: 언어셋 관리 체계, 언어별 Figma 그리는 방식

### 7. 완료

- 할 일: 상태 · 버전 기록, 대표 저장소에 올림
- 끝 관문: 질문 대기 0개, 작업 기록의 모든 관문 통과
- 지금 있는 것: `old-rules/status-lifecycle.md`, `old-rules/schedule.md`
- 정할 것: 상태 원본 하나 (`archive/background/rules-overhaul-audit.md` 1절 5번)

## 4. 모든 단계에 걸치는 것

| 무엇 | 왜 |
| --- | --- |
| 작업 기록 | 다음 사람 · 다음 대화가 이어감, 누락이 드러남. 단계마다 다시 읽고 시작 |
| 문서 지도 | 케이스 1 · 2의 근거 찾기와 5단계 영향 판단을 기계적으로 |
| 잘 된 예시 모음 | 판단이 갈리는 곳(케이스 화면 고르기, 질문 안 쓰기, 피드백 분류)을 예시로 맞춤 |
| 컴포넌트 대응표 | 같은 요소를 같은 컴포넌트로 그림 |
| 같은 요청 두 번 돌리기 시험 | 스킬을 고칠 때마다 결과가 비슷한지 확인 |

## 5. 문서를 새 토대로 다시 쓸 때 (안)

- **다시 쓰는 것:** 절차 문서(지금 `old-rules/` 14개 · `CLAUDE.md` · 템플릿). 7단계를 뼈대로 단계마다 한 문서
- **그대로 두는 것:** 내용 자료(정책서 `policy/`, 기준데이터 `glossary/`, 화면 정의서 `screens/`, IA, 언어셋, 회의록). 이것은 절차가 아니라 일의 재료
- **헌법:** 그대로 두고 필요한 곳만 고침
- **잃지 않게:** 지금 규칙의 문장마다 "새 문서 어디로 / 뺌(이유)"를 표로 대조함. `archive/background/rules-overhaul-audit.md`(2026-11-05 감사)를 출발점으로 씀
- **바꾸는 동안:** 새 문서가 다 될 때까지 지금 규칙으로 일하고, 다 되면 한 번에 바꿈

새 구조 예:

```
CLAUDE.md          진입점: 케이스 가르기 → 단계 문서
constitution.md    헌법
flow/              단계마다 한 문서 (0-start ~ 7-done) + 케이스별 차이
reference-rules/   단계에서 함께 쓰는 쓰는 법 (디스크립션, 정책 쓰는 법, ID, 용어 표기)
examples/          잘 된 예시 (Samples 테스트 등)
.claude/skills/    단계 스킬
.claude/agents/    검토 에이전트
tools/             문서 지도 · 용어 점검 · 관문 검사 스크립트
```
