# 흐름 토대: 종합 분석과 토대 안

> 작업 자료 (2026-11-14). 2026-11-13 ~ 14 대화에서 나온 이슈 · 결정 · 분석을 한 곳에 모았습니다. 정해진 규칙이 아니며 화면설계 작업의 근거로 쓰지 않습니다. 1부를 읽고 3부의 순서대로 하나씩 구조화합니다. 확정된 것은 `flow/` 문서로 옮깁니다.

# 기조 (2026-11-14 사용자)

토대를 잡을 때마다 이 기조에 비춰 봅니다. 2부의 토대 안은 이 기조보다 먼저 쓴 것이라, 이 기조로 다시 잡습니다.

1. **요청으로 시작하고, 그 안에서는 자유롭게 한다.** 작업 안에서 요건을 더하고, 빼고, 정책을 보고, 완료시킬 수 있어야 합니다. 모든 일을 하나의 흐름에 맞추는 것은 불가능합니다.
2. **열어 줄 것은 열어 주고, 분명히 할 수 있는 것은 분명히 한다.** 방향은 넓게 잡되, 확실히 잡을 수 있는 것은 확실히 잡습니다.
3. **모든 것을 통제할 수 없다.** 통제할 수 있는 것을 찾아 그것만 깔끔하게 합니다. 통제할 수 없는 경우는 막지 않고 진행하게 합니다.
4. **증거를 남긴다.** 왜 그렇게 했는지, 왜 그런 결정이 났는지, 왜 하지 않았는지를 남겨 다음에 참고할 자원으로 쌓습니다. 이것으로 모호한 정책을 점점 정교하게 다듬습니다.
5. **모듈은 스킬로 만든다.** 요청자가 필요한 것을 골라 작업에 더하거나 뺄 수 있게 합니다.
6. **이슈는 들고 다닌다.** 4부의 이슈를 토대를 잡을 때마다 확인하고, 걸리는 것과 바뀐 기조를 4부 끝의 "이슈 진행 기록"에 적으며 하나씩 없앱니다.
7. **묻는 것을 줄인다.** 먼저 그리고 난 뒤 하나씩 해결합니다. 선택 사항은 최대한 줄이고, 꼭 물어야 하는 것만 묻습니다.
8. **이 흐름은 화면설계만 다룬다.** 작업 기록에 기반해 소프트웨어의 화면 · 정책을 다루는 일(UX/UI 작업)로 한정합니다. 흐름은 "완료"에서 끝납니다. 개발사 공유 · 산출물 작성 · 주간 업무 보고 작성은 화면설계와 정책서를 건드리지 않는 다른 업무로, 따로 흐름을 만들거나 그때 요청합니다. 다른 업무의 정의는 화면설계 흐름을 완성한 뒤에 합니다.

# 1부. 종합 분석

**가고자 하는 곳:** 다양한 일을 틀에 가두지 않고, 짧은 토대 위에서 필요한 것만 켜서 진행한다. 그러면서도 장비 정책에 맞는지는 놓치지 않는다.

## 나. 우리가 하는 일의 실제 모양

**일의 순서 (사용자 정리)**

1. 고객 요청을 받음
2. UX팀이 분석해 요건을 정의하고 고객과 1차 확인
3. 화면설계
4. 고객과 UX 리뷰 → 수정 → UX 확정

**이 일의 성격 (사용자 정리)**

- 장비를 다루는 소프트웨어라 정책 영향도가 높음. 장비 스펙에 맞춘 검토가 중요함

- 요청이 4단계에서 고객 의견으로 보완 · 제거되는 일이 흔함
- 4단계는 고객 미팅 날짜에 맞춰 며칠씩 쉬었다가 이어 감

## 마. 이야기해서 방향이 잡혔지만 아직 문서에 넣지 않은 것

2부(토대 안)에 자세히 있습니다.

1. 요청자는 아무것도 고르지 않고 요건을 던짐. 길은 1단계 끝에서 정함
2. 단계는 0 시작 · 1 요건 정의 · 2 근거 · 분석 · 3 그리기 · 4 수정 · 확인 · 5 마무리. 다국어 단계와 UI 단계는 따로 두지 않음
3. 스위치 다섯 개(정책 대조 · 다른 화면 · 새 화면 · 다국어 · 고객 컨펌)를 요건마다 정함
4. 판단하지 않고 정책 대조를 켜는 "늘 켜는 것" 목록
5. 작업의 단위는 메뉴 하나 또는 원인 하나
6. 요건 목록은 작업 내내 고쳐 감. 도중에 들어온 요건 · 4단계에서 바뀐 요건도 같은 목록에 달림
7. 케이스 1 · 2 · 3은 화면마다 붙는 "그리는 방법"으로 남음 (0단계에서 고르지 않음)
8. 4단계 안에 이정표 둘(UX 확정 · UI 확정). 쉬었다 이어 가는 것이 정상인 단계
9. 5단계 마무리는 UX · UI가 모두 끝나 개발사에 공유하는 때
10. 끝난 방식 넷(반영 / 바뀌어 반영 / 반영 안 함 / 정책만 반영)

**흐르는 방식**

- 고객 요청 → 검토 → 화면 반영 → 컨펌
- 고객 요청 → 검토 → 정책만 바뀌고 화면에는 반영되지 않음
- 내부에서 시작해 내부에서 마무리 (8 · 9번)

**끝나는 방식**

- 요청대로 끝남
- 이슈가 생겨 요청이 바뀐 채로 끝남
- 이슈가 풀리지 않아 기존 화면을 그대로 두고 끝남 (바뀐 것 없음)
- 미리 구두로 확정받고, 화면에 반영만 하고 끝남 (작은 요소만 바뀔 때)

## 2. 범위

이 흐름은 **화면설계(UX/UI 작업)** 만 다룹니다. 작업 기록에 기반해 소프트웨어의 화면과 정책을 다루는 일입니다.

| 업무 | 이 흐름에서 |
| --- | --- |
| 화면설계 (UX/UI 작업) | 다룸 |
| 개발사 공유 | 다루지 않음. 완료된 작업을 묶어 나가는 다른 업무 |
| 산출물 작성 | 다루지 않음 |
| 주간 업무 보고 작성 | 다루지 않음 |

- 흐름은 "완료"에서 끝납니다. 개발사 공유는 완료 뒤의 일입니다.
- 다른 업무는 화면설계 흐름을 완성한 뒤 하나씩 만듭니다. 지금은 정의하지 않습니다.

## 3. 흐름 (1 ~ 5단계)

```
1 시작 · 요건 정의 → 2 근거 · 분석 → 3 화면 설계 → 4 수정 · 확인 → 5 완료
                                                (UX 확정 · UI 확정)
```

0단계는 1단계에 합쳤습니다(2026-11-14 서보경). 아래 표의 0 · 1 행은 합치기 전 모양이며, 합친 단계의 할 일은 `flow/1-requirements.md`에 씁니다.

| 단계 | 하는 일 | 끝나면 남는 것 | 사람이 멈춰서 답하는 곳 |
| --- | --- | --- | --- |
| 0 시작 | 작업 기록을 엽니다 (요청자, 메뉴, 그릴 곳, 작업 기준) | 열린 작업 기록 | 신규 메뉴의 이름 · CID 체계를 받을 때만 |
| 1 요건 정의 | 요청을 요건 목록으로 정리하고 대상 화면을 정합니다. 요건마다 갈래를 가릅니다 | 요건 목록 (갈래의 답 포함) | 한 번 (요건 목록 확인) ※ 정할 것 |
| 2 근거 · 분석 | 정책을 봐야 하는 요건만 정책 · 기준데이터와 대조합니다. 여러 메뉴에 걸친 일이면 걸린 화면을 찾습니다 | 읽은 근거, 정책과 다른 곳 | 정책을 바꿔야 할 때만 |
| 3 화면 설계 | 화면 MD → Figma. 모르는 것은 빨간 `※ 질문 대기`로 남기고 그립니다 | 초안 | 없음 |
| 4 수정 · 확인 | 검토 의견과 질문 대기를 하나씩 풉니다. 더 들어온 요건 · 바뀐 요건 · 빠진 요건을 요건 목록에 달고 고칩니다 | 확정된 화면, UX 확정 · UI 확정 날짜 | 검토 |
| 5 완료 | 무엇을 했고 무엇을 하지 않았는지 남기고, 확정된 것을 넣고, 작업을 닫습니다 | 닫힌 작업 기록 | 완료 확인 (새 CID 확정 포함) |

**단계를 지나는 규칙**

1. **0 → 3단계는 한 번씩 앞으로 갑니다.** 되돌아가지 않습니다.
2. **4단계는 머무는 단계입니다.** 초안이 나온 뒤부터 완료 전까지 수정을 되풀이하고, 며칠씩 쉬었다가 이어 갑니다(고객 미팅, UI팀 작업을 기다림). 작업 기록의 `이어서 작업할 곳:` 줄에서 이어 갑니다.
3. **4단계에서 요건이 더 들어와도 앞 단계로 돌아가지 않습니다.** 요건 목록에 달고, 그 요건에 필요한 일(갈래 가르기, 정책 보기, 그리기)만 4단계 안에서 합니다. 1 ~ 3단계에서 하는 일을 스킬로 만들어 두는 까닭이 이것입니다.
4. **할 일이 없는 단계는 "해당 없음 (이유)"으로 지나갑니다.** 정책을 볼 요건이 없으면 2단계를, 화면이 바뀌지 않으면(정책만 바뀜) 3 · 4단계를 지나갑니다.
5. **UX 확정 · UI 확정은 단계가 아니라 4단계 안의 날짜입니다.** 요청자가 알리면 작업 기록에 적습니다. UI 리뷰에서 나온 UX 수정도 4단계의 수정입니다.
6. 다국어 단계, UI 단계, 개발사 공유 단계는 두지 않습니다.

※ 정할 것: 1단계 끝에서 요건 목록을 확인받고 멈출지, 알리고 바로 2단계로 갈지. 안: 한 번 확인받음. 요건이 틀리면 그린 것을 모두 다시 하게 되기 때문. 미리 구두로 확정받은 일은 알리고 넘어감.

**실제 일의 순서와 단계**

| 실제 일 | 단계 |
| --- | --- |
| 1. 고객 요청을 받음 | 0 |
| 2. UX팀이 분석해 요건을 정의하고 고객과 1차 확인 | 1 · 2 |
| 3. 화면설계 | 3 |
| 4. 고객과 UX 리뷰 → 수정 → UX 확정 | 4. **UX 확정** 날짜를 적음 |
| 5 · 6. UI팀이 디자인하고 완료를 알림 | 4. 작업이 쉼 |
| 7. 디자인 리뷰 → UI 재수정 → UI 확정 | 4. **UI 확정** 날짜를 적음 |
| (끝) | 5 |
| 8. 개발사에 공유 | 이 흐름 밖 |

**지금 `flow/` 문서와 다른 곳:** 지금 문서는 0 ~ 6단계(5 다국어, 6 완료)입니다. 토대에서는 다국어 단계가 빠져 완료가 5단계가 됩니다.

## 6. 스위치와 스킬 (다음에 정함)

갈래를 확정한 뒤, 갈래마다 아래 둘 중 무엇으로 둘지 정합니다.

| 종류 | 뜻 | 누가 정하나 |
| --- | --- | --- |
| 스위치 | 요건을 보면 답이 나오는 것. 켜지면 따라오는 일이 정해져 있음 | Claude가 가르고 알림. 요청자는 원할 때 바꿈 |
| 스킬 | 하는 일의 묶음. 작업에 더하거나 뺄 수 있음 | Claude가 골라 알림. 요청자가 더하거나 뺌 |

스킬 후보: 정책 보기, 걸린 화면 찾기, 새 화면 구상, 화면 그리기(DY 3단계), 문구 맞추기, 점검.

**묻는 것 (안)**

묻는 것은 줄이고 아래만 묻습니다. 나머지는 Claude가 판단해 알리고 진행합니다.

1. 신규 메뉴의 이름 · CID 체계 (시작)
2. 요건이 서로, 또는 정책과 부딪칠 때
3. 장비에 닿는 것(상태값, Alert · Confirm · Toast, 장비 동작, 수량 · 단위, User Type · Client Mode)을 근거 없이 정해야 할 때
4. 완료 (새 CID 확정 포함)

## 7. 요건 목록

작업 내내 고쳐 가는 표입니다. 덮어쓰지 않고 상태에 "추가 · 변경 · 제거 (날짜, 누가, 왜)"를 남깁니다.

```markdown

| --- | --- | --- | --- | --- |
| 1 | 목록에 LIS Transmission 항목 추가 | TI-TMG-01 | 1 | 최초 |
| 2 | Resend 버튼으로 실패 항목 재전송 | TI-TMG-01 | 1 | 최초 |
| 2 | Resend 버튼으로 실패 항목 재전송 | LI-TMG-01 | 1 | 최초 |
```

갈래의 답을 이 표에 칸으로 둘지는 6절을 정할 때 함께 정합니다.
