# UX 문서 메뉴 구조 제안 (Figma AI Run)

> 상태: 초안 v0.5 (2026-11-03). v0.2에서 규칙 담당자 1명 반영, 임시 정책 작업, 화면의 공통 규칙 버전 기록을 반영 (헌법 4조 v1.3). v0.3에서 임시 정책 메뉴(목록·문서·승인·반려 버튼)와 다른 화면 영향 검토를 더함. 팀 프로그램 "Figma AI Run"의 UX 문서 메뉴에 이 저장소(CURECA UX 규칙)를 올리기 위한 구조 제안. 프로그램 담당 팀원에게 전달해 구조 변경을 요청하는 용도. v0.4에서 회의 중심 절차를 빼고 승인 담당자의 승인·반려로 줄이고, 알림은 추후 연동으로 둠 (헌법 4조 v1.4). v0.5에서 겹치는 임시 정책을 A/B 선택 문서로 합치는 방식을 더함. 같은 날 탭 구성 예시 화면, 프로그램이 읽는 칸, 프로그램 담당자 요청 목록(8절)을 더함. 2026-11-04: 새 메뉴 일정/작업(일정 · 주간 진행 현황 · 화면설계서 작업대기 · 회의록 · 임시 정책 · 논의·결정), 요청 R15~R18.

## 1. 목표

- 팀원 누구나 같은 규칙을 보고, 같은 규칙으로 Claude가 일해서 같은 결과물이 나오게 함
- 규칙·정책·기준 데이터·화면 정의·논의 상태를 한곳에서 찾고, 서로 이어서 볼 수 있게 함
- 고칠 때는 화면에서 요청하고, 원본 파일이 고쳐지고, 검토를 거쳐 대표 git에 남게 함

## 2. 원칙

1. **원본은 규칙 저장소의 파일.** md·csv와 머리말(front matter)이 원본이고, UX 문서는 그 파일을 읽어 보여 주는 화면임. 화면에서 따로 만든 사본(guide.md 변환본)은 두지 않음.
2. **ID로 이어짐.** 정책 ID(POL-…), 화면 CID(LI-/TI-…), 알럿 ID(Alert_, Confirm_, MS_Alert_, MS_Confirm_), 논의 ID(CA-, PD-, PV-)는 어디에 나오든 눌러서 그 문서로 감. 반대로 문서마다 "이 문서를 참조하는 곳"을 보여 줌.
3. **상태가 보임.** 확정, 임시 정책, 논의 대기, 확인 필요가 배지로 보이고, 미결 항목만 모아 볼 수 있음.
4. **Claude 작업 기준 = 대표 저장소의 규칙 전체.** 가이드 하나를 고르는 방식 대신, 각 PC가 받아 둔 대표 저장소 기준 브랜치의 `CLAUDE.md`(진입점)를 따르게 함. 화면을 그릴 때 정책·용어집·상태값·알럿을 함께 읽는 순서가 이미 그 안에 있음 (2-1).

## 2-1. 4명이 함께 쓰는 구조 (2026-11-03 사용자 설명 반영)

- 작업자 4명이 각자 Figma AI Run을 쓰고, 각자 Claude 계정과 각자 git 작업 공간을 가짐. 작업 결과는 각자 git에서 대표 저장소로 올림.
- UX 문서는 모든 Claude가 일하기 전에 보는 **공통 규칙 공간**임. 누가 어느 PC에서 돌려도 같은 규칙으로 일해야 같은 결과물이 나옴.

| 구분 | 어디에 | 누가 바꿈 | 각 PC의 Claude가 쓰는 것 |
| --- | --- | --- | --- |
| 공통 규칙 (작업 규칙, 정책서, 기준 데이터) = UX 문서 | 대표 저장소의 기준 브랜치 | 승인 담당자 1명만. 승인한 것만 | 항상 기준 브랜치의 최신본 (UX 문서에 보이는 것과 같음) |
| 임시 정책 (기존 정책을 바꿔야 할 때) | 대표 저장소 `provisional/` (PV 파일만 올림) | 등록한 작업자 | 그 PV를 적용한 작업에서만. 다른 사람의 Claude에는 영향 없음 |
| 화면 정의서·화면 작업 | 각자 git 작업 공간 → 대표 저장소 | 메뉴 담당 작성자 | 공통 규칙 + 그 화면에 적은 임시 정책 |
| Figma 화면 | 작업방 Figma | 본인 (Workbench 요청) | 공통 규칙으로 그림 |

1. **규칙은 대표 저장소 하나에서만 읽음.** 각 PC의 프로그램이 대표 저장소 기준 브랜치를 자동으로 받아(지금 history 브랜치처럼) UX 문서에 보여 주고, Claude도 그 받은 본을 읽음. 각자 작업 브랜치에 있는 고치는 중인 규칙은 공통 규칙으로 쓰지 않음.
2. **Claude는 작업을 시작할 때 규칙 최신본을 확인함.** 받은 공통 규칙 버전(예: rules-v0.3)을 확인하고, 그 버전으로 작업함.
3. **규칙을 바꾸는 길은 하나.** 팀원은 공통 규칙을 직접 고치지 않음. 기존 정책을 바꿔야 하면 임시 정책(PV)으로 등록하고 그 기준으로 작업함 → 승인 담당자가 작성자와 의견을 나눠 승인 또는 반려 → 승인 담당자가 UX 문서(공통 규칙)를 고치고 공통 규칙 버전을 올림 → 모든 PC가 자동으로 받음 → 그 임시 정책을 썼던 화면은 작성자가 새 버전에 맞춤. UX 문서에는 임시 정책이 "승인 대기"으로 보이고, 어느 정책을 바꾸려는 것인지 그 정책 화면에 표시됨.
4. **화면에 공통 규칙 버전을 남김.** 화면 정의서 머리말에 `rules_version`(따른 공통 규칙 버전)과 `provisional`(적용한 임시 정책)을 적음. 버전이 올라가면 이전 버전으로 그린 화면 중 바뀐 정책을 쓰는 화면을 UX 문서에서 모아 보여 줌. UX 문서와 Workbench에서 화면마다 버전과 "임시 정책 포함"이 보임.
5. **결정은 저장소에 남김.** 각자 Claude의 개인 메모리에만 있는 규칙은 다른 사람의 Claude가 모름. 작업 방식과 결정은 반드시 저장소(규칙·정책 문서)에 적음.
6. **같은 파일을 동시에 고치지 않게.** 화면 정의서는 메뉴 담당자(`screens/{메뉴}/_menu.md`의 owner)가 고치고, 공통 규칙·정책은 승인 담당자만 고침. 같은 규칙을 다르게 바꾸는 임시 정책이 생기면 Claude가 A/B 선택 문서로 합치고 승인 담당자가 고름.

## 3-1. 임시 정책 메뉴 (승인·반려)

승인 담당자가 임시 정책을 하나씩 열어 보고 바로 승인하거나 반려하는 화면. 원본은 `provisional/PV-*.md` 파일이고, 버튼은 그 파일을 고쳐 대표 저장소에 커밋함(`rules/provisional-policy.md` 5절).

```
┌───────────────────────────┬──────────────────────────────────────────────┐
│ 임시 정책  [승인 대기 ▼]  │ PV-0003 제목                 [승인]  [반려]  │
│ ───────────────────────── │ ──────────────────────────────────────────── │
│ ▶ PV-0003  승인 대기  김OO│ 상태 · 바꾸는 정책(링크) · 작성자 · 고객 확인 │
│   영향 화면 3             │ 바꾸는 내용                                   │
│   PV-0002  승인 대기 서보경│ 이유와 근거                                   │
│   PV-0001  승인 대기 서보경│ 적용한 화면 (CID 칩)                          │
│   ...                     │ 영향 화면 (표)                                │
│                           │ 결정                                          │
└───────────────────────────┴──────────────────────────────────────────────┘
```

| 영역 | 보여 줄 것 |
| --- | --- |
| 왼쪽 목록 | PV ID, 제목, 상태, 작성자, 등록일, 영향 화면 수. A/B 선택 문서는 "A/B" 표시. "바꾸는 정책"이 같은 항목은 같은 색 표시로 묶어 보여 줌. 상태 필터(기본 "승인 대기"). 닫힌 항목(`provisional/closed/`)은 필터로 따로 봄 |
| 오른쪽 문서 | 목록에서 고른 PV 파일 전체. 바꾸는 정책은 정책서 항목 링크, CID는 화면 정의서 칩, 영향 화면 표는 영향을 색 배지로. A/B 선택 문서는 A안·B안을 나란히 놓고 "두 안의 차이"를 위에. "같은 정책을 바꾸는 임시 정책"은 링크로 |
| 위쪽 버튼 | [승인] [반려]. 승인 담당자 계정에만 보이고, 상태가 "승인 대기"일 때만 누를 수 있음. A/B 선택 문서는 [A안 승인] [B안 승인] [반려] |

| 버튼 | 받는 것 | 파일에 남는 것 | 그다음 |
| --- | --- | --- | --- |
| [승인] | 메모(선택) | 상태 "승인", 결정 한 줄(오늘 날짜, 승인, 결정자 = 로그인한 승인 담당자, 메모) | 승인 담당자가 공통 규칙에 반영하고 버전을 올리면 `closed/`로 옮김 |
| [반려] | 사유(필수) | 상태 "반려", 결정 한 줄(오늘 날짜, 반려, 결정자, 사유) | `closed/`로 옮김. 적용한 화면은 작성자가 기존 정책으로 되돌림 |

- 커밋 메시지: `PV-0003 승인` / `PV-0003 반려: 사유`. A/B는 `PV-0003 B안 승인`.
- [승인]을 누를 때 "바꾸는 정책"이 같은 다른 "승인 대기" 임시 정책이 있으면 먼저 알려 줌. 동시에 등록돼 Claude가 합치지 못한 경우를 막기 위해서임.
- 작성자 계정에서는 버튼 없이 보기만 됨. 목록 위에 [새 임시 정책]을 두어 여기서도 등록할 수 있음.
- 메신저(Slack 등) 알림은 추후 연동. 그 전까지 작성자는 이 메뉴에서 확인함.

프로그램이 PV 파일에서 읽고 쓰는 칸 (이 칸 이름은 바꾸지 않음):

## 5. 고치는 흐름

1. **등록 (작성자):** 작업 중 기존 정책을 바꿔야 하면 [임시 정책 등록]을 누르고 바꿀 내용을 적음. Claude가 `provisional/PV-*.md`를 만들고, 화면 머리말 `provisional`에 PV ID를 넣고 그 기준으로 작업함. 적용한 화면만 고치고, 영향받는 다른 화면은 PV 파일 "영향 화면"에 적음. 등록할 때 Claude가 "승인 대기" 임시 정책을 확인해, 같은 규칙을 다르게 바꾸는 것이 있으면 A/B 선택 문서로 합치고, 같은 정책의 다른 규칙이면 서로 연결함.
2. **승인·반려 (승인 담당자):** 작성자와 의견을 나눠 임시 정책 메뉴에서 [승인] 또는 [반려]. 회의를 기다리지 않아도 됨.
3. **반영 (승인 담당자):** 승인된 것을 Claude가 공통 규칙 원본 파일에 고친 초안을 만들고, 승인 담당자가 확인한 뒤 기준 브랜치에 합치고 버전 태그를 붙임. 모든 PC가 자동으로 받음. 영향 화면 작성자는 새 버전에 맞춰 화면을 고침.
4. 고객 논의(CA)와 논의만 필요한 항목(PD)은 논의·결정 보드에서 봄.

## 7. 정할 것

1. 대표 git 위치: 규칙 저장소를 `PJ-CRC/CURECA_UX` 안의 별도 브랜치·폴더로 둘지, 별도 저장소로 둘지
1-1. 각자 git 작업 공간: 대표 저장소의 fork로 할지, 대표 저장소 안의 사람별 브랜치로 할지. 대표 저장소에 올리는 방법(Pull Request 또는 직접 push)
1-2. 공통 규칙 버전 이름: 반영할 때마다 태그(예: rules-v0.3)를 붙이는 것으로 초안을 씀(`rules/change-flow.md` 2절). 번호 올리는 규칙과 1차 테스트 시작 버전
2. 승인 담당자: 누구로 정할지, 없을 때 대신 승인할 사람, 프로그램에서 승인 담당자 계정을 어떻게 정할지
3. 오타처럼 뜻이 바뀌지 않는 수정도 임시 정책을 거칠지, 승인 담당자가 바로 고칠지
4. 1차 테스트에 화면 정의서(약 190개)까지 넣을지
5. 기존 "공통 규칙"(만든 UX 가이드)과 "정의서" 탭을 어떻게 옮길지 (UX 가이드는 별도 탭으로 정함, 2026-11-04). Common UX 최종본(V2.2.00)과 프로그램의 "CURECA UX 가이드"(Common UX 2.0 기준) 중 무엇을 기준 가이드로 올릴지
