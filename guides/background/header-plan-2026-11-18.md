### 1-2. Event History asis 6개를 git에 남아 있는 기록으로 되살리기

방법은 "git에서 되살리기"로 정했습니다. 함께 `screens/README.md`의 Event History 줄을 6개로 고칩니다.

**왜**

지금 `screens/asis/event-history/`의 6개는 asis가 아니라 **테스트로 그린 To-Be**입니다.

| 날짜 | 일어난 일 |
| --- | --- |
| 2026-11-02 | 기존 작업방 화면 6개를 `source: asis`로 옮김(`ed468ff`) |
| 2026-11-06 | 케이스 1 테스트에서 **같은 파일에 To-Be로 덮어씀**(`dedeae0`). asis · tobe 폴더를 나누기 전이었음 |
| 2026-11-17 | 폴더를 나누면서 이 파일을 그대로 `screens/asis/`로 옮기고(`7ef627d`) `source`만 asis로 바꿈(`bed8926`) |

**폴더와 `source`만 asis이고 내용은 테스트 To-Be라서, asis 폴더로 옮긴 것으로는 해결되지 않습니다.** 지금 남아 있는 문제는 아래와 같습니다(2026-11-18 확인).

- **링크가 다른 곳을 가리킵니다.** 6개 모두 머리말 `figma`가 기존 작업방의 기획 프레임이 아니라 테스트 작업방(UX-AI-TEST Page 10)의 섹션입니다.
- **반영 대기 목록이 실제와 다릅니다.**
  - 테스트에서 그린 것을 반영된 것으로 처리해서, 6개 파일에서 20개 항목이 `반영 완료 (2026-11-06)`로 되어 있습니다.
  - 기존 작업방 화면은 바뀌지 않았으므로, 실제로는 해결되지 않은 `대기`입니다.
- **화면 정보가 비어 있습니다.** 6개 모두 `version`이 "확인 필요 (질문 대기 Q1)"이고, `date`는 빈 값, `figma_region`은 없습니다. 기존 화면의 Ver(2.1.01)과 Date가 사라졌습니다.
- **본문이 기존 화면 원문이 아닙니다.** asis 틀(기존 화면 · 화면 글자 · 디스크립션 원문)이 아니라, 테스트에서 다시 쓴 디스크립션입니다.
- **케이스 3에서 틀린 근거로 이어집니다.**
  - 1단계에서 케이스 3 화면을 다시 옮길 때는 본문만 바꾸고, 머리말 · 반영 대기 목록 · 변경 이력은 그대로 두고 읽습니다.
  - 그래서 지금 파일을 근거로 쓰면, 틀린 링크와 해결된 것처럼 보이는 반영 대기 항목이 tobe까지 그대로 이어집니다.
- **README 줄이 12개처럼 읽힙니다.** `screens/README.md`의 Event History 줄은 "기획 화면 6개 옮김"과 "예전 틀로 쓴 To-Be 6개도 둠"을 따로 적었습니다. 실제 파일은 6개입니다.

**그래서 기존 asis를 되살리는 것이 낫다고 판단했습니다.**

- 위 문제들은 지금 파일을 하나씩 고쳐 맞추는 것보다, 덮어쓰기 전의 asis를 되살리는 편이 낫습니다. 그러면 링크 · 반영 대기 목록 상태 · 화면 정보 · 본문 원문이 한 번에 원래대로 돌아옵니다.
- 원래 asis는 git(`dedeae0`의 바로 앞 판)에 6개 모두 그대로 있습니다.
- 되살린 뒤에는 2026-11-06 이후의 연동 변경을 다시 적용해야 합니다. 머리말 키 `service_mode → client_mode`(DS-0001), 경로 `glossary/review-v0.md → archive/glossary/review-v0.md`입니다.

- 지금의 테스트 To-Be는 git(`dedeae0`)과 테스트 작업방에 남으므로 지워도 됩니다.

## 2. 알려 드릴 것 (서보경 매니저님)

### 2-1. tobe 머리말에 `figma_region` · 기존 프레임 링크를 두지 않음 (DY 정함)

**왜**

- 어느 기존 화면에서 옮겼는지는 asis 머리말의 Figma 프레임 링크로 알 수 있습니다.
- 3단계 3-2는 tobe 화면 MD의 변경 이력에 "작업방에 새로 그림 (기존 작업방 링크 · Ver)"을 남깁니다. 머리말에 또 두면 같은 링크가 두 곳에 적힙니다.
- To-Be 틀(`templates/screen.md`)에도 이 키가 없으므로 고칠 것은 없습니다.

### 2-2. 1단계 "`figma_region`의 기준일을 다시 옮긴 날로 고친다" 규칙을 빼도 되는지 확인

옮긴 때의 버전은 따로 남기지 않기로 했습니다(DY 정함).

- **규칙이 있는 곳:** `flow/1-requirements.md` 절차 3번 "케이스 3에서 더 하는 것"
- **규칙의 뜻:**
  - 1단계에서 케이스 3을 시작할 때 기존 작업방 화면을 다시 옮깁니다(본문만 바꿈).
  - 이때 머리말 `figma_region` 값 안의 날짜를 "다시 옮긴 날"로 바꾸라는 규칙입니다. `figma_region`은 asis 화면 MD에만 있는 키로, 기존 작업방의 어느 영역(2.1 1차 / 2.1 2차)에서 옮겼는지를 적습니다.
  - 디스크립션 위 화면 정보의 Date(기존 화면을 작성한 날)와는 다른 값입니다. 그 Date는 머리말 `date`에 따로 적습니다.
- **들어온 때:** 2026-11-16, 서보경 매니저님 자료를 반영할 때(`eb78ba6`)
- **실제 값과 맞지 않는 점:**
  - 틀(`templates/screen-asis.md`)의 주석은 `2.1 1차 | 2.1 2차`로, 날짜 자리가 없습니다.
  - 실제 asis 값 132개(2.1 1차 15개, 2.1 2차 117개)에는 날짜가 없어서, 고칠 기준일이 없습니다.
  - 날짜가 있는 것은 Material Setup 49개(`SH2-MS 얼럿 수정 테스트 (2026-11-03 기준)`)뿐이고, 이 날짜는 옮긴 날과 같습니다.
  - 값의 모양을 정한 문서도 없습니다.
- **검토한 걱정:**
  - 이 날짜는 "언제 기준으로 옮겼는지"를 남기기 위한 것입니다.
  - tobe 머리말에 `figma_region` 대신 기존 프레임 링크를 두는 방법을 얘기할 때도 같은 점이 나왔습니다.
  - Figma 링크는 누를 때마다 그 프레임의 "지금 모습"을 보여 줍니다. 그래서 옮긴 뒤에 누군가 기존 작업방 화면을 고치면, 링크를 열어도 옮길 때 어떤 모습(어느 Ver)이었는지 알 수 없습니다.
- **빼도 되는 이유:**
  1. 기존 작업방은 케이스 3으로 모두 옮긴 뒤 더 고치지 않고 그대로 둘 예정입니다. 그래서 링크로 여는 모습이 곧 옮길 때의 모습이고, 옮긴 날과 Ver을 따로 남겨 "언제 기준인지"를 가릴 필요가 없습니다.
  2. 어느 기존 화면에서 옮겼는지는 asis 머리말의 Figma 프레임 링크로 알 수 있습니다.
  3. 같은 이유로 tobe 머리말에도 `figma_region`과 기존 프레임 링크를 두지 않기로 했습니다(2-1).
