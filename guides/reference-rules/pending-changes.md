# 반영 대기 목록

> 상태: 초안 (2026-11-10). 2026-11-10 결정(화면 작업이 있는 결정은 완료 때 반영, 임시 정책 없앰)을 옮긴 문서입니다. 2026-11-10부터 이 문서로 작업합니다.

**반영 대기 목록 = 내 작업 밖의 다른 화면에 반영해야 하는 변경을 모든 화면에 걸쳐 한 곳에 남겨 두는 목록(`pending/open.md`)**입니다. 줄마다 메뉴와 화면(CID)을 적어 어느 화면의 것인지 가립니다. 반영을 마치거나 제외한 항목은 `pending/closed.md`로 옮깁니다(4절). 내가 지금 고치는 화면은 바로 고치므로 항목을 만들지 않습니다. 다른 작성자에게 알리는 대신 이 항목이 알림입니다(헌법 5조).

## 1. 항목이 생기는 때

| 때 | 무엇 |
| --- | --- |
| **화면설계 작업의 5단계 작업 완료** | 그 작업의 결정 반영(`reference-rules/discussions.md` 6절)으로 영향 화면에 항목이 생김. 정책이 바뀌지 않았어도 내 화면을 고쳐 다른 화면도 맞춰야 하면(예: 내가 고친 Popup을 부르는 화면) 이때 항목을 만듦 |
| **화면 작업이 없는 결정을 확인했을 때** | 회의 · 고객 답 · 정책 정리 · 후속 확인의 답으로 결정 반영을 돌릴 때 |
| **기준 자료 · 외부 원본이 바뀌었을 때** | 용어집 · 상태값 · Alert · Toast 카탈로그 · Common UX · 언어셋을 고치거나, 씨젠 문서 · IA 새 버전을 반영할 때 |
| **주기 점검** | "주기 점검 해 줘"로 어긋난 곳을 찾았을 때 (5절) |

- 작업 중(1 ~ 4단계)에는 영향 화면을 작업 기록 "영향 화면" 표에만 두고 항목을 만들지 않습니다. 결정이 바뀌어도 다른 사람에게 번지지 않게 하려는 것입니다.
- **영향 화면은 이번 작업에서 고치지 않습니다.** 변경의 크기와 상관없이 늘 그 화면의 반영 대기 목록에 항목으로 남깁니다. 그 화면을 맡은 작성자가 항목을 보고 알 수 있게 하려는 것입니다(헌법 5조). 아직 작업방에 그려지지 않은 화면도 같은 목록에 적고, `screens/asis/`와 `{메뉴}_asis` 페이지는 고치지 않습니다. 그 화면의 케이스 3에서 반영합니다.

## 2. 타입 (왜 올라왔나)

| 타입 | 언제 | 근거 칸 |
| --- | --- | --- |
| 논의 결정 | 논의 대상의 결정이 반영됨 (영향 범위가 `정책서 + 화면` 또는 `화면`). 후속 확인의 답으로 바뀐 경우도 여기 | DS ID, 바뀐 정책 ID |
| 다른 화면 파급 | 다른 화면을 고쳐서 이 화면(짝 CID, 부르는 · 불리는 화면, 공통 Popup)도 맞춰야 함 | 원인 CID |
| 기준 자료 변경 | 용어집 · 상태값 · Alert · Toast 카탈로그 · Common UX · 언어셋이 바뀜 | 자료 이름 · 항목 |
| 외부 원본 변경 | 씨젠 문서 · IA 새 버전 | 원본 이름 · 날짜 |
| 점검 발견 | 주기 점검 · 검토 · 기존 화면 옮기기에서 찾은 어긋남 · 오타 | 찾은 점검 |

맞지 않는 항목이 나오면 그때 타입을 하나 더합니다.

## 3. 칸과 쓰는 법

목록은 파일 둘입니다. 틀 파일은 따로 두지 않고, 두 파일 맨 위의 표 머리를 그대로 씁니다.

| 파일 | 담는 것 | 읽는 때 |
| --- | --- | --- |
| `pending/open.md` (반영 대기 목록) | 상태가 `대기` · `작업 중`인 항목 | 1단계에서 대상 화면의 CID로 걸러 읽음, 주기 점검 |
| `pending/closed.md` (끝난 반영 대기 항목) | `반영 완료` · `제외`가 된 항목 | 따로 요청할 때만 |

```markdown
| ID | 메뉴 | 화면 (CID) | 타입 | 변경 전 | 변경 후 | 근거 | 상태 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| TI-EVT-01-P-R01 | Event History | Event History Detail (TI-EVT-01-P) | 논의 결정 | 5-1 Status 칩 "Open · Close" | 디스크립션에 넣음: Main Mode에서만 바꿀 수 있음. 화면 예시 글자도 Close 칩 비활성 | DS-0012, POL-EVT-002 | 대기 |
```

- **메뉴:** IA의 메뉴 이름(화면 MD 머리말 `path`의 첫 칸).
- **화면 (CID):** `화면 이름 (CID)`.
- 줄은 메뉴 · CID · 번호 순서로 둡니다. 새 줄은 그 CID의 마지막 줄 다음에 넣습니다(그 CID의 줄이 없으면 그 메뉴의 끝).

- **변경 전:** 그 화면에 지금 있는 문구 · 동작 (어느 번호의 무엇인지)
- **변경 후:** 디스크립션에 들어갈 내용은 `디스크립션에 넣음: …`, 화면 예시 글자에 보이는 것(숫자 형식 · 단위 · 상태 · 칩 · 버튼 상태)은 그 뒤에 `화면 예시 글자도 …`. **무엇으로 바꿀지 정해지지 않았으면 반영 대기 항목을 만들지 않습니다.** 정책에 관한 것은 논의 대상으로, 화면에 관한 것은 질문 대기로 올립니다("확인 필요"는 새 항목에 쓰지 않음)
- **근거:** 원인 ID를 맨 앞에(예: `DS-0012 (원인 TI-STN-05), POL-ACC-006`). 같은 원인으로 만든 항목은 근거 칸의 원인 ID로 한꺼번에 찾습니다. 원인 문서에 항목 ID를 되적지 않습니다(한 방향으로 찾음).
- **ID:** `{CID}-R{번호}` (예: `TI-INS-01-T-R03`). 번호는 CID마다 R01부터 순서대로, `open.md` · `closed.md`를 통틀어 한 번 쓴 번호는 다시 쓰지 않습니다(새 번호는 두 파일에서 그 CID의 가장 큰 번호 다음). 짝 CID에 같은 내용을 넣을 때도 항목은 화면마다 따로 두고, 근거 칸에 짝 항목의 ID를 적어 잇습니다.
- **겹칠 때:** 같은 곳을 같은 내용으로 바꾸는 `대기` 항목이 이미 있으면 새로 만들지 않고 그 항목 근거 칸에 원인 ID를 더합니다. 같은 곳을 다르게 바꾸면 새 항목을 만들고 앞 항목은 `제외 (날짜, R05로 바뀜)`으로 두어 `closed.md`로 옮깁니다.
- To-Be 화면 MD가 없는 화면도 이 목록에 적습니다. To-Be 화면 MD는 만들지 않습니다(To-Be 화면 MD가 없어 1단계에서 케이스 3으로 갈림).

## 4. 상태

| 상태 | 뜻 |
| --- | --- |
| `대기` | 다음에 그 화면을 고칠 때 반영할 것 |
| `작업 중 (작업 기록 이름)` | 진행 중인 화면설계 작업이 이번에 반영하기로 고른 항목. 작업 완료 전이라 아직 반영이 끝나지 않음 |
| `반영 완료 (날짜)` | 5단계 작업 완료으로 화면 MD · Figma에 반영이 끝남 |
| `제외 (날짜, 이유)` | 반영하지 않기로 함 (예: 취소선으로 제거된 항목, 다른 항목으로 바뀜) |

- 항목은 지우지 않습니다. 상태가 `반영 완료` · `제외`가 되면 그 줄을 내용 그대로 `pending/open.md`에서 `pending/closed.md`로 옮깁니다(메뉴 · CID · 번호 순서 자리에 넣음). 되돌릴 때(`대기`로)는 `open.md`로 다시 옮깁니다.
- **상태가 바뀌는 때 (화면설계 케이스 1 · 2 · 3 모두 같음):** 작업에서 나온 결정과 마찬가지로 **5단계 완료 때 확정**합니다.
  - 1단계에서 후보를 적을 때, 그 화면 케이스의 규칙과 부딪혀 반영할 수 없는 항목(예: 빈 번호를 채우는 "번호 정리")은 묻지 않고 `제외 (날짜, 케이스 N 규칙과 부딪힘: 무엇)`으로 바꿈. 요청자에게 보여 주지 않음(`flow/1-requirements.md` 절차 4번 순서 5)
  - 1단계 요청자 확인에서 "이번에 반영"으로 고르면 `대기` → `작업 중 (작업 기록 이름)`
  - 3단계에서 화면에 반영해도 상태는 `작업 중` 그대로
  - 5단계 작업 완료 때 `작업 중` → `반영 완료 (날짜)`, 그 줄을 `closed.md`로 옮김. 반영한 항목 ID는 화면 변경 이력(`screen-history.md`)에서 그 작업 줄의 근거 칸에 적음(`flow/5-done.md` 절차 2번 순서 7)
  - 작업 도중 그 항목을 반영하지 않기로 하면 `대기`로 되돌림(또는 `제외`). 작업을 멈추면(`status: 멈춤`) `작업 중`인 항목을 모두 `대기`로 되돌림
  - "테스트로" 하는 작업은 상태를 바꾸지 않음
- `작업 중`인 항목은 다른 작업이 반영하지 않습니다. 같은 화면을 고치려면 1단계 겹침 확인(`flow/1-requirements.md` 절차 2번 순서 6)에서 먼저 정합니다.
- **되돌릴 때:** 반영한 항목을 되돌려야 하면 되돌리는 내용을 새 `대기` 항목으로 만듭니다(근거에 되돌리는 이유와 앞 항목 ID).
- 다른 작업에서 이미 UI 확정(UI 작업이 없으면 UX 확정)까지 마친 화면에 항목이 생기면 그 화면의 상태 처리는 5단계 문서(`flow/5-done.md`)를 따릅니다.

## 5. 주기 점검

Claude는 혼자 정기적으로 돌지 못하므로, 사람이 **"주기 점검 해 줘"**라고 요청할 때 돕니다(팀 프로그램에 점검 버튼을 두는 것은 요청서). 점검하는 것은 `screens/tobe/`의 화면 MD와 반영 대기 목록(`pending/open.md`)입니다. `screens/asis/`는 히스토리라 점검하지 않습니다(기존 화면의 어긋남은 그 화면을 케이스 3으로 다시 옮길 때 1단계에서 "점검 발견"으로 적음). 대조할 것:

1. 화면 MD 정책 참고의 정책 ID가 정책서에 있고, 폐기(Deprecated)되지 않았는지
2. 화면 MD의 말이 용어집 표준어인지 (단어 단위)
3. 화면 MD Alert · Confirm · Toast 표의 코드 · 상태값이 Alert · Toast 카탈로그(`alert/`) · 상태값 표와 맞는지
4. 정책서의 `cids`와 화면 MD 정책 참고가 서로 맞는지
5. T/L 짝 화면의 반영 대기가 한쪽에만 있지 않은지
6. 화면의 기준점(`basis`) 뒤로 바뀐 정책인데 그 화면에 반영 대기 항목이 없는지

찾은 것은 타입 `점검 발견` 항목으로 만들고, 정책을 정해야 하는 것은 논의 대상으로 올립니다. 나중에 스크립트로 만들어 4명이 돌려도 결과가 같게 합니다.

## 하지 않는 것

- 작업 중(1 ~ 4단계)에 다른 화면에 항목 만들기 (완료 때 한꺼번에)
- 다른 작성자의 화면을 크게 고치기 (항목만 만듦)
- 항목 지우기, 원인 문서에 항목 ID 되적기

## 6. asis에서 옮긴 항목 (2026-11-24)

예전에는 반영 대기 목록을 화면 MD마다 따로 두었습니다(`screens/asis/` 화면 MD의 "반영 대기 목록" 표, 예전 칸 `ID | 구분 | 지금 | 바꿀 것 | 근거 | 상태`). 2026-11-24에 이 표의 항목을 모두 `pending/open.md`(`대기`) · `pending/closed.md`(`반영 완료` · `제외`)로 옮겼습니다.

- **asis 화면 MD에서는 지웠습니다.** 옮긴 뒤 asis 화면 MD의 "반영 대기 목록" 절(과 "변경 이력" 절)을 지웠습니다(git 기록에 남음). asis 화면 MD에는 반영 대기를 다시 두지 않습니다.
- **ID:** 예전 번호(R01 …) 앞에 CID를 붙였습니다(`TI-SPT-01` 화면의 `R04` → `TI-SPT-01-R04`). 이미 다른 문서에 적힌 "TI-SPT-01 R04"도 같은 항목입니다.
- **칸:** 지금 → 변경 전, 바꿀 것 → 변경 후. 상태는 그대로 옮겼습니다(`대기 (확인 필요)` 같은 괄호도 그대로).
- **타입:** 예전 구분(화면의 어디를 고치는지: 디스크립션 · 표기 · 화면 정보 · 정책 반영 등)은 타입과 뜻이 달라 근거 칸으로 다시 매겼습니다. 근거에 논의 대상 ID가 있거나 예전 결정(임시 정책 PV · 고객 논의 CA · 사용자 답변)이 있으면 `논의 결정`, 정책 · 기준 자료(용어집 · 상태값 · 카탈로그 · Common UX · 헌법 · 정책서 · IA 등)가 있으면 `기준 자료 변경`, 근거가 다른 화면의 CID뿐이면 `다른 화면 파급`, 그 밖은 `점검 발견`입니다.
- **예전 항목의 `대기 (확인 필요)`:** 옮길 때 224줄이 이 상태였습니다. 2026-11-24에 변경 후 칸에 바꿀 안이 이미 있는 85줄은 `대기`로 바꾸고, 정할 것이 남은 139줄("어느 쪽으로 맞출지", "정의", "~할지", "품목 표에 없음" 등)만 `대기 (확인 필요)`로 두었습니다. 새 항목에는 이 상태를 쓰지 않습니다(3절 "변경 후").
  - 1단계에서 다른 `대기` 항목과 같이 "이번에 반영할지"를 묻습니다(묶음 하나로 따로 보여 줌, `flow/1-requirements.md` 절차 4번 순서 5 · 절차 5번 질문 6). 답이 화면을 보지 않아도 정해지는 항목은 그때 값도 함께 묻습니다(같은 문서 절차 4번 순서 3 "뒤 단계로 넘김"의 3).
  - "반영"을 고르면 `작업 중 (작업 기록 이름)`으로 바꾸고 작업 기록 "뒤 단계용 확인 항목(claude)"에 적습니다. 2단계가 정책 · 기준데이터로 풀어 보고, 못 풀면 3단계 질문 대기로 그립니다. 정책을 정해야 하면 논의 대상으로 올립니다.
  - 답이 정해지면 그 항목의 변경 후를 채워 반영합니다. 답이 "바꾸지 않음"이면 `제외 (날짜, 이유)`로 두고 `closed.md`로 옮깁니다.
  - "이번엔 안 함"이면 `대기 (확인 필요)` 그대로 둡니다.
