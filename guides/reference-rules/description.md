# 디스크립션 쓰는 법

> 상태: 초안 (2026-11-10). 본보기 중심으로 다시 썼습니다. 2026-11-10부터 이 문서로 작업합니다.

디스크립션은 **고객사와 개발사가 그 화면만 보고 확인 · 개발하는 글**입니다. 화면에서 일어나는 일을 풀어 쓰고, 정책 ID는 끝에 참고로만 붙입니다(헌법 3조).

## 1. 본보기를 따릅니다

**`examples/description-samples.md`의 본보기 세 화면과 같은 결로 씁니다.** 이 문서의 문장과 본보기가 다르게 읽히면 본보기를 따릅니다. 쓰기 전에 본보기를 먼저 읽습니다. 목록 화면은 본보기 1, 그 밖의 화면은 본보기 2를 따르고, 차트가 있는 화면만 본보기 3을 함께 봅니다.

## 2. 모양

```
3-2  [Save] 버튼
 ● 정의
   - 입력한 내용을 저장하는 버튼
 ● 활성화 조건
   - 필수 항목 모두 입력 시 활성화
   - 필수 항목 미입력 시 비활성화
 ● 동작
   - 클릭 시 입력 내용 저장 후 목록 화면으로 이동
 ● 정책 참고 : POL-SMP-004
```

| 무엇 | 쓰는 법 |
| --- | --- |
| **말투** | 개조식. 명사로 끝냄: 노출 · 조회 · 이동 · 닫힘 · 가능 · 불가 · 미노출 처리. "~됩니다 · ~합니다"를 쓰지 않음 |
| **한 줄에 한 가지** | 한 줄에 사실 하나. 조건이 둘이면 두 줄로 나눔 |
| **번호** | 0은 화면 정의, 1 · 2 · 3은 영역, 1-1 · 1-2는 그 안의 요소. 화면 위 번호 표시와 같음. T · L의 같은 영역은 같은 번호 |
| **제목** | 영역은 `○○ 영역` · `○○ 리스트`, 요소는 이름 뒤에 종류를 괄호로: `Sample ID(Text Input)`, `Status(Dropdown)`. 버튼은 `[Save] 버튼` |
| **라벨** | `● 라벨` 아래에 `- 내용`. 내용이 한 줄이면 `● 라벨 : 내용`. 더 풀 때는 `ㄴ` |
| **참고** | 블록 맨 끝에 한 줄씩: `● 공통 UX 참고 : COMM-5-f`, `● 정책 참고 : POL-SMP-004`, `● 참고 : TI-SPT-01/Case > Case 2`. 문장 중간에 ID를 넣지 않음 |

## 3. 풀어 쓰기와 정책 ID

- 화면에서 일어나는 일(조건 · 동작 · 표기 · 값이 없을 때)은 **정책서에 있어도 디스크립션에 풀어 씁니다.** 읽는 사람이 정책서를 열지 않고도 화면을 이해할 수 있어야 합니다.
- 정책 ID는 그 블록 끝 `● 정책 참고`에 ID만 적습니다. 규칙 번호는 적지 않습니다.
- 풀어 쓰는 범위는 **그 화면에서 보이고 일어나는 것까지**입니다. 다른 화면의 동작, 장비 안쪽 처리, 정책이 그렇게 정해진 이유는 쓰지 않습니다.
- 정책이 바뀌면 그 정책을 쓰는 화면의 반영 대기 목록에 항목이 생기고, 그때 디스크립션을 고칩니다(`reference-rules/pending-changes.md`).
- 공통 UX에 정의된 동작(페이지네이션, 드롭다운 열림 등)은 풀어 쓰지 않고 `● 공통 UX 참고`만 적습니다. 그 화면에서만 다른 점이 있으면 그것만 씁니다.

### 공통 UX가 화면에 맡긴 것 (디스크립션에 꼭 적음)

공통 UX는 동작만 정하고 아래 값은 화면마다 정하게 했습니다. 해당 요소가 있으면 디스크립션에 빠뜨리지 않습니다. 가이드 번호는 가이드 원본(그 Figma 파일에 고른 UX가이드)에서 찾아 적습니다.

| 요소 | 디스크립션에 꼭 적을 것 |
| --- | --- |
| 표 (Data Table) | 칸 구성(표출 항목), 데이터가 없을 때 문구, 줄 수가 기본과 다르면 그 줄 수 |
| 정렬 (Sorting) | 기본 정렬 기준, 정렬되는 칸 |
| 페이지 (Pagination) | 어느 형을 쓰는지 |
| 검색 영역 (Search Bar) | 조건 칸, 입력 규칙, 기본값 |
| 입력 · 검증 (Text Input) | 글자 수 제한, 최댓값, 오류 문구, 검증 뒤 다시 누르면 초기화하는지 |
| 드롭다운 · 선택 (Dropdown · Checkbox · Chips) | 옵션 값, 기본값 |
| 날짜 고르기 (Calendar) | 기본 기간, 최대 기간이 기본과 다르면 그 값 |
| 날짜 · 시간 표기 | 좁은 영역에서 줄인 형식을 쓰면 그 형식 |
| 목록 노출 순서 | 공통 순서와 다르면 그 순서 |
| 팝업 | 어느 형인지, 저장하지 않고 닫을 때 |
| Alert · Confirm · Toast | 문구 (알럿 카탈로그 ID) |
| 툴팁 | 문구 |
| 로딩 | 어느 형을 쓰는지 |
| 스크롤 · 화면 위로 | 어느 경우인지 |
| Badge 숫자 | 상한이 기본과 다르면 그 값 |
| 입력 방법 | 당겨서 새로고침 · 드래그 앤 드롭 · 단축키를 쓰면 그 동작 |

## 4. 꼭 지킬 것

| 지킬 것 | 내용 |
| --- | --- |
| 빠짐없이 | 화면의 모든 영역 · 요소에 번호와 디스크립션이 있음 |
| 화면마다 완결 | T-IOS와 L-IOS는 개발사가 다름. 짝 화면과 내용이 같아도 그 화면에 다 씀. "T 참고", "원문은 TI-…와 같음", "(T-IOS는 조회만 가능)"처럼 상대 플랫폼을 가리키거나 설명하지 않음 |
| 0번 | 정의 · 동작. User Type은 값만(Service, Admin, User), Service Mode는 L-IOS에만 노출 Mode 값만. 권한 설명 · 모드별 기능 설명은 넣지 않음 |
| 값은 그대로 | 드롭다운 항목 · 상태값 · 표기는 기준데이터 값을 그대로 나열. 출처 파일 이름은 쓰지 않음 |
| 값이 없을 때 | 늘 보이는 항목은 지우지 않고 값이 없을 때의 표기를 적음(예: `데이터 존재 시 노출/부재 시 '-' 노출`). 영역이 사라지는 경우만 `노출 조건`으로 적음 |
| 내부 표기 금지 | 저장소 경로, 질문 번호, "확인 필요", 정책 규칙 번호, 회의 ID, 논의 대상 ID, 화면 MD 절 이름을 쓰지 않음 |
| 지어 쓰지 않음 | 문장마다 출처가 있어야 함: 기존 원문(T · L 각각), 정책서, 공통 UX, 기준데이터, 확인받은 결정. 출처가 없으면 아래 질문 대기로 |
| 기존 원문 살리기 | 기존 디스크립션의 표현이 정책 · 용어집과 맞으면 그대로 씀. 틀린 값 · 오타 · 지운 기능(취소선)만 고침 |

## 5. 빨간 글씨 표시 (질문 대기 · 변경 확인)

빨간 글씨는 두 가지입니다. 둘 다 확인이 끝나면 지우고, 하나라도 남은 화면은 완료가 아닙니다.

| 표시 | 뜻 | 요청자가 할 일 | 예 |
| --- | --- | --- | --- |
| `※ 질문 대기 Q번호: {정해야 할 것}` | 정해지지 않아 임시로 그린 것 | 답을 정함 | ※ 질문 대기 Q3: 데이터가 없을 때 버튼을 비활성화할지 |
| `※ 변경 확인 C번호: {기존 → 바꾼 것, 이유}` | 근거가 있어 **기존 화면과 다르게** 그린 것 | 맞는지 확인함 | ※ 변경 확인 C2: 기존 화면은 Query Mode 기본, 정책에 따라 Push Mode 기본으로 변경 |

**질문 대기**

- 정해지지 않은 곳은 아래 순서로 따를 것을 찾아 그 내용으로 쓰고, 그 줄 바로 아래(같은 블록, 한 단계 들여 씀)에 빨간 글씨를 둡니다.
  1. 그 화면의 기존 원본(UX 화면설계서의 기획 프레임 · 디스크립션)
  2. 정책서
  3. 공통 UX
  4. 같은 메뉴의 다른 화면
- 넷 다 없으면 내용을 지어 쓰지 않고, 그 자리에 빨간 질문만 둡니다.
- 화면 MD "질문 대기" 표와 1:1로 맞춥니다.

**변경 확인**

- 기존 화면을 다시 그릴 때, 2단계에서 정책 · 용어집 · 기준데이터 · 공통 UX와 기존 화면이 다른 것으로 드러난 곳은 **기준 자료를 따라 그리고** 이 표시를 둡니다. 작업자가 기존 화면과 달라진 곳을 알아보고 맞는지 확인하게 하려는 것입니다.
- 표의 행을 최대 개수보다 줄여 그린 것처럼, 규칙과 다르게 그릴 수밖에 없던 곳도 이 표시를 둡니다(예: ※ 변경 확인: 최대 10행 중 8행만 그림, 화면 높이 초과).
- 반영 대기 항목을 반영해 기존과 달라진 곳에도 둡니다(예: ※ 변경 확인: 날짜 표기를 YYYY-MM-DD로 변경).
- 화면 MD "변경 확인" 표와 1:1로 맞춥니다.

**번호 (2026-11-11 정함)**

- 빨간 글씨에는 번호를 넣습니다: `※ 질문 대기 Q3: …`, `※ 변경 확인 C2: …`
- 번호는 **작업 하나에 통번호**입니다. 그 작업의 모든 화면을 통틀어 질문 대기는 Q1, Q2 …, 변경 확인은 C1, C2 …로 매깁니다. T-IOS와 L-IOS에 같은 질문 · 같은 변경이면 같은 번호를 씁니다.
- 같은 번호를 네 곳에 씁니다: 디스크립션의 빨간 줄, 화면의 빨간 표시, 화면 MD의 표, 작업 기록의 표. 번호 하나는 한 가지만 가리킵니다.
- 한 번 쓴 번호는 다시 쓰지 않습니다. 풀려서 지운 번호도 비워 둡니다.

**함께 지킬 것**

- 화면에서 그 번호 표시 옆에도 같은 빨간 글씨를 둡니다.
- 확인이 끝나면 빨간 줄을 지웁니다(질문 대기는 답대로 내용을 고친 뒤). 확인된 `※ 변경 확인`은 지우면서 아래 "변경 내역 상자"에 정리합니다.
- 전달 때까지 정해지지 않았는데 개발에 꼭 알려야 하면 읽는 사람 말로 한 줄: `※ 협의 중: {무엇}`


### 변경 내역 상자 (2026-11-11 정함)

`※ 변경 확인`을 요청자가 확인하면 빨간 글씨를 지우고, 그 내용을 **패널 옆 변경 내역 상자**에 정리합니다. 기존 작업방에서 버전마다 패널 옆에 두던 update 상자와 같은 모양입니다.

| 무엇 | 값 |
| --- | --- |
| 위치 | 기획 프레임 오른쪽 바깥, 패널 옆에 위쪽을 맞춰 둠. 상자가 여럿이면 위에서 아래로 쌓음 |
| 크기 | 너비 230 고정, 높이는 내용만큼. 안쪽 여백 위아래 6 · 좌우 8 |
| 테두리 · 글자 | 테두리 검정, 글자 Inter Regular 10 검정 |
| 제목 (첫 줄) | 케이스 3(기존 화면 다시 그리기): **`재설계 후 변경 내역`** |
| 배경 | 케이스 3: **회색 계열 `#E5E5E5`** |
| 내용 | 제목 아래 글머리로, 확인된 변경을 개조식으로 한 줄씩 (번호 · 무엇이 어떻게 달라졌나). 더 풀 때는 한 단계 들여 씀 |

```
재설계 후 변경 내역
 • 3 Order Reception Mode 기본값 변경
   • 기존 Query Mode → Push Mode (정책에 따름)
 • 2 리스트에 노출 개수 Dropdown 추가 (공통 UX)
 • 2-1 날짜 표기 YYYY-MM-DD로 변경
```

- 상자의 원본은 화면 MD "변경 확인" 표입니다. 표에서 "확인" 칸에 날짜가 적힌 줄을 상자로 옮깁니다. 확인받지 않은 변경은 상자에 넣지 않습니다(빨간 글씨로 남음).
- 상자에는 내부 표기(정책 규칙 번호, 논의 대상 ID, 반영 대기 항목 ID)를 쓰지 않습니다.
- 케이스 1(화면 부분 수정)도 바뀐 곳에 `※ 변경 확인`을 두고, 확인되면 같은 모양의 상자에 정리합니다. 제목은 기존 방식대로 `v{Ver} update`이고, Ver을 정하는 법과 배경색은 7단계(화면 Ver 체계)에서 정합니다.
- 기존 작업방의 상자는 `ver` 컴포넌트였지만 팀 라이브러리에 올라 있지 않습니다. 신규 작업방에서는 위 값으로 직접 그립니다.
## 6. 화면 MD와 Figma

- 화면 MD의 디스크립션이 원본이고, Figma 패널은 그대로 옮긴 것입니다. 고칠 때는 둘을 함께 고칩니다(헌법 6조).

## 7. 패널 틀 (2026-11-10 정함)

모든 화면의 패널을 같은 틀 · 같은 크기 · 같은 위치로 그립니다. 값은 기존 작업방 패널(Part.2 TI-SPT-01)을 잰 것입니다.

### 위치와 크기

| 무엇 | 값 |
| --- | --- |
| 기획 프레임 | 너비 2252 = 화면 1920 + 패널 332 |
| 패널 위치 | 화면 오른쪽에 붙임 (x 1920, y 0) |
| 패널 너비 | 332 고정. 높이는 내용만큼 |
| 줄 | 한 줄(행)이 번호 칸 22 + 내용 칸 310. 줄 높이는 내용만큼, 가장 낮은 줄 26 |
| 테두리 | 칸마다 `#D9D9D9` |

- 패널이 화면(1080)보다 길어지면 기획 프레임 높이를 패널에 맞춰 늘립니다. 패널을 둘로 나누거나 글자를 줄이지 않습니다.

### 그리는 컴포넌트

기존 작업방과 같은 **`Description` 컴포넌트**(라이브러리에 올라 있음)를 줄마다 인스턴스로 쌓아 만듭니다. 직접 그리지 않고, 떼어 내지(detach) 않습니다. 이 컴포넌트를 쓰면 위 크기 · 색이 저절로 맞습니다.

| Variant (`Property 1`) | 쓰는 줄 | 컴포넌트 키 |
| --- | --- | --- |
| `title` | Ver · Date 줄, CID · 작성자 줄 | `a27ce722d5486f110a29f4bcced61b50251eb14f` |
| `write` | 화면 줄, 경로 줄, 디스크립션 줄 | `897db05bf195bd55bc78ad5b8da44a9c0fdefa44` |
| `check` | Dev · SG 확인 일자 줄 — **쓰지 않음** | — |

- 컴포넌트 세트 키: `5c7ccc13d150f6f8fffdfbcfd71ac3c8391a4b4d`
- 번호 칸 색(영역 `#F1F1F1` · 요소 `#FCFCFC`)은 인스턴스에서 번호 칸 배경만 바꿔 맞춥니다.
- 글자가 내용 칸(310)을 넘지 않게 줄을 바꾸고, 줄 높이는 내용에 맞춰 늘립니다.

### 위에서 아래로

| 순서 | 줄 | 모양 |
| --- | --- | --- |
| 1 | Ver · Date | 왼쪽 232(라벨 `Ver` + 값), 오른쪽 100(라벨 `Date` 30 + 값 70) |
| 2 | CID · 작성자 | 같은 나눔 (라벨 `CID` + 값, 라벨 `작성자` + 값) |
| 3 | 화면 | 라벨 + 화면 이름 |
| 4 | 경로 | 라벨 + `메뉴 > 화면` 경로 |
| 5 ~ | 디스크립션 | 번호 칸 + 내용 칸. 0번부터 번호 순서대로 |

- **맨 아래 Dev · SG 확인 일자 줄은 두지 않습니다.**
- 라벨 칸(Ver · Date · CID · 작성자 · 화면 · 경로) 배경은 `#F1F1F1`입니다.

### 번호 칸 색 (영역과 요소 구분)

| 줄 | 번호 칸 배경 |
| --- | --- |
| 화면 · 영역 (0, 1, 2, 3 …) | `#F1F1F1` (회색) |
| 요소 (1-1, 2-1 …) | `#FCFCFC` (거의 흰색) |

- 내용 칸은 모두 흰색입니다. 제목(첫 줄)은 굵게 씁니다.
- 질문 대기 항목만 빨간 글씨입니다(5절).

### 화면 정보에 적는 값

| 케이스 | Ver | Date | 작성자 |

| 케이스 3 기존 화면 다시 그리기 | 기존 화면의 Ver 그대로 | 기존 화면의 Date 그대로 | 기존 화면 담당자 그대로 |

## 하지 않는 것

- 정책 ID만 적고 내용을 쓰지 않기 (예: `활성화 조건 : POL-SMP-004 규칙 2`)
- "~됩니다 · ~합니다 · ~할 수 있습니다"로 길게 쓰기
- 한 줄에 조건과 동작과 예외를 함께 쓰기
- 본보기에 없는 새 라벨을 만들어 쓰기 (꼭 필요하면 요청자에게 묻고, 정해지면 2절 라벨 표에 더함)
