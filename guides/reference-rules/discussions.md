# 논의 대상

> 상태: 초안 (2026-11-10). `background/cleanup-plan.md` 2절(방향 A)에서 정한 것과 2026-11-10 결정(임시 정책 없앰 · 화면 작업이 있는 결정은 완료 때 반영 · 상태 넷 · 갈래 없앰 · 후속 확인)을 옮긴 문서입니다. 2026-11-10부터 이 문서로 작업합니다.

정책 · 화면에서 **정해야 할 것**을 한 리스트로 받아, 결정하면 정책서와 영향 화면 반영 대기 목록에 정해진 순서로 따라 들어가게 하는 쓰는 법입니다. 내부 논의 · 고객 논의를 따로 두지 않습니다(헌법 4조).

## 1. 리스트 하나

- **항목 하나 = 파일 하나:** `discussions/DS-0001.md`. 번호는 네 자리 일련번호이고, 가장 큰 번호에 1을 더합니다. 한 번 쓴 번호는 다시 쓰지 않습니다. 같은 번호가 동시에 생기면 나중에 올린 쪽 번호를 바꿉니다.
- **리스트 = `discussions/list.md`:** 항목 머리말을 모아 다시 만드는 보기입니다. 손으로 고치지 않고, 항목을 만들거나 상태를 바꿀 때마다 Claude가 다시 만듭니다.

### 상태는 넷

| 상태 | 뜻 | 누구 차례 |
| --- | --- | --- |
| `논의 중` | 답이 아직 없음 | 정할 사람 (고객 · 내부) |
| `결정` | 정해졌고, 정책서 · 화면에 넣는 일이 남음 | 작업자 · Claude |
| `보류` | 정하지 않고 미뤄 둠. 언제 다시 볼지와 이유를 4절 논의 기록에 적음 | 다시 볼 때가 되면 정할 사람 |
| `종료` | 논의가 끝났고 처리할 것도 모두 처리해, 이 항목을 닫아도 됨 (반영을 마쳤거나, 반영할 것이 없음) | 없음 |

- 하지 않기로 한 것은 따로 상태를 두지 않습니다. 결정 문장에 "하지 않음"과 이유를 적고 `종료`로 둡니다.
- 같은 질문을 하나로 모으는 일(합침)은 상태가 아닙니다. 9절 순서로 정리합니다.
- 보류를 다시 꺼내면 `논의 중`으로 바꿉니다.

### 리스트 묶음

**"논의 리스트 보여 줘"** 하면 아래 순서로 묶어 보여 줍니다. 묶음은 Claude가 상태와 칸을 읽어 나눕니다. `종료`는 따로 요청할 때만 보여 줍니다.

| 묶음 | 무엇 |
| --- | --- |
| 1. 결정 · 반영할 것 | 상태 `결정`이고 `work`가 비어 있음: 결정했는데 아직 반영하지 않은 것 (가장 먼저 처리) |
| 2. 논의 중 · 고객 | 고객이 정할 것 (고객 회의 안건) |
| 3. 논의 중 · 내부 | 우리끼리 정할 것 |
| 4. 결정 · 작업 중 | 상태 `결정`이고 `work`에 작업 기록 이름이 있음: 그 화면 작업이 완료되면 반영할 것 |
| 5. 보류 | 미뤄 둔 것 (다시 볼 때 함께) |
| 6. 후속 확인 필요 | `종료`인 것 중 5절에 "후속 확인 필요" 줄이 남은 것 (누구에게 무엇을). 회의 안건이 됨 |

각 줄: `ID | 제목 | 누가 정하나 | 걸린 정책 | 걸린 화면 | 생긴 날 | 상태`

## 2. 생기는 곳

| 어디서 | 언제 |
| --- | --- |
| 화면설계 작업 | 2단계 정책 수정 범위를 정할 때, 3 · 4 · 5단계에서 질문 대기 · 검토 · 고객 피드백으로 정책을 정해야 할 때 |
| 회의 | 회의록을 정리하다 결정된 것 · 논의가 남은 것이 나올 때 |
| 고객 · 개발사가 알려 줌 | 개발 중 생긴 이슈, 고객사 내부 정책 이슈, 정책 변경 요청 |
| 정책 정리 · 검토 | 정책서를 정리하다 출처끼리 다르거나 정의가 없는 곳을 찾을 때 |
| 주기 점검 | "주기 점검 해 줘"로 어긋난 곳을 찾았는데 정책을 정해야 할 때 |

- **새로 만들기 전에** 같은 정책 · 규칙을 다루는 열린 항목이 있는지 찾습니다. 같은 질문이면 그 항목에 잇고(안이 다르면 "제안" 표에 안을 더함), 새로 만들지 않습니다.
- **결정 전에 화면에 써야 하면** 따로 등록하지 않고 따를 것을 정해진 순서(기존 원본 → 정책서 → 공통 UX → 같은 메뉴의 다른 화면)로 찾아 그린 뒤 빨간 글씨 `※ 질문 대기`로 표시하고, 화면 MD 질문 대기 표에 DS ID를 잇습니다.
- **개발사 검토에 따라 화면이 달라질 수 있는 것**은 `논의 중`으로 둡니다. 다 정해졌고 한 번 확인만 해 보면 되는 것만 `종료` + "후속 확인 필요"로 둡니다(7절).

### 자주 있는 네 가지 경우

| 경우 | 흐름 |
| --- | --- |
| 가. 화면 영향은 없지만 작업할 때 알아야 하는 이슈 | 논의 대상을 만들고 결정 문장에 내용을 적음 → 영향 범위 `없음` → 바로 `종료`. 걸린 정책 · 화면을 적어 두면 그 화면을 작업하는 사람의 2단계에서 Claude가 읽어 근거에 올림 |
| 나. 화면이 달라져야 하는 이슈 (정책을 듣고 바로 설계) | `결정` + `work`에 작업 기록 이름 → 그 기준으로 화면 작업 → 7단계 완료(화면 컨펌) 때 정책서 · 다른 화면에 한꺼번에 반영 → `종료` |
| 다. 설계 중에 고객이 그 이슈를 다시 고침 | 같은 항목 5절에 결정 줄을 더함. 상태는 `결정` 그대로. 정책서는 아직 고치지 않았으므로 되돌릴 것이 없고, 화면 컨펌 때 맨 아래 결정 줄로 한 번만 반영 |
| 라. 설계하다 우리가 발견한 이슈 | `논의 중` + `work`에 작업 기록 이름, 화면에 빨간 "※ 질문 대기" → 질문 대기가 남아 있으면 7단계를 통과하지 못하므로 그 화면은 멈춰 있음 → 답이 오면 `결정` → 화면 마무리 → 화면 컨펌 때 반영 → `종료` |

- 결정이 바뀌면 5절에 줄을 더하고 지우지 않습니다. 가장 아래 줄이 유효한 결정입니다.

## 4. 영향 범위

결정이 어디까지 고치게 하는지입니다. **사람이 고르지 않습니다.** Claude가 결정 문장과 정책서 · 화면을 대조해 정리안에 적어 보여 주고, 확인을 받은 뒤 6절 "반영" 첫 줄에 남깁니다.

| 영향 범위 | 뜻 | 예 | 반영하는 것 |
| --- | --- | --- | --- |
| 정책서 + 화면 | 정책서의 규칙이 바뀌거나 더해짐 | "Error인 Module의 Door를 열면 Paused가 된다" → POL-EQP-004 규칙을 고침 | 정책서, 영향 화면 반영 대기 항목 |
| 화면 | 정책은 그대로이고 화면의 표현 · 배치 · 문구만 정함 | "Event 목록 기본 정렬은 발생 시각 내림차순", "[Export] 버튼을 표 오른쪽 위로" | 영향 화면 반영 대기 항목 (정책서는 고치지 않음) |
| 없음 | 고칠 문서가 없음: 작업할 때 알아야 하는 참고 이슈, 하지 않기로 한 요청 | "Empty Waste Bin을 Main Mode에서도" 요청 → 하지 않음 | 없음 |

- 영향 범위가 `없음`인 항목은 정책서에도 화면에도 남지 않습니다. 그래서 걸린 정책 · 화면(`policies` · `cids`)을 꼭 적고, 그 화면을 작업하는 사람의 2단계(근거 찾기)에서 Claude가 찾아 읽습니다(`flow/2-evidence.md`).
- 내 작업 안에서 내 화면만 바뀌는 결정은 논의 대상을 만들지 않아도 됩니다. 화면 MD에 쓰고 질문 대기를 지우면 됩니다. 고객이 요청했거나, 여러 화면이 같은 결정을 따라야 하거나, 회의에서 정한 것이면 논의 대상으로 남깁니다.

## 5. 언제 반영하나 (결정 반영의 트리거)

**트리거는 "결정 + 확인"입니다.** 결정 줄(결정 문장 · 정한 사람)이 적히고, Claude가 정리안(영향 범위 · 바뀌는 정책 문장 · 올릴 반영 대기 항목)을 보여 준 뒤 정한 사람(또는 요청자)이 확인하면 반영합니다. 확인 없이 정책서나 다른 화면이 바뀌는 일은 없습니다.

| 결정의 종류 | 반영하는 때 |
| --- | --- |
| **그 결정으로 화면을 그리는 작업이 있음** (`work`에 작업 기록 이름) | **그 작업의 7단계 완료(화면 컨펌) 때 한꺼번에.** 그동안 결정이 바뀌면 5절에 줄을 더함. 정책서 · 다른 화면은 그때까지 그대로 |
| **화면 작업이 없음** (`work`가 비어 있음: 정책 문장만 바뀜, 참고 이슈, 하지 않기로 함) | 결정을 확인하면 **바로** |
| 화면 작업 중이지만 다른 작업이 그 정책을 꼭 먼저 써야 할 때 | 요청자가 정하면 **그 결정만 먼저** 반영 |

- 회의나 고객이 알려 준 정책이라도 그것으로 곧바로 화면 작업을 시작하면 `work`에 그 작업 기록 이름을 적고 화면 컨펌 때 반영합니다.
- 화면 컨펌 전에 다른 작업자가 같은 정책을 볼 때는, 2단계에서 걸린 논의 대상(`결정` + `work`)을 읽으므로 바뀌는 중인 것을 알 수 있습니다.

결정 줄이 적히는 길:

| 길 | 트리거 |
| --- | --- |
| 대화에서 말함 | "DS-0003은 A안으로 정했어 (정한 사람: ○○)" → 정리안 → "확인" |
| 단계 요청자 확인에서 정함 | 질문에 답함 → 정리안 → 확인 (화면 작업 중이면 `결정`으로 두기까지만) |
| 팀 프로그램 논의 탭 | [답변] → 정리안 → [확인 · 반영] |
| 회의록 정리 | 회의에서 결정된 문장을 결정으로 적음 → 정리안 → 확인 |

- 파일에 결정 줄을 직접 적기만 하면 반영이 시작되지 않습니다. 그런 항목은 상태 `결정`인데 6절이 비어 있어 리스트 "1. 결정 · 반영할 것"에 보이고, "논의 리스트 보여 줘"나 주기 점검 때 Claude가 먼저 보여 주며 반영할지 묻습니다.

## 6. 결정 반영 순서

한 번에 돌립니다. 7단계에서는 그 작업 기록 이름이 `work`에 적힌 `결정` 항목을 모두 이 순서로 돌립니다.

1. **확인:** 결정 문장과 정한 사람이 있는지. 없으면 멈추고 묻습니다(결정을 지어 쓰지 않음).
2. **영향 화면 찾기:** DS의 `cids` + 걸린 정책의 `cids` + 그 화면들의 짝 CID + `flow/2-evidence.md` "쓰는 곳" 표. 찾은 화면은 DS `cids`에도 더합니다.
3. **정리안 보여 주기:** 영향 범위, 바뀌는 정책 문장, 영향 화면마다 올릴 반영 대기 항목을 보여 주고 확인을 받습니다. 고칠 점을 말하면 다시 정리합니다.
4. **정책서 (영향 범위가 `정책서 + 화면`일 때):** 규칙을 고치거나 더하고 정책 변경 이력에 DS ID를 적습니다.
5. **반영 대기 항목:** 영향 화면의 화면 MD마다 한 줄 — 타입 `논의 결정`, 근거 칸에 DS ID와 정책 ID(`reference-rules/pending-changes.md`). 작업에서 **함께 고친** 화면에는 줄을 만들지 않고 6절 "함께 고친 화면"에 적습니다.
6. **닫기:** DS 6절을 채우고 상태를 `종료`로 바꿉니다. `list.md`를 다시 만듭니다.
7. **보고:** 고친 정책 문장, 만든 반영 대기 항목을 표로 보여 줍니다.

영향 범위가 `없음`이면 3번에서 "고칠 것 없음"을 확인받고 4 · 5번을 건너뜁니다.

## 7. 후속 확인

다 정해져 반영까지 마쳤지만 한 번 확인해 보기로 한 것(예: 고객이 컨펌했고, 장비 개발사에 한 번 확인해 보기로 함)입니다. 상태가 아니라 **5절에 적는 한 줄**입니다.

- 적는 모양: `- 후속 확인 필요: 장비 개발사 · Door 센서가 Paused 신호를 보낼 수 있는지`
- 상태는 `종료`입니다. 정책서 · 화면에는 표시하지 않습니다.
- 찾는 법: "후속 확인 필요"로 검색하거나 "논의 리스트 보여 줘"의 묶음 6.
- **답이 그대로 맞음:** 그 줄을 `- 후속 확인 끝 (날짜 · 누구): 그대로`로 고칩니다. 더 할 일이 없습니다.
- **답이 바뀜:** 그 줄을 `- 후속 확인 끝 (날짜 · 누구): 바뀜`으로 고치고, 5절에 결정 줄을 더해 상태를 `결정`으로 되돌린 뒤 결정 반영을 돌립니다(정책서 고침 + 영향 화면 반영 대기 항목). 이미 전달한 화면은 다음 Ver에서 반영합니다.

## 8. 회의에서 들어오는 길

회의록 정리본의 정책이 될 만한 문장마다 정책서 · 열린 논의 대상과 대조해 나눕니다.

| 결과 | 처리 |
| --- | --- |
| 정책에 있음 | 논의 대상을 만들지 않음 |
| 정책을 바꾸거나 더하기로 결정됨 | 논의 대상을 만들고 결정까지 적어 결정 반영 (그것으로 화면 작업을 시작하면 `work`에 묶음) |
| 화면 영향은 없지만 작업할 때 알아야 하는 이슈 | 논의 대상을 만들고 결정 문장에 적음 (영향 범위 `없음`) |
| 열린 논의 대상에 대한 답 | 그 항목 4절에 회의 ID로 기록, 결정이면 5절 |
| 후속 확인의 답 | 7절 |
| 더 논의할 것 | 논의 대상 `논의 중` (고객이 정할 것이면 `decider: 고객`) |

## 9. 같은 질문 합치기

같은 질문을 다루는 항목이 둘 이상 생긴 것을 찾았을 때만 씁니다(새로 만들기 전에 먼저 찾으므로 드뭅니다). 순서를 그대로 지킵니다.

1. **제안 · 확인:** Claude가 "DS-0007과 DS-0012가 같은 질문으로 보입니다"라고 두 항목의 "정할 것"을 나란히 보여 주고, 사람이 확인합니다. 확인 없이 합치지 않습니다.
2. **남길 쪽 정하기:** 먼저 생긴 쪽(번호가 작은 쪽)을 남깁니다.
3. **옮기기:** 없어지는 쪽의 3절 제안 · 4절 논의 기록 · 5절 결정 줄 · `policies` · `cids` · `old_ids`를 남는 쪽에 모두 옮깁니다. 옮긴 논의 기록 줄에는 `(DS-0012에서 옮김)`을 붙입니다.
4. **ID 남기기:** 남는 쪽 `old_ids`에 없어지는 쪽 ID를 적습니다.
5. **가리키던 곳 고치기:** 화면 MD 질문 대기 표, 작업 기록, 반영 대기 항목 근거 칸, 정책 변경 이력에 적힌 없어지는 쪽 ID를 찾아 남는 쪽 ID로 바꿉니다.
6. **지우기:** 5번에서 남은 곳이 없는지 다시 찾아본 뒤 없어지는 쪽 파일을 지웁니다. 그 번호는 다시 쓰지 않습니다.
7. **리스트 · 보고:** `list.md`를 다시 만들고, 옮긴 것과 고친 곳을 보고합니다.

## 10. 옛 항목 옮기기

열린 PD(협의 대기) · PV(임시 정책) · CA(고객 논의)를 DS로 옮기고 `old_ids`에 옛 ID를 남깁니다. 같은 것을 다루는 항목은 9절 순서로 하나로 합칩니다. PV는 결정된 것이므로 결정으로 옮기되, 답에 따라 화면이 달라질 수 있으면 `논의 중`으로, 한 번 확인만 남았으면 "후속 확인 필요"를 적습니다. 닫힌 PD · PV는 옮기지 않고 정책 근거의 옛 ID로 둡니다.

- 리스트(`list.md`)를 손으로 고치기
- 다른 작성자에게 알린다고 쓰기 (Claude는 알림을 보내지 못함. 반영 대기 항목이 알림을 대신함)
