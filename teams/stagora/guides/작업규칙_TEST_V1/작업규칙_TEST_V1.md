# 작업규칙_TEST_V1

화면을 수정할 때 따르는 작업 순서와 수정 이력 표기 규칙이다. 참고 파일 `Action_Flows.md`(액션별 동작 흐름: 요청 등록 → 적용 문서 확인 → Figma 반영 → 캡처 → 완료 · 변경 이력)의 흐름을 기준으로 정리했다.

> 이 문서는 작업 방식(순서 · 확인 항목 · 산출물 형식)을 정한다. 화면 내용은 화면 정의서 → 정책서 → 기준데이터, 공통 구성 · 컴포넌트는 UX가이드를 따른다.

## 0. 문서 구성 (목차)

화면 수정 작업은 아래 순서로 진행한다.

### 0-1. 작업 순서 요약

1. 반영할 화면 리스트를 정리한다.
2. 리스트의 화면마다 수정할 부분을 정리한다.
3. 수정 작업 후, 수정한 부분에 히스토리를 남긴다.

## 1. 반영 화면 리스트 정리

작업 전에 반영되어야 하는 화면을 먼저 모은다.

### 1-1. 반영 화면 리스트 작성

반영되어야 하는 화면의 목록을 작성한다.

| 항목 | 내용 |
|---|---|
| 화면 ID | 예: TI-STN-08 |
| 프레임 | 예: TI-STN-08-P (수정 가능 페이지 안의 프레임만) |
| 수정 사유 | 요청 번호 · 정책서 · 회의록 등 근거 |

- 수정 가능 페이지가 아닌 화면은 리스트에 넣지 않고 담당자 확인을 남긴다.
- 정책 · 문서 변경으로 생기는 경우 연관 항목 찾기 결과와 화면설계서 작업대기의 반영 대기 줄을 근거로 한다.

## 2. 수정 부분 정리

리스트에 올린 화면마다 고칠 곳을 정리한 뒤 작업한다.

### 2-1. 화면별 수정 내용 정리

반영되어야 하는 화면 리스트 안에서 수정되어야 하는 부분을 화면마다 정리한다.

| 항목 | 내용 |
|---|---|
| 화면 | 화면 ID · 프레임 이름 |
| 수정 위치 | 영역 · 레이어(디스크립션인지 화면 요소인지) |
| 지금 | 현재 내용 |
| 바꿀 것 | 수정 후 내용 |
| 근거 | 요청 · 문서 · 항목 |

- 요청과 문서가 어긋나면 요청을 따르고 어긋난 점을 기록한다.
- 정할 수 없는 부분은 임의로 고치지 않고 확인 필요로 남긴다.

## 3. 수정 이력 표기

수정 작업 후, 작업된 부분은 히스토리를 남긴다.

### 3-1. 히스토리 문구 형식

수정한 부분에 아래 형식으로 문구를 남긴다.

`[$버전명$/$수정된 내용$]`

- `$버전명$`: 이번 수정의 버전.
- `$수정된 내용$`: 무엇을 어떻게 고쳤는지 한 줄.

### 3-2. 표기 색상

| 대상 | 텍스트 색 | 배경(Bg) |
|---|---|---|
| 일반 텍스트 | #ff0000 | 없음 |
| 디스크립션 | #ff0000 | Bg도 색상 표기: #ff0000, 투명도 10% |

- 디스크립션 안의 수정은 글자색 #ff0000과 함께 배경(Bg)을 #ff0000 투명도 10%로 표기한다.
- 일반 텍스트는 글자색만 #ff0000으로 표기한다.

### 3-3. 작업 후 기록

- 수정 이력 문구를 남긴 뒤 프레임 캡처를 갱신하고, 변경 이력에 무엇을 고쳤는지 적는다.
