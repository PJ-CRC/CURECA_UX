# 작업규칙_TEST_V2

Workbench 수정 요청을 처리하는 순서, 단계마다 확인할 항목, 산출물(화면 · 캡처 · 기록) 형식을 정리한다. 참고 파일 `CLAUDE.md`의 「Workbench 수정 요청 처리」 · 「캡처」 · 「팀」 규칙을 기준으로 했다.

> 이 문서는 작업 방식(순서 · 확인 항목 · 산출물 형식)을 정한다. 화면 내용은 화면 정의서 → 정책서 → 기준데이터, 공통 구성 · 컴포넌트 · 표기는 UX가이드를 따른다. 문서와 요청이 어긋나면 요청을 따르고 note에 어긋난 점을 적는다.

## 0. 문서 구성 (목차)

### 0-1. 처리 순서 요약

1. 요청 확인 (대상 파일 · 수정 가능 페이지)
2. 「진행 중」으로 변경 (한 요청씩)
3. 작업 기준 문서 확인 (카테고리마다 적용한 문서 하나)
4. Figma 반영
5. 캡처 갱신
6. 변경 이력 기록
7. 「완료」 또는 「보류」 (note 작성)
8. 프로토타입 맞추기 (해당할 때)

## 1. 처리 순서와 확인 항목

요청은 감시가 알려 준 순서(우선순위 「높음」 먼저, 같은 우선순위는 먼저 등록한 것부터)대로 한 개씩 끝내고 다음 요청을 시작한다.

### 1-1. 단계별 순서 · 확인 항목

| 순서 | 단계 | 할 일 | 확인 항목 |
|---|---|---|---|
| 1 | 요청 확인 | 요청의 `fileKey`(없으면 시작 안내 작업 링크의 파일)와 `page` 확인 | `page`가 지금 수정 가능 페이지(project.json editablePageName)인가 · 아니면 「보류」, note에 「○○ 페이지는 보기 전용입니다. 담당자 확인 필요」 |
| 2 | 겹침 확인 | 감시의 `CONFLICT` 줄 확인 | 같은 프레임에 다른 작업자의 대기 · 진행 중 요청이 있는가 · 있으면 Figma를 고치지 않고 「보류」, note는 「겹침 대기」로 시작 |
| 3 | 진행 중 | 상태를 「진행 중」으로 | 서버가 「이미 진행 중」으로 거절하면 다른 세션이 처리 중이니 건너뜀 |
| 4 | 첨부 · 답변 읽기 | `images` 원본, `replies`(사람의 답) 읽기 | 이미지와 글이 어긋나면 「보류」와 질문 · 답이 있으면 마지막 답대로 이어서 처리, 같은 질문 반복 금지 |
| 5 | 작업 기준 확인 | `GET /api/guides?team={요청 팀}`의 `applied[fileKey].docs` | 작업규칙 · 정책서 · UX가이드 · 기준데이터 · 화면 정의서마다 적용한 문서 하나만 읽음 · 적용하지 않은 문서는 읽지 않음 |
| 6 | Figma 반영 | 수정 가능 페이지의 프레임을 요청대로 고침 | 레이아웃 지정이 있으면 Layout_Structure를 따름 · 새 텍스트 폰트는 Inter 또는 Noto Sans KR · Pretendard 글은 플러그인 text 작업 |
| 7 | 캡처 갱신 | 실제로 고친 프레임 모두 캡처 | 요청 프레임을 고치지 않았으면 그것은 찍지 않음 |
| 8 | 변경 이력 | `Common_UX_Changelog.md` 맨 위에 항목 추가 | 제목 앞에 파일명 (예: `[CURECA 기획] …`) |
| 9 | 상태 변경 | 「완료」 또는 「보류」로 변경하고 note 작성 | 캡처(7)를 완료보다 먼저 · `frames` 함께 전송 |
| 10 | 프로토타입 맞추기 | `GET /api/prototypes`에서 「갱신 필요」 확인 | 있으면 prototype-sync 작업을 쌓음 (요청은 기다리지 않음) |

### 1-2. 작업 기준 문서 역할과 우선순위

| 카테고리 | 역할 |
|---|---|
| 작업규칙 | 작업 방식 (순서 · 확인 항목 · 산출물 형식) |
| 정책서 | 업무 규칙 (권한 · 상태 전이 · 예외 처리) |
| UX가이드 | 구성 · 크기 · 컴포넌트 · 표기 |
| 기준데이터 | 코드 · 상태값 · 단위 · 표기 값 |
| 화면 정의서 | 그 화면의 용어 · 값 · 상태 · 동작 · 화면 이동 |

- 어긋나면 화면 내용은 화면 정의서 → 정책서 → 기준데이터 순, 공통 구성 · 컴포넌트 · 표기는 UX가이드를 따른다.
- 기본 문서는 없다. 적용한 문서가 하나도 없으면 요청 내용과 그 파일의 기존 화면을 따른다.

### 1-3. 보류 · 질문 기준

| 상황 | 상태 | note / ask |
|---|---|---|
| 수정 가능 페이지가 아님 | 보류 | 「○○ 페이지는 보기 전용입니다. 담당자 확인 필요」 |
| 다른 작업자와 같은 프레임 | 보류 | 「겹침 대기: {by}({pc}) {reqId} {진행 중\|대기} — 그 요청이 끝나면 이어서 처리합니다」 |
| 해석이 모호함 | 보류 | 질문 + `ask` (선택지 2~4개, 직접 입력 가능) |
| 기존 정책과 다르게 고쳐야 함 | 요청을 따름 | 임시 정책(PV) 등록, note에 ID |
| 정할 수 없어 보류 | 보류 | 논의(PD)로 올리고 note에 ID |

## 2. 산출물 형식

### 2-1. 산출물 표

| 산출물 | 형식 | 위치 · 전달 방법 |
|---|---|---|
| 수정한 화면 | 수정 가능 페이지의 Figma 프레임 | 요청의 파일 · 페이지 |
| 캡처 | 고친 프레임마다 `get_screenshot`(긴 변 = 원본 크기, 최대 8000) PNG | `POST /api/shots` → `projects/{fileKey}/shots/` |
| 고친 프레임 알림 | `frames:[{nodeId, name}]` (고친 순서, 최대 12개) | 「완료」 update에 함께 전송 |
| 변경 이력 | `Common_UX_Changelog.md` 항목 | 파일 맨 위, 제목 앞에 파일명 |
| 작업 이력 · 토큰 사용량 | 서버가 상태 변경마다 자동 기록 | `.history/` (깃 공유) |
| 요청 note | 줄바꿈으로 나눈 답변 | Workbench 「Claude 답변」 |

### 2-2. note 작성 형식

| 줄 | 내용 |
|---|---|
| 첫 줄 | 처리 요약 한 문장 |
| 다음 줄들 | `- 화면: 무엇 → 어떻게` (고친 곳마다 한 줄) |
| 참고 · 확인 필요 | 어긋난 점, 남은 일 (마지막 줄 앞) |
| 마지막 줄 | `작업 기준: 작업규칙 {제목\|없음} · 정책서 {제목\|없음} · UX가이드 {제목\|없음} · 기준데이터 {제목\|없음} · 화면 정의서 {제목\|없음}` |

### 2-3. 수정 이력 표기 (화면 위)

화면 위 수정 표기는 적용한 UX 문서의 규칙을 따른다. 규칙이 없으면 화면에 별도 표기를 넣지 않고 변경 이력으로만 남긴다.

## 3. 처리할 때 지킬 점

### 3-1. 공통 원칙

- 수정 가능 페이지는 파일마다 하나다. 다른 페이지는 읽기만 하고, 요청을 처리할 때마다 그때의 editablePageName으로 확인한다.
- 요청은 한 개씩 「진행 중」으로 바꾸고 끝낸 뒤 다음을 시작한다(토큰 사용량 구간이 겹치지 않게).
- 요청 · 작업의 팀(`team`, 없으면 cureca)대로 일한다: API에 `?team={team}`, 사용량은 `-Team {team}`.
- 해석이 모호하면 임의로 고치지 않고 「보류」와 질문을 남긴다.
- 커밋 · 푸시는 사용자가 요청할 때만 한다.

### 3-2. 처리 후 확인

| 확인 | 내용 |
|---|---|
| 캡처 | 고친 프레임 모두 갱신했는가 |
| 이력 | 변경 이력 항목에 파일명 접두가 있는가 |
| note | 요약 · 고친 곳 · 작업 기준 줄이 있는가 |
| 프로토타입 | 「갱신 필요」 프로토타입에 맞추기 작업을 쌓았는가 |
