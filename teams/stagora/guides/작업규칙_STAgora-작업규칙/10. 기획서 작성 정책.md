# 10. 기획서 작성 정책

Nov 16, 2026 · @브렉스

## 1. 목적과 적용 범위

화면 기획서(SB)는 프로젝트와 상관없이 이 정책서로 작성하고, 개발·QA가 기획서만 보고 구현과 검수를 할 수 있게 만드는 것을 목표로 해요.

- **적용 대상** : 화면 프레임의 디스크립션, 케이스 프레임, 문구 표·변수 표, `[공통]` 프레임
- **제외** : 디자인 시안, 레퍼런스, 프로토타입 화면, 파일·페이지 구성과 진행 상태 관리
- **우선순위** : 프로젝트의 \<Common UX>(조직 단위 UI 규칙)가 있으면 그것을 따르고, 이 정책서는 기획서 작성 방식만 정해요.
- **새 프로젝트** : 1-1 프로젝트 설정 표만 채우고, 나머지 규칙은 그대로 써요.

### 1-1. 프로젝트 설정

프로젝트마다 다른 값은 이 표에만 두고, 본문에서는 이 값을 가리켜요. CID(화면 ID) 규칙은 IA 문서에서 관리하고, 본문 예시의 `XX-ABC`는 CID 자리예요.

| 설정 | 정하는 것 |
| --- | --- |
| Common UX | 공통 UI 문서와 ID 형식 |
| 데이터 정의 문서 : 제품목록 | 제품·분석체의 이름, 약어, Full name |
| 데이터 정의 문서 : 정책 | 데이터 정의, 집계·계산 기준 |
| 미확정 표시 색 | 미확정 내용의 글자색 |

### 1-2. 작성 순서

새 화면 기획서는 아래 순서로 써요. 단계마다 괄호 안의 장에 자세한 규칙이 있어요.

1. **준비** : IA 문서에서 CID를 확인하고, PRD·데이터 정의 문서·\<Common UX>에서 이 화면에 해당하는 내용을 찾아요 (1-1)
2. **프레임** : CID 이름으로 화면 프레임을 만들고, 왼쪽에 와이어프레임, 오른쪽에 디스크립션 열을 두어요 (2-1)
3. **헤더 표** : Ver, Date, CID, 작성자, 화면, 경로를 채워요 (2-2)
4. **배지** : 와이어프레임에 위 → 아래, 왼쪽 → 오른쪽 순서로 배지를 붙여요 (3장)
5. **\* 화면 공통** : Default 화면, 표시 형식, 참고 자료(PRD·데이터 정의 링크), 팝업 닫힘을 써요 (2-3, 7장, 8장)
6. **# 화면 전체 규칙** : 메뉴 접속 권한, 사용자·데이터 조건에 따른 화면 분기를 써요 (2-3)
7. **번호 항목** : 배지 순서대로 노출 → 표시 → 참고를 쓰고, 빠뜨리기 쉬운 것 표를 훑어봐요 (4장\~8장)
8. **케이스** : 케이스로 확인할 것 표로 필요한 상태를 고르고, 케이스 순서대로 번호를 매겨 케이스 프레임을 만들어요. 본 화면 참고에 케이스 참조를 적어요 (9장)
9. **문구 표·변수 표** : 조건마다 문장이 달라지면 표를 만들어요 (10장)
10. **미확정 정리** : 정해지지 않은 내용에 미확정 색과 (확인 필요)를 붙여요 (12장)
11. **검수** : 검수 체크리스트로 확인하고, 확인 행에 확인 일자를 받아요 (14장, 2-2)

이미 있는 화면을 고칠 때는 헤더 Date를 갱신하고, 기록 시작 뒤에는 업데이트 표시를 남겨요 (13장, 13-1).

## 2. 문서 구성

화면 1개는 프레임 1개로 만들고, 왼쪽에 와이어프레임, 오른쪽에 디스크립션 열을 두어요.

### 2-1. 프레임 종류

| 종류 | 이름 형식 | 내용 |
| --- | --- | --- |
| 화면 | `CID` (예 : XX-ABC, XX-ABC-01-P), 규칙은 IA 문서 | 와이어프레임 + 디스크립션 |
| 케이스 | `CID/CaseN`, 하위 케이스는 `CID/CaseN-M` (예 : XX-ABC/Case6-1) | 본 화면과 다른 상태·레이아웃·문구 표 |
| 해상도 변형 | `CID_해상도` (예 : XX-ABC\_1280) | 해상도별로 레이아웃이 다른 화면 |
| 공통 | `[공통] 이름` (예 : \[공통\] 유효성 메시지) | 여러 화면이 함께 참조하는 규칙·메시지 |

### 2-2. 헤더 표와 확인 행

디스크립션 열 맨 위에 헤더 표를, 맨 아래에 확인 행을 두어요.

| 칸 | 작성 내용 | 예 |
| --- | --- | --- |
| Ver | 문서 버전 (`v` 없이) | 0.1 |
| Date | 마지막 수정일, `YYYY.MM.DD` | 2026.11.17 |
| CID | 화면 ID | XX-ABC-01-P |
| 작성자 | 작성자 이름 |  |
| 화면 | 화면 이름 (UI 언어 그대로) | Report Preview |
| 경로 | 진입 경로, `>`로 연결. 여러 개면 줄을 나눔 | Report List > Report Preview |
| 확인 행 (하단) | 확인 담당자(예 : Dev, SG)별 확인 일자 | Dev : 확인 일자 : 2026.00.00 |

헤더 Date와 업데이트 표시(13-1)의 날짜는 문서 관리용 형식이라, 화면에 보이는 날짜 형식(7장)과 달라요.

### 2-3. 디스크립션 열 순서

1. 헤더 표
2. `*` 화면 공통 (Default 화면, 표시 형식, 참고 자료(PRD·데이터 정의 링크), 팝업 닫힘)
3. `#` 화면 전체 규칙 (메뉴 접속 권한, 사용자·데이터 조건에 따른 화면 분기)
4. 번호 항목 (화면 위 → 아래, 왼쪽 → 오른쪽)
5. 확인 행

- `*` 박스는 `Default 화면`·`표시`·`참고`를 0단계 제목으로 나열해요. 내용이 약 30줄을 넘으면 `* 공통`, `* 표시`, `* 참고`처럼 박스를 나눠도 돼요.
- 조건에 따라 화면 전체가 달라지면 `#`에 조건과 케이스를 짝지어 써요 (예 : `소속 기관 유형이 A인 경우 : 본 화면`, `그 외 : [Case 9. 제목]`).

## 3. 번호 체계와 배지

디스크립션 번호와 와이어프레임 배지는 반드시 1 : 1로 맞춰요.

| 디스크립션 | 배지 | 쓰임 |
| --- | --- | --- |
| `1` | `1` | 영역 |
| `1.1` | `1-1` | 영역 안의 요소 |
| `1.1.1` | `1-1-1` | 요소를 쪼갠 하위 항목 |
| `*` | 없음 | 화면 공통 |
| `#` | 없음 | 특정 요소가 아닌 화면 전체 규칙 |

- 번호는 화면 위 → 아래, 왼쪽 → 오른쪽 순서예요.
- 케이스 설명 박스는 본 화면의 번호를 그대로 써요.
- 한 항목이 약 30줄을 넘거나 성격이 다른 규칙이 섞이면 하위 번호로 나눠요. 나눌 때는 배지도 함께 추가하고, 상위 항목 `참고`에 하위 번호를 적어요.
- 번호를 바꾸면 그 번호를 부르는 다른 화면의 참조도 함께 바꿔요.

## 4. 디스크립션 구조 : 노출 / 표시 / 참고

번호 항목은 제목 아래에 `노출 → 표시 → 참고` 순서로, 필요한 것만 써요.

| 단계 | 내용 | 서식 |
| --- | --- | --- |
| 0단계 | 항목 제목 (영역명 또는 UI 이름) | 굵게, 불릿 없음 |
| 1단계 | `노출` / `표시` / `참고` | 불릿 |
| 2\~5단계 | 실제 내용 | 불릿, 들여쓰기로 계층 |

- **노출** : 언제, 어떤 상태로 보이고, 사용자가 무엇을 하면 어떻게 되는지 (노출 조건, `Default :`, 활성/비활성, `선택 시,`)
- **표시** : 무엇을 어떤 형식과 문구로 보여 주는지 (값, 형식, `msg :`, `title :`, 목록 값, 정렬, 말줄임)
- **참고** : 더 볼 곳 (케이스, 공통 프레임, \<Common UX>, 다른 화면, 데이터 정의 문서)
- `노출`과 `표시`를 한 제목(`노출/표시`)으로 묶지 않아요. 들여쓰기를 두 단계 이상 건너뛰지 않고, `Default`는 `노출` 아래에 두어요.

**노출에 빠뜨리기 쉬운 것**

| 내용 | 쓰는 법 | 예 |
| --- | --- | --- |
| 권한·대상 조건 | `~ 권한이 있는 경우`, `~ 한정` | 관리자 권한이 있는 경우에만 노출 |
| 진입·재진입 상태 | 최초 진입, 다른 화면에서 돌아올 때, 조건을 바꿀 때 무엇이 유지·초기화되는지 | 다른 화면에서 다시 진입 시, Default로 표시 |
| 선택 제약 | 최소·최대 선택 수 | 최소 1개는 항상 선택된 상태 유지 |
| 해상도별 차이 | `~ 해상도에서` | 1280 해상도에서 Region 컬럼 생략 |
| 동작 없는 요소 | 누를 수 있어 보이지만 동작이 없을 때 | 값이 - 인 경우, 선택 시 반응 없음 |

**표시에 빠뜨리기 쉬운 것**

- **값의 출처** : 관리 화면에서 입력한 값인지, 수신 데이터인지, 계산 값인지 (예 : `관리자 화면에서 입력한 기관명`)
- **계산 값** : 산식, 기준일, 반올림을 함께 (7장)

**입력 필드에 빠뜨리기 쉬운 것**

- 최대 길이 : 단위까지 (예 : `최대 100Byte (공백 포함)`, `최대 50자`)
- 허용 문자 : 영문·숫자·특수문자, 공백 허용 여부
- 대소문자 구분 여부
- 필수 여부 : 필수 항목은 라벨 우측에 `*` 표시
- 중복 검사 : 검사 시점(입력 중 / 포커스 아웃 / 저장 시)과 중복일 때 메시지
- Default : 플레이스 홀더 또는 기본값
- 오류 메시지 : 조건별 `msg :`

```
키워드 검색필드
  • 노출
    • 입력창
      • Default : 플레이스 홀더 노출
        • msg : Please enter a keyword
    • 검색 조건
      • 조회 기준 : 입력값을 포함하는 항목, 대소문자 구분 없음
      • 제시어를 선택하지 않고 [Search] 버튼 선택 시, 입력값으로 조회
  • 참고
    • 검색 : <Common UX (COMM-x-x)>
```

**저장·확인 버튼 흐름** : 입력을 반영하는 버튼(저장, 확인, 등록 등)은 아래 순서로 써요. 버튼 이름은 화면 그대로 써요.

```
[Save] 버튼
  • 노출
    • Default : 비활성화
    • 활성 조건 : 필수 항목 모두 입력, 입력값 변경 있음
    • 선택 시, 유효성 검사
      • 정상 : 저장 → 팝업 닫힘 → 토스트 메시지 노출 → 목록 갱신
        • msg : Saved successfully.
      • 오류 : 오류 항목에 오류 상태 표시
  • 참고
    • 입력 오류 : [Case N. 입력 오류]
    • 토스트 : <Common UX (COMM-x-x)>
```

## 5. 문장 작성 규칙

설명은 한국어 명사형으로 끝내고, 한 줄에 규칙 하나만 써요. 끝에 마침표를 찍지 않아요 (예 : `~ 표시`, `~ 이동`, `~ 초기화`).

| 표현 | 쓰임 | 예 |
| --- | --- | --- |
| `~ 시,` | 동작이 일어날 때 | 선택 시, 상세(XX-ABC-01-P) 팝업 표시 |
| `~일 경우` | 상태 조건 | 조회 결과가 0건일 경우 비활성화 |
| `Default :` | 기본값 | Default : All |
| `→` | 순서가 있는 흐름 | 저장 → 팝업 닫힘 → 토스트 메시지 노출 |
| `:` | 항목과 값, 앞뒤 공백 한 칸 | 등록일 : YYYY-MM-DD |

**동작 용어** : 선택(클릭), 마우스 호버, 포커스 아웃, 펼침/접힘, 말줄임 처리, 활성화/비활성화, 노출/미노출, 반응 없음

**노출과 표시** : 요소(버튼, 영역, 컬럼)가 화면에 보이는지는 `노출 / 미노출`, 값·문구를 보여 주는지는 `표시 / 미표시`로 써요 (예 : `[Capture] 버튼 미노출`, `값 미표시`).

**쓰지 않는 것**

- `표기` → `표시`, `쪽` → `페이지`, `클릭` → `선택`
- `ㄴ`으로 하위 내용 잇기 → 들여쓰기 단계 사용
- `참고)`처럼 짝이 없는 괄호, 중괄호 `{ }`, 괄호 안의 괄호 → `참고` 단계 사용
- 괄호로 붙이는 보충 설명(같은 값, 조건, 이유) → 한 단계 아래 줄로 내림. 짧은 예시 `(예 : …)`와 단위는 괄호 유지
- 콜론을 앞 글자에 붙여 쓰기 (`조건:`) → `조건 :`
- `~와 동일`만 쓰는 참조 → 핵심 한 줄을 쓰고 참조를 붙임

**영문 뒤 조사** : 영문의 마지막 발음 기준으로 붙여요 (예 : `Panel로`, `Lab을`, `Report를`). 이름을 바꿀 때 조사도 함께 확인해요.

## 6. UI 문구 표기

UI에 보이는 이름(버튼, 라벨, 컬럼, 값, 메시지, 툴팁)은 화면에 보이는 언어 그대로 쓰고, 설명 문장은 한국어로 써요.

| 대상 | 규칙 (영문 UI) | 예 |
| --- | --- | --- |
| 버튼, 라벨, 컬럼, 메뉴, 화면명 | Title Case | Print Date, Report History |
| 메시지, 툴팁 문장 | 첫 글자만 대문자, 끝에 마침표 | No data available for the selected conditions. |
| 플레이스 홀더 | 마침표 없음 | Please enter a keyword |
| 약어 | 원래 표기 | ID, PDF |

국문 UI는 화면 문구를 그대로 옮기고, 메시지 끝 마침표만 맞춰요.

**대괄호는 누르는 UI에만** 쓰고, 뒤에 종류를 붙여요.

- `[Save] 버튼`, `[Detail] 탭`, `[All] 라디오`, `[편집] 아이콘`, LNB `[Notice] 메뉴`
- 컬럼명, 라벨, 화면명, 드롭다운 값에는 쓰지 않아요.

**메시지 쓰는 법**

- 일반 : `msg : 문장.`
- 토스트 : `토스트 메시지 노출 - msg : …`
- 플레이스 홀더 : `Default : 플레이스 홀더 노출` 아래에 `msg : …`
- 팝업 : `title :`, `msg :`
- 툴팁 : 툴팁 항목에 `msg : …`

**말줄임 쓰는 법** (표준 문장)

- `최대 N줄 노출, 넘을 경우 말줄임 처리`
- `말줄임 처리된 경우, 마우스 호버 시 툴팁으로 전체 표시`

**영문 뒤 괄호** : 영문 뒤에 오는 괄호는 한 칸 띄어요 (예 : `Region (지역)`). 한글 뒤 괄호는 붙여요 (예 : `미리보기(XX-ABC-01-P)`).

**영문 라벨의 뜻** : 영문 라벨만으로 뜻이 분명하지 않으면 디스크립션에서 괄호로 국문 뜻을 붙여요 (예 : `Hospital (참여 병원 수)`).

**약어와 풀네임**

- 드롭다운 : `약어 (Full name)`
- 리스트 : 약어 표시, 마우스 호버 시 Full name
- 여러 값 연결 : `A + B` (`+` 앞뒤 공백), 순서는 표시 순서와 동일

## 7. 자리 표시자(변수)와 형식

`$…$`는 실제 값으로 바뀌는 자리이고, 같은 대상은 문서 전체에서 하나의 변수 이름만 써요.

| 표기 | 뜻 | 예 |
| --- | --- | --- |
| `$N$` | 정수·건수 | `Printed $N$ times` |
| `$N,NNN$` | 세 자리마다 쉼표 | `Total $N,NNN$` |
| `$NN.N$` | 소수점 첫째 자리 | `$NN.N$%` |
| `$M$` | 개월 수 | `Past $M$ months` |
| `$이름$` | 데이터 값 이름 | `$기관명$`, `$Test Panel$` |
| `$이름 #N$` | 순서가 정해진 값 (값은 변수 표, 10장) | `$항목 유형 #1$`, `$항목 유형 #2$` |

- 한글이 들어간 변수도 값의 이름이에요.
- 날짜·시간 형식에는 `$`를 붙이지 않아요 (`YYYY-MM-DD`, `$YYYY-MM-DD$` 아님).
- 템플릿 바로 아래에 `예 :` 줄로 실제 예시를 붙여요.
- 같은 대상에 다른 이름을 쓰지 않아요 (예 : `$유형 A$`와 `$항목 유형 #1$`을 섞어 쓰지 않음).

| 대상 | 형식 |
| --- | --- |
| 날짜 | YYYY-MM-DD |
| 일시 | YYYY-MM-DD HH:mm:ss |
| 기간 | YYYY-MM-DD \~ YYYY-MM-DD |
| 숫자 | 세 자리마다 쉼표 |
| 퍼센트 | 소수점 첫째 자리 (0% : 0.0%, 0.1% 미만 : <0.1%) |
| 0 | 0 |
| 값 없음 | - |

**데이터가 없을 때** : 건수와 비율(계산 값)을 다르게 표시하고, 화면 `*` 표시에 `예외 표시`로 적어요.

- 검사 데이터 없음 : 건수 `0`, 비율·계산 값 `-`
- API 오류 : 건수와 비율 모두 `-`

**계산 값** : 소수점을 계산해서 보여 주는 값은 반올림을 함께 써요.

- 반올림 : `소수점 둘째 자리에서 반올림`

\<Common UX>에 없는 형식이나 화면별 예외만 각 화면 `*` 표시에 쓰고, 나머지는 \<Common UX>를 참조해요. 두 문서가 다르면 \<Common UX>를 우선하고, \<Common UX>가 없으면 이 장의 표가 기준이에요.

## 8. 참조와 링크

참조는 어느 화면의 무엇인지 바로 보이게 쓰고, 다른 페이지나 다른 파일에 있는 대상은 링크를 걸어요.

| 대상 | 표기 | 예 |
| --- | --- | --- |
| 같은 화면 항목 | `(번호)` | (4.4.2) |
| 다른 화면 항목 | `CID (번호)` | XX-ABC (4.4.2) |
| 다른 화면 | `화면명(CID)` | 상세(XX-ABC-01-P) 팝업 |
| 같은 화면 케이스 | `[Case N. 제목]` | \[Case 1. 검색 결과 없음\] |
| 다른 화면 케이스 | `CID [Case N. 제목]` | XX-ABC \[Case 1. 세션 종료 처리\] |
| 공통 프레임 | `[공통] 이름` | \[공통\] 유효성 메시지 |
| Common UX | 대상 : `<Common UX (COMM-x-x)>` | 검색 : \<Common UX (COMM-5-s)> |
| 데이터 정의 문서 | 파일명 : 문서명 → 항목 → 컬럼명 : | 파일명 : 제품목록 → Analyte Full name → 컬럼명 : Analyte Full Name |

- 케이스 참조의 제목은 케이스 배너 글자와 똑같이 써요.
- Common UX 참조 앞에는 무엇에 대한 규칙인지 대상을 써요 (예 : `페이지네이션 : <Common UX (COMM-5-i)>`). 한 항목에서 Common UX를 여러 개 참조해도 각각이 무엇인지 바로 보이게 하기 위해서예요.
- 다른 화면의 번호를 CID 없이 쓰지 않아요 (예 : `Header (1) : XX-ABC와 동일` → `XX-ABC (1)`).
- 영문 화면명은 괄호 앞을 한 칸 띄워요 (예 : `Report Preview (XX-ABC-01-P)`).

**데이터 정의 문서 참조 쓰는 법** : `파일명 :` 줄에 문서 이름과 링크를 두고, 한 단계 아래에 화면에서 쓰는 항목 이름, 그 아래에 문서의 `컬럼명 :`을 써요.

```
참고
  • 파일명 : 제품목록 (링크)
    • Analyte Full name
      • 컬럼명 : Analyte Full Name
    • Analyte 약어
      • 컬럼명 : Analyte Acronym
```

- 링크는 `파일명 :` 줄의 문서 이름에만 걸어요.
- 항목 이름은 화면에 보이는 이름 그대로, 컬럼명은 문서의 컬럼 이름 그대로 써요.

**링크 (팀 규칙)**

- 같은 파일의 다른 페이지, 또는 다른 파일에 있는 화면·케이스를 참조하면 링크를 걸어요.
- 링크 대상 : 화면은 디스크립션이 있는 기획서 프레임, 케이스는 케이스 프레임, Common UX는 같은 파일에 있는 해당 COMM 프레임만 (다른 파일의 Common UX는 링크 없이 ID만 씀)
- 링크가 걸린 글자는 밑줄로 표시해요.
- 같은 페이지 안의 참조에는 링크를 걸지 않아요.
- 한 화면의 여러 항목에서 다른 페이지의 같은 대상을 참조하면, 나오는 곳마다 모두 링크를 걸어요.
- 화면 `*` 공통에 링크를 건 문서(예 : PRD)는 항목에서 링크 없이 이름으로만 가리켜요 (예 : `지점 리스트, 정렬 : PRD 참고`). 그 화면 `*` 공통에 없으면 항목에 링크를 걸어요.
- 프레임을 다른 파일로 옮기면, 원래 파일에 남은 대상을 가리키는 참조에 링크를 다시 걸어요.

## 9. 케이스 작성

본 화면과 다른 상태·레이아웃은 케이스 프레임으로 빼고, 케이스 설명에는 본 화면과 달라지는 점만 써요.

**케이스로 뺄지 판단하는 순서**

1. 새 화면인가 : 진입 경로가 다르거나 팝업·별도 페이지로 열리면 새 CID(IA 문서)로 만들고, 케이스로 쓰지 않아요.
2. 와이어프레임을 다시 그려야 이해되는가 : 영역의 구성·배치가 바뀌거나 두 영역 이상이 함께 바뀌면 케이스로 빼요.
3. 둘 다 아니면 디스크립션에 한 줄로 써요 (예 : 버튼 비활성, 마우스 호버, 문구만 바뀌는 메시지, \<Common UX>의 표준 동작).

**케이스로 확인할 것** : 화면마다 아래 구분을 훑어보고, 해당하는 상태를 케이스로 만들지 디스크립션 한 줄로 쓸지 위 판단 순서로 정해요.

| 구분 | 케이스로 만들 것 | 디스크립션 한 줄로 충분한 것 |
| --- | --- | --- |
| 권한·조건 | 권한 없음, 사용자·데이터 조건에 따라 화면 구성이 다른 경우 | 버튼 하나만 숨김·비활성 |
| 상태 변형 | 보기 전환(예 : 차트 ↔ 테이블), 펼친 상태(드롭다운·제시어), 편집·선택 모드 | 마우스 호버, 선택 상태 표시 |
| 경계값 | 목록이 기준 개수 미만·초과, 긴 값 때문에 배치가 바뀌는 경우 | 말줄임만 생기는 경우 |
| 흐름 | 단계가 있는 입력, 진행 중 → 완료 | 토스트 메시지 |
| 빈 상태 | 데이터 일부·전체 없음, 검색·필터 결과 없음, 처음 사용(등록 0건) | 값 하나가 없을 때 - 표시 |
| 오류 | 조회 실패(API 오류), 저장·전송 실패, 세션 종료 | 입력 필드 하나의 유효성 메시지 |
| 산출물 | 다운로드 파일, 인쇄물, 발송 메일 | 파일명 규칙 |
| 문서용 표 | 문구 표·변수 표(10장) | - |

**묶기와 나누기**

- 한 요소가 이어서 바뀌는 상태는 한 케이스에 나란히 둬요 (예 : 검색 중 → 제시어 선택 → 검색 결과 없음).
- 서로 다른 조건은 케이스를 나눠요 (예 : 데이터 0건과 권한 없음).
- 데이터 없음과 API 오류는 표시 값이 달라서 케이스를 나눠요 (건수 0 / -).

**이름과 번호**

- 배너 : `Case N. 제목` (Case와 숫자 사이 띄어쓰기)
- 프레임 : `CID/CaseN`, 프레임 1개에 케이스 1개, 본 화면 프레임 밖에 둠
- 번호 : 화면마다 1부터, 아래 케이스 순서대로 매김
- 하위 케이스 : 한 화면(예 : 탭)의 상태 변형은 `Case 6-1`, `Case 6-2`
- 개발 전달 후에는 케이스 번호를 바꾸지 않아요. 새 케이스는 뒤에 붙여요.

**케이스 순서** : 한 화면의 케이스는 아래 기준을 차례로 적용해 번호를 매겨요.

1. 케이스가 바꾸는 본 화면 항목 중 가장 앞 번호 순서. `#` 화면 전체 조건에 따른 케이스가 가장 먼저
2. 같은 항목이면 넓은 범위 먼저 : 영역 전체 → 하위 요소 (예 : (3) 리스트 전체 → (3.2) 컬럼 하나)
3. 같은 범위면 정상 흐름 먼저, 예외는 뒤 : 상태 변형 → 경계값 → 흐름 → 빈 상태(일부 → 전체) → 오류
4. 산출물 예시는 그것을 만드는 항목(예 : 다운로드 버튼) 자리에, 문구 표·변수 표는 맨 뒤

개발 전달 전에 케이스를 추가하거나 지우면 이 순서대로 번호를 다시 매기고, 케이스 배너·프레임 이름·참조를 함께 고쳐요.

**설명 박스**

```
검색 결과 없음
  • 화면 : (3) 검색 결과가 0건인 경우
  • (3) 리스트
    • 컬럼 헤더 유지, 리스트 영역 가운데에 안내 문구 표시
      • msg : No results found.
```

- 설명 박스의 번호와 케이스 배지는 본 화면 항목 번호를 그대로 써요.
- 첫 줄 `화면 :`에 어떤 조건의 화면인지 써요.
- 같은 내용을 두 케이스에 복사하지 않고 참조해요 (예 : 세션 종료는 XX-ABC \[Case 1. 세션 종료 처리\]에만).

**본 화면 디스크립션에 케이스 참조 쓰는 법**

- 위치 : 케이스에서 달라지는 항목의 `참고` 아래에 써요. 화면 전체가 조건에 따라 바뀌면 `#`에, 기본 상태가 다르면 `*`에 써요.
- 형식 : `조건 : [Case N. 제목]`. 조건은 케이스 설명 박스 첫 줄 `화면 :`과 같은 말로 써요.
- 여러 항목이 같은 케이스로 바뀌면 그 항목들의 `참고`에 모두 적어요.
- 케이스를 지우거나 제목을 바꾸면 참조한 곳도 함께 고쳐요.

```
리스트
  • 노출
    • …
  • 참고
    • 검색 결과가 0건인 경우 : [Case 1. 검색 결과 없음]
    • 테이블 보기 : [Case 2. 테이블 보기]
```

## 10. 문구 표와 변수 표

조건마다 문장이 달라지는 문구는 케이스의 표가 기준이고, 디스크립션에는 규칙과 참조만 써요.

**표 구성**

| 표 | 열 | 내용 |
| --- | --- | --- |
| 표 1. 변수 | 조건 \| `$변수 #1$` \| `$변수 #2$` … | 조건(예 : 검사, 플랜)별로 변수에 들어가는 값 |
| 표 2. 문구 템플릿 | 구분 \| 항목 \| 문구 | 자리별 문장, 변수는 `$…$` |

- 같은 문장을 조건별 열로 반복하지 않아요. 바뀌는 부분만 표 1의 변수로 빼요.
- 변수 뒤 조사가 값마다 달라지면, 조사까지 포함한 표기 열을 표 1에 따로 둬요 (예 : `$항목 이름 #1$` = `호흡기 바이러스가` / `폐렴원인균이`).
- 건수에 따라 단수·복수가 달라지면 행을 나눠요 (0건 / 1건 / 2건 이상).
- 문구를 바꾸면 표를 먼저 고치고, 디스크립션·와이어프레임 예시를 표에 맞춰요.
- 표 설명 박스에 `문구의 기준은 이 표`를 적어요.

## 11. Common UX와 화면 디스크립션의 관계

같은 규칙은 한 곳에만 두고, 나머지는 참조해요.

| 내용 | 쓰는 곳 |
| --- | --- |
| 범용 UI 패턴 (팝업, 드롭다운, 페이지네이션, 날짜·숫자 표기) | \<Common UX> 참조 |
| 화면에서만 보이는 것, 화면별 예외 | 화면 디스크립션 |

- \<Common UX>에 있는 규칙은 화면에 다시 쓰지 않고 참조만 해요.
- 화면마다 다른 부분은 화면에 남겨요 (예 : 정렬의 첫 기준).

## 12. 미확정 표시

확정되지 않은 내용은 1-1의 미확정 표시 색으로 쓰고, 정해지면 검은색으로 바꿔요.

- 범례 : `■ : 미확정된 정책, 수정 가능` (기획서 상단)
- 디스크립션에서는 줄 끝에 `(확인 필요)`를 붙이고 미확정 색으로 써요.
- 기획서에 근거가 없는 내용(추정·제안)을 넣을 때도 미확정 색으로 구분해요.

## 13. 변경 관리와 전달 전 정리

수정한 화면은 그날 헤더 Date를 갱신하고, 개발 전달 전에 아래를 정리해요.

- **이름 변경** : 용어·문구를 바꾸면 디스크립션, 와이어프레임, 케이스, 문구 표를 함께 바꿔요. 디자인 섹션은 별도로 디자이너에게 전달해요.
- **숨긴 레이어** : 기획서 프레임의 필요 없는 숨긴 레이어는 지워요. 디자인·프로토타입 화면은 건드리지 않아요.
- **같은 이름 프레임** : 예전 초안은 지우거나 기획서 영역 밖으로 옮겨요.
- **변경 이력** : 버전마다 13-1 업데이트 표시 규칙으로 기록해요 (`[버전_날짜 : 내용]`).
- **번호** : 전달 후에는 항목·케이스 번호를 바꾸지 않아요.
- **공유 파일** : 다른 파일로 공유할 때 페이지 간 참조에 링크가 걸려 있는지 확인해요.

### 13-1. 업데이트 표시

바뀐 내용은 화면 옆 라벨, 디스크립션 표시, Revision History 표 세 곳에 함께 남겨요.

| 위치 | 방법 |
| --- | --- |
| 화면 옆 라벨 | 프레임 오른쪽 위 바깥에 `Update history` 컴포넌트, 버전 변형(v0.1\~v1.0) 선택 |
| 디스크립션 | 항목 제목 아래 빨간 안내 + 항목 배경 |
| 이전 문구 | 회색 취소선으로 남기고, 새 문구는 굵게 |
| Revision History 표 | 화면 묶음 위에 표, 최신 버전이 위 |

**디스크립션 표시**

- 안내 : `[v버전_MM/DD : 변경 내용]`, 글자색 #FF0000, 굵게, 불릿 없이 항목 제목 바로 아래 (예 : `[v0.2_11/16 : 검색 조건 추가]`)
- 배경 : 디스크립션 인스턴스에 #FF0000, 불투명도 10%
- 지운 줄 : 회색 취소선으로 원래 자리에 남김. 원문은 이전 버전에서 가져오고 다시 쓰지 않아요.
- 일부만 바뀐 줄 : 같은 줄 안에서 바뀐 부분만 회색 취소선으로 남기고, 바로 뒤에 새 내용을 써요. 줄의 나머지 글자는 굵게 (예 : `[주간 실적][병원 참여 현황] 탭`에서 `[주간 실적]`만 취소선)
- 통째로 바뀐 줄 : 이전 줄 전체를 회색 취소선으로 남기고, 새 줄을 굵게
- 마침표·띄어쓰기 같은 표기 차이는 변경으로 표시하지 않아요. `(확인 필요)` 해제는 취소선 없이 그 줄만 굵게
- 새로 생긴 줄 : 굵게
- 케이스 번호나 항목 제목이 바뀐 경우도 일부만 바뀐 줄과 같이 바뀐 부분만 취소선으로 표시해요 (예 : Case 3이 Case 4가 되면 숫자 3만 취소선).

**라벨 작성**

- 첫 줄 : `v0.2 update : 11/16` (최초는 `v0.1 : 11/16`)
- `[번호] 변경 내용` 아래에 세부 내용 (예 : `[4] 검색 조건 추가` → `Default : 전체 → Default : 최근 3개월`)
- 여러 항목이 같은 변경이면 번호를 이어 붙여요 (예 : `[*][2][3] 메뉴 이름 변경`).
- 버전이 여러 개면 오래된 버전이 위로 쌓아요.
- 케이스가 바뀌면 케이스 프레임 옆에도 붙여요.

**Revision History 표**

- 열 : 개발 반영 / 버전 / 요청인 / 컨펌 요청 / 통합 공유 / 변경사항 / 페이지 / 담당자 / Design 수정·반영
- 행 : 화면·케이스 단위 (예 : `XX-ABC`, `XX-ABC/Case6`), 최신 버전이 위
- 변경사항 : 라벨과 같은 `[번호] 변경 내용` 형식

**주의**

- 기록 시작 : 기획서를 나누거나 개발에 전달한 시점부터
- 라벨은 프레임 바깥에 둬요. 프레임 폭을 넓히면 오른쪽 고정(MAX) 요소가 밀려 겹칠 수 있어요.

## 14. 검수 체크리스트

개발 전달 전에 화면마다 확인해요.

- [ ] 디스크립션 번호와 배지가 1 : 1로 맞는가 (케이스 배지 포함)
- [ ] 참조한 번호와 케이스가 실제로 있는가 (케이스 제목 글자까지)
- [ ] 다른 화면 참조에 CID가 붙어 있는가
- [ ] 다른 페이지·다른 파일 참조에 링크와 밑줄이 있는가
- [ ] 항목이 `노출 / 표시 / 참고` 구조인가, 들여쓰기를 건너뛰지 않았는가
- [ ] 진입·재진입 상태, 권한 조건, 동작 없는 요소를 빠뜨리지 않았는가
- [ ] 입력 필드의 길이·문자·중복 규칙과 저장 버튼의 활성 조건·정상·오류 흐름을 썼는가
- [ ] UI 이름은 화면 언어 그대로, 설명은 한국어인가
- [ ] 버튼은 `[이름] 버튼`, 메시지는 `msg :`, 플레이스 홀더는 마침표 없이 썼는가
- [ ] `:` 앞뒤 공백, `참고)`·`ㄴ`·`표기`가 남아 있지 않은가
- [ ] 변수 이름이 문서 전체에서 하나로 통일됐는가, 날짜 형식에 `$`를 붙이지 않았는가
- [ ] 계산 값에 산식·기준일·반올림이 있는가
- [ ] 날짜·숫자·퍼센트 형식과 `+` 앞뒤 공백이 규칙대로인가
- [ ] 이름을 바꾼 용어가 남아 있지 않은가 (수정된 조사, 오타 포함)
- [ ] 미확정 내용이 미확정 색과 `(확인 필요)`로 구분됐는가
- [ ] 한 항목이 30줄을 넘지 않는가
- [ ] 괄호로 붙인 보충 설명을 아래 줄로 내렸는가
- [ ] 영문 뒤 괄호를 한 칸 띄웠는가
- [ ] 케이스 프레임 1개에 케이스 1개를 두었는가
- [ ] 케이스 번호가 케이스 순서 규칙대로인가
- [ ] 데이터 없음·API 오류의 건수·비율 표시가 규칙대로인가
- [ ] 헤더 Date를 갱신했는가
- [ ] 필요 없는 숨긴 레이어를 지웠는가
- [ ] 바뀐 항목에 업데이트 표시(라벨, 빨간 안내, 배경, 취소선, Revision History)를 했는가
