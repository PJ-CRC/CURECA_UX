# STAgora 작업규칙

기획 업무(정책서, 화면설계서 등)를 AI와 함께 진행할 때 반드시 지켜야 하는 규칙을 섹션별로 나눠 정리한 작업규칙이다. 기준 파일은 `STAgora 작업규칙_v0.1_261110.md`이다.

> 아래 **최상위 원칙**은 다른 어떤 원칙보다 우선한다.

### 문서 구성

| 섹션 | 내용 |
|---|---|
| 1. 최상위 원칙 | 다른 모든 원칙보다 우선하는 5가지 원칙 |
| 2. 변경 이력 | 이 문서의 버전 · 작업자 · 변경 내용 |
| 3. 작업의 흐름 | 공통 자료 · 화면설계서(SB) · 언어셋 작업 방식 |
| 4. 서비스별 화면 언어 · 디스크립션 언어 | 서비스별 기본 화면 언어, 디스크립션 언어 |
| 5. 작업 유형 | 대분류 · 중분류별 설명과 사전 확인 · 승인 |
| 6. 화면설계서 Figma 수정 시 규칙 | 변경 표기 형식 · 색 · 크기 |
| 7. 작업 흐름 요약 | 요청 판단 흐름 |
| 8. 확인 요청이 필요한 경우 | 상황별 AI의 행동 |

## 1. 최상위 원칙

다른 어떤 원칙보다 우선하는 5가지 원칙을 정의한다.

### 1-1. 정책이 화면설계서(SB)보다 우선한다

정책이 먼저 수립되고, 수립된 정책을 SB에 적용한다. (정책 → SB 순서)

| 항목 | 규칙 |
|---|---|
| 적용 순서 | 정책 수립 → SB 적용 |
| 정책 위배 시 | **작업을 바로 진행하지 않고** 작업 요청자에게 먼저 확인을 요청한 뒤 진행 |
| 확인 요청에 포함할 내용 | 위배되는 정책 항목, 위배되는 이유, 가능한 대안 |

### 1-2. 관련 정책이 없는 경우

요청한 작업과 관련된 정책이 없으면 SB만 작업해도 무방하다.

| 항목 | 규칙 |
|---|---|
| 모니터링 1 | 요청한 작업이 **서비스 전체에 영향**을 미치는가? |
| 모니터링 2 | 다른 화면 · 서비스에서도 동일하게 적용되어야 하는 내용인가? |
| 정책 개설이 필요하다고 판단되면 | **작업 완료 시 사용자에게 별도로 알린다.** |
| 정책 신설 제안에 포함할 내용 | 필요 사유, 영향 범위 |

### 1-3. 정책이 변경된 경우: 공통 자료는 임시 정책으로 등록, SB는 즉시 수정하지 않는다

정책 변경 요청 시 **공통 자료(정책서 등)의 확정 내용을 바로 수정하지 않고, 임시 정책으로 등록**한다. (상세 절차는 「3. 작업의 흐름」 참고)

| 대상 | 규칙 | 이유 |
|---|---|---|
| 공통 자료 | 확정 내용을 바로 수정하지 않고 임시 정책으로 등록 | 모두 함께 확인한 뒤 승인 |
| SB | **바로 수정하지 않음** | 서비스별로 정책(SB 변경 사항)을 적용하는 시기가 다름 |
| 대신 제공할 것 | 정책 변경으로 영향받는 SB의 위치를 리스트업하여 사용자가 직접 체크하게 함 | |

사용자가 체크한 항목에 대해서만 SB 수정을 진행한다.

**영향도 리스트 작성 형식 (예시)**

| 체크 | 서비스 | 문서/화면 | 위치(화면 ID/번호) | 영향받는 내용 | 변경 필요 사항 |
|:---:|---|---|---|---|---|
| ☐ | | | | | |

### 1-4. 모든 문서는 변경 시 히스토리를 남긴다

대상은 SB, 정책서 등 **모든 문서**이다.

| 구분 | 항목 | 설명 |
|---|---|---|
| 필수 | 버전명 | 버전 관리 방식은 문서마다 규칙이 다를 수 있으므로 해당 문서의 기존 규칙을 따른다 |
| 필수 | 작업자 | |
| 필수 | 변경 내용 | |
| 선택 | 비고 등 | |

**히스토리 작성 형식 (예시)**

| 버전 | 작업자 | 변경 내용 | 비고 |
|---|---|---|---|
| | | | |

### 1-5. 논리적 오류 또는 공통 UX 위배 시 반드시 확인 요청

아래 경우에는 임의로 판단해 진행하지 말고, **반드시 사용자에게 확인을 요청**한 뒤 진행한다.

| 해당 경우 | 확인 요청에 포함할 내용 |
|---|---|
| 작업자가 요청한 내용이 **논리적으로 맞지 않는 경우** | 문제라고 판단한 부분, 근거(논리), 제안하는 대안 |
| 우리가 정한 **공통 UX 기준에 위배**되는 방식으로 적용하려는 경우 | 문제라고 판단한 부분, 근거(공통 UX 기준), 제안하는 대안 |

## 3. 작업의 흐름

작업 대상 문서는 공통 자료 · 화면설계서(SB) · 언어셋 3가지로 구분하며, 문서 종류에 따라 작업 방식이 다르다.

### 3-1. 공통 자료

작업의 기준을 마련해 주는 문서이며, 바로 수정하지 않는다.

| 항목 | 내용 |
|---|---|
| 정의 | 작업규칙, 정책서, UX 가이드, 용어집, Common UX 등 **작업의 기준**을 마련해 주는 문서 |
| 원칙 | 바로 수정하지 않는다 |

**변경 절차**

```
임시 정책으로 등록
   ↓
모두가 함께 확인
   ↓
SB 영향도 리스트업 후 확인
   ↓
[승인]
   ↓
[승인] 후에만 SB 반영
```

| 단계 | AI의 행동 | 비고 |
|---|---|---|
| ① 임시 정책 등록 | 변경안을 확정 내용과 구분하여 "임시 정책"으로 등록 | 공통 자료 확정 내용은 수정하지 않음 |
| ② 전체 확인 | 변경 내용을 모두가 확인할 수 있도록 정리하여 공유 | |
| ③ SB 영향도 확인 | 영향받는 SB 리스트업 (최상위 원칙 3의 형식) → 사용자 확인 | |
| ④ 승인 | 승인 여부 확인 | **승인 전에는 SB를 수정하지 않는다** |
| ⑤ SB 반영 | 승인된 항목만 SB에 반영 + 히스토리 기록 | |

### 3-2. 화면설계서 (SB)

개별 화면에 대한 정의를 담은 문서이다.

| 항목 | 내용 |
|---|---|
| 정의 | 개별 화면에 대한 정의를 담은 문서. 와이어프레임과 이에 대한 기능 설명이 주로 구성된다 |
| 성격 | 각 작업자가 **실제로 반영해야 하는 문서** |
| 작업 기준 | 반드시 승인된 정책(공통 자료)을 기준으로 작업한다 |
| 히스토리 | 변경 시 히스토리를 남긴다 (최상위 원칙 4) |

### 3-3. 언어셋

서비스에서 운영 중인 7개 언어 리스트를 반영한 문서이다.

| 항목 | 내용 |
|---|---|
| 정의 | 서비스에서 운영 중인 **7개 언어** 리스트를 반영한 문서 |
| 운영 언어(7개) | 한국어, 영어, 독일어, 스페인어, 이탈리아어, 프랑스어, 포르투갈어 |
| 반영 시점 | SB 변경으로 **UI 또는 문구가 변경**되면, 변경해야 할 언어셋을 함께 반영한다 |
| 확인 | SB를 수정할 때마다 언어셋 영향 여부를 확인한다 (신규 · 수정 · 삭제 문구, 7개 언어 모두 대상) |
| 히스토리 | 변경 시 히스토리를 남긴다 (최상위 원칙 4) |

## 4. 서비스별 화면 언어 · 디스크립션 언어

화면에 표시되는 문구와 디스크립션에 쓰는 언어를 정의한다.

### 4-1. 서비스별 기본 화면 언어

화면(와이어프레임)에 표시되는 UI · 문구는 서비스별 기본 언어로 작성한다.

| 서비스 | 기본 화면 언어 |
|---|---|
| STAgora 임상의 | 한국어 |
| STAgora 검사실 | 영어 |
| GMCS | 영어 |
| Admin | 영어 |
| 초대시스템 | 영어 |
| Secure Uploader | 영어 |

### 4-2. 디스크립션 언어

| 구분 | 규칙 |
|---|---|
| 디스크립션 | **기본 화면 언어와 상관없이 모든 디스크립션은 한국어로 작성한다** |
| 예시 | GMCS(기본 화면 언어: 영어)의 화면 문구는 영어, 해당 화면의 디스크립션은 한국어 |

## 5. 작업 유형

작업을 대분류 · 중분류로 나누고 사전 확인 · 승인 조건을 정의한다.

| 대분류 | 중분류 | 설명 | 사전 확인·승인 |
|---|---|---|---|
| **1. 공통 자료 변경** | 임시 정책 등록 | 정책서, UX 가이드, 용어집, Common UX, 작업규칙의 변경안을 임시 정책으로 등록 | 모두 확인 필요 |
| | 임시 정책 확정/폐기 | 승인 결과에 따라 정식 반영하거나 폐기 | [승인] 필수 |
| | 정책 신설 제안 | 관련 정책이 없는데 서비스 전체에 영향을 주는 경우 별도 정책 개설을 제안 | 사용자에게 알림 |
| **2. 화면설계서(SB) 수정** | 화면 수정 | 개별 화면의 신규/변경/삭제. 와이어프레임과 기능 설명(디스크립션) 수정 | 정책 위배 시 확인 요청 |
| | 승인된 공통 정책 반영 | [승인]된 정책을 영향도 리스트의 체크 항목에 따라 SB에 반영 | [승인] 이후에만 가능 |
| | 정책 없는 화면 작업 | 관련 정책이 없어 SB만 작업. 서비스 전체 영향 여부 모니터링 포함 | 영향 있으면 알림 |
| **3. 언어셋 반영** | 문구 추가/수정/삭제 | SB의 UI·문구 변경에 따른 언어셋 변경 | SB 변경 시 동반 |
| | 7개 언어 반영 | 한국어, 영어, 독일어, 스페인어, 이탈리아어, 프랑스어, 포르투갈어 전체 반영 | |
| | 용어 변경에 따른 일괄 변경 | 용어집이 변경되어 여러 화면의 문구를 한꺼번에 바꾸는 경우 | 용어집 [승인] 이후 |
| **4. 검토·분석** | SB 영향도 리스트업 | 정책 변경 시 영향받는 화면/위치를 체크 가능한 리스트로 정리 | 사용자 체크 필요 |
| | 정책 위배 검토 | 요청 작업이 정책서에 위배되는지 확인 | 위배 시 작업 보류 |
| | 논리·공통 UX 검토 | 요청이 논리적 오류이거나 공통 UX에 위배되는지 확인 | 해당 시 확인 요청 |
| **5. 문서 관리** | 변경 히스토리 기록 | 버전명, 작업자, 변경 내용 필수 기록. 비고는 선택 | 모든 문서 변경 시 |
| | 버전 관리 | 문서별 버전 규칙에 따라 버전 업데이트 | 사용자 요청 시에만 변경 |

> 한 요청이 여러 유형에 걸칠 수 있다. 예) 용어 변경 요청: 1(임시 정책 등록) → 4(영향도 리스트업) → 승인 → 2(SB 반영) → 3(언어셋) → 5(히스토리)

## 6. 화면설계서 Figma 수정 시 규칙

작업 이전 내용과 변경된 내용을 반드시 구분할 수 있도록 히스토리를 남긴다. 문서 히스토리 표 기록과 별개로 Figma 화면 위에도 변경 표기를 남긴다.

### 6-1. 화면 수정 시

변경한 화면 요소 근처에 아래 형식의 표기를 남긴다.

| 항목 | 규칙 |
|---|---|
| 표기 형식 | `[$버전명$/$변경된 내용$]` |
| 텍스트 컬러 | `#ff0000` |
| 폰트 크기 | `12` |
| 위치/크기 조절 | 다른 화면 요소를 가리지 않는 선에서 유동적으로 조절 가능 |

### 6-2. 디스크립션 수정 시

| 항목 | 규칙 |
|---|---|
| 표기 위치 | 해당 디스크립션 **타이틀 옆** |
| 표기 형식 | `[$버전명$/$변경된 내용$]` |
| 텍스트 컬러 | `#ff0000` |
| 폰트 크기 | `10` |
| 디스크립션 박스 배경 | 해당 넘버의 **디스크립션 박스 전체**에 bg 컬러 추가: `#ff0000`, 투명도 `10%` |

### 6-3. 공통 사항

| 항목 | 규칙 |
|---|---|
| 값 치환 | `$버전명$`, `$변경된 내용$`은 실제 값으로 치환하여 기재한다 (예: `[v0.2/버튼 문구 변경]`) |
| 구분 | 변경 표기는 작업 전 내용과 변경 후 내용이 구분되도록 남기며, 임의로 삭제하지 않는다 |
| 문서 히스토리 | Figma 표기와 별개로 문서 히스토리(버전명, 작업자, 변경 내용)도 반드시 기록한다 |

## 7. 작업 흐름 요약

요청을 받았을 때 판단하는 순서를 한눈에 정리한다.

```
작업 요청
  │
  ├─ 관련 정책이 있는가?
  │    ├─ 있음 ─ 정책에 위배되는가?
  │    │          ├─ 위배 ─→ 작업 중단, 요청자에게 확인 요청
  │    │          └─ 부합 ─→ 정책에 따라 SB 작업
  │    └─ 없음 ─→ SB 작업 + 서비스 전체 영향 여부 모니터링
  │                 └─ 정책 개설 필요 시 사용자에게 별도 알림
  │
  ├─ 정책 변경 요청인가?
  │    └─ 임시 정책 등록 → 전체 확인 → SB 영향도 리스트업 → [승인] → SB 반영
  │       (승인 전 SB는 수정하지 않음)
  │
  ├─ 요청이 논리적 오류 / 공통 UX 위배인가?
  │    └─ 작업 중단, 요청자에게 확인 요청
  │
  ├─ SB 변경으로 UI/문구가 바뀌는가?
  │    └─ 7개 언어 언어셋 반영 필요 여부 확인 및 함께 반영
  │
  └─ 문서 변경 시: 히스토리(버전명, 작업자, 변경 내용) 기록
```

## 8. 확인 요청이 필요한 경우

상황별로 AI가 어떻게 행동하는지 한눈에 정리한다.

| 상황 | AI의 행동 |
|---|---|
| 요청이 정책서에 위배됨 | 작업 보류 → 확인 요청 |
| 요청이 논리적으로 맞지 않음 | 작업 보류 → 확인 요청 |
| 요청이 공통 UX에 위배됨 | 작업 보류 → 확인 요청 |
| 관련 정책이 없고 서비스 전체 영향 가능성 있음 | SB 작업 진행 + 정책 개설 필요성 별도 안내 |
| 공통 자료(정책서 등) 변경 요청 | 바로 수정하지 않고 임시 정책 등록 → 확인 → SB 영향도 리스트 → [승인] 후 SB 반영 |
| SB 변경으로 UI/문구가 바뀜 | 언어셋(7개 언어) 변경 사항 함께 반영 |
