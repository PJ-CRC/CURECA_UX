# 1. 최상위 원칙

다른 어떤 원칙보다 우선하는 5가지 원칙을 정의한다.

## 1-1. 정책이 화면설계서(SB)보다 우선한다

정책이 먼저 수립되고, 수립된 정책을 SB에 적용한다. (정책 → SB 순서)

| 항목 | 규칙 |
|---|---|
| 적용 순서 | 정책 수립 → SB 적용 |
| 정책 위배 시 | **작업을 바로 진행하지 않고** 작업 요청자에게 먼저 확인을 요청한 뒤 진행 |
| 확인 요청에 포함할 내용 | 위배되는 정책 항목, 위배되는 이유, 가능한 대안 |

## 1-2. 관련 정책이 없는 경우

요청한 작업과 관련된 정책이 없으면 SB만 작업해도 무방하다.

| 항목 | 규칙 |
|---|---|
| 모니터링 1 | 요청한 작업이 **서비스 전체에 영향**을 미치는가? |
| 모니터링 2 | 다른 화면 · 서비스에서도 동일하게 적용되어야 하는 내용인가? |
| 정책 개설이 필요하다고 판단되면 | **작업 완료 시 사용자에게 별도로 알린다.** |
| 정책 신설 제안에 포함할 내용 | 필요 사유, 영향 범위 |

## 1-3. 정책이 변경된 경우: 공통 자료는 임시 정책으로 등록, SB는 즉시 수정하지 않는다

정책 변경 요청 시 **공통 자료(정책서 등)의 확정 내용을 바로 수정하지 않고, 임시 정책으로 등록**한다. (상세 절차는 「3. 작업의 흐름」 참고)

| 대상 | 규칙 | 이유 |
|---|---|---|
| 공통 자료 | 확정 내용을 바로 수정하지 않고 임시 정책으로 등록 | 모두 함께 확인한 뒤 승인 |
| SB | **바로 수정하지 않음** | 서비스별로 정책(SB 변경 사항)을 적용하는 시기가 다름 |
| 대신 제공할 것 | 정책 변경으로 영향받는 SB의 위치를 리스트업하여 사용자가 직접 체크하게 함 | |

사용자가 체크한 항목에 대해서만 SB 수정을 진행한다.

**영향도 리스트 작성 형식 (예시)**

| 체크 | 서비스 | 문서/화면 | 위치(화면 ID/번호) | 영향받는 내용 | 변경 필요 사항 |
|:---:|---|---|---|---|---|
| ☐ | | | | | |

## 1-4. 모든 문서는 변경 시 히스토리를 남긴다

대상은 SB, 정책서 등 **모든 문서**이다.

| 구분 | 항목 | 설명 |
|---|---|---|
| 필수 | 버전명 | 버전 관리 방식은 문서마다 규칙이 다를 수 있으므로 해당 문서의 기존 규칙을 따른다 |
| 필수 | 작업자 | |
| 필수 | 변경 내용 | |
| 선택 | 비고 등 | |

**히스토리 작성 형식 (예시)**

| 버전 | 작업자 | 변경 내용 | 비고 |
|---|---|---|---|
| | | | |

## 1-5. 논리적 오류 또는 공통 UX 위배 시 반드시 확인 요청

아래 경우에는 임의로 판단해 진행하지 말고, **반드시 사용자에게 확인을 요청**한 뒤 진행한다.

| 해당 경우 | 확인 요청에 포함할 내용 |
|---|---|
| 작업자가 요청한 내용이 **논리적으로 맞지 않는 경우** | 문제라고 판단한 부분, 근거(논리), 제안하는 대안 |
| 우리가 정한 **공통 UX 기준에 위배**되는 방식으로 적용하려는 경우 | 문제라고 판단한 부분, 근거(공통 UX 기준), 제안하는 대안 |
